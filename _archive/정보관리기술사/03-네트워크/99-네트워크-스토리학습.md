# 네트워크 스토리 학습 — 브라우저의 주문이 서버에 도착하기까지

> [네트워크 전체 개념지도](00-전체.md)의 통신 기반·주소·경로·전송·품질·운영을 하나의 주문 요청으로 이해한다. 패킷 전달은 실제 처리 흐름으로, 무선·SDN·NFV·IoT는 **병렬적인 환경·설계 관점**으로 구분한다.

## 1. 주소창에서 주문 버튼을 누르면 — 계층과 통신 기반

고객이 휴대폰 브라우저에서 주문 버튼을 눌렀다. 화면의 데이터가 멀리 있는 서버까지 어떻게 갈까?

**질문: 애플리케이션이 서버까지 데이터를 직접 전송할까?**

응용 계층의 HTTP 요청은 Transport, Network, Link, Physical 계층의 기능을 활용한다. 각 계층은 맡은 문제를 해결하고, 전송할 때 상위 데이터에 필요한 Header를 붙이는 **Encapsulation**이 일어난다.

~~~text
Application → HTTP 요청의 의미
Transport   → Port / TCP·UDP / 종단 전달 특성
Network     → IP 주소 / 다른 네트워크까지 경로
Link        → 같은 링크 영역에서 Frame 전달
Physical    → 실제 신호·매체
~~~

**질문: 데이터가 전송되려면 무조건 하나의 선을 독점해야 할까?**

그렇지 않다. 매체와 신호, 변조, 다중화는 제한된 통신 자원을 통해 데이터를 전달하는 기반 기술이다. OSI 7계층과 TCP/IP 모델은 역할을 설명하는 추상화이며 모든 실제 프로토콜이 계층에 딱 하나씩 대응하지는 않는다.

## 2. 같은 Wi-Fi에서 공유기까지 — MAC·Switch·VLAN

휴대폰은 먼저 같은 링크의 다음 장치로 데이터를 보낸다.

**질문: IP 주소만 알면 같은 링크에서 Frame을 어떻게 보낼지까지 해결될까?**

같은 L2 영역에서는 MAC 주소와 Link 계층 전달이 중요하다. Switch는 MAC 주소를 기반으로 Frame을 전달하고 VLAN은 L2 영역을 논리적으로 구분할 수 있다. IPv4에서는 ARP가 IP 주소에 대응하는 링크 주소를 알아내는 데 사용된다.

**질문: MAC 주소로 인터넷 반대편의 서버까지 직접 찾아갈 수 있을까?**

아니다. MAC 기반 전달은 링크 범위의 문제다. 다른 네트워크로 나가려면 IP 주소와 라우팅이 필요하다.

## 3. 다른 네트워크까지 — IP·Subnet·Gateway·Routing

목적지 서버는 다른 네트워크에 있다.

**질문: 휴대폰이 서버까지 연결된 모든 장치를 미리 알아야 할까?**

그럴 필요는 없다. IP 주소와 Subnet으로 목적지가 같은 네트워크에 있는지 판단하고, 다른 네트워크라면 Gateway를 통해 보낸다. Router는 라우팅 테이블을 참고해 다음 홉을 결정한다.

**질문: Router는 어떤 기준으로 다음 경로를 선택할까?**

경로 정보와 정책에 따른다. RIP·OSPF·BGP 등은 라우팅 정보를 교환하는 대표적인 프로토콜이지만 같은 환경에서 같은 역할을 수행하는 것은 아니다. [통신·주소·경로 지도](01-통신-주소-경로.md)와 [라우팅 원리](라우팅-원리와-RIP-OSPF-BGP.md)에서 비교한다.

## 4. 서버 컴퓨터에 도착했는데 어느 프로그램으로? — Port·TCP/UDP·Socket

패킷이 목적지 서버에 도착했다. 서버에서는 주문 처리와 다른 서비스들이 함께 실행 중이다.

**질문: IP 주소만으로 어느 프로세스에 데이터를 전달할지 알 수 있을까?**

IP는 주로 호스트·인터페이스까지의 전달을 다루고, **Port**는 전송 계층에서 응용 종단을 식별하는 데 쓰인다. TCP는 연결·순서·신뢰성 등을 제공하고 UDP는 단순한 데이터그램 전달을 제공한다.

**질문: TCP가 신뢰성을 제공하면 애플리케이션의 모든 주문 오류도 자동으로 해결될까?**

아니다. TCP는 바이트 전달 특성을 제공할 뿐 주문 중복 처리 같은 업무 규칙은 애플리케이션이 관리해야 한다. **Socket API**는 애플리케이션이 OS의 네트워크 기능을 사용하는 접점이다. 실제 Server I/O와 Event Loop는 [Socket·Server I/O 보충학습](_보충학습/Socket-서버-IO.md)에서 살펴본다.

## 5. 주문 요청이 늦거나 사라진다 — 오류·흐름·혼잡 제어

주문 요청이 지연되거나 전송 중 일부 데이터가 손실됐다.

**질문: 데이터 손실, 느린 수신자, 혼잡한 네트워크는 같은 문제일까?**

아니다.

- **오류 제어:** 손실·오류를 검출하고 필요한 경우 복구하는 문제
- **흐름 제어:** 송신자가 수신자의 처리 능력을 초과하지 않도록 하는 문제
- **혼잡 제어:** 네트워크 내부에 과도한 트래픽이 몰리는 것을 제어하는 문제

**질문: 패킷 손실이 적으면 사용자가 반드시 빠르다고 느낄까?**

그렇지는 않다. 지연·지터·처리량과 응용의 특성도 중요하다. **QoS**는 네트워크 서비스 품질을, **QoE**는 사용자가 체감하는 경험 품질을 보는 관점이다. [전송·품질·운영 지도](02-전송-품질-운영.md)에서 차이를 복원한다.

## 6. 고객이 이동 중이라면 — 무선·이동성

고객이 Wi-Fi를 사용하다 다른 액세스 포인트 쪽으로 이동한다.

**질문: 무선 매체는 유선과 무엇이 다를까?**

여러 장치가 공유하는 무선 매체의 간섭·충돌 회피 문제가 중요하다. WLAN은 CSMA/CA 같은 접근 제어를 활용하고, 이동 시 Roaming·Handover가 연결 유지와 관련된다. 이는 기본 IP·전송 계층의 대체물이 아니라 무선 환경에서 추가로 고려하는 문제다. [무선·이동 지도](03-무선-이동.md)를 참고한다.

## 7. 서비스를 운영하면서 네트워크를 어떻게 관리할까?

서비스가 느려졌다. 운영자는 서버 문제인지 링크 문제인지 경로 문제인지 알아야 한다.

**질문: 네트워크가 연결되어 있다는 사실만으로 운영 상태를 충분히 알 수 있을까?**

아니다. NMS/SNMP 등으로 장치·링크 상태를 관측하고 장애와 성능을 관리한다.

**질문: SDN·NFV·VPN·CDN·IoT는 차례대로 발전하는 네트워크 기술일까?**

아니다. **SDN**은 제어 구조, **NFV**는 네트워크 기능 구현의 가상화, **VPN**은 논리적 사설 연결, **CDN**은 콘텐츠 전달 최적화, **IoT/센서 네트워크**는 자원 제약이 있는 연결 환경이다. HTTP·RTP/RTCP 같은 응용 프로토콜도 별도 역할을 가진다. [서비스·가상화·제약환경 지도](04-서비스-가상화-제약환경.md)에서 병렬 관점을 확인한다.

## 8. 다시 요청 한 건을 따라가기

~~~text
브라우저 주문 요청
  ↓ 응용 데이터
TCP/UDP + Port → 종단 전달 특성·프로세스 식별
  ↓
IP + Routing → 다른 네트워크까지 경로
  ↓
MAC + Link → 현재 링크의 다음 장치
  ↓
신호·매체 → 실제 전송

[전 과정] 오류·흐름·혼잡 제어 / QoS·QoE / 운영·관측
[병렬 관점] 무선·이동 / VPN·SDN·NFV / CDN·IoT
~~~

**스스로 설명해 보기:** MAC과 IP는 왜 둘 다 필요한가? IP와 Port는 무엇을 다르게 식별하는가? TCP의 신뢰성이 업무 중복 처리를 해결하지 못하는 이유는? 흐름 제어와 혼잡 제어는 누구를 보호하는가? SDN·NFV는 왜 필수 전달 단계가 아닌가?
