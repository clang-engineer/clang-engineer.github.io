# 제어·품질·운영 개념지도

**핵심 질문: 데이터를 어떻게 안정적으로 전송하고, 서비스 품질과 망 상태를 관리하는가?**

## 0. 전체 구조 — 제어·품질·운영

```text
제어·품질·운영
│
├─ ① 전송 제어 — 어떻게 안정적으로 전달하는가?
│  ├─ 전송·확인 → Stop-and-Wait / Sliding Window
│  ├─ 오류 제어 → 검출(Checksum·CRC) / 복구(ARQ·FEC)
│  ├─ 흐름 제어 → 수신자 한계(rwnd)
│  └─ 혼잡 제어 → 네트워크 한계(cwnd)
│
├─ ② 네트워크·서비스 품질 — 무엇을 측정·관리·평가하는가?
│  ├─ NP  → 네트워크 성능: Throughput / Delay / Jitter / Loss
│  ├─ QoS → 서비스 품질: 분류·속도·큐 관리
│  │  └─ IntServ(Flow 예약) / DiffServ(Class 차등 처리)
│  └─ QoE → 사용자 경험: 영향 요인 / MOS·객관적 평가
│
└─ ③ 운영 관리 — 네트워크 상태를 어떻게 관측하는가?
   ├─ NMS → 중앙 관리 시스템
   └─ SNMP → 관리 정보 교환 프로토콜
      └─ Polling / Trap·Inform
```

①은 전송 신뢰성과 전송량 제어, ②는 품질, ③은 운영 관리 관점이다. 세 가지는 실제 패킷의 처리 순서가 아니다. 상위 [네트워크 전체 개념지도](00-전체.md)의 신뢰성·품질·운영 축을 확대한다.

## 1. 전송 제어 — 전송 방식과 제어 목적을 구분

TCP(Transmission Control Protocol)·UDP(User Datagram Protocol)와 연결 관리의 기본 구조는 [네트워크 전달 구조](01-네트워크-전달-구조.md)에서 다룬다. 여기서는 안정적인 전송을 위한 제어 원리에 집중한다.

### 전송·확인과 오류 복구

```text
전송·확인 메커니즘
├─ Stop-and-Wait → 하나 전송 → ACK(Acknowledgment) 확인 → 다음 전송
└─ Sliding Window → 여러 데이터 연속 전송
                    → ACK에 따라 전송 가능 범위 이동

오류 제어
├─ 검출 → CRC(Cyclic Redundancy Check)/FCS(Frame Check Sequence)(링크 프레임) · Checksum(TCP/UDP)
└─ 복구
   ├─ ARQ(Automatic Repeat reQuest)(재전송)
   │  ├─ Stop-and-Wait
   │  ├─ Go-Back-N
   │  └─ Selective Repeat
   └─ FEC(Forward Error Correction)(중복 정보로 수신 측 정정)
```

**Stop-and-Wait와 Sliding Window는 전송·확인 메커니즘의 비교축**이고, Stop-and-Wait·Go-Back-N·Selective Repeat는 **ARQ의 대표적인 프로토콜 유형**이기도 하다. 서로 배타적인 분류가 아니다. Sliding Window는 미확인 데이터를 여러 개 전송해 효율을 높이며, 오류 복구와 흐름 제어에도 활용된다. 그 자체가 혼잡 제어 알고리즘은 아니다.

**ARQ는 특정 계층 전용이 아닌 재전송 원리**다. 일반적인 유선 Ethernet 스위치는 CRC 오류 프레임을 폐기하지만 L2 ARQ를 수행하지 않으며, TCP는 종단 간 ACK와 재전송으로 손실을 복구한다. TCP를 고전적인 ARQ 세 유형 중 하나와 그대로 동일시하지 않는다. FEC는 재전송 없이 수신 측에서 정정한다.

### 흐름 제어와 혼잡 제어 — 무엇을 보호하는가?

```text
                  TCP 송신자
                      │
              미확인 데이터 전송량
                      │
                min(rwnd, cwnd)
                 /          \
                /            \
       rwnd (수신자가 광고)   cwnd (송신자가 관리)
       수신 버퍼 여유         혼잡 신호로 망 여유 추정
            │                    │
         흐름 제어             혼잡 제어
       수신자 과부하 방지     네트워크 과부하 완화
```

| 구분 | 흐름 제어(Flow Control) | 혼잡 제어(Congestion Control) |
|---|---|---|
| 문제 | 수신자가 처리하지 못함 | 네트워크가 전송량을 감당하지 못함 |
| 기준 | `rwnd`(Receive Window) | `cwnd`(Congestion Window) |
| 판단 주체 | 수신자가 수용 가능량 광고 | 송신자가 혼잡 신호를 관찰 |
| TCP 적용 | Sliding Window의 수신 측 한계 | Sliding Window의 혼잡 측 한계 |

TCP의 미확인 데이터량은 일반적으로 두 윈도우의 최솟값에 의해 제한된다. Stop-and-Wait에서도 수신자 한계를 고려할 수 있지만, **실제 TCP는 Sliding Window와 `rwnd`·`cwnd`를 함께 사용**한다.

### TCP 혼잡 제어 — 증가와 손실 대응

```text
cwnd로 네트워크 수용량 탐색 (고전적인 TCP Reno)
│
├─ 증가
│  ├─ Slow Start         → 작은 창에서 빠르게 증가
│  └─ Congestion Avoidance → ssthresh(Slow Start Threshold) 이후 완만히 증가
│
└─ 손실 대응
   ├─ Fast Retransmit → 중복 ACK 등으로 Timeout 전 재전송
   ├─ Fast Recovery   → 창을 줄이고 전송 회복
   └─ Timeout         → 더 보수적으로 Slow Start 재진입
```

네 기법은 경쟁하는 대안이 아니라 **Reno 계열에서 증가와 손실 대응을 구성하는 동작**이다. Fast Retransmit은 손실 복구이면서 혼잡 제어 과정에도 참여한다. 현대 TCP의 모든 구현이 Reno와 동일하게 동작하는 것은 아니다.

## 2. 네트워크·서비스 품질 — NP·QoS·QoE는 서로 다른 관점

```text
같은 네트워크 서비스의 세 관점
│
├─ NP (Network Performance) — 네트워크 자체의 성능
│  └─ Bandwidth / Throughput / Delay / Jitter / Loss
│
├─ QoS (Quality of Service) — 서비스 요구에 맞는 품질 제공·관리
│  ├─ 기법: Classification·Marking / Policing·Shaping / Queueing·Scheduling
│  └─ 모델: IntServ(Integrated Services)(Flow별 예약) / DiffServ(Differentiated Services)(Class별 차등 처리)
│
└─ QoE (Quality of Experience) — 사용자가 실제 경험하는 품질
   ├─ 영향: 네트워크 / 서버·응용·코덱·단말 / 사용자 환경
   └─ 평가: 주관적 MOS(Mean Opinion Score) / 객관적 서비스 지표·추정 모델
```

| 관점 | 핵심 질문 | 영상통화 예 |
|---|---|---|
| **NP** | 네트워크가 얼마나 잘 전달하는가? | 지연·지터·손실은 얼마인가? |
| **QoS** | 서비스에 필요한 품질을 어떻게 제공하는가? | 음성 패킷을 우선 처리하는가? |
| **QoE** | 사용자는 실제로 어떤 품질을 경험하는가? | 음성이 끊기거나 영상이 멈추는가? |

이들은 **측정 → 관리 → 체감 평가**로 생각을 확장할 수 있지만 반드시 순서대로 실행되는 단계는 아니다. Bandwidth는 링크의 전송 용량이고 Throughput은 실제 전달량이다. QoS는 회선 용량 자체를 늘리지 않으며, QoE는 서버·응용·단말 등에도 영향을 받으므로 QoS만으로 결정되지 않는다.

### QoS의 기법과 서비스 모델은 다른 분류축

```text
QoS 기법 — 패킷을 어떻게 처리할까?
├─ Classification / Marking → 분류하고 등급 표시(예: DSCP(Differentiated Services Code Point))
├─ Policing / Shaping       → 초과분 폐기·재표시 / 버퍼링 후 전송
└─ Queueing / Scheduling   → 대기열 관리 / 전송 순서·비율 결정

QoS 모델 — 어떤 단위로 관리할까?
├─ IntServ → Flow마다 예약(RSVP(Resource Reservation Protocol)) · 세밀한 보장 / 상태 관리 부담
└─ DiffServ → Class별 차등 처리(DSCP·PHB(Per-Hop Behavior)) · 확장성 / 개별 보장 한계
```

**Policing은 초과 트래픽을 즉시 제한**하고 **Shaping은 대기시켜 속도를 완만하게 만든다**(버퍼가 가득 차면 손실 가능). IntServ는 흐름별 상태를 유지하므로 확장성 부담이 크고, DiffServ는 등급별로 처리해 대규모 네트워크에 유리하다. DSCP로 등급을 표시하더라도 PHB 정책과 네트워크 용량이 뒷받침되지 않으면 품질이 자동 보장되지는 않는다.

```text
트래픽 증가 → Queue 증가 → Delay / Jitter / Loss 악화
│
├─ TCP 송신자 → cwnd로 송신량 조절 (혼잡 제어)
└─ 네트워크 장비 → 등급·속도·큐 정책 적용 (QoS)
                         │
                         └─ QoE에 영향 (단독 결정은 아님)
```

## 3. 운영 관리 — NMS와 SNMP

```text
NMS (Network Management System) — 중앙 관리 시스템
│
└─ SNMP (Simple Network Management Protocol) — 관리 정보 교환
   ├─ 구조 → Manager / Agent · MIB(Management Information Base) / OID(Object Identifier)
   ├─ Polling → Manager가 Agent를 주기적으로 조회
   └─ Trap / Inform → Agent가 Manager에게 이벤트 통지
```

**Manager**는 관리 요청을 보내고 **Agent**는 장비의 관리 값을 제공한다. MIB는 현재 측정값을 저장하는 DB가 아니라 객체 정의이며, OID는 그 객체를 식별한다. **Polling**은 Manager의 주기적 조회, **Trap**은 Agent의 비요청 통지, **Inform**은 수신 확인을 받는 통지다. 조회와 이벤트 통지는 상호 보완적이다.

**NMS의 관리 범위(FCAPS):** Fault(장애) · Configuration(구성) · Accounting(사용량·과금) · Performance(성능) · Security(보안). SNMP는 이를 위한 대표 정보 교환 수단 중 하나이지 NMS 전체 기능과 동일하지 않다.

→ [NMS와 SNMP](NMS와-SNMP.md): 관리 구성·메시지 상세
