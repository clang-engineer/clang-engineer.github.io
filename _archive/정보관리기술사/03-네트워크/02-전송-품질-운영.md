# 전송·품질·운영 개념지도

**핵심 질문: IP가 목적지 호스트까지 전달한 데이터를 어떻게 프로세스에 넘기고, 안정적으로 전송하며, 서비스 품질과 망 상태를 관리하는가?**

## 0. 전체 구조 — 종단 통신·품질·운영

```text
종단 통신·품질·운영
│
├─ ① 종단 통신과 전송 제어 — 안정적으로 누구에게 전달하는가?
│  ├─ 전달 종단 → IP(Host) / Port(프로세스 통신 종단) / Socket
│  ├─ 프로토콜 → TCP(연결·신뢰성) / UDP(비연결·데이터그램)
│  └─ 전송 제어
│     ├─ 연결 관리 → 3-Way Handshake / FIN 종료
│     ├─ 전송·확인 → Stop-and-Wait / Sliding Window
│     ├─ 오류 제어 → 검출(Checksum·CRC) / 복구(ARQ·FEC)
│     ├─ 흐름 제어 → 수신자 한계(rwnd)
│     └─ 혼잡 제어 → 네트워크 한계(cwnd)
│
├─ ② 네트워크·서비스 품질 — 무엇을 측정·관리·평가하는가?
│  ├─ NP  → 네트워크 성능: Throughput / Delay / Jitter / Loss
│  ├─ QoS → 서비스 품질: 분류·속도·큐 관리
│  │  └─ IntServ(Flow 예약) / DiffServ(Class 차등 처리)
│  └─ QoE → 사용자 경험: 영향 요인 / MOS·객관적 평가
│
└─ ③ 운영 관리 — 네트워크 상태를 어떻게 관측하는가?
   ├─ NMS → 중앙 관리 시스템
   └─ SNMP → 관리 정보 교환 프로토콜
      └─ Polling / Trap·Inform
```

**①은 종단 통신 안에 전송 제어가 포함되는 관계**이고, ②는 품질을 바라보는 관점, ③은 운영 관측이다. 세 가지는 실제 패킷의 처리 순서가 아니다. 상위 [네트워크 전체 개념지도](00-전체.md)에서 종단 통신은 통신 구조에, 제어·품질·운영은 관리 관점에 각각 연결되는 **횡단 지도**다.

## 1. 종단 통신과 전송 제어 — Host에서 프로세스까지

```text
송신 Application
      │ Socket API
      ▼
TCP / UDP — Port로 통신 종단 구분
      │
      ▼
IP — 목적지 Host까지 전달
      │
      ▼
수신 Host → Port → 수신 Application
```

| 비교축 | TCP | UDP |
|---|---|---|
| 전달 형태 | 연결지향 바이트 스트림 | 비연결 데이터그램 |
| 순서·손실 복구 | 순서 보장, ACK·재전송 | 기본 제공하지 않음 |
| 흐름·혼잡 제어 | 기본 제공 | 기본 제공하지 않음 |
| 오류 검출 | Checksum | Checksum |
| 대표 선택 | 파일 전송 등 순서·신뢰성 중시 | 실시간 미디어 등 응용별 제어 중시 |

**TCP(Transmission Control Protocol, 전송 제어 프로토콜)**는 연결 상태와 신뢰성 있는 바이트 스트림을 관리한다. **UDP(User Datagram Protocol, 사용자 데이터그램 프로토콜)**는 연결 상태 없이 데이터그램을 전달한다. **IP(Internet Protocol, 인터넷 프로토콜)**는 호스트 간 주소 지정·전달을 맡는다. **Socket API(Application Programming Interface, 응용 프로그래밍 인터페이스)**는 응용이 OS의 통신 기능을 호출하는 접점이다.

**Port는 호스트 안의 통신 종단을 구분**하고, Socket API(Application Programming Interface)는 응용이 OS 네트워크 스택을 사용하는 접점이다. TCP는 3-Way Handshake로 연결을 수립하고 FIN 기반으로 정상 종료한다. UDP는 기본 기능이 단순하지만 항상 더 빠르다는 뜻은 아니다. UDP 위에서도 **QUIC(표준상 별도의 확장형 정식 명칭 없이 사용하는 프로토콜 이름)**처럼 신뢰성·혼잡 제어를 구현할 수 있으며 HTTP/3가 그 예다.

**HTTP(Hypertext Transfer Protocol, 하이퍼텍스트 전송 프로토콜)**의 Persistent Connection/Keep-Alive와 응용의 Connection Pool은 **이미 수립한 TCP 연결을 상위 계층에서 재사용**하는 개념이다. TCP의 연결 관리 자체와 구분한다.

→ [TCP 연결·종료·흐름·혼잡 제어](TCP-연결-종료-흐름-혼잡제어.md): 연결 상태·윈도우·혼잡 알고리즘 · [Socket·Server I/O](_보충학습/Socket-서버-IO.md): 응용과 OS의 접점

### 전송 제어 — 전송 방식과 제어 목적을 구분

### 전송·확인과 오류 복구

```text
전송·확인 메커니즘
├─ Stop-and-Wait → 하나 전송 → ACK 확인 → 다음 전송
└─ Sliding Window → 여러 데이터 연속 전송
                    → ACK에 따라 전송 가능 범위 이동

오류 제어
├─ 검출 → CRC/FCS(링크 프레임) · Checksum(TCP/UDP)
└─ 복구
   ├─ ARQ(재전송)
   │  ├─ Stop-and-Wait
   │  ├─ Go-Back-N
   │  └─ Selective Repeat
   └─ FEC(중복 정보로 수신 측 정정)
```

**Stop-and-Wait와 Sliding Window는 전송·확인 메커니즘의 비교축**이고, Stop-and-Wait·Go-Back-N·Selective Repeat는 **ARQ의 대표적인 프로토콜 유형**이기도 하다. 서로 배타적인 분류가 아니다. Sliding Window는 미확인 데이터를 여러 개 전송해 효율을 높이며, 오류 복구와 흐름 제어에도 활용된다. 그 자체가 혼잡 제어 알고리즘은 아니다.

**CRC(Cyclic Redundancy Check, 순환 중복 검사)**는 오류 검출 계산 방식이고, **FCS(Frame Check Sequence, 프레임 검사 시퀀스)**는 링크 프레임에 실리는 검사 필드다. **ARQ(Automatic Repeat reQuest, 자동 재전송 요구)**는 특정 계층 전용이 아닌 재전송 원리**다. 일반적인 유선 Ethernet 스위치는 CRC 오류 프레임을 폐기하지만 L2 ARQ를 수행하지 않으며, TCP는 종단 간 ACK(Acknowledgment, 수신 확인)와 재전송으로 손실을 복구한다. TCP를 고전적인 ARQ 세 유형 중 하나와 그대로 동일시하지 않는다. FEC(Forward Error Correction, 전방 오류 정정)는 재전송 없이 중복 정보로 수신 측에서 오류를 정정한다.

### 흐름 제어와 혼잡 제어 — 무엇을 보호하는가?

```text
                  TCP 송신자
                      │
              미확인 데이터 전송량
                      │
                min(rwnd, cwnd)
                 /          \
                /            \
       rwnd (수신자가 광고)   cwnd (송신자가 관리)
       수신 버퍼 여유         혼잡 신호로 망 여유 추정
            │                    │
         흐름 제어             혼잡 제어
       수신자 과부하 방지     네트워크 과부하 완화
```

| 구분 | 흐름 제어(Flow Control) | 혼잡 제어(Congestion Control) |
|---|---|---|
| 문제 | 수신자가 처리하지 못함 | 네트워크가 전송량을 감당하지 못함 |
| 기준 | `rwnd`(Receive Window) | `cwnd`(Congestion Window) |
| 판단 주체 | 수신자가 수용 가능량 광고 | 송신자가 혼잡 신호를 관찰 |
| TCP 적용 | Sliding Window의 수신 측 한계 | Sliding Window의 혼잡 측 한계 |

**rwnd(Receive Window, 수신 윈도우)**는 수신자가 광고하는 수용 가능량이고, **cwnd(Congestion Window, 혼잡 윈도우)**는 송신자가 네트워크 혼잡을 추정해 관리하는 전송 한계다. **ssthresh(Slow Start Threshold, 느린 시작 임계값)**는 혼잡 윈도우 증가 방식을 전환하는 기준이다.

TCP의 미확인 데이터량은 일반적으로 두 윈도우의 최솟값에 의해 제한된다. Stop-and-Wait에서도 수신자 한계를 고려할 수 있지만, **실제 TCP는 Sliding Window와 `rwnd`·`cwnd`를 함께 사용**한다.

### TCP 혼잡 제어 — 증가와 손실 대응

```text
cwnd로 네트워크 수용량 탐색 (고전적인 TCP Reno)
│
├─ 증가
│  ├─ Slow Start         → 작은 창에서 빠르게 증가
│  └─ Congestion Avoidance → ssthresh 이후 완만히 증가
│
└─ 손실 대응
   ├─ Fast Retransmit → 중복 ACK 등으로 Timeout 전 재전송
   ├─ Fast Recovery   → 창을 줄이고 전송 회복
   └─ Timeout         → 더 보수적으로 Slow Start 재진입
```

네 기법은 경쟁하는 대안이 아니라 **Reno 계열에서 증가와 손실 대응을 구성하는 동작**이다. Fast Retransmit은 손실 복구이면서 혼잡 제어 과정에도 참여한다. 현대 TCP의 모든 구현이 Reno와 동일하게 동작하는 것은 아니다.

## 2. 네트워크·서비스 품질 — NP·QoS·QoE는 서로 다른 관점

```text
같은 네트워크 서비스의 세 관점
│
├─ NP (Network Performance) — 네트워크 자체의 성능
│  └─ Bandwidth / Throughput / Delay / Jitter / Loss
│
├─ QoS (Quality of Service) — 서비스 요구에 맞는 품질 제공·관리
│  ├─ 기법: Classification·Marking / Policing·Shaping / Queueing·Scheduling
│  └─ 모델: IntServ(Flow별 예약) / DiffServ(Class별 차등 처리)
│
└─ QoE (Quality of Experience) — 사용자가 실제 경험하는 품질
   ├─ 영향: 네트워크 / 서버·응용·코덱·단말 / 사용자 환경
   └─ 평가: 주관적 MOS / 객관적 서비스 지표·추정 모델
```

| 관점 | 핵심 질문 | 영상통화 예 |
|---|---|---|
| **NP** | 네트워크가 얼마나 잘 전달하는가? | 지연·지터·손실은 얼마인가? |
| **QoS** | 서비스에 필요한 품질을 어떻게 제공하는가? | 음성 패킷을 우선 처리하는가? |
| **QoE** | 사용자는 실제로 어떤 품질을 경험하는가? | 음성이 끊기거나 영상이 멈추는가? |

**NP(Network Performance, 네트워크 성능)**는 망 자체의 전달 능력, **QoS(Quality of Service, 서비스 품질)**는 서비스별 품질과 이를 관리하는 정책, **QoE(Quality of Experience, 경험 품질)**는 사용자가 실제 느끼는 품질을 뜻한다. **MOS(Mean Opinion Score, 평균 의견 점수)**는 이용자 평가를 평균한 대표적인 주관적 품질 척도다.

이들은 **측정 → 관리 → 체감 평가**로 생각을 확장할 수 있지만 반드시 순서대로 실행되는 단계는 아니다. Bandwidth는 링크의 전송 용량이고 Throughput은 실제 전달량이다. QoS는 회선 용량 자체를 늘리지 않으며, QoE는 서버·응용·단말 등에도 영향을 받으므로 QoS만으로 결정되지 않는다. MOS(Mean Opinion Score)는 대표적인 주관적 평가 점수다.

### QoS의 기법과 서비스 모델은 다른 분류축

```text
QoS 기법 — 패킷을 어떻게 처리할까?
├─ Classification / Marking → 분류하고 등급 표시(예: DSCP)
├─ Policing / Shaping       → 초과분 폐기·재표시 / 버퍼링 후 전송
└─ Queueing / Scheduling   → 대기열 관리 / 전송 순서·비율 결정

QoS 모델 — 어떤 단위로 관리할까?
├─ IntServ → Flow마다 예약(RSVP) · 세밀한 보장 / 상태 관리 부담
└─ DiffServ → Class별 차등 처리(DSCP·PHB) · 확장성 / 개별 보장 한계
```

**Policing은 초과 트래픽을 즉시 제한**하고 **Shaping은 대기시켜 속도를 완만하게 만든다**(버퍼가 가득 차면 손실 가능). IntServ는 흐름별 상태를 유지하므로 확장성 부담이 크고, DiffServ는 등급별로 처리해 대규모 네트워크에 유리하다. **IntServ(Integrated Services, 통합 서비스)**는 개별 흐름별 자원 예약 방식이며 **RSVP(Resource Reservation Protocol, 자원 예약 프로토콜)**를 예약 신호에 활용한다. **DiffServ(Differentiated Services, 차등 서비스)**는 트래픽을 등급별로 처리한다. **DSCP(Differentiated Services Code Point, 차등 서비스 코드값)**는 IP 헤더의 등급 표시이고, **PHB(Per-Hop Behavior, 홉별 처리 동작)**는 라우터가 그 등급에 적용하는 처리 정책이다.

```text
트래픽 증가 → Queue 증가 → Delay / Jitter / Loss 악화
│
├─ TCP 송신자 → cwnd로 송신량 조절 (혼잡 제어)
└─ 네트워크 장비 → 등급·속도·큐 정책 적용 (QoS)
                         │
                         └─ QoE에 영향 (단독 결정은 아님)
```

## 3. 운영 관리 — NMS와 SNMP

```text
NMS (Network Management System) — 중앙 관리 시스템
│
└─ SNMP (Simple Network Management Protocol) — 관리 정보 교환
   ├─ Polling → Manager가 Agent를 주기적으로 조회
   └─ Trap / Inform → Agent가 Manager에게 이벤트 통지
```

**NMS(Network Management System, 네트워크 관리 시스템)**는 장비 상태를 중앙에서 관측·관리하는 시스템이고, **SNMP(Simple Network Management Protocol, 단순 네트워크 관리 프로토콜)**는 관리 정보를 교환하는 프로토콜이다. **OID(Object Identifier, 객체 식별자)**는 관리 항목을 구분하는 식별자다. **Polling**은 Manager가 Agent를 조회하는 방식이고, **Trap**은 Agent의 비요청 통지, **Inform**은 수신 확인을 받는 통지다. 조회와 이벤트 통지는 상호 보완적이다.

→ [NMS와 SNMP](NMS와-SNMP.md): 관리 구성·메시지 상세
