# 전송·품질·운영 개념지도

**핵심 질문: 목적지 호스트에 도착한 데이터를 프로그램에 전달하고, 손실·과부하·품질·운영 문제를 어떻게 해결하는가?**

## 1. 한눈에 보는 구조

```text
종단 통신과 품질 관리
│
├─ ① 프로세스까지 전달 — 누구에게 넘기는가?
│  └─ Port / TCP·UDP / Socket API
│
├─ ② 데이터 전달 제어 — 무엇을 보장·조절하는가?
│  ├─ 연결 관리 → 3-Way Handshake / 종료
│  ├─ 오류·손실 → ACK / ARQ / FEC
│  ├─ 수신자 처리 한계 → 흐름 제어(rwnd)
│  └─ 네트워크 수용 한계 → 혼잡 제어(cwnd)
│
├─ ③ 서비스 품질 — 트래픽을 어떻게 다르게 취급하는가?
│  └─ QoS → 분류·표시·속도 정책·큐·스케줄링
│     └─ QoE → 사용자 체감 품질
│
└─ ④ 운영 관측 — 망 상태를 어떻게 확인하는가?
   └─ NMS / SNMP → Polling / Trap·Inform
```

네 가지는 **기능별 관점**이다. 연결 종료 뒤에 오류·흐름·혼잡 제어를 수행한다는 순서가 아니다.

## 2. 종단 통신 — IP 다음에 Port가 필요한 이유

```text
IP → 목적지 Host
  ↓
Port → Host 안의 통신 종단
  ↓
Application ↔ Socket API ↔ OS Network Stack
```

- **TCP(Transmission Control Protocol):** 연결 상태를 관리하고 순서 있는 신뢰성 높은 바이트 스트림 제공.
- **UDP(User Datagram Protocol):** 연결 상태 없이 데이터그램 단위 전송.
- **API(Application Programming Interface):** 응용 프로그램이 통신 기능을 사용하는 접점.

TCP의 **연결 관리**(3-Way Handshake, FIN 기반 종료)와 **전송 중 제어**(오류·흐름·혼잡)는 구분한다.

→ [TCP 연결·종료·흐름·혼잡 제어](TCP-연결-종료-흐름-혼잡제어.md) · [Socket·Server I/O](_보충학습/Socket-서버-IO.md)

## 3. 신뢰성 — 무엇을 검출하고 누가 복구하는가?

```text
오류 검출 → CRC(Cyclic Redundancy Check) 계산
             └─ FCS(Frame Check Sequence)에 검사값
오류 복구
├─ ARQ(Automatic Repeat reQuest) — ACK·Timeout 기반 재전송
│  ├─ Stop-and-Wait
│  ├─ Go-Back-N
│  └─ Selective Repeat
└─ FEC(Forward Error Correction) — 중복 정보로 수신 측 정정

전송 속도 제어
├─ Flow Control → rwnd(Receive Window) — 수신자 한계
└─ Congestion Control → cwnd(Congestion Window) — 망 혼잡
```

TCP 송신자는 **수신자가 받을 수 있는 양(rwnd)**과 **망 혼잡을 고려한 전송 한계(cwnd)**를 함께 지킨다. 일반적으로 전송 가능한 미확인 데이터 양은 두 창의 최솟값에 의해 제한된다. 수신 버퍼가 부족하면 흐름 제어가, 네트워크가 혼잡하면 혼잡 제어가 송신량을 줄이는 이유다.

ACK는 Acknowledgment(수신 확인)다. CRC·ARQ·FEC는 반드시 한 계층에서 순차 실행되는 기술이 아니다. 일반적인 유선 Ethernet 스위치는 CRC 오류 프레임을 버리지만 L2 ARQ를 수행하지 않는다. TCP는 종단 간 재전송으로 손실에 대응한다.

## 4. 품질 — TCP 혼잡 제어와 QoS는 다르다

```text
트래픽 증가 → Queue 증가 → Delay / Jitter / Loss 증가
│
├─ 개별 TCP 송신자 → 혼잡 제어
└─ 네트워크 정책 → QoS(Quality of Service)
   ├─ Classification / Marking
   ├─ Policing / Shaping
   └─ Queueing / Scheduling
        ↓
   QoE(Quality of Experience) — 사용자 체감 품질
```

QoS는 회선 용량 자체를 늘리지 않는다. QoE에는 네트워크뿐 아니라 서버·응용·코덱·단말 상태도 영향을 준다. HTTP(Hypertext Transfer Protocol)의 Persistent Connection/Keep-Alive와 응용의 Connection Pool은 **TCP 연결을 상위 계층에서 재사용**하는 방식이다.

→ [QoS와 QoE](QoS와-QoE.md)

## 5. 운영 — NMS와 SNMP의 역할

```text
NMS(Network Management System) — 중앙 관리 시스템
└─ SNMP(Simple Network Management Protocol) — 관리 정보 교환
   ├─ Polling: Manager → Agent, 주기적 조회
   └─ Trap / Inform: Agent → Manager, 이벤트 통지
```

NMS는 시스템이고 SNMP는 프로토콜이다. OID(Object Identifier)는 관리 객체 식별자다. Polling과 이벤트 통지는 대체가 아니라 보완 관계다.

→ [NMS와 SNMP](NMS와-SNMP.md)

**복습 기준:** TCP/UDP → 오류·흐름·혼잡 제어 → QoS/QoE → NMS/SNMP의 차이를 설명한다. 상태 전이·알고리즘·SNMP PDU 세부는 별도 학습으로 내려간다.
