# 네트워크 전달 구조 개념지도

**핵심 질문: 데이터는 계층을 거쳐 현재 링크를 지나 다른 네트워크의 목적지 응용까지 어떻게 도달하는가?**

## 0. 한눈에 보는 구조

```text
네트워크 전달
│
├─ ① 계층화 — 역할 분리
│  └─ OSI / TCP-IP · 캡슐화 · SAP/SDU/PDU
│
├─ ② 링크 계층 — 현재 링크에서 전달
│  ├─ Ethernet / NIC / MAC / ARP / L2 Switch
│  ├─ 오류 검출 → CRC / FCS
│  ├─ 공유 매체 접근 → CSMA/CD · CSMA/CA
│  └─ 망 분리 → VLAN / Access·Trunk
│
├─ ③ 네트워크 계층 — 주소와 경로
│  ├─ 주소 관리 → Subnet / CIDR / VLSM / DHCP
│  │  └─ IPv4 부족 → 사설 IP / NAT·PAT / IPv6
│  └─ 경로 선택 → Routing / Forwarding
│     ├─ Unicast → Static / RIP / OSPF / BGP
│     └─ Multicast → Group / IGMP·MLD / PIM·RPF
│
└─ ④ 종단·응용 통신
   ├─ 전송 → TCP / UDP / Port · 연결 관리
   └─ 응용과 접점 → Socket / HTTP · 연결 재사용
```

ARP는 링크 전달을 위한 주소 해석, DHCP는 IP 설정, Socket은 응용과 OS의 통신 접점으로 관련 기능에 배치한다. 엄밀한 프로토콜 계층 분류와는 구분한다.

망 구성·설계는 [전체 지도](00-전체.md)의 별도 관점이며, 전송 제어는 [제어·품질·운영](02-전송-품질-운영.md)에서 다룬다.

## 1. 계층화 — 계층별 역할

```text
Application Data
  ↓ TCP(Transmission Control Protocol)/UDP(User Datagram Protocol) Header
Segment / Datagram (L4) — Port: 종단 통신
  ↓ IP Header
Packet (L3)            — IP: 목적지·경로
  ↓ Link Header/Trailer
Frame (L2)             — MAC: 현재 링크 전달
  ↓
Bit / Signal (L1)
```

OSI(Open Systems Interconnection)는 7계층 참조 모델, TCP/IP는 인터넷 프로토콜 체계다. IP(Internet Protocol)는 네트워크 계층의 주소 지정·전달을 담당한다. **상위 PDU가 하위 계층의 SDU**가 되고, 하위 계층이 제어 정보를 추가한다.

- **SAP(Service Access Point):** 상위 계층이 하위 계층 서비스를 이용하는 접점
- **SDU(Service Data Unit):** 하위 계층에 넘긴 데이터
- **PCI(Protocol Control Information):** 해당 계층이 추가한 제어 정보
- **PDU(Protocol Data Unit):** 계층이 다루는 데이터 단위(개념적으로 SDU + PCI)

예를 들어 TCP Segment는 IP 계층의 SDU가 되고 IP Header가 붙어 Packet이 된다. 수신 측에서는 역순으로 Header를 해석한다. **IP는 종단 목적지, MAC은 현재 링크의 전달 대상, Port는 호스트 내부의 통신 종단**을 구분한다.

장비도 기준 정보가 다르다. L1 Hub/Repeater는 신호, L2 Switch는 MAC, L3 Router/L3 Switch는 IP, L4 Load Balancer는 IP·Port, L7 Proxy/Load Balancer/WAF(Web Application Firewall)는 응용 정보를 활용한다. **L4는 전송 정보 기반 분산, L7은 URL·Host 등 요청 내용 기반 분산**이 대표적이다. L4·L7 Switch라는 이름은 실무에서 Load Balancer/ADC를 가리키기도 한다. 계층 이름보다 **어떤 정보를 보고 결정하는가**가 중요하다.

## 2. 링크 계층 — 현재 링크에서 전달

```text
목적지 IP와 Prefix 확인
├─ 직접 전달 가능 → 목적지 MAC 확인(ARP) → Frame 전송
└─ 다른 Subnet    → Gateway MAC 확인(ARP) → Router → 다음 망
```

ARP(Address Resolution Protocol)는 IPv4 주소에 대응하는 MAC(Media Access Control) 주소를 확인한다. IPv6에서는 ARP 대신 Neighbor Discovery를 쓴다. 같은 Subnet이라도 실제 L2 도달 가능성이 전제되어야 한다. **일반 라우팅에서는 목적지 IP가 유지되지만 링크마다 MAC은 바뀔 수 있다**(NAT는 예외). 예를 들어 다른 Subnet의 서버로 보낼 때 PC는 서버의 IP를 목적지로 유지하면서, 첫 Ethernet Frame의 목적지 MAC은 Gateway로 설정한다. Router는 IP를 보고 다음 홉을 선택하고 다음 링크에 맞는 새 Frame을 만든다. L2 Switch는 같은 VLAN 안에서 학습한 MAC·Port 정보로 Frame을 전달한다.

**Ethernet 프레임·매체 접근과 관련 오류 복구**

```text
Ethernet (IEEE 802.3)
├─ NIC(Network Interface Card) / Switch Port
├─ 오류 검출 → CRC(Cyclic Redundancy Check) 계산
│             └─ FCS(Frame Check Sequence) 필드에 검사값 저장
└─ 공유 매체 접근 → CSMA/CD(Carrier Sense Multiple Access with Collision Detection) — 충돌 감지, 과거 공유형 반이중 Ethernet

관련 기술 (Ethernet의 필수 기능·처리 순서가 아님)
├─ 무선 매체 접근 → CSMA/CA(Carrier Sense Multiple Access with Collision Avoidance) — 충돌 회피, WLAN
└─ 오류 복구
   ├─ ARQ(Automatic Repeat reQuest) — 재전송
   │  ├─ Stop-and-Wait
   │  ├─ Go-Back-N
   │  └─ Selective Repeat
   └─ FEC(Forward Error Correction) — 수신 측 정정
```

**CSMA의 공통 원리:** 여러 장치가 하나의 매체를 공유하므로, 송신 전에 Carrier Sense로 사용 여부를 확인한다. 그러나 두 장치가 동시에 '비어 있음'을 확인하고 송신하면 충돌할 수 있다. **CSMA/CD도 송신 전에 감지**하며, CD는 송신 도중 충돌을 발견했을 때 중단·대기·재시도하는 방식이다. CSMA/CA는 무선에서 송신 중 충돌 검출이 어려워 임의 대기(Backoff) 등으로 충돌 가능성을 줄인다. 충돌을 완전히 없앤다는 뜻은 아니다.

CRC는 오류 검출, ARQ는 재전송 복구, FEC는 수신 측 정정으로 **서로 다른 역할**을 한다. ARQ의 대표 방식은 **Stop-and-Wait / Go-Back-N / Selective Repeat**이며, 재전송 범위와 미확인 프레임 처리 방식이 다르다. 이는 링크 전달과 연관된 오류 복구 방식의 **개념적 분류**이지 Ethernet의 필수 처리 단계가 아니다. 일반적인 유선 Ethernet 스위치는 오류 프레임을 폐기하며 L2 ARQ를 수행하지 않는다. 전이중 스위치 링크에는 충돌이 없어 CSMA/CD가 필요 없다. ARQ 방식별 차이와 종단 신뢰성 제어는 [제어·품질·운영 개념지도](02-전송-품질-운영.md)에서 다룬다.

### VLAN과 Subnet — L2 경계와 L3 경계

```text
VLAN(Virtual Local Area Network) — L2 프레임 전달 영역 분리
├─ Access Port — 보통 한 VLAN
└─ Trunk Port  — 여러 VLAN을 802.1Q Tag로 구분

Subnet — IP Prefix 기준 L3 주소 범위
└─ 서로 다른 Subnet의 일반적인 IP 통신에는 Routing 필요
```

VLAN과 Subnet은 실무에서 자주 대응시키지만 **같은 개념이 아니다**. VLAN은 스위치의 L2 전달·Broadcast 범위를 나누고, Subnet은 IP Prefix로 L3 주소 범위를 나눈다. 일반적으로 Access Port는 한 VLAN의 단말을 연결하고 Trunk는 여러 VLAN을 하나의 링크로 전달한다. **Trunk는 VLAN을 운반할 뿐 VLAN 간 Routing을 수행하지 않는다.** VLAN 사이 통신에는 Router 또는 L3 Switch의 Routing이 필요하다.

→ [VLAN·서브넷·브로드캐스트 도메인](VLAN-서브넷-브로드캐스트-도메인.md)

## 3. 네트워크 계층 — 주소와 경로

### 주소의 설계·설정·변환

```text
IP 주소 관리
├─ 범위 설계
│  ├─ Subnetting — 주소 범위 분할
│  ├─ CIDR — Classless Inter-Domain Routing
│  │         Class 고정 경계 없이 Prefix로 표현·할당·집약
│  └─ VLSM — Variable Length Subnet Mask
│            Subnet마다 필요한 크기로 분할
├─ 설정 → DHCP(Dynamic Host Configuration Protocol)
│         IP·Mask·Gateway·DNS 등 자동 제공
└─ IPv4(32bit) 주소 부족 대응
   ├─ 주소 재사용 → 사설 IP
   ├─ 주소 변환 → NAT(Network Address Translation)
   │             └─ PAT(Port Address Translation) / NAPT
   │                (Network Address and Port Translation)
   │                IP와 Port 변환으로 공인 IP 공유
   ├─ 효율적 할당 → CIDR
   └─ 주소 공간 확대 → IPv6(128bit)
      ├─ 전달 대상 → Unicast / Multicast / Anycast
      ├─ 사용 범위 → Global / Link-Local / Unique Local
      └─ IPv4 공존 → Dual Stack / Tunneling / Translation
```

**DHCP 주소 할당의 대표 흐름은 DORA(Discover → Offer → Request → ACK)**다. IP뿐 아니라 Mask·Gateway·DNS 등을 임대(Lease)하며, 다른 Subnet의 DHCP 서버에는 Relay를 통해 요청을 전달할 수 있다. DHCP는 주소 설정 기술이지 NAT처럼 패킷 주소를 변환하는 기술이 아니다.

IPv6 주소의 **전달 대상**은 Unicast(하나의 인터페이스), Multicast(가입한 그룹), Anycast(동일 주소를 공유하는 여러 인터페이스 중 라우팅상 가까운 하나)로 구분한다. **사용 범위**는 Global Unicast(인터넷 라우팅), Link-Local(같은 링크), Unique Local(내부망 용도)로 구분하며, IPv6에는 Broadcast 주소가 없다.

CIDR은 클래스에 묶이지 않는 Prefix 기반 주소 체계이고, VLSM은 각 Subnet의 크기를 다르게 정하는 설계 방법이다. **DHCP는 주소 설정**, NAT/PAT는 **패킷 주소·포트 변환**이다. NAT는 IP 주소를 변환하며 PAT(NAPT)는 Port까지 이용해 여러 내부 연결이 하나의 공인 IP를 공유하게 한다. 변환 장치는 대응 정보를 유지해 응답을 올바른 내부 연결로 되돌린다. IPv4와 IPv6는 패킷 형식이 달라 점진적 공존 기술이 필요하다. IPv6의 전달 대상과 사용 범위는 서로 다른 분류축이다.

→ [IP 주소·NAT·DHCP·CIDR·VLSM](IP-주소-NAT-DHCP-CIDR-VLSM.md): Prefix 분할·DHCP DORA·PAT 변환 테이블 등 예시.

### 경로 선택 — Routing과 Forwarding

```text
Control Plane — 경로 학습·선택(Routing)
├─ Static — 관리자 설정
└─ Dynamic — 경로 정보 교환
   ├─ AS 내부: RIP(Routing Information Protocol) — Distance Vector
   │           OSPF(Open Shortest Path First) — Link State
   └─ AS 간:   BGP(Border Gateway Protocol) — Path Vector / 정책
         ↓
Routing Table → 전달 정보
         ↓
Data Plane — Forwarding
목적지 IP → Longest Prefix Match → 다음 홉·출력 인터페이스
```

Control Plane이 경로 정보를 학습·선택하고, Data Plane은 목적지 IP에 가장 구체적으로 일치하는 경로(Longest Prefix Match)를 이용해 출력 인터페이스와 다음 홉을 정한다. **Routing은 경로 결정, Forwarding은 실제 패킷 전달**이다. RIP는 이웃에게서 거리·방향 정보를 받아 경로를 선택하는 Distance Vector, OSPF는 링크 상태를 공유해 네트워크 지도를 구성하고 최단 경로를 계산하는 Link State, BGP는 AS(Autonomous System, 자율 시스템) 사이의 경로 정보와 정책을 다루는 Path Vector 방식이다. 즉 RIP·OSPF는 주로 AS 내부, BGP는 AS 간 경로 교환에 쓰이며 단순한 발전 순서가 아니다.

#### 멀티캐스트 — 하나의 패킷을 여러 수신자에게 전달

```text
Multicast — 그룹 기반 전달
├─ 전달 대상 → Unicast(1:1) / Broadcast(영역 전체) / Multicast(그룹)
├─ 그룹 식별 → IPv4 224.0.0.0/4 / IPv6 ff00::/8
├─ 그룹 멤버십 → IGMP(IPv4) / MLD(IPv6)
└─ 그룹별 전달 경로 → PIM
   ├─ Dense Mode  → Flood 후 Prune(불필요한 방향 제외)
   ├─ Sparse Mode → Join한 방향만 전달
   └─ RPF → 송신자 쪽 정상 입력 경로인지 검사
```

Unicast는 수신자마다 별도 전달 흐름을 만들지만, **Multicast는 그룹 주소로 전송하고 공통 구간에서는 한 번 전달하다가 경로가 갈라지는 지점에서 복제**한다. 주소는 특정 단말이 아니라 수신자 **그룹**을 나타낸다. 이는 앞의 Casting Mode와 IPv6 주소 분류에서 본 Multicast를 실제 네트워크 전달로 확장한 관점이다.

**그룹 관리와 라우팅은 역할이 다르다.** IGMP(Internet Group Management Protocol)와 MLD(Multicast Listener Discovery)는 단말이 연결된 네트워크에 해당 그룹의 수신자가 있는지 인접 라우터가 파악하도록 돕는다. PIM(Protocol Independent Multicast)은 라우터 간에 그룹 패킷을 전달할 트리를 구성한다. 라우터는 모든 수신자 IP를 외우는 대신, 그룹별 또는 송신자·그룹별로 **패킷이 들어올 인터페이스와 복제해 내보낼 인터페이스 목록**을 관리한다.

예를 들어 송신자 S의 그룹 G 패킷을 R1이 받았고, R2·R3 쪽에만 수신자가 있다면 R1은 R2·R3 방향으로만 복제한다. 이처럼 여러 수신자 방향으로 갈라지는 경로가 **멀티캐스트 전달 트리**다.

PIM의 트리 구성 전략은 **Dense Mode(밀집 가정: 일단 넓게 전달한 뒤 수신자가 없는 방향에서 Prune)**와 **Sparse Mode(희소 가정: 수신자가 있는 방향에서 Join해 필요한 경로만 구성)**로 대비된다. Sparse Mode는 RP(Rendezvous Point)를 중심으로 공유 트리를 구성할 수도 있다. PIM은 특정 유니캐스트 라우팅 프로토콜에 종속되지 않고 기존 경로 정보를 활용한다.

**RPF(Reverse Path Forwarding)**는 송신자에게 실제로 회신하는 기능이 아니다. 라우터가 송신자 쪽으로 패킷을 보낸다면 이용할 경로를 참고해, **멀티캐스트 패킷이 예상한 입력 인터페이스로 들어왔는지** 검사한다. 다른 방향에서 들어온 패킷은 폐기해 중복 전달과 루프를 방지한다. RPF와 Dense/Sparse는 각각 **입력 경로 검사**와 **트리 구성 전략**이라는 서로 다른 역할이다.

**복원할 핵심:** 그룹 주소(어떤 그룹인가) → IGMP·MLD(수신자가 있는가) → PIM(어느 방향으로 복제할까) → RPF(올바른 방향에서 왔는가). 이 연결은 역할 구분이지 고정된 실행 순서가 아니다.

## 4. 종단·응용 통신 — Host에서 프로세스까지

```text
송신 Application
      │ Socket API(Application Programming Interface)
      ▼
TCP / UDP — Port로 통신 종단 구분
      │
      ▼
IP — 목적지 Host까지 전달
      │
      ▼
수신 Host → Port → 수신 Application
```

| 비교축 | TCP | UDP |
|---|---|---|
| 전달 형태 | 연결지향 바이트 스트림 | 비연결 데이터그램 |
| 순서·손실 복구 | 순서 보장, ACK·재전송 | 기본 제공하지 않음 |
| 흐름·혼잡 제어 | 기본 제공 | 기본 제공하지 않음 |
| 오류 검출 | Checksum | Checksum |
| 대표 선택 | 파일 전송 등 순서·신뢰성 중시 | 실시간 미디어 등 응용별 제어 중시 |

**Port**는 호스트 안의 통신 종단을 구분하고, **Socket API**는 응용과 OS 네트워크 스택을 연결한다. TCP는 3-Way Handshake로 연결을 수립하고 FIN 기반으로 정상 종료한다. UDP는 단순하지만 항상 더 빠른 것은 아니다. UDP 위에서도 **QUIC**처럼 신뢰성·혼잡 제어를 구현할 수 있으며 HTTP(Hypertext Transfer Protocol)/3가 그 예다(QUIC은 현재 별도의 공식 약어 풀이 없이 쓰이는 프로토콜 이름이다).

**HTTP Persistent Connection(HTTP Keep-Alive)**은 여러 요청에 연결을 재사용해 반복 연결 비용을 줄인다. **TCP Keepalive**는 유휴 TCP 연결의 생존 여부를 확인하며, **Connection Pool**은 응용이 재사용할 연결을 관리한다. 세 개념은 목적과 관리 주체가 다르다. HTTP/1.1은 지속 연결이 기본이고, HTTP/2는 스트림 다중화를 지원한다. HTTP/3는 TCP가 아닌 QUIC/UDP를 사용한다.
