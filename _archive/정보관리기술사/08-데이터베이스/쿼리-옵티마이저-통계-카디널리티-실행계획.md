# 쿼리 옵티마이저, 통계와 실행계획

## 이 문서의 개념지도

```text
SQL → Parser → Rewriter → Optimizer → Executor
                         │
                         ▼
              실행 방법 후보 비교
              ├─ Access Path
              ├─ Join Order
              └─ Join Algorithm
                         ▲
Statistics → Selectivity → Cardinality 추정
                         │
                         ▼
                   Cost 추정
                         ↓
                  Execution Plan
                         ↓
           EXPLAIN 예상치 ↔ 실제 실행치

※ Cardinality 추정 오류는 후보 비용 판단과 Plan 선택에 전파된다.
```

이 지도는 Optimizer의 **통계 기반 추정 → 실행전략 비교 → Plan 선택 → 실제 실행 확인** 관계를 먼저 보여준다.


## 1. Query Engine에서 Optimizer의 위치

SQL이 실행될 때는 크게 `해석 → 변환 → 실행 방법 선택 → 실행`의 흐름을 거친다.

아래는 MySQL 계열을 기준으로 SQL 처리와 데이터 접근 요청을 연결한 개념적 조망도다.

```text
SQL
 ↓ 처리 흐름
┌──────────────────────────────────┐
│ Query Engine                     │
│ Parser → Rewriter/Preprocessor   │
│              ↓                   │
│ Optimizer → Plan → Executor      │
└──────────────┬───────────────────┘
               │ 데이터 접근 요청
               ▼
┌──────────────────────────────────┐
│ Storage Engine (예: InnoDB)      │
│ Index · DB Page · Buffer Pool    │
└──────────────┬───────────────────┘
               │ 필요 시 읽기·쓰기
               ▼
           Data Files
```

Query Engine 안의 화살표는 SQL 처리 흐름이고, 아래 화살표는 데이터 접근 요청과 저장장치 I/O를 뜻한다. Buffer Pool은 InnoDB의 예이며 모든 DBMS가 같은 내부 구조를 갖는 것은 아니다. 이 문서는 Optimizer의 판단을 확대하고, [탐색트리와 DB 인덱스](탐색트리와-DB인덱스-BTree-BPlusTree-BStarTree-TTree.md)에서 저장구조를 이어서 본다.


```text
SQL
 ↓
Query Engine
├─ Parser    → SQL 문법·구조 해석
├─ Rewriter  → 의미를 유지하며 Query 변환
├─ Optimizer → 여러 실행 방법 중 Plan 선택
└─ Executor  → 선택된 Plan을 실제 실행
 ↓
Result
```

이 문서는 이 가운데 **Optimizer가 어떤 근거로 Execution Plan을 선택하는가**를 Zoom-in한다.

SQL은 원하는 결과를 선언하지만 같은 결과를 만드는 Physical Plan은 여러 개일 수 있다.

```text
Optimizer
│
├─ Statistics
│    ↓
│  Selectivity 추정
│    ↓
│  Cardinality 추정
│
└─ 후보 실행 방법
    ├─ Access Path
    │   ├─ Table Scan
    │   └─ Index Scan
    ├─ Join Order
    └─ Join Algorithm
          ↓
      처리량 · Cost 추정
          ↓
      후보별 Cost 비교
          ↓
    Execution Plan 선택
```

즉 이 문서의 핵심 인과관계는 다음과 같다.

```text
Statistics
    ↓
Selectivity
    ↓
Cardinality
    ↓
Cost
    ↓
Execution Plan
    ↓
실제 실행
    ↓
Estimated ↔ Actual 비교
```

## 2. Statistics와 Cardinality

둘 다 조건을 적용한 뒤 얼마나 남을지를 표현하지만 단위가 다르다.

```text
전체 Row = 1,000,000
조건: age = 30

Selectivity = 1%
→ 전체 중 몇 %가 남을 것으로 보는가?

Cardinality = 10,000 Row
→ 그래서 몇 Row가 남을 것으로 보는가?
```

즉:

```text
Statistics
    ↓
Selectivity
"몇 %가 남을까?"
    ↓
Cardinality
"그래서 몇 Row가 남을까?"
    ↓
Cost
```

여기서 Cardinality는 **실행계획의 각 연산이 출력할 것으로 예상되는 Row 수**다. 문맥에 따라 컬럼의 Cardinality를 `Distinct 값 수`라는 뜻으로 부르기도 하지만, 둘은 다르다. 예를 들어 성별 컬럼의 Distinct 값이 2개여도 `gender='M'` 조건을 만족하는 Row는 수십만 건일 수 있다.

Cardinality는 각 연산 뒤에 몇 Row가 남는지에 대한 추정이다. 같은 연산도 처리 Row 수가 달라지면 비용이 크게 달라지므로 **Cardinality가 Cost 계산의 중요한 출발점**이 된다.

```text
Filter 결과 10 Row 예상
→ Index Lookup 반복이 저렴할 수 있음

실제 1,000,000 Row
→ 반복 Lookup이 폭증
```

따라서 실행계획이 잘못된 것처럼 보일 때 먼저 **Optimizer가 입력 Row 수를 얼마나 정확히 예상했는지** 본다.

### 통계가 Cardinality를 만든다

Optimizer는 실제 모든 Row를 매 Query마다 조사하지 않고 수집된 통계를 이용한다.

대표 정보는 다음과 같다.

- 전체 Row 수
- NULL 비율
- Distinct 값 수
- 자주 등장하는 값(MCV)
- 값 분포 Histogram

```text
통계
 ↓
조건 Selectivity 추정
 ↓
Cardinality 추정
 ↓
Access Path / Join Cost 계산
```

대량 적재·삭제나 데이터 분포 변화 뒤 통계가 오래되면 과거 분포를 기준으로 Plan을 선택할 수 있다. PostgreSQL의 `ANALYZE` 같은 기능은 이 통계를 다시 수집한다.

### 여러 조건과 컬럼 간 상관관계

통계가 최신이어도 여러 조건의 관계를 충분히 표현하지 못하면 추정이 틀릴 수 있다. 예를 들어 다음 두 조건은 서로 독립적이지 않다.

```sql
WHERE city = '서울'
  AND district = '강남구'
```

`강남구`라는 구 이름이 `서울`과 밀접하게 연관되어 있다면, 각 조건의 Selectivity를 독립적이라고 가정해 단순히 곱하는 방식은 결과 Row 수를 과소 추정할 수 있다. 실제 Optimizer의 추정 방식은 DBMS와 통계 기능에 따라 다르며, 다중 컬럼 통계 등으로 일부 상관관계를 보완할 수 있다.

```text
컬럼 간 상관관계를 통계가 충분히 반영하지 못함
        ↓
Selectivity / Cardinality 추정 오류
        ↓
후보 Plan의 Cost 비교가 왜곡될 수 있음
        ↓
비효율적인 Access Path / Join 선택 가능
```

따라서 **통계가 오래된 문제와 통계만으로 관계를 충분히 표현하지 못하는 문제**를 구분한다.

## 3. Cost와 실행전략 선택

Optimizer는 예상 Cardinality와 접근 방식에 따른 I/O·CPU·Memory 등의 비용을 추정해 후보 Plan을 비교한다. **Cost는 보통 실제 시간 자체가 아니라 DBMS 내부의 상대 비용 단위**다. 비교 대상은 Access Path, Join Order, Join Algorithm이며, 어떤 선택이 유리한지는 예상 입력 크기와 데이터 분포에 달려 있다.

Cardinality와 Access Path가 바뀌면 적절한 JOIN 전략도 달라진다.

- 작은 Outer + 빠른 Inner Lookup → Nested Loop 후보
- 큰 Equality Join + 충분한 Memory → Hash Join 후보
- 정렬된 입력 활용 → Merge Join 후보

이 문서에서는 세 전략이 **예상 입력 Row 수·Index Lookup 가능성·정렬 여부·Memory 비용**에 따라 선택된다는 점까지 이해하면 충분하다. 각 JOIN Operator의 내부 처리와 Trade-off를 별도로 비교하고 싶을 때만 [JOIN 실행전략](질의최적화와-JOIN-실행전략.md)을 참고한다.

## 4. Execution Plan과 EXPLAIN

### 실행계획은 Tree로 읽는다

Execution Plan은 보통 **하위 Operator의 결과가 상위 Operator의 입력이 되는 Tree**로 표현된다.

```text
Scan A ───────┐
              ├→ Hash Join → 결과
Scan B → Hash ┘
```

```text
Leaf
→ Table / Index에서 Data를 읽음
        ↓
중간 Operator
→ Filter / Sort / Hash / Join 등 처리
        ↓
Root
→ 최종 Query 결과
```

즉 각 Node는 하위 Node의 결과를 입력으로 받아 처리하고 그 결과를 상위 Node에 넘긴다. 실행계획을 읽을 때는 가장 안쪽에서 어떤 Data를 읽는지 확인하고 바깥 연산으로 올라간다.

다만 **Plan Tree는 연산의 의존 관계와 데이터 흐름을 나타내는 표현**이지, 모든 Operator가 한 번씩 순차적으로 끝나는 실행 순서표는 아니다. 예를 들어 Nested Loop는 내부 입력을 여러 번 호출할 수 있고, Hash Join은 해시 테이블을 구성하는 단계가 필요하다. 실행 방식은 Operator에 따라 달라진다.

확인할 핵심은 다음이다.

```text
Access Path
→ Table Scan / Index Scan 등

Estimated Rows ↔ Actual Rows
→ 추정이 맞는가?

Loops
→ 작은 비용이 몇 번 반복되는가?

Sort / Hash
→ Memory를 넘겨 Spill하는가?

Filter
→ 많은 Row를 읽은 뒤 대부분 버리고 있지는 않은가?
```

### EXPLAIN과 실제 실행을 구분한다

PostgreSQL 기준으로 `EXPLAIN`은 예상 Plan을 보여주고, `EXPLAIN ANALYZE`는 Query를 실제 실행하여 예상과 실제를 비교할 수 있게 한다. DBMS마다 명령과 출력 항목은 다르므로 동일한 문법으로 일반화하지 않는다.

```text
EXPLAIN
→ Estimated Cost / Rows

EXPLAIN ANALYZE
→ Estimated + Actual Time / Rows / Loops
```

PostgreSQL에서 쓰기 Query에 `EXPLAIN ANALYZE`를 사용하면 실제 변경이 실행될 수 있다. 필요하면 `BEGIN`으로 시작해 실행을 확인한 뒤 `ROLLBACK`하는 등 안전한 검증 절차를 사용한다. 실제 실행 자체의 잠금·트리거·외부 부작용 가능성도 고려한다.

## 5. 튜닝 판단 순서

```text
느린 Query
 ↓
실행계획 확인
 ↓
Estimated ↔ Actual Row 비교
 ↓
실제로 시간·I/O가 집중된 Operator 확인
 ↓
추정 오류가 병목과 연결되는지 판단
 ↓
통계·Selectivity·Access Path·반복 횟수·Sort·Spill 확인
 ↓
Index / SQL / Schema / 통계 조정
 ↓
재측정
```

**Cardinality 추정 오류와 실제 실행 병목은 같은 말이 아니다.** 추정이 정확해도 대량 데이터 처리나 I/O 때문에 느릴 수 있고, 추정이 틀려도 선택된 Plan의 실행 성능에 영향이 작을 수 있다. 따라서 차이가 큰 숫자만 찾기보다 그 차이가 반복 Lookup, Join 방식, Sort·Spill 등 실제 비용으로 이어졌는지 확인한다.

Hint나 특정 Plan 강제는 현재 데이터 분포에서는 빨라도 분포가 바뀌면 오히려 위험할 수 있으므로 마지막 수단으로 본다.

> **쿼리 튜닝의 핵심은 Plan 이름을 외우는 것이 아니라, Optimizer가 어떤 입력 크기와 비용을 예상했으며 그 예상이 실제와 어디서 달라졌는지 찾는 것이다.**

1. 같은 SQL에서 여러 Physical Plan이 가능한 이유는 무엇인가?

3. `city='서울' AND district='강남구'`에서 조건을 독립적으로 취급하면 왜 추정 오류가 생길 수 있는가?
4. 실행계획 Tree가 모든 Operator의 단순한 시간 순서를 뜻하지 않는 이유는 무엇인가?
5. Estimated Rows가 Actual Rows와 크게 달라도 반드시 성능 병목의 원인은 아닌 이유는 무엇인가?
6. PostgreSQL에서 쓰기 Query에 `EXPLAIN ANALYZE`를 사용할 때 무엇을 주의해야 하는가?
