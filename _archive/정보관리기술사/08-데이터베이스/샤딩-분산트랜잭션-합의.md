# 샤딩, 분산 트랜잭션과 합의

## 이 문서의 개념지도

```text
단일 Node의 용량·처리량 한계
       ↓ Scale-out
├─ Sharding    → 데이터를 여러 Shard로 분할
│   └─ Shard Key · Hotspot · Rebalancing
└─ Replication → 같은 데이터를 복제
       ↓ Network를 넘는 조정 문제
       ├─ 분산 원자성 → 2PC (공동 Commit) / Saga (보상)
       └─ 복제 상태·순서 합의 → Consensus

※ 2PC·Saga·Consensus는 같은 문제의 대체 알고리즘이 아니다.
※ CAP은 분산 환경의 별도 일관성·가용성 선택 관점이다.
```

이 지도는 본문을 읽기 전 핵심 개념의 **위치·관계·구분 기준**을 확인하는 인출 좌표다. 세부 원리와 예외는 아래에서 설명한다.


## 이 문서에서 되짚을 질문

- 단일 DB의 한계를 넘기 위해 왜 Sharding을 사용하는가?
- 좋은 Shard Key는 무엇을 피해야 하는가?
- 여러 Node에 걸친 원자성을 2PC와 Saga는 어떻게 다르게 다루는가?
- Replication 환경에서 Consensus는 왜 필요한가?
- Sharding, Replication, CAP은 어떤 관계인가?

## 1. Scale-out을 선택하면 새 문제가 생긴다

단일 Node의 용량·처리량 한계가 커지면 더 큰 장비로 가는 Scale-up과 Node 수를 늘리는 Scale-out을 비교한다.

```text
단일 Node 한계
   ↓
Scale-out
├─ Replication : 같은 데이터를 복제
└─ Sharding    : 데이터를 분할
   ↓
Network 경계가 생김
   ↓
분산 Transaction · Consistency · Consensus 문제
```

확장성은 공짜가 아니다. 한 Process·한 DB 안에서 당연했던 원자성과 즉시 일관성이 Network를 넘는 순간 별도 설계 문제가 된다.

## 2. Sharding — 데이터를 여러 Node로 분할한다

Sharding은 하나의 논리 데이터 집합을 Shard Key 기준으로 여러 Node에 나누어 저장한다.

좋은 Shard Key는 두 가지를 함께 본다.

- 데이터와 Traffic을 고르게 분산하는가?
- 자주 함께 사용하는 데이터가 불필요하게 여러 Shard로 갈라지지 않는가?

### Hotspot

특정 Key 범위나 Tenant에 Write가 몰리면 일부 Shard만 과부하가 된다.

### Rebalancing

Node를 추가·제거할 때 어느 데이터를 얼마나 이동해야 하는지 고려한다. Hash 기반 분산에서는 Consistent Hashing 같은 방법으로 재배치 범위를 줄일 수 있다.

### Hash와 Range

```text
Hash Sharding
→ 균등 분산에 유리
→ Range Query는 여러 Shard에 퍼질 수 있음

Range Sharding
→ 인접 Range Query에 유리
→ 특정 최신 Range에 Traffic이 몰릴 수 있음
```

## 3. Sharding의 대가

관련 데이터가 여러 Shard로 갈라지면 Cross-Shard JOIN과 Transaction이 어려워진다.

가능하면 Shard Key를 이용해 함께 변경되는 데이터를 같은 Shard에 두는 Co-location을 먼저 검토한다.

```text
같은 Shard
→ Local Transaction

여러 Shard
→ Network + 부분 실패 가능
→ 분산 Transaction 문제
```

## 4. 2PC — 여러 참여자의 Commit을 하나로 묶는다

2PC(Two-Phase Commit)는 Coordinator가 여러 Participant의 Commit을 조정한다.

```text
1. Prepare
Coordinator → Participant들
"Commit 가능한가?"

2. Commit / Abort 결정
모두 YES 응답 → Commit 결정
NO 응답 / Prepare 응답 대기 실패 → Abort 결정
```

위 Abort 경로는 **아직 Commit을 결정하지 않은 단계**를 뜻한다. Commit을 확정한 뒤 메시지 전달에 실패했다고 Abort로 바꾸는 것은 아니다.

### 정상 경로 — 준비와 최종 결정을 구분한다

아래는 참여자 A와 B가 모두 YES로 응답하는 예시다. 위에서 아래로 시간이 흐르며, 가로 화살표는 메시지 전송이다. 최종 결정 수신 확인 메시지는 생략했다.

```text
Coordinator           A             B
  |                   |             |
  |-- PREPARE ------->|             |
  |-- PREPARE --------------------->|
  |<- YES ------------|             |
  |<- YES --------------------------|
  | COMMIT 결정·기록
  |-- COMMIT -------->|             |
  |-- COMMIT ---------------------->|
```

참여자는 준비 상태를 복구 가능하게 기록한 뒤 YES로 응답한다. **YES는 이미 Commit했다는 뜻이 아니라, 이후 최종 결정을 따를 준비가 됐다는 뜻**이다. Coordinator는 모두의 YES를 확인해 Commit 결정을 기록하고 전달한다. 물리적으로 같은 순간에 모든 Node가 Commit한다는 뜻은 아니다.

### 장애 경로 — YES 이후에는 왜 기다릴 수 있는가

```text
Coordinator: PREPARE 전송
        ↓
A와 B: PREPARED 기록 → YES 응답
        ↓
최종 결정을 아직 받지 못한 시점에
Coordinator 장애 / 통신 단절
        ↓
A와 B: COMMIT인지 ABORT인지 확인 불가
        ↓
임의로 Commit / Abort하지 못하고 결정 대기
        ↓
관련 Lock·자원이 오래 유지될 수 있음
```

문제는 단순히 Coordinator가 잠깐 느리다는 것이 아니라 **참여자가 원자성을 깨지 않고 혼자 결정할 근거가 없다는 것**이다. 복구된 Coordinator나 결정을 아는 다른 참여자 등을 통해 최종 결정을 확인하면 진행할 수 있다. 최종 결정을 확인할 수 없는 경우에 Blocking이 발생할 수 있다는 뜻이지, Coordinator 장애가 항상 영구 대기로 이어진다는 뜻은 아니다.

장점은 여러 참여자의 원자성을 강하게 맞출 수 있다는 점이다. 대가는 Prepare 이후 Participant가 최종 결정을 기다리며 자원을 잡을 수 있고, Coordinator 장애가 지연·Blocking 문제를 만들 수 있다는 점이다. 이미 기록된 Commit 결정의 전달 실패는 **그 결정을 복구·재전달하는 문제**로 다룬다.

## 5. Saga — 이미 Commit한 Local Transaction을 보상한다

Saga는 긴 분산 업무를 여러 Local Transaction으로 나누고 실패하면 이미 완료된 단계에 대한 Compensating Transaction을 실행한다.

```text
주문 생성
→ 결제 승인
→ 재고 차감
        ↓ 실패
결제 취소
→ 주문 취소
```

보상은 DB Rollback과 다르다. 이미 Commit된 업무 결과를 **의미적으로 상쇄하는 새로운 업무 처리**다.

| 비교 | 2PC | Saga |
|---|---|---|
| 중심 목표 | 참여자들의 원자적 Commit 결정 | 긴 업무 흐름의 최종 일관성 |
| 자원 Lock | 오래 유지될 수 있음 | 각 Local Transaction 단위 |
| 실패 처리 | 결정 전 Abort / 결정 후 복구·재전달 | 보상 Transaction |
| 복잡성 | Coordinator·Participant Protocol | 보상·중복·순서 설계 |

Saga가 2PC의 무조건적인 상위 기술은 아니다. 요구하는 일관성, 업무 지속시간, 부분 상태 노출 허용 여부에 따라 선택한다.

## 6. Consensus — 복제본이 하나의 순서에 동의한다

Sharding이 **분할** 문제라면 Consensus는 주로 **복제된 상태의 합의** 문제다.

```text
같은 Log를 가진 여러 Node
   ↓
어느 Write가 먼저인가?
누가 Leader인가?
어느 상태가 Commit됐는가?
   ↓
Consensus
```

Raft는 대표적인 Consensus Algorithm으로 Leader Election과 Log Replication을 이해의 중심으로 잡는다.

```text
Leader 선출
   ↓
Client Write를 Leader가 Log에 기록
   ↓
Follower에 복제
   ↓
Quorum이 확인
   ↓
Commit
```

Quorum은 전체 Node가 아니라 필요한 다수의 동의를 이용해 일부 장애가 있어도 진행할 수 있게 한다.

## 7. CAP과의 관계

CAP은 Sharding 자체를 설명하는 이론이 아니다. 데이터가 여러 Node에 존재하여 Network Partition이 가능한 상태에서 **Partition 중 Consistency와 Availability의 선택**을 설명한다.

```text
Sharding / Replication
→ 여러 Node에 상태가 존재
→ Network Partition 가능
→ CAP Trade-off가 중요해짐
```

CAP·PACELC와 NoSQL의 모델 선택은 [분산-데이터베이스-CAP-PACELC-NoSQL](분산-데이터베이스-CAP-PACELC-NoSQL.md)에서 이어서 본다.
