# 데이터베이스 스토리 학습 — 주문 데이터가 커지면서 생기는 문제

> [데이터베이스 전체 개념지도](00-전체.md)의 모델링·처리·신뢰성·성능·확장·활용·거버넌스를 가상 주문 시스템의 문제와 질문으로 이해한다. **신뢰성·성능·확장은 순차적인 기술 발전 단계가 아니라 병렬 운영 과제**다.

## 이 이야기에서 따라갈 질문과 흐름

~~~text
[출발] 주문 데이터 관리
   │ 어떤 문제가 생기고 무엇이 필요할까?
   ▼
1. DBMS·3-Schema
   │ 다음 문제를 어떻게 해결할까?
   ▼
2. 모델링·정규화
   │ 그 과정에서 무엇을 선택할까?
   ▼
3. SQL 처리
   │ 실제 운영에서는 무엇이 달라질까?
   ▼
4. 트랜잭션·성능·분산
   │ 결과와 한계는 어떻게 확인할까?
   ▼
5. OLTP·DW·OLAP·BI

[관계 주의] 신뢰성·성능·확장은 병렬 운영 문제; Governance는 전 과정
~~~

위 그림은 **본문을 읽을 때 따라갈 학습 경로**다. 실제 인과관계가 없는 개념을 필수 선후 단계로 해석하지 않는다.

## 1. 엑셀로 주문을 관리하면 안 될까 — DBMS와 데이터 독립성

영업팀과 물류팀이 각자 주문 엑셀을 수정한다. 같은 고객 정보가 서로 달라지고 누가 마지막으로 수정했는지도 불명확하다.

파일을 공동 폴더에 두는 것만으로 일관성 문제가 해결되지는 않는다. 데이터 구조·동시 접근·무결성·권한·회복을 일관되게 관리해야 한다. DBMS는 이러한 공통 관리 기능을 제공한다.

저장 구조를 변경할 때마다 모든 사용자 화면이 영향을 받지 않도록 계층을 분리할 필요가 있다. ANSI/SPARC 3-Schema는 외부(사용자 View)·개념(DB 전체 논리 구조)·내부(저장 구조)를 구분해 **논리적·물리적 데이터 독립성**을 지향한다. Schema는 구조 정의, Instance는 특정 시점의 실제 데이터다. 이 아키텍처의 '개념 스키마'는 모델링 단계의 '개념 모델'과 같은 용어가 아니다.

## 2. 고객·주문·상품을 어떻게 표현할까 — 모델링과 정규화

주문 하나에 고객 주소·상품·수량을 모두 한 표에 중복 기록했다. 고객 주소를 바꿀 때 일부 주문만 수정된다.

업무의 의미를 데이터로 표현하려면 대상과 관계를 식별해야 한다. 개념 모델링에서 Entity·Attribute·관계를 찾고, 논리 모델링에서 Relation·Key·제약조건을 정하며, 물리 설계에서 Index·저장 구조 등을 결정한다. Chen·Crow's Foot·IDEF1X는 표기법의 차이이지 설계 단계 자체가 아니다.

같은 사실이 여러 행에 반복되면 변경 과정에서 이상현상이 생길 수 있다. 삽입·갱신·삭제 이상현상이 발생할 수 있다. 함수 종속(FD) 등 종속성을 분석해 정규화로 관계를 분해하면 중복과 이상현상을 줄인다. 무손실 분해와 업무 제약을 함께 고려해야 한다.

그러나 정규화가 모든 조회의 성능까지 개선하는 것은 아니다. 조회 비용이 늘 수 있어 측정된 요구에 따라 반정규화를 선택하기도 한다. [정규화·함수종속 지도](정규화-함수종속-정규형-반정규화.md)에서 판단 기준을 본다.

## 3. 마지막 재고를 두 고객이 동시에 산다 — 트랜잭션과 동시성

재고가 1개 남았는데 두 주문이 동시에 성공했다.

각 SQL 문이 실행됐다고 주문 업무 전체가 올바르게 처리된 것은 아니다. 주문 생성과 재고 차감은 함께 성공하거나 실패해야 할 수 있다. Transaction의 **ACID**는 원자성·일관성·격리성·지속성의 성질을 설명한다.

동시에 실행하는 트랜잭션 간 간섭을 제어하는 것도 필요하다. Isolation Level, Lock·2PL, MVCC 같은 동시성 제어를 사용한다. 하지만 격리 수준에 따라 허용하는 현상과 비용이 다르다.

Commit 이후 장애가 나더라도 결과를 유지하려면 회복 메커니즘이 필요하다. Log·Undo·Redo·Checkpoint 같은 회복 메커니즘이 필요하다. 동시성 제어와 장애 회복은 연결되지만 서로 다른 문제다. [트랜잭션·동시성·격리수준](트랜잭션-동시성-격리수준-Lock-MVCC.md)에서 더 본다.

## 4. 주문 조회가 느리다 — Query Engine과 Index

주문이 수천만 건이 되자 특정 고객의 최근 주문을 조회하는 SQL이 느려졌다.

SQL을 작성한 순서와 실제 실행 계획은 같지 않을 수 있다. DBMS는 구문 분석·의미 확인 뒤 Optimizer가 여러 실행 계획의 비용을 비교하고 Executor가 선택한 계획을 수행한다. 통계와 Cardinality 추정은 계획 선택에 영향을 준다.

Index는 유용하지만 모든 쿼리를 무조건 빠르게 만들지는 않는다. Index는 탐색 비용을 줄일 수 있지만 저장 공간과 쓰기·유지 비용이 든다. B+Tree는 범위 탐색에 활용되고 Clustered/Non-clustered는 실제 행 조직·참조 방식의 차이다. JOIN도 Nested Loop·Hash·Merge 등 입력 특성에 따라 선택한다.

Optimizer도 통계와 비용 추정의 한계로 비효율적인 계획을 선택할 수 있다. 통계와 비용 추정의 오차, 데이터 분포 때문에 비효율적인 계획을 선택할 수 있다. [옵티마이저·실행계획](쿼리-옵티마이저-통계-카디널리티-실행계획.md)에서 원인을 살펴본다.

## 5. 서버 하나로 감당하기 어렵다 — 복제·샤딩·분산

읽기 요청이 많아지고 저장 데이터도 커졌다.

Replication과 Sharding은 모두 여러 노드를 활용하지만 목적이 다르다. **Replication**은 데이터를 복제해 읽기 분산·가용성 등에 활용하고, **Sharding**은 데이터를 분할해 저장 용량·쓰기 부하 등을 분산한다. 복제는 일관성·지연 문제를, 샤딩은 분산 트랜잭션·재배치·조정 문제를 낳을 수 있다.

분산 환경에서는 네트워크 분리와 일관성·가용성 사이의 제약도 고려해야 한다. CAP/PACELC는 분산 시스템의 일관성·가용성·지연에 관한 제약과 Trade-off를 생각하는 틀이다. NoSQL은 단일한 일관성 모델을 뜻하지 않는다. [분산 DB·CAP·PACELC](분산-데이터베이스-CAP-PACELC-NoSQL.md)에서 구분한다.

## 6. 데이터를 모았으니 분석에도 그대로 쓸까 — OLTP와 분석

주문 처리는 빠르지만 경영진은 지역별 판매 추세와 장기 수요를 보고 싶어 한다.

거래 처리에 적합한 구조가 대규모 분석에도 최적인 것은 아니다. **OLTP**는 일상 거래 처리, **DW**는 분석용 데이터 통합 저장, **OLAP**는 다차원 분석, **BI**는 의사결정 지원이라는 서로 다른 역할을 가진다.

분석 결과를 신뢰하려면 부서마다 다른 데이터 정의도 조정해야 한다. Data Governance는 데이터 소유·표준·품질·Metadata·보안·책임을 다룬다. 특정 마지막 단계가 아니라 모델링·운영·분석 전체에 걸친다.

[활용] OLTP / DW·OLAP·BI
[전 과정] Data Governance·품질·보안
~~~
