# 정규화, 함수 종속과 반정규화

## 이 문서의 개념지도

```text
한 Relation에 서로 다른 사실이 중복
       ↓ 삽입 · 갱신 · 삭제 이상
종속성 분석
├─ FD  (함수 종속) → 2NF · 3NF · BCNF
├─ MVD (다치 종속) → 4NF
└─ JD  (결합 종속) → 5NF
       ↓ 무손실 분해와 제약 보존 검토
정규화 → 중복·이상현상 감소
       ↕ 성능·운영 Trade-off
반정규화 → 의도적인 중복·구조 조정

※ 정규형은 단순한 Table 수 증가 단계가 아니라 종속성 제약의 구분이다.
```

| 정규형 | 핵심 확인 기준 |
|---|---|
| 1NF | 속성 값의 원자성 |
| 2NF | 비주요 속성의 후보 Key 일부에 대한 부분 함수 종속 제거 |
| 3NF | 비자명한 FD에서 결정자가 Superkey이거나 종속 속성이 주요 속성 |
| BCNF | 모든 비자명한 FD의 결정자가 Superkey |
| 4NF / 5NF | 비자명한 MVD / JD에 따른 분해 조건 |

**복습 단서:** FD·MVD·JD는 서로 다른 종속성이다. 분해할 때는 **무손실 결합**을 확인하고 종속성 보존 가능성도 검토한다. 반정규화는 성능 요구에 따른 의도적 Trade-off다.

이 지도는 본문을 읽기 전 핵심 개념의 **위치·관계·구분 기준**을 확인하는 인출 좌표다. 세부 원리와 예외는 아래에서 설명한다.


## 이 문서에서 되짚을 질문

- 정규화는 왜 필요한가?
- 함수 종속은 정규화의 기준으로 어떻게 쓰이는가?
- 1NF·2NF·3NF·BCNF·4NF·5NF는 각각 어떤 종속성을 다루는가?
- 함수 종속(FD)과 다치 종속(MVD), 결합 종속(JD)은 어떻게 다른가?
- 반정규화는 정규화의 반대인가, 성능을 위한 의도적 Trade-off인가?

## 1. 정규화가 필요한 이유

한 Table에 서로 다른 사실을 함께 저장하면 같은 정보가 여러 Row에 반복되고, 그 중복이 이상현상(Anomaly)을 만든다.

```text
서로 다른 사실을 한 Table에 중복 저장
        ↓
갱신 이상 · 삽입 이상 · 삭제 이상
        ↓
함수 종속을 기준으로 사실의 책임 분리
        ↓
정규화
```

- 갱신 이상: 같은 사실을 여러 Row에서 함께 바꿔야 한다.
- 삽입 이상: 한 사실을 저장하려고 관련 없는 값을 억지로 넣어야 한다.
- 삭제 이상: 한 사실을 지우다가 다른 독립적인 사실까지 잃는다.

정규화의 목적은 Table 수를 늘리는 것이 아니라 **하나의 사실을 한 책임 위치에 두어 중복과 변경 불일치를 줄이는 것**이다.

## 2. 함수 종속

`X → Y`는 X가 정해지면 Y가 하나로 결정된다는 뜻이다.

```text
customer_id → customer_name
product_id  → product_name
```

### 결정자·종속자·Key의 관계

```text
함수 종속(FD)
     X ───────→ Y
     │          │
   결정자      종속 속성
 Determinant   Dependent

예: 학과ID → 학과명
    학과ID는 학과명을 결정하지만
    학생(학생ID, 학과ID, 학과명) Relation에서는
    학과ID만으로 학생 Row 전체를 식별할 수 없음
```

**결정자(Determinant)는 함수 종속 `X → Y`의 왼쪽 속성 집합 X**다. 결정자는 특정 속성을 결정하는 기준이지, 반드시 Relation의 Key인 것은 아니다.

```text
결정자 X
├─ Superkey인 경우     → Row 전체를 유일하게 식별
│  └─ 후보 Key         → 최소 Superkey
└─ Superkey가 아닌 경우 → Y는 결정해도 Row 전체는 식별 못함
```

### 자명·비자명 함수 종속을 구분한다

```text
             함수 종속 X → Y
                    │
          Y가 X에 포함되는가?
                    │
           ┌────────┴────────┐
           │                 │
          YES                NO
           │                 │
       자명 FD            비자명 FD
       (Trivial)          (Non-trivial)
           │                 │
 {학번, 이름} → 이름       학번 → 이름
   이미 왼쪽에 있음       업무 규칙으로 결정
```

- **자명 FD:** `Y ⊆ X`. 오른쪽 속성이 왼쪽 집합에 이미 포함되므로 언제나 성립한다.
- **비자명 FD:** `Y ⊈ X`. 오른쪽에 왼쪽에 없는 속성이 하나 이상 포함된다. 실제로 성립하는지는 업무 제약에 달려 있다.
- **완전 비자명 FD:** `X ∩ Y = ∅`. 양쪽 속성 집합이 겹치지 않는 비자명 FD다.

예를 들어 `{학번, 이름} → {이름, 학과}`는 일부 속성(이름)이 겹치더라도 학과가 왼쪽에 없으므로 **비자명 FD**다. 비자명이라는 말이 '반드시 성립하는 함수 종속'이라는 뜻은 아니다.

**BCNF가 자명 FD를 제외하는 이유:** `{학번, 이름} → 이름`은 결정자가 후보키인지와 관계없이 항상 성립하는 포함 관계다. BCNF는 이런 당연한 FD가 아니라 **새로운 속성을 결정하는 비자명 FD의 왼쪽이 Superkey인지** 검사한다.

BCNF는 **모든 비자명 FD의 결정자가 Superkey인지** 확인한다. `X → Y`에서 Y가 X에 포함되는 자명한 FD는 이 제한의 대상이 아니다.

정규화에서는 어떤 Attribute가 실제로 어느 결정자(Determinant)에 속하는지를 본다. 핵심 질문은 다음과 같다.

> 이 값은 정말 현재 Key 전체의 속성인가?

## 3. 정규형을 한 흐름으로 보기

| 정규형 | 제거하려는 문제 | 기억할 질문 |
|---|---|---|
| 1NF | 반복 Group·다중값 | 한 Cell에 하나의 값인가? |
| 2NF | 복합 Key 일부에 대한 부분 종속 | Key 전체에 종속되는가? |
| 3NF | 비 Key Attribute를 거치는 이행 종속 | Key에 직접 종속되는가? |
| BCNF | Superkey가 아닌 결정자 | 모든 비자명 함수 종속의 결정자가 Superkey인가? |
| 4NF | 독립적인 다치 종속(MVD)으로 인한 중복 | 비자명 MVD의 결정자가 Superkey인가? |
| 5NF | 결합 종속(JD)으로 인한 분해 가능한 중복 | 모든 비자명 JD가 후보 Key로부터 함의되는가? |

### 정규형 만족 조건 — 암기와 판정을 구분한다

아래 표는 **정규형의 만족 조건**을 먼저 인출하고, 오른쪽에서 **대표적으로 해결하는 문제**를 연결하기 위한 것이다. 단순 암기 문구와 엄밀한 판정 조건을 혼동하지 않는다.

| 정규형 | 만족 조건 | 대표적인 위반·해결 대상 |
|---|---|---|
| 1NF | 각 Attribute 값이 해당 도메인에서 원자적인 단일 값 | 반복 Group·다중값 |
| 2NF | 1NF + 비주요 속성이 어떤 후보 Key의 진부분집합에도 함수 종속되지 않음 | 부분 함수 종속 |
| 3NF | 모든 비자명 FD `X → A`에서 X가 Superkey이거나 A가 Prime Attribute | 비주요 속성의 이행 종속(대표 형태) |
| BCNF | 모든 비자명 FD `X → Y`에서 X가 Superkey | Superkey가 아닌 결정자 |
| 4NF | 모든 비자명 MVD `X ↠ Y`에서 X가 Superkey | 독립 다치 값의 중복 조합 |
| 5NF | 모든 비자명 JD가 후보 Key로부터 함의됨 | 더 분해 가능한 결합 종속 |

`Prime Attribute`는 **어느 하나의 후보 Key에라도 포함된 속성**이고, 비주요 속성(Non-prime Attribute)은 어떤 후보 Key에도 포함되지 않은 속성이다. 3NF의 엄밀한 정의에서 오른쪽을 단일 속성 A로 쓰는 것은 다중 속성의 FD를 속성별로 나누어 검사할 수 있기 때문이다.

```text
[시험에서 조건을 인출]
1NF  → 원자값
2NF  → 비주요 속성의 부분 종속 없음
3NF  → 결정자가 Superkey OR 오른쪽이 Prime
BCNF → 모든 비자명 FD의 결정자가 Superkey
4NF  → 모든 비자명 MVD의 결정자가 Superkey
5NF  → 모든 비자명 JD가 후보 Key로부터 함의

[실제 Relation 판정]
업무 규칙 → FD/MVD/JD 식별 → 후보 Key·Superkey 확인
         → 정규형 조건 대조 → 위반 시 무손실 분해
         → 필요하면 종속성 보존과 운영 비용 검토
```

**'2NF는 부분 종속 제거', '3NF는 이행 종속 제거'**는 대표적인 문제를 기억하는 문장이다. 반면 정규형을 엄밀하게 판정할 때는 위의 만족 조건을 적용한다. 4NF와 5NF도 기존 정규형 조건을 포함하는 더 강한 정규형이다.

### 정규형이 높아질수록 검사하는 종속성이 확장된다

```text
정규화의 검사 관점
│
├─ 1NF          → 값의 원자성 (FD 검사 단계는 아님)
│
├─ 2NF ~ BCNF   → 함수 종속(FD)
│  ├─ 2NF       → 비주요 속성의 부분 종속
│  ├─ 3NF       → 비주요 속성의 이행 종속 (대표 위반 형태)
│  └─ BCNF      → 모든 비자명 FD의 결정자는 Superkey
│
├─ 4NF          → 다치 종속(MVD)
│  └─ 모든 비자명 MVD의 결정자는 Superkey
│
└─ 5NF          → 결합 종속(JD)
   └─ 모든 비자명 JD가 후보 Key로부터 함의
```

```text
종속성의 포괄 관계
FD (X → Y) → MVD (X ↠ Y) → JD (투영·JOIN 복원 제약)
    │            │                  │
  BCNF          4NF                5NF

정규형의 강도: 5NF ⇒ 4NF ⇒ BCNF ⇒ 3NF ⇒ 2NF ⇒ 1NF
```

이 화살표는 **함의·특수한 경우의 관계**를 뜻한다. FD는 MVD를 함의하고, MVD는 두 투영으로 복원되는 JD의 특수한 경우다. 따라서 4NF가 함수 종속을 무시하거나 5NF가 다치 종속을 무시하는 것이 아니다. **기존 조건을 충족하면서 검사하는 제약의 범위가 넓어지는 것**이다.

- **BCNF:** 어떤 값을 결정하는 X가 Relation 전체를 식별할 수 있는가?
- **4NF:** X에 속한 여러 값의 집합이 나머지 속성과 독립적으로 조합되는가?
- **5NF:** 여러 투영 Relation을 JOIN해 정확히 복원해야 하는 결합 제약이 있는가?

4NF와 5NF에서는 단순히 값이 여러 개이거나 Table을 나눌 수 있다는 이유만으로 정규화를 결정하지 않는다. **업무 규칙에서 실제 MVD·JD가 성립하는지와 무손실 분해 여부**를 확인한다.

### 1NF — 값의 원자성

한 Column에 여러 값을 문자열처럼 묶지 않고 관계형 모델이 다룰 수 있는 단일 값 단위로 표현한다.

### 2NF — 부분 종속 제거

복합 Key `(A, B)`가 있는데 비 Key Attribute가 `A` 하나만으로 결정된다면 부분 종속을 분리해야 한다.

한 학기의 수강 정보를 예로 보자. 학생 ID는 학생명을, 과목 ID는 과목명을 결정하고, 학생은 같은 과목을 한 번만 수강한다고 가정한다. 아래 Row는 이 업무 규칙을 보여주는 예시이지, 몇 개의 Row만 보고 함수 종속을 추측하는 근거가 아니다.

```text
[분해 전]
수강(학생ID, 과목ID, 학생명, 과목명, 성적)
  (S1, C1, 민수, DB, A)
  (S1, C2, 민수, OS, B)
  (S2, C1, 영희, DB, B)

Key = (학생ID, 과목ID)

학생ID ──────────→ 학생명  : Key 일부에 종속
과목ID ──────────→ 과목명  : Key 일부에 종속
(학생ID, 과목ID) ─→ 성적    : Key 전체에 종속
```

학생명이 바뀌면 S1의 두 Row를 함께 바꿔야 하고, C2의 마지막 수강 Row를 지우면 OS라는 과목 정보까지 잃는다. 이를 함수 종속에 따라 분해한다.

```text
[분해 후]
학생(학생ID, 학생명)
  (S1, 민수), (S2, 영희)

과목(과목ID, 과목명)
  (C1, DB), (C2, OS)

수강(학생ID, 과목ID, 성적)
  (S1, C1, A), (S1, C2, B), (S2, C1, B)

수강 ── 학생ID로 JOIN ──→ 학생
수강 ── 과목ID로 JOIN ──→ 과목
```

이제 학생명은 학생 Table에서 한 번만 수정하고, 수강 여부와 독립적으로 과목을 저장할 수 있다. 두 JOIN으로 원래의 정보를 복원할 수 있으므로 **정보를 버리는 것이 아니라 사실의 저장 책임을 옮긴 것**이다.

### 3NF — 이행 종속 제거

```text
Key → A → B
```

처럼 B가 Key가 아니라 다른 비 Key Attribute A에 의해 결정된다면 B의 사실을 분리한다.

앞의 학생 Table에 학과 정보를 추가한다고 하자. 학생은 한 학과에 소속되고, 학과 ID가 학과명을 결정한다고 가정한다.

```text
[분해 전]
학생(학생ID, 학생명, 학과ID, 학과명)

학생ID ─→ 학과ID ─→ 학과명
          └─ 학과명은 학생보다 학과의 속성

[분해 후]
학생(학생ID, 학생명, 학과ID)
학과(학과ID, 학과명)

학생 ── 학과ID로 JOIN ──→ 학과
```

학과명이 바뀌어도 그 학과 학생 전체를 수정하지 않고 학과 Table의 한 Row만 수정하면 된다. 앞의 2NF 예제는 **복합 Key의 일부**, 이 예제는 **다른 비 Key Attribute를 거친 종속**을 분리한다는 차이가 있다.

위 설명은 대표적인 학습 형태다. 엄밀한 3NF는 비자명 함수 종속 `X → A`마다 **X가 Superkey이거나 A가 어떤 후보 Key에 포함되는 Attribute**일 것을 요구한다. 후보 Key가 겹치는 경우에는 다음 BCNF와 차이가 생길 수 있다.

### BCNF — 결정자 자체를 본다

3NF보다 더 엄격하게 모든 비자명 함수 종속 `X → Y`에서 X가 **Superkey**인지 확인한다. Superkey는 Row를 유일하게 식별하는 속성 집합이고, 후보 Key는 그중 불필요한 속성이 없는 최소 집합이다. 따라서 조건을 `모든 결정자가 후보 Key`라고 좁혀 외우지 않는다.

```text
학생(학번, 이름, 학과)  — 학번이 유일하다고 가정
후보 Key: {학번}
Superkey: {학번}, {학번, 이름}, {학번, 이름, 학과}, ...

{학번, 이름} → 학과
   └─ 결정자는 후보 Key가 아니지만 Superkey
      → BCNF 위반이 아님
```

교재의 **'모든 결정자가 후보키'**는 최소 결정자를 중심으로 한 암기용 축약 표현으로 이해할 수 있지만, 임의의 비자명 FD에 그대로 적용하면 부정확하다. 정확한 판정은 **모든 비자명 FD의 결정자가 Superkey**라는 조건이다.

후보 Key가 여러 개이고 겹치는 구조에서 3NF로 남을 수 있는 이상을 더 제거한다.

### 왜 3NF 다음이 BCNF인가?

```text
3NF  → 비자명 FD X → A에서
       X가 Superkey이거나 A가 Prime Attribute이면 허용
                  │
                  │ Prime Attribute 예외가 남음
                  ▼
BCNF → 모든 비자명 FD의 결정자 X가 Superkey
                  │
                  │ FD만으로 설명되지 않는
                  │ 독립적인 다치 값의 중복이 남을 수 있음
                  ▼
4NF  → 모든 비자명 MVD의 결정자가 Superkey
                  │
                  ▼
5NF  → 후보 Key로부터 함의되지 않는 JD를 제거
```

3NF는 종속 속성 A가 **후보 Key의 일부인 Prime Attribute**라면 결정자 X가 Superkey가 아니어도 허용한다. BCNF는 이 예외를 제거해 함수 종속에 관한 조건을 강화한 것이다. **BCNF(Boyce–Codd Normal Form)**는 Boyce와 Codd의 이름을 딴 명칭으로, 3NF보다 강한 정규형으로 자리 잡았다. 4NF는 이를 단순히 '다음 숫자'로 바꿔 부른 것이 아니라 **다치 종속(MVD)**이라는 더 넓은 종속성 문제를 다룬다.

주의할 점은 **4NF가 BCNF를 포함하는 더 강한 조건**이라는 것이다. 모든 함수 종속은 다치 종속을 함의하므로, 4NF를 만족하면 BCNF도 만족한다. 5NF는 결합 종속(JD)까지 다룬다.

### BCNF 분해 예제 — 3NF로도 남는 함수 종속

한 학생이 과목별로 강사를 선택하고, **강사마다 담당 과목이 하나로 정해져 있다**고 가정한다. 한 과목에 여러 강사가 있을 수 있으며 학생은 과목마다 한 강사를 선택한다.

```text
수강배정(학생, 과목, 강사)
후보 Key: (학생, 과목), (학생, 강사)

함수 종속
(학생, 과목) → 강사
강사 → 과목

강사 → 과목에서
  강사는 Superkey가 아님
  과목은 후보 Key의 일부(Prime Attribute)
→ 3NF는 만족할 수 있지만 BCNF는 위반
```

```text
[분해 전]
학생  과목  강사
민수  DB    김교수
영희  DB    김교수
철수  OS    이교수

[분해 후]
강사과목(강사, 과목)
  김교수 DB
  이교수 OS

학생강사(학생, 강사)
  민수 김교수
  영희 김교수
  철수 이교수
```

강사의 담당 과목이 바뀌면 원래 Table에서는 여러 수강 Row를 수정해야 할 수 있다. 분해 후에는 강사과목에서 한 번만 수정한다. 이 예제의 분해는 **무손실**이지만, 원래의 `(학생, 과목) → 강사` 제약을 분해된 개별 Relation만으로 검사하기 어려워질 수 있다. BCNF 분해에서는 **무손실 분해와 함수 종속 보존의 Trade-off**를 확인해야 한다.

### 4NF — 독립적인 다치 종속(MVD)

함수 종속 `X → Y`는 X마다 Y가 **하나로 결정**된다는 뜻이다. 반면 다치 종속 `X ↠ Y`는 X가 정해졌을 때 Y의 **값 집합이 나머지 속성의 값과 독립적으로 조합**된다는 뜻이다.

#### 실무에서 다치 종속을 식별하는 관점

**범주형 필드가 두 개 있다고 곧바로 MVD가 성립하는 것은 아니다.** 범주형 여부가 아니라 **공통 기준 X에 연결된 Y 값 집합이 나머지 Z와 독립적인지**를 확인한다.

```text
R(X, Y, Z) — 세 속성 영역
│
├─ X : 공통 기준       (회원ID)
├─ Y : 여러 값의 집합  (관심분야)
└─ Z : 다른 값의 집합  (자격증)
       │
       ▼
X ↠ Y : 같은 X에서 Y 값 집합이 Z와 독립
       │
       ▼
비자명 MVD인가? (Y ⊈ X, X ∪ Y ≠ R)
       │ YES
       ▼
X가 Superkey인가?
├─ YES → 해당 MVD는 4NF 위반 아님
└─ NO  → 4NF 위반, 독립 사실 분해 검토
```

`회원(회원ID, 회원등급)`처럼 회원마다 등급 하나만 정해지면 `회원ID → 회원등급`인 **함수 종속**이다. 반면 `회원관심자격(회원ID, 관심분야, 자격증)`에서 한 회원의 관심분야와 자격증이 각각 여러 개이고 서로 독립적이면 `회원ID ↠ 관심분야`라는 **비자명 다치 종속**을 검토한다.

여기서 `회원ID`는 회원관심자격의 Row 전체를 유일하게 식별하지 못하므로 Superkey가 아니다. **BCNF를 이미 만족하더라도, BCNF는 FD의 결정자만 검사했기 때문에 이 MVD의 결정자까지 Superkey라고 보장하지 않는다.**

```text
[BCNF를 만족하지만 4NF는 위반할 수 있는 이유]
회원ID → 관심분야   : 성립하지 않음 (값이 여러 개)
회원ID ↠ 관심분야  : 성립 (자격증과 독립)
       │
       └─ 회원ID는 Superkey 아님 → 4NF 위반

[분해 후]
회원관심분야(회원ID, 관심분야)
회원자격증(회원ID, 자격증)
→ 각 Relation의 해당 MVD는 자명해져 4NF 위반 아님
```

**세 속성 영역 X·Y·Z가 필요하다는 것은 비자명 MVD의 구조적 조건**이지, 반드시 '범주형 필드 두 개'가 있어야 한다는 뜻이 아니다. 전화번호·주소처럼 범주형이 아닌 값도 해당할 수 있다. 또한 모든 조합을 일부러 만들라는 뜻이 아니라, 독립적인 두 집합을 하나의 Relation에 함께 표현하면 조합 중복이 발생한다는 설명이다.

한 학생의 취미와 외국어 능력이 서로 독립적이라고 가정한다. 민수의 취미는 축구·독서이고 언어는 영어·일본어다.

```text
[분해 전: 학생취미언어]
학생  취미  언어
민수  축구  영어
민수  축구  일본어
민수  독서  영어
민수  독서  일본어

학생 ↠ 취미
학생 ↠ 언어

취미 2개 × 언어 2개 → 4 Row
취미와 언어는 서로 독립인데 모든 조합을 반복 저장
```

```text
[4NF 분해]
학생취미(학생, 취미)
  민수 축구
  민수 독서

학생언어(학생, 언어)
  민수 영어
  민수 일본어

학생취미 ⋈ 학생언어
  → 원래 4개 조합 복원 (무손실)
```

4NF에서는 **모든 비자명 MVD `X ↠ Y`에 대해 X가 Superkey**여야 한다. 이 예제에서는 `학생`만으로 각 Row를 식별할 수 없으므로 분해 대상이다. 단, 취미와 언어의 조합 자체에 업무 의미가 있다면 독립 MVD라고 가정할 수 없고 무조건 분해해서도 안 된다.

### 5NF — 결합 종속(JD)

**5NF는 'JOIN하면 가짜 Row가 생기는 문제를 해결하는 정규형'이 아니다.** 오히려 **업무 규칙상 여러 Relation으로 나누어도 JOIN으로 원본을 항상 정확히 복원할 수 있는 경우**에, 불필요한 삼중 관계 저장을 줄일 수 있는지 검토한다.

#### 먼저 구분 — JOIN 가능과 결합 종속은 다르다

```text
원본 R(S, P, J)
     │
     ├─ SP(공급자, 부품)
     ├─ SJ(공급자, 프로젝트)
     └─ PJ(부품, 프로젝트)
               │
               ▼
          SP ⋈ SJ ⋈ PJ
               │
      ┌────────┴────────┐
      │                 │
   원본과 동일        원본에 없던 Row 발생
      │                 │
 현재 데이터에서       가짜 Tuple
 복원 성공             → 이 분해는 손실 발생
      │
      ▼
 모든 유효한 데이터에서도 항상 같은가?
      └─ 업무 규칙으로 보장되어야 JD 성립
```

**현재 데이터에서 JOIN 결과가 우연히 같다는 것만으로 JD가 성립하는 것은 아니다.** 반대로 JOIN에서 가짜 Tuple이 생기면 해당 분해는 무손실이 아니므로 실행해서는 안 된다.

#### 사례 — 세 쌍의 사실이 삼중 관계를 보장하는가?

공급자(S)·부품(P)·프로젝트(J)의 삼중 관계 `SPJ`를 관리한다고 하자.

```text
SP : S1이 P1을 취급한다
SJ : S1이 J1에 참여한다
PJ : J1이 P1을 사용한다

이 세 사실만으로
S1이 J1에 P1을 공급한다고 단정할 수 있는가?
→ 일반적으로 NO
```

실제 공급은 다른 회사가 맡을 수도 있다. 이 경우 삼중 관계에는 쌍 관계만으로는 알 수 없는 **추가 사실**이 있으므로 `SPJ`를 세 쌍으로 분해하면 가짜 Tuple이 생길 수 있다.

반대로 **'세 쌍의 관계가 모두 성립하면 그 삼중 관계도 반드시 성립한다'**는 업무 규칙이 *정말로* 존재한다면, 그 규칙에 따라 `SPJ = SP ⋈ SJ ⋈ PJ`가 항상 성립할 수 있다. 이때 JD `*(SP, SJ, PJ)`를 검토한다.

```text
[업무 규칙이 JD를 보장하는 경우의 작은 예]
SPJ(공급자, 부품, 프로젝트)
  (S1, P1, J1)
  (S1, P2, J1)
  (S2, P1, J1)

SP = {(S1,P1), (S1,P2), (S2,P1)}
SJ = {(S1,J1), (S2,J1)}
PJ = {(P1,J1), (P2,J1)}

SP ⋈ SJ ⋈ PJ = SPJ
```

위 데이터는 **JOIN 복원 방식의 예시일 뿐, 이 세 행만으로 비자명 JD나 5NF 위반을 증명하는 예제는 아니다.** 5NF 위반 여부는 해당 Relation에 **후보 Key로부터 함의되지 않는 비자명 JD**가 업무 제약으로 성립하는지를 따져야 한다.

#### 5NF에서 실제로 판단하는 것

```text
업무 규칙 확인
      │
      ▼
비자명 결합 종속(JD)이 존재하는가?
      │ YES
      ▼
그 JD가 후보 Key로부터 함의되는가?
      ├─ YES → 해당 JD는 5NF 위반 아님
      └─ NO  → 5NF 위반
                │
                ▼
       JD에 따라 무손실 분해
       (가짜 Tuple 없이 복원)
```

**4NF와의 경계:** 4NF는 독립적인 다치 값 집합에 관한 MVD를 검사한다. 5NF는 그보다 일반적인 JD를 검사하며, **세 개 이상의 투영으로 나누어야 드러나는 분해**가 대표적이다. 하지만 '세 테이블로 나눈다'는 사실 자체가 5NF의 정의는 아니다.

**나중에 복습할 인출 문장:** *'쌍 관계만으로 삼중 관계가 반드시 결정되는가? 업무 규칙으로 보장되지 않으면 분해하지 않는다.'* 이 질문은 JD를 직관적으로 확인하는 출발점이고, 최종 5NF 판정에는 후보 Key 조건까지 필요하다.

### 정규형 인출 구조

```text
정규화의 판단 기준
├─ 1NF  → 원자값·반복 Group
├─ 2NF  → 부분 함수 종속
├─ 3NF  → 이행 함수 종속 (대표 형태)
├─ BCNF → 모든 비자명 FD의 결정자는 Superkey
├─ 4NF  → 모든 비자명 MVD의 결정자는 Superkey
└─ 5NF  → 모든 비자명 JD는 후보 Key로부터 함의

FD  : X → Y  (하나로 결정)
MVD : X ↠ Y  (독립적인 값 집합)
JD  : 여러 투영을 JOIN해 원본 복원하는 제약
```

정규화는 **종속성·업무 제약을 먼저 확인한 뒤 무손실 분해**해야 한다. 정규형이 높다고 언제나 실무에 더 적합한 것은 아니며, 고급 정규형은 해당 종속성이 실제로 존재하는지부터 확인한다.

## 4. 정규화와 반정규화의 관계

정규화는 변경 정확성과 무결성에 유리하지만 Relation이 나뉘면서 조회 시 JOIN 비용이 늘 수 있다.

```text
정규화
→ 중복 감소 · 변경 일관성 향상
→ JOIN 증가 가능

읽기 병목이 실제로 확인됨
→ 일부 중복을 의도적으로 허용
→ 반정규화
```

따라서 반정규화는 정규화를 몰라서 Table을 합치는 것이 아니다. **정규화된 구조와 중복의 위험을 이해한 상태에서 측정된 성능 문제를 해결하기 위해 읽기 비용을 쓰기·일관성 관리 비용으로 바꾸는 선택**이다.

반정규화 전에는 다음을 확인한다.

1. 실제 JOIN이 병목인가?
2. Index·Query·실행계획 개선으로 해결되지 않는가?
3. 어떤 중복값을 누가 갱신할 것인가?
4. 불일치 탐지·복구 수단이 있는가?

**정규화는 함수 종속과 다치·결합 종속 등 업무 제약을 따라 사실의 저장 책임을 올바른 Relation으로 옮기는 과정**이다. 막히는 부분만 다시 읽는다.
