# 데이터베이스 개념지도

> 데이터베이스는 **업무 데이터를 공통 구조로 관리하고, 정확성·동시성·장애·성능·확장 문제를 해결하면서 안전하게 활용하는 체계**다.

## 1. 데이터베이스 전체 좌표

```text
현실의 업무
  ↓
DBMS 기초
├─ ANSI/SPARC 3-Schema → 외부·개념·내부 관점 / 데이터 독립성
├─ Schema / Instance
└─ DDL / DML / DCL
  ↓
데이터 모델링
  ↓
Schema · Key · 무결성
  ↓
정규화 / 반정규화
  ↓
관계형 모델 · SQL
  │
  ├────────────────┬────────────────┐
  ▼                ▼                ▼
신뢰성             성능             확장
Transaction        Optimizer        Replication
동시성 · 회복      Index            Sharding
                   Partition        분산 DB

[별도 활용 축]
OLTP ↔ DW / OLAP / BI

[전 영역 관리 축]
보안 · 품질 · 표준 · Metadata · Governance
```

처음에는 **업무를 데이터 구조로 옮기는 기반**을 잡고, 그 위에서 `신뢰성 · 성능 · 확장`이라는 서로 다른 시스템 문제를 본다. 세 가지는 발전 단계가 아니라 같은 데이터 시스템을 보는 서로 다른 문제 축이다.

`분석 활용`은 운영 DB의 다음 단계가 아니라 목적이 다른 활용 축이고, `보안 · 품질 · 표준 · Metadata · Governance`는 구조화부터 활용까지 전체를 가로지른다.

## 2. 어디를 파고들 것인가

### DBMS 3-Schema · 데이터 독립성

ANSI/SPARC 3-Schema는 **사용자별 데이터 관점, DB 전체의 논리 구조, 내부 저장 구조**를 분리해 변경의 영향을 줄이는 아키텍처 관점이다.

```text
             사용자 · Application
                       │
          ┌────────────┴────────────┐
          ▼                         ▼
     외부 스키마 A              외부 스키마 B
     (영업 View)                (정산 View)
          │                         │
          └────────────┬────────────┘
                       ▼
                  개념 스키마
             DB 전체의 논리 구조
          Entity · 관계 · 제약조건
                       │
                       ▼
                  내부 스키마
             File · Index · 저장 구조
                       │
                       ▼
                   물리 저장

외부 ↔ 개념 스키마 변경 영향 분리 → 논리적 데이터 독립성
개념 ↔ 내부 스키마 변경 영향 분리 → 물리적 데이터 독립성
```

예를 들어 주문 데이터를 사용하는 영업·정산 Application은 서로 다른 외부 View를 가질 수 있지만, DB 전체에서는 주문과 회원의 관계 및 무결성 제약을 하나의 개념 스키마로 정의한다. 인덱스나 파일 배치를 바꿔도 이 논리 구조를 유지할 수 있는 성질이 **물리적 데이터 독립성**이다. 반대로 개념 스키마의 일부 구조를 변경해도 기존 외부 View와 Application에 미치는 영향을 최소화할 수 있는 성질이 **논리적 데이터 독립성**이다. 두 독립성 모두 변경 영향의 최소화를 뜻하며 모든 변경을 자동으로 숨긴다는 보장은 아니다.

`Schema`는 데이터 구조·제약의 정의이고, `Instance`는 특정 시점의 실제 데이터 상태다. **ANSI/SPARC의 개념 스키마는 설계 단계의 개념 데이터 모델과 같은 용어가 아니다.** 전자는 DB 전체의 논리 구조를 설명하는 아키텍처 계층이고, 후자는 업무의 Entity·관계를 추상화한 설계 산출물이다.

### 데이터 구조화 · 관계형 모델

```text
현실의 업무 · 요구사항
   ↓
개념 모델링 → Entity · Attribute · 관계 (업무 의미)
   ↓
논리 모델링 → Relation · Key · 제약조건 (논리 구조)
   ↓
물리 설계   → 저장 구조 · Index · Partition (접근·성능)
   │
   └─ Schema
   │
   ├─ 함수 종속 · 중복 · 갱신 이상
   │        ↓
   │      정규화
   │        → 중복과 이상 현상 감소
   │
   └─ 성능 · 운영 요구
            ↓
         반정규화

관계형 DB
→ Relation을 SQL로 정의 · 조회 · 변경
```

모델링의 개념·논리·물리 단계는 **설계의 상세 수준**이고, Chen·Crow's Foot·IDEF1X는 **그림의 표기법**이다. Chen은 개념 모델에서, Crow's Foot·IDEF1X는 논리·물리 모델에서 자주 사용하지만 특정 단계에 고정되지는 않는다. 여기서 말하는 개념 모델은 ANSI/SPARC의 개념 스키마와도 구분한다.

핵심은 현실의 업무 의미를 관계형 구조로 옮기고, `Key · 무결성 · 정규화`로 데이터의 일관성과 변경 비용을 통제하는 것이다. 반정규화는 정규화의 반대 이론이라기보다 성능·운영 요구에 따라 구조를 의도적으로 조정하는 선택으로 본다.

→ [정규화 · 함수 종속 · 정규형 · 반정규화](정규화-함수종속-정규형-반정규화.md) — 이상현상의 원인과 정규형의 차이, 반정규화의 선택 기준

### Transaction · 동시성 · 회복

```text
Transaction — ACID
├─ Atomicity   → 전부 반영하거나 전부 취소
├─ Consistency → 정의된 무결성 규칙 유지
├─ Isolation   → 동시 실행 간 간섭 제어
└─ Durability  → Commit 결과 유지

[동시성 제어] Isolation Level / Lock·2PL / MVCC
[장애 회복]
├─ Log 기반 회복 → Undo(미완료 취소) / Redo(완료 재적용)
│                 └─ Checkpoint(회복 탐색 범위 축소)
└─ Shadow Paging → 변경 Page를 별도로 관리하고 Commit 시 전환

[별도 복구 수단] Backup / Restore → 저장 매체 손상·데이터 유실 대응
```

동시성 제어는 병행 실행의 간섭을, 회복은 장애 뒤의 원자성·지속성을 다룬다. **Log 기반 회복 ↔ Shadow Paging**은 대표 회복 기법의 비교 축이므로 지도에 유지한다. 세부 구현 절차와 WAL·LSN·ARIES 등의 내부 규칙은 필요할 때 별도로 학습한다.

→ [Transaction · 동시성 · 격리수준 · Lock · MVCC](트랜잭션-동시성-격리수준-Lock-MVCC.md) — 동시 실행과 격리 원리

### Query Engine · 물리 접근 구조

```text
Query Engine

┌────────┐   ┌──────────┐   ┌───────────┐   ┌──────────┐
│ Parser │ → │ Rewriter │ → │ Optimizer │ → │ Executor │
└────────┘   └──────────┘   └───────────┘   └──────────┘
                                │
                                ├─ Rule Based / Cost Based
                                ├─ Statistics
                                │   ├─ Selectivity
                                │   └─ Cardinality
                                ├─ Access Path
                                ├─ Join Order
                                └─ Join Algorithm
                                    ├─ Nested Loop
                                    ├─ Sort Merge
                                    └─ Hash Join
                                ↓
                         Execution Plan
```

Query Engine은 `Parser → Rewriter → Optimizer → Executor` 순서로 SQL을 처리한다. 이 흐름에서 Cost Based Optimizer는 통계와 추정 비용을 바탕으로 Access Path, Join Order, Join Algorithm을 비교해 Execution Plan을 만든다. Rule Based Optimizer는 사전에 정한 규칙과 우선순위를 따른다. Executor는 선택된 Plan을 실제로 수행한다.

```text
Physical Access Structure
├─ Hashing
│   ├─ Hash Function
│   └─ Collision → Chaining / Open Addressing
│
├─ Index
│   ├─ B-Tree / B+Tree
│   ├─ Clustered / Nonclustered
│   ├─ Hash Index
│   └─ Bitmap Index
│
└─ Partition
    └─ Partition Pruning
```

Index와 Partition은 Query Engine의 구성요소라기보다 Optimizer가 실행전략을 정할 때 활용하는 물리 구조다.

```text
Index / Partition
       ↓
Optimizer의 Access Path 판단에 활용
       ↓
Execution Plan에 반영
```

### 분산 · 확장

```text
Scale Out

┌─────────────┐            ┌──────────┐
│ Replication │            │ Sharding │
└─────────────┘            └──────────┘
      │                          │
      ▼                          ▼
같은 Data 복제              Data 분할
      │                          │
      ├─ Read Scale              ├─ Capacity
      ├─ Availability            └─ Write Scale
      └──────────────┬───────────┘
                     ▼
              Distributed DB
                     │
       ┌─────────────┼─────────────┐
       ▼             ▼             ▼
 Consistency    Transaction     Coordination
       │             │             │
 CAP / PACELC   Distributed Tx   Consensus
```

Replication과 Sharding은 모두 단일 DB의 용량·처리량·가용성 한계를 넘기 위한 Scale Out 수단이지만, 해결하는 문제는 다르다. Replication은 같은 Data를 여러 Node에 복제해 읽기 확장과 가용성을 높이고, Sharding은 Data 자체를 나눠 용량과 쓰기 처리량을 확장한다.

Data가 여러 Node에 걸쳐 존재하면 일관성·분산 Transaction·Node 간 조정 문제가 생긴다. `CAP`는 네트워크 분할 시 일관성과 가용성의 선택을, `PACELC`는 정상 상황의 지연시간과 일관성 간 Trade-off까지 떠올리는 단서다. `Distributed Transaction`은 여러 Node에 걸친 작업의 원자성을, `Consensus`는 Node 사이의 합의된 결정과 상태 조정을 다룬다.

- Sharding · Distributed Transaction · Consensus → [Sharding · 분산 Transaction · 합의](샤딩-분산트랜잭션-합의.md)

### 분석 활용

운영과 분석은 같은 Data를 사용하더라도 목적과 Workload가 다르다.

```text
[운영]
OLTP
├─ 현재 업무 상태 처리
├─ 빈번한 Insert / Update
└─ 짧은 Transaction

[분석]
Operational Data
      ↓
   ETL / ELT
      ↓
      DW
주제지향 · 통합 · 시간변이 · 비휘발성
      │
      ├─ OLAP → 다차원 · 집계 분석
      ├─ Data Mining → 분류 · 군집 · 연관 규칙 탐색
      └─ 보고 · Dashboard
                ↓
         BI · 의사결정 지원

※ OLAP · Data Mining · 보고는 필수적인 순차 단계가 아닌 대표 활용 방식이다.
```

OLTP는 현재 업무 상태를 빠르게 처리하는 데 초점이 있고, DW · OLAP · BI는 축적된 Data를 통합·집계하여 분석하고 의사결정을 지원하는 데 초점이 있다.

### DBMS를 구분하는 관점

DBMS는 하나의 기준으로만 분류되지 않는다. 같은 DBMS가 여러 관점의 특성을 동시에 가질 수 있다.

```text
DBMS 분류 관점
├─ Data Model     → RDBMS / OODBMS / ORDBMS / NoSQL 계열
├─ 저장 방식      → Disk 중심 / MMDB
├─ 실행 형태      → Embedded / Server
├─ 분산 여부      → 단일 Node / Distributed DB
└─ Workload       → OLTP / OLAP / Streaming
```

전체 지도에서는 제품별 차이보다 **어떤 질문으로 DBMS를 구분하는지**를 기억한다. Data Model은 표현·질의 방식, 저장 방식은 메모리·디스크 접근 특성, 실행 형태는 배포·운영 구조, 분산 여부는 확장·가용성, Workload는 처리 목적과 연결된다. 특히 NoSQL과 Distributed DB는 같은 분류축이 아니며 서로 배타적인 유형도 아니다.

### Data Management · Governance

Data를 저장하고 활용하는 전 과정에는 별도의 관리 관점이 가로지른다.

```text
Data Management
├─ Data Quality
│   └─ 정확성 · 완전성 · 일관성
├─ Metadata
│   └─ Data의 의미 · 구조 · 위치
├─ Data Standard
│   └─ 공통 명칭 · 형식 · 정의
├─ Security
│   └─ 접근 통제 · 보호
└─ Governance
    └─ 정책 · 책임 · 통제
```

품질은 데이터가 요구사항에 맞는지를, 표준은 공통 명칭·형식·정의를, Metadata는 그 의미와 구조를 설명한다. Governance는 이러한 관리의 정책·책임·의사결정 기준을 정하고, Security는 접근과 사용을 통제한다. 이 축들은 특정 단계의 후속 작업이 아니라 모델링·저장·운영·분석 전반에 적용되는 횡단 관리 영역이다.
