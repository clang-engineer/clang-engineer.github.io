# 테이블 파티셔닝과 파티션 프루닝

## 이 문서에서 되짚을 질문

- Table Partitioning은 어떤 문제를 해결하는가?
- Range·List·Hash는 어떤 기준으로 선택하는가?
- Partition Pruning이 왜 핵심 성능 이점인가?
- Partitioning과 Sharding은 무엇이 다른가?

## 1. 파티셔닝은 큰 Table을 관리 가능한 단위로 나눈다

대용량 Table에서는 조회뿐 아니라 Index 크기, 유지보수, 오래된 데이터 삭제 같은 비용도 데이터 양과 함께 커진다.

```text
Table 증가
├─ Scan 범위 증가
├─ Index·Maintenance 부담 증가
└─ 대량 DELETE 비용 증가
        ↓
Partition Key로 논리 분할
        ↓
필요한 Partition만 접근·관리
```

Partitioning의 목적은 단순히 파일을 여러 개 만드는 것이 아니라 **Query와 운영 작업의 범위를 줄이는 것**이다.

## 2. Partitioning과 Sharding의 경계

| 구분 | Partitioning | Sharding |
|---|---|---|
| 분할 범위 | 하나의 DB System/Instance 안 | 여러 Node/Instance |
| 중심 목적 | Scan·Maintenance 범위 축소 | 용량·처리량 Scale-out |
| Network 분산 문제 | 기본적으로 없음 | 발생 |
| 분산 Transaction·Consensus | 기본적으로 불필요 | 필요해질 수 있음 |

둘 다 데이터를 나누지만 **나누는 계층이 다르다.**

## 3. Range·List·Hash

### Range

연속된 값 범위로 나눈다. 날짜·시간처럼 Query와 보관정책이 범위 조건으로 움직일 때 자연스럽다.

### List

명시적인 값 Group으로 나눈다. Region, Category처럼 값의 의미가 분명할 때 사용한다.

### Hash

Hash 결과로 균등하게 분산한다. 자연스러운 범위가 없고 데이터·Write 부하를 고르게 나누는 것이 중요할 때 후보가 된다.

```text
Range → 범위 조회·시간 기반 Lifecycle
List  → 의미 있는 값 Group
Hash  → 균등 분산
```

## 4. 핵심은 Partition Pruning이다

Partition Pruning은 Query 조건과 무관한 Partition을 실행 대상에서 제외하는 것이다.

```text
WHERE created_at >= 특정 날짜
        ↓
Partition Boundary와 비교
        ↓
조건에 닿지 않는 Partition 제거
        ↓
필요한 Partition만 Scan
```

따라서 Partition Key를 Query가 거의 사용하지 않는 Column으로 고르면 모든 Partition을 탐색할 수 있어 효과가 줄어든다.

> **좋은 Partition Key는 데이터가 잘 나뉘는 값이면서 실제 Query의 Predicate와 Lifecycle 관리 기준에 반복해서 등장하는 값이다.**

## 5. 운영 측면의 이점

Range Partition을 기간 단위로 운영하면 오래된 대량 데이터를 Row 단위 `DELETE` 대신 Partition 단위로 제거할 수 있다.

```text
Row 수천만 건 DELETE
→ 많은 변경·로그·정리 비용

오래된 Partition 제거
→ 관리 단위 자체를 떼어냄
```

또 Maintenance와 Index 관리도 Partition 단위로 분리할 수 있어 한 번의 작업 범위를 줄일 수 있다.

## 6. 주의할 점

- Partition 수가 지나치게 많으면 Plan·Metadata 관리 비용이 늘 수 있다.
- Partition Key가 Query 조건과 맞지 않으면 Pruning이 되지 않는다.
- Unique Constraint 같은 무결성 규칙은 DBMS의 Partition 구현 제약을 확인해야 한다.
- Partitioning이 느린 Query를 자동으로 해결하지 않는다. Access Path·Index·통계·SQL도 함께 본다.

PostgreSQL 같은 DBMS는 선언적 Partitioning과 Plan-time/Execution-time Pruning을 제공하지만, 구체 문법·제약은 제품별 구현사항으로 구분한다.

## 7. 기억 흐름

```text
대용량 Table
   ↓
Query·Maintenance 범위가 너무 큼
   ↓
Partition Key 선택
   ↓
Range / List / Hash
   ↓
Partition Pruning
   ↓
읽지 않을 조각 제거
   ↓
조회·보관·정리 범위 축소
```

> **파티셔닝의 핵심은 '나누었다'가 아니라, 실제 Query와 운영 작업에서 필요 없는 조각을 건드리지 않게 만드는 데 있다.**
