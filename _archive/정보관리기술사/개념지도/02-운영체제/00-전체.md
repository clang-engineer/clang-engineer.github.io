# 운영체제 전체 개념지도

이 문서는 `../../학습등급표/02-운영체제.md`에서 정한 학습 범위를 **개념 관계로 재배치한 최상위 탐색 지도**다.

운영체제는 CPU·메모리·저장장치·I/O 같은 물리 자원을 애플리케이션이 직접 다루지 않아도 되도록 추상화하고, 여러 실행 주체가 한정된 자원을 안전하고 효율적으로 공유하게 한다.

여기서는 Algorithm 이름을 순서대로 외우기보다 **무엇을 실행하고, 한정된 자원을 어떻게 나누며, 공유 때문에 생기는 문제를 어떻게 통제하고, 운영 품질을 어떻게 유지하는가**라는 큰 질문부터 잡는다.

---

## 1. 가장 먼저 잡을 큰 그림

```text
Application이 Hardware를 직접 다루기 어려움
        ↓
운영체제가 공통 실행환경과 자원 추상화 제공
        ↓
프로그램을 실행 가능한 단위로 관리
├─ Process
└─ Thread
        ↓
여러 실행 주체가 한정된 자원을 공유
│
├─ CPU를 누가 언제 쓰지?
│   └─ Scheduling / Context Switch
│
├─ 동시에 같은 자원을 건드리면?
│   └─ Synchronization / Mutual Exclusion
│       └─ 잘못 기다리면 Deadlock
│
├─ Memory를 어떻게 나누고 보호하지?
│   └─ Paging / Segmentation / Virtual Memory
│       └─ Page Fault / Thrashing
│
├─ File과 Device는 어떻게 사용하지?
│   └─ System Call / File System / I/O
│
└─ 더 큰 단위로 자원을 나누고 운영하려면?
    ├─ Virtualization
    └─ Performance / Capacity / HA / Checkpointing
```

운영체제의 중심은 개별 Algorithm보다 다음 다섯 축이다.

```text
추상화
자원 배분
격리
동시성
성능과 안전성의 Trade-off
```

---

## 2. 실행환경: 프로그램을 어떻게 실행 단위로 만들까

운영체제는 실행 중인 프로그램과 Hardware 사이에 관리 경계를 만든다.

```text
Application
  ↓
System Call
  ↓
Kernel
  ↓
CPU / Memory / Device
```

Application은 보호된 Hardware 자원에 임의로 접근하지 않고 System Call을 통해 Kernel 서비스를 요청한다.

실행 단위에서는 Process와 Thread의 경계를 먼저 잡는다.

```text
Program
  ↓ 실행
Process
= 자원과 주소 공간을 소유하는 실행 인스턴스
  ↓
Thread
= Process 자원을 공유하며 실제 실행되는 흐름
```

여러 Process·Thread를 번갈아 실행하려면 상태를 저장하고 복원해야 한다.

```text
실행 중인 Task
  ↓ 전환 필요
Context Switch
  ↓
다른 Task 실행
```

Context Switch는 동시 실행을 가능하게 하는 Mechanism이지만 그 자체가 처리해야 할 업무는 아니므로 Overhead가 된다.

Kernel 구조는 별도의 비교축이다.

```text
Monolithic Kernel
↔
Microkernel

비교축
= 성능 / 장애 격리 / 확장성
```

---

## 3. CPU 배분: 실행할 것은 많은데 CPU는 한정돼 있다

실행 가능한 Process·Thread가 CPU보다 많으면 누가 먼저 얼마나 사용할지 결정해야 한다.

```text
여러 Ready Task
        ↓
CPU는 한정됨
        ↓
Scheduling
        ↓
어떤 품질을 중요하게 볼 것인가?
├─ Throughput
├─ Response Time
├─ Waiting Time
├─ Fairness
└─ Deadline / Predictability
        ↓
Workload에 맞는 정책 선택
```

먼저 정책의 큰 경계를 잡는다.

```text
Scheduling
├─ Non-preemptive
│   └─ 실행권을 자발적 반납·종료까지 유지
└─ Preemptive
    └─ OS가 실행 중인 Task의 CPU를 회수 가능
```

대표 Algorithm은 하나의 발전 순서가 아니라 목표와 Workload에 따른 선택지다.

```text
FCFS
SJF / SRT
Round Robin
MLQ / MLFQ
Priority Scheduling
RM / EDF
```

이 과정에서 기아(Starvation), Context Switch 비용, 우선순위 역전 같은 부작용이 생길 수 있다.

---

## 4. 동시성: 자원을 공유하면 실행 순서가 문제가 된다

Process·Thread가 동시에 실행되면서 같은 자원을 공유하면 실행 순서에 따라 결과가 달라질 수 있다.

```text
공유 자원
  ↓
동시 접근
  ↓
Race Condition
  ↓
Critical Section
  ↓
Mutual Exclusion / Synchronization
  └─ Semaphore 등
```

동기화는 공유를 안전하게 만들지만 새로운 비용도 만든다.

```text
Synchronization
├─ 안전한 공유
└─ 비용
    ├─ Waiting
    ├─ Contention
    ├─ Priority Inversion
    └─ Deadlock 가능성
```

여러 자원을 서로 점유한 채 기다리면 Deadlock으로 이어질 수 있다.

```text
Deadlock
├─ 발생 조건
│   ├─ Mutual Exclusion
│   ├─ Hold and Wait
│   ├─ No Preemption
│   └─ Circular Wait
└─ 대응
    ├─ Prevention
    ├─ Avoidance → Banker's Algorithm
    └─ Detection / Recovery
```

IPC(Inter-Process Communication)는 별개의 핵심 축이다. Process가 격리되어 있기 때문에 협업하려면 데이터를 주고받는 방법이 필요하고, Shared Memory와 Message Passing 등은 성능·격리·동기화 특성이 다르다.

---

## 5. Memory: 주소 공간과 물리 Memory를 어떻게 연결할까

Memory에서는 `배치`, `주소 공간`, `속도` 문제를 구분한다.

```text
[배치]
연속 할당
  ↓ 외부 단편화와 연속 공간 제약
불연속 할당
├─ Paging
└─ Segmentation

[주소 공간]
Process별 독립 주소 공간 필요
  ↓
Virtual Memory
  ↓
Page Table / MMU / TLB
  ↓
Demand Paging
├─ Page Fault
└─ Page Replacement
    ↓ 과도한 Page Fault
  Thrashing

[속도]
CPU ↔ RAM 속도 차이
  ↓
Cache
```

Paging과 Virtual Memory는 같은 개념이 아니다.

```text
Paging
= Page / Frame 단위로 불연속 배치하는 방식

Virtual Memory
= Process가 보는 주소 공간을 물리 Memory 배치와 분리하는 구조

Cache
= 접근 속도 차이를 줄이는 성능 계층
```

Memory의 Hardware 주소 변환 구조는 컴퓨터 구조 영역의 `MMU / TLB`와 직접 연결된다.

---

## 6. File과 I/O: 보호된 Device를 어떻게 사용하게 할까

Application이 Device와 Storage를 사용하려면 Kernel이 공통 Interface와 추상화를 제공해야 한다.

```text
Application
  ↓
System Call
  ↓
Kernel
  ↓
File System / Device I/O
```

File System은 Storage를 파일 이름·권한·Metadata 구조로 추상화한다.

```text
Storage
  ↓
File System
├─ File / Directory
├─ inode 등 Metadata
└─ Journaling
    └─ 장애 후 File System 일관성 복구 지원
```

I/O에서는 서로 다른 분류축을 한 줄의 단계처럼 섞지 않는다.

```text
[장치 완료를 어떻게 감지하는가]
Polling ↔ Interrupt

[호출한 실행 흐름이 기다리는가]
Blocking ↔ Non-blocking

[완료 결과를 어떤 제어 흐름으로 받는가]
Synchronous ↔ Asynchronous
```

Buffer와 Cache도 목적을 구분한다.

```text
Buffer
= 생산자와 소비자의 속도·처리 단위 차이를 완화

Cache
= 다시 사용할 가능성이 높은 Data의 접근시간을 단축
```

## 7. 기본 자원관리에서 시스템 단위 추상화로 확장된다

가상화는 운영체제의 다음 순서에 있는 기술이라기보다 **자원 추상화·격리라는 원리를 더 큰 단위로 확장하는 별도 축**이다.

```text
Physical Resource
CPU / Memory / Storage
        ↓
추상화 · 격리
        ↓
Logical Resource
        ↓
Virtualization
├─ Compute
└─ Storage
        ↓
Resource Pooling / 이동 / 탄력적 할당
        ↓
Cloud 운영모델과 연결
```

OpenStack 같은 Cloud Infrastructure 관리 Platform은 OS Kernel 자체와 구분한다.

---

## 8. 운영 중에는 성능과 가용성을 계속 관리해야 한다

자원을 배분하는 것만으로 끝나지 않는다. Workload와 서비스 목표를 기준으로 실제 운영 품질을 측정하고 개선한다.

```text
Workload / Service Goal
        ↓
Metric 측정
├─ Throughput
├─ Response Time
└─ Utilization 등
        ↓
병목 식별
        ↓
System Tuning
        ↓
재측정
        ↓
Capacity Planning
```

가용성은 별도의 평가축이다.

```text
장애 발생
  ↓
장애 영향 최소화
├─ Clustering / HA
└─ Checkpointing
    └─ 상태 저장 → 복구 지원
```

성능과 가용성은 하나의 발전 순서가 아니다. 빠르게 처리하는 것과 장애에도 서비스를 지속하는 것은 서로 다른 목표이며 실제 운영에서는 함께 판단한다.

---

## 9. 선택적으로 붙는 환경별 가지

실시간·임베디드 환경은 일반 운영체제 뒤의 발전 단계가 아니라 요구조건이 달라지는 별도 축이다.

```text
[Real-time]
Deadline과 결정성이 중요
  ↓
Real-time OS
  ↓
RM / EDF와 연결

[Embedded]
제한된 CPU / Memory / Power
  ↓
Embedded OS
  ↓
목적 특화 · 신뢰성 · 실시간성
```

특정 OS의 구현 상세, 부팅 순서, C 언어 Code, 플랫폼별 개발 절차는 전체 지도에서 펼치지 않는다.

---

## 10. 큰 학습 가지

```text
운영체제 전체
│
├─ 실행 모델과 CPU 배분
│   └─ Process / Thread → System Call → Scheduling / Context Switch
│
├─ 동시성과 자원 공유
│   └─ Race Condition → Synchronization → Semaphore → Deadlock / IPC
│
├─ Memory 관리
│   └─ 할당 → Paging / Segmentation → Virtual Memory → Page Fault / Thrashing
│
├─ File과 I/O
│   └─ System Call → File System / I/O → Buffer / Cache
│
└─ 가상화와 운영 품질
    ├─ Virtualization → Cloud와 연결
    └─ Metric → Tuning / Capacity → HA / Checkpointing
```

이 다섯 가지는 교재 Part를 그대로 옮긴 것이 아니라, 학습등급표에서 반복되는 관계를 **함께 보면 이해가 좋아지는 문제 묶음**으로 재배치한 것이다.

현재 운영체제 전용 세부학습 디렉터리는 없으므로 존재하지 않는 세부학습 파일을 가정해 링크하지 않는다. Memory의 Paging·Virtual Memory는 현재 컴퓨터 구조 개념지도와 세부학습에서도 함께 다루고 있으므로 영역 간 연결점으로 본다.

---

## 11. 이 지도를 보는 순서

```text
학습등급표
"무엇을 얼마나 볼 것인가"
        ↓
운영체제 전체 개념지도
"어떤 자원 문제를 보고 있는가"
        ↓
실행 / CPU / 동시성 / Memory / I/O / 운영 품질
        ↓
필요한 관계만 Zoom-in
        ↓
세부학습
"왜 필요하고 어떻게 동작하는가"
        ↓
다시 전체 지도에서 위치 확인
```

전체 지도에서 Scheduling 계산, Semaphore 구현, Page Replacement Algorithm, File System 내부 구조, 제품별 가상화 설정까지 이해하려 하지 않는다. **여기서는 어떤 자원을 관리하고, 어떤 문제가 생기며, 어떤 개념들이 서로 연결되는지를 잡으면 된다.**
