# 서비스·가상화·제약환경 개념지도

이 지도는 **기본 Network 전달 위에서 서비스 요구가 달라질 때 어떤 기술이 붙고, Network가 커질 때 운영을 어떻게 소프트웨어화하며, IoT처럼 제약된 환경에서는 무엇이 추가되는지**를 함께 본다.

먼저 이 문서는 하나의 발전 사슬이 아니라 **서로 다른 문제 축을 모아 보는 지도**라는 점을 잡는다.

```text
기본 Network 위에서
├─ Web 요청·응답을 하고 싶다        → HTTP
├─ 실시간 Voice / Video를 보내고 싶다 → RTP / RTCP
├─ 사용자 가까이서 Content를 주고 싶다 → CDN
├─ 공용망 위에 사설 연결이 필요하다    → VPN
├─ 많은 장비를 일관되게 제어하고 싶다  → SDN
├─ Network 기능을 SW로 실행하고 싶다    → NFV
└─ 저전력·대규모 단말을 연결해야 한다   → Sensor Network / IoT
```

각 기술은 해결하려는 문제가 다르며 실제 시스템에서는 필요에 따라 조합된다.

## 1. 기본 전달 위에 응용 Service가 올라간다

```text
Application 요구
├─ Web 요청·응답
│   └─ HTTP
├─ 실시간 Media
│   └─ RTP / RTCP
├─ 대규모 Content 전달
│   └─ CDN
└─ 사설 연결
    └─ VPN
```

이 기술들은 같은 계층이나 같은 분류축에 있는 것은 아니다. 여기서는 **기본 Network 위에서 어떤 Service 문제를 해결하는가**를 기준으로 함께 본다.

## 2. HTTP는 응용 계층에서 Request / Response 의미를 정한다

```text
Application
  ↓
HTTP Request / Response
  ↓
Transport
  └─ TCP 등
  ↓
IP Network
```

HTTP는 Network Layer나 Transport Layer의 기능이 아니다.

연결을 반복해서 만드는 비용이 문제라면 다음 개념을 함께 떠올린다.

```text
HTTP
  ↓
Persistent Connection
  └─ Keep-Alive

Application / Server
  ↓
Connection Pool
```

## 3. 실시간 Media는 Delay와 Jitter에 민감하다

```text
일반 Data
= 정확한 전달이 중요

실시간 Voice / Video
= Delay · Jitter · Loss의 영향이 큼
```

그래서 다음 관계를 같이 본다.

```text
실시간 Media
  ↓
RTP / RTCP
  ↓
Delay · Jitter · Loss 관리
  ↓
QoS
  ↓
QoE
```

RTP / RTCP와 QoS는 같은 개념이 아니며, 실시간 Service에서 함께 고려되는 관계다.

## 4. Content를 사용자 가까이 두면 전달 경로의 부담을 줄일 수 있다

```text
Origin에 요청 집중
  ↓
거리 증가·Backbone Traffic 증가
  ↓
사용자 가까운 지점에 Content 배치
  ↓
CDN
```

CDN은 Routing Protocol의 대체 기술이 아니다. IP Routing 위에서 **Content를 어디에서 제공할지 최적화하는 구조**다.

다수 수신자 전달이라는 공통 문제에서는 Multicast와 비교할 수 있다.

```text
Multicast
= Network가 하나의 Traffic을 여러 수신자에게 복제·전달

CDN
= 여러 위치에 Content를 배치하고 가까운 제공 지점을 선택
```

## 5. 공용 Network 위에 논리적인 사설 연결을 만들 수 있다

```text
공용 Network 사용
  ↓
조직 간 또는 사용자-조직 간 사설 통신 필요
  ↓
VPN
```

VPN은 단순히 암호화 하나를 뜻하지 않는다. 공용 Network 위에 **논리적인 사설 연결**을 구성하는 큰 개념으로 본다.

Tunnel 방식과 세부 보안 Protocol은 보안 영역의 세부학습과 연결한다.

## 6. Network가 커지면 장비별 수동 제어가 부담이 된다

```text
Network 장비 증가
  ↓
장비마다 개별 설정
  ↓
정책 변경과 일관성 유지가 어려움
  ↓
제어를 소프트웨어 중심으로 다루고 싶음
  ↓
SDN
```

복습할 핵심 경계는 다음이다.

```text
Control Plane
= 경로·정책을 결정

Data Plane
= 실제 Packet을 전달

SDN
= 제어와 전달을 분리해 중앙 정책화·자동화를 강화
```

## 7. Network 기능 자체를 SW로 실행할 수도 있다

```text
전용 Network Appliance
Firewall / Router / Load Balancer 등
  ↓
전용 장비 의존과 증설 부담
  ↓
Network 기능을 범용 Computing 자원에서 SW로 실행
  ↓
NFV
```

SDN과 NFV를 구분한다.

```text
SDN
= Network 제어 방식을 소프트웨어 중심으로 재구성

NFV
= Network 기능 자체를 소프트웨어로 구현·실행
```

둘은 자주 같이 쓰이지만 같은 개념은 아니다.

## 8. IoT에서는 일반 Network 문제에 자원 제약이 추가된다

```text
일반 Network
  ↓
저전력·저성능·불안정 Link·대규모 단말 환경
  ↓
Sensor Network / IoT
```

복습할 제약 축은 다음과 같다.

```text
IoT 환경
├─ 제한된 전력
├─ 제한된 CPU / Memory
├─ 다양한 Link
├─ 대규모 단말 관리
└─ 보안·운영 문제
```

주소·전송·보안·운영의 기본 원리는 이어지지만 **자원 제약과 규모 문제**가 더 강해진다.

## 9. 서로 다른 축을 섞지 않는다

```text
[응용 전달]
HTTP / RTP / RTCP / CDN

[사설 연결]
VPN

[운영 자동화]
SDN

[Network 기능 가상화]
NFV

[제약 환경]
Sensor Network / IoT
```

`HTTP → CDN → VPN → SDN → NFV → IoT` 같은 발전 사슬로 그리지 않는다.

## 10. 복습용 핵심 좌표

```text
Service
├─ HTTP
│   └─ Persistent Connection / Keep-Alive
├─ RTP / RTCP
│   └─ Delay / Jitter / Loss → QoS / QoE
├─ CDN
│   └─ Multicast와 비교
└─ VPN
    └─ 공용망 위 논리적 사설 연결

운영·가상화
├─ SDN
│   └─ Control Plane ↔ Data Plane
└─ NFV
    └─ Network Function을 SW로 실행

제약 환경
└─ Sensor Network / IoT
    ├─ 전력
    ├─ CPU / Memory
    ├─ Link
    ├─ 규모
    └─ 보안·운영
```

이 Node를 보고 각 기술이 **어떤 문제를 해결하고 무엇과 다른지** 떠올릴 수 있으면 된다. Protocol Header, VPN Tunnel 상세, SDN Interface, NFV 배치 구조, IoT 개별 규격은 세부학습으로 내려간다.
