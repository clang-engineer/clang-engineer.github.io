# 소프트웨어 공학 개념지도

> 소프트웨어 공학은 **불확실한 요구를 운영 가능한 소프트웨어로 바꾸고, 변경·품질·일정·비용의 위험을 생명주기 전체에서 통제하는 방법**을 다룬다.

## 1. 가장 먼저 잡을 큰 그림

소프트웨어 공학에는 **제품을 만들어 가는 흐름**과 **그 흐름 전체를 통제하는 활동**이 함께 존재한다.

```text
문제와 사용자 요구
        ↓
요구공학
        ↓
Architecture · 설계
        ↓
구현 · 통합
        ↓
검토 · V&V · Test
        ↓
Release · Deployment
        ↓
운영 · 유지보수
        ↓
새로운 문제와 요구
        └──────────────→ 앞 단계로 Feedback
```

실제 개발에서는 이 활동들이 한 번씩 순서대로 끝나는 것이 아니라 반복·병렬·점진적으로 수행된다.

```text
            [제품을 만드는 흐름]
요구 → 설계 → 구현 → 검증 → 배포 → 운영·유지보수
 │      │      │      │      │          │
 └──────┴──────┴──────┴──────┴──────────┘
                     ↑
               [전 과정 통제]
     개발 방식 · 형상/변경 · 품질
     규모/공수 · Project 관리 · 외부 제약
```

## 2. 왜 소프트웨어 개발을 공학적으로 관리할까?

소프트웨어 규모와 복잡성이 커지면 개인의 코딩 능력만으로 요구·변경·품질·일정·비용을 안정적으로 통제하기 어렵다.

```text
규모·복잡성 증가
        ↓
요구 누락 · 변경 영향 · 품질 문제 · 일정/비용 초과
        ↓
Software Engineering
        ↓
Process · Method · Tool로 개발 활동을 공학화
```

`SDLC`는 요구부터 운영·유지보수까지 전체 활동의 위치를 잡는 기본 좌표다.

## 3. 무엇을 만들어야 하는지 어떻게 명확하게 할까?

```text
사용자 · 이해관계자의 필요
        ↓
요구공학
        ↓
요구사항
├─ 기능 요구
└─ 비기능 요구 / 품질 요구
```

요구는 설계·구현·시험과 끊어져서는 안 된다.

```text
요구
 ↕ Traceability
설계
 ↕
구현
 ↕
시험
```

`추적성(Traceability)`은 요구가 실제 구현과 검증까지 빠짐없이 이어졌는지 확인하는 핵심 연결점이다.

## 4. 요구를 어떤 구조로 구현할까?

```text
요구사항
  ↓ 품질 요구가 주요 Architecture 결정에 영향
Architecture
  ↓
상세 설계
  ↓
구현
```

설계에서는 `모듈화 · 정보 은닉 · 응집도/결합도 · 객체지향 원칙 · Pattern` 같은 개념으로 책임과 변경 경계를 다룬다.

`UML`과 Architecture View는 설계 자체라기보다 **구조와 관계를 표현하는 수단**으로 본다.

## 5. 개발 방식은 왜 여러 가지일까?

생명주기 모델과 개발 방법론은 하나의 정답이 아니다. 요구 안정성, 기술 위험, Feedback 필요성에 따라 방식을 선택한다.

```text
개발 방식 선택
├─ Waterfall
├─ Iterative / Incremental
└─ Spiral
```

현대 개발에서는 짧은 Feedback을 중심으로 Agile, 자동화된 통합·시험, DevOps 같은 접근이 조합된다.

`Agile → Scrum → DevOps`를 하나의 발전 단계로 보지 않는다. 서로 역할과 분류축이 다르다.

## 6. 제대로 만들었고 실제 목적에도 맞는지 어떻게 확인할까?

```text
품질 요구
   ↓
Review · Inspection
   ↓
V&V
├─ Verification : 명세대로 만들었는가?
└─ Validation   : 실제 목적에 맞는가?
   ↓
Test
   ↓
결함 · Coverage · 품질 지표
```

`ISO/IEC 25010`은 소프트웨어 품질 특성을 이해하는 대표 좌표다.

시험 수준과 시험 기법은 다른 분류축이며, Coverage가 높다는 사실만으로 요구 충족이나 결함 부재가 증명되는 것은 아니다.

## 7. 배포한 뒤에는 무엇을 해야 할까?

운영에 들어간 소프트웨어도 오류 수정, 환경 변화, 새로운 요구, 품질 개선 때문에 계속 변경된다.

```text
운영
 ↓
유지보수
 ↓
운영 Feedback
 └────────→ 요구 · 설계 · 개발로 환류
```

유지보수 유형의 세부 분류는 세부학습에서 다루고, 전체 지도에서는 **운영 이후에도 변경이 계속되고 앞 단계로 Feedback된다는 관계**를 우선한다.

## 8. 전 과정의 변경·품질·일정·비용을 어떻게 통제할까?

제품 흐름과 별개로 다음 활동은 생명주기 전체를 가로지른다.

```text
전 과정 통제
├─ 형상·변경관리
│   └─ Configuration Item · Version · Baseline · 변경 통제
├─ 품질관리
├─ 규모·공수 추정
│   └─ FP · COCOMO 등
├─ Project 관리
│   └─ 범위 · 일정 · 비용 · 위험 · 이해관계자
└─ 외부 제약
    └─ 표준 · OSS License · IP · 공급망 통제
```

전체 지도에서는 `FP`, `COCOMO` 같은 대표 좌표까지만 남기고 계산식이나 세부 Project 관리 기법은 세부학습으로 내린다.

## 9. 전체 흐름을 가로지르는 핵심 관점

```text
소프트웨어 공학
├─ 추적성
│   └─ 요구 ↔ 설계 ↔ 구현 ↔ 시험
├─ Feedback
│   └─ 결과를 빨리 확인해 잘못된 방향의 비용을 줄임
├─ 모듈화
│   └─ 책임과 경계를 나눠 변경 영향 확산을 줄임
├─ 위험 기반 선택
│   └─ 상황에 맞는 개발 방식을 선택
└─ 품질 내재화
    └─ 품질을 마지막 Test가 아니라 요구부터 운영까지 관리
```

## 10. 기억할 핵심 경계

| 헷갈리기 쉬운 개념 | 핵심 경계 |
|---|---|
| SDLC ↔ 생명주기 모델 | 전체 개발 생명주기 ↔ 생명주기를 진행하는 방식 |
| 요구공학 ↔ 요구사항 | 요구를 찾아·분석·명세·관리하는 활동 ↔ 그 활동의 산출물 |
| Architecture ↔ 상세 설계 | 시스템 전체 구조·주요 결정 ↔ 내부 구성요소 수준 구체화 |
| Architecture ↔ UML | 구조와 주요 결정 ↔ 구조 등을 표현하는 Modeling 언어 |
| Verification ↔ Validation | 명세대로 만들었는가 ↔ 실제 목적에 맞는가 |
| Release ↔ Deployment | 제공할 변경 단위 확정 ↔ 실행 환경에 실제 적용 |
| 형상관리 ↔ Project 관리 | 산출물의 버전·변경 통제 ↔ 범위·일정·비용·위험 통제 |
| Agile ↔ DevOps | 개발 접근과 Feedback 방식 ↔ 개발·전달·운영을 연결하는 더 넓은 운영 방식 |

## 11. 한 번에 다시 떠올리기

```text
복잡한 SW 개발을 공학적으로 관리
        ↓
SDLC
        ↓
요구공학
        ↓ Traceability
Architecture · 설계
        ↓
구현
        ↓
V&V · Test
        ↓
Release · Deployment
        ↓
운영 · 유지보수
        ↓
Feedback ─────────→ 앞 단계로 환류

[전체 통제]
개발 방식 · 형상/변경 · 품질
규모/공수 · Project 관리 · 표준/OSS/IP
```

> **무엇을 만들지 요구로 명확히 하고 → 변경에 견딜 구조를 설계하고 → 구현·검증·배포·운영하며 → 운영 결과를 다시 앞 단계로 Feedback한다. 변경·품질·일정·비용과 외부 제약은 이 전체를 계속 통제한다.**
