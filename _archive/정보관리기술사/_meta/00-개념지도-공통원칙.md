# 정보관리기술사 개념지도 공통 원칙

## 0. 작성 전 확인

개념지도를 작성하거나 수정하기 전에 다음을 확인한다.

1. [정보관리기술사 문서작성 공통 원칙](00-문서작성-공통원칙.md)
2. [저장소 공통 지식 구성 원칙](../../../docs/KNOWLEDGE_ORGANIZATION.md)
3. [저장소 공통 문체·표기 원칙](../../../docs/WRITING_STYLE.md)
4. 이 문서

개념지도는 **학습할 개념의 위치·관계·학습 경로를 보여주고, 복습할 때 핵심 Node에서 세부 이해를 다시 꺼내는 탐색 지도**다.

학습 우선순위와 깊이는 `../학습등급표/`에서 정하고, 상세 원리·동작·예제는 세부학습 문서에서 다룬다.

저장소 공통 원칙에 이미 있는 묶음·관계·Story 기준은 여기서 반복하지 않는다.

## 1. 자료별 역할

```text
교재 · 기출 · 공식 출제기준
        ↓
학습등급표
= 무엇을 얼마나 우선해서 공부할 것인가
        ↓
개념지도
= 어디에 있고 무엇과 연결되는가
  + 어디로 더 파고들 것인가
        ↓
세부학습
= 왜 필요하고 어떻게 동작하는가
```

개념지도는 교재 목차나 세부학습 요약본이 아니다.

## 2. Node와 File을 구분한다

개념지도 Node와 세부학습 File은 1:1일 필요가 없다.

> **Node = 파고들 개념 꼭지 + 복습 인출 단서**  
> **File = 함께 이해할 때 좋은 학습 단위**

Node는 상위·하위·인접·비교·의존 관계를 우선해서 연결한다. 교재 번호나 이름이 비슷하다는 이유만으로 연결하지 않는다.

## 3. 전체 지도 → 필요한 Zoom → 세부학습

개념지도는 목차보다 깊고 세부학습보다 얕다.

```text
영역 전체 지도
= 큰 개념군의 위치·관계·학습 진입점
        ↓ 필요한 곳만
하위 개념지도
= 한 개념군 내부의 관계·경계 Zoom-in
        ↓
세부학습
= 원리·동작·비교·예제
```

전체 지도에는 큰 개념군의 위치·관계, 주요 경계, 다음 학습 가지를 고르는 이유, 대표 인출 Node를 우선 남긴다.

다음은 하위 지도 또는 세부학습으로 내리는 것을 우선한다.

- 상위 Node만으로 충분히 복원되는 반복적 하위 분류
- 관계 없이 이름만 늘어놓는 세부 기법·대표 예시
- 수식·Algorithm 상세 단계
- Parameter, 구현 Code, 제품별 설정
- 긴 설명 자체

단, **대표 기법·분류가 기술사 답안의 핵심 인출 좌표가 되거나, 상위 Node만으로는 중요한 비교·선택 구조가 복원되지 않는다면 전체 지도에 한 단계 더 펼쳐 둘 수 있다.**

```text
상위 개념
├─ 대표 분류 A
├─ 대표 분류 B
└─ 대표 분류 C
```

이때 목적은 세부 내용을 설명하는 것이 아니라 **이름을 보고 원리·비교·Trade-off를 다시 떠올릴 수 있게 하는 것**이다. 따라서 대표 항목의 이름과 관계까지만 남기고, 동작 원리·장단점·예제는 세부학습으로 내린다.

Node를 남길지 애매하면 다음만 확인한다.

```text
이 Node가 없으면 큰 그림이나 주요 경로가 끊기는가?
이 Node가 있어야 중요한 경계가 보이는가?
복습할 때 대표 인출 좌표가 되는가?
```

아니라면 아래로 내리는 것을 우선한다.

반대로 다음 중 하나에 해당하면 한 단계 더 펼치는 것을 허용한다.

- 대표 기법 이름 자체가 시험 답안의 기본 분류 축이 되는가?
- 기술사 문제에서 반복적으로 비교·분류·선택 기준이 되는 **대표 비교·분류 축**인가?
- 상위 Node만 두면 서로 다른 접근 방식의 경계가 사라지는가?
- 복습할 때 하위 핵심 Keyword를 직접 보고 인출하는 편이 학습 효율이 높은가?
- 3~5개 안팎의 대표 항목으로 압축해도 Diagram의 구조가 흐트러지지 않는가?

대표 비교·분류 축은 가능한 한 개념지도에 직접 드러낸다.

```text
Recovery
├─ Log 기반 회복
└─ Shadow Paging

Scale Out
├─ Replication
└─ Sharding

Optimizer
├─ Rule Based
└─ Cost Based
```

이런 축은 단순 Keyword 나열이 아니라 **서로 다른 접근 방식을 구분하고, 비교 기준과 선택 논리를 떠올리게 하는 인출 좌표**다.

여기서도 **대표 항목까지만 펼치고, 대표 항목 아래의 세부 단계까지 연쇄적으로 확장하지 않는다.**

## 4. 하위 지도는 필요한 곳에만 만든다

```text
전체 지도
  ↓
한 번 더 묶어 보면 관계가 더 잘 보이는가?
  ├─ Yes → 하위 개념지도 → 세부학습
  └─ No  → 세부학습으로 직접
```

파일 길이, Keyword 수, 교재 Chapter 수만으로 하위 지도를 만들지 않는다.

```text
00-*   = 영역 전체 지도
01-* ~ = 정규 학습 가지
99-*   = 정규 가지는 아니지만 큰 그림을 잇는 횡단·보강 지도
```

`99-*`는 기타 지식 모음이 아니다. 정규 지도만으로 중요한 연결이나 경계가 끊길 때만 만든다.

## 5. 쉬운 진입과 정확한 용어를 함께 유지한다

```text
쉬운 큰 질문
  ↓
정확한 핵심 개념명과 관계
  ↓
대표 인출 Node
  ↓
필요한 Zoom
```

낯선 약어·공식 용어는 지도를 읽는 데 필요한 최소 의미만 처음 한 번 붙인다.

## 6. 여러 영역에 걸친 개념은 설명 소유권을 나눈다

같은 Concept은 여러 지도에 Node로 등장할 수 있다. 대신 같은 정의·동작·세부 분류를 복사하지 않는다.

```text
같은 Concept
├─ 영역 A → A 관점에서 왜 필요한지
└─ 영역 B → B 관점에서 왜 필요한지

상세 설명
→ 가장 자연스러운 한 영역이 중심 소유
```

예:

```text
컴퓨터 구조
→ Memory Hierarchy / Cache / MMU / TLB

운영체제
→ Address Space / Protection / Frame / Replacement / Thrashing
```

현재 영역에서 필요한 연결 이유만 설명하고, 다른 영역이 중심 소유하는 내부 동작은 짧게 언급한 뒤 링크한다.

## 7. Diagram은 개념지도의 탐색 좌표로 사용한다

Diagram의 사용 판단과 대표 Mental Model / Zoom-in 원칙은 [저장소 공통 지식 구성 원칙](../../../docs/KNOWLEDGE_ORGANIZATION.md)을 따른다.

개념지도에서는 특히 다음 역할만 추가로 기억한다.

```text
영역 전체 지도 → 큰 가지와 대표 인출 Node를 잇는 Mental Model
하위 개념지도 → 선택한 가지 내부의 관계·경계 Zoom-in
```

ASCII Diagram은 단순히 내용을 세로로 나열하지 않고, **무엇을 가장 먼저 인출하게 할 것인지에 따라 형태를 선택한다.**

- 처리 **순서**가 핵심이면 화살표 흐름을 분명하게 만든다.
- 같은 시스템의 **구성요소**가 핵심이면 같은 레벨에 나란히 배치한다.
- **분류 체계**가 핵심이면 Tree 구조를 사용한다.
- 두 접근법의 **비교·대칭 관계**가 핵심이면 좌우 병렬 구조를 사용한다.
- 상위 구성요소 내부의 **판단 요소·세부 기준**은 해당 Node 아래로 분기한다.
- 하나의 Diagram에서 순서와 구성요소를 함께 보여줄 수 있다면, 세로 나열보다 가로 흐름 + 하위 분기를 우선 검토한다.

예:

```text
Query Engine
┌────────┐   ┌──────────┐   ┌───────────┐   ┌──────────┐
│ Parser │ → │ Rewriter │ → │ Optimizer │ → │ Executor │
└────────┘   └──────────┘   └───────────┘   └──────────┘
                                │
                                ├─ Statistics
                                ├─ Access Path
                                └─ Join Strategy
```

이 형태는 `Parser → Rewriter → Optimizer → Executor`의 **처리 순서**와, 네 요소가 Query Engine의 **구성요소**라는 점을 동시에 보여준다.

Diagram은 예쁘게 만드는 것이 목적이 아니라 **관계·순서·경계·분류를 한눈에 복원하는 것**이 목적이다. 같은 내용을 세로로 길게 늘어놓았을 때 핵심 구조가 약해진다면 배치를 다시 설계한다.

Diagram을 세부 Keyword 목록으로 비대하게 만들지 않는다.
## 8. 성안당 교재는 범위·누락 점검의 1차 기준으로 사용한다

정보관리기술사 개념지도는 저장소의 `성안당/` 정리 문서를 **학습 범위와 누락 여부를 점검하는 1차 기준**으로 사용한다.

```text
성안당 교재
= 무엇이 학습 범위에 들어오는가
= 큰 개념군이 빠지지 않았는가
        ↓
개념지도
= 교재 목차를 그대로 복사하지 않고
  실제 관계·흐름·비교 구조로 재배치
        ↓
세부학습
= 필요한 원리·동작·비교를 깊게 이해
```

따라서 성안당 교재에 등장하는 개념이 개념지도에서 보이지 않는다면 먼저 **의도적으로 아래로 내린 것인지, 실제 누락인지** 확인한다. 특히 회복 기법, 인덱스 유형, 분산 처리 방식처럼 대표 분류 축이 되는 항목은 누락 여부를 우선 점검한다.

다만 성안당 교재의 장·절 순서와 분류를 개념지도 구조로 그대로 복사하지 않는다. 서로 떨어져 있는 Topic이라도 실제로 하나의 처리 흐름이나 비교 축을 이루면 개념지도에서 재구성할 수 있다.

예를 들어 교재의 여러 항목을 `Parser → Rewriter → Optimizer → Executor`처럼 실제 Query Engine 처리 흐름으로 재배치하는 것은 허용한다.

교재 밖 지식은 다음 경우에만 보강한다.

- 교재의 개념을 이해하기 위한 연결 고리가 필요한 경우
- 서로 다른 교재 Topic의 관계를 설명해야 하는 경우
- 기술사 답안에서 대표 인출 좌표로 유용한 경우

이때 **교재 기반 범위와 보강 지식을 혼동하지 않도록**, 보강 지식은 교재 항목을 대체하거나 범위를 무제한 확장하는 용도로 사용하지 않는다.


## 9. 문제 중심으로 뼈대를 잡되 관계 중심으로 재구성한다

성안당 교재를 볼 때는 설명 순서보다 **문제·출제 Topic이 요구하는 핵심 개념군**을 먼저 확인한다.

```text
성안당 문제·Topic
      ↓
핵심 개념군 추출
      ↓
비교 · 흐름 · 원인-대응 관계로 재구성
      ↓
개념지도
```

즉, 교재의 목차 순서를 따라가는 것이 아니라 **문제에서 반복적으로 요구되는 분류·비교·원리·선택 기준이 무엇인지**를 중심으로 뼈대를 세운다.

## 10. 흐름과 분류는 필요하면 Diagram을 나눈다

하나의 Diagram에 처리 순서와 유형 분류를 모두 억지로 넣지 않는다.

- 처리 **흐름**은 시간·단계 순서가 보이게 구성한다.
- 개념 **분류**는 같은 수준의 Node를 Tree나 병렬 구조로 보여준다.
- 두 관점이 다르면 Diagram을 나누고 연결 관계만 별도로 표시한다.

예:

```text
[처리 흐름]
Parser → Rewriter → Optimizer → Executor

[물리 구조 분류]
Physical Access Structure
├─ Index
└─ Partition
```

## 11. 목록보다 인과관계를 우선한다

개념지도는 단순한 Keyword 목록보다 **왜 다음 개념이 필요한지**가 보이도록 구성한다.

가능하면 다음 형태를 우선 검토한다.

```text
문제
  ↓
대응 기술
  ↓
얻는 효과
  ↓
새로 생기는 Trade-off / 제약
```

예:

```text
단일 DB 확장 한계
   ↓
Replication / Sharding
   ↓
Scale Out
   ↓
Consistency / Distributed Transaction / Coordination 문제
```

## 12. 같은 레벨의 Node는 추상도를 맞춘다

같은 부모 아래에 있는 형제 Node는 가능한 한 **비슷한 추상 수준**을 유지한다.

잘못된 예:

```text
Query Engine
├─ Parser
├─ Rewriter
├─ Optimizer
├─ Cardinality
└─ Executor
```

`Cardinality`는 구성요소가 아니라 Optimizer 내부 판단 요소이므로 같은 레벨에 두지 않는다.

올바른 예:

```text
Query Engine
├─ Parser
├─ Rewriter
├─ Optimizer
│   └─ Cardinality
└─ Executor
```

## 13. 지도 수정 시 역점검한다

새 Node를 추가하거나 구조를 바꾼 뒤에는 최소한 다음을 확인한다.

```text
[ ] 성안당 문제·Topic에 근거한 핵심 범위인가?
[ ] 교재 밖 보강 개념이라면 왜 필요한지 설명 가능한가?
[ ] 기존 Node와 어떤 관계로 연결되는가?
[ ] 형제 Node와 추상 수준이 맞는가?
[ ] 별도 세부학습이 필요한가, 기존 문서로 연결 가능한가?
[ ] Diagram 형태가 순서·분류·비교·인과 중 강조하려는 목적에 맞는가?
```

## 14. 학습등급표는 출발점이지 지도 복사본이 아니다

A/B/C는 Topic별 학습 우선순위와 깊이를 정하는 기준이지 개념지도 포함 등급이 아니다.

- B/C Topic이 직접 보이지 않는다고 누락으로 판단하지 않는다.
- 등급이 낮아도 큰 그림 연결에 필요하면 Node로 넣을 수 있다.
- 기출 여부나 교재 Chapter 자체를 개념지도 구조로 복사하지 않는다.
- 누락 여부는 개별 Topic 수보다 **큰 개념군과 관계가 빠졌는가**로 판단한다.

## 15. 세부학습과 왕복하며 보정한다

```text
개념지도에서 위치·관계 파악
        ↓
세부학습에서 원리·동작 이해
        ↓
새 관계·경계·의존성 발견
        ↓
개념지도 보정
```

세부학습에서 새 관계를 발견해도 전체 지도에는 관계 복원에 필요한 최소 Node만 올린다.

Obsidian 내부 링크도 실제 학습 경로에만 둔다. 존재하지 않는 파일을 가정하거나 단순 관련성만으로 모든 Node에 링크하지 않는다.

대표 Node를 펼쳤고 해당 내용을 다루는 **기존 세부학습 문서가 있다면, 실제로 더 파고들 수 있도록 가까운 위치에 링크를 둔다.** 링크는 Node마다 기계적으로 붙이지 않고, 한 문서가 여러 Node를 함께 다룬다면 묶어서 연결한다.

세부학습 링크는 단순한 참고문헌 목록이 아니라 **학습 경로 안내**로 작성한다. 각 링크에는 가능한 한 다음 세 가지를 짧게 드러낸다.

- 왜 이 문서를 보는가
- 이 문서에서 무엇을 이해해야 하는가
- 앞·뒤 어떤 학습과 이어지는가

선후관계가 있는 경우에는 읽는 순서를 명시하고, 서로 독립적인 경우에는 병렬 학습 가지라고 표시한다.

```text
개념지도 Node
   ↓
1. 먼저 보는 세부학습
   = 다음 단계의 판단 근거를 이해
   ↓
2. 그다음 보는 세부학습
   = 실제 실행 방식·비교 기준을 이해
   ↓
3. 필요할 때 선택하는 세부학습
   = 특정 구조·기법으로 Zoom-in
```

즉, 개념지도는 **인출 좌표만 보여주고 끝나는 문서가 아니라 실제 세부학습으로 진입할 수 있는 탐색 지도**가 되어야 한다. 다만 세부학습 문서가 아직 없다면 빈 링크나 예정 링크를 만들지 않는다.
