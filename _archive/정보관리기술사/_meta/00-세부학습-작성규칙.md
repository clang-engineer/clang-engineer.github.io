# 정보관리기술사 세부학습 작성 규칙

## 0. 작성 전 확인

세부학습 문서를 작성하거나 수정하기 전에 다음을 확인한다.

1. [정보관리기술사 문서작성 공통 원칙](00-문서작성-공통원칙.md)
2. [저장소 공통 지식 구성 원칙](../../../docs/KNOWLEDGE_ORGANIZATION.md)
3. [저장소 공통 문체·표기 원칙](../../../docs/WRITING_STYLE.md)
4. 이 문서

세부학습의 목적은 **시험 직전 암기용 요약본이 아니라, 학습 과정에서 이해한 내용을 나중에 다시 읽었을 때 그 이해가 복원되는 문서**를 만드는 것이다.

공통적인 묶음·Story·비교·문서 유형 원칙은 상위 문서를 따르고 여기서는 기술사 세부학습에만 필요한 깊이·인출·보충학습 규칙을 추가한다.

## 1. 상위 학습 자료와 역할을 나눈다

```text
학습등급표
= 무엇을 얼마나 우선해서 공부할지
        ↓
개념지도
= 어디에 있고 무엇과 연결되는지
        ↓
세부학습
= 왜 필요하고 어떻게 동작하는지 깊게 이해
```

개념지도 Node와 세부학습 File은 1:1일 필요가 없다. 함께 이해할 때 더 잘 이해되는 개념은 하나의 세부학습 문서에서 같이 다룬다.

내용을 이동하거나 덜어낼 때는 이해에 필요한 설명이 다른 적절한 문서에 보존되어 있는지 먼저 확인한다.

## 2. 기술사에 필요한 깊이까지만 내려간다

기본 범위:

```text
정의
→ 왜 필요한가
→ 핵심 구조·동작
→ 주요 구성요소
→ 대표 비교·경계
→ 장단점·Trade-off
→ 적용·운영 고려사항
```

새 세부 내용을 넣기 전에 묻는다.

```text
이 내용을 빼면 핵심 개념을 잘못 이해하는가?
기술사 답안을 구성하는 데 실질적으로 필요한가?
```

둘 다 아니라면 기본 범위에서는 생략한다.

구현체 내부 구조, 제품 옵션, 버전별 차이, 논문 수준 수식, 지나친 최적화 세부는 핵심 이해에 필요할 때만 포함한다. 문서가 길다는 이유만으로 이해에 필요한 설명을 삭제하지는 않는다.

## 3. 이해가 됐던 설명과 인출 장치를 보존한다

대화나 학습 중 특정 설명·비유·예제로 이해가 됐다면 그 부분을 우선 보존한다.

기술사 시험에서 즉시 비교·열거·서술해야 하는 핵심은 **기억·인출 장치**를 함께 둔다.

- 인과관계와 단계 흐름
- 핵심 질문
- 비교·대칭
- 용어의 의미·어원
- 작은 예제
- Text/ASCII Diagram
- 필요한 경우에만 연상법

외우기 쉬운 표현보다 **왜 그런지 다시 도출할 수 있는 방식**을 우선한다.

## 4. `_보충학습/`은 이해의 빈틈을 메울 때만 사용한다

직접 출제 Topic은 아니지만 모르면 핵심 관계·동작을 잘못 이해하는 기반·실무 개념은 해당 영역의 `_보충학습/`에 둘 수 있다.

```text
본 학습에서 이해의 빈틈 발견
        ↓
직접 출제 Topic은 아니지만 이해에 필요
        ↓
_보충학습에서 필요한 만큼만 Zoom-in
        ↓
본 학습으로 복귀
```

- 범위 밖 지식 모음으로 사용하지 않는다.
- 흥미만으로 계속 확장하지 않는다.
- 별도 `기반학습/`, `보조학습/` 최상위 분류를 만들지 않는다.
- 디렉터리 자체가 성격을 나타내므로 파일명에 별도 `99-` Prefix를 붙이지 않는다.
- 큰 그림을 방해하는 구현 동작·호출 순서·예외 경계는 여기로 내릴 수 있다.

## 5. 가지 주제는 중앙 TODO로 보낸다

현재 이해에 당장 필요하지 않지만 나중에 학습 가치가 있는 주제는 현재 문서를 확장하지 않고 `_meta/00-학습-TODO.md`에 등록한다.

TODO에는 최소한 다음을 남긴다.

```text
무엇을 볼 것인가
왜 이 주제가 나왔는가
어느 주제와 연결되는가
```

현재 개념을 정확히 이해하는 데 반드시 필요한 내용은 TODO로 미루지 않는다.

## 6. 문서는 이해를 복원할 수 있어야 한다

다시 읽었을 때 다음 질문에 답할 수 있어야 한다.

```text
이 개념은 전체에서 어디에 있는가?
왜 필요한가?
무엇을 해결하는가?
어떻게 동작하는가?
무엇과 헷갈리기 쉬운가?
실제 시스템에서는 어디에 위치하는가?
```

권장 기본 흐름은 다음이지만 같은 Template을 강제하지 않는다.

```text
큰 그림 / 현재 위치
        ↓
왜 필요한가
        ↓
핵심 구조·동작
        ↓
비교·경계
        ↓
적용·Trade-off
        ↓
기억 흐름
```

실제 인과가 있으면 `왜 → 어떻게 → 그래서`를 살리고, 인과가 없으면 비교·계층·경계·조합 관계를 사용한다.

## 7. 세부로 내려갔다가 다시 전체로 돌아온다

```text
큰 그림
 ↓
현재 위치
 ↓
주변 관계·경계
 ↓
상세 원리
 ↓
Mechanism / Algorithm
```

세부학습에서 새 관계가 드러나면 관련 개념지도도 다시 확인하고 필요한 경우 보정한다.

## 8. 처리 과정·비교·분류축을 분명히 한다

동작 원리가 있는 주제는 가능하면 `입력 → 처리 → 출력`으로 먼저 단순화한다.

비슷한 개념은 차이를 나열하기 전에 **같은 비교축인지** 확인한다. 서로 다른 분류축을 하나의 발전 순서로 만들지 않는다.

예:

```text
Fine-tuning
├─ 학습 신호 관점 → SFT
└─ Parameter 효율 관점
    ├─ Full Fine-tuning
    └─ PEFT → LoRA
```

학습 중 실제로 생긴 질문과 헷갈린 지점은 FAQ로 쌓기보다 자연스러운 Section과 설명 흐름에 녹인다.

## 9. Diagram은 이해 복원에 사용한다

Diagram의 사용 판단, 대표 Mental Model, Zoom-in 원칙은 [저장소 공통 지식 구성 원칙](../../../docs/KNOWLEDGE_ORGANIZATION.md)을 따른다.

세부학습에서는 **나중에 다시 봤을 때 동작·분기·경계를 빠르게 복원해야 하는 지점**에 Diagram을 우선 사용한다. 그림 뒤에는 오해하기 쉬운 관계만 짧게 해석한다.
## 10. 기존 문서를 먼저 보강한다

새 파일을 만들기 전에 기존 문서가 같은 이해 단위를 다루는지 확인한다.

다음 경우에만 분리를 적극 검토한다.

- 독립적으로 깊게 학습할 가치가 큼
- 깊이 차이가 커서 본선 흐름을 방해함
- 별도 문서로 볼 때 관계가 더 명확함
- 한 문서 안에서 반복적으로 멀리 왕복해야 함

파일 길이 자체는 분리 기준이 아니다.

## 11. 수식·특수기호는 Viewer 독립성을 우선한다

모바일 GitHub, Obsidian, Terminal 등에서 읽을 수 있도록 LaTeX보다 **Unicode + 일반 Text**를 우선한다.

```text
H₀: μ = 70
H₁: μ ≠ 70
α = 0.05
p-value ≥ 0.05

t = (x̄ - μ₀) / (s / √n)
```

복잡한 수식이 핵심이 아니라면 기호만 남기지 말고 자연어 설명을 함께 적는다.

우선순위:

```text
1. 여러 Viewer에서 깨지지 않는가?
2. 의미가 바로 보이는가?
3. 정확성을 유지하는가?
4. 그 다음에 미려함
```

## 12. 작성 후 확인

```text
[ ] 나중에 읽었을 때 당시 이해가 복원되는가?
[ ] 기술사에 필요한 깊이를 넘어 불필요하게 확장하지 않았는가?
[ ] 이해에 결정적이었던 설명·질문·예제를 보존했는가?
[ ] 현재 위치와 주변 관계가 먼저 보이는가?
[ ] 비슷한 개념의 비교축과 경계가 분명한가?
[ ] 세부를 이해한 뒤 큰 그림으로 다시 돌아갈 수 있는가?
[ ] ASCII Diagram이 실제 흐름·분기·경계를 더 잘 보여주는가?
[ ] 같은 관계를 Diagram으로 반복하지 않았는가?
[ ] 새 파일보다 기존 문서 보강이 적절한지 먼저 검토했는가?
[ ] 새 관계가 상위 개념지도에도 반영되어야 하는지 확인했는가?
```

## 13. 한 문장 원칙

> **세부학습은 기술사에 필요한 깊이까지 개념의 위치·필요성·동작·경계를 이해하고, 나중에 다시 읽었을 때 그 이해와 답안 구성 능력을 복원할 수 있게 기록한다.**
