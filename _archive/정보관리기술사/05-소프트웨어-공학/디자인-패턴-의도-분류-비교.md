# 디자인 패턴 — 의도·분류·비교

> 연결: [[00-전체|소프트웨어 공학 개념지도]]
>
> 학습 범위: Pattern 이름이나 코드 구현을 외우기보다 **반복되는 설계 문제 → 패턴의 의도 → 적용 조건 → Trade-off → 유사 패턴과의 경계**를 이해한다.

## 1. 디자인 패턴은 무엇을 해결하는가

소프트웨어 설계에서는 같은 종류의 변경 문제가 반복된다.

```text
객체 생성 방식이 자주 바뀜
→ 생성 책임을 분리할 필요

기존 객체를 조합해 기능을 확장해야 함
→ 상속 대신 조합 구조 필요

객체 사이의 책임·호출 관계가 복잡해짐
→ 상호작용을 분리·조정할 필요
```

디자인 패턴은 이런 반복 문제에 대한 **재사용 가능한 설계 의도와 책임·협력 방식**이다. 핵심은 클래스 모양보다 어떤 변경을 분리하는가에 있다.

```text
Context
→ 어떤 문제가 반복되는가

Intent
→ 무엇을 분리하거나 보호하려는가

Structure
→ 책임을 어디에 배치하는가

Consequence
→ 무엇을 얻고 어떤 복잡성을 추가하는가
```

같은 구조라도 의도가 다르면 다른 Pattern일 수 있고, 같은 의도도 언어의 함수·Closure·DI 같은 기능으로 더 단순하게 구현할 수 있다.

## 2. GoF 23개 전체 지도 — 생성 5·구조 7·행위 11

GoF Pattern은 객체 **생성·조합·협력** 중 해결하려는 설계 문제에 따라 나뉜다. 아래는 전체를 먼저 조망하는 지도이며, 각 패턴의 객체 관계와 C++ 코드는 뒤에서 살펴본다.

```text
Design Pattern
│
├─ 생성 — 객체 생성 변화 격리
│   ├─ Factory Method  : 생성할 타입을 하위 Class가 결정
│   ├─ Abstract Factory: 관련 객체 제품군 생성
│   ├─ Builder       : 복잡한 조립 절차
│   ├─ Prototype     : 기존 객체 복제
│   └─ Singleton     : Instance 수명·개수 제한
│
├─ 구조 — 객체 조합·경계
│   ├─ Adapter       : Interface 변환
│   ├─ Facade        : Subsystem 단순화
│   ├─ Decorator     : 기능 추가
│   ├─ Proxy         : 접근 제어
│   ├─ Composite     : 부분-전체 Tree
│   ├─ Bridge        : 두 변화축 분리
│   └─ Flyweight     : 공통 상태 공유
│
└─ 행위 — 책임·상호작용 분리
    ├─ Strategy      : Algorithm 교체
    ├─ State         : 상태별 행동·전이
    ├─ Template      : Algorithm 골격
    ├─ Observer      : 일대다 통지
    ├─ Mediator      : 다대다 조정
    ├─ Command       : 요청 객체화
    ├─ Memento       : 상태 Snapshot
    ├─ Chain         : Handler 연결
    ├─ Iterator      : 순회 추상화
    ├─ Visitor       : 구조와 연산 분리
    └─ Interpreter   : 간단한 문법 해석
```

### 패턴의 공통 기반: 다형성·합성·위임

```text
변경되는 부분을 분리
       │
       ├─ 다형성 (Polymorphism)
       │    같은 Interface → 다른 구현
       │    예: Strategy, State
       │
       ├─ 합성 (Composition)
       │    객체 안에 다른 객체를 조합
       │    예: Decorator, Bridge
       │
       └─ 위임 (Delegation)
            다른 객체에 실제 작업을 맡김
            예: Proxy, Command
```

**주의:** 디자인 패턴은 '다형성 사용법 23가지'가 아니다. **반복되는 설계 문제를 해결하는 의도와 객체 책임 배치**가 중심이고, 다형성·합성·위임은 이를 구현하는 대표적인 수단이다.

### 구조와 행위의 경계: 연결 방식인가, 협력 방식인가?

**구조 패턴(Structural)**은 객체·클래스를 **어떻게 감싸고 조합·연결할지**가 중심이고, **행위 패턴(Behavioral)**은 객체들이 **어떤 책임을 맡고 어떤 순서·규칙으로 상호작용할지**가 중심이다. 둘 다 객체 관계를 사용하므로 **UML 모양이 아니라 해결하려는 설계 문제**로 구분한다.

```text
구조 — Decorator: 기능을 겹쳐 조합
주문 → SyrupDecorator → MilkDecorator → Coffee
       (감싸기)          (감싸기)

행위 — Observer: 상태 변경 시 구독자에게 알림
YouTubeChannel ──notify()──┬─> Subscriber A
                           ├─> Subscriber B
                           └─> Subscriber C
```

| 비교 질문 | 구조 패턴 | 행위 패턴 |
| --- | --- | --- |
| 무엇을 바꾸려는가? | 객체 구성·연결·접근 경계 | 알고리즘·책임·상태 전이·협력 |
| 대표 문제 | 기능을 덧붙이거나 Interface를 변환 | 계산 방식을 교체하거나 변경을 통지 |
| 예 | Decorator·Adapter·Proxy | Strategy·State·Observer |

**비슷한 구조, 다른 의도:** Decorator와 Strategy 모두 Interface와 위임을 활용할 수 있다. 하지만 Decorator는 **객체를 감싸 기능을 조합**하려고, Strategy는 **동일 목적의 알고리즘을 교체**하려고 사용한다.

**다형성은 여러 패턴의 핵심 수단이지만 전부는 아니다.** Strategy·State·Factory Method 등은 공통 Interface와 다형성을 활용하고, Decorator·Bridge는 합성·위임까지 함께 활용한다. Singleton(생성 통제)·Flyweight(상태 공유)는 다형성이 주목적이 아니다.

**ASCII 표기:** `△ 상속`은 일반화, `△ 구현`은 인터페이스 실체화, `──has──`는 객체 참조 관계를 뜻한다. 그림은 UML의 엄밀한 선 모양보다 관계의 의미를 간략히 표현했다.

## 3. 생성 Pattern — 생성 책임을 분리한다

### 3.1 Factory Method — 생성할 객체 종류를 하위 Class에 위임한다

```text
Client가 구체 Class를 직접 생성
→ 구체 타입 변경 시 Client 수정
→ 공통 생성 Interface를 두고 하위 Class가 생성 대상 결정
```

**Intent**: 객체 생성 Interface를 정의하되, 어떤 구체 객체를 만들지는 하위 Class가 결정하도록 한다.

**적용 신호**: Framework가 생성 시점과 사용 흐름은 통제하지만 실제 생성 타입은 확장 지점에서 결정해야 할 때.

**대가**: Creator 계층과 하위 Class가 늘어날 수 있다.

**일상 예시 — 피자 가게:** 주문 처리 흐름은 공통으로 두고, 매장별로 만드는 피자 종류를 결정한다.

```text
PizzaStore (Creator)
├─ orderPizza() : 공통 주문 흐름
└─ createPizza(): Pizza  ← 생성 지점
          △ 상속
    ┌─────┴──────────┐
NYPizzaStore   ChicagoPizzaStore
 createPizza()    createPizza()
      │ 생성            │ 생성
   NYPizza        ChicagoPizza
```

**왜 쓰나?** 주문 절차를 바꾸지 않고도 매장별 생성 객체를 달리할 수 있다.

**핵심 코드 (C++17):** 뉴욕·시카고 매장 예시의 생성 책임을 한 매장(치즈 피자)으로 축약한 코드다. 공통 주문 흐름은 유지하고 생성할 피자만 하위 매장이 결정한다.

```cpp
#include <memory>
#include <string>
struct Pizza {
    virtual ~Pizza() = default;
    virtual std::string name() const = 0;
};
struct CheesePizza : Pizza {
    std::string name() const override { return "치즈 피자"; }
};
struct PizzaStore {
    virtual ~PizzaStore() = default;
    std::string order() const { return createPizza()->name(); }
protected:
    virtual std::unique_ptr<Pizza> createPizza() const = 0;
};
struct CheeseStore : PizzaStore {
    std::unique_ptr<Pizza> createPizza() const override {
        return std::make_unique<CheesePizza>();
    }
};
// CheeseStore{}.order() → "치즈 피자"
```

### 3.2 Abstract Factory — 관련 객체 제품군을 일관되게 생성한다

**Intent**: 서로 관련되거나 함께 사용해야 하는 객체들의 **제품군(Family)**을 구체 Class에 의존하지 않고 생성한다.

```text
UI Factory
├─ Windows → WindowsButton + WindowsCheckbox
└─ macOS   → MacButton     + MacCheckbox
```

Factory Method는 **하나의 생성 지점을 하위 Class에 위임**하는 데, Abstract Factory는 **서로 맞는 제품군을 생성**하는 데 초점이 있다. Abstract Factory 내부에서 Factory Method를 사용할 수도 있다.

**Simple Factory**는 생성 분기를 한 곳에 모으는 유용한 관용구지만, GoF 23개에 포함되는 독립 패턴은 아니다.

**일상 예시 — 가구 세트:** 모던 가구와 클래식 가구의 의자·책상을 서로 어울리는 제품군으로 만든다.

```text
FurnitureFactory «interface»
├─ createChair(): Chair
└─ createDesk(): Desk
           △ 구현
      ┌────┴─────────┐
 ModernFactory  ClassicFactory
  ├─ ModernChair  ├─ ClassicChair
  └─ ModernDesk   └─ ClassicDesk
```

**왜 쓰나?** 서로 맞지 않는 제품 조합을 방지하고 제품군을 통째로 교체할 수 있다.

**핵심 코드 (C++17):** Factory 구현을 바꾸면 서로 어울리는 제품군이 함께 바뀐다.

```cpp
#include <memory>
#include <string>
struct Chair {
    virtual ~Chair() = default;
    virtual std::string style() const = 0;
};
struct Desk {
    virtual ~Desk() = default;
    virtual std::string style() const = 0;
};
struct ModernChair : Chair {
    std::string style() const override { return "모던 의자"; }
};
struct ModernDesk : Desk {
    std::string style() const override { return "모던 책상"; }
};
struct FurnitureFactory {
    virtual ~FurnitureFactory() = default;
    virtual std::unique_ptr<Chair> chair() const = 0;
    virtual std::unique_ptr<Desk> desk() const = 0;
};
struct ModernFactory : FurnitureFactory {
    std::unique_ptr<Chair> chair() const override {
        return std::make_unique<ModernChair>();
    }
    std::unique_ptr<Desk> desk() const override {
        return std::make_unique<ModernDesk>();
    }
};
// ModernFactory f; f.chair()->style(), f.desk()->style()
```

### 3.3 Builder — 복잡한 생성 절차를 분리한다

**Intent**: 복잡한 객체의 생성 절차를 객체 표현과 분리한다.

Factory 계열이 **어떤 객체를 생성할지**에 초점이라면 Builder는 **복잡한 객체를 어떤 절차로 조립할지**에 초점이 있다.

**일상 예시 — 햄버거 주문:** 빵·패티·치즈·소스를 원하는 순서와 옵션으로 조립한다. 옵션이 많아져도 긴 생성자 인자 목록을 피할 수 있다.

**객체 구성과 조립 흐름**

```text
BurgerBuilder
├─ bun("통밀빵") ─┐
├─ addCheese() ───┼─> 내부 Burger 설정
└─ build() ───────┘         │
                            ▼
                    Burger {통밀빵, 치즈}
```

**핵심:** Client가 긴 생성자 대신 Builder에 설정을 누적하고 마지막에 완성 객체를 받는다.

**핵심 코드 (C++17):** 옵션을 단계적으로 설정한 뒤 완성한다.

```cpp
#include <utility>
#include <string>
struct Burger {
    std::string bun = "기본빵";
    bool cheese = false;
    bool sauce = false;
};
class BurgerBuilder {
    Burger burger;
public:
    BurgerBuilder& bun(std::string value) {
        burger.bun = std::move(value); return *this;
    }
    BurgerBuilder& addCheese() { burger.cheese = true; return *this; }
    BurgerBuilder& addSauce() { burger.sauce = true; return *this; }
    Burger build() const { return burger; }
};
// Burger order = BurgerBuilder{}.bun("통밀빵").addCheese().build();
```

생성자 인자를 늘리는 대신 **Builder가 조립 과정**을 담당한다. 이 코드는 Fluent Builder 예시이며 GoF의 Director는 필요할 때 별도로 둘 수 있다.

### 3.4 Prototype — 기존 객체를 복제해 만든다

**Intent**: Client가 구체 Class의 생성 방법을 몰라도 **기존 객체(Prototype)를 복제해 새 객체를 얻도록** 생성 책임을 구성한다.

**일상 예시 — 문서 템플릿:** 이미 글꼴·여백·표가 설정된 이력서 원본을 복제해 여러 이력서를 만든다. 매번 설정을 다시 조립할 필요가 없다.

**copy()/clone() 메서드가 필수인가?** 아니다. 객체가 스스로 복제하는 방식이 대표적이지만, **외부 복제 함수나 복제 서비스**를 통해서도 구현할 수 있다. 핵심은 복제 함수의 위치가 아니라 **기존 객체를 생성 원형으로 사용하고, Client의 구체 생성 타입 의존을 줄이는 설계 의도**다.

단순히 `copy()` 함수가 있다는 이유만으로 Prototype 패턴이 되는 것은 아니다. 외부 함수가 구체 타입마다 분기·생성자를 직접 알아야 한다면, Client의 의존성을 어디까지 줄였는지 따져봐야 한다.

**적용 신호:** 생성·초기화가 복잡하거나 비용이 크고, 실행 중 구성된 객체를 원형으로 재사용하거나, 구체 Class를 몰라도 복제해야 할 때.

**Trade-off:** 복제가 항상 생성보다 빠른 것은 아니며, 내부 참조를 공유하는 **얕은 복사(Shallow Copy)**와 참조 대상까지 복제하는 **깊은 복사(Deep Copy)**를 구분해야 한다.

**복제 관계와 호출 흐름**

```text
Client → duplicate(Document& original)
                  │
                  ▼ clone() (가상 함수)
          Document «interface»
                  △ 구현
                  │
               Resume
                  │ 복제
                  ▼
            새 Resume 객체
```

**핵심:** Client는 원형의 실제 타입을 몰라도 `clone()`으로 같은 구체 타입을 복제한다.

**핵심 코드 (C++17):** Client는 구체 문서 타입을 몰라도 원형에 복제를 요청한다.

```cpp
#include <utility>
#include <memory>
#include <string>
struct Document {
    virtual ~Document() = default;
    virtual std::unique_ptr<Document> clone() const = 0;
    virtual std::string title() const = 0;
};
struct Resume : Document {
    std::string name;
    explicit Resume(std::string n) : name(std::move(n)) {}
    std::unique_ptr<Document> clone() const override {
        return std::make_unique<Resume>(*this);
    }
    std::string title() const override { return name; }
};
std::unique_ptr<Document> duplicate(const Document& original) {
    return original.clone();
}
// Resume original{"이력서"}; auto copy = duplicate(original);
```

`clone()`은 대표 구현일 뿐 필수 메서드명은 아니다. 참조 멤버가 있다면 복사 정책을 별도로 정한다.

### 3.5 Singleton — Instance를 하나로 제한한다

**Intent**: 특정 Class의 Instance를 하나로 제한하고 접근점을 제공한다.

**일상 예시 — 앱 설정:** 여러 서비스가 하나의 설정 객체를 공유한다.

**핵심 경계:** 객체가 **하나라는 것**과 그 객체에 **전역에서 직접 접근한다는 것**은 서로 다른 설계 결정이다. `static` 필드·메서드는 전역 접근의 대표적 구현 수단이지만, 객체를 외부에서 주입받아 공유할 수도 있다.

**Trade-off:** 전역 접근은 편리하지만 의존성이 숨겨지고 테스트 격리가 어려워질 수 있다. 인스턴스가 하나여야 하는 범위와 접근 방식을 별도로 판단한다.

Spring Bean의 기본 Singleton Scope, DI, ApplicationContext별 인스턴스 관리 등은 프레임워크 수명 관리의 세부 사항이므로 별도 보충학습에서 다룬다.

**단일 인스턴스와 접근 관계**

```text
Service A ──┐
            ├──> Config::instance()
Service B ──┘           │
                        ▼
                 static Config 1개
```

**핵심:** 전형적인 구현은 정적 접근점으로 한 객체를 공유한다. 공유 인스턴스를 DI로 전달하는 설계와는 구분한다.

**핵심 코드 (C++17):** 함수 내부 정적 객체로 단일 인스턴스를 제공한다.

```cpp
struct Config {
    static Config& instance() {
        static Config value; // C++11 이후 초기화는 thread-safe
        return value;
    }
    Config(const Config&) = delete;
    Config& operator=(const Config&) = delete;
private:
    Config() = default;
};
// Config& a = Config::instance();
// Config& b = Config::instance(); // &a == &b
```

전역 접근 방식의 대표 구현이다. DI로 같은 객체를 공유하는 것과 **접근 방식은 구분**한다.

## 4. 구조 Pattern — 조합과 경계를 다룬다

구조 패턴은 **객체를 어떤 관계로 연결해 기능을 구성할지**를 다룬다. 아래 ASCII에서 `──has──`는 객체 참조, `△ 구현`은 Interface 구현, `△ 상속`은 일반화를 뜻한다. **호출 흐름(→)**과 **객체 관계(──has──)**는 구분해서 읽는다.

### 4.1 Adapter — Interface 모양을 변환한다

**문제:** 해외 플러그를 한국 콘센트에 바로 꽂을 수 없듯, 기존 라이브러리의 메서드가 Client가 기대하는 Interface와 다를 수 있다.

**클래스 관계도**

```text
         ┌────────────────┐
         │ «interface»    │
Client ──> PowerPort      │
         │ + plugIn()     │
         └────────────────┘
                  △ 구현
                  │
         ┌────────────────┐       참조        ┌────────────────┐
         │ PlugAdapter    │ ────────────────> │ ForeignPlug    │
         │ + plugIn()     │                   │ + connectForeign()│
         └────────────────┘                   └────────────────┘
```

**실제 호출:** `Client → PowerPort.plugIn() → PlugAdapter.plugIn() → ForeignPlug.connectForeign()`. Adapter는 두 인터페이스 사이의 **호출 번역기**다.

**Intent:** 기존 객체를 변경하지 않고 Adapter가 **기대 Interface를 구현하고 기존 호출로 변환**한다.

**효과·대가:** Client를 바꾸지 않고 호환성을 확보하지만, 변환용 객체가 하나 더 필요하다. **Facade는 Interface 호환보다 여러 기능의 진입점 단순화**가 목적이다.

**핵심 코드 (C++17):** `PowerPort`를 기대하는 Client는 기존 `ForeignPlug`의 메서드를 몰라도 된다.

```cpp
#include <iostream>
struct PowerPort {
    virtual ~PowerPort() = default;
    virtual void plugIn() = 0;
};
struct ForeignPlug {
    void connectForeign() { std::cout << "전원 연결\n"; }
};
struct PlugAdapter : PowerPort {
    ForeignPlug& plug; // 기존 객체를 소유하지 않음
    explicit PlugAdapter(ForeignPlug& p) : plug(p) {}
    void plugIn() override { plug.connectForeign(); }
};
void useOutlet(PowerPort& port) { port.plugIn(); }

// ForeignPlug foreign;
// PlugAdapter adapter{foreign};
// useOutlet(adapter); // "전원 연결"
```

`PlugAdapter`는 `PowerPort`를 **구현**하고 `ForeignPlug`를 **참조**한다. 기존 객체의 수명은 Adapter보다 길어야 한다.

### 4.2 Facade — 복잡한 Subsystem 앞을 단순화한다

**문제:** 호텔 투숙객이 청소·식당·차량 담당자를 일일이 찾아다녀야 한다면 이용이 복잡하다.

**객체 관계도**

```text
               ┌─────────────────┐
Guest ────────>│ FrontDesk       │
               │ + arrangeStay() │
               └─────────────────┘
                 │      │      │
               참조   참조   참조
                 ▼      ▼      ▼
             Cleaning Restaurant TaxiService
              request() reserve()   call()
```

**실제 호출:** 손님은 `arrangeStay()`만 호출하고, Facade가 세 서비스를 순서대로 호출한다. **인터페이스 변환이 아니라 호출 진입점의 단순화**가 목적이다.

**Intent:** 여러 Subsystem의 호출을 **단일한 단순 진입점**으로 제공한다.

**효과·대가:** Client의 호출·의존 관계를 단순화하지만 Facade에 너무 많은 역할을 몰아넣지 않도록 한다. 하위 기능을 반드시 숨기거나 접근을 금지하는 것은 아니다.

**핵심 코드 (C++17):** 손님은 하위 서비스의 호출 순서를 몰라도 프런트 한 곳에 요청한다.

```cpp
#include <iostream>
struct Cleaning {
    void request() { std::cout << "청소 요청\n"; }
};
struct Restaurant {
    void reserve() { std::cout << "식당 예약\n"; }
};
struct TaxiService {
    void call() { std::cout << "택시 호출\n"; }
};
struct FrontDesk {
    Cleaning& cleaning;
    Restaurant& restaurant;
    TaxiService& taxi;
    FrontDesk(Cleaning& c, Restaurant& r, TaxiService& t)
        : cleaning(c), restaurant(r), taxi(t) {}
    void arrangeStay() {
        cleaning.request();
        restaurant.reserve();
        taxi.call();
    }
};
// Cleaning c; Restaurant r; TaxiService t;
// FrontDesk front{c, r, t};
// front.arrangeStay();
```

`FrontDesk`는 하위 객체들을 **참조**하고 호출을 조정한다. Adapter와 달리 별도의 기존 Interface를 변환할 필요는 없다. 세 서비스는 FrontDesk보다 오래 살아 있어야 한다.

### 4.3 Decorator — 같은 Interface로 기능을 덧붙인다

**문제:** 커피에 우유·시럽·휘핑을 추가할 때 모든 조합을 별도 Class로 만들면 Class 수가 늘어난다.

```text
[적용 전: 조합마다 별도 Class]
Coffee
├─ MilkCoffee
├─ SyrupCoffee
└─ MilkSyrupCoffee ...  ← 옵션이 늘수록 조합 증가
```

**클래스 관계:** 기본 커피와 모든 Decorator는 동일한 `Beverage` Interface를 구현한다. Decorator는 자신도 Beverage이면서 **내부에 또 다른 Beverage를 보관**한다.

```text
                    ┌───────────────────┐
                    │    «interface»    │
                    │     Beverage      │
                    │    + price()      │
                    └───────────────────┘
                             △ 구현
                ┌────────────┴─────────────┐
                │                          │
          ┌───────────┐            ┌────────────────┐
          │  Coffee   │            │    Decorator   │
          │ + price() │            │ - inner:       │
          └───────────┘            │   Beverage     │
                                   └────────────────┘
                                            △ 상속
                                     ┌──────┴──────┐
                                     │             │
                               MilkDecorator  SyrupDecorator

Decorator ──has──> Beverage  (감싸는 객체를 참조·소유)
```

**실제 객체 관계와 호출 흐름:** 같은 Interface이므로 원하는 순서로 겹겹이 감쌀 수 있다.

```text
[객체 구성]
SyrupDecorator
└─ inner → MilkDecorator
           └─ inner → Coffee

[price() 호출과 결과]
Syrup.price()
  → Milk.price() + 300
      → Coffee.price() + 500
          → 3000
  = 3800
```

**Intent:** 같은 Interface를 유지하는 Wrapper로 기존 객체를 감싸 기능을 **겹쳐 조합**한다.

**효과·대가:** 옵션 조합마다 Class를 만들 필요가 없지만 Wrapper가 여러 겹이면 호출 흐름 추적이 어려워진다. **Proxy도 감싸는 구조를 쓰지만 접근 제어가 목적**이라는 점이 다르다.

**핵심 코드 (C++17):** `unique_ptr<Beverage>`가 감싸는 객체의 소유 관계를 표현한다.

```cpp
#include <memory>
#include <utility>

struct Beverage {
    virtual ~Beverage() = default;
    virtual int price() const = 0;
};
struct Coffee : Beverage {
    int price() const override { return 3000; }
};
struct MilkDecorator : Beverage {
    std::unique_ptr<Beverage> inner;
    explicit MilkDecorator(std::unique_ptr<Beverage> b)
        : inner(std::move(b)) {}
    int price() const override { return inner->price() + 500; }
};
struct SyrupDecorator : Beverage {
    std::unique_ptr<Beverage> inner;
    explicit SyrupDecorator(std::unique_ptr<Beverage> b)
        : inner(std::move(b)) {}
    int price() const override { return inner->price() + 300; }
};

// auto order = std::make_unique<SyrupDecorator>(
//     std::make_unique<MilkDecorator>(std::make_unique<Coffee>()));
// order->price() == 3800
```

### 4.4 Proxy — 실제 객체 앞에서 접근을 통제한다

**문제:** 아파트 방문자가 누구나 바로 출입할 수 없도록 경비실에서 확인해야 한다.

**클래스 관계도**

```text
               ┌────────────────┐
               │ «interface»    │
               │ Door           │
               │ + enter()      │
               └────────────────┘
                        △ 구현
                ┌───────┴────────┐
                │                │
          ┌───────────┐    ┌─────────────┐
          │ RealDoor  │<───│ GuardProxy  │
          │ + enter() │참조│ + enter()   │
          └───────────┘    └─────────────┘

호출: Visitor → GuardProxy
                   ├─ 허용 → RealDoor.enter()
                   └─ 거부 → 종료
```

**Decorator와 차이:** 같은 인터페이스로 감싸지만 Proxy는 **실제 객체로의 접근을 통제**한다.

**Intent:** 실제 객체와 **같은 Interface를 제공하는 대리 객체**가 호출을 통제한다.

**변형:** Protection Proxy(권한), Virtual Proxy(지연 생성), Remote Proxy(원격 호출 대리). Decorator는 기능을 덧붙이고 Proxy는 접근·생성·호출을 대신 관리한다.

**핵심 코드 (C++17):** Proxy가 같은 Interface로 요청을 받아 접근을 통제한다.

```cpp
#include <memory>
#include <string>
struct Door {
    virtual ~Door() = default;
    virtual std::string enter() const = 0;
};
struct RealDoor : Door {
    std::string enter() const override { return "입장"; }
};
struct GuardProxy : Door {
    std::unique_ptr<Door> target = std::make_unique<RealDoor>();
    bool allowed;
    explicit GuardProxy(bool ok) : allowed(ok) {}
    std::string enter() const override {
        return allowed ? target->enter() : "출입 거부";
    }
};
// GuardProxy{false}.enter() → "출입 거부"
```

### 4.5 Composite — 부분과 전체를 같은 방식으로 다룬다

**문제:** 파일 하나와 여러 파일을 담은 폴더에 각각 다른 사용법을 강요하면 Client가 매번 종류를 구분해야 한다.

**클래스 관계도**

```text
               ┌─────────────────┐
               │ «interface»     │
               │ Item            │
               │ + size()        │
               └─────────────────┘
                        △ 구현
                  ┌─────┴──────┐
                  │            │
                File         Folder
                size()       size()
                               │ 소유 (0..*)
                               └────────> Item
```

**실제 객체 트리**

```text
RootFolder.size()
├─ photo.jpg      3 MB
├─ notes.txt      1 MB
└─ DocsFolder.size()
   ├─ a.pdf       2 MB
   └─ b.pdf       4 MB
합계 = 10 MB
```

**핵심:** Folder도 Item이므로 다른 Folder 안에 들어갈 수 있다.

**Intent:** Leaf(파일)와 Composite(폴더)를 **같은 Interface**로 다루고, Composite가 자식에게 작업을 위임한다.

**효과·대가:** 재귀적 트리 처리가 쉬워지지만 모든 작업이 Leaf와 Composite 양쪽에서 자연스럽지는 않을 수 있다.

**핵심 코드 (C++17):** 파일과 폴더가 같은 `size()` Interface를 제공한다.

```cpp
#include <utility>
#include <memory>
#include <vector>
struct Item {
    virtual ~Item() = default;
    virtual int size() const = 0;
};
struct File : Item {
    int mb;
    explicit File(int n) : mb(n) {}
    int size() const override { return mb; }
};
struct Folder : Item {
    std::vector<std::unique_ptr<Item>> children;
    void add(std::unique_ptr<Item> item) {
        children.push_back(std::move(item));
    }
    int size() const override {
        int total = 0;
        for (const auto& child : children) total += child->size();
        return total;
    }
};
// Folder root; root.add(std::make_unique<File>(3));
// root.add(std::make_unique<File>(7)); // root.size() == 10
```

폴더가 자식 객체를 **소유**하고 재귀적으로 위임한다.

### 4.6 Bridge — 독립적으로 변하는 두 축을 분리한다

**문제:** 기본·고급 리모컨과 삼성·LG TV를 상속만으로 조합하면 `BasicSamsungRemote`, `AdvancedSamsungRemote`, `BasicLGRemote`처럼 조합별 Class가 늘어난다.

**클래스 관계도: 두 축의 독립적 확장**

```text
       추상화 계층                     구현 계층
┌──────────────────┐             ┌─────────────────┐
│ Remote           │ ──참조─────> │ «interface»     │
│ - device: Device │             │ Device          │
│ + on()           │             │ + powerOn()     │
└──────────────────┘             └─────────────────┘
         △ 상속                           △ 구현
    ┌────┴──────┐                    ┌─────┴─────┐
 BasicRemote  AdvancedRemote       SamsungTV    LGTV

실제 조합: AdvancedRemote ──참조──> LGTV
다른 조합: BasicRemote    ──참조──> SamsungTV
```

**핵심:** Remote의 하위 타입을 추가해도 Device 구현을 수정하지 않고, TV 제조사가 늘어도 Remote 계층을 수정할 필요가 없다.

**Intent:** 리모컨 기능(추상화)과 TV 제어 구현을 분리해 **두 축을 독립적으로 확장**한다.

**효과·대가:** 조합별 상속 Class 폭증을 줄이지만 추상화와 위임 객체가 추가된다. Strategy와 유사한 위임 구조를 사용해도 Bridge는 **두 계층의 독립적 확장**이 중심이다.

**핵심 코드 (C++17):** 리모컨 계층과 TV 구현 계층을 객체 참조로 분리한다.

```cpp
#include <iostream>
struct Device {
    virtual ~Device() = default;
    virtual void powerOn() = 0;
};
struct TV : Device {
    void powerOn() override { std::cout << "TV 켜짐\n"; }
};
struct Remote {
    Device& device; // 소유하지 않는 참조
    explicit Remote(Device& d) : device(d) {}
    virtual ~Remote() = default;
    void on() { device.powerOn(); }
};
struct AdvancedRemote : Remote {
    using Remote::Remote;
    void quickOn() { on(); }
};
// TV tv; AdvancedRemote remote{tv}; remote.quickOn();
```

### 4.7 Flyweight — 반복되는 공통 상태를 공유한다

**문제:** 지도에 카페 핀이 수만 개 있을 때 각 핀마다 같은 아이콘 이미지·스타일을 복사하면 메모리를 낭비한다.

**공유 객체 관계도**

```text
          각 Pin (위치는 개별 상태)
┌────────────────┐
│ Pin A (10, 20) │ ──┐
├────────────────┤   │
│ Pin B (40, 80) │ ──┼──참조──> ┌──────────────────┐
├────────────────┤   │          │ CafeIcon         │
│ Pin C (60, 90) │ ──┘          │ image, style     │
└────────────────┘              │ 공유 인스턴스 1개 │
                                └──────────────────┘
```

**핵심:** 좌표는 Pin마다 다르지만 동일 아이콘 데이터는 공유한다.

**Intent:** 대량의 객체에서 변하지 않는 **공통 상태를 Flyweight 객체로 공유**하고 위치 같은 개별 상태는 외부에서 관리한다.

**효과·대가:** 메모리를 절약할 수 있지만 공유 상태와 개별 상태를 분리·관리해야 한다. 객체 수가 적으면 효과가 작다.

**핵심 코드 (C++17):** 각 핀은 좌표만 따로 갖고 아이콘 객체는 공유한다.

```cpp
#include <utility>
#include <memory>
#include <string>
struct Icon {
    std::string image;
    explicit Icon(std::string s) : image(std::move(s)) {}
};
struct Pin {
    int x, y; // 개별 상태
    std::shared_ptr<const Icon> icon; // 공유 상태
};
auto cafeIcon = std::make_shared<const Icon>("cafe.png");
Pin a{10, 20, cafeIcon};
Pin b{40, 80, cafeIcon};
// a.icon == b.icon
```

`shared_ptr`는 공유 수명을 표현하는 예시다. 실제 Flyweight에서는 Factory/Cache로 같은 아이콘을 재사용하도록 관리할 수도 있다.

## 5. 행위 Pattern — 책임과 상호작용을 다룬다

### 5.1 Strategy — 알고리즘을 교체 가능하게 만든다

**Intent**: 동일 목적의 Algorithm·Policy를 공통 Interface 뒤로 분리해 Runtime에 교체한다.

적용 신호는 같은 목적의 `if / else if` 알고리즘 분기가 반복되는 경우다.

**일상 예시 — 내비게이션:** 목적지는 같지만 도보·자동차·자전거 경로 계산 방법을 바꿔 끼운다.

**왜 쓰나?** 새로운 이동 수단이 추가되어도 Navigator의 경로 계산 분기를 늘리지 않는다.

**객체 관계와 호출 흐름**

```text
Navigator ──참조──> RouteStrategy «interface»
                              △ 구현
                        ┌─────┴─────┐
                     WalkRoute    CarRoute

Navigator.guide()
  → strategy.route() → "도보 경로" 또는 "자동차 경로"
```

**핵심:** Navigator는 계산 방법의 구체 타입을 몰라도 Strategy를 교체할 수 있다.

**핵심 코드 (C++17):** 경로 계산을 Strategy 객체에 위임해 교체한다.

```cpp
#include <string>
struct RouteStrategy {
    virtual ~RouteStrategy() = default;
    virtual std::string route() const = 0;
};
struct WalkRoute : RouteStrategy {
    std::string route() const override { return "도보 경로"; }
};
struct CarRoute : RouteStrategy {
    std::string route() const override { return "자동차 경로"; }
};
struct Navigator {
    const RouteStrategy& strategy; // 소유하지 않는 참조
    explicit Navigator(const RouteStrategy& s) : strategy(s) {}
    std::string guide() const { return strategy.route(); }
};
// WalkRoute walk; Navigator nav{walk}; nav.guide() → "도보 경로"
```

### 5.2 State — 상태에 따른 행동과 전이를 객체로 분리한다

**Intent**: 객체의 Lifecycle State에 따라 달라지는 행동을 State 객체로 분리한다.

Strategy와 구조는 유사하지만 질문이 다르다.

**일상 예시 — 자판기:** 대기·동전 투입·상품 배출 상태에 따라 같은 버튼을 눌러도 행동이 달라진다.

**Strategy와 차이:** 정책 선택보다 **상태에 따른 행동·전이**가 핵심이다.

**상태 객체 관계와 전이**

```text
VendingMachine ──소유──> State «interface»
                            △ 구현
                        ┌───┴────┐
                       Idle     Paid

[호출 순서]
Idle ──insertCoin()──> Paid
Paid ──press()───────> "상품 배출"
                        │
                        └──> Idle로 전이
```

**핵심:** 현재 State가 행동을 결정하고, Context가 그 결과에 따라 상태 객체를 교체한다.

**핵심 코드 (C++17):** State가 동작 결과를 반환하고 Context가 그 결과에 따라 상태를 전환한다. 현재 State의 메서드가 실행 중일 때 자기 객체를 파괴하지 않도록 전이 시점을 분리한 간략 예시다.

```cpp
#include <memory>
#include <string>
struct VendingMachine;
struct State {
    virtual ~State() = default;
    virtual std::string press(VendingMachine& m) = 0;
};
struct Idle : State {
    std::string press(VendingMachine&) override { return "동전을 넣으세요"; }
};
struct Paid : State {
    std::string press(VendingMachine& m) override;
};
struct VendingMachine {
    std::unique_ptr<State> state = std::make_unique<Idle>();
    void insertCoin() { state = std::make_unique<Paid>(); }
    std::string press() {
        auto result = state->press(*this);
        if (result == "상품 배출") state = std::make_unique<Idle>();
        return result;
    }
};
inline std::string Paid::press(VendingMachine&) {
    return "상품 배출"; // 호출이 끝난 뒤 Context가 Idle로 전이
}
// VendingMachine m; m.insertCoin(); m.press() → "상품 배출"
```

### 5.3 Template Method — 알고리즘 골격을 고정하고 일부 단계를 확장한다

**Intent**: 상위 Class가 전체 Algorithm의 Skeleton을 정의하고 일부 단계만 하위 Class가 구현한다.

Strategy가 **Composition으로 전체 알고리즘을 교체**한다면 Template Method는 **Inheritance로 알고리즘의 일부 단계만 바꾼다.**

**일상 예시 — 라면 조리법:** 물 끓이기 → 재료 넣기 → 완성 순서는 고정하고, 종류에 따라 재료 넣기 단계만 바꾼다.

**상속 관계와 실행 순서**

```text
        Ramen (추상 클래스)
        + cook() [고정]
        # addIngredients() [변경 지점]
                 △ 상속
                 │
             CheeseRamen
             + addIngredients()

cook(): boilWater() → addIngredients() → serve()
              공통          하위 구현        공통
```

**핵심:** 알고리즘의 전체 순서는 상위 클래스에, 바뀌는 단계는 하위 클래스에 둔다.

**핵심 코드 (C++17):** 상위 클래스가 조리 순서를 고정하고 하위 클래스가 일부 단계를 구현한다.

```cpp
#include <iostream>
struct Ramen {
    virtual ~Ramen() = default;
    void cook() { boilWater(); addIngredients(); serve(); }
protected:
    void boilWater() { std::cout << "물 끓이기\n"; }
    virtual void addIngredients() = 0;
    void serve() { std::cout << "완성\n"; }
};
struct CheeseRamen : Ramen {
    void addIngredients() override { std::cout << "면과 치즈\n"; }
};
// CheeseRamen{}.cook();
```

`cook()`이 Template Method이며 **상속으로 일부 단계만 교체**한다.

### 5.4 Observer — 상태 변화를 다수 구독자에게 알린다

**Intent**: Subject와 Observer를 느슨하게 결합해 상태 변화 시 여러 Observer에 Notification한다.

주의점은 Event 흐름이 많아지면 호출 경로와 실패 전파가 보이지 않게 될 수 있다는 것이다.

**일상 예시 — 유튜브 구독:** 채널이 영상을 올리면 구독자들이 알림을 받는다.

**왜 쓰나?** 채널이 구독자별 알림 구현을 직접 알 필요가 없다.

**구독 관계와 통지 흐름**

```text
Channel ──구독자 목록──> Subscriber «interface»
                                △ 구현
                                │
                              Viewer

Channel.upload("새 영상")
    └─ for each Subscriber → update("새 영상")
```

**핵심:** Channel은 구독자의 구체 타입을 몰라도 모두에게 통지한다. 구독자 수명은 별도 관리한다.

**핵심 코드 (C++17):** 채널은 Subscriber Interface만 알고 모든 구독자에게 통지한다.

```cpp
#include <string>
#include <vector>
#include <iostream>
struct Subscriber {
    virtual ~Subscriber() = default;
    virtual void update(const std::string& title) = 0;
};
struct Viewer : Subscriber {
    void update(const std::string& title) override {
        std::cout << "새 영상: " << title << '\n';
    }
};
struct Channel {
    std::vector<Subscriber*> subscribers; // 비소유 포인터; 구독자 수명 보장 필요
    void subscribe(Subscriber& s) { subscribers.push_back(&s); }
    void upload(const std::string& title) {
        for (auto* s : subscribers) s->update(title);
    }
};
// Viewer v; Channel c; c.subscribe(v); c.upload("여행 브이로그");
// 실제 구현에서는 unsubscribe 및 구독자 파괴 시 안전성 처리 필요
```

### 5.5 Mediator — 다대다 통신을 중앙 조정한다

**Intent**: 여러 객체가 서로 직접 참조하는 Mesh 관계를 Mediator로 모아 결합도를 줄인다.

Observer가 **일대다 Notification**에 가깝다면 Mediator는 **다대다 상호작용 조정**이 핵심이다.

**일상 예시 — 관제탑:** 비행기들이 서로 직접 조율하지 않고 관제탑을 통해 이착륙을 조정한다.

**객체 간 협력 조정**

```text
[직접 결합]
Checkbox ─────────> SubmitButton

[Mediator 사용]
Checkbox ──changed(true)──> Form
                              │
                              └─ submit.enabled = true
                                      │
                                      ▼
                                 SubmitButton
```

**핵심:** Checkbox가 SubmitButton을 직접 조작하지 않고 Form이 상호작용을 조정한다.

**핵심 코드 (C++17):** Checkbox가 직접 SubmitButton을 조작하지 않고 Form에 상태 변경을 알린다.

```cpp
#include <string>
struct SubmitButton {
    bool enabled = false;
};
struct Form {
    SubmitButton& submit;
    explicit Form(SubmitButton& b) : submit(b) {}
    void agreementChanged(bool checked) { submit.enabled = checked; }
};
struct Checkbox {
    Form& mediator;
    explicit Checkbox(Form& f) : mediator(f) {}
    void click(bool checked) { mediator.agreementChanged(checked); }
};
// SubmitButton button; Form form{button}; Checkbox check{form};
// check.click(true); // button.enabled == true
```

Checkbox는 SubmitButton을 직접 참조하지 않는다. 실제 Mediator는 **여러 UI 객체 간 상호작용을 중앙 조정 객체로 모으는 것**이 핵심이다.

### 5.6 Command — 요청 자체를 객체로 만든다

**Intent**: 요청을 객체로 캡슐화해 호출자(Invoker)와 실제 처리자(Receiver)를 분리한다.

그 결과 요청을 다음처럼 다룰 수 있다.

- Queue
- Log
- Retry
- Delay
- Undo

**일상 예시 — 리모컨 버튼:** 버튼은 '불 켜기' 명령 객체를 실행하고, 실제 전등은 명령 객체가 제어한다. 명령을 큐에 넣거나 취소 이력을 관리할 수 있다.

**객체 관계와 명령 실행**

```text
RemoteButton (Invoker) ──참조──> Command «interface»
                                    △ 구현
                                    │
                                LightOn
                                    │ 참조
                                    ▼
                                  Light

press() → execute() → Light.turnOn()
```

**핵심:** 버튼은 명령의 내용이 아니라 실행 인터페이스만 안다.

**핵심 코드 (C++17):** 버튼이 전등을 직접 몰라도 Command를 실행한다.

```cpp
#include <memory>
struct Light { bool on = false; void turnOn() { on = true; } };
struct Command {
    virtual ~Command() = default;
    virtual void execute() = 0;
};
struct LightOn : Command {
    Light& light;
    explicit LightOn(Light& l) : light(l) {}
    void execute() override { light.turnOn(); }
};
struct RemoteButton {
    Command& command;
    explicit RemoteButton(Command& c) : command(c) {}
    void press() { command.execute(); }
};
// Light light; LightOn cmd{light};
// RemoteButton button{cmd}; button.press(); // light.on == true
```

Invoker는 Command만 알고 Receiver인 Light의 구체 동작은 모른다.

### 5.7 Memento — 이전 상태를 Snapshot으로 보존한다

**Intent**: Encapsulation을 깨지 않고 객체 내부 상태를 Snapshot으로 저장·복원한다.

Command와 함께 Undo에 쓰이지만 역할은 다르다.

**일상 예시 — 그림판 되돌리기:** 그림을 수정하기 전 상태를 Snapshot으로 보관하고, Undo 시 복원한다.

**상태 저장·복원 흐름**

```text
Editor(text="초안")
    │ save()
    ▼
Snapshot("초안")  ← 상태 보관
    │
Editor.text = "수정"
    │ restore(snapshot)
    ▼
Editor(text="초안")
```

**핵심:** Command가 '무엇을 실행했는가'를 기록한다면 Memento는 '어떤 상태였는가'를 보존한다.

**핵심 코드 (C++17):** 상태를 Snapshot으로 저장했다가 복원한다.

```cpp
#include <string>
struct Editor {
    struct Snapshot { std::string text; };
    std::string text;
    Snapshot save() const { return {text}; }
    void restore(const Snapshot& old) { text = old.text; }
};
// Editor editor; editor.text = "초안";
// auto before = editor.save();
// editor.text = "수정"; editor.restore(before);
// editor.text == "초안"
```

이 예시는 값 복사로 Snapshot을 만든다. 실제 패턴에서는 **내부 상태의 캡슐화와 복원 권한**도 고려한다.

### 5.8 Chain of Responsibility — 처리자를 사슬로 연결한다

**Intent**: 요청의 최종 처리자를 호출자가 직접 정하지 않고 Handler Chain을 따라 전달한다.

Middleware, Filter, 인증·검증 Pipeline처럼 처리 단계가 조합되는 구조에서 자주 나타난다.

**일상 예시 — 고객센터:** 상담 요청을 1차 상담원 → 담당 팀 → 관리자 순으로 전달하고 처리 가능한 곳에서 멈춘다.

**책임 연쇄와 처리 흐름**

```text
Client → Staff(Handler)
            │ level <= 1 ?
            ├─ Yes → "상담원 처리"
            └─ No
                 ▼ next
             Manager(Handler)
                 └─ "관리자 처리"
```

**핵심:** 요청을 누가 처리할지 Client가 직접 선택하지 않고 Handler가 다음 Handler에 위임한다.

**핵심 코드 (C++17):** 처리할 수 없으면 다음 Handler로 넘긴다.

```cpp
#include <string>
struct Handler {
    Handler* next = nullptr; // 비소유 참조
    virtual ~Handler() = default;
    virtual std::string handle(int level) {
        return next ? next->handle(level) : "처리 불가";
    }
};
struct Staff : Handler {
    std::string handle(int level) override {
        return level <= 1 ? "상담원 처리" : Handler::handle(level);
    }
};
struct Manager : Handler {
    std::string handle(int level) override {
        return "관리자 처리";
    }
};
// Staff staff; Manager manager; staff.next = &manager;
// staff.handle(2) → "관리자 처리"
```

요청은 **Chain을 따라 전달**되고, 처리 가능한 Handler에서 종료된다.

### 5.9 Iterator — 순회 방법을 Collection에서 분리한다

**Intent**: Collection 내부 표현을 노출하지 않고 원소를 순차적으로 접근하는 방법을 제공한다.

Iterator Pattern과 Lazy Evaluation은 같은 개념이 아니다. Iterator는 **순회 Interface**, Lazy는 **계산 시점**의 문제다.

**일상 예시 — 음악 재생목록:** 재생목록 내부 저장 방식과 무관하게 '다음 곡'을 순서대로 가져온다.

**반복자와 순회 흐름**

```text
playlist: [101, 102, 103]
              │ begin()
              ▼
Iterator → 101 → 102 → 103 → end()
           *it   ++it  ++it

Client는 배열 내부 인덱싱 대신 Iterator 인터페이스 사용
```

**핵심:** 저장 구조의 세부 표현보다 순회 인터페이스에 의존한다.

**핵심 코드 (C++17):** Collection 내부 표현 대신 Iterator로 순회한다.

```cpp
#include <iostream>
#include <vector>
std::vector<int> playlist{101, 102, 103};
for (auto it = playlist.begin(); it != playlist.end(); ++it) {
    std::cout << *it << '\n';
}
```

C++ STL의 Iterator는 패턴의 실용적 구현이다. Client는 원소를 순회할 때 Container의 내부 저장 구조를 직접 다루지 않는다.

### 5.10 Visitor — 구조와 연산의 변화축을 분리한다

**Intent**: 객체 구조는 안정적이지만 그 위의 연산 종류가 자주 늘어날 때 연산을 Visitor로 분리한다.

장점과 대가가 뚜렷하다.

AST처럼 구조 타입은 비교적 안정적이고 분석·출력·검사 연산이 계속 늘어나는 경우에 적합하다.

**일상 예시 — 도형 계산:** 원·사각형 구조는 유지한 채 넓이 계산·출력·통계 기능을 Visitor로 추가한다. 도형 종류가 늘면 기존 Visitor들을 수정해야 할 수 있다.

**객체 관계와 Double Dispatch**

```text
Shape «interface»          Visitor «interface»
    △ 구현                       △ 구현
    │                             │
  Circle                      PrintVisitor
    │ accept(visitor)              │
    └──────────> visitor.visit(Circle)
```

**핵심:** `accept()`가 자신의 구체 타입에 맞는 `visit()`을 호출한다. 새 도형 타입이 추가되면 Visitor 구현들도 변경될 수 있다.

**핵심 코드 (C++17):** 도형 클래스에 새 연산을 추가하지 않고 Visitor가 처리한다.

```cpp
struct Circle;
struct Square;
struct Visitor {
    virtual ~Visitor() = default;
    virtual void visit(const Circle&) = 0;
    virtual void visit(const Square&) = 0;
};
struct Shape {
    virtual ~Shape() = default;
    virtual void accept(Visitor&) const = 0;
};
struct Circle : Shape {
    void accept(Visitor& v) const override { v.visit(*this); }
};
struct Square : Shape {
    void accept(Visitor& v) const override { v.visit(*this); }
};
struct PrintVisitor : Visitor {
    void visit(const Circle&) override {}
    void visit(const Square&) override {}
};
// Circle c; PrintVisitor printer; c.accept(printer);
```

`accept → visit`의 **Double Dispatch**가 핵심이다. 도형 타입을 추가하면 기존 Visitor들도 수정해야 한다.

### 5.11 Interpreter — 간단한 문법 규칙을 객체 구조로 표현한다

**Intent**: 작은 Language·DSL의 Grammar를 Class 구조로 표현하고 문장을 해석한다.

문법이 커지면 Parser Generator나 전용 Parser Architecture가 더 적합하므로 적용 범위가 좁다.

**일상 예시 — 계산기:** 숫자·덧셈·곱셈을 표현하는 노드가 `2 + 3 × 4` 같은 간단한 수식을 해석한다. 복잡한 문법에는 별도 Parser가 낫다.

**표현식 트리와 평가 순서**

```text
         Add : Expr
          /      \
   Number(2)   Number(3)

Add.eval()
  ├─ left.eval()  → 2
  └─ right.eval() → 3
  = 5
```

**핵심:** 문법 요소를 객체 트리로 구성하고 각 노드가 자신의 평가 규칙을 구현한다.

**핵심 코드 (C++17):** 작은 수식을 Expression 객체의 트리로 해석한다.

```cpp
#include <utility>
#include <memory>
struct Expr {
    virtual ~Expr() = default;
    virtual int eval() const = 0;
};
struct Number : Expr {
    int value;
    explicit Number(int n) : value(n) {}
    int eval() const override { return value; }
};
struct Add : Expr {
    std::unique_ptr<Expr> left, right;
    Add(std::unique_ptr<Expr> a, std::unique_ptr<Expr> b)
        : left(std::move(a)), right(std::move(b)) {}
    int eval() const override { return left->eval() + right->eval(); }
};
// Add{std::make_unique<Number>(2), std::make_unique<Number>(3)}.eval() == 5
```

문법 규칙을 객체 구조로 나타내는 최소 예시다. 연산자 우선순위·파싱은 별도 문제다.

## 6. 자주 헷갈리는 Pattern은 의도로 구분한다

| 비교 | 공통점 | 가르는 기준 |
|---|---|---|
| Strategy ↔ State | 동일 Interface로 행동 위임 | 정책 교체 ↔ Lifecycle 상태·전이 |
| Decorator ↔ Proxy | 같은 Interface로 Wrapper | 기능 추가 ↔ 접근 제어 |
| Adapter ↔ Facade | 앞에 다른 Interface를 둠 | Interface 변환 ↔ Subsystem 단순화 |
| Factory Method ↔ Template Method | 하위 타입이 일부 결정 | 생성 객체 결정 ↔ Algorithm 단계 결정 |
| Factory Method ↔ Prototype | 객체 생성 분리 | 하위 Class가 생성 타입 결정 ↔ 기존 Instance 복제 |
| Observer ↔ Mediator | 직접 결합을 줄임 | 일대다 통지 ↔ 다대다 조정 |
| Command ↔ Memento | Undo 구현에 조합 가능 | 요청 캡슐화 ↔ 상태 Snapshot |
| Strategy ↔ Template Method | Algorithm 변화 분리 | Composition ↔ Inheritance |

### 같은 객체 구조, 다른 설계 의도

GoF 23개는 23가지 완전히 독립적인 클래스 모양이 아니다. **같은 다형성·위임·합성 구조를 사용해도 해결하려는 문제가 다르면 다른 Pattern**이다. 아래는 정식 분류가 아니라 **구조적 유사성을 이용한 복습 지도**다.

```text
[1. 같은 Interface + Wrapper + 위임]

Component «interface»
       △ 구현
  ┌────┴────────┐
RealObject   Wrapper ──has──> Component

Decorator → 기능을 겹쳐 추가 (Milk(Coffee))
Proxy     → 접근·생성·호출 통제 (Guard → RealDoor)

[2. 같은 Interface + 구현 교체]

Context ──has──> Behavior «interface»
                       △ 구현
                    A / B / C

Strategy → 사용 목적에 따라 알고리즘 선택 (도보 / 자동차)
State    → 현재 상태에 따라 행동·전이 (대기 / 결제)

[3. 상속 + Hook 재정의]

Base
├─ 공통 흐름
└─ virtual hook()
       △ 상속
    Derived

Factory Method  → hook에서 생성할 객체를 결정
Template Method → hook에서 알고리즘의 일부 단계를 구현
```

| 구조적 유사성 | 구별할 질문 |
| --- | --- |
| Adapter ↔ Bridge | 기존 Interface를 **호환**시키려는가, 두 확장 축을 **독립**시키려는가? |
| Composite ↔ Decorator | 같은 Interface로 **부분·전체 트리**를 다루는가, **기능을 중첩**하는가? |
| Observer ↔ Mediator | 상태 변경을 **일대다 통지**하는가, 객체 간 **다대다 협력을 조정**하는가? |

**주의:** 유사한 UML 구조가 곧 같은 Pattern이라는 뜻은 아니다. 실제 구현은 언어·설계 선택에 따라 달라질 수 있으며, 한 설계에서 여러 Pattern을 조합할 수도 있다.

## 7. Pattern을 선택하는 판단 순서

Pattern 이름부터 찾지 않는다.

```text
1. 무엇이 자주 변하는가?
2. 그 변화가 현재 어느 객체에 퍼지는가?
3. 어떤 책임을 분리하면 변경 영향이 줄어드는가?
4. Interface / Composition / Delegation으로 경계를 만들 가치가 있는가?
5. Pattern을 적용해 얻는 이득이 추가 Class·간접 호출·추적 복잡성보다 큰가?
```

Pattern은 문제를 해결하기 위한 수단이지 Architecture의 목표가 아니다.

```text
Pattern 먼저 적용
→ 불필요한 추상화
→ Class 증가
→ 호출 흐름 복잡
→ 유지보수 비용 증가
```

두 번째 구현이 실제로 등장하지 않았는데 교체 가능성을 위해 Strategy를 미리 만들거나, Instance가 하나일 뿐인데 Singleton Global Access를 만드는 식의 사용은 피한다.

## 8. 객체지향 설계 원리와 연결

Pattern은 SOLID·결합도·응집도와 따로 외우는 주제가 아니다.

```text
변경 가능성 발견
        ↓
책임 분리
        ↓
Interface / Composition / Delegation
        ↓
결합도 감소 · 응집도 증가
        ↓
필요하면 Pattern으로 반복 구조 명명
```

예를 들면:

- Strategy: 변하는 Algorithm을 분리 → OCP
- Factory Method / Abstract Factory: 생성 책임과 사용 책임 분리 → DIP/OCP
- Decorator: 상속 대신 Composition으로 기능 확장 → OCP
- Facade: Subsystem 의존점을 하나로 줄임 → 결합도 감소
- Observer: Subject가 구체 Observer를 몰라도 됨 → 느슨한 결합

Pattern의 가치는 이름을 많이 아는 것이 아니라 **변경이 어디에서 발생하고 어떤 경계를 두면 영향이 줄어드는지 다시 도출할 수 있는 것**에 있다.
