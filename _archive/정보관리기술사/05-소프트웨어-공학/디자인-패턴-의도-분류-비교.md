# 디자인 패턴 — 의도·분류·비교

> 연결: [[00-전체|소프트웨어 공학 개념지도]]
>
> 학습 범위: Pattern 이름이나 코드 구현을 외우기보다 **반복되는 설계 문제 → 패턴의 의도 → 적용 조건 → Trade-off → 유사 패턴과의 경계**를 이해한다.

## 1. 디자인 패턴은 무엇을 해결하는가

소프트웨어 설계에서는 같은 종류의 변경 문제가 반복된다.

```text
객체 생성 방식이 자주 바뀜
→ 생성 책임을 분리할 필요

기존 객체를 조합해 기능을 확장해야 함
→ 상속 대신 조합 구조 필요

객체 사이의 책임·호출 관계가 복잡해짐
→ 상호작용을 분리·조정할 필요
```

디자인 패턴은 이런 반복 문제에 대해 검증된 **설계 의도와 책임 배치 방법**을 이름 붙인 것이다.

```text
Design Pattern
= 특정 Context에서 반복되는 설계 문제에 대한
  재사용 가능한 구조·책임·협력 방식
```

패턴의 핵심은 클래스 모양이 아니다.

```text
Context
→ 어떤 문제가 반복되는가

Intent
→ 무엇을 분리하거나 보호하려는가

Structure
→ 책임을 어디에 배치하는가

Consequence
→ 무엇을 얻고 어떤 복잡성을 추가하는가
```

같은 구조라도 의도가 다르면 다른 Pattern일 수 있고, 같은 의도도 언어의 함수·Closure·DI 같은 기능으로 더 단순하게 구현할 수 있다.

## 2. 전체 지도 — 생성·구조·행위

GoF Pattern은 **무엇을 바꾸고 분리하려는가**에 따라 세 갈래로 본다.

```text
Design Pattern
│
├─ Creational
│   └─ 객체를 어떻게 생성할 것인가
│
├─ Structural
│   └─ 객체·클래스를 어떻게 조합할 것인가
│
└─ Behavioral
    └─ 객체가 책임과 Message를 어떻게 주고받을 것인가
```

**GoF 23개 = 생성 5개 + 구조 7개 + 행위 11개.** 각 패턴의 전체 이름과 핵심 의도는 마지막 [복습용 전체 지도](#9-복습용-전체-지도)에 한 번만 모아 둔다.

이 세 분류는 발전 단계가 아니다. 서로 다른 설계 문제의 분류축이다.

## 3. 생성 Pattern — 생성 책임을 분리한다

### 3.1 Factory Method — 생성할 객체 종류를 하위 Class에 위임한다

```text
Client가 구체 Class를 직접 생성
→ 구체 타입 변경 시 Client 수정
→ 공통 생성 Interface를 두고 하위 Class가 생성 대상 결정
```

**Intent**: 객체 생성 Interface를 정의하되, 어떤 구체 객체를 만들지는 하위 Class가 결정하도록 한다.

**적용 신호**: Framework가 생성 시점과 사용 흐름은 통제하지만 실제 생성 타입은 확장 지점에서 결정해야 할 때.

**대가**: Creator 계층과 하위 Class가 늘어날 수 있다.


**예시 — 문서 Export:** `Exporter`의 공통 처리 흐름은 유지하고 `PdfExporter`는 `PdfWriter`, `CsvExporter`는 `CsvWriter`를 생성한다. 생성할 구체 타입의 결정 책임이 하위 Creator에 있다.

### 3.2 Abstract Factory — 관련 객체 제품군을 일관되게 생성한다

**Intent**: 서로 관련되거나 함께 사용해야 하는 객체들의 **제품군(Family)**을 구체 Class에 의존하지 않고 생성한다.

```text
UI Factory
├─ Windows → WindowsButton + WindowsCheckbox
└─ macOS   → MacButton     + MacCheckbox
```

Factory Method는 **하나의 생성 지점을 하위 Class에 위임**하는 데, Abstract Factory는 **서로 맞는 제품군을 생성**하는 데 초점이 있다. Abstract Factory 내부에서 Factory Method를 사용할 수도 있다.

**Simple Factory**는 생성 분기를 한 곳에 모으는 유용한 관용구지만, GoF 23개에 포함되는 독립 패턴은 아니다.

### 3.3 Builder — 복잡한 생성 절차를 분리한다

```text
Constructor Parameter 증가
→ 선택 조합이 복잡
→ 생성 과정 자체를 단계화
→ Builder
```

**Intent**: 복잡한 객체의 생성 절차를 객체 표현과 분리한다.

Factory 계열이 **어떤 객체를 생성할지**에 초점이라면 Builder는 **복잡한 객체를 어떤 절차로 조립할지**에 초점이 있다.


**예시 — HTTP 요청:** URL·Header·Timeout·Body를 선택적으로 조립해 `Request`를 만든다. 선택 항목이 늘어도 긴 Constructor 인자를 피할 수 있다.

### 3.4 Prototype — 기존 객체를 복제해 만든다

**Intent**: 구체 타입의 생성 과정을 직접 알지 않고 기존 Instance를 복제해 새 객체를 만든다.

적합한 경우:

- 초기화 비용이 큰 객체
- Runtime에 구성된 객체를 Template처럼 복제
- 구체 Class 의존을 줄이고 싶은 경우

주의점은 Deep Copy와 Shared Reference의 경계다.


**예시 — 보고서 양식:** 미리 구성한 `ReportTemplate`을 복제해 환자별 보고서를 만든다. 복제 시 내부 List를 공유할지 깊은 복사를 할지 결정해야 한다.

### 3.5 Singleton — Instance를 하나로 제한한다

**Intent**: 특정 Class의 Instance를 하나로 제한하고 접근점을 제공한다.

하지만 Singleton은 전역 상태가 되어 다음 문제를 만들 수 있다.

```text
Global Access
→ 의존성이 숨겨짐
→ Test 격리 어려움
→ 상태 결합 증가
```

따라서 "하나여야 한다"와 "전역에서 직접 접근해야 한다"는 별개다. 현대 Application에서는 DI Container가 수명 Scope를 관리하는 방식이 더 적절한 경우가 많다.

## 4. 구조 Pattern — 조합과 경계를 다룬다


**예시 — 설정 Registry:** 하나의 Registry Instance를 공유할 수 있지만, 전역 접근은 Test 간 상태 오염과 숨은 의존성을 만들 수 있다.

### 4.1 Adapter — Interface 모양을 변환한다

```text
Client가 원하는 Interface A
        ↕ 변환
기존 객체의 Interface B
```

**Intent**: 기존 객체를 수정하지 않고 Client가 기대하는 Interface로 변환한다.


**예시 — 외부 결제 연동:** 내부 `PaymentPort.pay()`를 외부 SDK의 `charge()` 호출로 변환한다.

```text
OrderService → PaymentPort.pay()
                    ↑ 구현
               SDKAdapter
                    ↓ 변환
              VendorSDK.charge()
```

### 4.2 Facade — 복잡한 Subsystem 앞을 단순화한다

**Intent**: 여러 Subsystem의 복잡한 호출을 하나의 단순한 진입점으로 제공한다.

```text
Client
  ↓
Facade
  ↓
Subsystem A · B · C
```

Adapter가 **Interface 변환**이라면 Facade는 **사용 진입점 단순화**다.


**예시 — 퇴원 처리:** `DischargeFacade`가 진료 기록 확인·정산·알림 Subsystem 호출을 하나의 `discharge()` 진입점으로 묶는다.

### 4.3 Decorator — 같은 Interface로 기능을 덧붙인다

**Intent**: 객체를 같은 Interface의 Wrapper로 감싸 기능을 동적으로 추가한다.

```text
Component
   ↑
Decorator ──has── Component
   ↑
Concrete Decorator
```

상속으로 기능 조합 Class가 폭발하는 문제를 Composition으로 푼다.


**예시 — HTTP Client:** 기본 Client를 `LoggingClient`, `RetryClient`로 감싸며 같은 `request()` Interface를 유지한다.

```text
Caller → Retry → Logging → HttpClient
         (모두 같은 Client Interface)
```

### 4.4 Proxy — 같은 Interface로 접근을 제어한다

**Intent**: 실제 객체 앞에 대리 객체를 두어 접근을 제어한다.

대표 목적:

- Virtual Proxy: 비싼 객체의 Lazy Loading
- Protection Proxy: 권한 통제
- Remote Proxy: 원격 객체 대리

Decorator와 구조는 비슷하지만 목적이 다르다.

```text
Decorator → 기능 추가
Proxy     → 접근 제어
```


**예시 — 접근 제어:** `PatientRecordProxy`가 권한을 확인한 뒤 실제 `PatientRecordService`로 요청을 전달한다.

```text
Caller → PatientRecordProxy → PatientRecordService
               │
          권한 확인 후 위임
```

### 4.5 Composite — 단일 객체와 집합을 같은 방식으로 다룬다

**Intent**: Tree 구조에서 Leaf와 Composite를 같은 Component Interface로 다룬다.

```text
Component
├─ Leaf
└─ Composite
   └─ children: Component[]
```

파일·디렉터리, UI Tree, 조직도처럼 **부분-전체 계층**이 핵심 신호다.


**예시 — 메뉴 트리:** 단일 `MenuItem`과 하위 항목을 가진 `MenuGroup`을 같은 `MenuComponent.render()`로 처리한다.

### 4.6 Bridge — 독립적으로 변하는 두 축을 분리한다

**Intent**: 추상화와 구현을 상속 계층 하나에 섞지 않고 Composition으로 분리해 각각 독립적으로 확장한다.

```text
Abstraction ──has── Implementor
     │                  │
Refined A/B        Impl X/Y
```

두 변화축의 조합 때문에 Class 수가 곱셈으로 늘어날 때 의미가 선명하다.


**예시 — 알림 채널:** `UrgentNotification`/`NormalNotification`과 `EmailSender`/`SmsSender`를 독립 축으로 두어 조합한다.

```text
Notification ──has── Sender
  ├─ Urgent            ├─ Email
  └─ Normal            └─ SMS
```

### 4.7 Flyweight — 공통 상태를 공유한다

**Intent**: 대량의 작은 객체에서 공통되는 Intrinsic State를 공유해 Memory 사용을 줄인다.

적용 전제는 **객체 수가 매우 많고 공유 가능한 상태가 분명할 것**이다. 일반 객체 수가 적다면 복잡성만 늘 수 있다.

## 5. 행위 Pattern — 책임과 상호작용을 다룬다


**예시 — 텍스트 편집기:** 동일한 글꼴·스타일 정보는 공유하고 글자 위치·선택 상태처럼 개별적인 정보는 외부에서 관리한다.

### 5.1 Strategy — 알고리즘을 교체 가능하게 만든다

**Intent**: 동일 목적의 Algorithm·Policy를 공통 Interface 뒤로 분리해 Runtime에 교체한다.

```text
Context ──has── Strategy
                 ↑
          Strategy A/B/C
```

적용 신호는 같은 목적의 `if / else if` 알고리즘 분기가 반복되는 경우다.


**예시 — 배송비 계산:** `ShippingCalculator`가 `StandardFee`와 `ExpressFee` 전략 중 하나에 계산을 위임한다.

```text
ShippingCalculator → FeeStrategy
                         △
                    ┌────┴────┐
                 Standard   Express
```

### 5.2 State — 상태에 따른 행동과 전이를 객체로 분리한다

**Intent**: 객체의 Lifecycle State에 따라 달라지는 행동을 State 객체로 분리한다.

Strategy와 구조는 유사하지만 질문이 다르다.

```text
Strategy
→ 어떤 정책·Algorithm을 선택할까?

State
→ 현재 Lifecycle State가 무엇이며 어떤 전이가 가능한가?
```


**예시 — 주문 상태:** 주문이 `Pending → Paid → Shipped`로 전이하며, 상태마다 취소·배송 요청에 대한 동작이 달라진다. 단순 상태값 열거가 아니라 상태별 책임을 객체에 둔다.

### 5.3 Template Method — 알고리즘 골격을 고정하고 일부 단계를 확장한다

**Intent**: 상위 Class가 전체 Algorithm의 Skeleton을 정의하고 일부 단계만 하위 Class가 구현한다.

Strategy가 **Composition으로 전체 알고리즘을 교체**한다면 Template Method는 **Inheritance로 알고리즘의 일부 단계만 바꾼다.**


**예시 — 파일 Import:** 상위 `Importer`가 `read → validate → save` 순서를 고정하고, 하위 `CsvImporter`와 `JsonImporter`가 `read()`를 구현한다.

### 5.4 Observer — 상태 변화를 다수 구독자에게 알린다

**Intent**: Subject와 Observer를 느슨하게 결합해 상태 변화 시 여러 Observer에 Notification한다.

```text
Subject
  ├─ Observer A
  ├─ Observer B
  └─ Observer C
```

주의점은 Event 흐름이 많아지면 호출 경로와 실패 전파가 보이지 않게 될 수 있다는 것이다.


**예시 — 주문 완료 이벤트:** `Order`의 상태 변경을 `EmailNotifier`, `AnalyticsListener`가 구독한다. Subject는 구독자의 구체 구현을 몰라도 된다.

### 5.5 Mediator — 다대다 통신을 중앙 조정한다

**Intent**: 여러 객체가 서로 직접 참조하는 Mesh 관계를 Mediator로 모아 결합도를 줄인다.

Observer가 **일대다 Notification**에 가깝다면 Mediator는 **다대다 상호작용 조정**이 핵심이다.


**예시 — 화면 Form:** 입력 필드들이 서로 직접 활성화 상태를 변경하는 대신 `FormMediator`가 필드 간 상호작용을 조정한다.

```text
Field A ──┐
Field B ──┼── FormMediator
Field C ──┘
```

### 5.6 Command — 요청 자체를 객체로 만든다

**Intent**: 요청을 객체로 캡슐화해 호출자(Invoker)와 실제 처리자(Receiver)를 분리한다.

그 결과 요청을 다음처럼 다룰 수 있다.

- Queue
- Log
- Retry
- Delay
- Undo


**예시 — 작업 Queue:** `SendEmailCommand`를 생성해 Queue에 넣으면 Worker가 나중에 실행한다. 요청 생성자와 실제 실행 시점을 분리한다.

### 5.7 Memento — 이전 상태를 Snapshot으로 보존한다

**Intent**: Encapsulation을 깨지 않고 객체 내부 상태를 Snapshot으로 저장·복원한다.

Command와 함께 Undo에 쓰이지만 역할은 다르다.

```text
Command
→ 무엇을 실행했는가

Memento
→ 이전 상태가 무엇이었는가
```


**예시 — 문서 편집 Undo:** 편집 전 상태를 `Snapshot`으로 저장하고 복원한다. Command는 실행한 작업, Memento는 저장한 상태를 담당한다.

### 5.8 Chain of Responsibility — 처리자를 사슬로 연결한다

**Intent**: 요청의 최종 처리자를 호출자가 직접 정하지 않고 Handler Chain을 따라 전달한다.

```text
Request
→ Handler A
→ Handler B
→ Handler C
```

Middleware, Filter, 인증·검증 Pipeline처럼 처리 단계가 조합되는 구조에서 자주 나타난다.


**예시 — HTTP Middleware:** 인증 → 권한 → Rate Limit Handler를 순서대로 연결하고, 각 Handler가 다음 단계로 넘기거나 요청을 종료한다.

### 5.9 Iterator — 순회 방법을 Collection에서 분리한다

**Intent**: Collection 내부 표현을 노출하지 않고 원소를 순차적으로 접근하는 방법을 제공한다.

Iterator Pattern과 Lazy Evaluation은 같은 개념이 아니다. Iterator는 **순회 Interface**, Lazy는 **계산 시점**의 문제다.


**예시 — 조회 결과 순회:** Client는 내부가 Array인지 Tree인지 몰라도 `next()`로 원소를 순회한다.

### 5.10 Visitor — 구조와 연산의 변화축을 분리한다

**Intent**: 객체 구조는 안정적이지만 그 위의 연산 종류가 자주 늘어날 때 연산을 Visitor로 분리한다.

장점과 대가가 뚜렷하다.

```text
새 Operation 추가
→ 쉬움

새 Element Type 추가
→ 모든 Visitor 수정 가능
```

AST처럼 구조 타입은 비교적 안정적이고 분석·출력·검사 연산이 계속 늘어나는 경우에 적합하다.


**예시 — AST 처리:** `NumberNode`, `BinaryNode` 구조를 유지하면서 `PrintVisitor`, `TypeCheckVisitor` 같은 연산을 추가한다. 반대로 Node 종류가 늘면 Visitor도 수정해야 한다.

### 5.11 Interpreter — 간단한 문법 규칙을 객체 구조로 표현한다

**Intent**: 작은 Language·DSL의 Grammar를 Class 구조로 표현하고 문장을 해석한다.

문법이 커지면 Parser Generator나 전용 Parser Architecture가 더 적합하므로 적용 범위가 좁다.


**예시 — 작은 검색 조건식:** `AND`, `OR`, `Term` 노드로 단순 필터 표현식을 구성하고 각 노드가 해석한다. 복잡한 언어에는 전용 Parser가 적합하다.

## 6. 자주 헷갈리는 Pattern은 의도로 구분한다

| 비교 | 공통점 | 가르는 기준 |
|---|---|---|
| Strategy ↔ State | 동일 Interface로 행동 위임 | 정책 교체 ↔ Lifecycle 상태·전이 |
| Decorator ↔ Proxy | 같은 Interface로 Wrapper | 기능 추가 ↔ 접근 제어 |
| Adapter ↔ Facade | 앞에 다른 Interface를 둠 | Interface 변환 ↔ Subsystem 단순화 |
| Factory Method ↔ Template Method | 하위 타입이 일부 결정 | 생성 객체 결정 ↔ Algorithm 단계 결정 |
| Factory Method ↔ Prototype | 객체 생성 분리 | 하위 Class가 생성 타입 결정 ↔ 기존 Instance 복제 |
| Observer ↔ Mediator | 직접 결합을 줄임 | 일대다 통지 ↔ 다대다 조정 |
| Command ↔ Memento | Undo 구현에 조합 가능 | 요청 캡슐화 ↔ 상태 Snapshot |
| Strategy ↔ Template Method | Algorithm 변화 분리 | Composition ↔ Inheritance |

## 7. Pattern을 선택하는 판단 순서

Pattern 이름부터 찾지 않는다.

```text
1. 무엇이 자주 변하는가?
2. 그 변화가 현재 어느 객체에 퍼지는가?
3. 어떤 책임을 분리하면 변경 영향이 줄어드는가?
4. Interface / Composition / Delegation으로 경계를 만들 가치가 있는가?
5. Pattern을 적용해 얻는 이득이 추가 Class·간접 호출·추적 복잡성보다 큰가?
```

Pattern은 문제를 해결하기 위한 수단이지 Architecture의 목표가 아니다.

```text
Pattern 먼저 적용
→ 불필요한 추상화
→ Class 증가
→ 호출 흐름 복잡
→ 유지보수 비용 증가
```

두 번째 구현이 실제로 등장하지 않았는데 교체 가능성을 위해 Strategy를 미리 만들거나, Instance가 하나일 뿐인데 Singleton Global Access를 만드는 식의 사용은 피한다.

## 8. 객체지향 설계 원리와 연결

Pattern은 SOLID·결합도·응집도와 따로 외우는 주제가 아니다.

```text
변경 가능성 발견
        ↓
책임 분리
        ↓
Interface / Composition / Delegation
        ↓
결합도 감소 · 응집도 증가
        ↓
필요하면 Pattern으로 반복 구조 명명
```

예를 들면:

- Strategy: 변하는 Algorithm을 분리 → OCP
- Factory Method / Abstract Factory: 생성 책임과 사용 책임 분리 → DIP/OCP
- Decorator: 상속 대신 Composition으로 기능 확장 → OCP
- Facade: Subsystem 의존점을 하나로 줄임 → 결합도 감소
- Observer: Subject가 구체 Observer를 몰라도 됨 → 느슨한 결합

Pattern의 가치는 이름을 많이 아는 것이 아니라 **변경이 어디에서 발생하고 어떤 경계를 두면 영향이 줄어드는지 다시 도출할 수 있는 것**에 있다.

## 9. 복습용 전체 지도

```text
Design Pattern
│
├─ 생성 — 객체 생성 변화 격리
│   ├─ Factory Method  : 생성할 타입을 하위 Class가 결정
│   ├─ Abstract Factory: 관련 객체 제품군 생성
│   ├─ Builder       : 복잡한 조립 절차
│   ├─ Prototype     : 기존 객체 복제
│   └─ Singleton     : Instance 수명·개수 제한
│
├─ 구조 — 객체 조합·경계
│   ├─ Adapter       : Interface 변환
│   ├─ Facade        : Subsystem 단순화
│   ├─ Decorator     : 기능 추가
│   ├─ Proxy         : 접근 제어
│   ├─ Composite     : 부분-전체 Tree
│   ├─ Bridge        : 두 변화축 분리
│   └─ Flyweight     : 공통 상태 공유
│
└─ 행위 — 책임·상호작용 분리
    ├─ Strategy      : Algorithm 교체
    ├─ State         : 상태별 행동·전이
    ├─ Template      : Algorithm 골격
    ├─ Observer      : 일대다 통지
    ├─ Mediator      : 다대다 조정
    ├─ Command       : 요청 객체화
    ├─ Memento       : 상태 Snapshot
    ├─ Chain         : Handler 연결
    ├─ Iterator      : 순회 추상화
    ├─ Visitor       : 구조와 연산 분리
    └─ Interpreter   : 간단한 문법 해석
```

> **Design Pattern은 생성·조합·상호작용에서 반복되는 변경 문제를 해결하기 위한 책임 배치 방법이다. 구조 모양을 외우기보다 무엇이 변하고, 무엇을 분리하며, 어떤 Trade-off가 생기는지를 먼저 본다.**
