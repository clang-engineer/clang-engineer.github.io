# 소프트웨어공학 스토리 학습 — 요구가 바뀌는 주문 서비스

> [전체 개념지도](00-전체.md)의 생명주기와 횡단 관리 개념을 가상 주문 서비스 프로젝트의 질문으로 이해한다. **생명주기와 개발 방법론은 같은 분류가 아니다.**

## 1. 무엇을 만들까 — 요구공학

고객이 '빠르고 편한 주문 서비스'를 요청했다.

**질문: 이 말만 듣고 개발하면 어떤 문제가 생길까?**

'빠르다'가 응답시간인지 배송시간인지 모른다. 요구공학은 이해관계자 필요의 도출(Elicitation), 분석, 명세, 검증을 다룬다. 기능 요구와 성능·보안 등 품질 요구도 구분한다.

**질문: 나중에 결제 오류가 나면 어느 요구에서 시작됐는지 어떻게 알까?**

요구 ↔ 설계 ↔ 구현 ↔ 시험의 **추적성(Traceability)**이 필요하다. 변경 영향도 파악할 수 있다.

## 2. 코드를 바로 작성할까 — 아키텍처와 설계

주문·결제·재고 로직을 뒤섞으면 한 기능의 변경이 다른 기능에 영향을 준다.

**질문: 책임을 어떻게 나누고 품질 요구를 만족시킬까?**

아키텍처는 구성요소·인터페이스·품질속성의 Trade-off를 다룬다. 상세 설계는 내부 구조를 구체화한다. UML은 구조·행위를 **표현하는 모델링 언어**이고, 객체지향 원칙은 설계 접근이며, Design Pattern은 반복 문제의 재사용 가능한 해법, Architecture Style은 시스템 수준 구조 선택이다.

**질문: UML을 그렸다는 이유만으로 아키텍처가 좋은가?**

아니다. UML은 표현 수단이다. 4+1 View Model은 아키텍처를 바라보는 관점이며 UML로 표현할 수 있다.

## 3. 요구가 계속 바뀐다 — 개발 모형·방법론

개발 중 쿠폰과 주문 취소 요구가 추가됐다.

**질문: 처음부터 모든 요구를 확정하는 방식이 항상 적절할까?**

요구가 안정적이면 Waterfall의 단계적 통제가 유리할 수 있다. 불확실하면 Iterative·Incremental로 반복·증분 개발하며 피드백을 얻는다. Agile은 변화 대응과 협업, RAD는 빠른 개발과 사용자 참여·도구 활용을 강조한다.

**질문: Waterfall → Agile → RAD는 차례대로 발전하는 단계일까?**

아니다. 개발 모형·방법론·지원 기법은 서로 다른 관점이며 함께 쓰이기도 한다. [개발 모형·방법론 지도](01-개발-모형과-방법론.md)에서 Prototyping·Spiral·Scrum·XP·JAD·CASE 등의 위치를 확인한다.

## 4. 코드가 실행되면 충분할까 — 검증·시험·품질

주문 기능은 명세대로 동작하지만 고객은 필요한 방식으로 주문을 취소하지 못한다.

**질문: 명세대로 만들었다는 것과 필요한 것을 만들었다는 것은 같을까?**

Verification은 명세·설계에 맞는지, Validation은 사용자 필요와 목적에 맞는지 보는 관점이다. Review와 Test로 확인하며 단위·통합·시스템·인수 시험은 검증 범위가 다르다. 시험 기법·Coverage는 또 다른 분류축이다.

**질문: 테스트가 모두 통과하면 결함이 전혀 없다고 증명되는가?**

아니다. 시험은 결함을 발견하고 위험을 줄이는 활동이다. [소프트웨어 테스트 전체 분류](소프트웨어-테스트의-전체-분류.md)에서 더 살펴본다.

## 5. 배포 후에도 개발은 계속된다 — 유지보수·DevOps

오픈 후 결제 오류, 신규 결제수단, 보안 업데이트가 생겼다.

**질문: 운영 중 변경을 모두 버그 수정이라고 부를까?**

유지보수는 수정·적응·개선·예방의 목적을 포함한다. DevOps는 개발·운영 협업과 피드백·자동화를 연결하고 CI/CD는 지속적 통합·전달·배포를 지원한다. Release와 Deployment도 동일하지 않다.

## 6. 모든 과정을 누가 통제할까 — 횡단 관리

여러 개발자가 동시에 수정해 어떤 버전이 기준인지 혼란스럽다.

**질문: 버전만 관리하면 변경 승인과 영향 분석도 끝날까?**

형상관리는 Configuration Item·Version·Baseline을 식별·통제하고, 변경관리는 변경의 영향·승인·추적을 다룬다. 프로젝트 관리는 범위·일정·비용·품질·위험·이해관계자를 조정한다. 외부 표준·OSS 라이선스·IP 역시 전 과정 제약이다.
