# 소프트웨어 개발 모형·방법론 개념지도

> **SDLC는 개발 활동의 생명주기**, 개발 모형은 그 흐름과 반복을 조직하는 방식, 개발 방법론은 활동을 수행하는 원칙·기법·산출물 체계를 다룬다. 모형과 방법론은 서로 배타적인 분류가 아니라 함께 적용될 수 있다.

이 지도는 [소프트웨어 공학 전체 개념지도](00-전체.md)의 '개발 방식 · 전달 · 운영'에서 내려온다. 성안당 Vol. 5의 PART 2(개발 모형), PART 3(개발 방법론)를 학습 범위 점검 기준으로 삼되 교재 목차를 그대로 복제하지 않는다.

## 1. 큰 그림: 무엇을 구분하는가

```text
SDLC: 요구 → 설계 → 구현 → 검증 → 배포 → 유지보수
  │
  ├─ 개발 모형: 단계를 어떤 흐름·반복·Feedback으로 운영할까?
  │   ├─ Waterfall         → 단계별 순차 진행
  │   ├─ Prototyping       → 시제품으로 요구 확인
  │   ├─ Spiral            → 반복마다 위험 분석
  │   ├─ Incremental       → 기능을 나누어 점진적 제공
  │   ├─ Evolutionary      → Feedback으로 제품 진화
  │   ├─ RAD               → 사용자 참여·도구·재사용으로 신속 개발
  │   └─ Cleanroom         → 정형적 명세·검증으로 결함 예방
  │
  └─ 개발 방법론·실천: 활동을 어떤 규칙과 기법으로 수행할까?
      ├─ 전통적: 구조적 / 정보공학 / 객체지향 / CBD
      ├─ Agile: XP / Scrum / Kanban / Lean
      ├─ RUP: 반복적·점진적, Use Case·Architecture 중심
      ├─ TDD: Test를 먼저 작성하는 개발 실천
      ├─ MDD / MDA: 모델 중심 개발 / 모델 기반 아키텍처
      ├─ SPL: 제품군의 공통성과 가변성 관리
      └─ DevOps: 개발·운영 협업 및 전달 자동화
```

**주의:** 위 가지는 학습을 위한 주된 위치다. Agile은 원칙·접근법이고 Scrum은 Framework, TDD는 실천 기법, DevOps는 협업·운영 문화와 실천의 결합이다. 같은 수준의 상호 배타적 '모형'으로 외우지 않는다.

## 2. 개발 모형은 어떤 문제를 해결하는가

| 모형 | 핵심 질문 | 구분점 |
| --- | --- | --- |
| Waterfall | 요구와 단계를 먼저 고정할 수 있는가? | 순차적 단계·산출물 중심 |
| Prototyping | 요구를 말보다 시제품으로 확인해야 하는가? | 사용자 Feedback을 통한 요구 명확화 |
| Spiral | 반복할 때 어떤 위험부터 줄일까? | 위험 분석 중심의 반복 |
| Incremental | 완성 기능을 나눠서 제공할 수 있는가? | 기능 증분 단위의 전달 |
| Evolutionary | Feedback에 따라 제품을 어떻게 발전시킬까? | 반복적 수정·진화 |
| RAD | 개발 기간을 어떻게 적극 단축할까? | 사용자 참여·프로토타입·자동화·재사용 |
| Cleanroom | 결함을 사전에 어떻게 예방할까? | 정형적 개발·검증, 통계적 품질 인증 |

증분형과 진화형은 함께 쓰일 수도 있다. '무엇을 나눠 전달하는가'와 'Feedback으로 어떻게 변화하는가'를 구분한다.

### 모델 간 관계: 무엇을 바꾸고 무엇을 결합하는가

아래는 **공식 계보도가 아니라 비교 관점 지도**다. 같은 모델이 여러 관점에 걸칠 수 있으며, 화살표는 역사적 파생이나 상속을 뜻하지 않는다.

```text
[개발을 조직할 때 달라지는 핵심 관점]
│
├─ 단계의 흐름
│  └─ Waterfall: 요구 → 설계 → 구현 → 시험 → 운영
│      └─ 요구가 비교적 안정적일 때 단계·산출물 관리가 쉬움
│
├─ 불확실성을 줄이는 대상
│  ├─ Prototyping: 시제품 → 사용자 확인 → 요구 보완
│  │   └─ "무엇을 만들어야 하는가?"를 확인
│  └─ Spiral: 목표·대안 → 위험 분석 → 개발·검증 → 다음 반복
│      └─ "어떤 위험을 먼저 줄여야 하는가?"에 초점
│
├─ 반복과 전달의 단위
│  ├─ Iterative: 같은 대상을 반복해 개선
│  ├─ Incremental: 기능·범위를 나눠 증분 제공
│  └─ Evolutionary: 사용 결과에 따라 제품을 진화
│      └─ 반복과 증분은 서로 결합 가능
│
├─ 개발 기간 단축
│  └─ RAD: 사용자 참여 + Prototyping + 자동화 + 재사용
│      └─ 속도를 높이기 위한 여러 수단의 조합
│
└─ 결함 예방·품질 보증
   └─ Cleanroom: 정형 명세·검증 + 통계적 품질 인증
       └─ 시험만으로 결함을 찾기보다 사전 예방 강조

[관점 간 연결 — 상속 관계 아님]
Prototyping ──활용 가능──> RAD / Spiral
Iterative   ──결합 가능──> Incremental / Evolutionary
위 개발 모형 ──함께 적용 가능──> 방법론·실천·도구
```

### 모델별 이해를 복원하는 최소 설명

- **Waterfall:** 단계별 산출물을 검토하고 다음 단계로 진행한다. 계획과 통제가 명확하지만, 뒤늦은 요구 변경에 대응하는 비용이 커질 수 있다. 실제 프로젝트에 피드백이나 재작업이 전혀 없다는 뜻은 아니다.
- **Prototyping:** 말이나 문서로 확인하기 어려운 요구를 시제품으로 구체화한다. 시제품을 폐기하고 본제품을 새로 만들 수도 있고, 진화시킬 수도 있다. 검증용 임시 구조를 그대로 제품화하면 품질 문제가 생길 수 있다.
- **Spiral:** 반복마다 목표와 대안을 검토하고 위험을 분석한 뒤 개발·검증한다. 대규모·고위험 프로젝트에 유용하지만 위험 분석 역량과 관리 비용이 필요하다.
- **Iterative / Incremental / Evolutionary:** 반복형은 같은 결과물을 재검토·개선하는 방식, 증분형은 기능 단위를 나누어 제공하는 방식, 진화형은 피드백에 따라 시스템을 발전시키는 관점이다. 하나의 프로젝트에 동시에 나타날 수 있다.
- **RAD:** 빠른 요구 합의와 시제품 피드백, CASE·4GL·재사용을 결합해 기간을 단축한다. 적극적인 사용자 참여와 모듈화 가능성에 영향을 받으며, 복잡한 통합·고위험 요구에는 제약이 생길 수 있다.
- **Cleanroom:** 정형적 명세와 정확성 검증으로 결함 유입을 줄이고, 통계적 사용 기반 시험으로 신뢰성을 평가한다. 수학적 명세·검증 역량이 요구된다.

**비교의 핵심:** Prototyping은 *요구 확인*, Spiral은 *위험 관리*, Incremental은 *전달 단위*, RAD는 *개발 속도*, Cleanroom은 *결함 예방*에 각각 무게를 둔다. 이 관점들은 상호 배타적이지 않다.

### 개발 방법론·실천의 위치

```text
개발 활동을 수행하는 접근
├─ 분석·설계 중심
│  ├─ 구조적 방법론   → 기능·프로세스 분해
│  ├─ 정보공학 방법론 → 데이터·정보 구조 중심
│  ├─ 객체지향 방법론 → 객체·책임·상호작용 중심
│  └─ CBD             → Component 조립·재사용
├─ 반복 개발 운영
│  ├─ Agile           → 변화 대응·고객 협력의 원칙
│  │  ├─ Scrum        → Sprint·역할·이벤트 중심 Framework
│  │  ├─ XP           → Pair Programming·TDD 등 개발 실천
│  │  └─ Kanban       → 작업 흐름 시각화·WIP 제한
│  └─ RUP             → Use Case·Architecture 중심 반복 프로세스
├─ 모델·제품 자산
│  ├─ MDD / MDA       → 모델을 개발의 핵심 산출물로 활용
│  └─ SPL             → 제품군 공통성·가변성 관리
└─ 품질·전달의 횡단 실천
   ├─ TDD             → 실패하는 Test → 구현 → Refactoring
   ├─ Lean            → 낭비 제거·흐름 개선
   └─ DevOps          → 개발·운영 협업·CI/CD·Feedback
```

이 역시 학습을 위한 위치 지도다. Lean은 Agile과 연관되고, Kanban은 Scrum과 결합할 수 있으며, TDD·DevOps는 여러 개발 모형에서 활용된다. 서로 배타적인 분류가 아니다.

## 3. RAD: 빠른 개발을 위한 협업·기술의 조합

```text
RAD (Rapid Application Development)
목표: 짧은 개발 기간 + 빠른 요구 검증
  │
  ├─ 사람·의사결정
  │   ├─ JRP (Joint Requirements Planning)
  │   │   → 사용자·개발자 공동 요구사항 도출·합의
  │   └─ JAD (Joint Application Development)
  │       → 사용자 참여 워크숍으로 요구 구체화·설계
  │
  ├─ 개발 지원·자동화
  │   └─ CASE (Computer-Aided Software Engineering)
  │       → 분석·설계·구현·시험을 지원하는 도구·기술 범주
  │
  ├─ 구현 생산성
  │   └─ 4GL (Fourth-Generation Language)
  │       → 고수준·선언적 표현 등을 통해 구현 부담 경감
  │
  └─ 짧은 반복
      → Prototyping · Feedback · Component 재사용
```

**개념 경계**

- RAD는 **개발 접근·모형**이다. JRP·JAD는 **공동 참여 기법**, CASE는 **개발 지원 도구·자동화 기술의 범주**, 4GL은 **프로그래밍 언어 세대·계열**이다.
- CASE 자체가 특정 제품 이름은 아니다. '그냥 도구를 쓰는 것'을 뜻하기보다, 공학적 개발 활동과 산출물을 체계적으로 지원·연계·자동화하는 접근이다.
- 4GL은 모두 선언형인 것은 아니다. SQL은 대표적인 선언형 사례다.
- JRP와 JAD는 실제 활동에서 겹칠 수 있다. JAD를 구현 방법 결정만으로 한정하지 않는다.
- CASE는 RAD에서 활용할 수 있지만 RAD 전용 기술은 아니다. 성안당 목차에서도 CASE는 별도 학습 주제다.

**기억 흐름:** 신속한 요구 합의(JRP·JAD) + 개발 지원 자동화(CASE) + 구현 생산성(4GL) + 반복 검증(Prototype) → RAD.

## 4. 개발 모형과 방법론의 경계

```text
개발 모형: 생명주기 진행·반복 구조
개발 방법론: 개발 활동을 수행하는 체계
기법·도구: 방법론이나 모형을 실현하는 수단

예) 반복·점진적 진행 + Scrum 운영 + TDD 실천 + CASE 도구
    → 서로 다른 축이 한 프로젝트에 함께 적용될 수 있음
```

성안당의 PART 2에는 SDLC·모형 선정·Review·OSS 개발 모델 비교 등이, PART 3에는 Agile·XP·RUP·Scrum·TDD·MDD/MDA·DevOps·CASE 등이 포함된다. 모두를 개별 파일로 만드는 것이 아니라, **지도에서 이해가 복원되지 않는 관계나 메커니즘만** 별도 세부학습으로 내린다.
