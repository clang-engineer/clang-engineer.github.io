# 소프트웨어 개발 모형·방법론 개념지도

> **SDLC는 개발 활동의 생명주기**, 개발 모형은 그 흐름·반복·위험 대응을 조직하는 방식, 개발 방법론은 활동을 수행하는 원칙·절차·기법의 체계다. 서로 다른 관점이므로 한 프로젝트에서 결합할 수 있다.

[소프트웨어 공학 전체 개념지도](00-전체.md)의 **개발 방식 · 전달 · 운영**을 확대한 지도다. 성안당 Vol. 5 PART 2(개발 모형)·PART 3(개발 방법론)를 학습 범위 확인에 사용하되, 교재 목차가 아닌 **해결하려는 문제와 관계**로 묶는다.

## 1. 큰 그림: 생명주기를 어떻게 운영하는가

```text
SDLC: 요구 → 설계 → 구현 → 검증 → 배포 → 운영
        ↑                              │
        └──────── 변경·Feedback ──────┘

같은 생명주기를 보는 서로 다른 질문
│
├─ 개발 모형: 단계·반복·위험을 어떻게 조직할까?
│  ├─ 순차적 흐름       → Waterfall
│  ├─ 요구의 불확실성   → Prototyping
│  ├─ 위험의 불확실성   → Spiral
│  ├─ 반복·전달 방식   → Iterative / Incremental / Evolutionary
│  ├─ 개발 기간 단축   → RAD
│  └─ 결함 예방·신뢰성 → Cleanroom
│
└─ 개발 방법론·실천: 각 활동을 무엇으로 수행할까?
   ├─ 분석·설계 체계   → 구조적 / 정보공학 / 객체지향 / CBD
   ├─ 가치·원칙       → Agile (변화 대응·고객 협력)
   ├─ 운영 Framework  → Scrum / Kanban
   ├─ 개발 실천·개선  → XP / Lean
   ├─ 반복 프로세스   → RUP
   ├─ 모델·제품군     → MDD / MDA / SPL
   └─ 품질·전달 실천  → TDD / DevOps
```

이 트리는 **공식 계보도나 상호 배타적 분류가 아니라 탐색 좌표**다. 특히 Agile은 반복·피드백을 중시하므로 개발 모형처럼 느껴지지만, 특정 단계 흐름을 규정하는 단일 모형이 아닌 **가치·원칙에 기반한 접근**이다. Scrum은 Framework, TDD는 개발 실천, DevOps는 개발·운영 협업과 자동화의 접근이다.

## 2. 개발 모형: 무엇을 우선 해결하는가

| 모형 | 해결하려는 문제 | 기억할 구분점 |
| --- | --- | --- |
| Waterfall | 요구가 안정적일 때 단계별 진행을 통제 | 순차적 단계·산출물 |
| Prototyping | 사용자가 원하는 결과를 명확히 알기 어려움 | 시제품으로 요구 확인·보완 |
| Spiral | 반복 개발 중 중요한 위험을 먼저 줄여야 함 | 위험 분석 중심 반복 |
| Iterative | 처음부터 완성도 높은 결과를 얻기 어려움 | 같은 대상을 반복 개선 |
| Incremental | 전체 기능을 한 번에 제공하기 어려움 | 기능 단위로 나누어 전달 |
| Evolutionary | 요구·사용 경험에 따라 제품이 변화 | Feedback에 따른 제품 진화 |
| RAD | 개발 기간을 적극적으로 단축해야 함 | 사용자 참여·자동화·재사용 |
| Cleanroom | 결함을 사전에 줄이고 신뢰성을 확보 | 정형적 검증·통계적 품질 인증 |

### 모형 간 연결과 경계

```text
Prototyping ──시제품으로 요구 확인──> RAD에서도 활용
           └─위험 해소 수단───────> Spiral에서도 활용

Iterative   ──반복 개선───────────┐
Incremental ──기능 단위 전달──────┼─ 결합 가능
Evolutionary──Feedback으로 진화───┘

Waterfall   → 단계·산출물의 순차 관리에 무게
Spiral      → 반복마다 위험 분석에 무게
RAD         → 개발 속도를 높이는 수단의 조합에 무게
Cleanroom   → 결함의 사전 예방과 신뢰성에 무게
```

연결선은 **활용·결합 관계**이며 역사적 파생이나 상속 관계가 아니다. Waterfall에도 피드백과 재작업이 가능하고, Spiral은 단순한 반복 모형이 아니라 위험 중심이라는 점이 중요하다. Prototyping의 시제품은 폐기형 또는 진화형으로 활용될 수 있다.

## 3. RAD: 빠른 개발을 위해 무엇을 결합하는가

```text
RAD (Rapid Application Development)
목적: 개발 기간 단축 + 빠른 요구 검증
│
├─ 협업·의사결정
│  ├─ JRP → 공동 요구사항 도출·합의
│  └─ JAD → 사용자 참여 워크숍으로 요구 구체화·설계
│
├─ 개발 지원·자동화
│  └─ CASE → 분석·설계·구현·시험 지원 도구·기술 범주
│
├─ 구현 생산성
│  └─ 4GL → 고수준 언어로 구현 부담 경감
│
└─ 빠른 검증·구현
   └─ Prototyping + Feedback + Component 재사용
```

**오늘 이해한 경계:** RAD는 개발 모형, JRP·JAD는 사용자 공동 참여 기법, CASE는 소프트웨어 공학 활동을 체계적으로 지원·자동화하는 **도구·기술의 범주**, 4GL은 **프로그래밍 언어의 세대·계열**이다. 따라서 CASE 자체는 특정 제품도, 개발 방법론도 아니다. SQL은 4GL의 대표적인 예지만 모든 4GL이 선언형인 것은 아니다.

JRP와 JAD의 활동은 실제로 겹칠 수 있고, CASE도 RAD 전용이 아니다. RAD는 적극적인 사용자 참여와 빠른 피드백이 가능할 때 유리하지만 복잡한 통합·높은 위험·엄격한 제약에서는 적용을 신중히 판단한다.

## 4. Cleanroom: 명세로 결함을 예방하고 통계적으로 신뢰성을 평가

**Cleanroom은 정형 명세와 정확성 검증으로 개발 중 결함 유입을 예방하고, 실제 사용 패턴에 기반한 통계적 테스트로 신뢰성을 평가하는 개발 모형**이다. 단순히 검수를 많이 하는 것이 아니라, **무엇이 올바른 동작인지 먼저 명세하고 그 명세를 만족함을 논리적으로 확인**하는 데 무게를 둔다.

```text
Cleanroom
│
├─ ① 개발 과정: 결함 예방
│   │
│   └─ 정형 명세를 단계적으로 구체화 (3-Box)
│       Black Box → 외부에서 관찰할 기능·동작
│            ↓ 명세 일치·정확성 검증
│       State Box → 내부 상태·상태 전이
│            ↓ 명세 일치·정확성 검증
│       Clear Box → 절차·제어 구조로 구현 명세
│            ↓ 정확성 검증
│          구현
│
└─ ② 품질 인증: 신뢰성 평가
    └─ 통계적 사용 기반 테스트
        → 실제 사용 빈도·패턴을 반영한 시험
        → 실패율 등으로 신뢰성 추정
```

**개념 경계:** 정형 명세는 올바른 동작의 기준을 명확히 표현하는 것, **3-Box는 그 명세를 외부 동작 → 내부 상태 → 구현 구조로 상세화하는 기법**, 정확성 검증은 각 상세화와 구현이 앞선 명세를 만족하는지 확인하는 활동이다. 따라서 세 가지가 서로 독립적인 순차 공정은 아니다.

예를 들어 ATM 출금이라면 Black Box에서 출금 요청의 외부 결과를, State Box에서 잔액·한도·인증 상태를, Clear Box에서 조건 검사와 상태 갱신 절차를 구체화한다. 단계마다 앞선 동작 명세를 만족하는지 검증한다.

통계적 테스트는 가능한 모든 입력을 균등하게 시험하는 것이 아니라 **실제 사용 분포(Operational Profile)**를 반영해 운영 중 신뢰성을 추정한다. 테스트를 하지 않는 모델이 아니며, 발견된 결함을 절대 수정하지 않는다는 뜻도 아니다.

**기억 흐름:** ① 명세 기반 결함 예방(3-Box + 정확성 검증) → ② 통계적 테스트 기반 신뢰성 평가.

## 5. 개발 방법론·실천: 모형과 어떻게 결합하는가

### Agile은 개발 모형인가, 방법론인가?

Agile은 **변화 대응·고객 협력·동작하는 소프트웨어·개인 간 상호작용**을 강조하는 가치와 원칙이다. 짧은 반복과 Feedback을 중시해 개발 모형과 겹쳐 보이지만, Waterfall처럼 단일한 생명주기 진행 구조를 정하는 모형은 아니다. 반대로 구조적·정보공학·객체지향·CBD처럼 시스템을 어떤 대상으로 분석·설계할지 정하는 방법론과도 분류축이 다르다.

```text
Agile: 개발의 가치·원칙 (왜, 무엇을 우선할까?)
  ├─ Scrum  → Sprint 기반 팀 운영 Framework
  ├─ XP     → TDD·Pair Programming 등 기술 실천 강조
  └─ Kanban → 작업 시각화·WIP 제한으로 흐름 개선

반복·증분 개발 모형 + Agile 원칙 + Scrum 운영 + XP/TDD 실천
→ 서로 다른 층위의 조합 (상속·단일 계보 아님)
```

Kanban과 Lean은 Agile과 자주 함께 활용되지만 Agile만의 전용 하위 개념은 아니다. **성안당에서는 Agile을 개발 방법론 PART에 배치**하지만, 이는 넓은 의미의 방법론 분류이며 구조적·정보공학과 동일한 성격이라는 뜻은 아니다.

### 네 가지 전통적 방법론의 중심 관점

```text
구조적      → 기능·처리 흐름 중심 (기능 분해, DFD)
정보공학    → 데이터·관계 중심 (ERD, 공통 데이터 모델)
객체지향    → 상태와 행위를 묶은 객체·책임 중심 (UML)
CBD         → Interface를 갖춘 Component 재사용·조립 중심
```

이 순서는 **역사적으로 강조점이 변화한 흐름을 이해하는 단서**이지, 앞선 방법론이 완전히 폐기되거나 반드시 다음 방법론으로 대체되었다는 뜻은 아니다.

기능 중심으로 업무별 처리를 설계하면 여러 기능이 공유하는 데이터의 중복·불일치·변경 영향을 통합적으로 다루기 어려울 수 있다. **정보공학은 공통 데이터 모델과 일관성을 강조하여 이를 보완**했다. 단, 구조적 방법론도 데이터를 분석하며 기능 중심 설계가 반드시 데이터 중복을 만든다는 뜻은 아니다.

객체지향은 **데이터(상태)와 행위를 객체에 묶고 책임을 배분**하는 관점을, CBD는 **명확한 Interface를 갖춘 Component의 재사용·조립**을 강조한다. 네 방법론의 차이는 반드시 먼저 수행하는 단계가 아니라, 시스템을 무엇을 중심으로 구조화하느냐에 있다.

**SDLC 모형과 구분:** Waterfall·Spiral·RAD는 개발의 진행·반복 방식, 네 방법론은 분석·설계·구현의 중심 관점이다. 예를 들어 Waterfall 모형과 객체지향 방법론은 함께 적용할 수 있다.

### RUP: 반복 개발을 체계적으로 수행·관리하는 프로세스

**RUP(Rational Unified Process)는 반복·점진적 개발을 조직적으로 수행하기 위해 단계·역할·활동·산출물을 체계화한 프로세스 Framework**다. 여기서 Rational은 원래 개발사 이름이다.

```text
RUP의 두 관점
│
├─ 시간 축: 언제 무엇에 집중하는가?
│   도입(Inception) → 정련(Elaboration)
│       → 구축(Construction) → 전이(Transition)
│
└─ 작업 축: 누가 무엇을 어떻게 수행하는가?
    역할 · 활동 · 산출물
    요구사항 / 분석·설계 / 구현 / 시험 등

각 단계 안에서도 분석·설계·구현·시험을 반복한다.
```

- **도입:** 개발 범위·사업적 타당성·핵심 요구를 파악한다.
- **정련:** 핵심 Architecture를 확립하고 주요 위험을 줄인다.
- **구축:** 반복·점진적으로 기능을 구현하고 검증한다.
- **전이:** 사용자 환경으로 배포하고 인수·전환한다.

**3대 특징:** 반복·점진적 개발, **Use Case 중심**, **Architecture 중심**. 네 단계가 있다고 Waterfall처럼 각 개발 활동을 한 번만 수행하는 것은 아니다.

**RAD와의 경계:** 둘 다 반복과 Feedback을 활용하지만 **RAD는 신속한 개발**, **RUP는 반복 개발을 수행할 절차·역할·산출물과 위험을 체계적으로 관리하는 데** 무게를 둔다. RUP는 프로젝트 관리만 하는 기법이 아니라 실제 개발 활동까지 정의하므로 개발 모형과 방법론의 성격이 겹친다.

### SPL: 공통성과 가변성을 설계해 제품군을 재사용한다

**SPL(Software Product Line)은 관련된 여러 제품을 개별 개발하는 대신, 제품군의 공통 부분과 달라지는 부분(가변성)을 체계적으로 관리하여 재사용하는 접근**이다.

```text
병원 애플리케이션 제품군
│
├─ 공통 자산 (Core Assets)
│  ├─ 인증·권한
│  ├─ 환자 관리
│  └─ 공통 Architecture·Test
│
└─ 가변성 (Variability)
   ├─ 예약 기능: 선택
   ├─ 수납 기능: 선택
   └─ ERAS 기능: 선택
           ↓
공통 자산 + 제품별 선택·설정
           ↓
병원 A / 병원 B / 병원 C 제품
```

| 구분 | CBD (Component-Based Development) | SPL |
| --- | --- | --- |
| 중심 질문 | 어떤 Component를 재사용·조립할까? | 제품군의 공통점과 차이점을 어떻게 관리할까? |
| 주된 단위 | Component와 Interface | 여러 제품에 걸친 공통 자산·가변성 |
| 재사용 범위 | Component 조립 | Architecture·Component·모델·Test 등 제품군 자산 |

**관계:** SPL도 Component 조립을 활용할 수 있지만, 단순 조립이 전부는 아니다. **CBD는 부품 재사용·조립에, SPL은 여러 제품의 공통성과 가변성에 초점**을 둔다. 서로 배타적이지 않다.

### 정보공학·DDD·MDD·MDA: 모두 모델을 쓰는데 무엇이 다른가?

**모델(Model)은 현실이나 시스템을 목적에 맞게 단순화한 표현**이다. 차이는 모델의 존재 여부가 아니라 **무엇을 표현하고, 그 모델을 개발에 어떻게 활용하는가**다.

| 접근 | 모델의 중심 | 모델을 쓰는 목적 |
| --- | --- | --- |
| 정보공학 | 업무 데이터·관계 (ERD 등) | 데이터 통합·일관성 있는 구조 설계 |
| DDD (Domain-Driven Design) | 도메인 개념·규칙·책임 | 업무 규칙을 소프트웨어 구조에 반영 |
| MDD (Model-Driven Development) | 다양한 시스템 모델 | 모델을 개발의 핵심 산출물로 사용하고 변환·코드 생성에 연결 |
| MDA (Model-Driven Architecture) | 플랫폼 독립·종속 모델 | 기술 독립 설계를 특정 플랫폼용 모델·구현으로 변환 |

**JHipster Entity Generator**는 MDD를 떠올리기 좋은 실무 사례다. JDL로 Entity와 관계를 선언하면 Entity·Repository·API·DB Migration 등의 구현 산출물을 생성할 수 있다. 다만 코드 생성 도구 하나를 사용했다고 프로젝트 전체가 MDD 방법론을 따른다고 단정할 수는 없다.

```text
JDL 모델 (Patient, 필드, 관계)
            ↓ JHipster Generator
     Entity / Repository / API
     DB Migration / Frontend 등
```

**MDD와 MDA의 관계:** **MDA는 MDD의 한 접근법으로, 플랫폼 독립성과 모델 변환을 특히 강조한다.** MDD는 모델을 개발의 중심에 놓는 넓은 접근이고, MDA는 OMG가 제안한 구체적인 접근이다. MDA에서 사용하는 대표적인 모델 구분이 CIM(업무 관점) → PIM(플랫폼 독립 설계) → PSM(플랫폼 종속 설계)이다. 이는 반드시 모든 프로젝트에서 고정 순서로 수행해야 하는 절차가 아니라, 추상화 수준과 변환 관계를 설명하는 대표 흐름이다.

#### MDA의 세 가지 모델 수준

```text
CIM — Computation Independent Model
      업무 관점: "환자를 등록하고 조회해야 한다"
             ↓ 업무 요구를 시스템 구조로 구체화
PIM — Platform Independent Model
      기술 독립 설계: Patient(name, age)
      (Spring·JPA·DBMS 등 특정 플랫폼을 전제하지 않음)
             ↓ 플랫폼별 변환 규칙 적용
PSM — Platform Specific Model
      기술 종속 설계: JPA Entity, @Id, @Column,
      PostgreSQL 매핑 등
             ↓ 코드 생성·구현
      실제 애플리케이션
```

- **CIM:** 시스템이 지원할 업무와 요구를 기술 구현과 분리해 표현한다.
- **PIM:** 시스템의 구조·행위를 모델링하되 특정 플랫폼의 세부 기술은 배제한다.
- **PSM:** 선택한 플랫폼의 기술 요소와 매핑을 반영한 모델이다.
- **변환:** PIM 하나를 여러 플랫폼용 PSM으로 구체화할 수 있지만, 자동 변환이 항상 완전하거나 모든 코드가 자동 생성되는 것은 아니다.

JHipster 예시는 **MDD적 코드 생성의 직관적 사례**이지, JHipster가 CIM → PIM → PSM을 엄격히 구현한다는 뜻은 아니다. 또한 DDD는 MDA의 단계가 아니며, 정보공학·DDD의 모델을 MDD 기법과 결합할 수도 있다.

**기억할 질문:** 정보공학은 *어떤 데이터를 구조화할까*, DDD는 *업무 규칙을 어떻게 표현할까*, MDD는 *모델을 구현에 어떻게 연결할까*, MDA는 *기술 독립 모델을 플랫폼별로 어떻게 변환할까*에 각각 무게를 둔다.

| 관점 | 대표 개념 | 핵심 역할 |
| --- | --- | --- |
| 분석·설계 대상 | 구조적 / 정보공학 / 객체지향 | 기능·데이터·객체 중심으로 문제를 구조화 |
| 재사용 단위 | CBD / SPL | Component 조립·재사용 / 제품군 공통성·가변성 |
| 가치·개선 원칙 | Agile / Lean | 변화 대응·고객 협력 / 낭비 제거·흐름 개선 |
| 팀 운영 | Scrum / Kanban | Sprint 기반 운영 / 작업 흐름·WIP 관리 |
| 개발 실천 | XP / TDD | 기술적 개발 실천 / Test 우선 개발 |
| 반복 프로세스 | RUP | Use Case·Architecture 중심 반복·점진 개발 |
| 모델 중심 | MDD / MDA | 모델 기반 개발 / 모델 변환·플랫폼 독립성 |
| 개발·운영 연결 | DevOps | 협업·CI/CD·운영 Feedback |

예를 들어 **반복·증분 개발 모형 + Scrum 팀 운영 + TDD 개발 실천 + CI/CD 자동화**는 동시에 적용 가능하다. Agile·Scrum·XP·Kanban·Lean도 서로 단일한 계보나 배타적인 선택지가 아니다.
