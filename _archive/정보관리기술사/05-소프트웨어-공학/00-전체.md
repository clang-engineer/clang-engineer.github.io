# 소프트웨어 공학 개념지도

> 소프트웨어 공학은 **불확실한 요구를 운영 가능한 소프트웨어로 바꾸고, 변경·품질·일정·비용의 위험을 생명주기 전체에서 통제하는 방법**을 다룬다.

## 1. 소프트웨어 공학 전체 좌표

```text
[제품 Lifecycle: 산출물과 처리의 흐름]
문제·사용자 요구
      ↓
요구공학
      ↓
Architecture·설계
      ↓
구현·통합
      ↓
검증·Test
      ↓
Release·Deployment
      ↓
운영·유지보수
      ↓ 운영 결과·변경 요구
Feedback → 요구·설계 재검토로 복귀

[위 Lifecycle 전 과정에 겹치는 관점]
├─ 개발 방식 · Feedback · 자동화 · DevOps
├─ 형상 · 변경관리
├─ 품질 · V&V · Test
├─ 범위 · 일정 · 비용 · 위험 · Project 관리
└─ 외부 제약 · 표준
```

첫 묶음은 **제품을 만들고 운영하는 Lifecycle**, 두 번째 묶음은 특정 한 단계에만 속하지 않고 **같은 Lifecycle 전체에 반복해서 적용되는 관점**이다. 가로로 긴 연결선을 겹치는 대신, 중심 흐름과 횡단 관점을 구분해 좁은 화면에서도 각각 읽을 수 있게 한다. 화살표는 기본 흐름을 나타내며 특정 개발 방법론의 일회성·고정 순서를 뜻하지 않는다.

```text
Lifecycle
= 무엇을 어떤 순서와 Feedback으로 만들어 운영하는가

개발 방식
= Lifecycle을 어떤 반복·협업·전달 방식으로 운영하는가

품질
= 각 단계의 산출물과 최종 제품을 어떻게 확인하는가

형상·변경
= 계속 바뀌는 산출물의 기준과 변경을 어떻게 통제하는가

Project 관리
= 전체 작업을 범위·일정·비용·위험 안에서 어떻게 통제하는가
```

핵심은 개발 생명주기가 한 번의 직선 흐름으로 끝나는 것이 아니라, **Feedback과 변경 통제가 전 과정을 계속 연결한다는 것**이다.

## 2. 어디를 파고들 것인가

### 요구 · Architecture · 설계

무엇을 만들지 명확히 하고, 변경에 견딜 구조로 구체화하는 축이다.

```text
사용자 · 이해관계자 필요
  ↓
요구공학
├─ Elicitation / Analysis
├─ Specification
├─ Validation
└─ Traceability
  ↓
Architecture
├─ 구조 · Component · Interface
└─ 품질속성 / Trade-off
  ↓
상세 설계
  ↓
구현
```

요구 ↔ 설계 ↔ 구현 ↔ 시험의 추적성은 전체 생명주기를 연결하는 대표 좌표다.

### 설계 구체화 — Modeling · 객체지향 · Architecture

앞선 요구·설계 흐름에서 **설계 단계만 확대**한 축이다. 별도의 생명주기 단계가 아니라 구조를 표현하고 설계 결정을 구체화하는 방법을 다룬다.

```text
요구 · 문제 구조
      ↓
Modeling / UML
      ↓
Object-Oriented Design
├─ Abstraction / Encapsulation
├─ Inheritance / Polymorphism
└─ 설계 원칙
      ↓
반복되는 설계 문제
      ↓
Design Pattern
      ↓
System 수준 구조
      ↓
Architecture Style
├─ Layered
├─ MVC
├─ Repository
└─ Pipe & Filter
```

→ [UML 다이어그램과 클래스 관계](UML-다이어그램과-클래스-관계.md) — 구조·행위 14종과 Class 관계선의 의미

UML은 개발 방법론 자체가 아니라 구조와 행위를 표현하는 Modeling 언어이고, Design Pattern은 반복되는 설계 문제의 재사용 가능한 해법, Architecture Style은 시스템 전체 구조 수준의 선택으로 구분한다.

**4+1 View Model과 UML의 경계:** 4+1 View Model(Philippe Kruchten)은 아키텍처를 **Logical·Process·Development·Physical의 네 관점과 이를 연결·검증하는 Use Case/Scenario(+1)**로 설명하는 관점 모델이다. UML은 그 관점들을 Class·Sequence·Component·Deployment·Use Case Diagram 등으로 **표현하는 모델링 언어**다. 따라서 'UML의 4+1 View'라는 표현은 UML 고유의 표준 모델로 오해될 수 있으며, **'UML을 활용한 4+1 아키텍처 View Model'**이 더 정확하다. UML 외의 표기법도 사용할 수 있다.

```text
4+1 View Model → 아키텍처의 무엇을 보여줄까? (관점)
UML          → 각 관점을 어떻게 표현할까? (표기 언어)
```

### 개발 방식 · 전달 · 운영

개발을 어떤 Feedback 주기와 전달 방식으로 운영할지 본다.

```text
개발 방식
├─ Waterfall
├─ Iterative / Incremental
└─ Agile
      ↓
짧은 Feedback · 지속적 통합
      ↓
CI / CD · 자동화
      ↓
Release / Deployment
      ↓
운영 · Monitoring
      ↓
Feedback → 다음 변경
```

개발 모형(Waterfall·Prototyping·Spiral·Incremental·Evolutionary·RAD·Cleanroom)과 개발 방법론(Agile·RUP·Scrum·XP 등)은 구분하되, 서로 다른 관점이 함께 적용될 수 있다. RAD의 JRP·JAD·CASE·4GL처럼 방법론을 뒷받침하는 기법·도구·언어도 연결해 본다.

→ [소프트웨어 개발 모형·방법론 개념지도](01-개발-모형과-방법론.md)

### 검증 · 시험 · 품질

제대로 만들었는지, 실제 목적에 맞는지, 어떤 품질 수준인지 확인하는 축이다.

```text
품질 요구
  ↓
V&V
├─ Verification → 제대로 만들고 있는가
└─ Validation   → 필요한 것을 만들고 있는가
  ↓
Review / Test
├─ 시험 수준
├─ 시험 기법
└─ Coverage
  ↓
결함 · 품질 지표
  ↓
개선 Feedback
```

Verification·Validation·시험 수준·시험 기법·품질 특성의 세부 경계는 필요한 세부학습에서 본다.

→ [소프트웨어 Test 전체 분류](소프트웨어-테스트의-전체-분류.md)

### 변경 · 형상 · Project 관리

소프트웨어와 산출물의 변경을 통제하고, 범위·일정·비용·위험을 관리하는 횡단 축이다.

```text
변경 발생
  ↓
형상·변경관리
├─ Configuration Item
├─ Version / Baseline
└─ 변경 식별 · 통제 · 상태관리 · 감사

[Project 관리]
범위 · 일정 · 비용 · 품질 · 위험 · 이해관계자
        ↓
계획 → 측정 → 통제
```

규모·공수 추정과 Project 관리 기법, 외부 표준·OSS License·IP 같은 제약도 이 축과 연결된다.

→ [Software License · 배포 의무 · Copyleft 경계](소프트웨어-라이선스-배포의무와-Copyleft-경계.md)

## 3. 기억할 큰 경계

```text
제품을 만드는 흐름
요구 → 설계 → 구현 → 검증 → 배포 → 운영

흐름을 개선하는 방식
개발 방법 / Feedback / 자동화 / DevOps

결과를 확인하는 축
Review / V&V / Test / 품질

전체를 통제하는 축
형상·변경 / 규모·공수 / Project 관리 / 외부 제약
```

SDLC와 생명주기 모델, Architecture와 UML, Verification과 Validation, Release와 Deployment처럼 **같은 가지 내부에서 구분해야 하는 개념은 세부학습에서 더 펼친다.**

## 4. 생명주기와 횡단 관점

```text
요구 → 설계 → 구현 → 검증 → 배포 → 운영
 ↑                                │
 └──────── Feedback ──────────────┘

[전 과정] 개발 방식 / 품질·Test / 형상·변경 / Project 관리
```
