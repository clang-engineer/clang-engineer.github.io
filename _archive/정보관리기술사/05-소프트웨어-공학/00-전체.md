# 소프트웨어 공학 개념지도

> 소프트웨어 공학은 **불확실한 요구를 운영 가능한 소프트웨어로 바꾸고, 변경·품질·일정·비용의 위험을 생명주기 전체에서 통제하는 방법**을 다룬다.

이 문서는 소프트웨어 공학의 큰 흐름과 학습 가지를 잡는 전체 지도다. 현재는 별도의 하위 개념지도를 두지 않고, 여기서 위치와 관계를 잡은 뒤 필요한 세부학습으로 바로 내려간다.

## 1. 소프트웨어 공학 전체 좌표

```text
                         [개발 방식 · Feedback · 자동화 · DevOps]
                                      ↓
문제·사용자 요구
      ↓
   요구공학 → Architecture·설계 → 구현·통합 → 검증·Test → Release·Deployment → 운영·유지보수
      ↑                                                                          │
      └────────────────────────────── Feedback ───────────────────────────────────┘
      │                  │                 │              │                │
      ├──────────────────┴──── 형상 · 변경관리 ───────────┴────────────────┤
      │                                                                   │
      ├────────────────────── 품질 · V&V · Test ──────────────────────────┤
      │                                                                   │
      └──────────── 범위 · 일정 · 비용 · 위험 · Project 관리 ─────────────┘

                         [전 과정의 외부 제약 · 표준]
```

가운데 가로축은 **제품을 만드는 Lifecycle**, 위·아래의 긴 축은 특정 한 단계에만 속하지 않고 Lifecycle 전체에 반복해서 적용되는 관점이다.

```text
Lifecycle
= 무엇을 어떤 순서와 Feedback으로 만들어 운영하는가

개발 방식
= Lifecycle을 어떤 반복·협업·전달 방식으로 운영하는가

품질
= 각 단계의 산출물과 최종 제품을 어떻게 확인하는가

형상·변경
= 계속 바뀌는 산출물의 기준과 변경을 어떻게 통제하는가

Project 관리
= 전체 작업을 범위·일정·비용·위험 안에서 어떻게 통제하는가
```

핵심은 개발 생명주기가 한 번의 직선 흐름으로 끝나는 것이 아니라, **Feedback과 변경 통제가 전 과정을 계속 연결한다는 것**이다.

## 2. 어디를 파고들 것인가

### 요구 · Architecture · 설계

무엇을 만들지 명확히 하고, 변경에 견딜 구조로 구체화하는 축이다.

```text
사용자 · 이해관계자 필요
  ↓
요구공학
  ↓ Traceability
Architecture
  ↓
상세 설계
  ↓
구현
```

요구 ↔ 설계 ↔ 구현 ↔ 시험의 추적성은 전체 생명주기를 연결하는 대표 좌표다.

### 개발 방식 · 전달 · 운영

개발을 어떤 Feedback 주기와 전달 방식으로 운영할지 본다.

```text
개발 방식
  ↓
반복 · 통합 · 자동화
  ↓
Release / Deployment
  ↓
운영 Feedback
```

Waterfall·Iterative·Agile·DevOps 같은 내부 비교는 필요한 세부학습에서 펼친다.

### 검증 · 시험 · 품질

제대로 만들었는지, 실제 목적에 맞는지, 어떤 품질 수준인지 확인하는 축이다.

```text
품질 요구
  ↓
Review / V&V / Test
  ↓
결함 · Coverage · 품질 지표
  ↓
개선 Feedback
```

Verification·Validation·시험 수준·시험 기법·품질 특성의 세부 경계는 필요한 세부학습에서 본다.

→ [[소프트웨어-테스트의-전체-분류|소프트웨어 Test 전체 분류]]

### 변경 · 형상 · Project 관리

소프트웨어와 산출물의 변경을 통제하고, 범위·일정·비용·위험을 관리하는 횡단 축이다.

```text
변경 발생
  ↓
형상·변경관리
  ↓
Version / Baseline / 변경 통제

[동시에]
범위 · 일정 · 비용 · 위험 · 이해관계자 관리
```

규모·공수 추정과 Project 관리 기법, 외부 표준·OSS License·IP 같은 제약도 이 축과 연결된다.

→ [[소프트웨어-라이선스-배포의무와-Copyleft-경계|Software License · 배포 의무 · Copyleft 경계]]

## 3. 기억할 큰 경계

```text
제품을 만드는 흐름
요구 → 설계 → 구현 → 검증 → 배포 → 운영

흐름을 개선하는 방식
개발 방법 / Feedback / 자동화 / DevOps

결과를 확인하는 축
Review / V&V / Test / 품질

전체를 통제하는 축
형상·변경 / 규모·공수 / Project 관리 / 외부 제약
```

SDLC와 생명주기 모델, Architecture와 UML, Verification과 Validation, Release와 Deployment처럼 **같은 가지 내부에서 구분해야 하는 개념은 세부학습에서 더 펼친다.**

## 4. 권장 탐색 흐름

소프트웨어 공학은 모든 가지를 하나의 직렬 순서로 읽기보다, 먼저 **제품을 만드는 생명주기 중심축**을 잡고 그 위에 개발 방식·품질·변경 통제 관점을 겹쳐 보는 편이 자연스럽다.

```text
[먼저 중심축]
요구
 ↓
Architecture · 설계
 ↓
구현 · 통합
 ↓
검증 · Test
 ↓
Release · Deployment
 ↓
운영 · 유지보수
 ↓
Feedback
```

그다음 같은 Lifecycle을 서로 다른 질문으로 다시 본다.

```text
어떻게 만들고 전달하며 운영 Feedback을 받을까?
→ 개발 방식 · 전달 · 운영

제대로 만들었고 목적에 맞는지 어떻게 확인할까?
→ 검증 · Test · 품질

계속 생기는 변경과 일정·비용·위험을 어떻게 통제할까?
→ 형상 · 변경 · Project 관리
```

세 관점은 기술의 발전 단계나 반드시 지켜야 하는 학습 순서가 아니다. **하나의 Software Lifecycle을 서로 다른 관점에서 다시 보는 구조**다.

```text
학습등급표
"무엇을 얼마나 볼 것인가"
        ↓
소프트웨어 공학 전체 개념지도
"Lifecycle 전체에서 지금 어떤 문제를 보는가"
        ↓
세부학습
"구체적인 방법·기법은 무엇인가"
```
전체 지도에서는 큰 흐름과 대표적인 횡단 관점까지만 남긴다. 개별 방법론·시험 기법·품질 모델·추정식·Project 관리 기법은 세부학습으로 내린다.
