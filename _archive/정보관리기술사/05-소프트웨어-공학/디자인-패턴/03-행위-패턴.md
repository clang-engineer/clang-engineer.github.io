## 행위 패턴 — 책임과 상호작용

### 3.1 Strategy — 알고리즘을 교체 가능하게 만든다

**Intent**: 동일 목적의 Algorithm·Policy를 공통 Interface 뒤로 분리해 Runtime에 교체한다.

적용 신호는 같은 목적의 `if / else if` 알고리즘 분기가 반복되는 경우다.

**일상 예시 — 내비게이션:** 목적지는 같지만 도보·자동차·자전거 경로 계산 방법을 바꿔 끼운다.

**왜 쓰나?** 새로운 이동 수단이 추가되어도 Navigator의 경로 계산 분기를 늘리지 않는다.

**객체 관계와 호출 흐름**

```text
Navigator ──참조──> RouteStrategy «interface»
                              △ 구현
                        ┌─────┴─────┐
                     WalkRoute    CarRoute

Navigator.guide()
  → strategy.route() → "도보 경로" 또는 "자동차 경로"
```

**핵심:** Navigator는 계산 방법의 구체 타입을 몰라도 Strategy를 교체할 수 있다.

**핵심 코드 (C++17):** 경로 계산을 Strategy 객체에 위임해 교체한다.

```cpp
#include <string>
struct RouteStrategy {
    virtual ~RouteStrategy() = default;
    virtual std::string route() const = 0;
};
struct WalkRoute : RouteStrategy {
    std::string route() const override { return "도보 경로"; }
};
struct CarRoute : RouteStrategy {
    std::string route() const override { return "자동차 경로"; }
};
struct Navigator {
    const RouteStrategy& strategy; // 소유하지 않는 참조
    explicit Navigator(const RouteStrategy& s) : strategy(s) {}
    std::string guide() const { return strategy.route(); }
};
// WalkRoute walk; Navigator nav{walk}; nav.guide() → "도보 경로"
```

### 3.2 State — 상태에 따른 행동과 전이를 객체로 분리한다

**Intent**: 객체의 Lifecycle State에 따라 달라지는 행동을 State 객체로 분리한다.

Strategy와 구조는 유사하지만 질문이 다르다.

**일상 예시 — 자판기:** 대기·동전 투입·상품 배출 상태에 따라 같은 버튼을 눌러도 행동이 달라진다.

**Strategy와 차이:** 정책 선택보다 **상태에 따른 행동·전이**가 핵심이다.

**상태 객체 관계와 전이**

```text
[클래스 관계]
VendingMachine ──소유──> State (추상)
                             △ 상속
                        ┌────┴────┐
                       Idle      Paid

[호출·상태 전이]
Idle.press() → "동전을 넣으세요"
insertCoin() → Paid
Paid.press() → "상품 배출" → Idle
```

**핵심:** 현재 State가 행동을 결정하고, Context가 그 결과에 따라 상태 객체를 교체한다.

**핵심 코드 (C++17):** State가 동작 결과를 반환하고 Context가 그 결과에 따라 상태를 전환한다. 현재 State의 메서드가 실행 중일 때 자기 객체를 파괴하지 않도록 전이 시점을 분리한 간략 예시다.

```cpp
#include <memory>
#include <string>
struct VendingMachine;
struct State {
    virtual ~State() = default;
    virtual std::string press(VendingMachine& m) = 0;
};
struct Idle : State {
    std::string press(VendingMachine&) override { return "동전을 넣으세요"; }
};
struct Paid : State {
    std::string press(VendingMachine& m) override;
};
struct VendingMachine {
    std::unique_ptr<State> state = std::make_unique<Idle>();
    void insertCoin() { state = std::make_unique<Paid>(); }
    std::string press() {
        auto result = state->press(*this);
        if (result == "상품 배출") state = std::make_unique<Idle>();
        return result;
    }
};
inline std::string Paid::press(VendingMachine&) {
    return "상품 배출"; // 호출이 끝난 뒤 Context가 Idle로 전이
}
// VendingMachine m; m.insertCoin(); m.press() → "상품 배출"
```

### 3.3 Template Method — 알고리즘 골격을 고정하고 일부 단계를 확장한다

**Intent**: 상위 Class가 전체 Algorithm의 Skeleton을 정의하고 일부 단계만 하위 Class가 구현한다.

Strategy가 **Composition으로 전체 알고리즘을 교체**한다면 Template Method는 **Inheritance로 알고리즘의 일부 단계만 바꾼다.**

**일상 예시 — 라면 조리법:** 물 끓이기 → 재료 넣기 → 완성 순서는 고정하고, 종류에 따라 재료 넣기 단계만 바꾼다.

**상속 관계와 실행 순서**

```text
        Ramen (추상 클래스)
        + cook() [고정]
        # addIngredients() [변경 지점]
                 △ 상속
                 │
             CheeseRamen
             + addIngredients()

cook(): boilWater() → addIngredients() → serve()
              공통          하위 구현        공통
```

**핵심:** 알고리즘의 전체 순서는 상위 클래스에, 바뀌는 단계는 하위 클래스에 둔다.

**핵심 코드 (C++17):** 상위 클래스가 조리 순서를 고정하고 하위 클래스가 일부 단계를 구현한다.

```cpp
#include <iostream>
struct Ramen {
    virtual ~Ramen() = default;
    void cook() { boilWater(); addIngredients(); serve(); }
protected:
    void boilWater() { std::cout << "물 끓이기\n"; }
    virtual void addIngredients() = 0;
    void serve() { std::cout << "완성\n"; }
};
struct CheeseRamen : Ramen {
    void addIngredients() override { std::cout << "면과 치즈\n"; }
};
// CheeseRamen{}.cook();
```

`cook()`이 Template Method이며 **상속으로 일부 단계만 교체**한다.

### 3.4 Observer — 상태 변화를 다수 구독자에게 알린다

**Intent**: Subject와 Observer를 느슨하게 결합해 상태 변화 시 여러 Observer에 Notification한다.

주의점은 Event 흐름이 많아지면 호출 경로와 실패 전파가 보이지 않게 될 수 있다는 것이다.

**일상 예시 — 유튜브 구독:** 채널이 영상을 올리면 구독자들이 알림을 받는다.

**왜 쓰나?** 채널이 구독자별 알림 구현을 직접 알 필요가 없다.

**구독 관계와 통지 흐름**

```text
Channel ──구독자 목록──> Subscriber «interface»
                                △ 구현
                                │
                              Viewer

Channel.upload("새 영상")
    └─ for each Subscriber → update("새 영상")
```

**핵심:** Channel은 구독자의 구체 타입을 몰라도 모두에게 통지한다. 구독자 수명은 별도 관리한다.

**핵심 코드 (C++17):** 채널은 Subscriber Interface만 알고 모든 구독자에게 통지한다.

```cpp
#include <string>
#include <vector>
#include <iostream>
struct Subscriber {
    virtual ~Subscriber() = default;
    virtual void update(const std::string& title) = 0;
};
struct Viewer : Subscriber {
    void update(const std::string& title) override {
        std::cout << "새 영상: " << title << '\n';
    }
};
struct Channel {
    std::vector<Subscriber*> subscribers; // 비소유 포인터; 구독자 수명 보장 필요
    void subscribe(Subscriber& s) { subscribers.push_back(&s); }
    void upload(const std::string& title) {
        for (auto* s : subscribers) s->update(title);
    }
};
// Viewer v; Channel c; c.subscribe(v); c.upload("여행 브이로그");
// 실제 구현에서는 unsubscribe 및 구독자 파괴 시 안전성 처리 필요
```

### 3.5 Mediator — 다대다 통신을 중앙 조정한다

**이름의 의미:** Mediator는 '중재자'. 여러 객체의 직접 상호작용을 **중앙에서 조정**한다.

**Intent**: 여러 객체가 서로 직접 참조하는 Mesh 관계를 Mediator로 모아 결합도를 줄인다.

Observer가 **일대다 Notification**에 가깝다면 Mediator는 **다대다 상호작용 조정**이 핵심이다.

**일상 예시 — 관제탑:** 비행기들이 서로 직접 조율하지 않고 관제탑을 통해 이착륙을 조정한다.

**객체 간 협력 조정**

```text
[객체 관계]
Checkbox ──참조──> Form (Mediator)
                       │ 참조
                       ▼
                  SubmitButton

[호출 흐름]
Checkbox.click(true)
  → Form.agreementChanged(true)
  → SubmitButton.enabled = true

Checkbox와 SubmitButton은 서로 직접 참조하지 않는다.
```

**핵심:** Checkbox가 SubmitButton을 직접 조작하지 않고 Form이 상호작용을 조정한다.

**핵심 코드 (C++17):** Checkbox가 직접 SubmitButton을 조작하지 않고 Form에 상태 변경을 알린다.

```cpp
#include <string>
struct SubmitButton {
    bool enabled = false;
};
struct Form {
    SubmitButton& submit;
    explicit Form(SubmitButton& b) : submit(b) {}
    void agreementChanged(bool checked) { submit.enabled = checked; }
};
struct Checkbox {
    Form& mediator;
    explicit Checkbox(Form& f) : mediator(f) {}
    void click(bool checked) { mediator.agreementChanged(checked); }
};
// SubmitButton button; Form form{button}; Checkbox check{form};
// check.click(true); // button.enabled == true
```

Checkbox는 SubmitButton을 직접 참조하지 않는다. 실제 Mediator는 **여러 UI 객체 간 상호작용을 중앙 조정 객체로 모으는 것**이 핵심이다.

### 3.6 Command — 요청 자체를 객체로 만든다

**Intent**: 요청을 객체로 캡슐화해 호출자(Invoker)와 실제 처리자(Receiver)를 분리한다.

그 결과 요청을 다음처럼 다룰 수 있다.

- Queue
- Log
- Retry
- Delay
- Undo

**일상 예시 — 리모컨 버튼:** 버튼은 '불 켜기' 명령 객체를 실행하고, 실제 전등은 명령 객체가 제어한다. 명령을 큐에 넣거나 취소 이력을 관리할 수 있다.

**객체 관계와 명령 실행**

```text
RemoteButton (Invoker) ──참조──> Command «interface»
                                    △ 구현
                                    │
                                LightOn
                                    │ 참조
                                    ▼
                                  Light

press() → execute() → Light.turnOn()
```

**핵심:** 버튼은 명령의 내용이 아니라 실행 인터페이스만 안다.

**핵심 코드 (C++17):** 버튼이 전등을 직접 몰라도 Command를 실행한다.

```cpp
#include <memory>
struct Light { bool on = false; void turnOn() { on = true; } };
struct Command {
    virtual ~Command() = default;
    virtual void execute() = 0;
};
struct LightOn : Command {
    Light& light;
    explicit LightOn(Light& l) : light(l) {}
    void execute() override { light.turnOn(); }
};
struct RemoteButton {
    Command& command;
    explicit RemoteButton(Command& c) : command(c) {}
    void press() { command.execute(); }
};
// Light light; LightOn cmd{light};
// RemoteButton button{cmd}; button.press(); // light.on == true
```

Invoker는 Command만 알고 Receiver인 Light의 구체 동작은 모른다.

### 3.7 Memento — 이전 상태를 Snapshot으로 보존한다

**이름의 의미:** Memento는 '기념물·기억을 떠올리게 하는 것'. 이전 상태를 **보존하고 복원하는 단서**라는 뜻으로 이해한다.

**Intent**: Encapsulation을 깨지 않고 객체 내부 상태를 Snapshot으로 저장·복원한다.

Command와 함께 Undo에 쓰이지만 역할은 다르다.

**일상 예시 — 그림판 되돌리기:** 그림을 수정하기 전 상태를 Snapshot으로 보관하고, Undo 시 복원한다.

**상태 저장·복원 흐름**

```text
[클래스·객체 관계]
Editor (Originator) ──생성──> Snapshot (Memento)
   │                              │
   └──────── restore() <──────────┘
              상태 전달

[상태 흐름]
Editor("초안") → save() → Snapshot("초안")
Editor("수정") → restore(snapshot) → Editor("초안")
```

**핵심:** Command가 '무엇을 실행했는가'를 기록한다면 Memento는 '어떤 상태였는가'를 보존한다.

**핵심 코드 (C++17):** 상태를 Snapshot으로 저장했다가 복원한다.

```cpp
#include <string>
struct Editor {
    struct Snapshot { std::string text; };
    std::string text;
    Snapshot save() const { return {text}; }
    void restore(const Snapshot& old) { text = old.text; }
};
// Editor editor; editor.text = "초안";
// auto before = editor.save();
// editor.text = "수정"; editor.restore(before);
// editor.text == "초안"
```

이 예시는 값 복사로 Snapshot을 만든다. 실제 패턴에서는 **내부 상태의 캡슐화와 복원 권한**도 고려한다.

### 3.8 Chain of Responsibility — 처리자를 사슬로 연결한다

**이름의 의미:** Chain of Responsibility는 '책임의 사슬'. 요청을 처리할 수 있는 객체를 만날 때까지 **처리 책임을 연쇄적으로 전달**한다.

**Intent**: 요청의 최종 처리자를 호출자가 직접 정하지 않고 Handler Chain을 따라 전달한다.

Middleware, Filter, 인증·검증 Pipeline처럼 처리 단계가 조합되는 구조에서 자주 나타난다.

**일상 예시 — 고객센터:** 상담 요청을 1차 상담원 → 담당 팀 → 관리자 순으로 전달하고 처리 가능한 곳에서 멈춘다.

**책임 연쇄와 처리 흐름**

```text
[클래스 관계]
Handler (Base)
   △ 상속
   ├─ Staff   ──next──> Handler
   └─ Manager ──next──> Handler

[실제 연결·호출]
Client → Staff
           ├─ level <= 1 → 상담원 처리
           └─ level > 1  → Manager → 관리자 처리
```

**핵심:** 요청을 누가 처리할지 Client가 직접 선택하지 않고 Handler가 다음 Handler에 위임한다.

**핵심 코드 (C++17):** 처리할 수 없으면 다음 Handler로 넘긴다.

```cpp
#include <string>
struct Handler {
    Handler* next = nullptr; // 비소유 참조
    virtual ~Handler() = default;
    virtual std::string handle(int level) {
        return next ? next->handle(level) : "처리 불가";
    }
};
struct Staff : Handler {
    std::string handle(int level) override {
        return level <= 1 ? "상담원 처리" : Handler::handle(level);
    }
};
struct Manager : Handler {
    std::string handle(int level) override {
        return "관리자 처리";
    }
};
// Staff staff; Manager manager; staff.next = &manager;
// staff.handle(2) → "관리자 처리"
```

요청은 **Chain을 따라 전달**되고, 처리 가능한 Handler에서 종료된다.

### 3.9 Iterator — 순회 방법을 Collection에서 분리한다

**Intent**: Collection 내부 표현을 노출하지 않고 원소를 순차적으로 접근하는 방법을 제공한다.

Iterator Pattern과 Lazy Evaluation은 같은 개념이 아니다. Iterator는 **순회 Interface**, Lazy는 **계산 시점**의 문제다.

**일상 예시 — 음악 재생목록:** 재생목록 내부 저장 방식과 무관하게 '다음 곡'을 순서대로 가져온다.

**반복자와 순회 흐름**

```text
[클래스·객체 관계]
Client ──사용──> std::vector<int>
  │                   │
  │                   └─ begin()/end() → Iterator
  └──────────────사용───────────────┘
                                    │
                                    ▼
                               원소 접근

[순회] begin() → *it → ++it → ... → end()
```

**핵심:** 저장 구조의 세부 표현보다 순회 인터페이스에 의존한다.

**핵심 코드 (C++17):** Collection 내부 표현 대신 Iterator로 순회한다.

```cpp
#include <iostream>
#include <vector>
std::vector<int> playlist{101, 102, 103};
for (auto it = playlist.begin(); it != playlist.end(); ++it) {
    std::cout << *it << '\n';
}
```

C++ STL의 Iterator는 패턴의 실용적 구현이다. Client는 원소를 순회할 때 Container의 내부 저장 구조를 직접 다루지 않는다.

### 3.10 Visitor — 구조와 연산의 변화축을 분리한다

**Intent**: 객체 구조는 안정적이지만 그 위의 연산 종류가 자주 늘어날 때 연산을 Visitor로 분리한다.

장점과 대가가 뚜렷하다.

AST처럼 구조 타입은 비교적 안정적이고 분석·출력·검사 연산이 계속 늘어나는 경우에 적합하다.

**일상 예시 — 도형 계산:** 원·사각형 구조는 유지한 채 넓이 계산·출력·통계 기능을 Visitor로 추가한다. 도형 종류가 늘면 기존 Visitor들을 수정해야 할 수 있다.

**객체 관계와 Double Dispatch**

```text
Shape «interface»          Visitor «interface»
    △ 구현                       △ 구현
    │                             │
  Circle                      PrintVisitor
    │ accept(visitor)              │
    └──────────> visitor.visit(Circle)
```

**핵심:** `accept()`가 자신의 구체 타입에 맞는 `visit()`을 호출한다. 새 도형 타입이 추가되면 Visitor 구현들도 변경될 수 있다.

**핵심 코드 (C++17):** 도형 클래스에 새 연산을 추가하지 않고 Visitor가 처리한다.

```cpp
struct Circle;
struct Square;
struct Visitor {
    virtual ~Visitor() = default;
    virtual void visit(const Circle&) = 0;
    virtual void visit(const Square&) = 0;
};
struct Shape {
    virtual ~Shape() = default;
    virtual void accept(Visitor&) const = 0;
};
struct Circle : Shape {
    void accept(Visitor& v) const override { v.visit(*this); }
};
struct Square : Shape {
    void accept(Visitor& v) const override { v.visit(*this); }
};
struct PrintVisitor : Visitor {
    void visit(const Circle&) override {}
    void visit(const Square&) override {}
};
// Circle c; PrintVisitor printer; c.accept(printer);
```

`accept → visit`의 **Double Dispatch**가 핵심이다. 도형 타입을 추가하면 기존 Visitor들도 수정해야 한다.

### 3.11 Interpreter — 간단한 문법 규칙을 객체 구조로 표현한다

**Intent**: 작은 Language·DSL의 Grammar를 Class 구조로 표현하고 문장을 해석한다.

문법이 커지면 Parser Generator나 전용 Parser Architecture가 더 적합하므로 적용 범위가 좁다.

**일상 예시 — 계산기:** 숫자·덧셈·곱셈을 표현하는 노드가 `2 + 3 × 4` 같은 간단한 수식을 해석한다. 복잡한 문법에는 별도 Parser가 낫다.

**표현식 트리와 평가 순서**

```text
[타입 관계]
Expr «interface»
   △ 구현
   ├─ Number
   └─ Add ──소유──> Expr (left, right)

[실제 표현식 트리]
         Add : Expr
          /      \
   Number(2)   Number(3)

[평가]
Add.eval() → left.eval() + right.eval() → 2 + 3 = 5
```

**핵심:** 문법 요소를 객체 트리로 구성하고 각 노드가 자신의 평가 규칙을 구현한다.

**핵심 코드 (C++17):** 작은 수식을 Expression 객체의 트리로 해석한다.

```cpp
#include <utility>
#include <memory>
struct Expr {
    virtual ~Expr() = default;
    virtual int eval() const = 0;
};
struct Number : Expr {
    int value;
    explicit Number(int n) : value(n) {}
    int eval() const override { return value; }
};
struct Add : Expr {
    std::unique_ptr<Expr> left, right;
    Add(std::unique_ptr<Expr> a, std::unique_ptr<Expr> b)
        : left(std::move(a)), right(std::move(b)) {}
    int eval() const override { return left->eval() + right->eval(); }
};
// Add{std::make_unique<Number>(2), std::make_unique<Number>(3)}.eval() == 5
```

문법 규칙을 객체 구조로 나타내는 최소 예시다. 연산자 우선순위·파싱은 별도 문제다.
