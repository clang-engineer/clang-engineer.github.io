# 데스크톱 가상화 — 제공 구조와 접속 단말

> [가상화 전체 개념지도](00-전체.md) → 데스크톱·사용자 환경

## 주제 개념지도

```text
사용자 업무환경을 단말에서 분리하여 중앙에서 제공
│
├─ 중앙의 실행·할당 구조 (무엇을 사용자에게 제공하는가?)
│  ├─ VDI → 사용자별 Desktop VM
│  ├─ RDS → 공유 Server OS의 사용자 Session
│  └─ CCI → 사용자별 전용 물리 Client 자원
│
├─ 접속 단말 (사용자는 무엇으로 접속하는가?)
│  ├─ 일반 PC → 범용 Local Computing
│  ├─ Thin Client → 경량 Local OS·접속 기능
│  └─ Zero Client → 범용 Local 기능 최소화·접속 특화
│
└─ 서비스 제공 모델 (누가 운영하여 제공하는가?)
   ├─ 자체 구축·운영
   └─ DaaS → Cloud 서비스로 Desktop 제공

공통 기반·연결: Compute / Storage / Network / 인증 / 화면 전송
```

세 축은 서로 경쟁하는 하나의 분류가 아니다. 예를 들어 **VDI로 제공되는 Desktop에 Thin Client로 접속**할 수 있고, **DaaS가 내부적으로 VDI와 유사한 구조를 사용**할 수도 있다.

## 1. 왜 중앙에서 Desktop을 제공하는가

사용자 PC마다 업무환경과 데이터를 분산하면 Patch·보안 정책·장애 대응을 일관되게 관리하기 어렵다. 데스크톱 중앙화는 **실행환경을 단말에서 분리**하여 사용자에게 화면을 전송하고 입력을 되돌리는 방식으로 이를 완화한다.

```text
중앙 실행환경 (Application 실행 · 업무 데이터 처리)
         │
         │ 화면·음성 등 출력 ↓ / 키보드·마우스 등 입력 ↑
         │ Network · Remote Display Protocol
         │
사용자 접속 단말 (일반 PC · Thin · Zero)
```

- **기대 효과:** 업무환경·Image·Patch 중앙 관리, 단말 내 데이터 잔존 감소, 장소·단말 변경 시 환경 접근
- **Trade-off:** 네트워크 품질과 중앙 인프라 의존, 동시 로그인·Storage·GPU 병목, 라이선스·운영 비용

단말을 경량화한다고 중앙의 자원 요구나 장애 위험이 사라지는 것은 아니다.

## 2. 중앙 Desktop 제공 구조 — VDI·RDS·CCI

### VDI — 사용자별 Desktop VM

VDI(Virtual Desktop Infrastructure)는 Hypervisor 기반의 **사용자별 Desktop VM**을 중앙에서 실행하고 원격 화면·입력을 전달하는 아키텍처다.

```text
사용자 단말 ↔ 화면 전송 ↔ Connection Broker / 인증
                                  ↓
                         Desktop VM Pool
                                  ↓
                             Hypervisor
                                  ↓
                           Physical Server
```

사용자별 VM 격리와 개인화가 유리하지만 CPU·Memory·Storage 자원이 많이 들 수 있다. Hypervisor만으로 VDI가 완성되지는 않으며 **Broker·인증·Desktop Image·Profile·VM 수명주기 관리**가 필요하다.

- **Persistent Desktop:** 사용자에게 전용 Desktop을 지속 할당하여 개인 설정 유지에 유리
- **Non-persistent Desktop:** Pool에서 할당·회수하고 초기화하여 표준화·일괄 관리에 유리

VDI의 ‘사용자별 VM’은 **사용자마다 VM을 영구 소유한다는 뜻이 아니다.**

### RDS — 공유 Server OS의 Session

RDS(Remote Desktop Services)는 하나의 Server OS에서 여러 사용자의 **Session**을 실행하는 방식이다.

```text
하나의 Server OS
├─ User A Session
├─ User B Session
└─ User C Session
```

사용자마다 VM을 생성하는 VDI보다 자원 효율이 높을 수 있지만 OS를 공유하므로 격리와 개인화에 제약이 있다. **Session 기반 RDS 자체에 Hypervisor가 필수인 것은 아니다.** RDS는 원격 앱 제공 등도 포괄하는 제품·서비스 체계이므로 여기서는 다중 사용자 Session 방식에 초점을 맞춘다.

### CCI — 사용자별 전용 물리 자원

CCI(Consolidated Client Infrastructure)는 중앙의 Blade PC 등 **물리 Client 자원을 사용자에게 전용으로 할당**하는 구조다.

```text
User A ↔ 전용 물리 Client A
User B ↔ 전용 물리 Client B
```

물리 자원 단위의 격리와 예측 가능한 성능에 유리하지만 자원 공유 효율·확장성·장비 비용 측면에서 불리할 수 있다. **중앙화가 목적이지 VM 가상화가 핵심은 아니다.**

| 비교축 | VDI | RDS (Session 기반) | CCI |
|---|---|---|---|
| 할당·격리 단위 | Desktop VM | Server OS의 사용자 Session | 전용 물리 Client |
| 실행환경 | 사용자별 Guest OS | 공유 Server OS | 사용자별 물리 환경 |
| 자원 효율 | VM별 자원 필요 | 상대적으로 높음 | 전용 자원 비용 큼 |
| 격리·개인화 | 상대적으로 강함 | 공유 OS 제약 | 물리 자원 단위 격리 |
| Hypervisor | 일반적으로 사용 | 구조상 필수 아님 | 구조상 필수 아님 |

## 3. 사용자 접속 단말 — 일반 PC·Thin·Zero Client

**VDI는 중앙 Desktop을 제공하는 구조**이고 **Thin·Zero Client는 접속하는 단말 유형**이다. 서로 대체 관계가 아니다.

### 일반 PC

범용 OS·Storage·Application을 갖추고 로컬 작업도 수행한다. 중앙 Desktop에 접속할 수 있지만, 로컬 기능이 많을수록 별도 단말 관리와 데이터 통제가 필요할 수 있다.

### Thin Client

일반 PC보다 **로컬 컴퓨팅 기능을 줄인 경량 단말**이다. 경량 OS, CPU·Memory, 제한된 Storage, 원격 Desktop Client, Browser나 일부 Local Application을 가질 수 있다.

‘Thin’은 로컬 기능이 **없다**가 아니라 **상대적으로 얇다**는 의미다. 따라서 OS Patch, Endpoint Security, Browser 및 접속 Client 관리는 여전히 필요할 수 있다.

### Zero Client

범용 로컬 OS·Storage를 최소화하고 **원격 Desktop 접속에 특화**한 단말이다. 부팅·Network·화면 출력·입력 처리에는 Hardware와 Firmware가 필요하므로 CPU가 ‘0개’라는 뜻이 아니다.

- **장점:** 로컬 관리·저장 영역 축소, 단순한 접속 환경
- **한계:** 중앙 시스템·네트워크 의존, 특정 Protocol·솔루션 종속 가능성, 로컬 독립 작업 제약

Thin과 Zero의 경계는 제품별로 달라진다. 명칭보다 **OS·Storage·일반 앱 실행·Protocol 호환·Offline 지원**을 확인해야 한다.

| 기준 | 일반 PC | Thin Client | Zero Client |
|---|---|---|---|
| 로컬 기능 | 폭넓음 | 일부 기능 유지 | 최소화 |
| 로컬 관리 | OS·앱·보안 관리 | 경량 OS·Client 관리 | Firmware·접속 기능 중심 |
| 중앙 의존 | 사용 업무에 따라 다름 | 상대적으로 큼 | 일반적으로 큼 |
| 오프라인 작업 | 가능할 수 있음 | 제품·구성에 따라 다름 | 대체로 제한적 |

**Zero PC**는 엄격하게 통일된 기술 분류라기보다 제품·사업자 문맥에서 Zero Client 계열 단말이나 중앙 Desktop 솔루션을 가리킬 수 있는 명칭이다. 실제 구조를 확인해야 한다.

## 4. DaaS — 실행 구조가 아니라 서비스 제공 모델

DaaS(Desktop as a Service)는 Desktop 환경을 **Cloud 서비스로 제공·소비**하는 모델이다. 내부적으로 VDI와 유사한 VM 구조를 사용할 수 있지만, VDI·RDS·CCI처럼 사용자에게 할당하는 실행 자원의 종류를 뜻하지는 않는다.

```text
구현 질문: 사용자별 VM / 공유 Session / 전용 물리 자원?
운영 질문: 자체 구축·운영 / Cloud Provider의 Desktop 서비스?
접속 질문: 일반 PC / Thin / Zero?
```

DaaS에서는 공급자가 인프라 운영의 일부 또는 상당 부분을 담당하지만, **사용자·접근권한·데이터·보안 설정의 책임까지 모두 사라지는 것은 아니다.** 실제 책임 경계는 서비스 계약과 구성에 따라 다르다.

## 5. 서버 가상화와의 관계

서버 가상화와 데스크톱 가상화는 **용도 관점의 분류**이고, Hypervisor·VM은 공통 기반 기술이 될 수 있다.

```text
Hypervisor / VM 기술
├─ Web·WAS·DB 실행 → 서버 워크로드
└─ 사용자 Desktop VM 실행 → VDI
```

서버 가상화 기술만 있다고 VDI가 완성되지는 않는다. 반대로 RDS의 Session 공유와 CCI의 전용 물리 자원 할당은 VM을 필수 전제로 하지 않는다.

## 6. 선택과 운영의 판단 기준

- **강한 사용자 격리·개인화:** VDI 또는 전용 물리 자원 방식 검토
- **표준화된 다수 사용자 업무·자원 효율:** Session 기반 RDS 검토
- **전용 하드웨어·성능 요구:** CCI 검토
- **단말 관리·로컬 데이터 축소:** Thin 또는 Zero Client 검토
- **자체 인프라 운영 부담 축소:** DaaS 검토

실제 설계에서는 Network 지연·Packet Loss, 동시 로그인 집중, Storage IOPS·GPU, Profile 관리, 인증·MFA, 주변기기, Clipboard·파일 전송 정책, HA·DR, Offline 업무 요구, 라이선스·총소유비용을 함께 검토한다.

## 7. 이해 복원

1. VDI·RDS·CCI는 **무엇을 사용자별로 할당하는가?** 왜 격리와 자원 효율이 달라지는가?
2. **VDI와 Thin Client를 비교 대안으로 놓으면** 어떤 분류축이 섞이는가?
3. Thin과 Zero의 차이를 **로컬 기능·관리·중앙 의존성**으로 설명할 수 있는가?
4. DaaS는 왜 VDI의 반대말이 아니며, 서비스 이용자가 계속 책임지는 부분은 무엇인가?
5. 업무 요구가 주어졌을 때 **중앙 제공 구조·접속 단말·운영 모델**을 각각 선택할 수 있는가?

**인출 단서:** VM = VDI / Session = RDS / 물리 자원 = CCI / 단말 경량화 = Thin·Zero / 서비스 소비 = DaaS.
