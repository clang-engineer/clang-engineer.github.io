# 캐시 패턴과 무효화

## 이 문서의 성격

이 문서는 특정 DB 제품 사용법이 아니라 **애플리케이션에서 원본 데이터 앞에 Cache Layer를 둘 때 생기는 성능·정합성 Trade-off**를 이해하기 위한 `99-` 보충학습이다.

## 이 문서에서 되짚을 질문

- 어떤 데이터가 Cache에 적합한가?
- Cache-Aside·Read-Through·Write-Through·Write-Behind는 책임이 어떻게 다른가?
- Cache Invalidation이 왜 어려운가?
- DB와 Cache 사이 Stale Data를 어떻게 다루는가?
- Stampede·Penetration·Hot Key는 어떤 실패 형태인가?

## 1. Cache는 비싼 원본 접근을 줄인다

```text
Application
   ↓
Cache
 ├─ HIT  → 즉시 반환
 └─ MISS → 원본 DB 조회
              ↓
           Cache 채움
```

Cache는 성능 최적화 계층이다. 같은 데이터를 반복해서 읽고, 쓰기 빈도가 낮으며, 짧은 Stale 상태를 허용할 수 있을수록 효과가 크다.

반대로 잔액·재고 차감처럼 매 순간 최신값이 정확해야 하는 데이터는 Cache 사용 자체가 새로운 위험이 될 수 있다.

## 2. 읽기와 쓰기 Pattern은 같은 축이 아니다

### Cache-Aside

Application이 먼저 Cache를 조회하고 MISS일 때 DB에서 읽어 Cache를 채운다.

```text
Read
Cache → MISS → DB → Cache 저장 → 반환

Write
DB 변경 → Cache 삭제
```

구현이 단순하고 필요한 데이터만 채우지만 Application이 Cache 책임을 직접 가진다.

### Read-Through

MISS 처리와 원본 Load를 Cache Layer가 담당한다. Cache-Aside와 비슷한 읽기 흐름이지만 **누가 Load 책임을 가지는가**가 다르다.

### Write-Through

Write를 Cache와 원본 저장소에 동기적으로 반영한다. 최신 Cache를 유지하기 쉽지만 Write Latency가 증가한다.

### Write-Behind

먼저 Cache에 반영하고 원본 저장소 갱신은 비동기로 넘긴다. 빠른 Write를 얻는 대신 장애 시 유실·복구·순서 문제를 별도로 설계해야 한다.

```text
읽기 책임 축
Cache-Aside ↔ Read-Through

쓰기 반영 축
Write-Through ↔ Write-Behind
```

따라서 네 용어를 한 줄의 발전 단계로 외우지 않는다.

## 3. Invalidation이 핵심 문제다

원본과 Cache에 같은 논리 데이터가 존재하면 둘의 상태가 어긋날 수 있다.

대표적인 무효화 수단은 다음과 같다.

- TTL: 일정 시간이 지나면 자동 만료
- 명시적 삭제: 원본 변경 뒤 Cache Key 제거
- 갱신: 원본 변경과 함께 Cache 값도 변경

TTL은 최신성 보장이 아니라 **Stale 상태가 지속될 수 있는 최대 시간을 제한하는 안전망**으로 이해한다.

## 4. DB와 Cache는 원자적으로 같이 바뀌지 않는다

Cache-Aside에서도 Race Condition이 생길 수 있다.

```text
T1: Cache MISS
T1: DB에서 old value 읽음
T2: DB를 new value로 변경
T2: Cache 삭제
T1: old value를 Cache에 저장
```

결과적으로 삭제가 성공했는데도 오래된 값이 다시 들어갈 수 있다.

따라서 정합성은 `완벽히 동기화`보다 요구사항에 맞는 Stale Window를 정의하는 문제로 본다.

일반적인 완화책은 다음과 같다.

- DB 변경 후 Cache 삭제 순서 유지
- TTL 적용
- 필요하면 CDC 기반 Invalidation
- 경쟁 조건이 중요한 경우 Version·Token 등으로 오래된 Write를 구분

특정 패턴을 기계적으로 적용하지 않고 실패 시 어떤 상태가 남는지 먼저 그린다.

## 5. 대표 장애 Pattern

### Cache Stampede

인기 Key가 동시에 만료되어 많은 요청이 한꺼번에 원본 DB로 몰린다.

```text
Hot Key 만료
→ 다수 MISS
→ 동시에 DB 조회
→ 원본 과부하
```

Single Flight/Lock, TTL Jitter, 미리 갱신 같은 방법으로 동시 재생성을 줄인다.

### Cache Penetration

존재하지 않는 Key 요청이 계속 들어와 매번 Cache MISS 후 DB까지 내려간다. Negative Caching이나 입력 검증, 필요하면 Bloom Filter 등을 검토한다.

### Hot Key

특정 Key에 Traffic이 지나치게 집중되어 Cache Node 하나가 병목이 된다. 복제·Local Cache·Key 분산 등으로 부하 위치를 조정할 수 있다.

## 6. 판단 순서

```text
원본 조회가 실제 병목인가?
        ↓
어떤 데이터가 반복 조회되는가?
        ↓
얼마나 오래된 값을 허용할 수 있는가?
        ↓
Read / Write 책임 Pattern 결정
        ↓
Invalidation + TTL 설계
        ↓
Stampede·Penetration·Hot Key 실패경로 검토
        ↓
Hit Ratio와 원본 부하 재측정
```

> **Cache는 데이터를 빠르게 만드는 복사본이다. 복사본을 추가하는 순간 성능 문제 일부를 정합성·무효화 문제로 바꾼다는 점을 함께 설계해야 한다.**
