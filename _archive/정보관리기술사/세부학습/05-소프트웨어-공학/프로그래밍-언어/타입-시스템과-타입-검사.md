# 타입 시스템과 타입 검사 — Static · Dynamic · Nominal · Structural

> 학습 원칙: [`00-프로그래밍-언어-학습원칙.md`](00-프로그래밍-언어-학습원칙.md)
>
> 핵심 질문: **어떤 값을 어떤 연산에 사용할 수 있는지 누가, 언제, 어떤 규칙으로 판단하는가?**

---

## 1. 큰 그림

타입 시스템은 단순히 `int`, `string`, `class` 같은 이름 목록이 아니다.

```text
값 / 표현식
   ↓
어떤 연산이 허용되는가?
   ↓
Type Rule
   ↓
언제 검사하는가?
├─ Compile Time
└─ Runtime
   ↓
타입 관계를 무엇으로 판단하는가?
├─ 이름/선언 관계
└─ 실제 구조/연산 가능성
```

핵심 질문은 다음이다.

```text
타입 오류를 언제 잡는가?
타입 관계를 어떻게 판단하는가?
변환을 얼마나 자동으로 허용하는가?
타입 정보가 Runtime에도 남는가?
```

---

## 2. C++ 기준점 — Static Type System

C++에서는 많은 타입 오류를 Compile Time에 검사한다.

```cpp
int x = 10;
std::string s = x; // 일반적으로 허용되지 않음
```

함수 호출도 Signature를 기준으로 검사한다.

```cpp
void print(int value);

print("hello"); // 타입 불일치
```

핵심 직관:

```text
Source Code
   ↓
Compiler가 Type Check
   ↓
허용된 연산만 Code Generation
```

하지만 C++도 `virtual`, RTTI, `dynamic_cast`처럼 일부 타입 판단을 Runtime에 수행할 수 있다. `정적 타입 언어 = Runtime 타입 정보 없음`이라고 단순화하지 않는다.

---

## 3. Static Typing과 Dynamic Typing

### Static Typing

```text
주요 타입 검사를 실행 전에 수행
```

대표:

- C++
- Java
- Rust
- Go

장점:

- 많은 타입 오류를 실행 전에 검출
- Tooling/Refactoring 지원에 유리
- Compiler Optimization에 타입 정보 활용 가능

Trade-off:

- 타입 선언·추론·제약 이해 필요
- 매우 동적인 구조 표현에 추가 추상화가 필요할 수 있음

### Dynamic Typing

```text
값의 타입과 연산 가능성을 Runtime에 판단
```

JavaScript:

```javascript
let x = 10;
x = "hello";
```

Python:

```python
x = 10
x = "hello"
```

장점:

- 코드 작성과 구조 변경이 유연
- Runtime 객체 구조를 동적으로 다루기 쉬움

Trade-off:

- 일부 오류가 실제 실행 경로에서만 드러남
- 대규모 변경 시 별도 Tooling/Type Annotation이 중요해질 수 있음

---

## 4. 변수에 타입이 있는가, 값에 타입이 있는가

정적 언어에서는 변수/표현식에 Compile Time 타입이 강하게 연결된다.

```cpp
int x = 10;
```

```text
x의 Static Type
→ int
```

동적 언어에서는 이름이 특정 타입에 고정되지 않고 Runtime 값이 타입을 가진다고 이해하는 편이 쉽다.

```javascript
let x = 10;
x = "hello";
```

```text
Binding x
→ 현재 Number 값 참조
→ 이후 String 값 참조 가능
```

단, 언어마다 내부 구현과 타입 모델이 다르므로 `동적 타입 = 타입이 없다`고 설명하지 않는다.

---

## 5. Type Inference — 타입을 안 쓰는 것과 Dynamic Typing은 다르다

C++:

```cpp
auto x = 10;
```

Rust:

```rust
let x = 10;
```

겉으로 타입을 직접 쓰지 않았지만 Compiler가 타입을 추론한다.

```text
Type Annotation 생략
≠ Dynamic Typing

Type Inference
→ Compiler가 문맥에서 Static Type을 추론
```

이 경계는 매우 중요하다.

---

## 6. Nominal Typing — 이름과 선언 관계로 타입 관계를 판단한다

명목적 타입 시스템에서는 타입의 이름이나 명시적 선언 관계가 중요하다.

예를 들어 Java:

```java
class Dog implements Animal { ... }
```

C++ 상속:

```cpp
struct Dog : Animal { ... };
```

```text
Dog가 Animal인가?
→ 명시적 상속/구현 관계 확인
```

구조가 우연히 같아도 선언 관계가 없으면 같은 추상 타입으로 보지 않을 수 있다.

---

## 7. Structural Typing — 구조가 맞으면 타입 관계를 인정한다

Go Interface가 좋은 예다.

```go
type Speaker interface {
    Speak()
}
```

어떤 타입이 `Speak()` Method를 제공하면 명시적으로 `implements Speaker`를 쓰지 않아도 Interface를 만족할 수 있다.

```text
이름이 무엇인가?
보다
필요한 구조/Method Set이 있는가?
```

TypeScript도 Structural Typing의 대표 사례다.

C++ Template의 Duck Typing-like한 Compile Time 요구사항도 비슷한 직관을 줄 수 있지만, 언어 차원의 Structural Type System과 완전히 같은 것은 아니다.

---

## 8. Duck Typing — 실제로 필요한 연산이 되면 사용한다

Python의 전형적인 직관:

```python
def run(x):
    x.speak()
```

`x`가 어떤 명시적 Interface를 상속했는지가 아니라 Runtime에 `speak()`를 수행할 수 있는지가 중요하다.

```text
Nominal
→ "어떤 타입이라고 선언했는가?"

Structural
→ "필요한 구조를 가지고 있는가?"

Duck Typing
→ "실제로 필요한 연산을 수행할 수 있는가?"
```

Structural Typing과 Duck Typing은 관련 있지만 검사 시점과 언어 규칙이 다를 수 있으므로 등치하지 않는다.

---

## 9. 강한 타입 / 약한 타입이라는 표현은 조심한다

`Strong Typing`, `Weak Typing`은 문헌마다 정의가 일관되지 않아 단독 분류 기준으로 쓰기 어렵다.

대신 구체적인 질문을 한다.

```text
암시적 Type Conversion을 얼마나 허용하는가?
서로 다른 타입의 연산을 어떻게 처리하는가?
Runtime에 자동 Coercion이 일어나는가?
타입 오류를 언제 검출하는가?
```

JavaScript:

```javascript
"5" + 1 // "51"
"5" - 1 // 4
```

이 현상은 단순히 "약한 타입"이라고 외우기보다 **연산자별 Type Coercion 규칙**을 이해하는 편이 정확하다.

---

## 10. Type Conversion — 명시적 변환과 암시적 변환

C++:

```cpp
double d = 10; // implicit conversion
int x = static_cast<int>(d); // explicit conversion
```

핵심 질문:

```text
어떤 변환을 자동으로 허용하는가?
정보 손실 가능성이 있는가?
Runtime 검사나 실패 가능성이 있는가?
```

언어별 타입 안전성 차이는 Conversion 규칙과 깊게 연결된다.

---

## 11. Sum Type와 Product Type

타입을 구조적으로 보면 많은 언어 기능이 정리된다.

### Product Type

여러 값을 동시에 가진다.

```cpp
struct Point {
    int x;
    int y;
};
```

개념:

```text
Point
= x AND y
```

### Sum Type

여러 경우 중 하나를 가진다.

Rust:

```rust
enum Result<T, E> {
    Ok(T),
    Err(E),
}
```

개념:

```text
Result
= Ok OR Err
```

C++ `std::variant`가 좋은 기준점이다.

이 관점은 `Result`, `Option`, AST, State Machine을 이해할 때 유용하다.

---

## 12. Runtime Type Information과 Reflection

정적 타입 언어도 Runtime 타입 정보를 일부 유지할 수 있다.

C++:

```cpp
dynamic_cast<Derived*>(base);
typeid(obj);
```

Java:

```text
Class Metadata
Reflection API
```

핵심은:

```text
Compile Time Type 정보
≠ Runtime Type Metadata
```

둘이 어느 정도 연결되고 Runtime에 무엇이 남는지는 언어/Runtime 설계에 따라 다르다.

## 13. 타입 시스템과 Generic / 다형성의 연결

```text
타입 시스템
  ↓
타입 관계와 허용 연산 정의
  ↓
Generic Constraint
Subtype 관계
Interface / Trait 만족
Overload Resolution
Dispatch 가능 범위
```

따라서 Generic과 다형성을 이해하려면 그 언어가 **타입 관계를 어떻게 판단하는지** 함께 봐야 한다.

## 14. 기술사 관점의 비교축

| 비교축 | 질문 |
|---|---|
| 검사 시점 | Compile Time인가 Runtime인가? |
| 타입 관계 | Nominal인가 Structural인가? |
| 추론 | Type Annotation 없이 얼마나 추론하는가? |
| 변환 | 암시적 Conversion/Coercion을 얼마나 허용하는가? |
| Runtime 정보 | Reflection/RTTI를 얼마나 제공하는가? |
| 추상화 | Generic·Interface·Trait와 어떻게 연결되는가? |

## 15. 기억·인출

```text
Static Typing
= 주로 실행 전에 Type Check

Dynamic Typing
= Runtime 값과 연산에서 Type Check

Type Inference
= 타입을 안 쓰는 것이 아니라 Compiler가 추론

Nominal
= 이름/선언 관계가 중요

Structural
= 필요한 구조가 맞으면 됨

Duck Typing
= 필요한 연산이 실제로 되면 사용
```

핵심 문장:

> **타입 시스템은 값에 붙이는 라벨이 아니라 어떤 연산을 허용하고 어떤 관계를 같은 타입 계열로 인정할지 정하는 규칙 체계이며, 언어마다 그 검사를 언제 수행하고 얼마나 강제하는지가 다르다.**
