# 비동기 실행 모델 — Callback · Event Loop · Promise/Future · Coroutine · async/await

> 학습 원칙: [`00-프로그래밍-언어-학습원칙.md`](00-프로그래밍-언어-학습원칙.md)
>
> 핵심 질문: **오래 걸리는 작업을 기다리는 동안 실행 흐름을 막지 않고, 완료된 뒤 필요한 코드를 어떻게 다시 실행하는가?**

---

## 1. 큰 그림

비동기 프로그래밍에는 서로 다른 층위의 개념이 함께 등장한다.

```text
오래 걸리는 작업
(I/O, Timer, Network)
        ↓
기다리는 동안 현재 실행 흐름을 막고 싶지 않다
        ↓
비동기 작업 시작
        ↓
완료 사실을 어떻게 전달할까?
├─ Callback
├─ Promise / Future
└─ Coroutine + async/await

완료된 작업을 언제 다시 실행할까?
├─ Event Loop
├─ Scheduler
└─ Thread Pool / Runtime
```

`Callback`, `Promise`, `Coroutine`은 결과를 이어가는 표현 방식이고, `Event Loop`는 실행 시점을 조정하는 Runtime 메커니즘이다. 같은 층위로 두지 않는다.

---

## 2. C++ 기준점 — 나중에 호출할 코드와 상태를 보관한다

가장 단순한 비동기 모델은 "작업이 끝나면 이 함수를 호출해 달라"는 Callback이다.

```cpp
void read_async(std::function<void(Result)> callback);

read_async([](Result r) {
    use(r);
});
```

C++ 관점에서 핵심은 다음이다.

```text
비동기 작업 시작
+
나중에 호출할 함수 객체 저장
+
완료 시점에 그 객체 호출
```

Callback이 외부 상태를 사용한다면 Capture Lambda가 된다.

```cpp
int request_id = 10;

read_async([request_id](Result r) {
    log(request_id, r);
});
```

여기서:

```text
request_id를 기억하는 이유
→ Closure / Capture

언제 Callback을 실행하는가
→ Scheduler / Event Loop / Runtime
```

두 문제를 분리한다.

---

## 3. Event Loop — 준비된 작업을 실행 흐름으로 되돌린다

Event Loop는 반복적으로 실행 가능한 작업을 확인하고 Dispatch하는 실행 모델이다.

```text
비동기 작업 등록
      ↓
Runtime / OS가 대기
      ↓
작업 완료 또는 Event 발생
      ↓
Queue에 실행 가능 작업 등록
      ↓
Event Loop
      ↓
실행 가능한 시점에 Callback 실행
```

JavaScript의 대표적인 직관은 다음과 같다.

```javascript
console.log("A");

setTimeout(() => {
  console.log("B");
}, 0);

console.log("C");
```

결과:

```text
A
C
B
```

`setTimeout(..., 0)`은 "즉시 실행"이 아니라 **최소 대기 조건을 만족한 뒤 Queue에 들어가고, 현재 실행 흐름이 끝난 뒤 실행 기회를 얻는다**고 이해한다.

---

## 4. Event Loop와 I/O Multiplexing은 같은 개념이 아니다

네트워크에서 사용하는 `select`, `poll`, `epoll`, `kqueue` 등은 **여러 I/O 상태를 한 번에 감시하는 OS 수준 메커니즘**이다.

Event Loop는 그보다 상위에서 Event를 받아 Application 작업을 Dispatch하는 반복 실행 구조다.

```text
Application
  ↓
Event Loop
  ↓
Runtime
  ↓
OS I/O Multiplexing
(select / poll / epoll / kqueue 등)
  ↓
준비된 I/O 통지
  ↑
Runtime
  ↑
Event Loop가 Callback/Task Dispatch
```

따라서:

```text
I/O Multiplexing
→ 어떤 I/O가 준비됐는지 효율적으로 감시

Event Loop
→ 준비된 Event/Task를 언제 어떤 실행 흐름으로 넘길지 조정
```

Node.js 같은 Runtime에서는 둘이 실제로 연결될 수 있지만 동일한 개념은 아니다.

---

## 5. Callback — 완료 이후의 행동을 직접 전달한다

Callback은 가장 직접적인 Continuation 표현이다.

```javascript
readFile(path, (err, data) => {
  if (err) return handle(err);
  use(data);
});
```

장점:

- 단순한 비동기 API 구현 가능
- 함수 자체를 값처럼 전달 가능

문제:

- 중첩이 깊어질 수 있음
- Error 전달 규칙이 분산될 수 있음
- 여러 비동기 작업의 조합이 복잡해질 수 있음

```text
A 완료
  ↓
Callback B
  ↓
B 완료
  ↓
Callback C
```

Callback 자체가 나쁜 것이 아니라 **복잡한 비동기 제어 흐름을 함수 중첩만으로 표현할 때 가독성과 조합성이 떨어질 수 있다**는 점이 핵심이다.

---

## 6. Promise / Future — 아직 없는 결과를 값으로 표현한다

Promise/Future 계열은 "나중에 생길 결과"를 객체로 표현한다.

C++:

```cpp
std::future<int> f = std::async([] {
    return compute();
});

int value = f.get();
```

JavaScript:

```javascript
fetch(url)
  .then(response => response.json())
  .then(data => use(data));
```

공통 직관:

```text
현재는 결과 없음
      ↓
미래 결과를 나타내는 객체
      ↓
Pending
  ├─ Fulfilled
  └─ Rejected / Error
```

다만 언어마다 `Promise`, `Future`의 실행 시점·Thread 관계·취소·Error 전파 의미론은 다르다.

---

## 7. Coroutine — 실행 상태를 저장하고 중단·재개한다

Coroutine은 **함수 실행을 끝내지 않고 중간 상태를 보존한 채 Suspend하고 나중에 Resume할 수 있는 실행 단위**다.

C++ 관점으로 풀면 다음 상태가 필요하다.

```text
현재 실행 위치
지역 변수 상태
중단 이유
재개할 다음 위치
```

개념적으로:

```cpp
struct CoroutineState {
    int state;
    int local_value;
};
```

그리고 실행은 상태 머신처럼 볼 수 있다.

```text
state 0
→ 작업 시작
→ I/O 요청
→ Suspend

I/O 완료
→ Resume
→ state 1부터 계속 실행
```

일반 Thread와 달리 Coroutine은 보통 **사용자 수준 Runtime이 실행 상태를 관리하고 명시적/논리적 Suspend 지점에서 양보**한다.

---

## 8. async/await — 비동기 상태 머신을 동기식 코드처럼 표현한다

`async/await`은 비동기 자체를 새로 만드는 마법이 아니라, Promise/Future 또는 Coroutine 기반 비동기 상태 전이를 더 읽기 쉽게 표현하는 문법이다.

```javascript
async function load() {
  const response = await fetch(url);
  const data = await response.json();
  return data;
}
```

개념적으로는:

```text
fetch 시작
  ↓
아직 완료 안 됨
  ↓
현재 함수 상태 저장
  ↓
실행권 반환
  ↓
fetch 완료
  ↓
저장된 상태 복원
  ↓
다음 문장부터 재개
```

C++ 관점에서는 **상태 머신 + Continuation + 저장된 지역 상태**로 풀어보면 이해하기 쉽다.

---

## 9. Thread와 Event Loop / Coroutine의 차이

```text
Thread
→ OS 또는 Runtime이 독립 실행 Stack/Context를 가진 실행 단위로 Scheduling

Event Loop
→ 하나 또는 소수의 실행 흐름에서 Event/Task를 순차적으로 Dispatch

Coroutine
→ 실행 상태를 보존하고 명시적/논리적 지점에서 Suspend/Resume
```

실제 시스템에서는 조합될 수 있다.

```text
Event Loop Thread
      ↓
I/O Event Dispatch
      ↓
Coroutine Resume
      ↓
CPU 작업은 Worker Thread Pool로 위임
```

따라서 `Event Loop = Single Thread`, `Coroutine = Thread 대체`, `async = 병렬 실행`처럼 단순 등치하지 않는다.

---

## 10. 동시성·병렬성·비동기를 구분한다

```text
비동기(Asynchrony)
→ 작업 완료를 기다리는 방식의 문제

동시성(Concurrency)
→ 여러 작업의 진행을 겹쳐 관리하는 구조

병렬성(Parallelism)
→ 여러 작업을 실제로 같은 시간에 실행
```

Event Loop는 병렬 실행이 없어도 동시성을 제공할 수 있다. 반대로 Thread Pool은 실제 Parallelism을 만들 수 있다.

## 11. 개념 경계 정리

| 개념 | 핵심 질문 | C++ 기준점 |
|---|---|---|
| Callback | 끝난 뒤 무엇을 실행할까? | 함수 포인터 / `std::function` / Lambda |
| Closure | Callback이 상태를 어떻게 기억할까? | Capture Lambda |
| Event Loop | 준비된 작업을 언제 실행할까? | Queue + Loop + Dispatcher |
| Promise/Future | 아직 없는 결과를 어떻게 표현할까? | `std::future` |
| Coroutine | 실행을 어떻게 중단하고 다시 이어갈까? | Coroutine State / Suspend / Resume |
| async/await | 비동기 상태 전이를 어떻게 읽기 쉽게 표현할까? | 상태 머신의 문법적 추상화 |
| I/O Multiplexing | 어떤 I/O가 준비됐는지 어떻게 감시할까? | `select` / `poll` / `epoll` 계열 |

---

## 12. 기억·인출

```text
Closure
= 무엇을 기억하는가

Event Loop
= 언제 다시 실행하는가

Promise/Future
= 아직 없는 결과를 값으로 만든다

Coroutine
= 실행 위치와 상태를 저장하고 중단·재개

async/await
= 그 상태 머신을 동기 코드처럼 보이게 한다
```

핵심 문장:

> **비동기 실행 모델은 오래 걸리는 작업을 다른 곳에 맡기는 것만이 아니라, 완료 결과와 실행 상태를 어떻게 보존하고 다시 실행 흐름에 연결하는지까지 포함한다.**
