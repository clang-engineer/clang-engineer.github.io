# 프로그래밍 언어 학습 원칙

이 문서는 정보관리기술사 세부학습에서 **프로그래밍 언어 관련 개념을 어떤 관점으로 이해하고 정리할지** 정의한다.

상위 공통 규칙은 반복하지 않는다. 문서 작성·개념 묶음·비유와 대응의 일반 원칙은 다음 문서를 따른다.

- [`../../../00-문서작성-공통원칙.md`](../../../00-문서작성-공통원칙.md)

이 문서에서는 프로그래밍 언어를 공부할 때 필요한 **언어 공통 개념 중심의 학습 방식과 C++ 기준점 사용 원칙**만 추가한다.

## 1. 언어 문법보다 언어를 가로지르는 개념을 먼저 본다

프로그래밍 언어 기능을 언어별 Keyword나 문법 이름으로 먼저 외우지 않는다.

먼저 여러 언어가 공통으로 해결하려는 문제를 찾는다.

```text
JavaScript Closure
C++ Capture Lambda
Rust Closure
        ↓
함수와 외부 상태를 어떻게 결합하고 보존하는가?
```

```text
C++ virtual
Java interface
Go interface
Rust trait object
        ↓
공통 추상 타입을 통해 실제 호출 대상을 어떻게 선택하는가?
```

언어가 바뀌어도 다시 사용할 수 있는 **원형 개념과 질문**을 먼저 잡고, 각 언어의 문법과 구현은 그다음에 본다.

> **언어가 하나 늘었다고 새로운 개념이 하나 생긴 것으로 보지 않는다. 먼저 기존 개념의 다른 표현인지 확인한다.**

---

## 2. 추상 개념은 가능하면 C++의 구체적 메커니즘으로 한 번 풀어본다

새로운 프로그래밍 언어 개념이 추상적으로 느껴지면, 먼저 C++에서 직접 표현하거나 구현한다면 어떤 요소가 필요한지 생각한다.

대표적인 기준점은 다음과 같다.

```text
다형성
→ virtual / vtable / dynamic dispatch

Closure
→ Functor → Lambda → Capture

Callback
→ 함수 포인터 / std::function / Lambda

상태를 가진 호출 가능 객체
→ operator()를 가진 Functor

Future
→ std::future와 결과 상태

Event Loop
→ Queue + Loop + Dispatcher + I/O 대기

Coroutine
→ 실행 상태 저장 + Suspend + Resume

RAII
→ 객체 Lifetime과 자원 해제 결합
```

C++를 정답 언어로 삼는 것이 아니라, **객체·함수 호출·메모리·Lifetime·Dispatch·Thread·Queue 같은 구체적인 실행 요소가 비교적 잘 드러나는 기준 언어**로 사용한다.

---

## 3. C++ 대응은 이해의 발판이지 개념의 정의가 아니다

C++에서 익숙한 기능과 대응했다고 해서 두 개념을 동일시하지 않는다.

설명은 가능하면 다음 순서를 따른다.

```text
1. C++에서 무엇을 떠올리면 되는가?
2. 어떤 역할과 구조가 비슷한가?
3. 해당 언어에서는 의미론이 어디서 달라지는가?
```

예를 들어 JavaScript Closure는 C++ Capture Lambda를 떠올리면 이해하기 쉽다.

```text
공통 직관
→ 함수가 외부 상태를 나중에도 사용할 수 있음

C++
→ [x], [&x]처럼 Capture 방식을 명시
→ 참조 Capture는 대상 Lifetime을 주의

JavaScript
→ 함수가 Lexical Environment의 Binding에 접근
→ 필요한 Environment의 Lifetime을 Runtime이 관리
```

따라서 최종 정리는 `Closure = C++ Capture`처럼 끝내지 않는다.

> **C++ 대응으로 이해하고, 언어별 의미론의 차이에서 학습을 완성한다.**

---

## 4. 문법을 내부 메커니즘과 실행 모델까지 한 단계 내려서 본다

새로운 문법이나 용어를 보면 다음 질문을 우선한다.

> **이 기능을 C++로 직접 구현한다면 결국 어떤 객체·상태·함수 호출·메모리·Queue가 필요할까?**

예:

```text
Closure
→ 호출 가능한 함수 + 외부 상태

Dynamic Polymorphism
→ 공통 Interface + 실제 객체 + 간접 Dispatch

Event Loop
→ Event/Task Queue + 반복 Loop + Dispatch

Coroutine
→ 실행 위치와 지역 상태 보존 + Suspend/Resume

GC
→ 객체 관계 추적 + Reachability 판단 + 회수

async/await
→ 비동기 작업 + 중단 지점 + 상태 보존 + 재개
```

이 단계의 목적은 구현체의 내부 세부를 끝까지 파는 것이 아니다. **추상 용어 뒤에 실제로 어떤 실행 요소와 상태 변화가 존재하는지 보이게 하는 것**이 목적이다.

---

## 5. 의미론과 구현 방법을 구분한다

언어 공통 개념과 특정 언어의 구현 장치를 같은 층위로 놓지 않는다.

```text
다형성
= 개념

C++ virtual / vtable
= C++에서 Runtime Subtype Polymorphism을 구현하는 대표 방법
```

```text
Closure
= 함수와 정의 환경의 결합이라는 개념

C++ Capture Lambda
= C++에서 이를 표현하는 한 방식
```

```text
비동기 실행
= 문제와 실행 모델의 상위 개념

Event Loop
= 비동기 작업을 조정하는 실행 모델 중 하나
```

`개념 = 특정 문법`으로 암기하면 다른 언어에서 같은 문제를 다시 새 개념처럼 배우게 되므로, **무엇이 의미론이고 무엇이 구현 전략인지** 구분한다.

---

## 6. 파일은 언어별 문법이 아니라 함께 이해할 가치가 있는 개념군 단위로 만든다

언어별 파생 기능마다 파일 하나를 만들지 않는다.

다음처럼 같은 원형 개념을 이해하는 데 서로 도움이 되는 경우 하나의 학습 단위에서 함께 다룬다.

```text
함수 객체와 Closure
├─ Function Object / Functor
├─ Lambda
├─ Capture
├─ Closure
└─ 언어별 Capture·Lifetime 의미 차이
```

```text
다형성과 Dispatch
├─ Subtype Polymorphism
├─ Dynamic Dispatch
├─ C++ virtual
├─ Java / Go / Rust의 대응 방식
└─ Static Polymorphism과의 경계
```

다음과 같은 사전식 파편화는 기본으로 하지 않는다.

```text
C++-Functor.md
C++-Lambda.md
JavaScript-Closure.md
Rust-Closure.md
Java-Lambda.md
```

언어가 추가되면 기존 개념 문서 안에서 **새로운 의미론 차이와 대표 사례**를 보강하는 방식을 우선한다.

다만 함께 볼 때 오히려 이해가 흐려지거나 독립적인 실행 모델·타입 체계로 충분한 학습 가치가 생기면 별도 문서로 분리할 수 있다.

---

## 7. C++ 대응이 흐릿하면 해당 언어의 고유한 학습 지점으로 본다

모든 개념을 억지로 C++에 끼워 맞추지 않는다.

C++ 대응을 찾았을 때 역할·Lifetime·타입 규칙·실행 모델이 크게 다르면, 그 차이는 단순 예외가 아니라 **해당 언어가 새로 제공하는 의미론일 수 있다.**

```text
C++ 대응이 선명함
→ 기존 지식에서 출발해 차이만 학습

C++ 대응이 부분적임
→ 공통 역할까지만 발판으로 사용
→ 의미론 차이를 핵심 학습 대상으로 봄

C++ 대응이 거의 없음
→ 해당 언어 고유 개념으로 새로 학습
```

C++로 설명하기 어렵다는 이유로 개념을 생략하거나 C++ 형태로 왜곡하지 않는다.

---

## 8. 언어별 비교는 문법 표가 아니라 의미론적 질문으로 정리한다

여러 언어를 비교할 때 `문법 A ↔ 문법 B` 대응표만 만들지 않는다.

먼저 비교 질문을 정한다.

```text
값과 상태
→ 복사되는가, 공유되는가, 이동되는가?

함수와 환경
→ 외부 상태를 어떻게 Capture하고 얼마나 오래 유지하는가?

다형성
→ 공통 계약을 어떻게 표현하고 호출 대상을 언제 결정하는가?

실패
→ 실패를 별도 제어 흐름, 반환값, 타입 중 무엇으로 표현하는가?

메모리
→ 객체와 자원의 Lifetime을 누가 추적하고 종료시키는가?

동시성·비동기
→ 실행 단위의 상태를 누가 저장하고 언제 다시 실행하는가?
```

그다음 C++, Java, JavaScript, Go, Rust 등의 선택을 같은 질문 위에 놓고 비교한다.

---

## 9. 기술사 학습에서는 언어 자체보다 재사용 가능한 설명 구조를 남긴다

정보관리기술사 세부학습의 목적은 특정 언어를 숙련하는 것이 아니다.

프로그래밍 언어 개념을 학습할 때는 다음을 다시 도출할 수 있어야 한다.

```text
이 개념은 어떤 문제를 해결하는가?
        ↓
언어와 무관한 핵심 의미론은 무엇인가?
        ↓
C++에서는 어떤 메커니즘으로 이해할 수 있는가?
        ↓
다른 언어는 같은 문제를 어떻게 다르게 해결하는가?
        ↓
그 차이가 타입·Lifetime·성능·안전성·실행 모델에 어떤 영향을 주는가?
```

특정 언어 문법을 많이 나열하는 것보다 **새로운 언어를 보더라도 기존 개념에 연결해서 설명할 수 있는 상태**를 목표로 한다.

---

## 10. 학습 중 새 용어를 만났을 때의 기본 순서

프로그래밍 언어의 낯선 용어를 만났을 때 다음 순서로 확인한다.

```text
새 용어 발견
   ↓
1. 이것이 해결하는 문제는 무엇인가?
   ↓
2. 이미 알고 있는 언어 공통 개념인가?
   ↓
3. C++에서는 무엇으로 풀어볼 수 있는가?
   ↓
4. 어디까지 비슷하고 어디서 달라지는가?
   ↓
5. 기존 개념군 문서에 포함할 수 있는가?
   ↓
6. 독립적인 의미론이 있을 때만 새 학습 단위로 분리
```

이 순서를 통해 언어별 Keyword가 늘어날수록 파일과 암기 항목이 함께 폭증하는 것을 피하고, **기존 개념 구조에 새 언어의 차이를 축적한다.**
