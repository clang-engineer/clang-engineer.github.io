# 프로그래밍 언어 의미론 — 실패·메모리·실행·다형성·모듈

> 연결: [[../../개념지도/05-소프트웨어-공학/00-소프트웨어-공학-개념지도|소프트웨어 공학 개념지도]]
>
> 성격: `99-*` 보충학습. 특정 언어 문법을 외우기보다 여러 언어에서 반복되는 의미론을 비교해 객체지향·설계·동시성·자원관리·모듈 구조 이해를 보강한다.

## 1. 먼저 다섯 질문으로 나눈다

프로그래밍 언어 기능을 이름으로 외우면 언어를 바꿀 때 다시 처음부터 배우기 쉽다. 먼저 언어를 가로지르는 질문을 잡는다.

```text
실패와 부재
→ 정상 값이 아닌 상태를 어떻게 표현하고 전달하는가?

메모리·값·불변
→ 값의 수명과 소유·복사·공유·변경을 어떻게 통제하는가?

함수·실행·상태
→ 함수가 환경을 어떻게 보존하고 계산을 언제 수행하는가?

타입 추상화와 디스패치
→ 여러 타입을 하나의 코드로 다루고 호출 대상을 어떻게 선택하는가?

모듈·의존관계
→ 코드 단위 사이의 의존관계를 언제 확정하고 무엇을 연결하는가?
```

이 다섯 축은 발전 단계가 아니라 서로 다른 분류축이다.

## 2. 실패와 부재 — Exception · Error Value · Result · Option

### 2.1 실패 전달 방식

```text
Exception
→ 정상 반환 경로와 별도 제어 흐름으로 실패 전파

Error Value
→ 실패도 반환값으로 명시적으로 전달

Result Type
→ 성공/실패를 타입의 Variant로 표현
```

| 모델 | 대표 언어 | 강점 | 주의점 |
|---|---|---|---|
| Exception | Java, C++ 등 | 정상 흐름과 오류 처리 분리, Stack 전파 | 숨은 제어 흐름·Catch 범위가 넓어질 수 있음 |
| Error Value | Go 등 | 실패가 함수 Signature와 호출부에 드러남 | 반복 처리와 무시 위험 |
| Result | Rust 등 | 성공/실패 처리를 타입으로 강제 | 조합 문법과 타입 이해 필요 |

어느 모델이 절대 우월한 것이 아니라 **실패를 호출 계약에 얼마나 명시적으로 드러내고, 전파 비용을 어디에 둘 것인지**의 Trade-off다.

### 2.2 Null Safety — 실패와 부재는 다르다

```text
Result / Error
→ 연산이 실패함

Option / Nullable
→ 정상적으로 값이 없을 수 있음
```

`null`/`nil` 하나에 "없음"과 "실패"를 함께 실으면 호출자가 의미를 추론해야 한다. `Option<T>`·nullable type은 **부재 가능성을 타입에 드러내는 방식**이다.

핵심은 `null을 없애는 문법`이 아니라:

```text
값이 반드시 존재하는가?
├─ Yes → non-null 계약
└─ No  → 부재를 타입/계약으로 표현
```

## 3. 메모리 관리 — 누가 수명을 추적하는가

동적으로 만든 객체와 자원은 언젠가 정리해야 한다.

```text
명시적 관리 / RAII
→ 개발자와 타입 설계가 수명을 표현

GC
→ 런타임이 도달 가능성을 추적해 회수

Ownership
→ 컴파일러가 소유·빌림·수명 규칙을 정적으로 검사
```

| 모델 | 대표 | 핵심 |
|---|---|---|
| 명시적 관리 + RAII | C/C++ | 해제 시점 제어와 객체 수명 결합 |
| GC | Java, Go, Python, JavaScript | 일반 객체 Memory 회수를 Runtime이 담당 |
| Ownership | Rust | 소유권·Borrow 규칙을 Compile Time에 검사하고 Drop 경로 생성 |

GC가 있어도 File·Socket·Lock 같은 외부 자원은 별도 수명 관리가 필요하다.

C++의 `unique_ptr`과 Rust Ownership은 **단일 소유와 이동**이라는 직관은 비슷하지만 동일한 제도는 아니다.

```text
C++
→ 소유권 타입을 설계자가 선택

Rust
→ 소유권과 Borrow가 언어 전반의 기본 의미론
```

## 4. 값 · 참조 · 이동 — 대입할 때 무엇이 일어나는가

같은 `a = b` 모양이라도 언어와 타입에 따라 의미가 다르다.

```text
Value Semantics
→ 값을 독립적으로 복사

Reference Semantics
→ 같은 객체/저장소를 공유

Move Semantics / Ownership Transfer
→ 자원 또는 소유권을 새 바인딩으로 넘김
```

중요한 질문은 "Stack인가 Heap인가"보다 다음이다.

```text
대입/전달 후
→ 원본과 새 값은 독립적인가?
→ 같은 상태를 공유하는가?
→ 원본 사용이 계속 허용되는가?
```

C++ `std::move`는 실제 이동 자체가 아니라 rvalue 취급을 위한 표현 변환이고, Rust의 move는 언어 의미론상의 Ownership 이전이다.

## 5. 불변성 — 무엇이 바뀌지 않는가

불변성은 한 축이 아니다.

```text
Binding Immutability
→ 이름이 다른 값을 다시 가리킬 수 있는가

Object / Value Immutability
→ 객체 내부 상태가 바뀔 수 있는가

Reference / Access Immutability
→ 현재 접근 경로에서 변경이 허용되는가
```

예를 들어 C++ `const`, Rust `&T`, Kotlin `val`은 모두 "불변"과 관련되지만 보장 범위가 다르다.

불변성의 실질적 가치는:

- 상태 변화 지점 감소
- 추론 범위 축소
- 공유 상태에서 위험 감소
- API 계약 명확화

다만 Immutable Object를 만들기 위해 매번 큰 복사를 유발하면 성능 비용이 생길 수 있으므로 Persistent Data Structure·Copy-on-Write 같은 다른 설계와 연결된다.

## 6. Closure — 함수가 정의 환경을 기억한다

Closure는 **함수 + 그 함수가 정의된 Lexical Environment**다.

```text
함수 정의
  +
외부 변수 Capture
  ↓
Closure
  ↓
나중에 호출해도 정의 시점의 환경 관계 유지
```

언어마다 Capture 의미론이 다르다.

- C++: 값/참조 Capture를 명시
- JavaScript/Python: Lexical Scope의 Binding을 참조
- Go: 외부 변수를 Capture
- Rust: 사용 방식에 따라 `Fn` / `FnMut` / `FnOnce`와 소유권이 연결

따라서 "Closure는 외부 변수 값을 복사해 저장한다"처럼 일반화하지 않는다.

Closure가 중요한 이유는 Callback·Iterator·Async 작업에서 **행동과 필요한 상태를 하나의 값처럼 전달**할 수 있기 때문이다.

## 7. Iterator와 Lazy Evaluation — 순회와 실행 시점을 분리한다

두 개념은 자주 함께 쓰이지만 같은 축이 아니다.

```text
Iterator
→ 원소를 어떤 Interface로 하나씩 순회할까

Lazy Evaluation
→ 계산을 언제 실제로 수행할까
```

Iterator Pipeline:

```text
Source
→ map
→ filter
→ take
→ collect
```

Lazy Iterator에서는 중간 연산이 Pipeline만 구성하고 Terminal Operation이나 실제 원소 요청 시 계산할 수 있다.

장점:

- 불필요한 중간 Collection 감소
- 필요한 범위만 계산 가능
- 조합 가능한 데이터 처리 Pipeline

주의점:

- Side Effect가 있으면 실제 실행 시점이 예상과 달라질 수 있음
- Iterator 자체와 Lazy 여부를 동일시하면 안 됨

## 8. Parametric Polymorphism — 타입을 매개변수화한다

```text
하나의 Algorithm
+ Type Parameter T
→ 여러 Type에 재사용
```

C++ Template, Java Generic, Go Generic, Rust Generic은 같은 **매개변수 다형성** 문제에 답하지만 구현 전략과 제약 방식이 다르다.

대표 구현 전략:

```text
Monomorphization
→ 타입별 Code 생성
→ 빠른 Dispatch 가능, Code Size 증가 가능

Type Erasure / Dictionary 등
→ 공통 Representation 또는 Runtime Metadata 활용
→ Binary Size/Compile 비용과 Runtime 비용 Trade-off
```

Generic의 핵심은 "문법 `<T>`"가 아니라 **타입에 독립적인 알고리즘을 어떤 계약과 비용으로 재사용하는가**다.

## 9. Subtype Polymorphism과 Dynamic Dispatch

다형성에는 서로 다른 질문이 있다.

```text
Parametric Polymorphism
→ 타입을 매개변수화하는가?

Subtype Polymorphism
→ 여러 구체 타입을 공통 추상 타입으로 다루는가?

Dispatch
→ 실제 호출 대상을 언제 결정하는가?
```

C++ Virtual, Java Interface, Go Interface, Rust Trait Object는 비슷한 목적을 제공하지만 **추상 계약을 만족하는 규칙**이 다르다.

```text
C++ / Java
→ 명시적 상속·구현 관계

Go
→ Method Set이 맞으면 암묵적으로 Interface 만족

Rust
→ Trait 구현을 명시, Generic Bound와 dyn Trait를 각각 사용 가능
```

`T: Trait` 같은 정적 제약과 `dyn Trait` 같은 동적 Dispatch도 구분한다.

## 10. 모듈 시스템 — 의존관계를 언제 확정하고 무엇을 연결하는가

`require()`와 `import`를 단순히 두 문법으로 비교하면 핵심을 놓친다. 먼저 모듈 시스템이 답하는 질문을 본다.

```text
의존관계를 언제 알 수 있는가?
→ 실행 중 / 실행 전

무엇을 외부에 노출하는가?
→ 값 객체 / Binding

동적 로딩이 필요한가?
→ 동기 호출 / 비동기 import

정적 분석이 가능한가?
→ Bundling · Tree Shaking 가능성에 영향
```

### 10.1 CommonJS — 실행 흐름 중심

CommonJS의 `require()`는 일반 함수 호출처럼 실행 흐름 안에 놓일 수 있다.

```javascript
if (featureEnabled) {
  const feature = require('./feature');
  feature.run();
}
```

따라서 의존관계가 실제 실행 경로에 따라 결정될 수 있다.

```text
실행 흐름
  ↓
require()
  ↓
Resolve
  ↓
Load / Evaluate
  ↓
module.exports 반환
```

핵심은 `require`라는 문법이 아니라 **런타임 호출을 통해 모듈을 로드하고 `module.exports` 객체를 노출하는 모델**이라는 점이다.

### 10.2 ESM — 선언적 Module Graph 중심

ESM의 정적 `import` / `export`는 모듈 본문 평가 전에 의존관계를 연결할 수 있다.

```text
Module A
├─ import B
└─ import C
      ↓
Resolve / Link
      ↓
Evaluation
```

이 정적 구조는 Tooling이 Module Graph를 사전에 분석할 수 있는 기반이 된다. Bundler가 Tree Shaking을 시도하기 쉬운 이유도 여기에 있다.

다만 다음 등 다른 조건도 영향을 준다.

```text
Side Effect
Bundler 설정
Package Metadata
동적 접근
Build Mode
```

따라서 `ESM = 사용하지 않은 코드를 무조건 제거`라고 외우지 않는다.

### 10.3 정적 import와 동적 import()는 다르다

```text
정적 import
→ 선언적 Dependency
→ 모듈 그래프를 사전에 구성

동적 import()
→ 실행 중 Module 요청
→ Promise 기반 비동기 로딩
```

ESM을 단순히 `비동기 import`라고 설명하면 안 된다. 정적 `import`와 런타임 `import()`는 역할과 실행 시점이 다르다.

### 10.4 Export 값과 Live Binding

CommonJS는 `module.exports` 객체를 통해 값을 노출한다. ESM의 Named Import는 단순 객체 Destructuring과 같지 않고 **Exported Binding에 연결되는 Live Binding**이다.

```javascript
export let count = 0;
export function inc() {
  count++;
}
```

Importer가 `count`를 참조하면 Exporter의 갱신된 Binding을 관찰할 수 있다. 이 차이는 Circular Dependency와 Module Initialization을 이해할 때 중요하다.

### 10.5 비교축으로 다시 본다

| 비교축 | CommonJS | ESM |
|---|---|---|
| 대표 문법 | `require`, `module.exports` | `import`, `export` |
| 의존관계 | 실행 중 동적으로 결정 가능 | 정적 import는 실행 전 분석 가능 |
| Export 모델 | 객체 값 중심 | Export Binding |
| 동적 로딩 | `require()` | `import()` Promise |
| 정적 분석 | 상대적으로 어려움 | 구조적으로 유리 |
| Tree Shaking | Tooling 분석 제약이 큼 | 정적 구조가 중요한 기반 |

> 기억: **CommonJS는 실행 흐름 중심 Module Loading, ESM은 선언적 Module Graph 중심**이다.

Node.js의 `package.json type`, `.mjs`, `.cjs` 같은 구체 설정은 JavaScript/Node 실전 문서에서 다루고, 여기서는 모듈 모델의 공통 비교축만 보존한다.

## 11. 전체 관계

```text
프로그래밍 언어 의미론
│
├─ 실패·부재
│   ├─ Exception
│   ├─ Error Value
│   ├─ Result
│   └─ Option / Nullable
│
├─ 메모리·값·불변
│   ├─ Manual / RAII / GC / Ownership
│   ├─ Value / Reference / Move
│   └─ Binding / Object / Access Immutability
│
├─ 함수·상태
│   ├─ Closure
│   └─ Iterator ↔ Lazy Evaluation
│
├─ 타입 추상화·Dispatch
│   ├─ Parametric Polymorphism / Generics
│   ├─ Subtype Polymorphism
│   └─ Static / Dynamic Dispatch
│
└─ 모듈·의존관계
    ├─ Runtime Loading
    ├─ Static Module Graph
    ├─ Export Value / Binding
    └─ Static / Dynamic Loading
```

## 12. 학습 경계

이 문서는 특정 언어의 문법·API를 대체하지 않는다.

```text
공통 의미론
→ 이 99-* 문서에서 위치와 비교축 이해

언어별 실제 규칙
→ C++ / Go / Rust / JavaScript 등 해당 언어 학습에서 확인
```

기술사 본 학습에서는 객체지향·다형성·설계 원칙을 이해하기 위한 배경으로 사용하고, 언어별 상세 문법·Compiler·Loader 구현은 직접 출제 범위를 넘어가면 더 확장하지 않는다.

> **언어를 외우는 대신 "실패를 어떻게 표현하는가, 값의 수명을 누가 관리하는가, 대입에서 무엇을 공유하는가, 타입 추상화와 Dispatch를 어떻게 구현하는가, 모듈 의존관계를 언제 확정하는가"라는 질문으로 보면 서로 다른 언어의 기능을 같은 좌표 위에서 비교할 수 있다.**
