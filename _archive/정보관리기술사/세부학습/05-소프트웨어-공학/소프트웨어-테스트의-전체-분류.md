# 소프트웨어 테스트의 전체 분류

이 문서는 소프트웨어 테스트 용어를 한 줄의 계층으로 외우지 않고, **서로 다른 분류축을 분리해서 이해하는 것**을 목적으로 한다.

가장 먼저 잡을 핵심은 다음이다.

```text
정적 / 동적
= 실행 여부 기준

명세 / 구조 / 경험 기반
= 테스트 케이스를 어떻게 설계하는지 기준

Unit / Integration / System / Acceptance
= 어느 수준에서 테스트하는지 기준

Verification / Validation
= 무엇을 확인하려는지 관점
```

이 축들을 섞으면 `화이트박스 = 정적`, `Validation = 동적` 같은 잘못된 연결이 생긴다.

---

## 1. 왜 테스트 분류가 여러 개인가

하나의 테스트 활동은 여러 관점에서 동시에 설명할 수 있다.

예를 들어 개발자가 Unit Test를 실행하면서 내부 Branch를 기준으로 테스트 케이스를 만든다면:

```text
실행 여부      : 동적 테스트
설계 기준      : 구조 기반 테스트
테스트 수준    : Unit Test
목적 관점      : Verification에 기여
```

즉 하나의 테스트가 한 분류에만 속하는 것이 아니다.

이 점을 먼저 이해하면 전체 테스트 체계가 훨씬 덜 헷갈린다.

---

# 2. 실행 여부 기준: 정적 테스트와 동적 테스트

## 2.1 정적 테스트

정적 테스트는 소프트웨어를 실제 실행하지 않고 산출물·설계·Code 등을 확인한다.

```text
요구사항 문서
설계서
Source Code
테스트 설계서
        ↓
실행 없이 검토·분석
        ↓
결함·불일치·위험 조기 발견
```

정적 테스트의 중요한 장점은 **결함을 이른 단계에서 발견할 수 있다는 것**이다.

요구사항 오류를 Coding이 끝난 뒤 발견하면 설계와 구현을 함께 고쳐야 하지만, 요구사항 Review 단계에서 찾으면 수정 범위가 훨씬 작다.

### Review

Review는 사람이 산출물을 읽고 결함과 개선점을 찾는 넓은 활동이다.

Walkthrough와 Inspection도 넓게 보면 Review의 한 형태로 볼 수 있다.

### Walkthrough

작성자가 문서나 Code를 다른 사람에게 설명하면서 함께 검토한다.

```text
작성자 중심 설명
→ 참여자 질문
→ 결함·모호성·개선점 발견
```

공식 절차보다 **이해 공유와 결함 발견**에 무게가 있다.

예를 들어 설계자가 Sequence Diagram을 팀원에게 설명하면서:

```text
"여기서 결제 실패하면 어디로 가죠?"
```

라는 질문을 받아 누락 Flow를 발견하는 것이 Walkthrough의 전형적인 모습이다.

### Inspection

Inspection은 Walkthrough보다 공식적인 검토 방식이다.

일반적으로:

- 역할 분담
- 사전 준비
- Checklist
- Moderator
- 결함 기록
- 후속 조치

등의 절차를 둔다.

핵심 차이를 단순화하면:

```text
Walkthrough
= 작성자가 설명하며 함께 이해·검토

Inspection
= 정해진 역할과 절차로 공식적으로 결함 검출
```

둘 다 실행하지 않으므로 정적 테스트다.

### 정적 분석

사람이 문서를 읽는 Review와 달리 Tool을 이용해 Code나 산출물을 분석한다.

예:

- Coding Rule 위반
- 사용되지 않는 변수
- Data Flow 이상
- 복잡도
- 취약한 Pattern
- Dependency 문제

```text
Source Code
→ 정적 분석 Tool
→ 잠재 결함 / Rule 위반 / Metric
```

실행하지 않는다고 해서 단순한 문서 검토만 의미하는 것은 아니다.

---

## 2.2 동적 테스트

동적 테스트는 실제 실행 가능한 소프트웨어에 입력을 주고 결과를 확인한다.

```text
Input
→ 실행
→ Actual Result
→ Expected Result와 비교
→ Pass / Fail
```

실행하면서만 발견할 수 있는 문제들이 있다.

- 실제 Logic 오류
- Runtime Error
- Interface 동작 문제
- 성능 저하
- Resource 누수
- Timing 문제

정적 테스트와 동적 테스트는 경쟁 관계가 아니라 서로 보완한다.

```text
정적 테스트
→ 실행 전 결함 조기 발견

동적 테스트
→ 실제 실행 결과 확인
```

# 3. 테스트 케이스 설계 기준: 명세·구조·경험 기반

이 분류는 **소프트웨어를 실행하느냐가 아니라 테스트 케이스를 무엇을 보고 설계하느냐**의 기준이다.

## 3.1 명세 기반 테스트

요구사항과 입출력 명세를 보고 테스트 케이스를 설계한다.

내부 Code를 몰라도 가능하므로 흔히 Black-box Testing이라고 부른다.

예를 들어 나이 입력 범위가 `1~120`이라면 내부 구현을 보지 않고도 다음 테스트를 만들 수 있다.

```text
정상 값  : 20
경계 값  : 1, 120
경계 밖  : 0, 121
```

대표 기법:

- 동등분할
- 경계값 분석
- 결정표
- 상태전이
- Use Case 기반 테스트

### 동등분할

입력 공간을 같은 동작을 보일 것으로 기대되는 그룹으로 나누고 대표값을 선택한다.

모든 값을 테스트할 수 없으므로 **동일한 결과를 낼 가능성이 높은 집합을 대표값으로 줄이는 것**이다.

### 경계값 분석

결함은 경계에서 자주 발생하므로 범위의 시작·끝과 바로 바깥 값을 집중적으로 테스트한다.

```text
허용 범위: 1 ~ 120

0 / 1 / 2 / ... / 119 / 120 / 121
↑   ↑                         ↑    ↑
경계 주변 집중
```

## 3.2 구조 기반 테스트

Code의 내부 구조를 보고 테스트 케이스를 설계한다.

흔히 White-box Testing이라고 한다.

관심 대상:

- Statement
- Branch
- Condition
- Path
- Loop

예를 들어 다음 Code가 있다고 하자.

```text
if age >= 20:
    allow()
else:
    deny()
```

구조 기반 테스트에서는 `if`의 True와 False Branch가 모두 실행되도록 테스트 케이스를 만든다.

여기서 매우 중요한 점:

> **Code를 본다고 정적 테스트가 되는 것이 아니다.**

Code 구조를 보고 테스트 케이스를 설계한 뒤 실제 Program을 실행해 결과를 확인하므로 구조 기반 테스트는 대표적인 동적 테스트 기법이다.

### Coverage의 의미

Coverage는 Code 구조 중 얼마나 실행했는지를 나타낸다.

하지만 Coverage가 100%라고 해서 결함이 없다는 뜻은 아니다.

```text
Coverage 100%
≠
Requirement 100% 만족
≠
Bug 0개
```

존재하는 Code를 모두 실행했어도 **애초에 구현되지 않은 요구사항**은 Coverage로 발견하기 어렵다.

## 3.3 경험 기반 테스트

명세나 Code 구조만이 아니라 Tester의 경험과 과거 결함 Pattern을 이용한다.

- Error Guessing
- Exploratory Testing
- Checklist 기반 테스트

예를 들어 과거에 날짜 말일 처리에서 장애가 반복됐다면 명세에 특별히 강조되지 않아도:

```text
2월 28일 / 29일
월말
연말
윤년
```

등을 집중적으로 테스트할 수 있다.

# 4. 테스트 수준: 어디까지 묶어서 테스트하는가

## Unit Test

함수·Class·Module 등 작은 단위를 확인한다.

```text
작은 Logic 단위
→ 기대한 결과인가?
```

## Integration Test

여러 Module이나 Service가 결합될 때 Interface가 올바르게 동작하는지 본다.

```text
Module A
   ↕
Interface
   ↕
Module B
```

각 Module이 독립적으로 정상이어도 Interface 계약, Data Format, 호출 순서 문제 때문에 Integration 단계에서 실패할 수 있다.

## System Test

전체 시스템이 기능·비기능 요구사항을 만족하는지 확인한다.

예:

- 업무 기능
- 성능
- 보안
- 복구
- 호환성

## Acceptance Test

사용자·고객·발주자 관점에서 **실제 업무 목적과 인수 조건을 만족하는지** 확인한다.

System Test와 Acceptance Test가 비슷해 보이지만 관점이 다르다.

```text
System Test
= 시스템 요구사항을 충족하는가

Acceptance Test
= 사용자가 이 시스템을 받아들여 실제 목적에 사용할 수 있는가
```

테스트 수준 역시 명세/구조 기반과 독립된 축이다.

Unit Test에서도 Black-box Test와 White-box Test를 모두 사용할 수 있다.

# 5. Verification과 Validation

이 둘을 한국어로 모두 `검증`, `확인`처럼 번역하면서 특히 헷갈리기 쉽다.

## Verification

> **우리가 제품을 올바르게 만들고 있는가?**

```text
Are we building the product right?
```

요구사항·설계·구현이 정해진 규격과 일치하는지 보는 관점이다.

Review, Inspection, 정적 분석, 각종 동적 테스트가 Verification의 근거가 될 수 있다.

## Validation

> **우리가 올바른 제품을 만들고 있는가?**

```text
Are we building the right product?
```

실제 사용자의 요구와 업무 목적을 만족하는지 본다.

예를 들어 요구사항 문서에 적힌 기능을 완벽하게 구현했더라도 그 요구사항 자체가 사용자가 원하는 업무와 어긋나면:

```text
Verification은 통과할 수 있음
하지만 Validation은 실패 가능
```

### 정적 = Verification, 동적 = Validation인가?

아니다.

Verification / Validation은 **목적 관점**이고, 정적 / 동적은 **실행 여부 관점**이다.

따라서 단순 1:1 대응시키면 안 된다.

# 6. 전체 분류를 하나의 예제로 보기

예를 들어 로그인 기능을 테스트한다고 하자.

### 요구사항 Review

```text
실행 여부 : 정적
활동       : Review
목적       : Verification 중심
```

### Boundary Test

비밀번호 길이가 8~20자라는 명세를 보고 7, 8, 20, 21자를 실제 입력한다.

```text
실행 여부 : 동적
설계 기준 : 명세 기반
테스트 수준 : Unit 또는 System 상황에 따라 다름
```

### Branch Coverage Test

Login Logic의 성공/실패 Branch를 모두 실행한다.

```text
실행 여부 : 동적
설계 기준 : 구조 기반
테스트 수준 : Unit
```

### 사용자 인수 테스트

실제 사용자가 업무 Scenario대로 로그인부터 업무 처리까지 확인한다.

```text
실행 여부 : 동적
테스트 수준 : Acceptance
목적       : Validation 비중 큼
```

하나의 용어를 다른 축과 섞지 않는 것이 핵심이다.

# 7. 전체 관계

```text
품질 목표와 요구사항
        ↓
정적 활동
├─ Review
│  ├─ Walkthrough
│  └─ Inspection
└─ 정적 분석
        ↓
동적 테스트
├─ 명세 기반 / Black-box
├─ 구조 기반 / White-box
└─ 경험 기반
        ↓
테스트 수준
Unit → Integration → System → Acceptance
        ↓
Verification / Validation 관점에서 증거 종합
        ↓
결함 수정과 Process 개선
```

여기서 각 줄은 모두 같은 분류축이 아니다.

# 8. 처음 헷갈리기 쉬운 부분

```text
화이트박스 = 정적 테스트?
→ X
Code 구조를 보고 테스트를 설계하고 실제 실행하면 동적 테스트다.

블랙박스 = System Test?
→ X
Unit Test에서도 명세 기반 Black-box 방식이 가능하다.

Verification = 정적, Validation = 동적?
→ X
서로 다른 분류 기준이다.

Coverage가 높으면 품질이 보장되는가?
→ X
실행된 구조의 비율이지 요구사항 완전성과 결함 부재를 보장하지 않는다.
```

# 9. 기술사 답안 포인트

테스트 분류 문제에서는 **먼저 분류축을 명시**하면 답안 구조가 안정된다.

```text
실행 여부
→ 정적 / 동적

테스트 설계 기준
→ 명세 / 구조 / 경험 기반

테스트 수준
→ Unit / Integration / System / Acceptance

목적 관점
→ Verification / Validation
```

비교 문제에서는 단순 정의보다:

```text
분류 기준
→ 대표 기법
→ 장점·한계
→ 서로의 관계
```

순으로 설명한다.

# 10. 압축 기억표

시험장이나 복습할 때는 먼저 다음 네 가지 질문으로 분류축을 복원한다.

```text
정적 / 동적
= 실행하나?

명세 / 구조 / 경험 기반
= 무엇을 보고 테스트 케이스를 만드나?

테스트 수준
= 어디까지 묶어서 보나?

Verification / Validation
= 무엇을 확인하려 하나?
```

더 짧게 줄이면 다음과 같다.

```text
실행 여부?   → 정적 / 동적
설계 기준?   → 명세 / 구조 / 경험
테스트 범위? → Unit / Integration / System / Acceptance
목적 관점?   → Verification / Validation
```

이 네 질문을 먼저 던지면 `화이트박스 = 정적`, `Validation = 동적`, `Black-box = System Test`처럼 서로 다른 축을 잘못 연결하는 실수를 줄일 수 있다.

# 11. 기억 흐름

```text
테스트 용어가 많다
        ↓
먼저 '무슨 기준으로 나눈 것인지' 확인
        ↓
실행 여부?       → 정적 / 동적
설계 기준?       → 명세 / 구조 / 경험
테스트 수준?     → Unit / Integration / System / Acceptance
목적 관점?       → Verification / Validation
        ↓
서로 다른 축을 섞지 않는다
```

가장 중요한 한 문장:

> **소프트웨어 테스트는 하나의 계층 구조가 아니라 여러 독립된 분류축이 겹쳐 있는 체계다.**
