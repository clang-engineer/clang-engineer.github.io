# DRY · KISS · YAGNI — 설계 원칙을 판단 도구로 쓰기

> 연결: [[../../개념지도/05-소프트웨어-공학/00-소프트웨어-공학-개념지도|소프트웨어 공학 개념지도]]
>
> 성격: `99-*` 보충학습. 모듈화·결합도·객체지향 설계원칙을 실제 변경 판단과 연결한다.

## 1. 세 원칙의 핵심

```text
DRY
→ 같은 지식이 여러 곳에서 따로 관리되지 않게 한다

KISS
→ 문제를 해결하는 데 필요하지 않은 복잡성을 줄인다

YAGNI
→ 아직 실제 요구가 없는 기능·추상화를 미리 만들지 않는다
```

세 원칙은 목표가 아니라 **변경 비용과 인지 복잡성을 줄이기 위한 판단 도구**다.

## 2. DRY — 코드 중복보다 지식 중복을 본다

같은 모양의 Code가 두 군데 있다고 무조건 합치지 않는다.

```text
겉모양이 같다
        ↓
같은 이유로 함께 바뀌는가?
├─ Yes → 하나의 지식이 중복됐을 가능성 → 통합 검토
└─ No  → 우연한 중복 가능성 → 분리 유지
```

잘못된 추상화로 서로 다른 변경 이유를 한 Module에 묶으면 결합도가 오히려 증가한다.

따라서 DRY의 질문은:

> **이 두 Code가 같은가?** 보다 **이 두 Code가 같은 지식을 표현하고 같은 이유로 바뀌는가?**

이다.

## 3. KISS — 짧은 Code보다 이해 비용을 줄인다

KISS는 함수 줄 수나 Class 수를 줄이라는 규칙이 아니다.

```text
단순성
= 독자가 현재 문제를 이해하기 위해 추적해야 하는
  상태·분기·간접 참조·추상 계층을 최소화하는 것
```

한 번만 쓰이는 짧은 Logic을 여러 Helper로 나눠 호출 흐름을 파편화하면 오히려 복잡해질 수 있다.

적용 질문:

- 현재 문제보다 일반화 범위가 지나치게 넓지 않은가?
- 이름을 따라 여러 파일을 이동해야만 흐름을 알 수 있는가?
- 영리한 표현보다 명백한 표현이 가능한가?
- 추상화가 실제 변경 지점을 줄이고 있는가?

## 4. YAGNI — 미래 가능성을 현재 구조에 미리 반영하지 않는다

```text
"나중에 필요할지도 모른다"
        ↓
Interface·Plugin·확장계층 선설계
        ↓
현재부터 유지해야 하는 구조 증가
```

두 번째 구현이 실제로 존재하지 않는데 교체 가능성을 위해 Interface를 먼저 만들거나, 단일 Tenant System에 미래 Multi-Tenant 추상화를 먼저 넣는 것은 현재 요구가 아닌 미래 추측에 비용을 지불하는 것이다.

YAGNI는 미래를 무시하라는 뜻이 아니다.

```text
미래 대비
≠ 모든 확장점 미리 생성

좋은 미래 대비
= 현재 구조를 단순하게 유지
  + Test와 Refactoring으로 변경 가능성 확보
```

## 5. 세 원칙은 충돌할 수 있다

| 충돌 | 위험 | 판단 기준 |
|---|---|---|
| DRY ↔ YAGNI | 중복 제거를 위해 미래 확장용 추상화를 만듦 | 현재 실제로 같은 지식이 여러 곳에 존재하는가 |
| DRY ↔ KISS | 공통화 후 간접 참조·결합도가 증가 | 통합이 실제 변경 비용을 줄이는가 |
| KISS ↔ 과도한 분리 | 작은 함수·Class가 많아 흐름이 파편화 | 인지 부하와 추적 거리가 줄었는가 |

원칙이 충돌하면 이름을 우선순위로 외우지 않고 **현재 변경 위험과 복잡도 비용**을 비교한다.

## 6. 모듈화·결합도와 연결

```text
변경 이유 식별
        ↓
같이 바뀌는 지식은 응집
        ↓
다른 이유로 바뀌는 지식은 분리
        ↓
필요한 만큼만 추상화
        ↓
변경 영향 최소화
```

- DRY는 진짜 지식 중복을 줄여 일관된 변경을 돕는다.
- KISS는 추상화와 간접성의 비용을 통제한다.
- YAGNI는 아직 존재하지 않는 변화축을 설계에 끌어들이지 않는다.

이 셋은 결국 **응집도는 높이고 불필요한 결합과 변경 면적은 줄이는 설계 판단**과 연결된다.

## 7. Refactoring과 연결

YAGNI를 지키면서도 미래 변경을 두려워하지 않을 수 있는 이유는 Refactoring과 Test 안전망 때문이다.

```text
현재 필요한 단순 구현
        ↓
두 번째 실제 요구 등장
        ↓
공통 변화축 확인
        ↓
Test 확보
        ↓
Refactoring
        ↓
필요한 추상화 도입
```

즉 처음부터 모든 변화를 예측하는 것이 아니라 **실제 변화가 드러났을 때 구조를 재조정할 수 있게 만든다.**

## 8. 한 번에 다시 떠올리기

```text
DRY
→ 같은 지식인가?

KISS
→ 지금 이해·유지에 필요한 최소 복잡도인가?

YAGNI
→ 실제 요구가 존재하는가?

세 질문의 공통 목적
→ 변경 비용과 불필요한 복잡성 감소
```

> **원칙을 적용했는데 Code가 더 결합되고 더 이해하기 어려워졌다면 원칙의 이름은 지켰어도 설계 목적은 실패한 것이다.**
