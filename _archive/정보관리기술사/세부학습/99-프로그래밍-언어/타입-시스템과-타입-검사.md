# 타입 시스템과 타입 검사 — Static · Dynamic · Nominal · Structural

> 학습 원칙: [`00-프로그래밍-언어-학습원칙.md`](00-프로그래밍-언어-학습원칙.md)
>
> 핵심 질문: **어떤 값에 어떤 연산을 해도 되는지 누가, 언제, 어떤 기준으로 판단하는가?**

---

## 1. 큰 그림

타입 시스템은 `int`, `string`, `class` 같은 타입 이름 목록이 아니다.

```text
값 / 표현식
   ↓
이 연산을 해도 되는가?
   ↓
Type Rule
   ↓
언제 확인하는가?
├─ Compile Time
└─ Runtime
   ↓
두 타입을 같은 계열로 볼 기준은 무엇인가?
├─ 이름/선언 관계
└─ 실제 구조/연산 가능성
```

핵심 질문은 다음이다.

```text
타입 오류를 언제 잡는가?
두 타입의 관계를 무엇으로 판단하는가?
변환을 얼마나 자동으로 허용하는가?
타입 정보가 Runtime에도 남는가?
```

---

## 2. C++ 기준점 — Static Type System

C++에서는 많은 타입 오류를 Compile Time에 잡는다.

```cpp
int x = 10;
std::string s = x; // 일반적으로 허용되지 않음
```

함수 호출도 Signature를 보고 검사한다.

```cpp
void print(int value);

print("hello"); // 타입 불일치
```

흐름은 단순하다.

```text
Source Code
   ↓
Compiler가 Type Check
   ↓
허용된 연산만 Code Generation
```

다만 C++도 `virtual`, RTTI, `dynamic_cast`처럼 Runtime에 타입 정보를 확인하는 기능이 있다. `정적 타입 언어 = Runtime 타입 정보가 없다`고 생각하면 안 된다.

---

## 3. Static Typing과 Dynamic Typing

### Static Typing

```text
주요 타입 검사를 실행 전에 수행
```

대표:

- C++
- Java
- Rust
- Go

장점:

- 많은 타입 오류를 실행 전에 잡을 수 있다.
- IDE, Refactoring 같은 Tooling에 유리하다.
- Compiler가 타입 정보를 최적화에 활용할 수 있다.

Trade-off:

- 타입 선언·추론·제약 규칙을 이해해야 한다.
- 매우 동적인 구조를 표현할 때 별도 추상화가 필요할 수 있다.

### Dynamic Typing

```text
Runtime 값과 실제 연산을 바탕으로 타입을 확인
```

JavaScript:

```javascript
let x = 10;
x = "hello";
```

Python:

```python
x = 10
x = "hello"
```

장점:

- 코드를 유연하게 작성하고 구조를 바꾸기 쉽다.
- Runtime 객체 구조를 동적으로 다루기 쉽다.

Trade-off:

- 일부 오류는 해당 실행 경로를 실제로 지나야 드러난다.
- 규모가 커질수록 Type Annotation이나 별도 Tooling이 중요해질 수 있다.

---

## 4. 변수에 타입이 있는가, 값에 타입이 있는가

정적 언어에서는 변수나 표현식에 Compile Time 타입이 강하게 연결된다.

```cpp
int x = 10;
```

```text
x의 Static Type
→ int
```

동적 언어에서는 이름이 특정 타입에 고정되지 않고, 이름이 현재 어떤 값을 가리키는지로 이해하면 쉽다.

```javascript
let x = 10;
x = "hello";
```

```text
Binding x
→ 처음에는 Number 값
→ 이후에는 String 값을 가리킬 수 있음
```

그렇다고 `동적 타입 = 타입이 없다`는 뜻은 아니다. 값과 연산에 대한 타입 규칙은 여전히 존재한다.

---

## 5. Type Inference — 타입을 안 썼다고 Dynamic Typing은 아니다

C++:

```cpp
auto x = 10;
```

Rust:

```rust
let x = 10;
```

직접 타입 이름을 적지 않았지만 Compiler가 문맥을 보고 타입을 정한다.

```text
Type Annotation 생략
≠ Dynamic Typing

Type Inference
→ Compiler가 문맥에서 Static Type을 추론
```

이 경계는 꼭 구분한다.

---

## 6. Nominal Typing — 이름과 선언 관계를 본다

Nominal Typing에서는 타입 이름과 명시적인 상속·구현 관계가 중요하다.

Java:

```java
class Dog implements Animal { ... }
```

C++:

```cpp
struct Dog : Animal { ... };
```

```text
Dog를 Animal로 볼 수 있는가?
→ 명시적 상속/구현 관계 확인
```

구조가 우연히 같아도 선언 관계가 없으면 같은 타입 계열로 보지 않을 수 있다.

---

## 7. Structural Typing — 필요한 구조가 맞는지를 본다

Go Interface가 좋은 예다.

```go
type Speaker interface {
    Speak()
}
```

어떤 타입이 `Speak()` Method를 제공하면 `implements Speaker`라고 따로 선언하지 않아도 Interface를 만족할 수 있다.

```text
타입 이름이 무엇인가?
보다
필요한 Method Set을 갖췄는가?
```

TypeScript도 Structural Typing의 대표 사례다.

C++ Template도 필요한 연산이 가능한지를 Compile Time에 확인한다는 점에서는 비슷한 직관을 주지만, 언어 차원의 Structural Type System과 완전히 같은 것은 아니다.

---

## 8. Duck Typing — 필요한 연산이 실제로 되면 사용한다

Python에서는 다음처럼 명시적인 Interface 없이도 코드를 작성할 수 있다.

```python
def run(x):
    x.speak()
```

중요한 건 `x`가 어떤 Interface를 상속했는지가 아니라 실제로 `speak()`를 실행할 수 있는가다.

```text
Nominal
→ "어떤 타입이라고 선언했는가?"

Structural
→ "필요한 구조를 갖췄는가?"

Duck Typing
→ "필요한 연산이 실제로 되는가?"
```

Structural Typing과 Duck Typing은 관련 있지만 검사 시점과 언어 규칙이 다를 수 있으므로 같은 개념으로 묶지 않는다.

---

## 9. 강한 타입 / 약한 타입이라는 표현은 조심해서 쓴다

`Strong Typing`, `Weak Typing`은 문헌마다 뜻이 달라 단독 분류 기준으로 쓰기 어렵다.

대신 구체적인 동작을 묻는다.

```text
암시적 Type Conversion을 얼마나 허용하는가?
서로 다른 타입끼리 연산하면 어떻게 처리하는가?
Runtime에 자동 Coercion이 일어나는가?
타입 오류를 언제 잡는가?
```

JavaScript:

```javascript
"5" + 1 // "51"
"5" - 1 // 4
```

이런 동작을 단순히 "약한 타입"이라고 외우기보다 **연산자마다 어떤 Type Coercion 규칙이 적용되는지** 보는 편이 정확하다.

---

## 10. Type Conversion — 자동 변환과 명시적 변환

C++:

```cpp
double d = 10; // implicit conversion
int x = static_cast<int>(d); // explicit conversion
```

핵심 질문:

```text
어떤 변환을 자동으로 허용하는가?
정보가 손실될 수 있는가?
Runtime 검사나 실패가 필요한가?
```

타입 안전성은 이런 Conversion 규칙과도 깊게 연결된다.

---

## 11. Sum Type와 Product Type

타입을 조합 방식으로 보면 여러 언어 기능이 한 번에 정리된다.

### Product Type

여러 값을 동시에 가진다.

```cpp
struct Point {
    int x;
    int y;
};
```

```text
Point
= x AND y
```

### Sum Type

여러 경우 중 하나를 가진다.

```rust
enum Result<T, E> {
    Ok(T),
    Err(E),
}
```

```text
Result
= Ok OR Err
```

C++에서는 `std::variant`를 떠올리면 이해하기 쉽다.

이 관점은 `Result`, `Option`, AST, State Machine을 이해할 때 도움이 된다. 여기서는 타입 구조를 이해하는 데 필요한 수준까지만 다룬다.

---

## 12. Runtime Type Information과 Reflection

정적 타입 언어도 Runtime에 타입 정보를 일부 남길 수 있다.

C++:

```cpp
dynamic_cast<Derived*>(base);
typeid(obj);
```

Java:

```text
Class Metadata
Reflection API
```

핵심은 다음과 같다.

```text
Compile Time Type 정보
≠ Runtime Type Metadata
```

Runtime에 어떤 정보가 남고, 그 정보를 얼마나 활용할 수 있는지는 언어와 Runtime마다 다르다.

## 13. 타입 시스템은 Generic과 다형성의 기반이 된다

```text
타입 시스템
  ↓
어떤 연산과 타입 관계를 허용할지 결정
  ↓
Generic Constraint
Subtype 관계
Interface / Trait 만족
Overload Resolution
Dispatch 가능 범위
```

따라서 Generic과 다형성을 이해하려면 그 언어가 **타입 관계를 어떤 기준으로 판단하는지** 함께 봐야 한다.

## 14. 기술사 관점의 비교축

| 비교축 | 질문 |
|---|---|
| 검사 시점 | Compile Time인가 Runtime인가? |
| 타입 관계 | Nominal인가 Structural인가? |
| 추론 | Type Annotation 없이 얼마나 추론하는가? |
| 변환 | 암시적 Conversion/Coercion을 얼마나 허용하는가? |
| Runtime 정보 | Reflection/RTTI를 얼마나 제공하는가? |
| 추상화 | Generic·Interface·Trait와 어떻게 연결되는가? |

## 15. 기억·인출

```text
Static Typing
= 주로 실행 전에 Type Check

Dynamic Typing
= Runtime 값과 연산에서 Type Check

Type Inference
= 타입을 안 쓰는 것이 아니라 Compiler가 추론

Nominal
= 이름/선언 관계가 중요

Structural
= 필요한 구조가 맞으면 됨

Duck Typing
= 필요한 연산이 실제로 되면 사용
```

핵심 문장:

> **타입 시스템은 값에 라벨을 붙이는 기능이 아니다. 어떤 값에 어떤 연산을 허용하고, 서로 다른 타입을 어떤 관계로 인정할지 정하는 규칙 체계다.**
