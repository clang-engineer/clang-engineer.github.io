# 실패와 부재 처리 — Exception · Error Value · Result · Option

> 학습 원칙: [`00-프로그래밍-언어-학습원칙.md`](00-프로그래밍-언어-학습원칙.md)
>
> 핵심 질문: **함수가 정상 값을 만들지 못했거나, 정상적으로 값이 없을 수 있을 때 그 상태를 어떻게 표현하고 호출자에게 전달하는가?**

---

## 1. 큰 그림

실패와 부재는 같은 문제가 아니다.

```text
정상 결과가 없음
├─ 연산이 실패함
│  ├─ Exception
│  ├─ Error Value
│  └─ Result Type
│
└─ 정상적으로 값이 없을 수 있음
   ├─ null / nil
   └─ Option / Optional / Nullable
```

먼저 다음 두 질문을 구분한다.

```text
실패인가?
→ 정상 처리 과정이 완료되지 못함

부재인가?
→ 정상 결과로 값이 없을 수 있음
```

---

## 2. C++ 기준점 — Exception과 Error Code

C++에서는 대표적으로 두 방식을 볼 수 있다.

### Exception

```cpp
Value load() {
    if (failed()) {
        throw Error{};
    }
    return value;
}
```

```text
정상 반환 경로
→ Value

실패 경로
→ throw
→ Stack을 따라 전파
→ catch 경계에서 처리
```

### Error Code

```cpp
bool load(Value& out, ErrorCode& err);
```

또는:

```cpp
std::pair<Value, ErrorCode> load();
```

```text
정상/실패를 반환 계약 안에 직접 표현
```

두 방식의 차이는 단순 문법이 아니라 **실패 경로를 호출부에 얼마나 명시적으로 드러내는가**다.

---

## 3. Exception — 정상 흐름과 실패 흐름을 분리한다

Exception의 핵심은 실패를 일반 반환값과 다른 제어 흐름으로 전달하는 것이다.

```text
A()
 ↓
B()
 ↓
C()에서 throw
 ↓
B 정상 흐름 중단
 ↓
A의 catch에서 처리
```

장점:

- 실패를 여러 호출 계층 위로 쉽게 전파
- 정상 코드와 오류 처리 코드를 분리 가능

Trade-off:

- 함수 Signature만 보고 어떤 Exception이 발생하는지 모두 알기 어려울 수 있음
- 제어 흐름이 눈에 덜 보일 수 있음
- Resource 정리가 안전해야 함

C++에서는 이 때문에 RAII가 중요하다.

```cpp
void f() {
    Resource r;
    g(); // throw 가능
} // Stack Unwinding 중 r의 Destructor 호출
```

---

## 4. Error Value — 실패도 일반 값으로 전달한다

Go가 대표적이다.

```go
value, err := load()
if err != nil {
    return err
}
```

공통 구조:

```text
함수 반환
├─ 정상 값
└─ 오류 값
```

장점:

- 실패 가능성이 호출부에 명시적으로 보임
- 일반 제어 흐름으로 처리 가능

Trade-off:

- 반복적인 오류 검사 코드
- 개발자가 오류를 무시할 수 있음
- 값과 오류의 조합 규칙을 일관되게 설계해야 함

---

## 5. Result Type — 성공/실패를 타입의 Variant로 표현한다

Rust:

```rust
fn load() -> Result<Value, Error> {
    ...
}
```

개념적으로:

```text
Result<Value, Error>
├─ Ok(Value)
└─ Err(Error)
```

C++ 관점에서는 Tagged Union / `std::variant` 또는 `std::expected`를 떠올리면 이해하기 쉽다.

```cpp
std::expected<Value, Error> load();
```

핵심은:

> **함수의 정상/실패 가능성을 반환 타입 자체에 포함시킨다.**

이다.

---

## 6. Exception과 Result의 차이

```text
Exception
→ 실패 시 별도 제어 흐름으로 점프

Result
→ 실패도 반환값의 한 Variant
```

따라서 호출자 관점에서:

```text
Exception
→ catch하지 않아도 더 위로 전파될 수 있음

Result
→ 반환값을 다루는 과정에서 성공/실패 분기 필요
```

어느 한쪽이 절대 우월한 것이 아니라 **API 계약의 명시성, 전파 편의성, 코드량, Runtime 비용, 언어 생태계 관례**의 Trade-off다.

---

## 7. 부재 — 값이 없는 것이 오류는 아닐 수 있다

예:

```text
사용자 검색
→ 검색 결과 없음
```

이게 시스템 실패는 아닐 수 있다.

```text
실패
→ DB 연결 실패

부재
→ 조건에 맞는 Row가 없음
```

이 둘을 같은 `null` 하나로 표현하면 호출자가 의미를 추론해야 한다.

---

## 8. Option / Optional — 부재 가능성을 타입에 드러낸다

Rust:

```rust
Option<T>
├─ Some(T)
└─ None
```

C++:

```cpp
std::optional<T>
```

Java:

```java
Optional<T>
```

공통 질문:

```text
값이 반드시 존재하는가?
├─ Yes → T
└─ No  → Optional / Option / Nullable
```

핵심은 `null`을 무조건 없애는 것이 아니라 **부재 가능성을 계약에 드러내는 것**이다.

---

## 9. null / nullptr / nil은 같은 의미로 보지 않는다

C++ `nullptr`, Java `null`, JavaScript `null`, Python `None`, Go `nil`은 비슷한 역할이 있지만 타입 시스템과 허용 범위가 다르다.

특히 JavaScript에는 `null`과 `undefined`가 함께 존재한다.

```text
null
→ 의도적으로 값이 없음을 표현하는 경우에 주로 사용

undefined
→ 값이 아직 지정되지 않았거나 존재하지 않는 상태에 자주 등장
```

언어마다 의미론이 다르므로 단순 대응표로 끝내지 않는다.

---

## 10. Error Propagation — 실패를 위로 넘기는 방식

언어마다 실패 전파 문법이 다르다.

```text
C++
→ throw / catch

Go
→ if err != nil { return err }

Rust
→ Result + ?

Java
→ Exception / checked·unchecked 계열
```

핵심 질문은 같다.

> **현재 함수가 처리하지 못하는 실패를 호출자에게 어떤 계약으로 넘길 것인가?**

---

## 11. Error와 Panic/Fatal은 구분한다

일반 복구 가능한 실패와 프로그램 계약 위반/치명적 상태는 같은 축이 아닐 수 있다.

```text
Recoverable Error
→ 호출자가 처리하거나 상위로 전달 가능

Panic / Assertion / Fatal
→ 정상 계약이 깨졌거나 계속 실행하기 어렵다고 판단
```

Go `panic`, Rust `panic!`, C++ `assert`/terminate 계열은 일반적인 오류 반환과 같은 용도로 사용하지 않는다.

---

## 12. 기술사 관점의 비교축

| 비교축 | 질문 |
|---|---|
| 명시성 | 함수 Signature에 실패 가능성이 보이는가? |
| 전파 | 실패를 여러 계층 위로 넘기기 쉬운가? |
| 강제성 | 호출자가 실패 처리를 무시하기 쉬운가? |
| 제어 흐름 | 정상 흐름과 실패 흐름이 분리되는가? |
| 조합성 | 여러 연산의 성공/실패를 연결하기 쉬운가? |
| 자원 정리 | 실패 중간에도 Resource 정리가 안전한가? |

---

## 13. 기억·인출

```text
Exception
= 실패를 별도 제어 흐름으로 던짐

Error Value
= 실패도 일반 반환값

Result
= 성공/실패를 타입 Variant로 표현

Option
= 정상적으로 값이 없을 수 있음을 타입에 표현
```

핵심 문장:

> **실패는 연산이 완료되지 못한 상태이고, 부재는 정상 결과로 값이 없을 수 있는 상태다. 언어는 이 둘을 제어 흐름, 반환값, 타입 계약 중 어디에 드러낼지 서로 다르게 선택한다.**
