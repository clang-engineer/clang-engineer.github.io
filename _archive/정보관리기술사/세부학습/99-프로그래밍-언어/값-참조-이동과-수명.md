# 값 · 참조 · 이동과 Lifetime — Value Semantics · Reference Semantics · Move · Ownership

> 학습 원칙: [`00-프로그래밍-언어-학습원칙.md`](00-프로그래밍-언어-학습원칙.md)
>
> 핵심 질문: **값을 대입하거나 함수에 넘겼을 때 무엇이 넘어가고, 전달 전후의 값은 어떤 관계가 되며, 누가 자원을 소유하고 언제까지 안전하게 사용할 수 있는가?**

---

## 1. 큰 그림 — 값 전달을 네 가지 질문으로 본다

`copy`, `reference`, `move`, `ownership`, `borrow`, `lifetime`, `GC`를 각각 따로 외우기보다 먼저 다음 네 질문으로 위치를 잡는다.

```text
1. 무엇이 넘어가는가?
├─ 값
├─ 참조
└─ 소유권

2. 전달한 뒤 둘의 관계는 어떻게 되는가?
├─ 서로 독립
├─ 같은 상태를 공유
└─ 원본 사용이 제한됨

3. 누가 자원을 소유하고 마지막 정리를 책임지는가?
├─ 명시적 관리
├─ RAII / Ownership
└─ GC

4. 얼마나 오래 안전하게 사용할 수 있는가?
├─ Lifetime
├─ Borrow / Reference
└─ Dangling 여부
```

이 네 질문은 서로 독립된 분류라기보다 같은 값을 서로 다른 관점에서 보는 축이다.

```text
Value / Reference
→ 무엇이 넘어가고, 전달 뒤 상태를 공유하는가?

Copy / Move
→ 값을 어떤 방식으로 전달하는가?

Ownership / GC
→ 누가 마지막 정리를 책임지는가?

Borrow / Lifetime
→ 소유하지 않는 참조를 언제까지 안전하게 쓸 수 있는가?
```

같은 `a = b` 문장도 언어와 타입에 따라 이 네 질문의 답이 달라진다.

```text
대입 / 전달 / 반환
      ↓
무엇이 넘어가는가?
      ↓
원본과 새 값은 독립인가, 같은 상태를 공유하는가?
      ↓
소유권은 누구에게 있는가?
      ↓
참조 대상은 언제까지 살아 있어야 하는가?
```

> **Stack/Heap부터 외우기보다 값의 관계 → 소유권 → Lifetime 순서로 내려가면 언어가 달라져도 같은 질문을 다시 쓸 수 있다.**

---

## 2. C++ 기준점 — 값과 객체 Lifetime이 눈에 잘 보인다

```cpp
int a = 10;
int b = a;
```

`b`는 `a`와 독립된 값이다.

```text
a = 10
b = 10
```

`b`를 바꿔도 `a`는 바뀌지 않는다.

반면:

```cpp
int a = 10;
int& r = a;
```

`r`은 `a`를 새로 복사한 값이 아니라 같은 객체를 가리키는 Alias다.

```text
r
 ↓
a 객체
```

그래서 다음 질문이 중요해진다.

> **`r`을 쓸 때 `a`가 아직 살아 있는가?**

이게 Lifetime 문제다.

---

## 3. Value Semantics — 전달 뒤 상태가 독립적인가

Value Semantics의 핵심은 단순히 "복사한다"가 아니라, **대입이나 전달 뒤 두 값이 논리적으로 서로 독립된 상태를 갖는가**에 있다.

```cpp
std::string a = "hello";
std::string b = a;

b += " world";
```

논리적으로 `a`와 `b`는 별도 값이다.

```text
Value Semantics
→ 전달 뒤 각 값이 독립적으로 변경 가능
→ 한쪽의 상태 변화가 다른 쪽에 바로 반영되지 않음
```

이 독립성은 Copy로 만들 수도 있고 Move를 통해 새 객체가 자원을 이어받는 방식으로 만들 수도 있다. 따라서 `Value Semantics = Copy`로 단순화하지 않는다.

내부적으로 Copy-on-Write나 공유 최적화를 쓰더라도 겉에서 값처럼 보일 수 있다. **메모리 안에서 어떻게 저장하는지와 언어 수준에서 어떤 의미로 보이는지는 구분한다.**

---

## 4. Reference Semantics — 같은 객체 상태를 함께 보는가

참조 의미론에서는 여러 이름이 같은 객체를 가리킬 수 있다.

```text
name A ─┐
        ├→ object
name B ─┘
```

한쪽에서 객체를 바꾸면 다른 쪽에서도 그 변경이 보일 수 있다.

JavaScript:

```javascript
const a = { value: 10 };
const b = a;

b.value = 20;
console.log(a.value); // 20
```

여기서는 객체 전체를 복사한 것이 아니라 `a`와 `b`가 같은 객체를 가리킨다.

C++에서는 Pointer, Reference, Smart Pointer 공유를 떠올리면 비슷한 직관을 얻을 수 있다.

---

## 5. Pointer, Reference, Object는 같은 것이 아니다

C++에서는 다음을 구분한다.

```text
Object
→ 실제 상태가 들어 있는 대상

Pointer
→ 객체 주소를 값으로 가짐

Reference
→ 기존 객체의 Alias

Smart Pointer
→ Pointer에 Ownership 정책을 함께 표현
```

다른 언어에서 "참조형"이라는 말을 봤다고 C++ `T&`와 같다고 생각하면 안 된다. 재바인딩, Null 가능성, GC와의 관계 등이 언어마다 다르다.

---

## 6. Copy와 Move — 값을 어떤 방식으로 넘기는가

값이 독립적인 관계를 만들더라도 새 값을 만드는 방식은 다를 수 있다.

```text
Copy
→ 원본을 유지한 채 새 값에 필요한 상태를 구성

Move
→ 원본이 가진 자원을 새 객체가 이어받도록 함
```

C++에서 큰 객체나 OS Resource를 매번 복사하면 비용이 크다.

```cpp
std::vector<int> a = make_big_vector();
std::vector<int> b = std::move(a);
```

다만 `std::move` 자체가 실제 자원을 옮기는 것은 아니다.

```cpp
std::move(a)
```

는 `a`를 rvalue로 취급하게 해 Move Constructor나 Move Assignment가 선택될 수 있게 만든다.

```text
std::move
≠ 실제 자원 이동

std::move
→ 이동 가능한 표현으로 바꿈
→ 실제 이동은 이후 호출되는 함수가 수행
```

---

## 7. Rust Move와 C++ std::move는 같은 개념이 아니다

Rust:

```rust
let a = String::from("hello");
let b = a;
```

일반적인 `String`에서는 Ownership이 `a`에서 `b`로 넘어가고 이후 `a`를 사용할 수 없다.

```text
C++
→ std::move는 표현을 rvalue로 바꿈
→ 실제 이동 뒤에도 moved-from 객체는 유효한 객체로 남음

Rust
→ Move 자체가 언어 차원의 Ownership 이전
→ 이전된 Binding 사용을 Compiler가 막음
```

따라서 Rust move는 C++ 이동 의미론으로 감을 잡을 수는 있지만 `std::move`와 같은 제도는 아니다.

---

## 8. Ownership — 누가 마지막 정리를 책임지는가

값이 어떻게 전달되는지와 별개로, 자원을 가진 객체에는 결국 다음 질문이 필요하다.

```text
누가 이 자원을 소유하는가?
      ↓
언제 소유가 끝나는가?
      ↓
누가 정리하는가?
```

C++:

```cpp
std::unique_ptr<Resource> p;
```

```text
unique_ptr
→ 한 객체가 단독 소유
→ Scope 종료 시 Destructor
→ Resource 해제
```

Rust:

```text
Binding이 Ownership을 가짐
→ Move / Borrow 규칙을 Compiler가 검사
→ Scope 종료 시 Drop
```

직관은 비슷하지만 C++에서는 Ownership 정책을 타입 설계자가 선택하고, Rust에서는 Ownership이 언어 전체의 기본 규칙이라는 차이가 있다.

---

## 9. Borrow / Reference — 소유권을 넘기지 않고 잠시 쓴다

Ownership을 가진 대상이 있다고 해서 사용할 때마다 소유권을 넘길 필요는 없다.

Rust의 Borrow는 C++ Reference를 떠올리면 일부 직관을 얻을 수 있다.

```rust
fn len(s: &String) -> usize {
    s.len()
}
```

```text
Ownership은 그대로 둠
→ 기존 값을 잠시 참조해서 사용
```

C++:

```cpp
size_t len(const std::string& s);
```

하지만 Rust는 Borrow Checker가 Alias와 Mutation, Lifetime 규칙을 Compile Time에 더 강하게 검사한다.

```text
C++ Reference
→ Lifetime 안전성을 개발자가 많이 책임

Rust Borrow
→ Borrow 규칙과 Lifetime 관계를 Compiler가 검사
```

---

## 10. Lifetime — 그 참조를 언제까지 안전하게 쓸 수 있는가

Lifetime은 객체나 참조가 단순히 "얼마나 오래 존재하는가"보다, **참조를 사용하는 시점에 대상이 여전히 유효한가**라는 질문으로 보는 편이 좋다.

C++에서 가장 직접적인 예:

```cpp
int& bad() {
    int x = 10;
    return x;
}
```

함수가 끝나면 `x`의 Lifetime도 끝난다.

```text
x 생성
 ↓
Reference 반환
 ↓
함수 종료
 ↓
x 파괴
 ↓
Reference가 더 이상 유효한 객체를 가리키지 않음
```

이런 Dangling Reference는 C++에서 개발자가 특히 주의해야 한다.

JavaScript 같은 GC 언어에서는 객체를 계속 참조하고 있으면 Runtime이 일반 객체를 회수하지 않는다.

하지만 GC가 있다고 모든 Lifetime 문제가 사라지는 것은 아니다.

- File
- Socket
- Lock
- Transaction
- Native Resource

같은 외부 자원은 별도의 종료 규칙이 필요하다.

---

## 11. Stack / Heap보다 먼저 값의 관계를 본다

흔히 다음처럼 외우기 쉽다.

```text
Value = Stack
Reference = Heap
```

하지만 정확하지 않다.

먼저 다음을 묻는다.

```text
무엇이 넘어가는가?
전달 뒤 두 값은 독립적인가?
같은 상태를 공유하는가?
누가 Ownership을 가지는가?
원본은 계속 쓸 수 있는가?
참조 대상은 언제까지 살아 있는가?
```

실제 Stack/Heap 배치는 Compiler Optimization, Escape Analysis, Runtime 구현 등에 따라 달라질 수 있다.

---

## 12. 상태를 공유하면 불변성이 중요해진다

Reference Semantics처럼 상태를 공유할 수 있는 구조에서는 "누가 바꿀 수 있는가"가 별도의 질문이 된다.

```text
Binding Immutability
→ 이름을 다른 값에 다시 묶을 수 있는가?

Object Immutability
→ 객체 내부 상태를 바꿀 수 있는가?

Access Immutability
→ 현재 참조 경로를 통해 바꿀 수 있는가?
```

C++ `const`, Rust `&T`, Kotlin `val`, JavaScript `const`는 모두 불변성과 관련 있지만 막는 범위가 다르다.

JavaScript:

```javascript
const obj = { value: 10 };
obj.value = 20; // 가능
```

`const`는 Binding 재대입을 막을 뿐 객체 자체를 Immutable하게 만들지는 않는다.

---

## 13. 메모리 관리 모델 — 누가 필요 여부를 판단하고 정리하는가

Ownership과 Lifetime을 누가 관리하는지를 보면 언어의 메모리 관리 모델도 같은 질문으로 비교할 수 있다.

```text
C / C++
→ 명시적 관리 + RAII

Java / Go / Python / JavaScript
→ 일반 객체는 GC가 Reachability를 보고 회수

Rust
→ Ownership / Borrow를 Compile Time에 검사 + Drop
```

세 모델 모두 결국 같은 질문에 답한다.

> **누가 객체가 아직 필요한지 판단하고, 언제 안전하게 정리하는가?**

## 14. 네 질문으로 다시 위치를 잡는다

| 상위 질문 | 연결되는 개념 | C++ 기준점 |
|---|---|---|
| 무엇이 넘어가는가? | Value / Reference / Ownership | Object / Reference / Smart Pointer |
| 전달 뒤 관계는? | Value Semantics / Reference Semantics / Move | Copy / Move / Alias |
| 누가 정리하는가? | Ownership / RAII / GC | Destructor / `unique_ptr` |
| 언제까지 안전한가? | Borrow / Lifetime / Dangling | Reference / Scope / Destructor |

세부 개념은 다시 다음처럼 정리할 수 있다.

| 개념 | 핵심 질문 | C++ 기준점 |
|---|---|---|
| Value Semantics | 전달 뒤 원본과 독립적인가? | 일반 객체의 독립된 값 |
| Reference Semantics | 같은 객체 상태를 공유하는가? | Pointer / Reference |
| Copy | 원본을 유지한 채 새 값을 만드는가? | Copy Constructor / Assignment |
| Move | 자원을 복사하지 않고 넘길 수 있는가? | Move Constructor / Assignment |
| Ownership | 누가 마지막 정리를 책임지는가? | RAII / `unique_ptr` |
| Borrow | 소유권을 넘기지 않고 사용할 수 있는가? | Reference가 일부 직관 제공 |
| Lifetime | 참조 대상이 언제까지 유효한가? | Scope / Destructor / Dangling |
| GC | 누가 일반 객체의 필요 여부를 추적하는가? | C++에는 기본 GC 없음 |

```text
누가 정리하는가?

언제까지 안전한가?
→ Lifetime / Borrow / Dangling
```

세부 개념으로 내려가면:

```text

Reference

Copy / Move
= 값을 어떤 방식으로 넘기는가?

Ownership
= 누가 마지막 정리를 책임지는가?

Lifetime
= 그 참조를 쓸 때 대상이 아직 살아 있는가?
```
