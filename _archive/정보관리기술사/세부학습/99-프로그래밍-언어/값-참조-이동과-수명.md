# 값 · 참조 · 이동과 Lifetime — Value Semantics · Reference Semantics · Move · Ownership

> 학습 원칙: [`00-프로그래밍-언어-학습원칙.md`](00-프로그래밍-언어-학습원칙.md)
>
> 핵심 질문: **값을 대입하거나 함수에 전달했을 때 무엇이 복사되고, 무엇이 공유되며, 누가 언제까지 살아 있어야 하는가?**

---

## 1. 큰 그림

같은 `a = b` 모양도 언어와 타입에 따라 의미가 다르다.

```text
대입 / 전달 / 반환
      ↓
무엇이 이동하는가?
├─ 값 자체
├─ 객체를 가리키는 참조
└─ 자원의 소유권
      ↓
원본과 새 값의 관계는?
├─ 독립
├─ 공유
└─ 원본 사용 제한
      ↓
Lifetime은 누가 보장하는가?
```

이 질문을 먼저 잡으면 `copy`, `reference`, `move`, `ownership`, `GC`, `borrow` 같은 용어가 하나의 축으로 정리된다.

---

## 2. C++ 기준점 — 값과 객체 Lifetime이 비교적 직접 보인다

```cpp
int a = 10;
int b = a;
```

`b`는 독립된 값이다.

```text
a = 10
b = 10
```

`b`를 바꿔도 `a`는 바뀌지 않는다.

반면:

```cpp
int a = 10;
int& r = a;
```

`r`은 `a`의 별도 복사본이 아니라 같은 객체를 참조한다.

```text
r
 ↓
a 객체
```

여기서부터 핵심 질문이 생긴다.

> **이 참조를 사용하는 동안 원본 객체가 살아 있는가?**

이게 Lifetime 문제다.

---

## 3. Value Semantics — 새 값이 독립되는가

Value Semantics는 대입·전달 후 새 값이 원본과 독립적인 상태를 갖는다는 직관이다.

```cpp
std::string a = "hello";
std::string b = a;

b += " world";
```

논리적으로 `a`와 `b`는 별도 값이다.

```text
Value Semantics
→ 새 값은 독립적으로 변경 가능
→ 복사 후 서로의 상태 변화가 직접 연결되지 않음
```

내부 구현이 Copy-on-Write나 공유 최적화를 사용하더라도 외부 의미론이 값처럼 보일 수 있다. 따라서 **메모리 내부 표현과 언어 수준 의미론을 구분**한다.

---

## 4. Reference Semantics — 같은 객체를 공유하는가

참조 의미론에서는 여러 이름이 같은 객체를 가리킬 수 있다.

```text
name A ─┐
        ├→ object
name B ─┘
```

한 경로에서 상태를 바꾸면 다른 경로에서도 변경이 보일 수 있다.

JavaScript 객체 예:

```javascript
const a = { value: 10 };
const b = a;

b.value = 20;
console.log(a.value); // 20
```

여기서 `a`와 `b`가 객체 전체를 독립 복사한 것이 아니다.

C++로 비슷한 직관을 만들면 Pointer/Reference/Smart Pointer 공유를 떠올릴 수 있다.

---

## 5. Pointer, Reference, Object는 같은 개념이 아니다

C++에서는 다음을 구분한다.

```text
Object
→ 실제 상태가 존재하는 대상

Pointer
→ 객체 주소를 값으로 가짐

Reference
→ 기존 객체에 대한 Alias

Smart Pointer
→ Pointer + Ownership 정책을 객체로 표현
```

다른 언어에서 "참조형"이라는 말을 볼 때 C++ `T&`와 동일하다고 생각하면 안 된다. 언어마다 Reference의 표현·재바인딩·Null 가능성·GC 관계가 다르다.

---

## 6. Move Semantics — 복사를 피하면서 자원을 넘긴다

C++에서 큰 객체나 OS Resource를 매번 복사하면 비용이 크다.

```cpp
std::vector<int> a = make_big_vector();
std::vector<int> b = std::move(a);
```

핵심 직관:

```text
복사
→ 새 자원을 다시 구성

이동
→ 기존 자원 소유 상태를 새 객체로 이전
```

하지만 `std::move` 자체가 실제 이동을 수행하는 것은 아니다.

```cpp
std::move(a)
```

는 `a`를 rvalue로 취급하게 해 Move Constructor/Move Assignment 선택을 가능하게 하는 표현 변환이다.

```text
std::move
≠ 실제 자원 이동

std::move
→ 이동 가능한 표현으로 바꿈
→ 이후 호출되는 함수가 실제 이동 수행 가능
```

---

## 7. Rust Move와 C++ std::move는 같은 개념이 아니다

Rust:

```rust
let a = String::from("hello");
let b = a;
```

일반적인 `String`에서는 `a`의 Ownership이 `b`로 Move되고 이후 `a` 사용이 제한된다.

```text
C++
→ 객체는 기본적으로 계속 존재
→ std::move는 이동 가능 표현으로 변환
→ moved-from 객체도 유효하지만 상태는 제한적으로만 가정

Rust
→ Move가 언어 차원의 Ownership 이전
→ 이전된 Binding 사용을 Compiler가 제한
```

따라서:

> Rust move는 C++ 이동 의미론을 떠올리면 이해하기 쉽지만, `std::move`가 언어 기본값이 된 것이라고 등치하지 않는다.

---

## 8. Ownership — 누가 정리 책임을 가지는가

동적 자원에는 결국 다음 질문이 필요하다.

```text
누가 이 자원을 소유하는가?
      ↓
언제 소유가 끝나는가?
      ↓
누가 정리하는가?
```

C++:

```cpp
std::unique_ptr<Resource> p;
```

```text
unique_ptr
→ 단일 소유
→ Scope 종료 시 Destructor
→ Resource 해제
```

Rust:

```text
Binding이 Ownership을 가짐
→ Move / Borrow 규칙을 Compiler가 검사
→ Scope 종료 시 Drop
```

비슷한 직관은 있지만 C++에서는 Ownership 정책을 타입 설계자가 선택하고, Rust에서는 Ownership이 언어 전반의 기본 규칙이라는 차이가 있다.

---

## 9. Borrow / Reference — 소유하지 않고 잠시 사용한다

Rust의 Borrow를 C++ Reference로 떠올리면 일부 직관을 얻을 수 있다.

```rust
fn len(s: &String) -> usize {
    s.len()
}
```

```text
Ownership 이전 없음
→ 기존 값을 잠시 참조
```

C++:

```cpp
size_t len(const std::string& s);
```

하지만 Rust Borrow Checker는 Alias와 Mutation 규칙을 Compile Time에 더 강하게 검사한다.

```text
C++ Reference
→ Lifetime 안전성 상당 부분을 개발자가 책임

Rust Borrow
→ Borrow 규칙과 Lifetime 관계를 Compiler가 정적으로 검사
```

---

## 10. Lifetime — 참조가 유효한 기간

C++에서 가장 직접적인 문제:

```cpp
int& bad() {
    int x = 10;
    return x;
}
```

함수가 끝나면 `x`의 Lifetime이 종료된다.

```text
x 생성
 ↓
Reference 반환
 ↓
함수 종료
 ↓
x 파괴
 ↓
Reference는 더 이상 유효한 객체를 가리키지 않음
```

이런 Dangling Reference는 C++에서 개발자가 크게 주의해야 한다.

JavaScript 같은 GC 언어에서는 객체를 참조하는 동안 Runtime이 일반 객체의 도달 가능성을 추적해 Lifetime을 연장할 수 있다.

하지만 GC가 있다고 모든 Lifetime 문제가 사라지는 것은 아니다.

- File
- Socket
- Lock
- Transaction
- Native Resource

같은 외부 자원은 별도의 종료 규칙이 필요하다.

---

## 11. Stack / Heap보다 먼저 의미론을 본다

초보 학습에서 흔히:

```text
Value = Stack
Reference = Heap
```

처럼 외우지만 정확하지 않다.

더 중요한 질문은:

```text
대입 후 값이 독립적인가?
같은 상태를 공유하는가?
누가 Ownership을 가지는가?
원본은 계속 사용 가능한가?
참조 대상은 언제까지 살아 있는가?
```

실제 Stack/Heap 배치는 Compiler Optimization, Escape Analysis, Runtime 구현 등에 따라 달라질 수 있다.

---

## 12. 불변성과도 연결된다

값을 공유하면 "누가 바꿀 수 있는가"가 중요해진다.

```text
Binding Immutability
→ 이름이 다른 값을 다시 가리킬 수 있는가?

Object Immutability
→ 객체 내부 상태가 바뀔 수 있는가?

Access Immutability
→ 현재 참조 경로를 통해 변경 가능한가?
```

C++ `const`, Rust `&T`, Kotlin `val`, JavaScript `const`는 모두 "불변"과 관련되지만 보장 범위가 다르다.

JavaScript:

```javascript
const obj = { value: 10 };
obj.value = 20; // 가능
```

`const`는 Binding 재대입을 막지만 객체 자체를 Immutable하게 만들지는 않는다.

---

## 13. 메모리 관리 모델과의 연결

```text
C / C++
→ 명시적 관리 + RAII

Java / Go / Python / JavaScript
→ 일반 객체는 GC가 Reachability 추적

Rust
→ Ownership / Borrow를 Compile Time에 검사 + Drop
```

세 모델의 핵심 질문은 같다.

> **누가 객체 Lifetime을 추적하고, 언제 안전하게 회수할 수 있다고 판단하는가?**

---

## 14. 개념 경계 정리

| 개념 | 핵심 질문 | C++ 기준점 |
|---|---|---|
| Value Semantics | 새 값이 원본과 독립적인가? | 일반 객체 복사 |
| Reference Semantics | 같은 객체 상태를 공유하는가? | Pointer / Reference |
| Move Semantics | 자원을 복사하지 않고 넘길 수 있는가? | Move Constructor / Assignment |
| Ownership | 누가 정리 책임을 갖는가? | RAII / `unique_ptr` |
| Borrow | 소유권 이전 없이 사용할 수 있는가? | Reference가 일부 직관 제공 |
| Lifetime | 참조 대상이 언제까지 유효한가? | Scope / Destructor / Dangling |
| GC | 누가 일반 객체 도달 가능성을 추적하는가? | C++에는 기본 GC 없음 |

---

## 15. 기억·인출

```text
값
= 복사 후 독립적인가?

참조
= 같은 상태를 함께 보는가?

Move
= 복사 대신 자원을 넘기는가?

Ownership
= 누가 마지막 정리를 책임지는가?

Lifetime
= 그 참조를 쓸 때 대상이 아직 살아 있는가?
```

핵심 문장:

> **프로그래밍 언어의 메모리 개념은 Stack/Heap 암기보다, 대입 후 값의 관계와 Ownership·Lifetime을 누가 어떻게 보장하는지를 묻는 것이 먼저다.**
