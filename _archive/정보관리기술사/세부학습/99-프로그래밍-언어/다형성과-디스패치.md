# 다형성과 Dispatch — Subtype · Parametric · Static · Dynamic

> 학습 원칙: [`00-프로그래밍-언어-학습원칙.md`](00-프로그래밍-언어-학습원칙.md)
>
> 핵심 질문: **하나의 코드나 추상 계약으로 여러 타입을 다룰 때 실제 동작을 어떻게 선택하는가?**

---

## 1. 큰 그림

`다형성(Polymorphism)`은 하나의 모양으로 여러 타입이나 동작을 다루는 상위 개념이다.

```text
다형성
├─ Subtype Polymorphism
│  → 공통 상위 타입/계약으로 여러 구체 타입을 다룸
│
├─ Parametric Polymorphism
│  → 타입 자체를 매개변수로 받아 하나의 알고리즘 재사용
│
└─ Ad-hoc Polymorphism
   → Overloading 등 같은 이름을 타입별로 다르게 해석
```

그리고 `Dispatch`는 **실제 어떤 구현을 호출할지 선택하는 문제**다.

```text
Compile Time에 결정
→ Static Dispatch

Runtime에 결정
→ Dynamic Dispatch
```

`다형성 = virtual`이라고 외우면 한 종류만 보게 된다.

---

## 2. C++ 기준점 — virtual이 보여주는 Runtime 다형성

```cpp
struct Animal {
    virtual void speak() = 0;
    virtual ~Animal() = default;
};

struct Dog : Animal {
    void speak() override {
        std::cout << "woof";
    }
};

struct Cat : Animal {
    void speak() override {
        std::cout << "meow";
    }
};

void run(Animal& a) {
    a.speak();
}
```

`run()`은 `Animal`만 알지만 실제 객체가 `Dog`인지 `Cat`인지에 따라 다른 함수가 실행된다.

```text
공통 Interface
      ↓
Animal&
      ↓
Runtime 실제 객체 확인
      ↓
Dog::speak() 또는 Cat::speak()
```

이게 **Subtype Polymorphism + Dynamic Dispatch**의 대표적인 C++ 구현이다.

---

## 3. vtable은 다형성의 개념이 아니라 구현 메커니즘이다

C++ 구현은 보통 개념적으로 다음처럼 생각할 수 있다.

```text
객체
├─ Data
└─ vptr
    ↓
vtable
├─ speak → Dog::speak
└─ ...
```

호출:

```cpp
a.speak();
```

개념적으로:

```text
객체의 vptr 확인
  ↓
vtable에서 함수 주소 검색
  ↓
간접 호출
```

하지만 중요한 경계는:

```text
다형성
= 하나의 추상 형태로 여러 구현을 다루는 의미론

virtual / vtable
= C++에서 Runtime 다형성을 구현하는 대표 방법
```

이다.

---

## 4. Static Polymorphism — Template

C++ Template도 다형성이다.

```cpp
template <typename T>
void print(const T& value) {
    value.print();
}
```

사용:

```cpp
print(foo);
print(bar);
```

여기서는 Runtime에 실제 호출 대상을 찾는 것이 아니라 Compile Time에 타입이 확정되고 코드가 생성될 수 있다.

```text
Template<T>
   ↓
T = Foo
→ Foo용 코드

T = Bar
→ Bar용 코드
```

따라서:

```text
virtual
→ Runtime Subtype Polymorphism

Template
→ Compile Time Parametric Polymorphism / Static Polymorphism
```

으로 구분하면 이해가 쉽다.

## 5. Parametric Polymorphism — 핵심은 타입을 매개변수화하는 것

C++ Template, Java Generic, Go Generic, Rust Generic은 문법은 다르지만 같은 질문에서 출발한다.

```text
하나의 알고리즘
+
Type Parameter T
        ↓
여러 타입에 재사용
```

C++:

```cpp
template <typename T>
T max_value(T a, T b) {
    return a > b ? a : b;
}
```

Java:

```java
<T> T identity(T value) {
    return value;
}
```

Rust:

```rust
fn identity<T>(value: T) -> T {
    value
}
```

핵심은 `<T>` 문법이 아니라 **타입에 독립적인 코드를 어떤 제약과 비용으로 재사용하는가**다.

---

## 6. 언어별 Interface 대응은 목적은 비슷해도 의미론이 다르다

### C++ / Java

```text
명시적 상속 또는 구현 관계
→ 상위 추상 타입과 하위 타입 관계를 선언
```

### Go

```text
Method Set이 Interface 요구사항을 만족
→ 명시적 implements 선언 없이 구조적으로 만족
```

### Rust

```text
Trait 구현을 명시
→ Generic Bound로 Static Dispatch 가능
→ dyn Trait로 Dynamic Dispatch 가능
```

따라서:

> `Go interface = 상속 없는 C++ virtual`

처럼 등치하지 않는다.

더 정확한 표현은:

> **Go Interface를 통한 호출은 C++ Virtual Dispatch와 비슷한 목적을 제공하지만, Interface 만족 여부를 구조적으로 판단하고 명시적 상속 관계를 요구하지 않는다.**

---

## 7. Static Dispatch와 Dynamic Dispatch

### Static Dispatch

```text
Compile Time에 호출 대상 확정
```

대표:

- C++ Template
- Rust Generic + Trait Bound
- 일반 함수 Overload Resolution

장점:

- 간접 호출 비용을 줄일 수 있음
- Inlining/Optimization에 유리할 수 있음

Trade-off:

- 타입별 코드 생성으로 Binary Size 증가 가능
- Compile Time 증가 가능

### Dynamic Dispatch

```text
Runtime 실제 객체/Metadata를 통해 호출 대상 결정
```

대표:

- C++ virtual
- Java Interface/Virtual Method
- Rust `dyn Trait`

장점:

- Runtime에 다양한 구체 타입을 같은 Collection/Interface로 다루기 쉬움
- 구현을 Compile Time에 모두 고정하지 않아도 됨

Trade-off:

- 간접 호출
- 일부 최적화 제한
- Runtime Metadata 필요 가능

## 8. Overloading은 다른 축이다

```cpp
void print(int v);
void print(std::string v);
```

같은 함수 이름이지만 인자 타입에 따라 Compile Time에 어떤 함수를 호출할지 결정한다.

이것도 넓게는 다형성으로 분류되지만 Subtype Polymorphism과는 다른 문제다.

```text
Overloading
→ 같은 이름을 여러 Signature에 사용

Subtype Polymorphism
→ 공통 추상 타입 뒤에 여러 구체 구현을 숨김

Parametric Polymorphism
→ 타입 자체를 매개변수화
```

---

## 9. Duck Typing과 구조적 타입도 같은 질문에서 비교한다

동적 언어에서는 명시적 Interface 선언이 없어도 필요한 Method가 있으면 사용할 수 있다.

```python
def run(x):
    x.speak()
```

핵심 질문은:

```text
"이 타입이 이 연산을 지원한다"는 계약을
언제, 어떻게 확인하는가?
```

```text
C++ virtual
→ 명시적 상속 관계 + Runtime Dispatch

C++ template
→ 필요한 표현이 Compile Time에 유효한지 검사

Go interface
→ Method Set 기반 구조적 만족

Python Duck Typing
→ Runtime에 실제 연산 가능 여부가 드러남
```

이렇게 같은 질문 위에서 비교하면 언어별 문법이 하나의 구조로 정리된다.

---

## 10. 다형성과 추상화는 같은 말이 아니다

```text
추상화
→ 중요하지 않은 세부를 감추고 핵심 계약/개념을 드러냄

다형성
→ 하나의 추상 형태로 여러 구체 타입/동작을 다룸
```

추상화된 Interface가 다형성을 제공할 수 있지만 둘은 같은 개념은 아니다.

---

## 11. 기술사 관점의 Trade-off

다형성 메커니즘을 비교할 때는 문법보다 다음 축을 본다.

| 비교축 | 질문 |
|---|---|
| 결정 시점 | Compile Time인가 Runtime인가? |
| 계약 방식 | 명시적 상속, 구조적 만족, Trait Bound 등 무엇인가? |
| 성능 | 간접 호출·Inlining·Code Size Trade-off는? |
| 확장성 | 새 타입과 새 동작 중 무엇을 추가하기 쉬운가? |
| 안전성 | 잘못된 구현을 언제 검출하는가? |
| 결합도 | 호출자가 구체 타입을 얼마나 알아야 하는가? |

---

## 12. 기억·인출

```text
다형성
= 한 형태로 여러 타입/동작을 다룸

Subtype
= 공통 부모/계약 뒤에 여러 구현

Parametric
= 타입을 T로 받음

Static Dispatch
= Compile Time에 결정

Dynamic Dispatch
= Runtime에 결정

C++ virtual
= Runtime Subtype Polymorphism의 대표 구현

C++ template
= Parametric / Static Polymorphism의 대표 구현
```

핵심 문장:

> **다형성은 `virtual`이 아니라 여러 타입을 하나의 추상 형태로 다루는 개념이고, `virtual`, Template, Interface, Trait은 각 언어가 그 문제를 해결하는 서로 다른 장치다.**
