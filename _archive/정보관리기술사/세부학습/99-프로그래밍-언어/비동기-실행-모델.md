# 비동기 실행 모델 — Callback · Event Loop · Promise/Future · Coroutine · async/await

> 학습 원칙: [`00-프로그래밍-언어-학습원칙.md`](00-프로그래밍-언어-학습원칙.md)
>
> 핵심 질문: **오래 걸리는 작업을 기다리는 동안 실행 흐름을 막지 않고, 작업이 끝난 뒤 필요한 코드를 어떻게 다시 실행하는가?**

---

## 1. 큰 그림

비동기 프로그래밍에서는 서로 다른 층위의 개념이 함께 나온다.

```text
오래 걸리는 작업
(I/O, Timer, Network)
        ↓
기다리는 동안 현재 실행 흐름을 막고 싶지 않다
        ↓
비동기 작업 시작
        ↓
작업이 끝난 뒤 다음 처리를 어떻게 연결할까?
├─ Callback
├─ Promise / Future
└─ Coroutine + async/await

준비된 작업은 누가 골라서 언제 실행할까?
├─ Event Loop
├─ Scheduler
└─ Thread Pool / Runtime
```

`Callback`, `Promise`, `Coroutine`은 **작업이 끝난 뒤 다음 처리를 이어가는 방법**이고, `Event Loop`는 **실행할 준비가 된 작업을 반복해서 골라 실제 실행으로 연결하는 Runtime의 실행 구조**다. 같은 층위의 개념으로 보지 않는다.

---

## 2. 먼저 언어와 Runtime을 나눈다

비동기 실행을 볼 때 `JavaScript`와 `Node.js`를 같은 것으로 생각하면 Event Loop가 어디에 있는지 헷갈리기 쉽다.

```text
JavaScript
= 언어
= Promise, async/await 같은 문법과 의미론을 정의

Node.js / Browser
= JavaScript를 실행하는 Runtime
= Timer, Network I/O, Event Loop 등 실행 환경을 제공
```

따라서 다음처럼 이해한다.

```text
JavaScript 코드
        ↓
Runtime API로 비동기 작업 등록
        ↓
Runtime / OS가 작업을 기다림
        ↓
작업이 준비되거나 완료됨
        ↓
Runtime이 다음에 실행할 작업을 준비
        ↓
Event Loop가 해당 Callback / Task를 실행
```

즉 `Event Loop`는 JavaScript 문법이 아니라 **JavaScript Runtime이 비동기 작업을 실행 흐름에 다시 연결하기 위해 사용하는 실행 구조**다.

## 3. C++ 기준점 — 나중에 실행할 코드와 상태를 보관한다

가장 단순한 비동기 모델은 "작업이 끝나면 이 함수를 호출해 달라"고 Callback을 넘기는 방식이다.

```cpp
void read_async(std::function<void(Result)> callback);

read_async([](Result r) {
    use(r);
});
```

C++ 관점에서는 다음 세 가지가 핵심이다.

```text
비동기 작업 시작
+
나중에 실행할 함수 객체 저장
+
작업이 끝나면 그 함수 객체 호출
```

Callback이 바깥 상태를 사용한다면 Capture Lambda가 된다.

```cpp
int request_id = 10;

read_async([request_id](Result r) {
    log(request_id, r);
});
```

여기서 문제를 둘로 나눈다.

```text
request_id를 왜 나중에도 사용할 수 있는가?
→ Closure / Capture

Callback은 언제 실행되는가?
→ Scheduler / Event Loop / Runtime
```

## 4. Event Loop — 메인 실행 흐름이 다음 작업을 고르는 반복 구조

Event Loop를 별도의 감시 프로그램이나 별도 스레드라고 생각하지 않는다.

핵심은 단순하다.

> **현재 작업이 끝나면 실행할 준비가 된 다음 작업을 고르고 실행한다. 이 과정을 계속 반복하는 구조가 Event Loop다.**

C++식으로 단순화하면 다음과 같다.

```cpp
while (running) {
    auto task = wait_for_ready_task();
    task();
}
```

조금 더 풀면:

```text
실행할 준비가 된 Task 확인
        ↓
하나 선택
        ↓
Callback / Task 실행
        ↓
현재 작업 종료
        ↓
Event Loop로 제어 복귀
        ↓
다음 Task 선택
        ↺
```

Node.js의 기본 실행 환경에서는 **메인 JavaScript Thread가 이 Event Loop를 돌면서 JavaScript Task를 순차적으로 실행**한다고 이해하면 된다.

```text
Main JS Thread
      ↓
Event Loop 반복
      ↓
ready Task 선택
      ↓
JavaScript Callback 실행
      ↓
Callback 종료
      ↓
다시 Event Loop
```

따라서 다음 둘을 구분한다.

```text
잘못된 이해
Main Thread = Event Loop라는 별도 객체

정확한 이해
Main Thread = Event Loop라는 반복 제어 구조를 실행하는 Thread
```

메인 스레드는 Event Loop와 별개의 일을 동시에 하는 것이 아니다. **Event Loop 자체가 다음 JavaScript 작업을 고르고 실행하는 방식**이다.

그래서 현재 JavaScript 작업 하나가 오래 끝나지 않으면 Event Loop로 제어가 돌아오지 못하고 다음 Callback도 실행되지 않는다.

```javascript
while (true) {
  // 끝나지 않는 CPU 작업
}
```

이런 코드가 Event Loop를 막는 이유가 바로 이것이다.

## 5. Event Loop와 I/O Multiplexing — 비슷한 뼈대를 가진다

I/O Multiplexing을 알고 있다면 Event Loop는 훨씬 쉽게 이해할 수 있다.

```cpp
while (running) {
    auto ready = epoll_wait(...);

    for (auto fd : ready) {
        handle(fd);
    }
}
```

여기서는:

```text
epoll_wait()
= 여러 I/O 중 Ready인 것을 찾음

handle(fd)
= 준비된 I/O 처리

while
= 처리 후 다시 감시
```

따라서 네트워크 관점에서는 다음처럼 보면 된다.

```text
I/O Multiplexing
= 여러 I/O 중 무엇이 Ready인지 함께 기다리는 메커니즘

Event Loop
= Ready 결과를 받아 처리하고 다시 기다리는 반복 실행 구조
```

즉 **Multiplexing을 반복해서 수행하면서 준비된 I/O를 처리하면 전형적인 Event Loop 형태가 된다.**

다만 두 개념의 범위는 다르다.

```text
I/O Multiplexing
→ 주로 FD / Socket의 readiness를 다룸

Event Loop
→ I/O뿐 아니라 Timer, Task, Callback 등 실행 가능한 여러 작업을 다룰 수 있음
```

`select / poll / epoll`, Readiness, Reactor까지 내려가는 자세한 원리는 네트워크 문서에서 다룬다.

- [`../03-네트워크/_보충학습/IO-Multiplexing-EventLoop-Reactor.md`](../03-네트워크/_보충학습/IO-Multiplexing-EventLoop-Reactor.md)

## 6. Node.js에 대입하면 어떻게 보이는가

Node.js에서는 개발자가 `epoll_wait()` 같은 저수준 감시 루프를 JavaScript 코드로 직접 작성하지 않는다. Runtime이 OS와 연결되는 부분을 맡고, JavaScript 개발자는 비동기 작업과 그 이후의 처리를 표현한다.

```text
JavaScript 코드
fetch / socket / timer 등 요청
        ↓
Node.js Runtime
        ↓
OS I/O 기능 또는 Runtime 내부 처리
        ↓
작업 준비 / 완료
        ↓
실행할 Callback / Task 준비
        ↓
Main JS Thread의 Event Loop
        ↓
JavaScript Callback 실행
```

멀티플렉싱에 빗대면 다음처럼 대응시킬 수 있다.

```text
ready FD 확인
↔ Runtime이 실행할 준비가 된 Event / Task 확인

FD별 Handler 실행
↔ Callback / Promise 후속 처리 / await 이후 코드 실행

감시 → 처리 → 다시 감시
↔ Event Loop 반복
```

다만 Node.js의 모든 비동기 작업이 하나의 OS I/O Multiplexing 방식으로 처리되는 것은 아니다. 작업 종류에 따라 OS 기능을 이용하기도 하고 Runtime 내부 Worker Thread Pool을 이용하기도 한다.

따라서 다음처럼 외우지 않는다.

```text
Node.js
= 비동기 감시 전용 Thread 하나가 따로 존재
```

대신 역할을 나눈다.

```text
Main JS Thread
→ Event Loop를 돌면서 JavaScript Task 실행

OS / Runtime
→ 기다려야 하는 비동기 작업의 상태를 관리하거나 완료를 통지

Worker Thread Pool
→ 필요한 일부 작업을 별도 Thread에서 처리
```

핵심은 **메인 스레드가 I/O가 끝날 때까지 붙잡혀 기다리지 않는다는 것**이다. 작업을 Runtime/OS에 맡기고 현재 JavaScript 실행을 계속 진행하다가, 나중에 준비된 후속 작업을 Event Loop가 다시 실행한다.

## 7. Event Loop는 꼭 하나인가

Event Loop라는 개념 자체가 시스템 전체에 하나만 있어야 하는 것은 아니다.

```text
Thread A
└─ Event Loop A

Thread B
└─ Event Loop B
```

처럼 여러 실행 흐름이 각각 Event Loop를 가질 수도 있다.

다만 Node.js의 기본적인 한 실행 환경에서는 다음 구조를 기준으로 이해하면 된다.

```text
Node.js Process
└─ Main JS Thread
   └─ Main Event Loop
```

여러 Process를 띄우거나 Worker를 사용하면 별도의 JavaScript 실행 환경과 Event Loop가 추가될 수 있다.

I/O Multiplexing 객체의 개수와 Event Loop 개수도 같은 규칙으로 묶지 않는다. `epoll` 같은 Multiplexing 객체는 한 Process 안에서도 필요에 따라 여러 개 만들 수 있다.

```text
Event Loop
= Application / Runtime의 실행 구조

Multiplexing 객체
= I/O readiness를 기다리는 도구
```

둘은 자주 함께 사용되지만 개수 규칙까지 같은 것은 아니다.

## 8. Callback — 작업이 끝난 뒤 할 일을 직접 넘긴다

Callback은 완료 이후에 할 일을 함수로 직접 넘기는 방식이다.

```javascript
readFile(path, (err, data) => {
  if (err) return handle(err);
  use(data);
});
```

장점:

- 단순한 비동기 API를 만들기 쉽다.
- 함수 자체를 값처럼 전달할 수 있다.

문제:

- 중첩이 깊어질 수 있다.
- Error 전달 규칙이 여러 곳으로 흩어질 수 있다.
- 여러 비동기 작업을 조합하면 흐름을 따라가기 어려워질 수 있다.

```text
A 완료
  ↓
Callback B
  ↓
B 완료
  ↓
Callback C
```

Callback 자체가 문제라기보다, **복잡한 비동기 흐름을 Callback 중첩만으로 표현할 때 읽기 어렵고 조합하기 힘들어질 수 있다**는 점이 핵심이다.

## 9. Promise / Future — 아직 없는 결과를 하나의 값처럼 다룬다

Promise/Future 계열은 "나중에 생길 결과"를 객체로 표현한다.

C++:

```cpp
std::future<int> f = std::async([] {
    return compute();
});

int value = f.get();
```

JavaScript:

```javascript
fetch(url)
  .then(response => response.json())
  .then(data => use(data));
```

공통 직관:

```text
현재는 결과 없음
      ↓
미래 결과를 나타내는 객체
      ↓
Pending
  ├─ Fulfilled
  └─ Rejected / Error
```

다만 `Promise`, `Future`가 언제 실행되고 어떤 Thread와 연결되는지, 취소와 Error 전파를 어떻게 다루는지는 언어와 Runtime마다 다르다.

## 10. Coroutine — 실행 위치와 지역 상태를 저장한 채 멈췄다가 다시 이어간다

Coroutine은 **함수를 끝내지 않고 중간에 멈춘 뒤, 그때의 실행 상태를 보존한 채 나중에 이어서 실행할 수 있는 실행 단위**다.

C++ 관점으로 풀면 다음 정보가 필요하다.

```text
현재 실행 위치
지역 변수 상태
왜 멈췄는지
다시 어디서 시작할지
```

개념적으로는 다음과 같은 상태를 가진다고 볼 수 있다.

```cpp
struct CoroutineState {
    int state;
    int local_value;
};
```

그리고 실행 흐름은 상태 머신처럼 생각할 수 있다.

```text
state 0
→ 작업 시작
→ I/O 요청
→ Suspend

I/O 완료
→ Resume
→ state 1부터 계속 실행
```

일반 Thread와 달리 Coroutine은 보통 사용자 수준 Runtime이 실행 상태를 관리하고, 정해진 Suspend 지점에서 실행권을 넘긴다.

## 11. async/await — 비동기 상태 전이를 동기 코드처럼 읽게 한다

`async/await`은 비동기 실행을 새로 만들어 내는 마법이 아니다. Promise/Future나 Coroutine 기반의 상태 전이를 **순서대로 읽히는 코드 형태로 표현하는 문법**이라고 보면 된다.

```javascript
async function load() {
  const response = await fetch(url);
  const data = await response.json();
  return data;
}
```

개념적으로는 다음과 같다.

```text
fetch 시작
  ↓
아직 완료 안 됨
  ↓
현재 함수 상태 저장
  ↓
실행권 반환
  ↓
fetch 완료
  ↓
저장된 상태 복원
  ↓
다음 문장부터 재개
```

C++ 관점에서는 **상태 머신 + 다음에 이어서 할 일 + 저장된 지역 상태**로 풀어보면 이해하기 쉽다.

## 12. Thread와 Event Loop / Coroutine의 차이

```text
Thread
→ 독립적인 실행 Context와 Stack을 가진 실행 단위
→ OS 또는 Runtime이 Scheduling

Event Loop
→ 하나 또는 소수의 실행 흐름에서 준비된 Event/Task를 차례로 실행

Coroutine
→ 실행 상태를 보존하고 중간에 Suspend했다가 Resume
```

실제 시스템에서는 이들을 함께 사용할 수 있다.

```text
Event Loop Thread
      ↓
I/O Event 확인
      ↓
Coroutine Resume
      ↓
CPU 작업은 Worker Thread Pool로 위임
```

따라서 `Event Loop = Single Thread`, `Coroutine = Thread 대체`, `async = 병렬 실행`처럼 단순하게 등치하지 않는다.

---

## 13. 비동기·동시성·병렬성은 다른 질문이다

```text
비동기(Asynchrony)
→ 작업 완료를 어떻게 기다릴 것인가?

동시성(Concurrency)
→ 여러 작업의 진행을 어떻게 겹쳐 관리할 것인가?

병렬성(Parallelism)
→ 여러 작업을 실제로 동시에 실행할 것인가?
```

Event Loop는 병렬 실행이 없어도 여러 작업의 진행을 겹쳐 관리할 수 있다. 반대로 Thread Pool은 여러 CPU Core를 이용해 실제 병렬 실행을 만들 수 있다.

## 14. 개념 경계 정리

| 개념 | 핵심 질문 | C++ 기준점 |
|---|---|---|
| Callback | 끝난 뒤 무엇을 실행할까? | 함수 포인터 / `std::function` / Lambda |
| Closure | Callback이 필요한 상태를 어떻게 기억할까? | Capture Lambda |
| Event Loop | 준비된 작업을 누가 반복해서 골라 실행할까? | `while` + ready Task + Dispatch |
| Promise/Future | 아직 없는 결과를 어떻게 값처럼 다룰까? | `std::future` |
| Coroutine | 실행을 어떻게 멈췄다가 이어갈까? | 상태 저장 + Suspend / Resume |
| async/await | 비동기 상태 전이를 어떻게 순서대로 읽히게 할까? | 상태 머신의 문법적 추상화 |
| I/O Multiplexing | 어떤 I/O가 준비됐는지 어떻게 함께 기다릴까? | `select` / `poll` / `epoll` 계열 |
| Runtime | 언어의 비동기 작업을 실제 OS/Thread/Queue와 누가 연결할까? | Event Loop / Scheduler / Thread Pool 조합 |

Promise/Future

Coroutine
