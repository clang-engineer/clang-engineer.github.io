# 비동기 실행 모델 — Callback · Event Loop · Promise/Future · Coroutine · async/await

> 학습 원칙: [`00-프로그래밍-언어-학습원칙.md`](00-프로그래밍-언어-학습원칙.md)
>
> 핵심 질문: **오래 걸리는 작업을 기다리는 동안 실행 흐름을 막지 않고, 작업이 끝난 뒤 필요한 코드를 어떻게 다시 실행하는가?**

---

## 1. 큰 그림

비동기 프로그래밍에서는 서로 다른 층위의 개념이 함께 나온다.

```text
오래 걸리는 작업
(I/O, Timer, Network)
        ↓
기다리는 동안 현재 실행 흐름을 막고 싶지 않다
        ↓
비동기 작업 시작
        ↓
작업이 끝난 뒤 다음 처리를 어떻게 연결할까?
├─ Callback
├─ Promise / Future
└─ Coroutine + async/await

완료된 작업은 언제 다시 실행할까?
├─ Event Loop
├─ Scheduler
└─ Thread Pool / Runtime
```

`Callback`, `Promise`, `Coroutine`은 **작업이 끝난 뒤 다음 처리를 이어가는 방법**이고, `Event Loop`는 **준비된 작업을 언제 실행할지 조정하는 Runtime 메커니즘**이다. 같은 층위의 개념으로 보지 않는다.

---

## 2. C++ 기준점 — 나중에 실행할 코드와 상태를 보관한다

가장 단순한 비동기 모델은 "작업이 끝나면 이 함수를 호출해 달라"고 Callback을 넘기는 방식이다.

```cpp
void read_async(std::function<void(Result)> callback);

read_async([](Result r) {
    use(r);
});
```

C++ 관점에서는 다음 세 가지가 핵심이다.

```text
비동기 작업 시작
+
나중에 실행할 함수 객체 저장
+
작업이 끝나면 그 함수 객체 호출
```

Callback이 바깥 상태를 사용한다면 Capture Lambda가 된다.

```cpp
int request_id = 10;

read_async([request_id](Result r) {
    log(request_id, r);
});
```

여기서 문제를 둘로 나눈다.

```text
request_id를 왜 나중에도 사용할 수 있는가?
→ Closure / Capture

Callback은 언제 실행되는가?
→ Scheduler / Event Loop / Runtime
```

---

## 3. Event Loop — 준비된 작업을 다시 실행 흐름에 올린다

Event Loop는 실행할 준비가 된 Event나 Task를 확인하고, 실행 가능한 시점에 하나씩 넘기는 반복 구조다.

```text
비동기 작업 등록
      ↓
Runtime / OS가 대기
      ↓
작업 완료 또는 Event 발생
      ↓
Queue에 실행할 작업 등록
      ↓
Event Loop
      ↓
실행 가능한 시점에 Callback / Task 실행
```

JavaScript에서는 다음 예제로 직관을 잡을 수 있다.

```javascript
console.log("A");

setTimeout(() => {
  console.log("B");
}, 0);

console.log("C");
```

결과:

```text
A
C
B
```

`setTimeout(..., 0)`은 "즉시 실행"을 뜻하지 않는다. 최소 대기 조건을 만족한 뒤 실행할 작업이 Queue에 들어가고, 현재 실행 중인 코드가 끝난 뒤 실행 기회를 얻는다고 이해하면 된다.

---

## 4. Event Loop와 I/O Multiplexing은 같은 개념이 아니다

네트워크에서 사용하는 `select`, `poll`, `epoll`, `kqueue` 등은 **여러 I/O 중 무엇이 준비됐는지 효율적으로 감시하는 OS 수준 메커니즘**이다.

Event Loop는 그보다 위에서 Event를 받아 Application 작업을 실행하도록 넘긴다.

```text
Application
  ↓
Event Loop
  ↓
Runtime
  ↓
OS I/O Multiplexing
(select / poll / epoll / kqueue 등)
  ↓
준비된 I/O 통지
  ↑
Runtime
  ↑
Event Loop가 Callback / Task 실행
```

따라서:

```text
I/O Multiplexing
→ 어떤 I/O가 준비됐는지 감시

Event Loop
→ 준비된 Event/Task를 언제 실행할지 조정
```

Node.js 같은 Runtime에서는 둘이 실제로 연결되지만 같은 개념은 아니다.

---

## 5. Callback — 작업이 끝난 뒤 할 일을 직접 넘긴다

Callback은 완료 이후에 할 일을 함수로 직접 넘기는 방식이다.

```javascript
readFile(path, (err, data) => {
  if (err) return handle(err);
  use(data);
});
```

장점:

- 단순한 비동기 API를 만들기 쉽다.
- 함수 자체를 값처럼 전달할 수 있다.

문제:

- 중첩이 깊어질 수 있다.
- Error 전달 규칙이 여러 곳으로 흩어질 수 있다.
- 여러 비동기 작업을 조합하면 흐름을 따라가기 어려워질 수 있다.

```text
A 완료
  ↓
Callback B
  ↓
B 완료
  ↓
Callback C
```

Callback 자체가 문제라기보다, **복잡한 비동기 흐름을 Callback 중첩만으로 표현할 때 읽기 어렵고 조합하기 힘들어질 수 있다**는 점이 핵심이다.

---

## 6. Promise / Future — 아직 없는 결과를 하나의 값처럼 다룬다

Promise/Future 계열은 "나중에 생길 결과"를 객체로 표현한다.

C++:

```cpp
std::future<int> f = std::async([] {
    return compute();
});

int value = f.get();
```

JavaScript:

```javascript
fetch(url)
  .then(response => response.json())
  .then(data => use(data));
```

공통 직관:

```text
현재는 결과 없음
      ↓
미래 결과를 나타내는 객체
      ↓
Pending
  ├─ Fulfilled
  └─ Rejected / Error
```

다만 `Promise`, `Future`가 언제 실행되고 어떤 Thread와 연결되는지, 취소와 Error 전파를 어떻게 다루는지는 언어와 Runtime마다 다르다.

---

## 7. Coroutine — 실행 위치와 지역 상태를 저장한 채 멈췄다가 다시 이어간다

Coroutine은 **함수를 끝내지 않고 중간에 멈춘 뒤, 그때의 실행 상태를 보존한 채 나중에 이어서 실행할 수 있는 실행 단위**다.

C++ 관점으로 풀면 다음 정보가 필요하다.

```text
현재 실행 위치
지역 변수 상태
왜 멈췄는지
다시 어디서 시작할지
```

개념적으로는 다음과 같은 상태를 가진다고 볼 수 있다.

```cpp
struct CoroutineState {
    int state;
    int local_value;
};
```

그리고 실행 흐름은 상태 머신처럼 생각할 수 있다.

```text
state 0
→ 작업 시작
→ I/O 요청
→ Suspend

I/O 완료
→ Resume
→ state 1부터 계속 실행
```

일반 Thread와 달리 Coroutine은 보통 사용자 수준 Runtime이 실행 상태를 관리하고, 정해진 Suspend 지점에서 실행권을 넘긴다.

---

## 8. async/await — 비동기 상태 전이를 동기 코드처럼 읽게 한다

`async/await`은 비동기 실행을 새로 만들어 내는 마법이 아니다. Promise/Future나 Coroutine 기반의 상태 전이를 **순서대로 읽히는 코드 형태로 표현하는 문법**이라고 보면 된다.

```javascript
async function load() {
  const response = await fetch(url);
  const data = await response.json();
  return data;
}
```

개념적으로는 다음과 같다.

```text
fetch 시작
  ↓
아직 완료 안 됨
  ↓
현재 함수 상태 저장
  ↓
실행권 반환
  ↓
fetch 완료
  ↓
저장된 상태 복원
  ↓
다음 문장부터 재개
```

C++ 관점에서는 **상태 머신 + 다음에 이어서 할 일 + 저장된 지역 상태**로 풀어보면 이해하기 쉽다.

---

## 9. Thread와 Event Loop / Coroutine의 차이

```text
Thread
→ 독립적인 실행 Context와 Stack을 가진 실행 단위
→ OS 또는 Runtime이 Scheduling

Event Loop
→ 하나 또는 소수의 실행 흐름에서 준비된 Event/Task를 차례로 실행

Coroutine
→ 실행 상태를 보존하고 중간에 Suspend했다가 Resume
```

실제 시스템에서는 이들을 함께 사용할 수 있다.

```text
Event Loop Thread
      ↓
I/O Event 확인
      ↓
Coroutine Resume
      ↓
CPU 작업은 Worker Thread Pool로 위임
```

따라서 `Event Loop = Single Thread`, `Coroutine = Thread 대체`, `async = 병렬 실행`처럼 단순하게 등치하지 않는다.

---

## 10. 비동기·동시성·병렬성은 다른 질문이다

```text
비동기(Asynchrony)
→ 작업 완료를 어떻게 기다릴 것인가?

동시성(Concurrency)
→ 여러 작업의 진행을 어떻게 겹쳐 관리할 것인가?

병렬성(Parallelism)
→ 여러 작업을 실제로 동시에 실행할 것인가?
```

Event Loop는 병렬 실행이 없어도 여러 작업의 진행을 겹쳐 관리할 수 있다. 반대로 Thread Pool은 여러 CPU Core를 이용해 실제 병렬 실행을 만들 수 있다.

## 11. 개념 경계 정리

| 개념 | 핵심 질문 | C++ 기준점 |
|---|---|---|
| Callback | 끝난 뒤 무엇을 실행할까? | 함수 포인터 / `std::function` / Lambda |
| Closure | Callback이 필요한 상태를 어떻게 기억할까? | Capture Lambda |
| Event Loop | 준비된 작업을 언제 실행할까? | Queue + Loop + Dispatcher |
| Promise/Future | 아직 없는 결과를 어떻게 값처럼 다룰까? | `std::future` |
| Coroutine | 실행을 어떻게 멈췄다가 이어갈까? | 상태 저장 + Suspend / Resume |
| async/await | 비동기 상태 전이를 어떻게 순서대로 읽히게 할까? | 상태 머신의 문법적 추상화 |
| I/O Multiplexing | 어떤 I/O가 준비됐는지 어떻게 감시할까? | `select` / `poll` / `epoll` 계열 |

---

## 12. 기억·인출

```text
Closure
= 무엇을 기억하는가

Event Loop
= 언제 다시 실행하는가

Promise/Future
= 아직 없는 결과를 값처럼 다룸

Coroutine
= 실행 위치와 상태를 저장하고 중단·재개

async/await
= 비동기 상태 전이를 순서대로 읽히게 함
```

핵심 문장:

> **비동기 실행 모델의 핵심은 오래 걸리는 작업을 다른 곳에 맡기는 데서 끝나지 않는다. 작업이 끝난 뒤 결과와 실행 상태를 어떻게 보존하고, 다시 실행 흐름에 연결할지까지 함께 봐야 한다.**
