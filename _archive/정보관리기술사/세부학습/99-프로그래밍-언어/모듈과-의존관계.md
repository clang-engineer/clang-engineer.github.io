# 모듈과 의존관계 — Import · Export · Linking · Loading

> 학습 원칙: [`00-프로그래밍-언어-학습원칙.md`](00-프로그래밍-언어-학습원칙.md)
>
> 핵심 질문: **코드 단위를 어떻게 나누고, 서로의 기능을 어떤 계약으로 노출하며, 의존관계를 언제 연결하는가?**

---

## 1. 큰 그림

모듈 시스템은 단순히 `import` 문법을 제공하는 기능이 아니다.

```text
코드를 여러 단위로 나눈다
        ↓
외부에 무엇을 공개할까?
        ↓
다른 모듈은 무엇을 참조할까?
        ↓
의존관계를 언제 찾고 연결할까?
├─ Compile / Link Time
└─ Runtime
        ↓
실제 코드는 언제 Load / Evaluate할까?
```

핵심 질문은 다음 네 가지다.

```text
무엇을 Export하는가?
무엇을 Import하는가?
의존관계를 언제 확정하는가?
실제 Module은 언제 Load/Evaluate되는가?
```

---

## 2. C++ 기준점 — 선언과 구현, Compile과 Link

C++에서는 Header와 Source, Object File과 Link 단계가 의존관계를 비교적 직접 보여준다.

```cpp
// math.h
int add(int a, int b);
```

```cpp
// math.cpp
int add(int a, int b) {
    return a + b;
}
```

사용 측:

```cpp
#include "math.h"
```

큰 흐름:

```text
Source
  ↓ Compile
Object File
  ↓ Link
Executable / Library
```

C++의 전통적 `#include`는 Module Import와 동일하지 않다. Preprocessor가 Text를 포함하는 방식이라는 점을 구분한다.

---

## 3. 선언과 정의 — 무엇을 안다는 뜻인가

C++에서:

```cpp
int add(int, int); // 선언
```

은 "이 함수가 존재한다"는 계약을 Compiler에 알려준다.

```cpp
int add(int a, int b) { // 정의
    return a + b;
}
```

은 실제 구현을 제공한다.

이 구분은 다른 언어의 Module에서도 유용하다.

```text
외부 계약
→ 어떤 이름/타입/함수를 사용할 수 있는가?

실제 구현
→ 그 이름이 어떤 코드와 상태를 가지는가?
```

---

## 4. Linking — 이름과 실제 구현을 연결한다

C++ 전통 Toolchain에서는 Compile된 여러 Object File의 Symbol을 Linker가 연결한다.

```text
main.o
  └─ add Symbol 필요

math.o
  └─ add Symbol 제공

        ↓ Link

Executable
```

따라서 `Linking`은 넓게 보면 **외부 참조를 실제 제공자와 연결하는 과정**이다.

언어/Runtime마다 이 연결 시점은 Compile Time, Link Time, Load Time, Runtime으로 달라질 수 있다.

---

## 5. Static Linking과 Dynamic Linking

### Static Linking

```text
Library Code
→ Build 시 Executable에 포함
```

### Dynamic Linking

```text
Executable
→ 외부 Shared Library 참조
→ Load/Runtime에 연결
```

핵심 Trade-off:

```text
Static
→ 배포 단순화 가능, Binary 증가 가능

Dynamic
→ Library 공유/교체 용이, Runtime 의존관계 관리 필요
```

이 개념은 언어 Module Import와 완전히 같지는 않지만 **의존관계를 언제 실제 구현과 결합하는가**라는 기준점을 제공한다.

---

## 6. JavaScript CommonJS — 실행 흐름 중심 Module Loading

```javascript
const fs = require("fs");
```

`require()`는 일반 함수 호출처럼 실행 흐름 안에 나타날 수 있다.

```javascript
if (enabled) {
  const feature = require("./feature");
  feature.run();
}
```

개념적으로:

```text
실행 흐름
  ↓
require()
  ↓
Resolve
  ↓
Load / Evaluate
  ↓
module.exports 반환
```

즉 Runtime 호출 중심이라는 점이 중요하다.

---

## 7. ESM — 선언적 Module Graph

```javascript
import { add } from "./math.js";
```

정적 `import`는 Module 본문 평가 전에 의존관계를 분석하고 연결할 수 있는 선언적 구조를 제공한다.

```text
Module A
├─ import B
└─ import C
      ↓
Resolve
      ↓
Module Graph 구성
      ↓
Link
      ↓
Evaluation
```

이 구조는 Bundler와 정적 분석 Tool이 Dependency Graph를 파악하는 기반이 된다.

---

## 8. 정적 import와 동적 import()는 다르다

```javascript
import { x } from "./a.js";
```

```text
정적 Import
→ 선언적 Dependency
→ Module Graph를 사전에 분석 가능
```

반면:

```javascript
const module = await import(path);
```

```text
동적 import()
→ 실행 중 Module 요청
→ Promise 기반 비동기 Loading
```

따라서 `ESM = 비동기 Import`라고 단순화하지 않는다.

---

## 9. Export 값과 Binding

Module System에서는 "무엇을 Export하느냐"도 중요하다.

```text
값의 Snapshot인가?
공유 객체인가?
이름 Binding 자체인가?
```

ESM은 `Live Binding` 개념을 제공한다.

```javascript
// counter.js
export let count = 0;
export function inc() {
  count++;
}
```

다른 Module에서 Import한 `count`는 해당 Export Binding의 변경을 반영한다.

단순히 "Import할 때 값을 한 번 복사한다"고 생각하면 틀릴 수 있다.

---

## 10. Module Cache와 Singleton-like 상태

Runtime Module System에서는 한 Module이 한 번 Evaluate된 뒤 Cache될 수 있다.

```text
첫 Import
→ Load
→ Evaluate
→ Module State 생성

다음 Import
→ 기존 Module Instance/Namespace 재사용
```

이 때문에 Module Top-level 상태가 Application 전체에서 사실상 공유 상태처럼 동작할 수 있다.

언어/Runtime마다 Cache와 Instance 규칙은 다르므로 확인이 필요하다.

---

## 11. Package와 Module은 같은 개념이 아니다

```text
Module
→ 언어/Runtime에서 Code와 Namespace를 나누는 단위

Package
→ 여러 Module·Metadata·Dependency·배포 단위를 묶는 더 큰 단위일 수 있음
```

Java Package, npm Package, Python Package, Rust Crate/Module은 이름과 계층이 다르다.

따라서 `Package = Folder`, `Module = File`처럼 모든 언어에 일반화하지 않는다.

---

## 12. Dependency Injection과 Module System도 구분한다

Module System:

```text
어떤 코드 단위가 어떤 이름/구현에 의존하는가?
```

Dependency Injection:

```text
필요한 구체 객체/구현을 누가 만들어 전달하는가?
```

둘은 실제 Application Architecture에서 연결되지만 같은 개념은 아니다.

C++ 관점:

```cpp
Service(Database& db) : db_(db) {}
```

이건 객체 Dependency 주입이고, Header/Library Linking은 Module/Build Dependency 문제다.

---

## 13. 순환 의존관계

```text
Module A → Module B
   ↑          ↓
   └──────────┘
```

Circular Dependency는 다음 문제를 만들 수 있다.

- 초기화 순서 복잡성
- 부분 초기화 상태 노출
- 결합도 증가
- Build/Link/Load 구조 복잡화

언어 Module System마다 순환 참조를 허용하는 방식과 초기화 의미론이 다르다.

---

## 14. 기술사 관점의 비교축

| 비교축 | 질문 |
|---|---|
| 의존관계 결정 시점 | Compile/Link/Load/Runtime 중 언제인가? |
| 노출 단위 | 값, Symbol, Binding, Type, Namespace 중 무엇인가? |
| 정적 분석 | Module Graph를 사전에 분석할 수 있는가? |
| 로딩 | 동기/비동기, Lazy/Eager 중 무엇인가? |
| 배포 | Static/Dynamic Library 또는 Package 단위는 무엇인가? |
| 초기화 | Module State를 언제 생성하고 몇 번 Evaluate하는가? |
| 순환 의존 | 허용 여부와 초기화 규칙은 무엇인가? |

---

## 15. 기억·인출

```text
Module
= 코드를 나누고 외부 계약을 노출

Import / Export
= 무엇을 가져오고 내보내는가

Link
= 외부 참조와 실제 구현을 연결

Load
= 실제 Code/Module을 Memory/Runtime에 올림

Evaluate
= Module Top-level Code 실행
```

핵심 문장:

> **모듈 시스템의 본질은 `import` 문법이 아니라 코드 단위의 경계와 의존관계를 정의하고, 그 참조를 언제 실제 구현과 연결하며 언제 실행 상태를 만드는가에 있다.**
