# 함수 객체와 Closure — Functor · Lambda · Capture · Lexical Scope

> 학습 원칙: [`00-프로그래밍-언어-학습원칙.md`](00-프로그래밍-언어-학습원칙.md)
>
> 핵심 질문: **함수에 상태를 붙여 값처럼 전달하고, 나중에도 그 상태를 사용할 수 있게 하려면 어떻게 해야 하는가?**

---

## 1. 큰 그림

Functor, Lambda, Capture, Closure, Lexical Scope는 서로 같은 개념은 아니지만 함께 볼 때 관계가 잘 보인다.

```text
호출 가능한 코드가 필요하다
        ↓
Function / Function Object
        ↓
객체 자체에 상태를 가질 수 있다
        ↓
Functor
        ↓
익명 함수 객체를 간결하게 만든다
        ↓
Lambda
        ↓
바깥 상태가 필요하다
        ↓
Capture
        ↓
함수와 정의 환경의 관계가 유지된다
        ↓
Closure

Closure가 어떤 바깥 이름을 볼 수 있는가?
        ↓
Lexical Scope
```

이 흐름은 개념의 역사적 발전 순서를 뜻하지 않는다. **C++의 구체적인 메커니즘에서 출발해 Closure와 Lexical Scope를 이해하기 위한 학습 경로**다.

---

## 2. Function Object / Functor — 상태를 가진 호출 가능 객체

C++에서 Functor(Function Object)는 보통 `operator()`를 정의하여 함수처럼 호출할 수 있는 객체를 뜻한다.

```cpp
struct Counter {
    int count = 0;

    int operator()() {
        return ++count;
    }
};

Counter counter;

counter(); // 1
counter(); // 2
counter(); // 3
```

겉으로는 함수 호출처럼 보이지만 실제로는 다음과 같은 멤버 함수 호출이다.

```cpp
counter.operator()();
```

일반 함수와 비교했을 때 중요한 차이는 **객체이므로 상태를 멤버로 가질 수 있다는 점**이다.

```text
일반 함수
→ 실행할 코드

Functor
→ 실행할 코드(operator()) + 객체 상태
```

이 관점이 Closure를 이해하는 첫 번째 발판이다.

---

## 3. Lambda — 익명 Function Object를 만드는 문법

C++ Lambda는 단순히 "이름 없는 함수"라고만 이해하면 내부 구조가 잘 보이지 않는다.

```cpp
int x = 10;

auto f = [x]() {
    return x;
};
```

개념적으로 컴파일러가 다음과 비슷한 익명 타입을 만든다고 생각할 수 있다.

```cpp
struct __Lambda {
    int x;

    int operator()() const {
        return x;
    }
};
```

즉 C++ 관점에서는:

```text
Lambda Expression
        ↓
익명 Closure Type
        ↓
Closure Object
        ↓
operator()를 통해 호출
```

Lambda는 새로운 종류의 "함수"라기보다 **Functor를 언어가 간결하게 만들어 주는 문법**으로 이해하면 구조가 선명해진다.

---

## 4. Capture — Lambda가 바깥 상태를 가져오는 방법

Lambda가 자신이 정의된 바깥 Scope의 값을 사용하려면 Capture가 필요하다.

```cpp
int x = 10;

auto by_value = [x]() {
    return x;
};

auto by_reference = [&x]() {
    return x;
};
```

C++은 Capture 의미를 문법으로 비교적 명시적으로 드러낸다.

```text
[x]
→ 값을 Capture
→ Lambda Object 내부에 값이 들어가는 직관

[&x]
→ 참조 Capture
→ 바깥 객체의 Lifetime을 주의
```

예를 들어 값 Capture는 다음과 비슷하게 생각할 수 있다.

```cpp
struct __Lambda {
    int x;
};
```

따라서 C++에서 Capture를 이해할 때는 먼저 다음을 묻는다.

```text
무엇을 Capture하는가?
→ 값인가, 참조인가?

Capture된 상태는 어디에 있는가?
→ Closure Object 내부인가, 외부 객체를 가리키는가?

Lifetime은 안전한가?
→ 나중에 호출할 때 대상이 살아 있는가?
```

---

## 5. Closure — 함수와 정의 환경이 함께 살아가는 개념

Closure는 특정 언어의 문법 이름이 아니라 **함수와 그 함수가 정의될 때 접근하던 환경의 관계를 함께 유지하는 개념**이다.

JavaScript 예제를 보자.

```javascript
function makeCounter() {
  let count = 0;

  return function () {
    return ++count;
  };
}

const counter = makeCounter();

counter(); // 1
counter(); // 2
counter(); // 3
```

`makeCounter()` 호출은 이미 끝났지만 반환된 함수는 계속 `count`에 접근한다.

```text
makeCounter() 실행
        ↓
count = 0 생성
        ↓
내부 함수 생성
        ↓
내부 함수가 count가 있는 환경을 참조
        ↓
makeCounter() 종료
        ↓
반환된 함수는 계속 count에 접근 가능
```

이때 중요한 것은 **함수가 바깥 값 하나를 단순 복사해서 저장했다**고 일반화하지 않는 것이다.

언어에 따라 Capture와 환경 유지의 의미론이 다르다.

---

## 6. C++ Capture Lambda와 JavaScript Closure의 대응

JavaScript Closure는 C++ Capture Lambda를 떠올리면 이해하기 쉽다.

```cpp
int x = 10;
auto f = [x]() { return x; };
```

```javascript
let x = 10;
const f = () => x;
```

둘 다 다음 직관을 제공한다.

```text
함수 코드
  +
바깥 상태와의 관계
  ↓
나중에 호출 가능한 값
```

하지만 의미론은 다르다.

### C++

```text
[x]
→ 값 Capture

[&x]
→ 참조 Capture

Capture 방식이 문법에 드러남
Lifetime을 개발자가 직접 의식해야 함
```

### JavaScript

```text
함수가 정의된 Lexical Environment의 Binding을 참조
필요한 Environment는 Runtime이 계속 유지
```

다음 예제가 차이를 잘 보여준다.

```javascript
let x = 10;
const f = () => console.log(x);

x = 20;
f(); // 20
```

`f`가 정의될 때 `10`이라는 값을 무조건 복사해 둔 것이 아니다. `x`라는 Binding이 있는 Lexical Environment를 통해 현재 값을 읽는다.

C++ 직관으로는 값 Capture보다는 참조 Capture가 더 비슷해 보인다.

```cpp
int x = 10;
auto f = [&x]() {
    std::cout << x;
};

x = 20;
f(); // 20
```

그러나 JavaScript에서는 C++처럼 dangling reference를 직접 관리하는 구조가 아니다. 필요한 Environment의 Lifetime을 Runtime이 관리한다.

> **JavaScript Closure ≈ C++ Capture Lambda라는 대응은 좋은 출발점이지만, Capture 방식과 Lifetime 관리까지 같다는 뜻은 아니다.**

## 7. Lexical Scope — 함수가 변수를 어디에서 찾는가

Closure를 이해하려면 Lexical Scope를 함께 봐야 한다.

Lexical Scope는 **변수 검색 관계가 함수의 호출 위치가 아니라 코드가 정의된 위치에 의해 결정되는 Scope 규칙**이다.

```javascript
let x = "global";

function foo() {
  console.log(x);
}

function bar() {
  let x = "bar";
  foo();
}

bar(); // global
```

`foo()`는 `bar()` 안에서 호출됐지만 `bar`의 `x`를 사용하지 않는다.

`foo`가 정의된 위치의 바깥 Scope가 Global이기 때문이다.

```text
foo 내부
  ↓ 없으면
foo가 정의된 바깥 Scope
  ↓
Global Scope
```

따라서:

```text
Lexical Scope
→ 함수가 어떤 바깥 이름을 볼 수 있는지 정하는 규칙

Closure
→ 그 Lexical Environment와의 관계를 나중에도 유지하는 현상
```

둘은 관련 있지만 같은 개념은 아니다.

---

## 8. C++ 관점에서 Lexical Scope를 이해하기

C++도 기본적으로 Lexical Scope를 사용한다.

```cpp
int x = 10;

void foo() {
    std::cout << x;
}
```

`foo` 안에서 `x`를 찾을 때 코드의 정적 Scope 구조를 따라 검색한다.

Lambda에서는 이 Scope 안에 있는 이름 중 실제로 사용할 외부 상태를 Capture한다.

```cpp
void outer() {
    int x = 10;

    auto f = [x]() {
        return x;
    };
}
```

C++ 관점에서 다음처럼 구분하면 쉽다.

```text
Lexical Scope
→ 어떤 바깥 이름이 현재 코드 위치에서 보이는가?

Capture
→ 그중 Lambda가 어떤 외부 상태를 가져가는가?

Closure Object
→ Capture된 상태와 호출 코드를 가진 실제 객체
```

JavaScript에서는 Capture 목록을 `[x]`처럼 명시하지 않지만, 함수가 Lexical Scope를 통해 외부 Binding을 참조하면 Closure가 형성될 수 있다.

---

## 9. Lambda와 Closure는 같은 개념이 아니다

다음 C++ Lambda는 아무것도 Capture하지 않는다.

```cpp
auto add = [](int a, int b) {
    return a + b;
};
```

Lambda이지만 외부 상태가 없다.

반면 다음 Lambda는 상태를 Capture한다.

```cpp
int offset = 10;

auto add = [offset](int value) {
    return value + offset;
};
```

따라서 학습할 때 다음처럼 구분한다.

```text
Lambda
→ 익명 함수/Function Object를 만드는 표현 방식

Capture
→ 외부 상태를 가져오는 방식

Closure
→ 함수와 정의 환경이 결합되어 나중에도 관계가 유지되는 개념
```

언어마다 이 세 개념을 표현하는 문법과 Runtime 모델은 다르다.

---

## 10. 왜 Closure가 필요한가

Closure의 핵심 가치는 **행동과 그 행동에 필요한 상태를 하나의 값처럼 전달할 수 있다는 것**이다.

```text
행동
+
상태
↓
하나의 호출 가능한 값
```

대표적으로 다음과 연결된다.

```text
Callback
→ 나중에 실행할 함수가 현재 상태를 기억해야 함

Iterator
→ 순회 상태와 다음 연산을 함께 유지

Event Handler
→ 등록 시점의 Context를 나중에 사용

Async 작업
→ 비동기 완료 후 필요한 상태를 다시 사용
```

예를 들어:

```javascript
function request(id) {
  fetch(`/items/${id}`).then(() => {
    console.log(id);
  });
}
```

비동기 Callback이 나중에 실행되더라도 `id`를 사용할 수 있는 것은 Closure와 연결된다.

이때 **Callback이 언제 실행되는가**는 Event Loop나 Promise Scheduling의 문제이고, **Callback이 `id`를 왜 계속 사용할 수 있는가**는 Closure의 문제다.

```text
무엇을 기억하는가?
→ Closure

언제 실행하는가?
→ Event Loop / Scheduler
```

이 둘을 구분한다.

## 11. 개념 경계 정리

| 개념 | 핵심 질문 | C++ 기준점 |
|---|---|---|
| Function Object / Functor | 함수처럼 호출되는 객체인가? | `operator()` |
| Lambda | 익명 호출 가능 객체를 어떻게 간결하게 만드는가? | Lambda Expression |
| Capture | 외부 상태를 어떻게 가져오는가? | `[x]`, `[&x]` |
| Closure | 함수와 정의 환경의 관계를 어떻게 유지하는가? | Capture Lambda / Closure Object가 좋은 기준점 |
| Lexical Scope | 변수 검색 관계를 무엇이 결정하는가? | 정적 Scope 구조 |

한 줄로 연결하면:

> **Functor는 상태를 가진 호출 가능 객체라는 실체를 보여주고, Lambda는 이를 간결하게 만들며, Capture는 외부 상태를 연결하고, Closure는 함수와 정의 환경의 관계를 보존하며, Lexical Scope는 그 함수가 어떤 외부 이름을 볼 수 있는지 결정한다.**

## 12. 기억·인출

```text
Functor
= 객체인데 ()로 호출

Lambda
= 익명 Functor를 만드는 문법

Capture
= 바깥 상태를 가져옴

Closure
= 함수 + 정의 환경

Lexical Scope
= 호출한 곳이 아니라 정의된 곳을 따라 변수 검색
```

C++ 기준으로 기억하면:

```text
Closure가 헷갈림
  ↓
Capture Lambda를 떠올림
  ↓
Lambda Object 안에는 코드(operator())와 상태가 있음
  ↓
다른 언어에서는 상태를 어떤 방식으로 붙잡는지 확인
  ↓
Capture·Lifetime·Scope 의미론의 차이를 학습
```

> **C++로 실체를 잡고, 언어별 의미론 차이에서 학습을 끝낸다.**
