# 클라우드 배치 유형과 서비스 유형

## 이 문서에서 되짚을 질문

- Multi-Cloud와 Intercloud는 모두 여러 Cloud를 쓰는 것 아닌가?
- BaaS와 Serverless는 Server를 직접 관리하지 않는다는 점에서 같은가?
- XaaS·TaaS 같은 이름을 모두 독립된 기술로 외워야 하는가?

## 두 분류를 나누어야 하는 이유

배치 유형은 자원을 어디에 둘 것인지 묻고, 서비스 유형은 어디까지 공급자에게 맡길 것인지 묻는다. 서로 영향을 주지만 같은 분류가 아니다.

## 배치 유형: 어디에 둘 것인가

### Public Cloud

Cloud 사업자의 공유 Infrastructure를 사용한다. 빠른 확장과 다양한 관리형 서비스가 장점이지만 Data 주권·규제·Vendor 종속·공유 책임을 검토해야 한다.

### Private Cloud

한 조직을 위한 Cloud 환경이다. 통제와 맞춤성이 높지만 구축·운영 비용과 자체 역량이 필요하다. 단순히 가상화 Server가 있다고 Private Cloud가 되는 것은 아니며 Self-Service·자동화·자원 Pooling 등의 운영 특성이 필요하다.

### Hybrid Cloud

Private·On-Premises 환경과 Public Cloud를 업무·Data·Network로 연결한다. 민감 Data는 내부에 두고 변동 부하는 Public에서 처리할 수 있지만, 연계·일관성·보안·운영 도구가 복잡해진다.

### Multi-Cloud

둘 이상의 Cloud 사업자를 사용한다. 서비스별 최적 선택과 공급자 위험 분산이 가능하지만 공통 운영·보안·비용·Data 이동이 어려워진다.

### Intercloud

서로 다른 Cloud가 표준·연동을 통해 자원과 서비스를 교환하는 개념이다. Multi-Cloud가 한 조직이 여러 Cloud를 사용하는 전략이라면 Intercloud는 Cloud 사이의 상호연결과 협력에 초점이 있다.

예를 들어 한 회사가 AWS와 Azure를 업무별로 나누어 쓰면 Multi-Cloud다. 서로 다른 Cloud가 표준화된 방식으로 자원 이동·공동 제공·연합을 수행한다면 Intercloud 관점이다. 실제 답안에서는 용어 자체보다 **사용 주체의 선택 전략인지, Cloud 사이 연동 구조인지**를 구분한다.

## 서비스 유형: 어디까지 맡길 것인가

- IaaS: 공급자가 Server·Storage·Network를 제공하고 사용자가 OS 위를 관리
- PaaS: 공급자가 Runtime·Middleware·개발 실행환경까지 관리
- SaaS: 공급자가 완성된 애플리케이션까지 운영
- BaaS: 인증·DB·Push 같은 Backend 기능을 API로 제공
- FaaS: 사용자가 작성한 함수를 Event 단위로 실행하고 Runtime·확장을 공급자가 관리
- Serverless: Server 준비·확장·Patch 같은 운영 책임을 공급자가 추상화하는 실행·운영 방식
- XaaS: 다양한 IT 자원과 기능을 Service 형태로 제공한다는 포괄 표현

IaaS·PaaS·SaaS는 공급자와 사용자의 관리 책임 경계를 설명하는 큰 틀이다. BaaS·FaaS 같은 이름은 특정 기능이나 실행 방식을 더 구체적으로 부르는 말이다. XaaS나 TaaS처럼 문맥에 따라 뜻이 달라질 수 있는 약어는 이름만 외우지 말고, **무엇을 서비스로 제공하며 누가 어디까지 운영하는가**를 먼저 확인한다.

### XaaS를 어떻게 이해할 것인가

XaaS(Everything/Anything as a Service)는 하나의 구체적인 구현 기술이라기보다, IT 자원과 기능을 필요할 때 Service 형태로 소비한다는 **상위 표현**이다.

따라서 다음과 같이 이해하면 된다.

```text
XaaS
├─ IaaS : Infrastructure
├─ PaaS : Platform
├─ SaaS : Software
├─ BaaS : Backend 기능
├─ FaaS : Function 실행
├─ DBaaS : Database
├─ NaaS : Network
└─ TaaS : 문맥에 따라 Testing 등
```

여기서 중요한 점은 이 목록이 엄격한 계층형 표준 분류표라는 뜻이 아니라는 것이다. XaaS는 여러 `~ as a Service` 모델을 묶어 부르는 포괄 용어이고, 각 약어의 범위와 의미는 문맥과 사업자에 따라 달라질 수 있다.

### TaaS는 왜 주의해야 하는가

TaaS는 단일하게 고정된 표준 약어가 아니다. Cloud·SW 개발 문맥에서는 **Testing as a Service**로 많이 쓰이며, Test 환경·자동화·부하·Browser/Device Test 등을 Service로 제공하는 형태를 말한다.

하지만 다른 분야에서는 Transportation as a Service 등 전혀 다른 뜻으로도 사용될 수 있다. 따라서 시험이나 문서에서 TaaS가 나오면 약어만 보고 단정하지 말고 **주변 문맥에서 무엇을 Service로 제공하는지 먼저 확인**한다.

### BaaS·FaaS·Serverless 관계

BaaS와 Serverless는 관련되지만 같지 않다.

- BaaS는 인증·DB·Storage·Push 같은 Backend 기능을 완성된 Service로 제공한다.
- FaaS는 사용자가 작성한 함수를 Event에 따라 실행하는 방식이다.
- Serverless는 이러한 관리형 서비스를 이용하면서 Server Provisioning·Scaling·Patch 같은 Infrastructure 운영을 개발자에게서 감추는 더 넓은 Architecture/운영 관점이다.

즉 `Serverless = FaaS + BaaS`라는 식으로 수학 공식처럼 고정해서 외우기보다는, **FaaS와 BaaS가 Serverless Architecture에서 자주 사용되는 대표 구성 방식**이라고 이해하는 편이 정확하다.

예를 들어 사용자가 로그인하면 BaaS의 인증 기능을 호출하고, 파일이 업로드될 때 FaaS 함수가 실행되어 썸네일을 생성하며, 결과를 관리형 DB·Storage에 저장하는 구조는 전형적인 Serverless Architecture다.

```text
사용자
  │
  ├─ 인증 ─────→ BaaS(Auth)
  │
  ├─ Data 저장 ─→ 관리형 DB/Storage
  │
  └─ Event ─────→ FaaS(Function)
                     │
                     └─ Business Logic 실행

        ↑ 공급자가 Server 운영·확장을 추상화
                = Serverless 관점
```

Serverless는 Server가 물리적으로 없다는 뜻이 아니다. 실제 Server는 존재하지만 개발자가 개별 Server를 직접 Provisioning·Patch·Scaling하지 않는다는 뜻이다.

## 선택 기준

- 업무 중요도와 장애 영향
- Data 민감도·규제·지역성
- 사용자에게 필요한 제어권
- 기존 기술·운영 역량
- 성능·지연·확장 패턴
- 비용 예측 가능성
- Vendor 종속과 Exit 계획
- SLA·RTO·RPO와 공유 책임

## 전체 흐름

업무와 제약 확인
→ 배치 위치 선택
→ 공급자에게 맡길 관리 범위 결정
→ VM·Container·Serverless 등 실행환경 선택
→ Network·Storage·보안 구성
→ 운영 지표와 비용으로 재평가
