# 쿼리 옵티마이저, 통계와 실행계획

## 이 문서에서 되짚을 질문

- 같은 SQL에 왜 여러 실행 방법이 존재하는가?
- Cost-Based Optimizer는 무엇을 근거로 Plan을 고르는가?
- Cardinality 추정 오류가 왜 큰 성능 문제로 번지는가?
- EXPLAIN과 실제 실행 결과는 어떻게 비교해야 하는가?

## 1. SQL은 논리 표현이고 실행 방법은 별도로 결정된다

SQL은 원하는 결과를 선언한다. DBMS는 그 결과를 만들기 위해 여러 Physical Plan을 비교한다.

```text
SQL
 ↓
Parse / Rewrite
 ↓
후보 Plan 생성
├─ Table / Index Scan
├─ Join Order
└─ Join Algorithm
 ↓
Cardinality 추정
 ↓
Cost 계산
 ↓
가장 낮은 예상 Cost의 Plan 선택
```

Cost는 보통 실제 시간 그 자체가 아니라 I/O·CPU·Memory 등의 상대 비용을 표현하는 내부 단위다.

## 2. Cardinality가 Cost 계산의 출발점이다

Cardinality는 각 연산 뒤에 몇 Row가 남는지에 대한 추정이다. 같은 연산도 처리 Row 수가 달라지면 비용이 크게 달라진다.

```text
Filter 결과 10 Row 예상
→ Index Lookup 반복이 저렴할 수 있음

실제 1,000,000 Row
→ 반복 Lookup이 폭증
```

따라서 실행계획이 잘못된 것처럼 보일 때 먼저 **Optimizer가 입력 Row 수를 얼마나 정확히 예상했는지** 본다.

## 3. 통계가 Cardinality를 만든다

Optimizer는 실제 모든 Row를 매 Query마다 조사하지 않고 수집된 통계를 이용한다.

대표 정보는 다음과 같다.

- 전체 Row 수
- NULL 비율
- Distinct 값 수
- 자주 등장하는 값(MCV)
- 값 분포 Histogram

```text
통계
 ↓
조건 Selectivity 추정
 ↓
Cardinality 추정
 ↓
Access Path / Join Cost 계산
```

대량 적재·삭제나 데이터 분포 변화 뒤 통계가 오래되면 과거 분포를 기준으로 Plan을 선택할 수 있다. PostgreSQL의 `ANALYZE` 같은 기능은 이 통계를 다시 수집한다.

## 4. 실행계획은 Tree로 읽는다

Execution Plan은 보통 자식 Node 결과가 부모 Node로 올라가는 Tree다.

```text
Hash Join
├─ Scan A
└─ Hash
   └─ Scan B
```

가장 안쪽에서 어떤 데이터를 읽는지 확인하고 바깥 연산으로 올라간다.

확인할 핵심은 다음이다.

```text
Access Path
→ Table Scan / Index Scan 등

Estimated Rows ↔ Actual Rows
→ 추정이 맞는가?

Loops
→ 작은 비용이 몇 번 반복되는가?

Sort / Hash
→ Memory를 넘겨 Spill하는가?

Filter
→ 많은 Row를 읽은 뒤 대부분 버리고 있지는 않은가?
```

## 5. EXPLAIN과 실제 실행을 구분한다

`EXPLAIN`은 예상 Plan을 보여주고, `EXPLAIN ANALYZE` 계열 기능은 Query를 실제 실행하여 예상과 실제를 비교할 수 있게 한다.

```text
EXPLAIN
→ Estimated Cost / Rows

EXPLAIN ANALYZE
→ Estimated + Actual Time / Rows / Loops
```

쓰기 Query에 실제 실행 분석을 사용하면 데이터가 변경될 수 있으므로 Transaction과 Rollback 등 안전한 검증 절차가 필요하다.

## 6. JOIN 실행전략과 연결

Cardinality와 Access Path가 바뀌면 적절한 JOIN 전략도 달라진다.

- 작은 Outer + 빠른 Inner Lookup → Nested Loop 후보
- 큰 Equality Join + 충분한 Memory → Hash Join 후보
- 정렬된 입력 활용 → Merge Join 후보

세부 전략은 [[질의최적화와-JOIN-실행전략]]에서 이어서 본다.

## 7. 튜닝 판단 순서

```text
느린 Query
 ↓
실행계획 확인
 ↓
Estimated ↔ Actual Row 비교
 ↓
통계·Selectivity·Access Path 확인
 ↓
반복 횟수·Sort·Spill·I/O 확인
 ↓
Index / SQL / Schema / 통계 조정
 ↓
재측정
```

Hint나 특정 Plan 강제는 현재 데이터 분포에서는 빨라도 분포가 바뀌면 오히려 위험할 수 있으므로 마지막 수단으로 본다.

> **쿼리 튜닝의 핵심은 Plan 이름을 외우는 것이 아니라, Optimizer가 어떤 입력 크기와 비용을 예상했으며 그 예상이 실제와 어디서 달라졌는지 찾는 것이다.**
