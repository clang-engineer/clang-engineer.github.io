# 정보관리기술사 세부학습 작성 규칙

## 0. 작성 전 필수 확인

세부학습 문서를 새로 작성하거나 수정하기 전에 다음 문서를 반드시 먼저 확인한다.

1. [`../00-문서작성-공통원칙.md`](../00-문서작성-공통원칙.md)
2. [`docs/KNOWLEDGE_ORGANIZATION.md`](../../../../docs/KNOWLEDGE_ORGANIZATION.md)
3. [`docs/WRITING_STYLE.md`](../../../../docs/WRITING_STYLE.md)
4. 이 문서(`00-세부학습-작성규칙.md`)

상위 문서를 확인하지 않은 상태에서 세부학습 문서 작성을 시작하지 않는다.

이 문서는 `_archive/license/정보관리기술사/세부학습/` 아래에 작성하는 세부학습 문서의 공통 기준이다.

세부학습 문서의 목적은 **시험 직전 암기용 요약본이 아니라, 학습 과정에서 이해한 내용을 나중에 다시 읽었을 때 그 이해가 복원되는 문서**를 만드는 것이다.

## 상위 학습 자료와의 역할 분리

```text
학습등급표
= 무엇을 얼마나 우선해서 공부할지 정한다.

        ↓ 학습할 Topic 공급

개념지도
= Topic을 상위·하위·인접·비교·의존 관계로 재배치한다.
  다음에 무엇을 파고들지 찾는다.

        ↓ 학습할 꼭지 선택

세부학습
= 선택한 꼭지를 깊게 이해한다.
  왜 필요한가, 어떻게 동작하는가, 무엇과 다른가,
  실제 시스템에서 어디에 위치하는가를 복원할 수 있게 기록한다.
```

개념지도의 Node와 세부학습 파일은 1:1일 필요가 없다. **함께 이해할 때 더 잘 이해되는 개념은 하나의 세부학습 문서에서 같이 다룰 수 있다.**

세부학습 문서에서 내용을 덜어내거나 다른 문서로 이동할 때는 동일 내용이 다른 적절한 세부학습 문서에 충분히 보존되어 있는지 먼저 확인한다. 없다면 먼저 해당 문서를 보강한 뒤 중복을 정리한다.

## 깊이와 범위

세부학습 문서는 **개념을 이해하고 정보관리기술사 답안을 구성하는 데 필요한 깊이까지만 다룬다.** 정확성을 위해 필요한 설명은 충분히 하되, 관련 있다는 이유만으로 구현체·제품·논문 수준의 세부사항까지 계속 확장하지 않는다.

- 기본 범위는 `정의 → 왜 필요한가 → 핵심 구조·동작 원리 → 주요 구성요소 → 대표 비교 → 장단점·Trade-off → 기술사 수준의 적용·고려사항 → 헷갈리기 쉬운 경계`다.
- 새로운 세부 개념을 추가하기 전에 **“이 내용을 빼면 핵심 개념을 잘못 이해하는가?” 또는 “정보관리기술사 답안 구성에 실질적으로 필요한가?”**를 확인한다. 둘 다 아니라면 원칙적으로 생략한다.
- 내부 Algorithm 세부, 수식 전개, 버전별 구현 차이, 특정 제품 옵션, 구현체 내부 구조는 핵심 이해나 기술사 수준의 설명에 꼭 필요한 경우에만 포함한다.
- 논문 수준의 수학적 전개, 특정 구현의 지나친 최적화 세부, 예외 사례의 장시간 나열, 단순히 흥미로운 주변 지식은 기본 범위에서 제외한다.
- 깊이가 필요한 내용이더라도 본문의 핵심 흐름을 깨면 별도 심화 문서나 참고 항목으로 분리하고, 기본 세부학습 문서를 백과사전처럼 만들지 않는다.
- 문서가 길다는 이유만으로 기존의 이해에 필요한 설명을 삭제하지 않는다. **깊이 제한은 핵심 설명을 압축하라는 뜻이 아니라, 핵심에서 불필요하게 더 내려가지 말라는 뜻**이다.

### `99-` 보충학습 문서

기술사 직접 출제 Topic 자체는 아니더라도, 개념지도나 세부학습을 이해하는 과정에서 **이 내용을 모르면 핵심 관계·동작을 잘못 이해하게 되는 기반·실무 개념**은 해당 영역의 `99-*` 세부학습 문서로 분리할 수 있다.

```text
개념지도 / 세부학습에서 이해의 빈틈 발견
        ↓
직접 출제 Topic은 아니지만 이해에 필요
        ↓
해당 영역의 세부학습/99-* 문서에서 보충
        ↓
이해를 복원한 뒤 본 학습 흐름으로 복귀
```

- `99-*`는 `기술사 범위 밖 지식 모음`이 아니라 **본 학습의 이해를 복원하기 위해 파생된 보충학습 문서**다.
- 직접 출제 범위를 넘어갈 수 있지만, 현재 개념의 이해에 필요한 깊이까지만 내려간다. 흥미만으로 계속 확장하지 않는다.
- 별도의 `기반학습/`, `보조학습/` 같은 최상위 분류를 새로 만들기보다 기존 영역의 세부학습 아래에 둔다.
- 일반 세부학습 Topic과 혼동되지 않도록 `99-` Prefix로 성격을 드러낸다.
- 개념지도에서 시작한 설명이 호출 순서·구현 동작·예외 경계 등으로 깊어져 큰 그림을 방해하면, 핵심 관계만 개념지도에 남기고 상세 설명은 `99-*`로 옮길 수 있다.
- `99-*`에서도 **대화 중 실제로 이해가 됐던 설명과 헷갈린 지점**은 우선 보존한다.

## 기억·인출 장치

정보관리기술사 시험에서 즉시 열거·비교·서술해야 하는 핵심 개념은 이해 설명만으로 끝내지 않는다. 문제를 보았을 때 핵심 구조를 빠르게 떠올리고, 세부 내용을 스스로 복원할 수 있는 **기억·인출 장치**를 함께 제시한다.

- 기억·인출 장치는 두문자 암기에 한정하지 않는다. 연상법, 용어 자체의 의미·어원, 대비와 대칭, 인과관계, 단계 흐름, 핵심 질문, 작은 예제, Text/ASCII Diagram 등 해당 개념에 가장 자연스러운 방식을 사용한다.
- 단순히 외우는 문구보다 **왜 그런지 다시 도출할 수 있는 기억법**을 우선한다.
- 예를 들어 Transaction Isolation Level은 `Committed → Repeatable → Serializable`을 `확정된 것만 → 다시 읽어도 같게 → 직렬 실행처럼`으로 연결하고, `Dirty → Non-repeatable → Phantom`이 단계적으로 제거되는 구조로 복원할 수 있다.
- 연상법이나 비유가 실제 개념의 경계를 왜곡하면 사용하지 않는다. 기억하기 쉬운 것보다 정확하게 복원되는 것이 우선이다.
- 모든 개념에 억지 기억법을 붙이지 않는다. 실제로 헷갈리기 쉽거나 시험에서 즉시 인출해야 하는 분류·단계·비교 개념에 선택적으로 적용한다.

## 가지 주제 관리

현재 주제를 이해하는 데 당장 필요하지 않지만 정보관리기술사 학습 가치가 있는 내용이 나오면, 그 자리에서 깊게 확장해 현재 학습 흐름을 끊지 않는다. **연결점만 짧게 확인하고 중앙 학습 TODO에 등록한 뒤 현재 주제로 돌아온다.**

- 가지 주제는 각 세부학습 문서의 TODO Section에 분산해서 관리하지 않고, `_archive/license/정보관리기술사/세부학습/00-학습-TODO.md`에서 통합 관리한다.
- TODO 대상은 `현재 핵심 흐름에는 불필요하지만 나중에 독립적으로 학습할 가치가 있는 주제`다.
- TODO에는 최소한 `무엇을 볼지`, `왜 이 주제가 나왔는지`, `어느 주제와 연결되는지`를 남긴다.
- 필요하면 분야별 Heading 아래에 항목을 배치해 나중에 한곳에서 우선순위와 진도를 확인할 수 있게 한다.
- TODO를 등록했다는 이유로 현재 세부학습 문서 본문에 해당 내용을 미리 상세히 확장하거나 TODO 목록을 복제하지 않는다.
- 현재 개념의 정확한 이해에 반드시 필요한 내용은 TODO로 미루지 않고 현재 흐름에서 설명한다.
- 예를 들어 MVCC 학습 중 PostgreSQL의 `VACUUM`이 나오면 중앙 TODO에 `MVCC의 오래된 Tuple Version 정리와 연결되는 PostgreSQL 주제`라고 등록하고, 현재 학습은 MVCC의 핵심 동작으로 돌아간다.

# 1. 세부학습 문서의 역할

세부학습 문서는 다음 질문에 답할 수 있어야 한다.

```text
이 개념은 전체 주제에서 어디에 위치하는가?
주변 개념과 어떤 관계인가?
왜 필요한가?
무엇을 해결하는가?
내부적으로 어떻게 동작하는가?
비슷한 개념과 무엇이 다른가?
실제 시스템에서는 어디에 위치하는가?
처음 배울 때 왜 헷갈렸는가?
```

> **세부학습 문서는 키워드를 저장하는 곳이 아니라 키워드 사이의 연결과 이해 흐름을 저장하는 곳이다.**

---

# 2. 함께 이해하면 좋은 개념을 하나의 학습 단위로 묶는다

세부학습 파일의 경계를 개별 Keyword 수로 결정하지 않는다.

다음과 같은 관계가 있고 함께 볼 때 이해가 좋아지면 하나의 문서에서 다룰 수 있다.

```text
├─ 문제 → 해결 → 한계 → 확장
├─ A ↔ B 비교·대안
├─ 상위 ↔ 하위
├─ 비슷한 개념의 경계
├─ 선행 → 의존
└─ 실제 시스템에서의 조합·합류
```

복잡하지 않더라도 함께 보는 편이 이해에 도움이 되면 묶는다. 반대로 같은 분야라는 이유만으로 서로의 이해에 도움이 되지 않는 개념은 억지로 합치지 않는다.

스토리는 가능한 묶음 중 하나일 뿐이다. 실제 인과가 없으면 `왜 → 어떻게 → 그래서`를 억지로 만들지 않는다.

---

# 3. 이해가 됐던 설명을 버리지 않는다

대화나 학습 과정에서 처음에는 이해되지 않던 개념이 특정 설명·비유·예제를 통해 이해됐다면 그 부분을 우선 보존한다.

즉 **대화에서 “아, 이제 이해됐다”가 나온 설명은 압축 과정에서 우선적으로 보존한다.**

---

# 4. 실제 인과가 있으면 `왜 → 어떻게 → 그래서`를 우선한다

```text
왜 필요한가
 ↓
어떤 문제가 있었는가
 ↓
어떻게 해결하는가
 ↓
내부적으로 어떻게 동작하는가
 ↓
그래서 어떤 장단점이 생기는가
 ↓
다른 개념과 어떻게 연결되는가
```

실제 인과가 없는 개념에는 이 형식을 강제하지 않고 비교·계층·경계·조합 관계로 설명한다.

---

# 5. 문서의 권장 기본 구조

모든 문서를 같은 Template으로 강제하지는 않지만 다음을 기본으로 한다.

```text
# 주제

이 문서에서 무엇을 이해하려는지 2~4문장

## 1. 가장 먼저 잡을 큰 그림 / 현재 위치 / 핵심
## 2. 전체 흐름 또는 전체 관계
## 3. 왜 필요한가 / 해결하려는 문제
## 4. 핵심 구성요소 또는 내부 동작
## 5. 처음 헷갈리기 쉬운 부분
## 6. 유사 개념과 비교·경계
## 7. 실제 적용 또는 예제
## 8. 장단점 · Trade-off · 운영 고려사항
## 9. 기억 흐름
```

주제에 따라 Section은 생략하거나 변경한다. 핵심은 **세부로 들어가기 전에 현재 개념의 좌표를 잃지 않게 하는 것**이다.

---

# 6. 큰 그림 → 현재 위치 → 관계 → 세부로 내려간다

```text
큰 그림
 ↓
현재 개념의 위치
 ↓
주변 개념과의 관계·경계
 ↓
필요한 상세 원리
 ↓
전체 처리 흐름 / Mechanism
 ↓
세부 구성요소
 ↓
Algorithm · Parameter
```

큰 그림을 보여준다는 이유로 관련 없는 주변 지식을 과도하게 확장하지 않는다.

---

# 7. 처리 과정은 `입력 → 처리 → 출력`으로 표현한다

동작 원리를 설명할 수 있는 주제에서는 단계별 흐름을 적극 사용한다. 각 단계가 **무엇을 입력받고 무엇을 출력하는지**가 보이도록 한다.

---

# 8. 비슷한 개념은 경계를 설명한다

예:

```text
LLM 내부 Embedding vs 검색용 Embedding
RAG vs Fine-tuning
Few-shot vs SFT
API vs MCP
HNSW vs IVF
Verification vs Validation
VLAN vs Subnet
QoS vs QoE
```

같은 단어를 사용하거나 비슷해 보이지만 역할·범위·분류축이 다르면 특히 명확히 구분한다.

---

# 9. 분류축이 다른 개념을 억지로 한 줄에 세우지 않는다

상위/하위 관계인지, 비교 관계인지, 서로 다른 분류축인지 먼저 확인한다.

```text
Fine-tuning
│
├─ [학습 신호 관점]
│   └─ SFT
└─ [Parameter 효율 관점]
    ├─ Full Fine-tuning
    └─ PEFT
        └─ LoRA
```

`CNN → RNN → GAN → Transformer`처럼 서로 다른 축을 하나의 발전 단계로 만들지 않는다.

---

# 10. 학습 중 실제로 생긴 질문을 문서에 반영한다

학습 중 생긴 질문은 개념의 경계를 정확하게 만드는 좋은 자료다. 단순 FAQ로 쌓기보다 자연스러운 Section과 설명 흐름에 녹여 보존한다.

---

# 11. 예제와 비유

추상적인 정의만으로 이해하기 어려우면 작은 예제를 적극 사용한다. 비유는 이해의 발판으로 사용하고 실제 기술과 동일시하지 않는다.

---

# 12. Diagram 작성 규칙

어디서든 읽히는 Text/ASCII Diagram을 기본으로 한다.

짧은 Pipeline, 계층·분류, 반복 Loop, Architecture 비교는 우선 Text Diagram으로 표현한다. Branch나 합류 관계가 복잡해 Mermaid가 확실히 이해를 돕는 경우에만 선택적으로 사용한다.

Mermaid를 사용하지 못하는 GitHub 모바일 앱, Terminal, 일반 Markdown Viewer에서도 핵심 내용을 완전히 이해할 수 있어야 한다. 기존 세부학습 문서를 수정할 때 단순한 Mermaid Diagram이 있으면 가능하면 Text/ASCII Diagram으로 교체한다.

# 13. 기존 문서를 먼저 보강한다

새 파일을 만들기 전에 기존 문서에서 같은 이해 단위를 다루고 있는지 확인한다.

같이 보면 더 잘 이해되는 내용이면 기존 문서를 보강하고, 다음 경우에는 분리를 고려한다.

- 독립적으로 깊게 학습할 가치가 크다.
- 깊이 차이가 커서 본선 흐름을 방해한다.
- 별도 문서로 보아야 관계가 더 명확해진다.
- 하나의 문서 안에서 반복적으로 멀리 왕복해야 한다.

파일 길이 자체는 분리 기준이 아니다.

# 14. 개념지도와 왕복한다

세부학습은 개념지도의 마지막 단계가 아니다.

```text
개념지도에서 위치·관계 파악
        ↓
세부학습에서 깊게 이해
        ↓
새로운 관계·경계·의존성 발견
        ↓
개념지도 보정
```

세부학습에서 새롭게 이해한 관계가 기존 지도와 다르면 지도를 다시 수정한다.

# 16. 한 문장 원칙

> **세부학습은 함께 이해할 때 좋은 개념을 하나의 학습 단위로 묶어, 위치·관계에서 시작해 필요한 만큼 원리와 동작을 깊게 파고들고, 새롭게 이해한 관계를 다시 상위 개념지도에 돌려주는 문서다.**
