# 03. 네트워크 문서 위치와 경계

이 문서는 `03-네트워크` 세부학습 문서가 전체 학습 흐름에서 **어디에 위치하고, 어디까지를 본문에서 다루며, 어디부터 보충학습으로 넘길지**를 정리한다.

본문은 정보관리기술사 Topic 자체의 핵심 원리와 관계를 다루고, 구현 · OS · Runtime · 특정 언어/Framework 수준으로 내려가면 `_보충학습`으로 분리한다.

---

## 1. 전체 위치

```text
Layer 2 경계
VLAN / Broadcast Domain
        ↓
Layer 3 주소와 경계
Subnet / CIDR / VLSM / DHCP / NAT
        ↓
경로 선택
Routing / RIP / OSPF / BGP
        ↓
End-to-End 전송
TCP
        ↓
Application 원격 통신
IPC / RPC / gRPC
        ↓
운영 · 품질
NMS / SNMP / QoS / QoE

별도 축
무선 공유 매체 / WLAN
```

본문 흐름을 이해하다 구현 수준의 질문이 생기면 다음 보충학습으로 내려간다.

```text
FD
↓
Socket Server I/O
↓
I/O Multiplexing
↓
Readiness
↓
Event Loop
↓
Reactor Pattern
↓
Java NIO / Netty
```

## 2. TCP 문서의 위치와 경계

대상 문서: [`TCP-연결-종료-흐름-혼잡제어.md`](TCP-연결-종료-흐름-혼잡제어.md)

### 위치

```text
IP / Routing
    ↓
   TCP
    ↓
HTTP · RPC 등 Application Protocol
```

TCP 문서는 IP 위에서 Application에 **신뢰할 수 있는 Byte Stream**을 제공하기 위해 어떤 문제를 해결하는지 설명한다.

### 본문에 남길 내용

```text
연결 설정 / 종료
Sequence / ACK / 재전송
흐름 제어
혼잡 제어
TIME_WAIT
HTTP Keep-Alive · TCP Keepalive · Connection Pool의 관계
```

TCP 연결이 OS에 상태로 유지되고 Socket · Buffer와 연결된다는 설명은 TCP의 실체를 이해하는 데 필요한 범위까지 본문에 둘 수 있다.

### 보충학습으로 넘길 내용

다음 질문부터는 TCP Topic 자체보다 **OS/Application 구현 관점**이 강해진다.

```text
Application Thread가 accept/read를 어떻게 호출하는가?
Socket과 FD는 어떻게 연결되는가?
Blocking / Non-blocking은 Thread에 어떻게 영향을 주는가?
여러 Socket을 하나의 Thread가 어떻게 기다리는가?
```

이 영역은 다음 문서로 넘긴다.

```text
TCP
↓
Socket-서버-IO.md
↓
FD-File-Descriptor.md
↓
IO-Multiplexing-EventLoop-Reactor.md
```

> **TCP 본문은 전송 계층의 원리까지, Socket 이후의 실행 구조는 보충학습으로 분리한다.**

## 3. IPC · RPC · gRPC 문서의 위치와 경계

대상 문서: [`IPC-RPC-gRPC-원격호출.md`](IPC-RPC-gRPC-원격호출.md)

이 문서는 서로 다른 종류의 개념이 한 흐름에서 만나는 문서다.

```text
Process 경계
    ↓
IPC
= 데이터를 어떻게 전달할 것인가

Application 호출 모델
    ↓
RPC
= 원격 기능을 어떻게 함수 호출처럼 추상화할 것인가

구체 Framework
    ↓
gRPC
= RPC 모델을 어떤 기술 조합으로 구현할 것인가
```

### IPC의 위치

IPC는 운영체제 관점의 **프로세스 간 통신 메커니즘**이다.

```text
Pipe
Unix Domain Socket
Message Queue
Shared Memory
```

따라서 IPC 전체를 네트워크 기술로 동일시하지 않는다.

### RPC의 위치

RPC는 프로세스나 시스템 경계를 넘어 메시지를 주고받는 과정을 **원격 Procedure 호출 모델**로 추상화한다.

```text
Application
↓
RPC Stub / Proxy
↓
Serialization
↓
IPC 또는 Network Transport
```

### gRPC의 위치

gRPC는 RPC라는 개념을 구현한 구체 Framework다.

```text
RPC Semantics
↓
gRPC
↓
Protocol Buffers / Stub
↓
HTTP/2
↓
TCP
```

### 문서 경계

본문에서는 IPC · RPC · gRPC의 **역할과 추상화 수준의 차이**를 중심으로 다룬다.

Socket API, FD, Event Loop, Netty 같은 실제 실행 계층으로 내려가면 `_보충학습`으로 넘긴다.

> **IPC는 전달 메커니즘, RPC는 호출 모델, gRPC는 구체 Framework다. 같은 층의 기술 목록이 아니다.**

## 4. WLAN 문서의 위치와 경계

대상 문서: [`무선-매체접근과-WLAN.md`](무선-매체접근과-WLAN.md)

무선 문서는 유선 Network 흐름의 단순 다음 단계라기보다 **Layer 1/2의 공유 매체 접근이라는 별도 축**으로 본다.

```text
공유 무선 매체
↓
Carrier Sense
↓
Collision Detection이 어려움
↓
CSMA/CA
↓
Authentication / Association
↓
보안 Key 협상
↓
DHCP
↓
IP 통신
```

### 본문에서 잡을 핵심

```text
공유 매체라는 특성
CSMA/CD와 CSMA/CA 차이
Hidden Node
RTS / CTS
Authentication / Association
보안 협상
DHCP와 IP 통신으로 넘어가는 경계
```

특히 다음 상태를 분리한다.

```text
AP가 보인다
≠ 인증 완료
≠ Association 완료
≠ 보안 협상 완료
≠ IP 획득 완료
≠ 정상 IP 통신 가능
```

### 보강 방향

WLAN 문서는 CSMA/CA만 설명하는 문서가 아니라 **무선 Link가 형성되고 IP Network에 진입하기까지의 전체 흐름**을 보여주는 문서로 유지한다.

따라서 특정 AP 제품 설정, Driver별 문제 해결, OS별 명령어 같은 내용은 본문 범위를 넘는다.

> **WLAN 본문의 핵심은 공유 무선 매체의 접근 제어와 Layer 2 연결이 Layer 3 IP 통신으로 이어지는 경계를 이해하는 것이다.**

## 5. 본문과 보충학습을 나누는 판정 기준

새 내용을 추가할 때 다음 질문으로 위치를 결정한다.

```text
이 내용이 기술사 Topic 자체의 원리 · 구조 · 비교 · Trade-off를 설명하는가?
→ 본문

이 내용이 OS 내부 구현, Thread 실행, FD, System Call, Runtime, 특정 언어/Framework 동작을 설명하는가?
→ _보충학습
```

다만 본문 개념을 이해하기 위해 구현 설명이 꼭 필요한 경우에는 **핵심 원리를 설명할 정도까지만 본문에 두고**, 더 깊은 실행 구조는 보충학습으로 연결한다.

## 6. 공통 작성 형식

가능하면 각 문서는 다음 흐름을 유지한다.

```text
# 제목

## 이 문서의 위치
전체 학습 흐름에서 앞뒤 문서와 Layer / 역할을 표시

## 이 문서에서 되짚을 질문
헷갈리는 경계와 왜 필요한지를 질문으로 제시

## 왜 이 순서로 학습하는가
개념을 문제 발생 순서와 인과관계로 연결

## 본문
왜 필요한가 → 어떻게 해결하는가 → 무엇이 다른가

## 기억 흐름 / 한 번에 연결하기
전체 관계를 다시 압축
```

모든 문서가 이 제목을 기계적으로 동일하게 가질 필요는 없지만, **위치 → 질문 → 인과 흐름 → 개념 경계 → 전체 연결**이라는 사고 순서는 유지한다.

## 7. 가장 중요한 원칙

```text
역사적으로 나중에 등장했다
≠ 반드시 Runtime에서 바로 아래 기술을 호출한다

개념적으로 상위 추상화다
≠ 구현에서 모든 중간 계층을 반드시 거친다
```

따라서 문서에서는 필요할 때 다음 세 가지를 구분한다.

```text
역사적 발전 순서
개념적 추상화 관계
실제 Runtime 호출 / 의존 경로
```

목표는 기술 이름을 계층처럼 외우는 것이 아니라, **각 기술이 어떤 문제를 해결하고 실제로 어느 계층과 연결되는지 설명할 수 있게 하는 것**이다.
