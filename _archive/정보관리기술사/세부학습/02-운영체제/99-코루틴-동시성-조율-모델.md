# 코루틴과 동시성 조율 모델

> 연결: [[../../개념지도/02-운영체제/01-실행모델-CPU-배분|실행 모델과 CPU 배분]] · [[../../개념지도/02-운영체제/02-동시성-자원공유|동시성과 자원 공유]]
>
> 성격: `99-*` 보충학습. Thread·Synchronization의 기본 개념을 현대 Language Runtime의 Coroutine·Async·Channel·Actor와 연결하기 위한 문서다.

## 1. 먼저 서로 다른 질문을 분리한다

동시성 문맥에서는 비슷한 단어가 쉽게 섞인다.

```text
Thread
→ 어떤 실행 흐름을 OS/Runtime이 Scheduling하는가?

Coroutine
→ 실행을 중단하고 상태를 보존한 채 재개할 수 있는가?

Blocking / Non-Blocking
→ 호출한 실행 흐름이 대기 때문에 멈추는가?

Sync / Async
→ 완료 결과가 현재 호출 흐름에서 직접 이어지는가?

Mutex / Channel / Actor
→ 여러 실행 흐름이 상태와 Message를 어떻게 조율하는가?
```

이 개념들은 하나의 발전 단계가 아니라 서로 다른 축이다.

## 2. Coroutine — Suspend / Resume 가능한 실행 상태

일반 함수는 호출 후 실행을 이어가다가 Return하면 해당 호출의 실행 위치를 다시 이어갈 수 없다.

```text
일반 함수
Call → Execute ─────────→ Return

Coroutine
Start → Execute → Suspend ⇢ Resume → Execute → ... → Complete
```

Coroutine의 핵심은 **Suspend 시점의 실행 위치와 필요한 상태를 보존하고 나중에 Resume하는 것**이다.

보존해야 하는 대표 상태:

- 다음 실행 위치
- 중단 이후 필요한 지역 변수
- 호출·예외 처리 등 실행 Context

### Stackless와 Stackful

```text
Coroutine의 본질
= Suspend / Resume + State 보존

구현 방식
├─ Stackless → 필요한 상태를 Coroutine Frame/State Machine으로 변환
└─ Stackful  → 독립 실행 Stack 자체를 보존
```

`Stackless vs Stackful`은 Coroutine 여부가 아니라 상태 보존 구현의 차이다.

## 3. Coroutine과 Thread는 대체 관계가 아니다

| 구분 | Thread | Coroutine |
|---|---|---|
| 중심 질문 | 실행 흐름 Scheduling | 실행 상태의 Suspend/Resume |
| Scheduling | OS 또는 Runtime | Runtime/Executor 정책과 결합 |
| 상태 | Stack·Register 등 | Frame 또는 Stack 등 구현 의존 |
| 관계 | Coroutine을 실행하는 기반이 될 수 있음 | 하나 이상의 Thread 위에서 실행 가능 |

따라서:

```text
Coroutine
≠ Thread를 더 가볍게 만든 것이라고만 정의
```

실제 Runtime은 소수 Thread 위에 많은 Coroutine/Task를 Scheduling할 수 있다.

## 4. async / await — Coroutine을 표현하는 대표 문법

많은 Language에서 `async/await`은 Stackless Coroutine을 다루는 대표 문법이다.

```text
Async Function
   ↓
I/O 요청
   ↓
await
   ↓
현재 Coroutine Suspend
   ↓
제어권을 Event Loop / Executor에 반환
   ↓
다른 준비된 Task 실행
   ↓
I/O 완료
   ↓
Coroutine Resume
```

중요한 경계:

- `await`을 쓴다고 새 Thread가 자동 생성되는 것은 아니다.
- Coroutine 내부에서 Blocking API를 호출하면 그 Coroutine을 실행하던 Thread가 막힐 수 있다.
- Coroutine 자체가 Event Loop나 Executor를 자동 제공하는 것은 아니다.

## 5. Go goroutine과 Coroutine의 경계

Go goroutine은 Go Runtime이 Scheduling하는 **Stackful 경량 실행 단위**다.

```text
Coroutine 일반 개념
→ Suspend / Resume 가능한 실행 상태

goroutine
→ Go Runtime이 Scheduling하는 경량 동시 실행 단위
```

둘은 관련 있지만 Scheduling 의미론과 문법까지 동일하지 않다.

## 6. 동시성 조율 — 공유 상태와 Message 전달

여러 실행 흐름이 같은 Mutable State를 동기화 없이 접근하면 Race Condition이 발생할 수 있다.

해결은 크게 두 방향으로 본다.

```text
공유 상태를 유지
→ Mutex / Semaphore / Atomic 등으로 보호

공유 자체를 줄임
→ Channel / Message Passing / Actor로 Data 전달 규약 구성
```

둘은 상호배타적인 철학이 아니다. 실제 시스템에서는 함께 사용한다.

## 7. Shared-State 모델 — Critical Section을 보호한다

```text
Shared Mutable State
        ↓
동시 Read / Write
        ↓
Race Condition
        ↓
Critical Section
        ↓
Mutex / Lock
```

Mutex는 보통 한 번에 하나의 실행 흐름만 Critical Section에 들어가게 한다.

Semaphore는 Count를 통해 동시에 사용할 수 있는 Resource 수를 제한할 수 있다.

```text
Mutex
→ 1개 실행 흐름의 배타 진입

Semaphore
→ N개 Resource / 동시성 한도 관리
```

동기화에는 Waiting·Contention·Deadlock 가능성이라는 비용이 따른다.

## 8. Message Passing — 공유를 통신 규약으로 줄인다

Channel을 통해 값을 전달하면 공유 Mutable State를 줄이기 쉽다.

```text
Producer
  ↓ Message
Channel / Queue
  ↓
Consumer
```

하지만 Message 전달 자체가 항상 Ownership 이전을 강제하는 것은 아니다.

예를 들어 Pointer·Slice·Map처럼 동일한 Backing State를 가리키는 값을 보낸 뒤 송신 측이 계속 수정하면 Data Race가 발생할 수 있다.

따라서:

```text
Channel 사용
≠ Race 자동 제거

Channel + 공유를 줄이는 Ownership-like 규약
→ 동기화 복잡성 감소 가능
```

## 9. Actor — 상태를 실행 단위 안에 가둔다

Actor Model은 각 Actor가 자기 상태를 소유하고 외부와 Message로만 통신하도록 한다.

```text
Actor A state
   ↑↓ Message
Mailbox
   ↑↓
Actor B state
```

Actor가 Message를 순차 처리하면 내부 상태에 대한 Lock 필요성을 줄일 수 있다.

적합한 경우:

- 독립된 상태 단위가 명확함
- Message 기반 Workflow
- Failure Isolation이 중요함

대가:

- Message Ordering·Mailbox Backpressure 고려
- 분산 환경에서는 Delivery·Retry·중복 처리 문제 추가

## 10. Rust가 보여주는 Type 기반 동기화 경계

Rust는 Shared-State와 Message Passing을 모두 제공하지만 Safe API가 잘못된 공유 경로를 줄인다.

```text
Mutex<T>
→ Data와 Lock을 하나의 Type Boundary 안에 둠
→ Guard 없이 내부 T 접근 제한

Send / Sync
→ Type이 Thread 사이 이동·공유에 안전한지 Compile Time 경계 제공
```

이는 Mutex 자체를 없애는 것이 아니라 **잠금 누락이나 안전하지 않은 공유 경로를 Type System으로 좁히는 접근**이다.

## 11. Coroutine이라고 Lock이 사라지는 것은 아니다

Single Thread Event Loop에서도 `await` 사이에 다른 Coroutine이 실행될 수 있다.

```text
Read shared state
↓
await   ← 다른 Coroutine 실행 가능
↓
Write shared state
```

따라서 Logical Race나 Lost Update가 가능하다.

Coroutine은 **실행을 어떻게 멈추고 이어가느냐**, Synchronization은 **여러 실행 흐름이 같은 상태를 어떻게 안전하게 다루느냐**의 문제다.

## 12. 전체 관계

```text
동시 실행
│
├─ 실행 단위·Scheduling
│   ├─ Process / Thread
│   ├─ Coroutine / Task
│   └─ Event Loop / Executor
│
├─ 대기·완료 방식
│   ├─ Blocking / Non-Blocking
│   └─ Sync / Async
│
└─ 상태 조율
    ├─ Shared State
    │   ├─ Mutex
    │   ├─ Semaphore
    │   └─ Atomic
    │
    └─ Message Passing
        ├─ Channel / Queue
        └─ Actor / Mailbox
```

> **Coroutine은 Suspend/Resume 가능한 실행 상태이고, Thread·Executor는 Scheduling의 축이며, Mutex·Channel·Actor는 공유 상태와 통신을 조율하는 축이다. 서로 다른 질문을 한 단계처럼 섞지 않는다.**
