# 커널 구조: Monolithic / Microkernel / Hybrid

> 연결: [[../../../개념지도/02-운영체제/01-실행모델-CPU-배분|실행 모델과 CPU 배분]]
>
> 성격: `99-*` 보충학습. Kernel이 운영체제 서비스를 어디에 배치하는지와 그에 따른 성능·격리·확장성 Trade-off를 정리한다.

## 1. 핵심 질문은 "어디까지 Kernel 안에 둘 것인가"다

Application은 보호된 Hardware 자원을 직접 제어하지 않고 System Call을 통해 Kernel 서비스를 요청한다.

```text
Application
  ↓ System Call
Kernel
  ↓
CPU / Memory / Device
```

Kernel Architecture는 이 경계 안에 **얼마나 많은 운영체제 기능을 포함할 것인가**를 결정하는 구조적 선택이다.

```text
Kernel 내부에 많이 배치
        ↓
Monolithic Kernel

Kernel은 최소 기능만 유지
        ↓
Microkernel

두 접근을 절충
        ↓
Hybrid Kernel
```

## 2. Monolithic Kernel

Monolithic Kernel은 Process 관리, Memory 관리, File System, Network, Device Driver 등 대부분의 핵심 OS 서비스를 Kernel Space에서 수행하는 구조다.

```text
User Space
└─ Application
      ↓ System Call
----------------------------
Kernel Space
├─ Process / Scheduling
├─ Memory Management
├─ File System
├─ Network Stack
└─ Device Driver
----------------------------
Hardware
```

서비스가 같은 Kernel Address Space 안에서 동작하므로 서로 직접 함수 호출하기 쉽고 통신 비용이 작다.

```text
장점
├─ 서비스 간 호출 비용이 작음
└─ 높은 성능에 유리

단점
├─ Kernel 규모와 복잡도 증가
└─ Driver 등 한 구성요소의 오류가 Kernel 전체에 영향을 줄 수 있음
```

Linux는 기본적으로 Monolithic Kernel 계열이지만 Loadable Kernel Module을 통해 Driver나 기능을 동적으로 추가·제거할 수 있으므로 흔히 **Modular Monolithic Kernel**로 설명한다.

## 3. Microkernel

Microkernel은 Kernel에는 핵심 Mechanism만 남기고 File System, Network, Device Driver 같은 서비스를 User Space의 독립 Server로 분리하는 구조다.

```text
User Space
├─ Application
├─ File Server
├─ Network Server
└─ Device Driver
       ↕ IPC / Message Passing
----------------------------
Microkernel
├─ IPC
├─ Scheduling
└─ 최소 Memory Management
----------------------------
Hardware
```

서비스가 서로 다른 Address Space에 분리되므로 직접 함수 호출보다 IPC와 Message Passing을 통해 협업한다.

```text
장점
├─ 장애 격리
├─ 서비스 독립성
├─ 유지보수·확장성
└─ 최소 Kernel로 Trusted Computing Base 축소에 유리

단점
├─ IPC 비용
├─ User ↔ Kernel 전환 비용
└─ 서비스 간 통신이 많으면 성능 부담 증가 가능
```

대표적인 예로 MINIX 3, QNX 등을 들 수 있다.

## 4. Hybrid Kernel

Hybrid Kernel은 Microkernel의 모듈화·구조화 아이디어를 받아들이면서 성능이 중요한 여러 서비스를 Kernel Space에 배치하는 절충 구조다.

```text
Microkernel 설계 사상
        +
성능이 중요한 서비스의 Kernel 배치
        ↓
Hybrid Kernel
```

따라서 Hybrid는 단순히 "Monolithic과 Microkernel의 정확한 중간"이라기보다 **격리·모듈성과 성능 사이에서 실제 구현을 절충한 구조**로 이해하는 것이 좋다.

## 5. 세 구조의 비교축

| 비교축 | Monolithic | Microkernel | Hybrid |
|---|---|---|---|
| Kernel 내부 기능 | 많음 | 최소화 | 선택적으로 많이 포함 |
| 서비스 위치 | 주로 Kernel Space | 다수 User Space Server | 혼합 |
| 서비스 간 통신 | Kernel 내부 함수 호출 | IPC / Message Passing 중심 | 내부 호출 + IPC |
| 성능 | 유리 | IPC 오버헤드 가능 | 성능과 구조성 절충 |
| 장애 격리 | 상대적으로 약함 | 상대적으로 강함 | 절충 |
| 확장·유지보수 | Kernel 복잡도 증가 가능 | 서비스 단위 분리 용이 | 구현에 따라 다름 |

핵심 Trade-off는 다음과 같다.

```text
Monolithic
성능 ↑
Kernel 내부 결합도·장애 영향 범위 ↑

        ↕ Trade-off

Microkernel
격리·모듈성 ↑
IPC / Context Switch 비용 ↑
```

## 6. 왜 Microkernel에서 IPC가 중요해지는가

Monolithic Kernel에서는 File System이나 Driver가 같은 Kernel Space에 있으므로 내부 함수 호출로 연결될 수 있다.

Microkernel에서는 여러 서비스가 별도 Process/Server로 분리된다.

```text
Application
   ↓ 요청
File Server
   ↓
Microkernel의 IPC
   ↓
Driver Server
```

따라서 Microkernel을 이해할 때 IPC는 단순한 Process 통신 기법이 아니라 **분리된 OS 서비스를 연결하는 핵심 Mechanism**으로 본다.

이 지점에서 [[../../../개념지도/02-운영체제/02-동시성-자원공유|동시성과 자원 공유]]의 IPC와 연결된다.

## 7. System Call과 Context Switch와의 관계

Kernel 구조와 System Call, IPC, Context Switch는 서로 같은 개념이 아니다.

```text
System Call
= Application이 Kernel 서비스를 요청하는 경계

IPC
= 서로 격리된 실행 주체가 통신하는 Mechanism

Context Switch
= 실행 중인 Process / Thread가 바뀌는 상태 전환

Kernel Architecture
= OS 서비스를 Kernel / User Space 어디에 배치할지에 대한 구조
```

Microkernel에서는 User Space Server 사이의 IPC가 많아질 수 있고, 구현 방식에 따라 Address Space 전환이나 Scheduling이 동반되어 추가 비용이 발생할 수 있다. 따라서 단순히 "IPC = Context Switch"라고 동일시하지 않는다.

## 8. 복습용 핵심 좌표

```text
Kernel Architecture
│
├─ Monolithic Kernel
│   ├─ OS 서비스 대부분 Kernel Space
│   ├─ 내부 함수 호출
│   └─ 성능 ↑ / 장애 영향 범위 ↑
│
├─ Microkernel
│   ├─ Kernel은 최소 Mechanism
│   ├─ 서비스는 User Space Server
│   ├─ IPC / Message Passing
│   └─ 격리·확장성 ↑ / 통신 비용 ↑
│
└─ Hybrid Kernel
    └─ 구조적 분리와 성능을 절충
```

기술사 답안에서는 다음 문장으로 압축할 수 있다.

> Kernel 구조는 운영체제 서비스를 Kernel Space에 배치하는 범위에 따라 Monolithic, Microkernel, Hybrid로 구분하며, 서비스 내부 호출에 따른 성능과 IPC 기반 분리에 따른 장애 격리·확장성 사이의 Trade-off를 갖는다.
