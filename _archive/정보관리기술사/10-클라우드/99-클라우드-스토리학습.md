# 클라우드 스토리 학습 — 주문 폭주를 감당하는 인프라

> [클라우드 전체 개념지도](00-전체.md)의 배치·서비스·실행·운영·통제 관점을 가상 유통기업의 선택으로 이해한다. 이들은 **필수 구축 순서가 아니라 서로 다른 분류축**이다.

위 그림은 **본문을 읽을 때 따라갈 학습 경로**다. 실제 인과관계가 없는 개념을 필수 선후 단계로 해석하지 않는다.

## 1. 행사 때만 주문이 폭주한다 — 왜 클라우드인가?

유통회사는 평소 주문이 적지만 행사 날에는 요청이 급증한다. 최대 부하에 맞춰 서버를 사면 평소에는 남고, 적게 사면 행사 때 느려진다.

**질문: 필요할 때 자원을 확보하고 부하가 줄면 반납할 수 있을까?**

클라우드는 컴퓨팅 자원을 네트워크를 통해 필요에 따라 제공·할당·관리한다. 자원 풀링, 프로비저닝, 자동화, 사용량 기반 과금 등이 핵심이다.

**질문: VM을 사용하면 이미 클라우드인가?**

아니다. 가상화는 물리 자원·실행환경의 추상화 기술이고 클라우드는 자원을 서비스로 제공하는 모델이다. 가상화는 기반이 될 수 있지만 동의어는 아니다. [가상화 전체 지도](../99-가상화/00-전체.md)에서 구분한다.

## 2. 어디에 두고 누가 관리할까 — 배치·서비스 모델

고객 데이터는 자체 환경에 두고 주문 서비스를 외부 클라우드에 운영하려 한다.

**질문: Public·Private·Hybrid·Multi-Cloud는 무엇을 구분할까?**

자원의 배치와 활용 환경에 관한 관점이다. Hybrid는 서로 다른 환경의 결합, Multi-Cloud는 여러 클라우드 공급자의 활용을 뜻하며 겹칠 수 있다.

**질문: IaaS·PaaS·SaaS도 서버의 배치 위치를 뜻할까?**

아니다. 이들은 공급자가 무엇을 서비스로 제공하고 사용자가 어디까지 관리하는지의 구분이다. IaaS는 인프라, PaaS는 애플리케이션 실행 플랫폼, SaaS는 완성된 소프트웨어 서비스에 초점을 둔다. Shared Responsibility는 모델에 따라 달라진다.

배치 모델: 어디에·어떤 환경으로?
서비스 모델: 무엇을 서비스로 받고 누가 관리?
~~~

## 3. 서버를 클릭해서 만들면 내부에서는 무엇이 일어날까 — 인프라

사용자가 가상 서버를 요청한다.

**질문: 사용자가 물리 서버를 직접 설치·배선해야 할까?**

아니다. Compute·Network·Storage가 서비스로 제공되고, 내부적으로 자원 추상화·Resource Pooling·Provisioning·Orchestration이 자원을 할당하고 운영한다. VPC/Subnet은 가상 네트워크 구성, Block·File·Object는 저장 방식의 차이다.

**질문: 서비스로 보이는 가상 서버와 물리 구현은 일대일일까?**

아니다. 사업자 내부의 가상화·네트워크·스토리지 기술과 사용자 서비스는 서로 다른 계층이다. [클라우드 인프라 구성과 관리](클라우드-인프라-구성과-관리.md)에서 구조를 더 본다.

## 4. 앱을 클라우드에 옮기면 자동으로 Cloud Native일까?

기존 주문 서비스를 VM으로 옮겼지만 여전히 수동 배포와 고정 용량에 의존한다.

**질문: 클라우드에서 실행한다는 사실만으로 탄력성·자동화·복원력을 활용하고 있을까?**

아니다. Cloud Native는 클라우드 특성을 활용하도록 애플리케이션을 설계·배포·운영하는 접근이다. MSA는 서비스 분할이라는 설계, Container는 실행환경 격리, Kubernetes는 배포·확장 관리, Observability는 Metrics·Logs·Traces로 상태를 파악하는 관점이다.

**질문: MSA·Container·Kubernetes를 모두 써야 Cloud Native일까?**

아니다. 이들은 대표적인 수단이지 모두 필수인 구성요소가 아니다. Serverless 역시 VM·Container와 같은 격리 기술이 아니라 운영 추상화 관점이다.

## 5. 자동 확장만 하면 장애에도 안전할까 — 운영·신뢰성

행사 중 부하가 증가하자 Auto Scaling으로 인스턴스를 늘렸다. 그런데 데이터 저장소에 장애가 발생해 주문 서비스가 중단됐다.

**질문: Auto Scaling이 곧 HA·DR·Backup일까?**

아니다. Auto Scaling은 부하 변화에 따른 자원 증감, HA는 구성요소 장애 중 서비스 지속, DR은 대규모 장애 뒤 복구, Backup은 데이터 손실 대비 사본·복원 수단이다. 서로 다른 문제를 해결한다.

**질문: 상태를 관찰하지 않고 자동화만 해도 충분할까?**

아니다. Observability로 상태와 원인을 파악하고 SLA·비용·성능을 함께 관리해야 한다.

## 6. 공급자가 운영하니 보안 책임도 모두 공급자 것일까?

클라우드 사업자가 물리 서버를 관리한다. 그런데 회사가 공개 저장소에 고객 정보를 잘못 설정했다.

**질문: 사고 책임은 전적으로 사업자에게 있을까?**

아니다. **Shared Responsibility(공유 책임)**는 공급자와 사용자가 담당하는 보안·운영 범위를 구분한다. IAM·암호화·격리·규제 준수는 서비스 모델과 구성에 따라 책임이 달라진다. Multi-Tenancy, SLA, Compliance, CSAP/ISO 인증, Sovereign Cloud의 데이터 주권 요구도 설계·운영 전반의 판단 축이다.
