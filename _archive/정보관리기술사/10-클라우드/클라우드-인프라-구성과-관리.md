# 클라우드 인프라 구성과 관리

> [클라우드 전체 개념지도](00-전체.md) → Cloud Infrastructure  
> 범위: 성안당 Vol.10의 네트워크(PART 4), 스토리지(PART 5), 기반 기술(PART 7) 중 **인프라 구성과 관리의 관계**를 이해하는 데 필요한 내용.

## 1. 큰 그림 — 클라우드 서비스를 제공하는 기반

Cloud Infrastructure는 **클라우드가 제공하는 Compute·Network·Storage 자원**과 **이 자원을 구성·관리해 서비스로 제공하는 기술**로 나누어 이해한다.

```text
Cloud Infrastructure
│
├─ 기반 자원 — 무엇을 제공하나?
│  ├─ Compute — 어디서 실행?
│  │  └─ Bare Metal / VM / Container
│  ├─ Network — 어떻게 연결·통신?
│  │  └─ VLAN / VPN / 3-Tier / Spine-Leaf
│  └─ Storage — 어떻게 저장·접근?
│     ├─ Block / File / Object
│     └─ DAS / NAS / SAN
│
└─ 구성·관리 기술 — 자원을 어떻게 운영하나?
   ├─ 가상화 — 자원 추상화·격리
   ├─ SDN / NFV — 제어·기능 가상화
   ├─ Pool / Tiering / Provisioning / RAID — 저장 자원 관리·보호
   ├─ Converged / HCI — 인프라 통합
   └─ OpenStack — 클라우드 자원 서비스화·관리
```

**관계:** 자원은 서비스의 기반이고, 구성·관리 기술은 해당 자원을 추상화·연결·할당·보호하는 수단이다. 한 기술이 여러 자원에 걸쳐 적용될 수도 있다.

### 클라우드 서비스 제공 흐름 — VM 생성 예시

**구성 기술이 실제로 어떻게 연결되는지** 보기 위한 대표 흐름이다. 아래는 일반적인 개념 모델이며 사업자마다 구현은 다르다.

```text
사용자: "VM 하나 생성해 줘"
             │ API / Console 요청
             ▼
클라우드 관리 플랫폼 (예: OpenStack)
├─ 인증·권한 확인
├─ Compute 자원 확인·배치 결정
└─ Network / Storage 구성 요청
             │
       ┌─────┼────────────┐
       ▼     ▼            ▼
    Compute Network     Storage
    VM 생성  가상 NIC·망   Volume 할당
       │     연결          │
       └─────┼────────────┘
             ▼
       실행 가능한 VM 제공
             │
             ▼
     상태·사용량 관측 / 운영
```

- **Compute:** Hypervisor 등을 통해 VM 실행환경을 준비한다.
- **Network:** 가상 네트워크와 NIC를 연결하고 필요한 라우팅·보안 정책을 적용한다. SDN은 이런 제어를 구현하는 한 접근이다.
- **Storage:** 필요한 경우 Block Volume을 생성·연결한다.
- **관리 플랫폼:** 사용자의 요청을 받아 자원 할당과 구성 작업을 조정한다. NFV는 방화벽·라우터 같은 네트워크 기능을 소프트웨어로 제공할 때 활용할 수 있지만, **VM 생성 과정의 필수 단계는 아니다**.

즉, **인프라 구성 기술은 무엇으로 만드는가**, **서비스 제공 흐름은 요청을 받아 그 자원들을 어떻게 묶어 제공하는가**를 보여준다.

### 사용자 서비스와 사업자 내부 구현

```text
클라우드 사용자 — 무엇을 이용하나?
├─ VM / Container 실행
├─ VPC · Subnet · Routing 설정
└─ Block / File / Object Storage 이용
                 │ 서비스 요청
                 ▼
클라우드 사업자 — 어떻게 제공하나?
├─ Compute : 물리 서버 · 가상화
├─ Network : 네트워크 제어(SDN 등)
│            가상 네트워크 기능(NFV 등)
├─ Storage : 저장장치 · Pool · Provisioning
└─ 관리    : 자원 할당 · 자동화 · 모니터링
                 │
                 ▼
          물리 서버 · 네트워크 장비 · 디스크
```

**사용자는 서비스와 설정을 이용하고, 사업자는 기반 기술로 이를 구현한다.** 다만 VPC·방화벽 같은 서비스가 반드시 특정 SDN·NFV 구조로 구현되는 것은 아니며 사업자마다 다르다.

온프레미스에서는 네트워크 관리자가 스위치·라우터별 경로와 정책을 설정하고 전용 방화벽 장비를 설치하곤 했다. 이를 비교하면 **SDN은 제어 기능을 패킷 전달 기능과 분리해 소프트웨어로 관리하는 접근**, **NFV는 전용 방화벽·라우터의 기능을 범용 서버에서 소프트웨어로 실행하는 접근**이다. 둘은 서로 대체하지 않으며 함께 활용할 수 있다.

## 2. Compute — 클라우드가 제공하는 실행 자원

**클라우드 = VM 서비스**는 아니다. VM은 대표적인 제공 방식 중 하나이고, 클라우드는 물리 서버도 온디맨드 서비스로 제공할 수 있다.

```text
Cloud Compute Service
│
├─ Bare Metal — 전용 물리 서버
│  └─ OS → Application (필요하면 Hypervisor 설치 가능)
│
├─ VM — 가상 서버
│  └─ Hypervisor → Guest OS → Application
│
└─ Container — 격리된 애플리케이션 실행
   └─ Host Kernel 공유 (물리 서버 또는 VM 위에서도 실행)
```

| 구분 | 제공·실행 방식 | 주요 선택 기준 |
|---|---|---|
| Bare Metal | 전용 물리 서버를 직접 사용 | 하드웨어 제어·일정한 고부하·전용 자원 |
| VM | 물리 자원을 가상 서버로 제공 | 격리·유연한 자원 할당·범용 워크로드 |
| Container | 커널을 공유하는 애플리케이션 실행 단위 | 빠른 배포·이식성·실행환경 일관성 |

**IDC ↔ Bare Metal:** IDC는 서버를 수용하는 **시설**, Bare Metal은 물리 서버를 사용하는 **방식**이다. Bare Metal은 전용 자원이라 작은 워크로드에서는 비용 부담이 클 수 있지만, 지속적인 고부하에서는 비용 대비 성능이 유리할 수도 있다.

**가상화 ↔ 클라우드:** 가상화는 자원을 추상화·격리하는 기술이고, 클라우드는 자원을 필요에 따라 **서비스로 제공·관리하는 모델**이다. Container·Serverless 서비스도 내부적으로 VM이나 물리 서버에서 실행될 수 있다. 따라서 Bare Metal·VM·Container는 항상 서로 배타적인 물리 구조가 아니다.

## 3. Network — 무엇을 제어하고 어떻게 연결하는가

### SDN ↔ NFV — 제어 방식과 기능 구현 방식

```text
[SDN: 제어와 전달의 분리]
Controller ──정책·경로 제어──> Network Device
                                 └─ Packet 전달

[NFV: 네트워크 기능의 SW화]
범용 서버
  ├─ Virtual Firewall
  ├─ Virtual Router
  └─ 기타 Network Function
```

- **SDN(Software-Defined Networking):** 제어 평면(Control Plane)과 데이터 평면(Data Plane)을 분리해 정책과 경로를 소프트웨어로 제어하는 접근.
- **NFV(Network Functions Virtualization):** 방화벽·라우터 등의 네트워크 기능을 전용 장비 대신 범용 컴퓨팅 자원 위의 소프트웨어로 구현하는 접근.

SDN은 **제어 구조**, NFV는 **기능의 구현·배치**가 중심이다. 함께 사용할 수 있으며 서로 반대되는 기술이 아니다.

### VLAN / VPN / Bonding — 분리·연결·묶기

온프레미스에서 **부서별 망 분리, 본사·지사 연결, 서버 NIC 이중화**를 할 때 각각 쓰는 기술이다.

```text
[VLAN: 같은 물리 Switch에서 논리적 L2 망 분리]
               Switch
             /        \
       VLAN 10        VLAN 20
       개발팀 PC       인사팀 PC
  (서로 다른 VLAN 간 통신에는 L3 Routing 필요)

[VPN: 떨어진 사내망을 논리적으로 연결]
본사 LAN ─ VPN Gateway ══ 인터넷 ══ VPN Gateway ─ 지사 LAN
                  (예: IPsec 암호화 Tunnel)

[Bonding: 서버 NIC 여러 개를 논리적으로 묶음]
             Linux Server
                 bond0
                /     \
              NIC1   NIC2
                \     /
                Switch
      (모드에 따라 장애 전환 또는 트래픽 분산)
```

| 기술 | 질문 | 대표 상황 |
|---|---|---|
| VLAN | 같은 물리망을 어떻게 **분리**할까? | 부서별 L2 네트워크 |
| VPN | 떨어진 망을 어떻게 **연결**할까? | 본사·지사, 원격 접속 |
| Bonding / Teaming | 여러 NIC를 어떻게 **묶을까**? | 링크 이중화·트래픽 분산 |

VPN은 방식에 따라 보안 속성이 다르고, Bonding도 모드에 따라 단일 연결 속도가 증가하지 않을 수 있다.

### 3-Tier ↔ Spine-Leaf — Switch 연결 토폴로지

앞의 세 기술과 달리 **스위치를 어떤 구조로 연결할 것인가**의 문제다.

```text
[3-Tier: 계층형]                [Spine-Leaf: 서버 간 통신 중심]
         Core                     Spine A      Spine B
        /    \                    /  |  \     /  |  \
    Dist A  Dist B                /   |   \   /   |   \
     / \     / \                 Leaf A   Leaf B   Leaf C
   Access   Access                 |        |        |
     |        |                  Server   Server   Server
   Server   Server

Core       : 중심 연결
Distribution: Access 집선·정책·Routing
Access     : 실제 서버·PC 연결

Leaf A → Spine → Leaf B : 서로 다른 Leaf의 서버 간 대표 경로
```

3-Tier는 **Core·Distribution·Access** 역할을 계층으로 나눈다. Spine-Leaf는 각 Leaf가 모든 Spine에 연결되는 구조로, 데이터센터의 서버 간(East-West) 통신과 수평 확장에 유리하다. 실제 구성은 이중화·장비 수에 따라 달라진다.

**기억·인출:** VLAN(분리) / VPN(원격 연결) / Bonding(NIC 결합) / 3-Tier(계층형) / Spine-Leaf(데이터센터 서버 간 연결).

## 4. Storage — 제공 단위와 연결 방식은 다른 축

### Block / File / Object — 데이터를 어떤 형태로 제공하는가

| 유형 | 제공 단위·접근 방식 | 대표 용도 |
|---|---|---|
| Block | 블록 장치를 제공, 상위 계층이 파일시스템 등을 구성 | VM Disk·DB 저장공간 |
| File | 파일·디렉터리와 파일 공유 인터페이스 | 공유 폴더·공동 작업 |
| Object | 객체 ID·데이터·메타데이터, API 기반 접근 | 이미지·백업·대규모 비정형 데이터 |

### DAS / NAS / SAN — 저장장치를 어떻게 연결하는가

```text
DAS : Server ──직접 연결────────> Disk
NAS : Server ──Network─────────> File Storage
SAN : Server ──Storage Network─> Block Storage
```

DAS는 직접 연결, NAS는 네트워크 파일 공유, SAN은 저장장치용 네트워크를 통해 블록 저장공간을 제공하는 대표 구조다. **Block/File/Object는 제공 방식, DAS/NAS/SAN은 연결·구성 방식**이므로 같은 축에서 비교하지 않는다.

연결 프로토콜의 대표 인출 키워드: **iSCSI(네트워크 기반 블록 접근)**, **NFS / SMB·CIFS(파일 공유)**.

### Pool / Tiering / Provisioning / RAID — 관리·보호

```text
여러 Disk
  ├─ Pool         : 저장 자원을 논리적으로 묶음
  ├─ Provisioning : 필요한 용량을 할당
  ├─ Tiering      : 접근 특성에 따라 저장 계층 배치
  └─ RAID         : 여러 Disk를 조합해 성능·내결함성 확보
```

예를 들어 저장 Pool에서 VM용 블록 볼륨을 할당(Provisioning)하고, 자주 쓰는 데이터는 빠른 계층에 배치(Tiering)할 수 있다. RAID는 구성 방식에 따라 성능·용량·장애 대응 특성이 다르며 **백업 자체를 대신하지 않는다**.

성안당의 추가 인출 좌표: VTL(가상 테이프 라이브러리), Swift(오브젝트 스토리지).

## 5. 통합·관리 — HCI와 OpenStack은 무엇이 다른가

```text
[인프라 구성·통합]               [클라우드 서비스 관리]
Compute + Storage + Network
             │
     Converged / HCI           OpenStack
     자원 통합·운영 단순화        API·자원 프로비저닝
             │                       │
             └──── 함께 활용 가능 ───┘
```

- **Converged Infrastructure:** 컴퓨팅·스토리지·네트워크를 사전 통합된 구성으로 제공하는 방식.
- **HCI(Hyper-Converged Infrastructure):** 범용 서버의 가상화·소프트웨어 정의 스토리지 등을 통합해 자원 확장과 관리를 단순화하는 방식.
- **OpenStack:** 컴퓨팅·네트워크·스토리지 자원을 클라우드 API로 제공·관리하는 오픈소스 플랫폼. Nova(Compute), Neutron(Network), Cinder(Block Storage), Swift(Object Storage)가 대표 서비스다.

**HCI = 자원 통합 구조 / OpenStack = 클라우드 관리·서비스 제공 플랫폼.** 서로 대체 관계로 단정할 수 없다.

## 6. 기억·인출 장치

```text
Compute  → 무엇에서 실행하는가?
Network  → 어떻게 연결·제어하는가?
Storage  → 무엇을 어떤 단위로 저장·접근하는가?
통합·관리 → 자원을 어떻게 묶고 서비스로 제공하는가?
```

대표 비교: **SDN ↔ NFV**, **3-Tier ↔ Spine-Leaf**, **Block/File/Object ↔ DAS/NAS/SAN(분류 축 차이)**, **Converged/HCI ↔ OpenStack(역할 차이)**.

전체 관계를 다시 확인할 때는 [클라우드 전체 개념지도](00-전체.md)로 돌아간다.
