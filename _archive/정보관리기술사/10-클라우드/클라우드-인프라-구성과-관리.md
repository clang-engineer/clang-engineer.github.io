# 클라우드 인프라 구성과 관리

> [클라우드 전체 개념지도](00-전체.md) → Cloud Infrastructure  
> 학습 질문: 기존 Compute·Network·Storage를 어떻게 요청형 클라우드 서비스로 제공하는가? 기반 기술은 이 관계를 설명하는 데 필요한 만큼만 다룬다.

## 학습 조망 — 사용자 서비스와 사업자 구현

```text
클라우드 인프라
├─ 사용자 구성 → Compute / Network / Storage
│  ├─ 실행 → VM / Container / Bare Metal
│  ├─ 연결 → VPC / Subnet / Routing
│  └─ 저장 → Block / File / Object
├─ 사업자 구현 → Virtualization / SDN·NFV / Storage Pool
├─ 자원 관리 → Provisioning / Orchestration
└─ 기반 통합 → CI / HCI / OpenStack
```

사용자가 제공받는 자원을 먼저 살펴보고, 이를 제공하는 기반 기술과 자원 관리로 내려간다. 서비스와 구현 기술은 일대일로 대응하지 않는다.

## 1. 큰 그림 — 기존 자원을 어떻게 클라우드 서비스로 제공하는가?

온프레미스에서도 서버·네트워크·스토리지를 사용한다. 클라우드는 이러한 자원을 **풀링·추상화·자동 할당하여 사용자가 서비스로 요청할 수 있게 한다**.

```text
[클라우드 사용자]
VM 생성 / VPC 구성 / Storage 할당 요청
                  │ API·Console
                  ▼
[클라우드 관리·자동화 계층]
인증·권한 / 자원 배치 / Provisioning
                  │ 구성 요청
          ┌───────┼────────┐
          ▼       ▼        ▼
       Compute  Network  Storage
       VM 실행  가상망 연결 Volume 할당
          └───────┼────────┘
                  ▼
           서비스 이용·운영
────────────────────────────────────
[사업자 기반] 물리 서버·네트워크 장비·저장장치
```

이 흐름은 대표적인 **VM 제공 개념 모델**이다. 모든 클라우드가 동일한 구현이나 OpenStack을 사용하는 것은 아니다.

## 2. 사용자가 제공받는 자원

```text
Cloud Infrastructure Service
├─ Compute — 어디서 실행?
│  ├─ Bare Metal : 전용 물리 서버 (예: EC2 Metal)
│  ├─ VM         : Hypervisor 기반 가상 서버 (예: EC2)
│  └─ Container  : Kernel 공유 실행환경 (예: ECS / EKS)
├─ Network — 어떻게 연결·통제?
│  └─ VPC / Subnet / Route Table / Gateway / Security Group
└─ Storage — 어떤 형태로 저장?
   ├─ Block  : 서버에 Volume 연결 (예: AWS EBS)
   ├─ File   : 공유 File System   (예: AWS EFS)
   └─ Object : API로 객체 저장    (예: AWS S3)
```

**클라우드 ≠ VM.** 클라우드는 자원 제공·관리 모델이고 VM은 실행환경 중 하나다. Container는 물리 서버 또는 VM 위에서 실행될 수 있다. Bare Metal은 물리 서버를 전용으로 사용하는 방식이며, IDC(서버를 수용하는 시설)와 다르다.

스토리지에서 **Block/File/Object는 사용자에게 제공하는 접근 방식**이다. 특정 서비스가 전통적인 DAS·NAS·SAN으로 구현된다는 뜻은 아니다.

### Storage — 사용자가 선택하는 저장 서비스

```text
Cloud Storage — 데이터 접근 모델
├─ Block → 블록 장치·볼륨 (예: EBS)
├─ File → 파일·디렉터리 공유 (예: EFS)
└─ Object → 객체·키·API (예: S3)
```

| 구분 | 접근 방식 | 대표 활용 |
|---|---|---|
| Block | 서버가 블록 장치를 연결하고 파일시스템 등을 구성 | VM의 OS·데이터 볼륨 |
| File | 파일 경로와 공유 파일시스템 | 여러 서버의 공유 파일 |
| Object | 객체 키·메타데이터를 API로 접근 | 이미지·로그·백업 |

이 세 가지는 물리 디스크 종류가 아니라 **클라우드 이용자에게 제공하는 데이터 접근 방식**이다. Block은 파일 공유를 자동으로 제공하지 않으며, Object는 일반적인 블록 장치와 사용 방식이 다르다.

서비스를 선택한 다음에는 **데이터 보호(Replication·Snapshot·Backup)**, **보관·비용(Storage Class·Lifecycle)**, **성능·가용성·접근 권한**을 검토한다. 기능의 제공 범위는 서비스별로 다르다. 아래의 RAID·Pooling·Tiering은 이 서비스들이 활용할 수 있는 **사업자 구현·운영 관점**이며 일대일 대응하지 않는다.

### Network — 사용자가 논리적 통신 환경을 구성하는 방법

온프레미스에서는 네트워크 장비와 설정을 직접 관리하는 경우가 많지만, 클라우드 이용자는 **논리적 네트워크와 연결·보안 정책을 서비스로 구성**한다. 물리망을 직접 소유한다는 뜻은 아니다.

```text
클라우드 Network — 자원 간 통신 환경
├─ 공간·주소 → VPC / CIDR / Subnet
├─ 경로·출입구 → Route Table / Internet Gateway / NAT Gateway
├─ 접근 통제 → Security Group / Network ACL
├─ 망 간 연결 → Peering / VPN / 전용 연결
└─ 서비스 진입·분산 → DNS / Load Balancer
```

**VPC**는 논리적으로 격리된 네트워크 범위, **Subnet**은 그 안에서 주소 범위를 나누는 단위다. **Route Table**은 목적지별 다음 경로를 정하고, **Gateway**는 다른 네트워크와 통신할 수 있는 연결 지점을 제공한다. **Security Group·Network ACL**은 트래픽 허용 범위를 제어한다. 경로가 있다고 접근이 자동 허용되는 것은 아니다.

대표적인 AWS형 웹 서비스 구성을 단순화하면 다음과 같다.

```text
Internet
   │
Internet Gateway
   │
VPC
├─ Public Subnet → 외부용 Load Balancer
│
└─ Private Subnet → Application → Database
       │
       └─ 외부로 나가는 통신 → NAT Gateway (Public Subnet)
```

Public·Private는 단순히 Subnet의 이름이 아니라 **인터넷 게이트웨이로 향하는 라우팅 구성**으로 구분한다. 인터넷 통신에는 Route Table 외에도 공인 주소·보안 정책 등 조건이 필요하다. NAT Gateway는 대표적으로 Private Subnet 자원의 **외부 방향 통신**을 지원하며, 외부에서 그 자원으로 임의의 신규 연결을 허용하는 장치는 아니다.

Peering은 논리 네트워크 간 연결, VPN은 암호화된 터널을 통한 연결, 전용 연결은 사업자 네트워크와 별도 회선·연결 서비스를 통한 접속에 초점을 둔다. Load Balancer는 트래픽 분산, DNS는 이름을 주소 등으로 해석하는 기능으로 서로 역할이 다르다.

이 절은 **사용자가 무엇을 조합하는가**에 대한 설명이다. 아래 SDN·NFV는 **사업자가 네트워크 제어·기능을 어떤 방식으로 구현할 수 있는가**를 설명한다. VPC가 반드시 특정 SDN·NFV 구현과 일대일 대응하는 것은 아니다. AWS 용어는 대표 예시이며 다른 클라우드의 서비스명·세부 동작은 다를 수 있다.

## 3. 사업자가 서비스를 구현하는 기술

### Compute — 가상화와 자원 할당

```text
물리 서버 (CPU / RAM)
      │ 자원 추상화·할당
      ▼
Hypervisor → VM → Guest OS → Application

별도 실행 방식: Bare Metal 전용 제공
VM 또는 물리 서버 위: Container 실행 가능
```

가상화는 자원을 나누고 격리하는 **구현 기술**이다. 관리 플랫폼은 이 자원을 요청에 맞게 배치·할당한다.

### Network — 사업자의 SDN과 NFV

**기반 기술과 클라우드 활용:** SDN·NFV는 클라우드 전용 기술이 아니라 네트워크의 제어 구조와 기능 구현을 소프트웨어 중심으로 유연하게 만드는 기술이다. 클라우드 사업자는 이러한 접근을 활용해 가상 네트워크를 제어하거나 방화벽·라우터 같은 네트워크 기능을 제공할 수 있다. 모든 클라우드가 두 기술을 반드시 사용하는 것은 아니다.

```text
[SDN: 네트워크 제어 구조]
Controller ──경로·정책 제어──> Switch / 전달 장치

[NFV: 네트워크 기능 실행 방식]
범용 서버 ──실행──> Virtual Firewall / Virtual Router
```

- **SDN(Software-Defined Networking):** 제어 평면과 패킷 전달 평면을 분리해 네트워크를 소프트웨어 중심으로 제어한다.
- **NFV(Network Functions Virtualization):** 방화벽·라우터 같은 네트워크 기능을 전용 장비 대신 범용 컴퓨팅 자원의 소프트웨어로 실행한다.

**실제 상황으로 비교 — 무엇이 달라지는가?**

```text
[SDN: 데이터센터의 전달 정책 변경]

기존: 관리자 → Switch A 설정
             → Switch B 설정
             → Switch C 설정

SDN : 관리자 → SDN Controller (전달 정책)
                         │
                   ┌─────┼─────┐
                   ▼     ▼     ▼
                  SW A  SW B  SW C
                 (정책에 따라 패킷 전달)
```

예를 들어 데이터센터에서 특정 서버군으로 가는 트래픽의 전달 경로를 바꿀 때, SDN은 **제어 기능을 패킷 전달 기능과 분리**해 Controller 중심으로 정책을 적용할 수 있게 한다. 단순히 장비 여러 대를 중앙 관리하는 도구라면 모두 SDN인 것은 아니다.

```text
[NFV: 회사 방화벽을 제공하는 방식]

기존: 사내망 ── 물리 방화벽 전용 장비 ── 외부망

NFV : 사내망 ── 범용 서버의 가상 방화벽 ── 외부망
                     └─ VM 등에서 실행
```

방화벽의 트래픽 검사·차단이라는 **기능은 유지**하면서 전용 장비 대신 일반 서버의 소프트웨어로 실행한다. 실제 NFV는 가상 네트워크 기능의 배포·운영 관리까지 포함할 수 있다.

**기억:** SDN = *누가 전달을 제어하나?* / NFV = *네트워크 기능을 어디서 실행하나?* 두 기술은 함께 사용할 수 있지만 서로의 필수 조건은 아니다.

이 절의 핵심은 SDN·NFV의 원리를 새로 분류하는 것이 아니라, **클라우드 인프라가 네트워크 제어와 기능 제공을 소프트웨어로 유연하게 구현할 수 있다는 점**이다.

### Storage — Storage Pool·RAID·Tiering

**Storage Pooling은 Resource Pooling의 저장 자원 적용 사례**다. RAID는 데이터를 디스크에 배치·보호하는 방식이므로 Pooling과 목적이 다르다.

```text
[Storage Pooling: 저장 용량 통합]
Disk A   Disk B   Disk C
   └──────┼──────┘
          ▼
     Storage Pool
          │ Provisioning
      ┌───┴────┐
      ▼        ▼
   VM A 100GB  VM B 200GB

[RAID 1: 데이터 복제·장애 대비]
Disk A          Disk B
  Data X   =      Data X
        (Mirroring)
```

| 개념 | 핵심 역할 | 기억할 질문 |
|---|---|---|
| Pooling | 여러 저장 자원을 논리적으로 통합·관리 | 용량을 어떻게 묶어 관리할까? |
| Provisioning | Pool 등의 자원에서 Volume·용량을 생성·할당 | 필요한 공간을 어떻게 제공할까? |
| RAID | Striping·Mirroring·Parity 등 데이터 배치 방식 | 성능·내결함성을 어떻게 확보할까? |
| Tiering | 데이터 특성에 따라 저장 계층을 배치·이동 | 어떤 저장매체에 둘까? |

**Tiering 실제 예시 — 사용 특성에 따라 저장 계층 선택**

```text
데이터의 접근 빈도·성능·보관 비용
               │
       ┌───────┴────────┐
       ▼                ▼
   Hot Data          Cold Data
  자주 사용하는 데이터  드물게 사용하는 데이터
       │                │
       ▼                ▼
    SSD 계층          HDD 계층
   빠름·고비용        상대적으로 느림·저비용
```

Tiering은 **데이터를 어떤 성능·비용 계층에 배치하거나 이동할지** 결정하는 기술이다. 클라우드에서는 AWS S3 Standard·Standard-IA·Glacier 계열처럼 접근 패턴과 보관 요구에 따라 **스토리지 클래스를 선택·전환**하는 것도 서비스 수준의 계층화 사례다. 다만 S3 저장 클래스 전환이 곧 SSD와 HDD 사이의 물리적 이동을 뜻하지는 않는다.

**함께 사용하는 예시:** 물리 디스크 → RAID 구성 → 논리 저장장치 → Storage Pool → Volume Provisioning → VM 연결. 이는 한 가지 가능한 구조이며, 분산 스토리지나 소프트웨어 정의 스토리지는 RAID와 Pooling을 다른 방식으로 통합할 수 있다.

Provisioning은 단순히 디스크를 물리적으로 쪼개는 것이 아니다. **Thick**은 요청한 용량을 미리 확보하고, **Thin**은 논리적 용량을 제공하면서 실제 공간은 데이터 사용에 따라 소비하도록 할 수 있다. Pooling만으로 장애 보호가 보장되는 것은 아니며, RAID도 백업을 대신하지 않는다.

사업자는 DAS·NAS·SAN 또는 분산 스토리지 등 여러 기반 구조를 활용할 수 있다. **Block/File/Object는 사용자에게 제공하는 접근 방식이고, DAS/NAS/SAN은 연결·구성 방식**이므로 같은 분류 축이 아니다. 연결 방식 자체는 [I/O와 저장장치 개념지도](../01-컴퓨터-구조/03-IO-저장장치.md)의 DAS·NAS·SAN에서 확인한다.

### 자원 관리·자동화 — Pooling과 Provisioning

**Resource Pooling**은 여러 자원을 논리적으로 묶어 공유·관리하는 방식으로, 클라우드의 핵심 특성 중 하나다. Compute의 CPU·Memory 자원 풀, Network의 IP 주소·대역폭 자원 관리, Storage의 용량 풀이 대표적인 적용 사례다. 모든 자원이 하나의 물리적 풀로 합쳐진다는 뜻은 아니다.

Provisioning은 **자원을 사용할 수 있도록 준비·구성·할당하는 과정**이다. Storage에만 적용되는 기술이 아니라 클라우드 전반에 적용되는 관리 기능이다.

```text
기반 자원 → Resource Pooling (논리적 공유·관리)
                    │
사용자 요청 → 관리 플랫폼 / 자동화
                    │ Provisioning
           ┌────────┼────────┐
           ▼        ▼        ▼
        Compute   Network  Storage
        VM 생성   VPC 구성  Volume 생성
```

- **Compute:** VM을 생성하고 CPU·Memory 등 실행 자원을 준비한다(예: AWS EC2).
- **Network:** VPC·Subnet 등 논리적 네트워크를 생성·구성한다(예: AWS VPC).
- **Storage:** Volume을 생성·할당한다(예: AWS EBS).

**Pooling = 자원을 논리적으로 묶어 관리 / Provisioning = 필요한 자원을 사용 가능하게 준비·할당.** Orchestration은 이 여러 자원 구성 작업을 조정·자동화하는 개념이다. Storage의 Thick·Thin은 Provisioning의 저장 용량 할당 방식에 관한 세부 구분이다.

### 인프라 통합 — CI와 HCI

둘 다 서버·스토리지·네트워크를 통합해 구축·관리하려는 접근이다. 차이는 **무엇을 어떻게 통합하느냐**에 있다.

```text
[CI: 장비를 사전 통합한 구성]
┌─────────────────────────┐
│ Server A / Server B     │
│ 별도 공유 Storage (SAN) │
│ Network Switch          │
└─────────────────────────┘
   장비별 구성요소를 묶어 검증·제공

[HCI: 서버 자원을 SW로 통합]
┌──────────────┐   ┌──────────────┐
│ Server A     │   │ Server B     │
│ CPU/RAM/SSD  │   │ CPU/RAM/SSD  │
└──────┬───────┘   └──────┬───────┘
       └────────┬─────────┘
                ▼
     Software-defined Storage
         논리적 공유 Pool
```

| 구분 | CI (Converged Infrastructure) | HCI (Hyper-Converged Infrastructure) |
|---|---|---|
| 통합 중심 | 서버·스토리지·네트워크 장비의 사전 통합 | 범용 서버 노드의 자원을 소프트웨어로 통합 |
| 저장 구조 | 별도 공유 스토리지 장비를 두는 구성이 일반적 | 서버 로컬 디스크를 분산·공유 스토리지로 통합하는 구성이 대표적 |
| 확장 | 구성요소별 확장 가능 | 노드 단위 확장이 대표적(제품에 따라 자원별 확장 가능) |

**온프레미스 예시:** CI는 서버 3대와 별도 SAN·스위치를 검증된 한 구성으로 도입하는 방식이다. HCI는 CPU·RAM·디스크가 있는 서버 3대를 묶고 소프트웨어로 공유 스토리지를 구성하는 방식이다. HCI에도 물리 네트워크는 필요하다.

**기억:** CI = **장비 통합**, HCI = **서버 자원의 소프트웨어 통합**.

### 클라우드 관리 플랫폼 — OpenStack

OpenStack은 CI·HCI와 같은 인프라 통합 방식이 아니라, Compute(Nova)·Network(Neutron)·Block Storage(Cinder)·Object Storage(Swift) 등을 **API로 제공·관리하는 오픈소스 클라우드 플랫폼**이다.

```text
사용자 → OpenStack (API·자원 할당)
                   ↓
         물리·가상 인프라
       (일반 구성 / CI / HCI 등)
```

CI·HCI와 OpenStack은 서로 다른 계층이며, **어느 하나가 다른 하나의 필수 조건은 아니다**.

## 4. 기존 온프레미스 기술의 위치

다음은 클라우드 고유의 서비스 모델이 아니라, 사업자 내부 또는 일반 데이터센터에서 활용할 수 있는 **기존 인프라 기술**이다.

| 기술 | 기존 역할 | 클라우드와의 연결 |
|---|---|---|
| VLAN | 하나의 물리망을 논리적 L2 영역으로 분리 | 네트워크 격리 구현에 활용 가능 |
| VPN | 떨어진 네트워크를 논리적으로 연결 | 온프레미스·클라우드 연결 등에 활용 |
| Bonding / Teaming | 여러 NIC를 논리적으로 묶음 | 호스트 링크 이중화·분산 |
| 3-Tier / Spine-Leaf | 스위치 연결 토폴로지 | 데이터센터 네트워크 구성 |
| DAS / NAS / SAN | 저장장치 연결·접근 구조 | 기반 스토리지 구현에 활용 가능 |

```text
Network 구성: VLAN(분리) / VPN(연결) / Bonding(NIC 결합)
Topology    : 3-Tier(Core·Distribution·Access)
              ↔ Spine-Leaf(Leaf마다 Spine 연결)
Storage 연결: DAS(직접) / NAS(파일 공유) / SAN(블록 망)
```

이 기술들을 모두 사용해야 클라우드가 되는 것은 아니다. **기존 인프라의 연결·구성 방법**과 **클라우드의 서비스화·자동화**를 구분해서 이해한다.

## 5. 기억·인출 장치

```text
기존 인프라 (Server / Network / Storage)
               ↓ 추상화·풀링
관리 플랫폼 (요청 / 배치 / 할당 / 자동화)
               ↓ 서비스 제공
Compute / Network / Storage

VPC / Subnet / Route / Gateway → 사용자의 논리망 구성
SDN  → 네트워크 제어 구조
NFV  → 네트워크 기능의 SW 실행
HCI  → 기반 자원 통합
OpenStack → 클라우드 자원 관리·제공
```
