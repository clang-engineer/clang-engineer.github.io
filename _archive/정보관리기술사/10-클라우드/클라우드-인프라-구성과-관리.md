# 클라우드 인프라 구성과 관리

> [클라우드 전체 개념지도](00-전체.md) → Cloud Infrastructure  
> 범위: 성안당 Vol.10의 Compute·Network·Storage와 이를 서비스로 제공하는 기반 기술.

## 1. 큰 그림 — 기존 자원을 어떻게 클라우드 서비스로 제공하는가?

온프레미스에서도 서버·네트워크·스토리지를 사용한다. 클라우드는 이러한 자원을 **풀링·추상화·자동 할당하여 사용자가 서비스로 요청할 수 있게 한다**.

```text
[클라우드 사용자]
VM 생성 / VPC 구성 / Storage 할당 요청
                  │ API·Console
                  ▼
[클라우드 관리·자동화 계층]
인증·권한 / 자원 배치 / Provisioning
                  │ 구성 요청
          ┌───────┼────────┐
          ▼       ▼        ▼
       Compute  Network  Storage
       VM 실행  가상망 연결 Volume 할당
          └───────┼────────┘
                  ▼
           서비스 이용·운영
────────────────────────────────────
[사업자 기반] 물리 서버·네트워크 장비·저장장치
```

이 흐름은 대표적인 **VM 제공 개념 모델**이다. 모든 클라우드가 동일한 구현이나 OpenStack을 사용하는 것은 아니다.

## 2. 사용자가 제공받는 자원

```text
Cloud Infrastructure Service
├─ Compute — 어디서 실행?
│  ├─ Bare Metal : 전용 물리 서버 (예: EC2 Metal)
│  ├─ VM         : Hypervisor 기반 가상 서버 (예: EC2)
│  └─ Container  : Kernel 공유 실행환경 (예: ECS / EKS)
├─ Network — 어떻게 연결?
│  └─ VPC / Subnet / Routing / VPN (예: AWS VPC)
└─ Storage — 어떤 형태로 저장?
   ├─ Block  : 서버에 Volume 연결 (예: AWS EBS)
   ├─ File   : 공유 File System   (예: AWS EFS)
   └─ Object : API로 객체 저장    (예: AWS S3)
```

**클라우드 ≠ VM.** 클라우드는 자원 제공·관리 모델이고 VM은 실행환경 중 하나다. Container는 물리 서버 또는 VM 위에서 실행될 수 있다. Bare Metal은 물리 서버를 전용으로 사용하는 방식이며, IDC(서버를 수용하는 시설)와 다르다.

스토리지에서 **Block/File/Object는 사용자에게 제공하는 접근 방식**이다. 특정 서비스가 전통적인 DAS·NAS·SAN으로 구현된다는 뜻은 아니다.

## 3. 사업자가 서비스를 구현하는 기술

### Compute — 가상화와 자원 할당

```text
물리 서버 (CPU / RAM)
      │ 자원 추상화·할당
      ▼
Hypervisor → VM → Guest OS → Application

별도 실행 방식: Bare Metal 전용 제공
VM 또는 물리 서버 위: Container 실행 가능
```

가상화는 자원을 나누고 격리하는 **구현 기술**이다. 관리 플랫폼은 이 자원을 요청에 맞게 배치·할당한다.

### Network — SDN과 NFV

**기반 기술과 클라우드 활용:** SDN·NFV는 클라우드 전용 기술이 아니라 네트워크의 제어 구조와 기능 구현을 소프트웨어 중심으로 유연하게 만드는 기술이다. 클라우드 사업자는 이러한 접근을 활용해 가상 네트워크를 제어하거나 방화벽·라우터 같은 네트워크 기능을 제공할 수 있다. 모든 클라우드가 두 기술을 반드시 사용하는 것은 아니다.

```text
[SDN: 네트워크 제어 구조]
Controller ──경로·정책 제어──> Switch / 전달 장치

[NFV: 네트워크 기능 실행 방식]
범용 서버 ──실행──> Virtual Firewall / Virtual Router
```

- **SDN(Software-Defined Networking):** 제어 평면과 패킷 전달 평면을 분리해 네트워크를 소프트웨어 중심으로 제어한다.
- **NFV(Network Functions Virtualization):** 방화벽·라우터 같은 네트워크 기능을 전용 장비 대신 범용 컴퓨팅 자원의 소프트웨어로 실행한다.

**실제 상황으로 비교 — 무엇이 달라지는가?**

```text
[SDN: 데이터센터의 전달 정책 변경]

기존: 관리자 → Switch A 설정
             → Switch B 설정
             → Switch C 설정

SDN : 관리자 → SDN Controller (전달 정책)
                         │
                   ┌─────┼─────┐
                   ▼     ▼     ▼
                  SW A  SW B  SW C
                 (정책에 따라 패킷 전달)
```

예를 들어 데이터센터에서 특정 서버군으로 가는 트래픽의 전달 경로를 바꿀 때, SDN은 **제어 기능을 패킷 전달 기능과 분리**해 Controller 중심으로 정책을 적용할 수 있게 한다. 단순히 장비 여러 대를 중앙 관리하는 도구라면 모두 SDN인 것은 아니다.

```text
[NFV: 회사 방화벽을 제공하는 방식]

기존: 사내망 ── 물리 방화벽 전용 장비 ── 외부망

NFV : 사내망 ── 범용 서버의 가상 방화벽 ── 외부망
                     └─ VM 등에서 실행
```

방화벽의 트래픽 검사·차단이라는 **기능은 유지**하면서 전용 장비 대신 일반 서버의 소프트웨어로 실행한다. 실제 NFV는 가상 네트워크 기능의 배포·운영 관리까지 포함할 수 있다.

**기억:** SDN = *누가 전달을 제어하나?* / NFV = *네트워크 기능을 어디서 실행하나?* 두 기술은 함께 사용할 수 있지만 서로의 필수 조건은 아니다.

온프레미스의 **장비별 제어·설정**과 **전용 방화벽 장비**를 떠올리면 차이가 분명해진다. SDN은 *제어 구조*, NFV는 *기능의 실행 위치·방식*을 바꾼다. 둘은 함께 사용할 수 있지만, 모든 VPC나 VM 생성에 반드시 적용되는 기술은 아니다.

### Storage — Pooling·Provisioning과 RAID

**Pooling은 저장공간을 어떻게 묶어 관리할까, RAID는 데이터를 디스크에 어떻게 배치·보호할까**라는 서로 다른 질문이다.

```text
[Pooling: 용량 통합·할당]
Disk A   Disk B   Disk C
   └──────┼──────┘
          ▼
     Storage Pool
          │ Provisioning
      ┌───┴────┐
      ▼        ▼
   VM A 100GB  VM B 200GB

[RAID 1: 데이터 복제·장애 대비]
Disk A          Disk B
  Data X   =      Data X
        (Mirroring)
```

| 개념 | 핵심 역할 | 기억할 질문 |
|---|---|---|
| Pooling | 여러 저장 자원을 논리적으로 통합·관리 | 용량을 어떻게 묶어 관리할까? |
| Provisioning | Pool 등의 자원에서 Volume·용량을 생성·할당 | 필요한 공간을 어떻게 제공할까? |
| RAID | Striping·Mirroring·Parity 등 데이터 배치 방식 | 성능·내결함성을 어떻게 확보할까? |
| Tiering | 데이터 특성에 따라 저장 계층을 배치·이동 | 어떤 저장매체에 둘까? |

**함께 사용하는 예시:** 물리 디스크 → RAID 구성 → 논리 저장장치 → Storage Pool → Volume Provisioning → VM 연결. 이는 한 가지 가능한 구조이며, 분산 스토리지나 소프트웨어 정의 스토리지는 RAID와 Pooling을 다른 방식으로 통합할 수 있다.

Provisioning은 단순히 디스크를 물리적으로 쪼개는 것이 아니다. **Thick**은 요청한 용량을 미리 확보하고, **Thin**은 논리적 용량을 제공하면서 실제 공간은 데이터 사용에 따라 소비하도록 할 수 있다. Pooling만으로 장애 보호가 보장되는 것은 아니며, RAID도 백업을 대신하지 않는다.

사업자는 DAS·NAS·SAN 또는 분산 스토리지 등 여러 기반 구조를 활용할 수 있다. **Block/File/Object는 사용자에게 제공하는 접근 방식이고, DAS/NAS/SAN은 연결·구성 방식**이므로 같은 분류 축이 아니다.

### 인프라 통합 — CI와 HCI

둘 다 서버·스토리지·네트워크를 통합해 구축·관리하려는 접근이다. 차이는 **무엇을 어떻게 통합하느냐**에 있다.

```text
[CI: 장비를 사전 통합한 구성]
┌─────────────────────────┐
│ Server A / Server B     │
│ 별도 공유 Storage (SAN) │
│ Network Switch          │
└─────────────────────────┘
   장비별 구성요소를 묶어 검증·제공

[HCI: 서버 자원을 SW로 통합]
┌──────────────┐   ┌──────────────┐
│ Server A     │   │ Server B     │
│ CPU/RAM/SSD  │   │ CPU/RAM/SSD  │
└──────┬───────┘   └──────┬───────┘
       └────────┬─────────┘
                ▼
     Software-defined Storage
         논리적 공유 Pool
```

| 구분 | CI (Converged Infrastructure) | HCI (Hyper-Converged Infrastructure) |
|---|---|---|
| 통합 중심 | 서버·스토리지·네트워크 장비의 사전 통합 | 범용 서버 노드의 자원을 소프트웨어로 통합 |
| 저장 구조 | 별도 공유 스토리지 장비를 두는 구성이 일반적 | 서버 로컬 디스크를 분산·공유 스토리지로 통합하는 구성이 대표적 |
| 확장 | 구성요소별 확장 가능 | 노드 단위 확장이 대표적(제품에 따라 자원별 확장 가능) |

**온프레미스 예시:** CI는 서버 3대와 별도 SAN·스위치를 검증된 한 구성으로 도입하는 방식이다. HCI는 CPU·RAM·디스크가 있는 서버 3대를 묶고 소프트웨어로 공유 스토리지를 구성하는 방식이다. HCI에도 물리 네트워크는 필요하다.

**기억:** CI = **장비 통합**, HCI = **서버 자원의 소프트웨어 통합**.

### 클라우드 관리 플랫폼 — OpenStack

OpenStack은 CI·HCI와 같은 인프라 통합 방식이 아니라, Compute(Nova)·Network(Neutron)·Block Storage(Cinder)·Object Storage(Swift) 등을 **API로 제공·관리하는 오픈소스 클라우드 플랫폼**이다.

```text
사용자 → OpenStack (API·자원 할당)
                   ↓
         물리·가상 인프라
       (일반 구성 / CI / HCI 등)
```

CI·HCI와 OpenStack은 서로 다른 계층이며, **어느 하나가 다른 하나의 필수 조건은 아니다**.

## 4. 기존 온프레미스 기술의 위치

다음은 클라우드 고유의 서비스 모델이 아니라, 사업자 내부 또는 일반 데이터센터에서 활용할 수 있는 **기존 인프라 기술**이다.

| 기술 | 기존 역할 | 클라우드와의 연결 |
|---|---|---|
| VLAN | 하나의 물리망을 논리적 L2 영역으로 분리 | 네트워크 격리 구현에 활용 가능 |
| VPN | 떨어진 네트워크를 논리적으로 연결 | 온프레미스·클라우드 연결 등에 활용 |
| Bonding / Teaming | 여러 NIC를 논리적으로 묶음 | 호스트 링크 이중화·분산 |
| 3-Tier / Spine-Leaf | 스위치 연결 토폴로지 | 데이터센터 네트워크 구성 |
| DAS / NAS / SAN | 저장장치 연결·접근 구조 | 기반 스토리지 구현에 활용 가능 |

```text
Network 구성: VLAN(분리) / VPN(연결) / Bonding(NIC 결합)
Topology    : 3-Tier(Core·Distribution·Access)
              ↔ Spine-Leaf(Leaf마다 Spine 연결)
Storage 연결: DAS(직접) / NAS(파일 공유) / SAN(블록 망)
```

이 기술들을 모두 사용해야 클라우드가 되는 것은 아니다. **기존 인프라의 연결·구성 방법**과 **클라우드의 서비스화·자동화**를 구분해서 이해한다.

## 5. 기억·인출 장치

```text
기존 인프라 (Server / Network / Storage)
               ↓ 추상화·풀링
관리 플랫폼 (요청 / 배치 / 할당 / 자동화)
               ↓ 서비스 제공
Compute / Network / Storage

SDN  → 네트워크 제어 구조
NFV  → 네트워크 기능의 SW 실행
HCI  → 기반 자원 통합
OpenStack → 클라우드 자원 관리·제공
```
