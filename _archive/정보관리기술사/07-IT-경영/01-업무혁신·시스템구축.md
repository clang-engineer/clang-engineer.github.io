# 업무 혁신·시스템 구축 개념지도

> **업무를 어떻게 바꿀 것인가**, **그 업무를 어떤 시스템으로 지원할 것인가**, **여러 시스템을 어떻게 연결할 것인가**는 서로 다른 질문이다.

[IT 경영 전체 지도](00-전체.md)에서 변화 실행·구축 영역을 확대한다. 아래 가지들은 **병렬 관점**이며 필수 수행 순서가 아니다.

## 1. 전체 좌표

```text
사업 목표를 실행 가능한 변화로 전환
│
├─ 실행을 관리한다 → PM
│   └─ 범위 · 일정 · 비용 · 품질 · 위험 / 조달: RFP · SOW
│
├─ 업무 방식을 바꾼다 → BPR · PI · BPM
│   ├─ BPR: 기존 프로세스의 근본적 재설계에 초점
│   ├─ PI: 프로세스 혁신·성과 개선을 포괄(급진적 변화도 가능)
│   └─ BPM: 설계 · 실행 · 측정 · 지속 개선
│
├─ 업무를 시스템으로 지원한다 → ERP · SCM · CRM
│   ├─ ERP: 기업 내부 자원·업무 통합
│   ├─ SCM: 공급망 전체의 흐름
│   └─ CRM: 고객 관계·영업
│
└─ 시스템 간 정보를 연결한다 → EAI · API
    ├─ EAI: 여러 애플리케이션의 통합 접근
    └─ API: 기능·데이터를 제공하는 인터페이스
```

## 2. 왜 구분하는가

### 업무 혁신 ↔ 정보시스템

```text
업무 방식의 문제 → BPR / PI / BPM
정보 처리·공유의 문제 → ERP / SCM / CRM 등
```

BPR의 대표 결과는 **재설계된 업무 프로세스**이지 ERP 자체가 아니다. ERP 도입 없이도 업무를 바꿀 수 있고, ERP 도입 과정에서 업무를 함께 재설계할 수도 있다. **두 활동은 독립적이면서 상호 보완적**이다.

### 통합 구축 ↔ 단계적 구축 ↔ 시스템 분리

```text
구축 범위·투자 판단
├─ 한 시스템을 모듈별로 단계적 구축
└─ 여러 전문 시스템을 단계적 도입·연계
        ↓ 선택 판단
초기 투자 · 편익 실현 시점 · 실패 위험 · 연계 비용 · 장기 TCO
```

**단계적 구축 = 시스템 분리**는 아니다. 한 시스템도 단계적으로 구축할 수 있다. 분리·통합 중 어느 쪽이 적절한지는 EA의 목표 구조, ISP의 로드맵, ROI·TCO 및 위험을 함께 고려한다.

### EAI ↔ API

```text
여러 시스템의 통합 필요 → EAI 관점
개별 기능·데이터 접근 약속 → API
```

API를 이용해 직접 연계할 수도 있으므로 별도 EAI 솔루션은 필수가 아니다. EAI 역시 반드시 중앙 허브 형태일 필요는 없다.

## 3. 복습 인출 질문

- 프로젝트 관리(PM)와 업무 혁신(BPR)은 관리 대상이 어떻게 다른가?
- BPR을 했다고 ERP 도입이 필수인가?
- ERP·SCM·CRM의 관리 대상은 무엇이 다른가?
- 단계적 구축과 시스템 분리는 왜 동의어가 아닌가?
- EAI와 API는 각각 무엇을 설명하는가?
