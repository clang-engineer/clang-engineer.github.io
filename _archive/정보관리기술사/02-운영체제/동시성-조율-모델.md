# 동시성 조율 모델 — Shared State · Channel · Actor

> 연결: [[../../개념지도/02-운영체제/02-동시성-자원공유|동시성과 자원 공유]]
>
> 성격: 운영체제 보충학습. Thread·Synchronization에서 출발해 **공유 상태와 Message Passing을 어떻게 조율하는가**를 정리한다.
>
> Coroutine · Event Loop · Promise/Future · async/await처럼 **언어/Runtime의 비동기 실행 추상화**는 [`../../../99-프로그래밍-언어/비동기-실행-모델.md`](../../../99-프로그래밍-언어/비동기-실행-모델.md)에서 다룬다.

## 1. 이 문서의 위치

운영체제의 동시성 문제는 여러 실행 흐름이 같은 자원이나 상태를 함께 사용할 때 시작한다.

```text
Process / Thread
      ↓
동시 실행
      ↓
공유 상태 / 협업 필요
      ↓
동시성 조율
├─ Shared State를 보호
│  ├─ Mutex
│  ├─ Semaphore
│  └─ Atomic
└─ Message Passing으로 공유를 줄임
   ├─ Channel / Queue
   └─ Actor / Mailbox
```

이 문서의 핵심 질문은 **실행을 어떻게 중단·재개하는가**가 아니라 **여러 실행 흐름이 상태와 Message를 어떻게 안전하게 조율하는가**다.

## 2. 먼저 서로 다른 축을 분리한다

```text
Thread
→ 어떤 실행 흐름을 OS / Runtime이 Scheduling하는가?

Blocking / Non-blocking
→ I/O 호출이 현재 실행 흐름을 기다리게 하는가?

Coroutine / async-await
→ 실행 상태를 어떻게 중단·보존·재개하는가?

Mutex / Channel / Actor
→ 여러 실행 흐름이 상태와 Message를 어떻게 조율하는가?
```

이 개념들은 하나의 발전 단계가 아니다.

특히 Coroutine과 async/await은 이 문서의 중심이 아니다. 해당 축은 프로그래밍 언어 세부학습으로 넘긴다.

## 3. Shared-State 모델 — Critical Section을 보호한다

여러 실행 흐름이 같은 Mutable State를 동기화 없이 읽고 수정하면 Race Condition이 발생할 수 있다.

```text
Shared Mutable State
        ↓
동시 Read / Write
        ↓
Race Condition
        ↓
Critical Section
        ↓
Synchronization
```

가장 전통적인 접근은 공유 상태를 유지하되 접근을 통제하는 것이다.

```text
Mutex
→ Critical Section에 한 번에 하나만 진입

Semaphore
→ 동시에 사용할 수 있는 Resource 수 또는 실행 흐름 수를 제한

Atomic
→ 특정 연산을 중간 상태 없이 하나의 원자적 연산으로 수행
```

이 방식은 공유가 명확하지만 Waiting · Contention · Deadlock 가능성이라는 비용이 따른다.

## 4. Message Passing — 공유를 통신 규약으로 줄인다

다른 접근은 상태 자체를 여러 실행 흐름이 직접 공유하지 않고 Message를 전달하는 것이다.

```text
Producer
   ↓ Message
Channel / Queue
   ↓
Consumer
```

이 방식은 공유 Mutable State의 범위를 줄이고 실행 흐름 사이의 경계를 명확하게 만들 수 있다.

하지만 Channel을 사용한다고 Race가 자동으로 사라지는 것은 아니다.

```text
Message 안에 Pointer / Reference / Slice / Map 등
같은 Backing State를 가리키는 값이 들어감
        ↓
송신 측과 수신 측이 동시에 수정
        ↓
공유 상태 Race 가능
```

따라서 중요한 것은 Channel 자체보다 **Message를 통해 무엇을 공유하고 어떤 Ownership 규칙을 유지하는가**다.

## 5. Shared State와 Message Passing은 대체 관계가 아니다

실제 시스템에서는 둘을 함께 사용한다.

```text
Application
├─ 내부 자료구조 보호
│  └─ Mutex / Atomic
│
├─ 작업 전달
│  └─ Queue / Channel
│
└─ 독립 Component 간 통신
   └─ Message Passing
```

즉 다음처럼 외우지 않는다.

```text
Lock 방식 = 옛날
Message Passing = 새로운 정답
```

문제의 경계와 상태 소유 구조에 따라 적절한 조율 방식을 선택한다.

## 6. Actor — 상태를 실행 단위 안에 가둔다

Actor Model은 각 Actor가 자기 상태를 소유하고 외부와 Message로 통신하도록 한다.

```text
Actor A
├─ Private State
└─ Mailbox
      ↑↓ Message
Actor B
├─ Private State
└─ Mailbox
```

Actor가 Message를 순차적으로 처리하면 내부 상태에 대한 Lock 필요성을 줄일 수 있다.

적합한 경우:

- 독립된 상태 단위가 명확함
- Message 기반 Workflow
- Failure Isolation이 중요함

대가:

- Message Ordering 고려
- Mailbox Backpressure 고려
- 분산 환경에서는 Retry · Duplicate · Delivery 문제 추가

## 7. Channel과 Actor의 차이

둘 다 Message Passing을 사용하지만 추상화 수준이 다르다.

```text
Channel / Queue
= Message를 전달하는 통신 통로

Actor
= 상태 + Mailbox + Message 처리 규칙을 하나의 실행 단위로 묶는 모델
```

즉 Channel은 **전달 Mechanism**에 가깝고 Actor는 **상태 소유와 실행 규칙까지 포함한 동시성 모델**에 가깝다.

## 8. Type System이 조율 경계를 강화할 수 있다

일부 언어는 Type System으로 잘못된 공유 경로를 줄인다.

Rust를 예로 들면:

```text
Mutex<T>
→ Data와 Lock을 하나의 Type Boundary에 둠
→ Guard를 통해 내부 T 접근

Send / Sync
→ Type이 Thread 사이 이동·공유에 안전한지 Compile Time 경계 제공
```

이 접근은 Mutex나 Message Passing을 없애는 것이 아니다.

> **Runtime 동기화 Mechanism 위에 Compile Time 제약을 추가해 안전하지 않은 공유 경로를 줄이는 방식**으로 이해한다.

## 9. Coroutine과 조율 모델은 다른 질문이다

Coroutine을 사용해도 공유 상태 문제는 사라지지 않는다.

예를 들어 하나의 Thread 위에서 Coroutine이 번갈아 실행되더라도 `await` 사이에 다른 Coroutine이 실행될 수 있다.

```text
Coroutine A
Read shared state
↓
await
↓  ← Coroutine B가 상태 변경 가능
Resume
↓
Write shared state
```

따라서 Logical Race나 Lost Update가 발생할 수 있다.

```text
Coroutine / async-await
= 실행을 어떻게 중단하고 재개할 것인가

Mutex / Channel / Actor
= 여러 실행 흐름이 상태와 Message를 어떻게 조율할 것인가
```

Coroutine 자체의 상태 보존, Event Loop, Promise/Future와의 관계는 프로그래밍 언어의 비동기 실행 모델 문서에서 이어서 본다.

## 10. 전체 관계

```text
동시성 문제
│
├─ 공유 상태를 유지
│  ├─ Mutex
│  ├─ Semaphore
│  └─ Atomic
│      ↓
│   Waiting / Contention / Deadlock 가능
│
└─ 공유 자체를 줄임
   ├─ Channel / Queue
   └─ Actor / Mailbox
       ↓
    Message Ordering / Backpressure 고려

별도 축
Coroutine / async-await / Event Loop
→ 프로그래밍 언어 / Runtime의 비동기 실행 모델
```

> **운영체제 관점에서는 공유 상태와 실행 흐름의 안전한 조율을 중심으로 보고, Coroutine · async/await 같은 실행 추상화는 프로그래밍 언어/Runtime 관점으로 분리한다.**
