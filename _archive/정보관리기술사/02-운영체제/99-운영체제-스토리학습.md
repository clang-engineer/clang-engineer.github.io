# 운영체제 스토리 학습 — 주문 서버의 프로그램이 실행되는 동안

## 1. 프로그램을 실행하면 무슨 일이 생길까 — Process와 Thread

주문 서버 프로그램을 실행했다. 디스크에 저장된 실행 파일이 그대로 CPU에서 돌아가는 것일까?

**질문: 프로그램과 실행 중인 프로세스는 무엇이 다를까?**

프로그램은 실행 가능한 명령과 데이터이고, **Process**는 주소 공간·자원·실행 상태를 가진 실행 인스턴스다. 주문 요청을 여러 개 처리할 때 하나의 프로세스 안에서 여러 **Thread**가 실행 흐름을 나눌 수 있다.

**질문: Process와 Thread는 모두 CPU를 소유할까?**

둘을 구분해야 한다. 프로세스는 자원과 주소 공간의 관리 단위이고, 스레드는 그 안의 실행 흐름이다. 운영체제는 실행 가능한 스레드 등에 CPU 시간을 배분한다.

## 2. 주문 요청이 몰리면 CPU는 누구에게 돌아갈까 — Scheduling

주문 처리, 결제, 로그 저장 작업이 동시에 실행 준비를 마쳤다. 하지만 CPU 코어 수는 제한되어 있다.

**질문: 실행할 일이 더 많으면 누가 먼저 CPU를 사용할까?**

**Scheduling**이 실행 순서를 결정한다. 선점형은 실행 중인 작업에서 CPU를 회수할 수 있고, 비선점형은 실행 주체가 자발적으로 양보하거나 종료할 때 전환된다. 작업을 바꿀 때 **Context Switch**가 발생하며 상태 저장·복원 비용이 든다.

**질문: Context Switch를 많이 하면 무조건 처리량이 늘어날까?**

아니다. 응답성은 좋아질 수 있어도 전환 오버헤드가 증가한다. 공정성·응답시간·처리량 사이에 Trade-off가 있다. [실행 모델·CPU 배분 지도](01-실행모델-CPU-배분.md)에서 더 살펴본다.

## 3. 두 주문이 마지막 재고를 동시에 구매한다 — 동시성

재고가 1개 남았다. 두 스레드가 동시에 '재고 1개'를 읽고 각각 주문 성공으로 처리했다.

**질문: 스레드를 여러 개 만들었을 뿐인데 왜 잘못된 결과가 나왔을까?**

공유 상태에 대한 접근 순서가 결과를 바꾸는 **Race Condition** 때문이다. 임계영역을 보호하기 위해 Lock·Semaphore 등 **Synchronization** 수단을 사용한다.

그런데 스레드 A는 재고 Lock을 가진 채 결제 Lock을 기다리고, B는 결제 Lock을 가진 채 재고 Lock을 기다린다.

**질문: 동기화 수단을 사용했는데도 왜 프로그램이 멈출 수 있을까?**

서로 가진 자원을 기다리는 **Deadlock** 때문이다. Race Condition과 Deadlock은 같은 문제가 아니다. 또 서로 다른 프로세스가 정보를 교환하려면 Pipe·Socket·Shared Memory 등의 **IPC**가 필요할 수 있다.

~~~text
여러 실행 흐름
├─ 공유 데이터 충돌 → Race → 동기화
├─ 자원 대기 순환 → Deadlock → 예방·회피·탐지·회복
└─ 프로세스 간 협업 → IPC
~~~

이 셋은 필수 선후관계가 아닌 병렬 문제축이다. [동시성·자원공유 지도](02-동시성-자원공유.md)에서 관계를 복원한다.

## 4. 주문 서버가 메모리를 무한히 쓸 수 있을까 — Virtual Memory

주문 서버와 결제 서버가 같은 물리 메모리를 공유한다. 프로그램이 다른 프로그램의 메모리를 마음대로 읽을 수 있다면 위험하다.

**질문: 프로세스마다 독립적인 주소 공간을 어떻게 제공할까?**

**Virtual Memory**는 프로세스가 사용하는 가상 주소 공간과 실제 물리 메모리를 분리한다. Paging에서는 가상 Page를 물리 Frame에 대응시키고 Page Table이 변환 정보를 담는다. 주소 변환에는 하드웨어 MMU와 TLB가 관여한다.

**질문: 필요한 Page가 물리 메모리에 없다면 바로 프로그램이 실패할까?**

항상 그렇지는 않다. **Page Fault**가 발생하면 운영체제가 필요한 Page를 적재하는 등의 처리를 한다. 메모리가 부족하면 Page Replacement가 필요하다.

**질문: Page 교체가 너무 자주 일어나면?**

실제 계산보다 Page 교체에 시간을 쓰는 **Thrashing**이 발생할 수 있다. Paging은 배치 방식, Virtual Memory는 주소 공간·메모리 관리 체계, Page Fault는 그 안의 사건이라는 점을 구분한다. [메모리 관리 지도](03-메모리-관리.md)로 내려갈 수 있다.

## 5. 주문 기록은 어디에 남을까 — File과 Device I/O

주문 결과를 파일에 저장한다. 애플리케이션이 디스크 장치의 내부 명령을 직접 다 알아야 할까?

**질문: 서로 다른 저장장치를 어떻게 비슷한 방식으로 사용할 수 있을까?**

애플리케이션은 System Call과 File Descriptor 같은 인터페이스를 사용하고, 커널은 File System과 Device Driver 등을 통해 실제 장치를 다룬다. File System은 파일·디렉터리와 영속 데이터의 조직을, Device I/O는 장치 접근을 다룬다.

**질문: 디스크 작업이 끝날 때까지 CPU가 계속 상태를 확인해야 할까?**

Interrupt는 완료 등의 사건을 알리는 수단이고, Buffer/Cache는 데이터 이동과 성능을 보완한다. DMA는 CPU의 반복적인 데이터 복사 부담을 줄이는 하드웨어 전송 방식이다. 파일 추상화와 장치 I/O는 연결되지만 같은 층위는 아니다.

## 6. 주문 서버를 격리하면 안전하고 빨라질까 — Namespace·cgroup

같은 서버에서 여러 서비스를 실행한다. 한 서비스가 다른 서비스의 자원을 모두 사용하거나 프로세스 목록을 들여다보면 곤란하다.

**질문: 실행환경마다 보이는 자원과 사용할 수 있는 자원을 다르게 할 수 있을까?**

Linux의 **Namespace**는 자원에 대한 뷰를 분리하고, **cgroup**은 CPU·메모리 등의 사용량을 관리·제한한다. Container는 이런 OS 수준 기능을 활용하며 Host Kernel을 공유한다. VM은 Guest OS를 포함하는 별도 가상 컴퓨터라는 점에서 다르다. 상세 비교는 [가상화 전체 지도](../99-가상화/00-전체.md)를 참고한다.

**질문: 자원을 격리했다고 서비스 성능과 가용성이 자동으로 보장될까?**

아니다. 병목·용량·성능을 관측해야 하고 장애 영향 축소와 복구도 따로 고려해야 한다. Performance·Capacity·HA·Checkpointing은 자원 격리와 연결되지만 동일한 기술이 아니다.
