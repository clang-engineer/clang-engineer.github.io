# 함수 객체와 Closure — Functor · Lambda · Capture · Lexical Scope

> 학습 원칙: [`00-프로그래밍-언어-학습원칙.md`](00-프로그래밍-언어-학습원칙.md)
>
> 핵심 질문: **함수에 상태를 붙여 값처럼 전달하고, 나중에도 그 상태를 사용할 수 있게 하려면 어떻게 해야 하는가?**

---

## 1. 큰 그림

Functor, Lambda, Capture, Closure, Lexical Scope는 같은 개념은 아니지만 함께 보면 관계가 잘 보인다.

```text
호출 가능한 코드가 필요하다
        ↓
Function / Function Object
        ↓
객체에 상태를 함께 둘 수 있다
        ↓
Functor
        ↓
익명 함수 객체를 간결하게 만든다
        ↓
Lambda
        ↓
바깥 상태가 필요하다
        ↓
Capture
        ↓
함수가 자신이 만들어진 환경을 계속 사용할 수 있다
        ↓
Closure

그 함수는 어떤 바깥 이름을 볼 수 있는가?
        ↓
Lexical Scope
```

이 흐름은 개념이 역사적으로 발전한 순서를 뜻하지 않는다. **C++의 구체적인 메커니즘에서 출발해 Closure와 Lexical Scope를 이해하기 위한 학습 경로**다.

---

## 2. Function Object / Functor — 상태를 가진 호출 가능 객체

C++에서 Functor(Function Object)는 보통 `operator()`를 정의해 함수처럼 호출할 수 있는 객체를 뜻한다.

```cpp
struct Counter {
    int count = 0;

    int operator()() {
        return ++count;
    }
};

Counter counter;

counter(); // 1
counter(); // 2
counter(); // 3
```

겉으로는 함수 호출처럼 보이지만 실제로는 다음 멤버 함수를 호출한다.

```cpp
counter.operator()();
```

중요한 점은 Functor도 객체이므로 상태를 멤버로 가질 수 있다는 것이다.

```text
일반 함수
→ 실행할 코드

Functor
→ 실행할 코드(operator()) + 객체 상태
```

이 관점이 Closure를 이해하는 첫 번째 발판이다.

---

## 3. Lambda — 익명 Function Object를 간결하게 만드는 문법

C++ Lambda를 단순히 "이름 없는 함수"라고만 보면 내부 구조가 잘 보이지 않는다.

```cpp
int x = 10;

auto f = [x]() {
    return x;
};
```

개념적으로는 Compiler가 다음과 비슷한 익명 타입을 만든다고 생각할 수 있다.

```cpp
struct __Lambda {
    int x;

    int operator()() const {
        return x;
    }
};
```

C++ 관점에서는 다음 흐름으로 이해하면 된다.

```text
Lambda Expression
        ↓
익명 Closure Type 생성
        ↓
Closure Object 생성
        ↓
operator()로 호출
```

즉 Lambda는 완전히 새로운 종류의 함수라기보다 **Functor를 언어가 간결하게 만들어 주는 문법**으로 보면 구조가 선명해진다.

---

## 4. Capture — Lambda가 바깥 상태를 가져오는 방법

Lambda가 자신이 정의된 바깥 Scope의 값을 사용하려면 Capture가 필요하다.

```cpp
int x = 10;

auto by_value = [x]() {
    return x;
};

auto by_reference = [&x]() {
    return x;
};
```

C++은 무엇을 어떤 방식으로 Capture하는지 문법에 드러낸다.

```text
[x]
→ 값을 Capture
→ Lambda Object 안에 값이 들어간다고 이해하면 쉬움

[&x]
→ 참조로 Capture
→ 바깥 객체가 언제까지 살아 있는지 확인해야 함
```

값 Capture는 개념적으로 다음처럼 생각할 수 있다.

```cpp
struct __Lambda {
    int x;
};
```

따라서 C++에서 Capture를 볼 때는 세 가지를 묻는다.

```text
무엇을 가져오는가?
→ 값인가, 참조인가?

가져온 상태는 어디에 있는가?
→ Closure Object 안인가, 바깥 객체를 가리키는가?

나중에 호출해도 안전한가?
→ 참조 대상이 그때까지 살아 있는가?
```

---

## 5. Closure — 함수가 자신이 만들어진 환경을 계속 사용한다

Closure는 특정 언어의 문법 이름이 아니다. **함수가 자신이 만들어질 때 접근하던 바깥 환경을 나중에도 사용할 수 있게 하는 개념**이다.

JavaScript 예제를 보자.

```javascript
function makeCounter() {
  let count = 0;

  return function () {
    return ++count;
  };
}

const counter = makeCounter();

counter(); // 1
counter(); // 2
counter(); // 3
```

`makeCounter()` 호출은 이미 끝났지만 반환된 함수는 계속 `count`에 접근한다.

```text
makeCounter() 실행
        ↓
count = 0 생성
        ↓
내부 함수 생성
        ↓
내부 함수가 count가 있는 환경을 참조
        ↓
makeCounter() 종료
        ↓
반환된 함수는 계속 count를 사용할 수 있음
```

여기서 `count` 값을 무조건 복사해 저장한다고 일반화하면 안 된다. **어떤 값을 어떻게 Capture하고 환경을 얼마나 오래 유지하는지는 언어마다 다르다.**

---

## 6. C++ Capture Lambda와 JavaScript Closure 비교

JavaScript Closure는 C++ Capture Lambda를 떠올리면 이해하기 쉽다.

```cpp
int x = 10;
auto f = [x]() { return x; };
```

```javascript
let x = 10;
const f = () => x;
```

둘 다 다음 직관을 준다.

```text
실행할 코드
  +
바깥 상태
  ↓
나중에 호출할 수 있는 함수 값
```

하지만 동작 방식은 다르다.

### C++

```text
[x]
→ 값으로 Capture

[&x]
→ 참조로 Capture

Capture 방식이 문법에 드러남
참조 Capture에서는 대상 Lifetime을 개발자가 직접 확인해야 함
```

### JavaScript

```text
함수가 정의된 Lexical Environment의 Binding을 참조
필요한 Environment는 Runtime이 계속 유지
```

다음 예제가 차이를 잘 보여준다.

```javascript
let x = 10;
const f = () => console.log(x);

x = 20;
f(); // 20
```

`f`가 만들어질 때 `10`을 복사해 둔 것이 아니다. `x`라는 Binding이 있는 Lexical Environment를 통해 현재 값을 읽는다.

C++ 직관으로는 값 Capture보다 참조 Capture가 더 가깝다.

```cpp
int x = 10;
auto f = [&x]() {
    std::cout << x;
};

x = 20;
f(); // 20
```

다만 JavaScript에서는 C++처럼 Dangling Reference를 개발자가 직접 관리하지 않는다. 필요한 Environment의 Lifetime을 Runtime이 관리한다.

> **JavaScript Closure ≈ C++ Capture Lambda는 좋은 출발점이다. 다만 Capture 방식과 Lifetime 관리까지 같다는 뜻은 아니다.**

## 7. Lexical Scope — 변수는 호출한 곳이 아니라 정의된 곳을 따라 찾는다

Closure를 이해하려면 Lexical Scope를 함께 봐야 한다.

Lexical Scope는 **변수를 어디서 찾을지가 함수의 호출 위치가 아니라 코드가 정의된 위치로 결정되는 Scope 규칙**이다.

```javascript
let x = "global";

function foo() {
  console.log(x);
}

function bar() {
  let x = "bar";
  foo();
}

bar(); // global
```

`foo()`는 `bar()` 안에서 호출됐지만 `bar`의 `x`를 사용하지 않는다. `foo`가 정의된 위치에서 바깥 Scope를 따라가면 Global Scope가 나오기 때문이다.

```text
foo 내부
  ↓ 없으면
foo가 정의된 바깥 Scope
  ↓
Global Scope
```

따라서 둘은 이렇게 구분한다.

```text
Lexical Scope
→ 이 코드 위치에서 어떤 바깥 이름을 볼 수 있는가?

Closure
→ 그 바깥 환경을 나중에도 사용할 수 있는가?
```

관련은 있지만 같은 개념은 아니다.

---

## 8. C++ 관점에서 Lexical Scope 이해하기

C++도 기본적으로 Lexical Scope를 사용한다.

```cpp
int x = 10;

void foo() {
    std::cout << x;
}
```

`foo` 안에서 `x`를 찾을 때 코드의 정적인 Scope 구조를 따라간다.

Lambda에서는 그 Scope 안에서 보이는 이름 중 실제로 사용할 외부 상태를 Capture한다.

```cpp
void outer() {
    int x = 10;

    auto f = [x]() {
        return x;
    };
}
```

C++ 관점에서는 다음처럼 구분하면 쉽다.

```text
Lexical Scope
→ 현재 코드 위치에서 어떤 바깥 이름이 보이는가?

Capture
→ 그중 Lambda가 어떤 상태를 가져오는가?

Closure Object
→ Capture한 상태와 호출 코드를 함께 가진 실제 객체
```

JavaScript는 `[x]`처럼 Capture 목록을 적지 않지만, 함수가 Lexical Scope를 통해 외부 Binding을 사용하면 그 환경과의 관계가 유지된다.

## 9. Lambda와 Closure는 같은 개념이 아니다

다음 C++ Lambda는 아무것도 Capture하지 않는다.

```cpp
auto add = [](int a, int b) {
    return a + b;
};
```

Lambda이지만 외부 상태를 사용하지 않는다.

반면 다음 Lambda는 상태를 Capture한다.

```cpp
int offset = 10;

auto add = [offset](int value) {
    return value + offset;
};
```

따라서 다음처럼 구분한다.

```text
Lambda
→ 익명 호출 가능 객체를 만드는 표현 방식

Capture
→ 바깥 상태를 가져오는 방식

Closure
→ 함수가 자신이 만들어진 환경을 나중에도 사용할 수 있게 하는 개념
```

언어마다 이 세 가지를 표현하는 문법과 Runtime 동작이 다르다.

---

## 10. Closure가 필요한 이유

Closure의 핵심 가치는 **할 일과 그 일을 할 때 필요한 상태를 함께 묶어 전달할 수 있다는 것**이다.

```text
할 일
+
필요한 상태
↓
하나의 호출 가능한 값
```

대표적으로 다음과 연결된다.

```text
Callback
→ 나중에 실행할 함수가 현재 상태를 기억해야 함

Iterator
→ 순회 상태와 다음 연산을 함께 유지

Event Handler
→ 등록할 때의 Context를 나중에 사용

Async 작업
→ 작업이 끝난 뒤에도 필요한 상태를 다시 사용
```

예를 들어:

```javascript
function request(id) {
  fetch(`/items/${id}`).then(() => {
    console.log(id);
  });
}
```

Callback이 나중에 실행되어도 `id`를 사용할 수 있는 이유는 Closure와 관련 있다.

반면 Callback을 **언제 실행할지**는 Event Loop나 Promise Scheduling의 문제다.

```text
무엇을 기억하는가?
→ Closure

언제 실행하는가?
→ Event Loop / Scheduler
```

## 11. 개념 경계 정리

| 개념 | 핵심 질문 | C++ 기준점 |
|---|---|---|
| Function Object / Functor | 함수처럼 호출되는 객체인가? | `operator()` |
| Lambda | 익명 호출 가능 객체를 어떻게 간결하게 만드는가? | Lambda Expression |
| Capture | 바깥 상태를 어떻게 가져오는가? | `[x]`, `[&x]` |
| Closure | 함수가 정의될 때의 환경을 나중에도 사용할 수 있는가? | Capture Lambda / Closure Object |
| Lexical Scope | 변수 검색 관계를 무엇이 결정하는가? | 정적 Scope 구조 |

한 줄로 연결하면:

> **Functor는 상태를 가진 호출 가능 객체라는 실체를 보여주고, Lambda는 이를 간결하게 만들며, Capture는 바깥 상태를 연결한다. Closure는 함수가 그 환경을 나중에도 사용할 수 있게 하고, Lexical Scope는 어떤 바깥 이름을 볼 수 있는지 정한다.**

---

## 12. 기억·인출

```text
Functor
= 객체인데 ()로 호출

Lambda
= 익명 Functor를 만드는 문법

Capture
= 바깥 상태를 가져옴

Closure
= 함수가 만든 곳의 환경을 기억

Lexical Scope
= 호출한 곳이 아니라 정의된 곳을 따라 변수 검색
```

핵심 문장:

> **C++에서는 Capture Lambda를 떠올리면 Closure의 실체를 잡기 쉽다. 다만 각 언어가 외부 상태를 Capture하고 Lifetime을 관리하는 방식은 다르다.**
