# 모듈과 의존관계 — Import · Export · Linking · Loading

> 학습 원칙: [`00-프로그래밍-언어-학습원칙.md`](00-프로그래밍-언어-학습원칙.md)
>
> 핵심 질문: **코드를 어떤 단위로 나누고, 서로 무엇을 공개하며, 필요한 구현을 언제 연결하고 실행하는가?**

---

## 1. 큰 그림

Module System은 단순히 `import` 문법을 제공하는 기능이 아니다.

```text
코드를 여러 단위로 나눈다
        ↓
밖에 무엇을 공개할까?
        ↓
다른 Module은 무엇을 사용할까?
        ↓
필요한 Module을 언제 찾고 연결할까?
├─ Compile / Link Time
└─ Runtime
        ↓
실제 Code는 언제 Load하고 실행할까?
```

핵심 질문은 네 가지다.

```text
무엇을 Export하는가?
무엇을 Import하는가?
의존관계를 언제 연결하는가?
Module Code는 언제 Load/Evaluate되는가?
```

---

## 2. C++ 기준점 — 선언과 구현, Compile과 Link

C++에서는 Header와 Source, Object File과 Link 단계가 의존관계를 비교적 직접 보여준다.

```cpp
// math.h
int add(int a, int b);
```

```cpp
// math.cpp
int add(int a, int b) {
    return a + b;
}
```

사용 측:

```cpp
#include "math.h"
```

큰 흐름:

```text
Source
  ↓ Compile
Object File
  ↓ Link
Executable / Library
```

다만 C++의 전통적인 `#include`는 Module Import와 같은 기능이 아니다. Preprocessor가 Text를 포함하는 방식이라는 점을 구분한다.

---

## 3. 선언과 정의 — 사용할 수 있다는 사실과 실제 구현은 다르다

C++에서:

```cpp
int add(int, int); // 선언
```

은 Compiler에게 "이런 함수가 있다"고 알려준다.

```cpp
int add(int a, int b) { // 정의
    return a + b;
}
```

은 실제 구현을 제공한다.

이 구분은 다른 언어의 Module을 볼 때도 유용하다.

```text
외부 계약
→ 어떤 이름, 타입, 함수를 사용할 수 있는가?

실제 구현
→ 그 이름이 어떤 Code와 상태를 가지는가?
```

---

## 4. Linking — 필요한 이름과 실제 구현을 연결한다

C++ Toolchain에서는 Compile된 Object File들이 서로 필요한 Symbol을 Linker가 연결한다.

```text
main.o
  └─ add Symbol 필요

math.o
  └─ add Symbol 제공

        ↓ Link

Executable
```

즉 Linking은 **외부에서 필요로 하는 이름을 실제 구현과 연결하는 과정**으로 보면 된다.

언어와 Runtime에 따라 이 연결은 Compile Time, Link Time, Load Time, Runtime에 일어날 수 있다.

---

## 5. Static Linking과 Dynamic Linking

### Static Linking

```text
Library Code
→ Build할 때 Executable에 포함
```

### Dynamic Linking

```text
Executable
→ Shared Library를 참조
→ Load/Runtime에 실제 Library와 연결
```

핵심 Trade-off:

```text
Static
→ 배포가 단순해질 수 있음
→ Binary가 커질 수 있음

Dynamic
→ Library 공유와 교체가 쉬울 수 있음
→ Runtime 의존관계 관리가 필요
```

언어의 Module Import와 완전히 같은 개념은 아니지만 **필요한 구현을 언제 실제로 연결하느냐**를 이해하는 좋은 기준점이다.

---

## 6. JavaScript CommonJS — 실행하면서 Module을 불러온다

```javascript
const fs = require("fs");
```

`require()`는 일반 함수 호출처럼 실행 흐름 안에 둘 수 있다.

```javascript
if (enabled) {
  const feature = require("./feature");
  feature.run();
}
```

개념적으로는 다음과 같다.

```text
실행 흐름
  ↓
require()
  ↓
Resolve
  ↓
Load / Evaluate
  ↓
module.exports 반환
```

핵심은 **Runtime에 실제 코드가 실행되면서 Module을 찾고 불러올 수 있다는 점**이다.

---

## 7. ESM — 실행 전에 Module 관계를 파악할 수 있다

```javascript
import { add } from "./math.js";
```

정적 `import`는 Module 본문을 실행하기 전에 의존관계를 분석하고 연결할 수 있게 한다.

```text
Module A
├─ import B
└─ import C
      ↓
Resolve
      ↓
Module Graph 구성
      ↓
Link
      ↓
Evaluation
```

이 선언적 구조 덕분에 Bundler나 정적 분석 Tool이 Module Graph를 미리 파악할 수 있다.

---

## 8. 정적 import와 동적 import()는 다르다

```javascript
import { x } from "./a.js";
```

```text
정적 import
→ 의존관계를 선언
→ 실행 전에 Module Graph 분석 가능
```

반면:

```javascript
const module = await import(path);
```

```text
동적 import()
→ 실행 중 Module 요청
→ Promise 기반 비동기 Loading
```

따라서 `ESM = 비동기 Import`라고 외우면 안 된다.

---

## 9. Export할 때 값 자체를 넘기는가, Binding을 공유하는가

Module System에서는 "무엇을 Export하느냐"도 중요하다.

```text
한 번 복사한 값인가?
공유 객체인가?
이름 Binding 자체인가?
```

ESM은 `Live Binding`을 제공한다.

```javascript
// counter.js
export let count = 0;
export function inc() {
  count++;
}
```

다른 Module에서 Import한 `count`는 Export한 Binding의 변경을 반영한다.

즉 "Import할 때 값을 한 번 복사한다"고 생각하면 틀릴 수 있다.

---

## 10. Module Cache와 공유 상태

Runtime Module System에서는 Module을 한 번 Evaluate한 뒤 결과를 Cache할 수 있다.

```text
첫 Import
→ Load
→ Evaluate
→ Module State 생성

다음 Import
→ 기존 Module Instance / Namespace 재사용
```

이 때문에 Module의 Top-level 상태가 Application 전체에서 공유 상태처럼 동작할 수 있다.

Cache와 Module Instance 규칙은 언어와 Runtime마다 다르므로 따로 확인해야 한다.

---

## 11. Package와 Module은 같은 개념이 아니다

```text
Module
→ 언어/Runtime에서 Code와 Namespace를 나누는 단위

Package
→ 여러 Module, Metadata, Dependency, 배포 정보를 묶는 더 큰 단위일 수 있음
```

Java Package, npm Package, Python Package, Rust Crate/Module은 계층과 의미가 다르다.

따라서 `Package = Folder`, `Module = File`처럼 모든 언어에 똑같이 적용하지 않는다.

---

## 12. Dependency Injection과 Module System도 구분한다

Module System은 **코드 단위끼리 무엇에 의존하는가**를 다룬다.

Dependency Injection은 **필요한 구체 객체나 구현을 누가 만들어서 넘겨주는가**를 다룬다.

C++:

```cpp
Service(Database& db) : db_(db) {}
```

이 코드는 객체 Dependency를 주입하는 예다. Header/Library Linking과 같은 문제는 아니다.

두 개념은 실제 Application Architecture에서 연결될 수 있지만 같은 개념으로 보지 않는다.

---

## 13. 순환 의존관계

```text
Module A → Module B
   ↑          ↓
   └──────────┘
```

Circular Dependency가 생기면 다음 문제가 따라올 수 있다.

- 초기화 순서가 복잡해진다.
- 아직 다 만들어지지 않은 상태가 노출될 수 있다.
- Module 사이 결합도가 높아진다.
- Build/Link/Load 과정이 복잡해질 수 있다.

순환 참조를 허용하는 방식과 초기화 규칙은 Module System마다 다르다.

---

## 14. 기술사 관점의 비교축

| 비교축 | 질문 |
|---|---|
| 의존관계 결정 시점 | Compile/Link/Load/Runtime 중 언제인가? |
| 노출 단위 | 값, Symbol, Binding, Type, Namespace 중 무엇인가? |
| 정적 분석 | Module Graph를 실행 전에 분석할 수 있는가? |
| 로딩 | 동기/비동기, Lazy/Eager 중 무엇인가? |
| 배포 | Static/Dynamic Library 또는 Package 단위는 무엇인가? |
| 초기화 | Module State를 언제 만들고 몇 번 Evaluate하는가? |
| 순환 의존 | 허용 여부와 초기화 규칙은 무엇인가? |

---

## 15. 기억·인출

```text
Module
= 코드를 나누고 밖에 쓸 계약을 공개

Import / Export
= 무엇을 가져오고 내보내는가

Link
= 필요한 이름과 실제 구현을 연결

Load
= 실제 Code/Module을 Runtime에 올림

Evaluate
= Module Top-level Code 실행
```

핵심 문장:

> **Module System의 본질은 `import` 문법이 아니다. 코드를 어떤 단위로 나누고 무엇을 공개하며, 필요한 구현을 언제 연결하고 실행할지를 정하는 데 있다.**
