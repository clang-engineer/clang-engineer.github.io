# CPU 구조와 명령 실행 개념지도

이 문서는 [컴퓨터 구조 전체 개념지도](00-전체.md)에서 **CPU의 구성 → 명령 실행 → 성능 개선**을 따라가는 지도다. CPU를 먼저 하나의 실행 장치로 이해하고, ISA와 병렬 실행 기술은 해당 동작을 설명하는 자리에서 연결한다.

## 1. 전체 좌표 — CPU의 구성·동작·성능

```text
CPU — 명령어를 실행하는 중앙처리장치
│
├─ ① 구성 — 무엇으로 이루어지는가?
│  ├─ CU       → 명령 해독·제어
│  ├─ ALU      → 산술·논리연산
│  └─ Register → 값·실행 상태 임시 저장
│
├─ ② 동작 — 어떻게 명령어를 실행하는가?
│  ├─ Fetch → Decode → Execute
│  ├─ 명령어 규격 → ISA (설계 접근: CISC / RISC)
│  └─ 명령어·데이터 접근 구조 → 폰노이만 / 하버드
│
└─ ③ 성능 — 어떻게 처리량을 높이는가?
   ├─ Pipeline → 여러 명령어의 실행 단계 중첩
   │  └─ 제약 → Hazard
   └─ Multicore → 여러 코어 활용
      └─ 다른 병렬화 방식은 본문에서 소개
```

이 구분은 **구성·동작·성능이라는 서로 다른 질문**에 답한다. ISA는 명령어 실행의 규격이지 CPU의 구성요소나 별도의 실행 단계가 아니다. Pipeline·Multicore 역시 순서대로 교체되는 기술이 아니라 서로 조합 가능한 성능 개선 방법이다.

### 먼저 기억할 실행 관계

```text
메모리에 저장된 명령어
         │
         ▼
      CPU 인출 (Fetch)
         │
         ▼
      CU 해독 (Decode) ── 명령어 규격: ISA
         │
         ▼
      실행 (Execute)
      ├─ ALU → 필요한 연산 수행
      └─ Register ↔ 값·결과·상태 보관
         │
         ▼
      다음 명령어 처리

여러 명령어를 더 효율적으로 처리하려면
├─ 실행 단계 겹치기 → Pipeline
└─ 실행 자원 확대 → Multicore 등
```

이 흐름은 개념적 단순화이며, 명령어에 따라 ALU 연산 없이 메모리 접근이나 분기 등을 수행할 수도 있다. ISA·CISC·RISC는 아래 명령어 체계 설명에서 다루고, Superscalar·VLIW·SMT의 자세한 차이는 병렬 컴퓨터 학습에서 살펴본다.

## 2. CPU가 명령어를 실행하는 과정

CPU는 **메모리에 저장된 명령어를 가져와 해독하고 실행**한다. 이 과정을 이해하려면 먼저 CPU 내부에서 누가 무엇을 하는지, 명령어와 데이터가 어떻게 이동하는지 살펴봐야 한다.

```text
메모리의 명령어·데이터
          │
          ▼
CPU가 명령어 인출 → 해독 → 실행
    │                │
    ├─ Register      ├─ CU: 해독·제어
    └─ 주소·내용 보관 └─ ALU: 필요한 연산
          │
          └─ 메모리 접근에는 연결 경로가 필요
```

### 구성요소·구조·명령어 실행 사이클의 관계

```text
CPU
├─ CU (제어장치) → 명령어 해독, 데이터 경로 제어
├─ ALU (연산장치) → 산술·논리연산
└─ Register      → 피연산자·결과·실행 상태 임시 저장

명령어 실행 사이클 (개념적 모델)
Fetch → Decode → Execute → 필요시 결과 기록
```

명령어는 **수행할 작업**, 데이터는 **작업의 대상**이다. 예를 들어 ADD 명령은 더하기를 지시하고, 3과 5는 피연산자다. 제어장치는 덧셈을 해석하고 관련 신호를 제어하며, ALU가 연산하고 결과는 레지스터 등에 기록된다.

### ALU와 CU: 역할에서 내부 구현까지

- **ALU:** 가산기·논리연산 회로·연산 선택 회로 등을 이용해 연산하고, Zero(결과 0)·Carry(자리올림)·Overflow(부호 있는 연산 범위 초과) 등의 상태 플래그를 생성할 수 있다.
- **CU:** 명령어 해독, 제어 순서·타이밍 관리, ALU·레지스터·메모리 제어신호 생성을 담당한다.
- **Hardwired 제어:** 논리회로로 제어 규칙을 구현한다. 빠른 제어에 유리하지만 변경이 어려울 수 있다.
- **Microprogrammed 제어:** 제어 메모리에 저장된 마이크로명령어를 통해 제어 동작을 구성한다. 복잡한 제어 표현과 변경에 유리할 수 있다.

두 제어 방식 모두 하드웨어 구현이며 실제 CPU에서는 혼합될 수 있다. 회로도나 마이크로명령어 비트 구성은 1차 복습에서 보류한다.

### 레지스터는 저장 대상보다 역할로 구분한다

CPU의 기본 기능은 **CU(해독·제어), ALU(산술·논리연산), Register(임시 저장)**로 설명할 수 있다. Register는 하나의 저장 공간이 아니라 용도가 다른 여러 레지스터를 통칭한다.

| 레지스터 | 의미 | 핵심 역할 |
|---|---|---|
| PC (Program Counter) | 프로그램 카운터 | 다음에 인출할 명령어의 주소 |
| IR (Instruction Register) | 명령어 레지스터 | 현재 인출한 명령어 |
| MAR (Memory Address Register) | 메모리 주소 레지스터 | 현재 접근할 메모리 주소 |
| MDR (Memory Data Register) | 메모리 데이터 레지스터 | 메모리와 주고받는 내용 |
| ACC (Accumulator) | 누산기 | 연산 결과 누적 |
| GPR (General Purpose Register) | 범용 레지스터 | 피연산자·주소·결과 등 보관 |

```text
CPU 내부 Register — 역할에 따른 구분
├─ 명령 흐름 → PC(다음 명령어 주소), IR(현재 명령어)
├─ 메모리 접근 → MAR(접근 주소), MDR(읽고 쓸 내용)
└─ 연산 → ACC(누산), GPR(범용 데이터·주소·결과)
```

명령어 인출을 설명하는 전통적인 단순 모델에서는 **PC → MAR → Memory → MDR → IR → CU**로 연결한다. PC는 *다음 명령어 주소*, MAR은 *현재 메모리 접근 주소*라는 점이 다르다. MDR은 명칭에 Data가 있어도 명령어 인출 시 읽어 온 명령어 비트를 전달할 수 있다. 실제 현대 CPU가 이 레지스터들을 모두 독립된 물리 레지스터로 구현한다는 뜻은 아니다.

**레지스터의 역할별 구분 ≠ 하버드 구조의 명령어·데이터 메모리/경로 분리.** PC·IR·MAR·MDR·ACC 같은 역할 분류는 폰노이만·하버드 여부를 결정하지 않는다. L1 I-Cache/D-Cache의 구분 역시 캐시의 저장 용도에 관한 별도 분류다.

### 명령어 사이클과 CPU Major State의 관계

**명령어 사이클**은 명령어를 인출하고 실행하는 전체 처리 흐름이다. 기본 동작을 설명할 때는 **Fetch(인출) → Decode(해독) → Execute(실행)**로 단순화한다. 전통적인 **CPU Major State** 모델은 같은 처리 흐름을 **인출 → 간접 → 실행 → 인터럽트**라는 주요 상태로 나눈다. 둘은 별개의 CPU 실행 방식이 아니다.

```text
명령어 사이클 (전통적 주요 상태 모델)
인출(Fetch) → [간접(Indirect)] → 실행(Execute) → [인터럽트(Interrupt)]
    └─ 명령어 인출·해독        └─ 명령 수행        └─ 필요할 때 처리
```

- **Decode**는 명령어의 의미를 해석하는 동작이며, 전통적인 Major State 분류에서는 별도 상태가 아니라 인출 단계에 포함해 설명할 수 있다.
- **Indirect**는 간접 주소 지정 명령에서 실제 접근할 주소를 추가로 확인할 때만 필요하다.
- **Interrupt**는 처리할 인터럽트가 있을 때 실행 상태를 보존하고 처리 루틴으로 이동한 뒤 복귀하는 과정이다.

Major State는 **중요도 순위가 아닌 상태 분류**다. 모든 현대 CPU가 이 네 상태를 그대로 물리적으로 구현하는 것은 아니다.

### CPU와 메모리의 연결 — 시스템 버스

CPU는 명령어를 인출하거나 데이터를 읽고 쓰려면 메모리와 정보를 주고받아야 한다. 전통적인 CPU 중심 모델에서 이 연결을 설명하는 것이 **시스템 버스**다. 레지스터가 CPU 내부에 값을 보관한다면, 버스는 장치 사이에서 주소·데이터·제어신호를 전달한다.

```text
CPU ── 주소 버스 ──→ Memory  : 어디에 접근할까?
CPU ←─ 데이터 버스 ─→ Memory : 무엇을 읽고 쓸까?
CPU ←─ 제어 버스 ─→ Memory  : 읽기·쓰기 요청, 상태 신호 등
```

전통적인 CPU 중심 모델에서 **주소 버스는 대체로 단방향**, **데이터 버스는 양방향**이다. 제어 버스는 양방향 신호의 집합이지만 개별 제어신호에는 각자의 방향이 있다. 읽기와 쓰기 모두 CPU가 주소를 지정하므로 주소 버스 방향은 바뀌지 않는다.

**대역폭(Bandwidth)**은 단위 시간에 전송할 수 있는 데이터 양, **지연시간(Latency)**은 요청부터 응답까지 걸리는 시간이다. 여러 장치가 공유 경로를 동시에 요구하는 **버스 경합(Contention)**은 대기와 **버스 병목(Bottleneck)**을 일으킬 수 있다. 실제 현대 시스템은 단일 공유 버스보다 복잡한 인터커넥트를 사용한다.

### 메모리 접근 구조 — 폰노이만과 하버드

버스를 통해 명령어와 데이터가 이동한다는 것을 이해했다면, 다음 질문은 **명령어와 데이터가 같은 메모리·접근 경로를 공유하는가?**이다.

```text
명령어·데이터 접근 구조
├─ 폰노이만 → 메모리·접근 경로 공유
│             └─ 전송 경합·대역폭 병목 가능
└─ 하버드   → 명령어·데이터 메모리·경로 분리
              └─ 인출과 데이터 접근 병행에 유리
```

두 구조 모두 명령어를 인출·해독·실행한다. 현대 PC는 일반적으로 명령어와 데이터를 같은 주기억장치 주소 공간에 두면서 L1 명령어 캐시와 L1 데이터 캐시를 분리해 양쪽 특징을 활용한다. 순수 하버드 구조와는 구분한다. 캐시 계층은 [메모리 계층 지도](02-메모리-계층-가상메모리.md)에서 다룬다.

### 명령어 규격 — ISA와 CISC·RISC

CPU가 명령어를 가져오는 통로와 실행 과정을 알았다면, **그 명령어의 형식과 의미는 누가 정하는가?**라는 질문이 남는다. 그 규격이 ISA다. ISA는 전송 통로나 실행 단계 자체가 아니다.

**ISA(Instruction Set Architecture)**는 소프트웨어가 CPU에 요청할 수 있는 명령어의 종류·형식·레지스터 사용 규칙 등을 정의하는 **소프트웨어와 하드웨어 사이의 인터페이스**다. CU는 ISA에 맞게 인출된 명령어를 해독하고 실행을 제어한다. 즉 **ISA는 규칙, CU는 그 규칙을 구현하는 하드웨어**다.

```text
같은 소스 프로그램
       │
       ├─ x86-64용 컴파일 → x86-64 기계어 → Intel·AMD CPU
       └─ ARM64용 컴파일  → ARM64 기계어  → Apple M 시리즈 등

ISA (지원하는 명령어의 약속)
├─ x86-64 → 전통적으로 CISC 계열
├─ ARM64  → RISC 계열
└─ RISC-V → RISC 계열

CISC / RISC = 구체적 ISA의 이름이 아닌 설계 접근 방식
```

| 구분 | CISC | RISC |
|---|---|---|
| 설계 방향 | 다양하고 복잡한 명령어 지원 | 단순하고 규칙적인 명령어 중심 |
| 기대 효과 | 복합 작업 표현·코드 밀도에 유리할 수 있음 | 해독·실행 구조 단순화에 유리 |
| 고려할 대가 | 해독·구현 복잡도 증가 가능 | 같은 작업에 더 많은 명령어가 필요할 수 있음 |
| 대표 ISA | x86 계열 | ARM·RISC-V 계열 |

**칩마다 명령어가 전부 다른 것은 아니다.** Intel과 AMD는 공통 x86-64 ISA의 명령어를 실행할 수 있지만, ARM64와 x86-64의 기계어는 서로 다르므로 일반적으로 대상 ISA에 맞춰 컴파일하거나 변환·에뮬레이션해야 한다. 같은 ISA라도 CPU 모델별 확장 명령 지원과 내부 구현은 다를 수 있다.

**CISC가 무조건 느리거나 RISC가 무조건 빠른 것은 아니다.** 현대 x86 CPU는 복잡한 명령어를 내부 마이크로 연산으로 변환하기도 하며, 실제 성능·전력 효율은 마이크로아키텍처·제조 공정·워크로드에 따라 달라진다. 1차 복습에서는 **ISA = 명령어 규칙 / CU = 해독·제어 / CISC·RISC = 설계 철학**의 관계를 우선 이해한다.

## 3. 명령어를 더 많이 처리하려면 — 파이프라이닝

명령어를 하나씩 처리하는 기본 흐름을 이해했다면, 다음 질문은 **여러 명령어를 어떻게 효율적으로 처리할까?**이다. 이를 위해 서로 다른 명령어의 실행 단계를 겹치는 파이프라이닝을 사용할 수 있다.

파이프라이닝은 여러 명령의 실행 단계를 겹쳐 처리해 처리량을 높인다.

```text
명령 1: Fetch → Decode → Execute
명령 2:         Fetch → Decode → Execute
명령 3:                 Fetch → Decode → Execute
```

단계를 겹치면 서로 독립적이지 않은 명령이나 공유 자원 때문에 문제가 생긴다.

```text
파이프라이닝
  ↓
동시에 여러 명령이 진행
  ↓
해저드
├─ 데이터 해저드   → 명령 사이 데이터 의존
├─ 제어 해저드     → 분기 결과를 아직 모름
└─ 구조 해저드     → 같은 하드웨어 자원을 동시에 요구
```

기술사 관점에서는 각 해저드의 세부 회로보다 **왜 생기고 어떤 방식으로 완화하며, 그 대가가 무엇인지**를 중심으로 본다.

## 4. 병렬 실행을 더 넓히려면 — 명령 수준 병렬성

파이프라이닝만으로 충분하지 않을 때는 같은 시점에 여러 명령어를 발행·실행하는 방법을 생각할 수 있다. 파이프라이닝이 실행 단계를 겹치는 구조라면 Superscalar와 VLIW는 한 시점에 더 많은 명령을 병렬 실행하려는 대표 구조다.

```text
명령 수준 병렬성(ILP)
├─ Superscalar
│   └─ 하드웨어가 실행 가능한 명령을 동적으로 찾아 병렬 실행
│
└─ VLIW
    └─ 컴파일러가 병렬 실행할 명령 묶음을 미리 구성
```

둘은 같은 문제를 다른 위치에서 해결한다.

```text
Superscalar
→ 하드웨어 복잡도 증가

VLIW
→ 컴파일러 책임과 코드 스케줄링 부담 증가
```

## 5. 명령어를 넘어 코어·스레드 수준으로

명령어 단위의 병렬성과 별개로, 실행 자원을 여러 코어와 스레드에서 활용하는 방식도 있다.

```text
명령 하나의 실행 흐름을 개선
        ↓
명령 수준 병렬성
        ↓
더 큰 처리량이 필요
        ↓
실행 주체 자체를 늘림
├─ Multicore → 여러 Core
└─ SMT       → 한 Core의 실행 자원을 여러 Thread가 활용
```

Multicore와 SMT는 파이프라이닝의 단순 하위 단계가 아니다. 병렬성을 확보하는 수준이 다르다.

## 6. 처리량을 높여도 왜 한계가 있을까?

병렬 실행을 확대해도 순차 실행 구간과 자원 제약이 남으므로 성능 향상에는 한계가 있다. 이 관계를 정량적으로 설명하는 **Amdahl 법칙**과 CPI·클록 주파수·명령어 수에 따른 실행 시간 평가는 [성능과 신뢰성 지도](04-성능-신뢰성.md)에서 다룬다.

## 7. 이해 복원

1. ISA·CU·명령어 사이클·Major State는 각각 무엇을 정의하거나 수행하는가?
2. 주소·데이터·제어 버스는 무엇을 전달하고, 공유 경로에 왜 병목이 생기는가?
3. Hardwired와 Microprogrammed 제어는 CU의 무엇을 다르게 구현하는가?
4. Pipeline·Superscalar·Multicore는 병렬성을 어떤 수준에서 확보하는가?
5. CPU 성능을 평가할 때 CPI·클록 주파수·명령어 수를 왜 함께 보는가?

**복원 단서:** 명령 체계 → 실행 효율 → 병렬성 수준 → 개선 한계. 이 순서는 기술 도입의 필수 단계가 아니다.
