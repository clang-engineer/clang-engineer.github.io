# I/O와 저장장치 개념지도

이 문서는 [컴퓨터 구조 전체 개념지도](00-전체.md)에서 **I/O와 저장장치** 가지를 선택했을 때, CPU와 외부 장치가 협업하는 방법과 데이터를 지속적으로 저장하는 구조를 함께 파고들기 위한 지도다.

두 가지는 하나의 발전 순서가 아니다. **I/O는 CPU와 장치가 어떻게 협업하는가**, **저장장치는 데이터를 어떻게 지속적으로 저장하고 성능·가용성을 확보하는가**라는 서로 다른 큰 그림이다.

## 먼저 알아둘 용어

```text
Interrupt
= 장치가 CPU의 처리가 필요한 시점에 사건을 알리는 방식

DMA(Direct Memory Access)
= CPU의 반복 개입을 줄이고 장치와 메모리 사이의 데이터 전송을 지원하는 방식

RAID(Redundant Array of Independent Disks)
= 여러 Disk를 묶어 성능·가용성·용량 효율을 조절하는 구조

SSD(Solid State Drive)
= Flash Memory를 사용하는 반도체 기반 저장장치

FTL(Flash Translation Layer)
= SSD의 논리 Block 주소를 Flash의 실제 물리 위치와 연결하는 계층
```

처음에는 `Interrupt = 사건 알림`, `DMA = 데이터 전송의 CPU 개입 축소`, `RAID·SSD = 지속 저장` 정도의 위치부터 잡으면 된다.

## 1. 전체 좌표 — 무엇을 해결하는가?

I/O 처리와 저장장치는 서로 다른 문제 영역이다. 각 기술을 단순 나열하기보다 **제어·전송·접근**과 **매체·보호·추상화·연결**이라는 역할로 구분한다.

```text
I/O와 저장장치
│
├─ [1. I/O 처리 구조] — CPU와 장치가 어떻게 협업하는가?
│  ├─ 제어·상태 확인 → Polling / Interrupt
│  ├─ 데이터 전송 → Programmed I/O / DMA
│  └─ 장치 Register 접근 → Memory-mapped I/O / Isolated I/O
│
└─ [2. 저장장치 구조] — 데이터를 어떻게 저장·관리·공유하는가?
   ├─ 저장매체·내부 동작
   │  ├─ HDD
   │  └─ SSD → FTL (논리·물리 주소 매핑)
   ├─ 데이터 배치·보호
   │  └─ RAID → Striping / Mirroring / Parity
   ├─ 저장공간 구성·추상화
   │  ├─ Partition → 개별 Disk의 영역 분할
   │  └─ LVM → PV(관리 자원) → VG(자원 풀) → LV(논리 볼륨)
   └─ 연결·접근 구조
      ├─ DAS → 직접 연결
      ├─ NAS → 네트워크 파일 공유
      └─ SAN → 네트워크 블록 장치 제공
```

### 저장장치 구성 관계 — 어떻게 조합되는가?

위 그림은 **역할별 분류**이고, 아래는 **실제 시스템에서 조합할 수 있는 한 가지 예**다. 두 그림은 같은 분류를 반복하는 것이 아니다.

```text
Application
    ↓
File System
    ↓
LV (LVM에서 할당한 논리 Block Device)
    ↓
VG / PV (LVM의 자원 풀·물리 자원 매핑)
    ↓
Partition (선택적, RAID 장치 위에 구성 가능)
    ↓
RAID (선택적: 배치·보호)
    ↓
Physical Disk (HDD / SSD)
```

이 예에서는 RAID 장치를 Partition으로 나누어 PV로 등록한다. **Partition 없이 RAID 장치를 바로 PV로 사용할 수도 있고, LVM 없이 Partition에 File System을 직접 만들 수도 있다.** LVM이 RAID 기능을 직접 담당하는 구성도 가능하다. 따라서 그림의 순서를 모든 저장장치가 따라야 하는 필수 계층으로 외우지 않는다.

핵심 구분은 **RAID = 배치·보호 / Partition = 디스크 영역 분할 / LVM = 저장공간 풀링·논리 할당 / File System = 파일·디렉터리 관리**다.

## 2. CPU가 장치를 계속 확인하지 않게 한다: Interrupt

```text
CPU가 장치 상태를 계속 확인
        ↓
Polling 부담
        ↓
장치가 필요한 시점에 알려주면?
        ↓
Interrupt
```

Interrupt는 장치가 CPU의 처리가 필요한 시점에 사건을 알린다. CPU는 장치를 계속 확인하는 대신 다른 일을 하다가 필요한 시점에 처리할 수 있다.

## 3. 대량 전송에서 CPU 개입을 줄인다: DMA

Interrupt로 사건을 알릴 수 있어도 대량 데이터를 CPU가 하나씩 옮기면 여전히 부담이 크다.

```text
대량 데이터 전송
        ↓
CPU가 매번 데이터를 옮기면 비효율
        ↓
DMA
        ↓
장치 ↔ 메모리 데이터 전송
        ↓
완료 시 Interrupt로 CPU에 알림
```

따라서 Interrupt와 DMA는 경쟁 관계가 아니다.

```text
Interrupt
→ CPU에 사건을 알림

DMA
→ 데이터 전송 과정의 CPU 개입 축소
```

## 4. CPU는 장치 Register에 어떻게 접근하는가

CPU가 장치를 제어하려면 장치 Register에 접근할 방법이 필요하다.

```text
I/O 주소 지정
├─ Memory-mapped I/O
│   └─ Memory 주소 공간에 장치 Register를 함께 배치
└─ Isolated I/O
    └─ Memory와 별도 I/O 주소 공간 사용
```

세부 명령어와 주소 계산보다 **Memory 주소 공간을 공유하는가, 별도로 두는가**의 차이를 중심으로 본다.

## 5. 여러 Disk를 묶어 성능과 장애에 대응한다: RAID

지속 저장에서는 단순 용량뿐 아니라 성능·장애·복구를 함께 본다.

```text
여러 Disk 사용
        ↓
어떻게 조합할까?
├─ Striping
│   └─ 데이터를 나눠 병렬 처리 → 성능
├─ Mirroring
│   └─ 같은 데이터를 복제 → 가용성
└─ Parity
    └─ 복구 정보를 저장 → 용량 효율과 복구
```

RAID Level은 이 기본 원리를 조합한 결과다.

```text
RAID 0  → Striping
RAID 1  → Mirroring
RAID 10 → Mirroring + Striping
RAID 5  → Striping + 분산 Parity
RAID 6  → Striping + 이중 분산 Parity
```

세부학습: [RAID - Striping, Mirroring, Parity](RAID-스트라이핑-미러링-패리티.md)

## 6. Flash의 물리 제약을 감춘다: SSD와 FTL

SSD는 Flash Memory를 기반으로 하며, Flash의 실제 물리 위치를 Host에 그대로 노출하지 않고 논리 Block 주소를 제공한다.

```text
Host의 논리 Block 주소
        ↓
FTL
        ↓
Flash의 실제 물리 위치
```

FTL은 논리 주소와 Flash의 물리 위치를 Mapping하고, Flash의 쓰기·삭제 제약을 관리하는 계층이다.

이 관계는 가상 메모리의 주소 변환과 비슷해 보일 수 있지만 목적과 계층이 다르다.

```text
가상 메모리
→ 프로세스 가상주소 ↔ RAM 물리주소

FTL
→ 저장장치 논리 Block ↔ Flash 물리 위치
```

## 7. 서버·스토리지 연결 아키텍처 — DAS·NAS·SAN

이들은 클라우드 전용 개념이 아니라 **서버와 저장장치의 연결·접근 구조**를 구분하는 스토리지 인프라 기술이다. SSD·FTL은 저장장치 **내부 동작**, RAID는 **데이터 배치·보호**, DAS·NAS·SAN은 **서버와 저장장치 사이의 연결·공유 구조**이므로 같은 층위의 기술로 혼동하지 않는다.

```text
Storage 연결·접근
├─ DAS : 서버에 저장장치 직접 연결
├─ NAS : 네트워크를 통해 파일 공유 (NFS / SMB)
└─ SAN : 네트워크를 통해 블록 장치 제공
   ├─ FC-SAN : Fibre Channel 기반
   └─ IP-SAN : iSCSI 등 IP 기반
```

| 구분 | 서버의 접근 방식 | 대표 구성 |
|---|---|---|
| DAS | 직접 연결된 블록 장치 | 서버 내부 디스크·직결 스토리지 |
| NAS | 파일·디렉터리 공유 | Ethernet / NFS·SMB |
| SAN | 원격 블록 장치(LUN 등) | FC-SAN / IP-SAN |

**FC-SAN ↔ IP-SAN**은 SAN의 네트워크 기반을 비교하는 축이다. Fibre Channel은 스토리지 네트워크 기술이고, iSCSI는 TCP/IP 위에서 SCSI 명령을 전달하는 프로토콜이므로 동일 계층의 용어는 아니다. IP-SAN에는 iSCSI 외 다른 블록 스토리지 전송 방식도 활용할 수 있다.

DAS·NAS·SAN은 **어떻게 연결·접근하느냐**의 분류이고, RAID는 **데이터를 여러 디스크에 어떻게 배치·보호하느냐**의 기술이다. 서로 대체 관계가 아니다.

DAS·NAS·SAN은 **연결·접근 방식**이다. 저장공간을 논리적으로 관리하는 가상화와는 다른 분류축이며, 서로 조합할 수 있다.

## 8. 물리 저장공간을 논리적으로 할당한다: 스토리지 가상화와 LVM

스토리지 가상화는 물리 저장장치의 구성·위치를 직접 노출하는 대신 **논리적인 저장공간을 제공하는 추상화**다. 대표적으로 Linux LVM(Logical Volume Manager)은 저장 자원을 풀로 관리하고 필요한 크기의 논리 볼륨을 할당한다.

```text
물리 Disk (또는 RAID로 구성한 논리 Disk)
                ↓
Partition (선택)
                ↓
PV (Physical Volume) : LVM이 관리하는 저장 자원
                ↓
VG (Volume Group)    : 하나 이상의 PV를 묶은 저장공간 풀
                ↓
LV (Logical Volume)  : VG에서 할당한 논리 블록 장치
                ↓
File System → Mount → Application
```

- **PV:** 물리 디스크·파티션·RAID 장치 등 LVM이 사용할 저장 자원을 등록한 단위
- **VG:** PV의 공간을 모아 할당 가능한 자원 풀로 관리하는 단위
- **LV:** VG에서 필요한 용량을 할당받아 실제 파일시스템 등을 올릴 수 있는 논리 장치

예를 들어 PV 100GB·200GB·300GB를 VG로 묶으면 총 600GB 규모의 풀을 구성할 수 있다(실제 사용 가능 용량은 메타데이터 등으로 차이 가능). 여기에서 **LV 300GB와 LV 200GB를 만들고 나머지 공간을 VG에 남겨** 나중에 다른 LV를 만들거나 확장하는 데 사용할 수 있다. LV 하나가 여러 PV에 걸칠 수도 있다.

**왜 VG와 LV를 따로 두는가?** VG는 물리 자원을 **모으는 역할**, LV는 모인 공간을 **논리적으로 나누어 실제 사용하는 역할**이기 때문이다. LV가 하나뿐이더라도 두 계층의 역할은 다르다.

### Partitioning과 LVM은 왜 구분하는가?

Partitioning은 **하나의 Disk 주소 공간을 여러 영역(Partition)으로 나누는 방식**이다. LVM은 하나 이상의 저장 자원을 **VG라는 풀로 모은 뒤 LV로 논리적 공간을 할당**한다. 둘 다 논리적 구성이지만 **나누는 대상과 물리 Disk에 대한 종속성**이 다르다.

```text
[일반적인 Partition 구성]
Disk → Partition A → File System → Mount
     └→ Partition B → File System → Mount

[LVM 구성의 예]
Disk → Partition (선택) → PV ┐
다른 Disk ────────────→ PV ├→ VG → LV → File System → Mount
                              └────→ 다른 LV → File System
```

| 구분 | Partition | LVM의 LV |
|---|---|---|
| 공간을 나누는 기준 | 개별 Disk의 주소 범위 | VG에 모인 저장공간 |
| 여러 Disk의 공간 통합 | Partition 자체로는 불가 | 여러 PV를 하나의 VG로 통합 가능 |
| 크기 변경 | 가능하나 인접 공간·배치 등 제약 | VG 여유 공간을 이용해 상대적으로 유연 |
| File System | Partition에 직접 생성 가능 | LV에 생성 가능 |

예를 들어 **1TB Disk를 300GB·700GB Partition으로 분할**할 수 있다. LVM에서는 **1TB VG에서 LV 300GB·500GB를 할당하고 남은 공간을 이후 확장용으로 보유**할 수 있다. LVM도 실제 저장공간의 한계를 없애는 것은 아니다.

Partition은 LVM의 필수 선행 단계가 아니다. **Disk 전체나 RAID 장치를 PV로 사용할 수도 있고**, Partition을 PV로 사용할 수도 있다. 따라서 `Disk → Partition → PV → VG → LV`는 가능한 구성 중 하나다.

### RAID와 LVM은 같은 '묶기'인가?

둘 다 여러 디스크를 하나처럼 보이게 할 수 있지만 목적이 다르다.

| 구분 | RAID | LVM의 VG·LV |
|---|---|---|
| 핵심 질문 | 데이터를 디스크에 어떻게 배치·보호할까? | 저장공간을 어떻게 모으고 할당할까? |
| 대표 동작 | Striping·Mirroring·Parity | PV 통합·논리 볼륨 생성·확장 |
| 장애 보호 | RAID Level에 따라 제공 | 일반적인 단순 VG·LV 구성만으로 보장되지 않음 |

```text
Disk 여러 개
   ↓
RAID 5 (배치·패리티 보호)  ← 선택적
   ↓
PV → VG (풀) → LV (할당)
```

RAID 없이 디스크를 바로 PV로 사용할 수도 있고, LVM 자체의 RAID 기능을 사용할 수도 있다. 따라서 위 그림은 **대표적인 조합 예시이지 필수 순서가 아니다.** RAID는 백업을 대신하지 않으며, 여러 PV에 걸친 일반 LV는 디스크 장애 시 영향을 받을 수 있다.

스토리지 가상화는 RAID·DAS·NAS·SAN과 경쟁하는 분류가 아니다. **RAID는 배치·보호, DAS·NAS·SAN은 연결·접근, LVM은 저장공간 추상화·할당**이라는 질문으로 구분한다.

## 9. 기억 흐름

```text
CPU 밖의 장치를 사용
│
├─ [장치와 협업]
│   CPU가 계속 확인하는 부담
│       ↓
│   Interrupt
│       ↓ 대량 데이터 전송의 CPU 개입도 줄이고 싶음
│   DMA
│
└─ [데이터를 지속 저장]
    ├─ 연결·공유 구조 → DAS / NAS / SAN
    ├─ 여러 Disk의 성능·장애 문제 → RAID
    ├─ Flash의 물리 제약과 주소 관리 → SSD / FTL
    └─ 공간 분할·추상화 → Partition / PV·VG·LV (LVM)
```

`Interrupt → DMA → RAID → SSD → LVM`를 하나의 발전 순서로 외우지 않는다. **I/O 협업과 지속 저장이라는 두 가지 큰 그림 안에서 각 개념의 위치를 잡는 것이 핵심**이다.
