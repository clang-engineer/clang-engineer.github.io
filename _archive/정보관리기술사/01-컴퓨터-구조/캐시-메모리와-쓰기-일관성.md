# 캐시 메모리와 쓰기·일관성

이 문서는 Cache를 단순히 `CPU와 Memory 사이의 빠른 저장공간`으로 외우는 것이 아니라, **CPU-Memory 속도 차이를 해결하기 위해 Cache가 왜 필요해졌고, Cache를 운영하면서 Mapping·Replacement·Write Policy가 왜 필요하며, 멀티코어에서는 왜 Coherence와 Consistency 문제가 추가로 생기는지** 하나의 흐름으로 이해하기 위한 문서다.

## 1. 캐시 메모리 개요

CPU와 RAM 사이에는 큰 속도 차이가 있다. 캐시는 자주 사용할 가능성이 높은 데이터와 명령을 CPU 가까이에 복사해 두어 이 차이를 줄인다. 다만 빠른 복사본을 유지하려면 **운영 정책**이 필요하고, 여러 코어가 각자 복사본을 보유하면 **캐시 일관성** 문제도 해결해야 한다.

```text
CPU와 RAM의 속도 격차
        ↓
캐시 도입: 지역성을 이용해 접근 지연 감소
        │
        ├─ 캐시 동작: Cache Line · Hit / Miss
        │
        ├─ 캐시 운영 정책
        │    ├─ Mapping: 어디에 배치할까?
        │    ├─ Replacement: 무엇을 내보낼까?
        │    └─ Write Policy: 하위 계층에 언제 기록할까?
        │
        └─ 멀티코어의 복사본 관리
             └─ Cache Coherence: MESI · Snooping · Directory

관련되지만 별도의 질문:
Memory Consistency = 메모리 연산의 관측 순서
```

> **핵심:** 캐시는 성능을 위한 복사본이다. 캐시 운영 정책은 그 복사본을 효율적으로 관리하고, 캐시 일관성 프로토콜은 여러 코어의 복사본이 모순되게 사용되지 않도록 한다. 메모리 일관성 모델은 여러 메모리 연산의 관측 순서를 다룬다.

## 2. 캐시 동작 원리

CPU는 매우 빠르지만 주기억장치는 상대적으로 느리다. CPU가 매번 메모리 응답을 기다리면 실행 성능이 크게 떨어진다. 캐시는 최근 또는 곧 사용할 가능성이 높은 데이터와 명령을 CPU 가까이에 보관해 이 속도 차이를 줄인다.

```text
CPU
 ↓
L1 Cache
 ├─ Hit  → CPU로 즉시 반환
 └─ Miss ↓
        L2 Cache
         ├─ Hit  → CPU로 반환
         └─ Miss ↓
                L3 Cache
                 ├─ Hit  → CPU로 반환
                 └─ Miss ↓
                        Main Memory
```

핵심은 CPU가 매번 RAM까지 가지 않도록, 가까운 캐시 계층에서 가능한 한 빨리 요청을 끝내는 것이다.

### 지역성과 Hit/Miss

캐시가 효과적인 이유는 지역성 때문이다.

- 시간 지역성: 최근 사용한 데이터는 다시 사용할 가능성이 높다.
- 공간 지역성: 사용한 주소 주변의 데이터도 곧 사용할 가능성이 높다.
- 순차 지역성: 명령은 대체로 인접한 주소 순서로 실행된다.

CPU가 주소를 요청하면 캐시의 Tag를 비교한다. 데이터가 있으면 Hit, 없으면 Miss다. Miss가 발생하면 하위 메모리에서 Cache Line 단위로 가져온다.

```text
CPU 메모리 접근
      ↓
Cache Hit?
 ├─ Yes → 캐시 데이터 사용
 └─ No  → 하위 메모리 접근
            ↓
        Cache Line 단위 적재
            ↓
        캐시 데이터 사용
```

평균 접근시간은 Hit 시간뿐 아니라 Miss 비율과 Miss 처리 비용의 영향을 받는다. 캐시가 커져도 Hit 시간이 길어지거나 계층 관리 비용이 증가할 수 있으므로 무조건 큰 캐시가 좋은 것은 아니다.

여기서부터 Cache를 실제로 운영하기 위한 세 가지 질문이 자연스럽게 나온다.

```text
새 데이터를 Cache에 가져왔다.
        ↓
어디에 넣을까?
→ Mapping
        ↓
그 위치가 이미 차 있다면?
→ Replacement
        ↓
CPU가 값을 수정했다면?
→ Write Policy
```

## 3. 캐시 운영 정책

캐시 운영에는 **배치(Mapping), 교체(Replacement), 쓰기(Write Policy)**라는 세 가지 독립적인 설계 질문이 있다. 다음 절은 실행 순서가 아니라 정책별 분류다.

### 3.1 캐시 매핑 방식

매핑(Mapping)은 **메모리 블록의 주소를 기준으로 캐시의 저장 후보 위치를 정하는 규칙**이다. RAM의 주소를 변경하거나 새 주소를 부여하는 것이 아니다.

#### 이름으로 이해하는 세 방식

```text
Memory Block B4를 캐시에 넣는다면?

Direct Mapping          → 지정된 Line 한 곳
Fully Associative       → 전체 Line 중 어디든
2-way Set Associative   → 지정된 Set 안의 두 Way 중 하나
```

| 이름 | 어원·의미 | 주소와 캐시 위치의 관계 |
|---|---|---|
| Direct Mapping | Direct = 직접 | 주소로 저장할 Line 하나가 바로 결정됨 |
| Fully Associative | Fully = 전체, Associative = 연관 검색 | 전체 Line을 후보로 Tag를 비교해 찾음 |
| Set Associative | Set = 집합, Associative = 연관 검색 | 주소로 Set을 정하고 그 안의 Way에서 Tag를 비교함 |

여기서 **Associative(연관)**는 '아무 주소나 서로 연결한다'는 뜻이 아니라, 저장 위치가 하나로 고정되지 않아 **Tag 비교로 일치하는 블록을 찾는 방식**과 관련된 이름이다. Direct도 Tag를 확인하지만 후보 위치는 하나뿐이다.

**암기:** Direct = 한 자리 / Fully = 모든 자리 / Set = 지정 구역 안의 여러 자리. Direct Mapping은 구조적으로 **1-way Set Associative**로 볼 수 있다.

주기억장치의 블록을 캐시의 어느 위치에 저장할지를 결정하는 방식이다.

#### Direct Mapping

각 메모리 블록이 들어갈 Cache Line이 하나로 고정된다.

```text
Cache Line = Memory Block mod Cache Line 수
```

장점은 단순하고 빠르지만, 서로 다른 블록이 같은 Line을 계속 차지하려 하면 다른 Line이 비어 있어도 Conflict Miss가 발생할 수 있다.

#### Fully Associative Mapping

메모리 블록을 캐시의 어느 Line에든 저장할 수 있다. 충돌은 줄지만 요청한 블록이 어디 있는지 여러 Tag를 동시에 비교해야 하므로 하드웨어가 복잡해진다.

#### Set Associative Mapping

Direct와 Fully Associative의 절충이다. 메모리 블록이 들어갈 Set은 정해지지만, 해당 Set 내부의 여러 Way 중 하나에 저장할 수 있다.

```text
Memory Block
   ↓
Mapping 방식
   ├─ Direct Mapping
   │   └─ 특정 Line 1곳
   │      장점: 단순·빠름
   │      단점: Conflict Miss 증가
   │
   ├─ Fully Associative Mapping
   │   └─ Cache 어디든 저장 가능
   │      장점: 충돌 최소
   │      단점: 비교 회로 복잡
   │
   └─ Set Associative Mapping
       └─ 특정 Set 내부 여러 Way
          성능과 복잡도의 절충
```

실제 CPU 캐시는 Set Associative가 일반적으로 사용된다.

#### 예제: 빈 공간이 있어도 왜 Cache Miss가 날까?

**핵심 질문:** 캐시에 총 4개 Line이 있는데, 왜 Block 0과 Block 4를 번갈아 읽으면 매번 Miss가 발생할 수 있을까?

여기서 숫자 0과 4는 **RAM의 바이트 주소가 아니라 메모리 블록 번호**다. 두 캐시는 총 4개 Line, 동일한 Line 크기, 초기 빈 상태라고 가정한다.

**Direct Mapping: 지정석 하나**

```text
저장 위치 = Block 번호 mod 4

Block 0 → Line 0
Block 4 → Line 0

접근        Line 0       나머지 Line      결과
Block 0     [B0]         [빈칸 3개]       Miss
Block 4     [B4]         [빈칸 3개]       Miss (B0 축출)
Block 0     [B0]         [빈칸 3개]       Miss (B4 축출)
Block 4     [B4]         [빈칸 3개]       Miss (B0 축출)
```

**다른 세 칸이 비어 있어도** 두 블록 모두 Line 0에만 들어갈 수 있어 서로를 계속 밀어낸다. 이것이 **Conflict Miss(배치 위치 충돌로 발생하는 Miss)**다.

**2-way Set Associative: 지정된 구역 안에 두 자리**

```text
총 4 Line = 2 Set × 2 Way
Set 번호 = Block 번호 mod 2

Block 0 → Set 0
Block 4 → Set 0

접근열       Set 0          결과
Block 0      [B0][-]        Miss
Block 4      [B0][B4]       Miss
Block 0      [B0][B4]       Hit
Block 4      [B0][B4]       Hit
```

두 블록의 **Set은 같지만 Way가 두 개**라 함께 보관할 수 있다. 따라서 다시 읽을 때 Hit가 발생한다.

**결론:** 같은 총 캐시 용량에서도 **저장 후보 위치의 수(Associativity)**가 다르면 Conflict Miss가 달라진다. 다만 연관도가 높을수록 Tag 비교 회로와 관리 비용이 늘어날 수 있으므로 무조건 더 빠른 것은 아니다.

### 3.2 교체 정책

Set Associative나 Fully Associative에서 후보 위치가 모두 차 있으면 어떤 Cache Line을 제거할지 결정해야 한다.

- LRU(Least Recently Used): 가장 오랫동안 사용되지 않은 Line 제거
- FIFO: 가장 먼저 들어온 Line 제거
- Random: 임의의 Line 제거

LRU는 시간 지역성을 활용한다는 점에서 직관적이지만, Way 수가 증가할수록 정확한 사용 순서를 추적하는 비용이 커져 실제 하드웨어에서는 Pseudo-LRU와 같은 근사 방식도 사용한다.

```text
새 Cache Line 적재 필요
        ↓
빈 Way 존재?
 ├─ Yes → 빈 Way에 저장
 └─ No  → 교체 대상 선택
          ├─ LRU
          ├─ FIFO
          └─ Random / Pseudo-LRU
```

Direct Mapping은 들어갈 위치가 하나뿐이므로 별도의 교체 후보 선택이 필요하지 않는다.

### 3.3 쓰기 정책

쓰기 정책은 **서로 다른 두 질문**으로 나누어 이해한다.

```text
CPU가 주소 X에 쓰기 요청
        ↓
X가 캐시에 있는가?
   ├─ Hit  → 하위 메모리에 언제 반영할까?
   │          Write-through / Write-back
   │
   └─ Miss → X를 캐시에 새로 적재할까?
              Write-allocate / No-write-allocate
              (적재 후 쓰기에는 쓰기 반영 정책도 적용)
```

| 정책 축 | 판단 기준 | 대표 방식 |
|---|---|---|
| 쓰기 반영 정책 | 캐시에 쓴 내용을 하위 계층에 언제 전달하는가? | Write-through / Write-back |
| Write Miss 할당 정책 | 쓰려는 블록이 캐시에 없을 때 적재하는가? | Write-allocate / No-write-allocate |

두 축은 **상호 배타적인 네 선택지**가 아니라 조합 가능한 정책이다. Write-through/Write-back은 주로 캐시 적중 시 또는 할당 후의 쓰기 반영을 설명하고, Allocate 여부는 Write Miss에서의 배치 결정을 설명한다.

#### 쓰기 반영: Write-through

캐시에 쓸 때 하위 메모리에도 쓰기를 전달한다. 쓰기 버퍼가 있으면 CPU가 기다리지 않고 진행할 수 있으므로 물리적으로 같은 순간에 갱신된다는 뜻은 아니다.

- 장점: 하위 메모리가 항상 최신 상태에 가깝고 일관성 관리가 단순하다.
- 단점: 쓰기 트래픽과 지연이 증가한다.
- 보완: Write Buffer로 CPU의 대기를 줄인다.

#### 쓰기 반영: Write-back

먼저 캐시에 기록하고 하위 메모리 반영을 미룬다. 수정된 Line을 교체할 때는 반드시 반영해야 하며, 그 외에도 일관성 요청이나 캐시 계층의 동작으로 더 일찍 반영될 수 있다.

- 장점: 반복 쓰기를 합쳐 메모리 트래픽을 줄인다.
- 단점: Dirty Line 관리가 필요하고 장애 시 최신 데이터가 캐시에만 남을 수 있다.

```text
CPU Write
   ↓
Write Policy
   ├─ Write-through
   │    → Cache 갱신
   │    → Memory 즉시 갱신
   │
   └─ Write-back
        → Cache만 갱신
        → Dirty Bit = 1
        → Line 교체 시 Memory에 Write-back
```

Write-back에서는 Dirty Bit가 "이 Line의 값이 하위 메모리와 다르다"는 것을 표시한다. Dirty Line을 교체할 때는 먼저 하위 메모리에 변경 내용을 기록해야 한다.

#### 예제로 이해하는 Write-back: RAM과 캐시는 항상 같아야 할까?

**아니다.** Write-back에서는 캐시가 수정된 최신 값을 보유하고 RAM에는 이전 값이 남아 있어도 정상이다. 핵심은 *모든 복사본의 비트가 항상 동일한 것*이 아니라 *최신 데이터를 잃지 않고 올바르게 제공하는 것*이다.

```text
단계                Cache              RAM
처음 읽기           X=10 (Clean)       X=10
CPU가 X=20 쓰기     X=20 (Dirty)       X=10
CPU가 X=30 쓰기     X=30 (Dirty)       X=10
Dirty Line 교체     X를 내보냄         X=30
```

- **Clean**: 캐시 데이터가 하위 계층과 일치해 수정분을 따로 기록할 필요가 없다.
- **Dirty**: 캐시가 수정한 내용이 하위 계층에 아직 반영되지 않았다.
- **Eviction(축출)**: Dirty Line을 내보내기 전에는 수정분을 하위 계층에 전달해야 한다. 다단계 캐시에서는 바로 RAM이 아니라 L2/L3에 먼저 기록될 수도 있다.

따라서 Write-back은 'RAM에 쓰지 않는 방식'이 아니라 **RAM으로 향하는 쓰기를 지연·통합하는 방식**이다.

#### Write Miss 할당: Write-allocate와 No-write-allocate

**Write Miss**는 CPU가 쓰려는 주소의 블록이 캐시에 없는 경우다. 여기서 Allocate는 *메모리 주소를 새로 만드는 것*이 아니라 **캐시 라인에 자리를 마련하는 것**을 뜻한다.

- **Write-allocate (Fetch-on-write)**: 하위 계층에서 해당 블록을 캐시에 적재한 다음 캐시의 값을 수정한다. Write-back과 자주 조합된다.
- **No-write-allocate (Write-around)**: 이 Miss를 처리하면서 캐시에 새 라인을 할당하지 않고 쓰기를 하위 계층에 전달한다. Write-through와 자주 조합된다.

```text
캐시에 X가 없는데 CPU가 X=20 쓰기 요청

Write-allocate            No-write-allocate
  X의 Line 적재             캐시 적재 생략
       ↓                         ↓
  캐시에 X=20 기록           하위 계층에 쓰기 전달
```

예를 들어 **Write-back + Write-allocate**는 새 블록을 캐시에 올려 반복 수정을 모은 뒤 나중에 하위 계층에 기록한다. **Write-through + No-write-allocate**는 캐시에 없는 블록에 대한 쓰기를 캐시 적재 없이 아래로 전달한다. 이는 흔한 조합이지 반드시 고정된 조합은 아니다.

## 4. 캐시 일관성

### 멀티코어에서 발생하는 문제

지금까지의 Mapping, Replacement, Write Policy는 주로 **하나의 Cache를 어떻게 효율적으로 관리할 것인가**에 대한 문제였다.

하지만 CPU가 멀티코어가 되고 각 Core가 자신의 Cache를 가지면 새로운 문제가 생긴다.

```text
                Main Memory
                  A = 10
                 /      \
                /        \
        Core 1 Cache    Core 2 Cache
           A = 10          A = 10
```

두 Cache가 같은 Memory 주소 `A`의 복제본을 가지고 있는 상태에서 Core 1이 값을 변경하면 다음과 같은 상황이 가능하다.

```text
Core 1이 A = 20으로 변경
        ↓
Core 1 Cache : A = 20
Core 2 Cache : A = 10
        ↓
같은 Memory 주소의 복제본이 서로 다른 값
```

즉 Cache는 CPU-Memory 속도 차이를 해결했지만, **멀티코어에서는 동일 데이터가 여러 Cache에 복제되면서 새로운 일관성 문제가 생긴다.**

```text
CPU-Memory 속도 차이
        ↓
Cache로 해결
        ↓
멀티코어 + Core별 Cache
        ↓
같은 데이터의 복제본 증가
        ↓
복제본이 서로 다른 값을 가질 수 있음
        ↓
Cache Coherence 필요
```

---

### Cache Coherence의 역할

여러 코어의 캐시에 같은 메모리 값이 복제되면 한 코어의 변경을 다른 코어가 모를 수 있다.

```text
RAM       : A = 10
Core 1    : A = 20
Core 2    : A = 10
```

서로 다른 값이 캐시에 물리적으로 남아 있다는 사실만으로 Coherence 위반이 되는 것은 아니다. Core 1의 쓰기 과정에서 Core 2의 오래된 복제본이 Invalid 처리되면 그 값은 유효한 읽기 결과로 사용되지 않는다. Cache Coherence는 같은 주소에 대한 쓰기 권한·무효화·관찰 가능한 값을 조정한다.

#### 다른 코어에는 무효화할까, 갱신할까?

```text
초기: Core 1 X=10, Core 2 X=10

Core 1이 X=20으로 수정
  ├─ Write-invalidate: Core 2의 X를 Invalid 처리
  └─ Write-update    : Core 2에도 X=20을 전달
```

MESI는 대표적인 **Write-invalidate 기반** 프로토콜이다. 다른 코어가 당장 읽지 않는다면 수정할 때마다 새 값을 보내지 않아도 되어 통신량을 줄일 수 있다.

이 구분은 Write-through/Write-back과 다르다. 전자는 **다른 캐시의 복사본을 어떻게 처리할지**, 후자는 **하위 메모리에 언제 쓸지**를 결정한다.

#### MESI Protocol

MESI는 Cache Line을 네 가지 상태로 관리한다.

- M(Modified): 내가 가진 값이 최신이고 하위 메모리와 다르다.
- E(Exclusive): 하위 메모리와 값이 같고 이 Line을 가진 캐시는 나뿐이다.
- S(Shared): 다른 캐시에도 같은 값의 복제본이 존재한다.
- I(Invalid): 더 이상 유효하지 않아 사용할 수 없는 Line이다.

상태 변화는 복잡하지만 핵심 흐름만 보면 다음과 같다.

```text
I (Invalid)
├─ Read, 다른 캐시에 없음 → E
└─ Read, 다른 캐시에도 있음 → S

E (Exclusive)
├─ Local Write → M
└─ 다른 Core가 Read → S

S (Shared)
├─ Local Write
│   → 다른 복제본 Invalidate
│   → M
└─ 다른 Core가 Write → I

M (Modified)
├─ 다른 Core가 Read
│   → 최신값 제공
│   → S
├─ 다른 Core가 Write → I
└─ Eviction
    → Memory에 Write-back
    → I
```

예를 들어 두 코어가 같은 Line을 Shared 상태로 가지고 있을 때 한 코어가 값을 변경하려면 다른 코어의 복제본을 Invalid로 만들고 자신이 쓰기 권한을 얻는다.

```text
Memory A = 10
   ↓
Core 1 Cache : A=10, Shared
Core 2 Cache : A=10, Shared

Core 1이 A=20 Write 요청
   ↓
Core 2의 A Line Invalidate
   ↓
Core 2 : Invalid
Core 1 : A=20, Modified
```

이렇게 다른 캐시에 남아 있는 오래된 복제본을 사용하지 못하게 만들어 일관성을 유지한다.

#### 캐시끼리 어떻게 조정할까?

- **Snooping**: 캐시가 일관성 관련 요청을 감시하고 자신의 상태에 맞게 응답한다.
- **Directory**: 캐시 라인을 어느 캐시가 보유하는지 추적하여 필요한 대상에 요청을 보낸다.

둘은 통신·추적 구조에 대한 구분이며, MESI는 캐시 라인의 상태와 전이 규칙에 대한 구분이다. 실제 구현은 두 접근을 조합할 수 있다. 또한 MESI는 변수 단위가 아니라 **캐시 라인 단위**로 동작한다.

## 5. 메모리 일관성과의 관계

한국어로는 둘 다 일관성이라고 번역되기 쉬워 헷갈린다. 하지만 질문의 초점이 다르다.

```text
Coherence
= 같은 주소의 복제본들이 서로 모순되지 않게 하는 문제

Consistency
= 여러 메모리 연산의 순서가 다른 코어에 어떻게 보이는가의 문제
```

예를 들어 Core 1이 `A=20`을 기록한 후 Core 2가 무효화되지 않은 오래된 `A=10`을 계속 유효한 값으로 사용한다면 Coherence 문제가 된다. 단순히 복제본의 물리적 비트가 다르다는 사실만으로 위반이라고 단정하지 않는다.

반면 `A=1`을 먼저 쓰고 `B=1`을 나중에 썼는데, 다른 코어가 그 순서를 어떻게 관찰하는지는 Consistency 문제다. 즉 **Coherence는 같은 주소의 값 문제**, **Consistency는 여러 연산의 관찰 순서 문제**에 가깝다.

```text
Cache Coherence
"A라는 같은 주소를 여러 Core가 볼 때
 서로 모순된 값을 사용하지 않는가?"

Memory Consistency
"A, B 등 여러 Memory 연산이
 다른 Core에게 어떤 순서로 보이는가?"
```

두 개념은 관련 있지만 동일하지 않다. MESI 같은 Cache Coherence Protocol은 주로 같은 주소의 복제본 문제를 해결하고, Memory Consistency Model은 여러 메모리 연산의 순서가 어떻게 보장되는지를 정의한다.

### 서로 다른 주소의 관측 순서

```text
초기: X=0, Y=0

Core 1 (작성 순서)       Core 2 (읽기 순서)
X=1                      r1=Y
Y=1                      r2=X
```

'Core 2가 Y=1을 봤다면 X도 반드시 1일까?'는 MESI만으로 답할 수 없다. 허용되는 결과는 **언어와 하드웨어의 메모리 모델 및 동기화 방식**에 달려 있다. 일부 약한 메모리 모델에서는 필요한 동기화 없이 Y=1, X=0을 관측할 수 있다. 이는 같은 주소의 캐시 복사본이 충돌한다는 뜻이 아니라 **서로 다른 연산의 관측 순서** 문제다.

필요한 순서를 보장하려면 언어가 제공하는 원자 연산과 Release/Acquire 동기화, 또는 적절한 Memory Barrier(Fence)를 사용한다. 단순히 MESI가 있다고 해서 모든 연산이 작성한 순서대로 보이는 것은 아니다.

---

### 세 가지 질문으로 구분하기

| 질문 | 해당 개념 |
|---|---|
| 수정한 값을 하위 메모리에 언제 반영할까? | Write-through / Write-back |
| 다른 코어의 오래된 복사본을 어떻게 막을까? | Cache Coherence / MESI |
| X와 Y에 대한 연산이 어떤 순서로 보일까? | Memory Consistency / 동기화 |

### 기술사 답안 포인트

캐시는 성능 장치이지만 용량·계층 증가가 지연과 복잡도를 만든다. 답안에서는 지역성, Mapping·교체·쓰기 정책, Hit/Miss 지표, 멀티코어 일관성을 하나의 흐름으로 연결한다.

특히 단순 용어 나열보다 다음 Trade-off를 보여주는 것이 좋다.

- Direct Mapping: 빠르고 단순하지만 Conflict Miss 증가
- Associativity 증가: Conflict Miss 감소, 비교 회로 복잡도 증가
- Write-through: 일관성 관리 용이, 메모리 트래픽 증가
- Write-back: 성능 향상, Dirty Line 및 일관성 관리 복잡도 증가
- 멀티코어 Cache: 접근 성능 향상, Cache Coherence 문제 발생
