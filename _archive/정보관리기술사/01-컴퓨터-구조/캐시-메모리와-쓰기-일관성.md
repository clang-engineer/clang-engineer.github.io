# 캐시 메모리와 쓰기·일관성

이 문서는 Cache를 단순히 `CPU와 Memory 사이의 빠른 저장공간`으로 외우는 것이 아니라, **CPU-Memory 속도 차이를 해결하기 위해 Cache가 왜 필요해졌고, Cache를 운영하면서 Mapping·Replacement·Write Policy가 왜 필요하며, 멀티코어에서는 왜 Coherence와 Consistency 문제가 추가로 생기는지** 하나의 흐름으로 이해하기 위한 문서다.

## 1. 가장 먼저 잡을 전체 흐름

```text
CPU와 Memory 속도 차이
        ↓
Cache 도입
        ↓
지역성 활용
        ↓
Cache Line / Hit / Miss
        ↓
Cache를 실제로 운영하려면?
        ↓
어디에 넣을까?
→ Mapping
        ↓
자리가 없으면 누구를 버릴까?
→ Replacement
        ↓
CPU가 값을 수정하면 언제 Memory에 반영할까?
→ Write Policy
        ↓
여기까지는 주로 한 Cache의 관리 문제
        ↓
멀티코어
→ Core마다 Cache 존재
        ↓
같은 Memory 값을 여러 Cache가 복제
        ↓
한 Core가 값을 바꾸면 다른 Cache는?
        ↓
Cache Coherence
→ MESI
        ↓
같은 주소의 값뿐 아니라
여러 Memory 연산의 관찰 순서는?
        ↓
Memory Consistency
```

> **Cache 도입으로 CPU-Memory 속도 차이를 줄였지만, Cache를 어디에 배치하고 교체하고 쓰기를 반영할지 결정해야 하며, 멀티코어에서는 복제된 Cache 때문에 Coherence라는 새로운 문제가 생긴다.**

---

## 2. 왜 필요한가

CPU는 매우 빠르지만 주기억장치는 상대적으로 느리다. CPU가 매번 메모리 응답을 기다리면 실행 성능이 크게 떨어진다. 캐시는 최근 또는 곧 사용할 가능성이 높은 데이터와 명령을 CPU 가까이에 보관해 이 속도 차이를 줄인다.

```text
CPU
 ↓
L1 Cache
 ├─ Hit  → CPU로 즉시 반환
 └─ Miss ↓
        L2 Cache
         ├─ Hit  → CPU로 반환
         └─ Miss ↓
                L3 Cache
                 ├─ Hit  → CPU로 반환
                 └─ Miss ↓
                        Main Memory
```

핵심은 CPU가 매번 RAM까지 가지 않도록, 가까운 캐시 계층에서 가능한 한 빨리 요청을 끝내는 것이다.

## 3. 핵심 원리

캐시가 효과적인 이유는 지역성 때문이다.

- 시간 지역성: 최근 사용한 데이터는 다시 사용할 가능성이 높다.
- 공간 지역성: 사용한 주소 주변의 데이터도 곧 사용할 가능성이 높다.
- 순차 지역성: 명령은 대체로 인접한 주소 순서로 실행된다.

CPU가 주소를 요청하면 캐시의 Tag를 비교한다. 데이터가 있으면 Hit, 없으면 Miss다. Miss가 발생하면 하위 메모리에서 Cache Line 단위로 가져온다.

```text
CPU 메모리 접근
      ↓
Cache Hit?
 ├─ Yes → 캐시 데이터 사용
 └─ No  → 하위 메모리 접근
            ↓
        Cache Line 단위 적재
            ↓
        캐시 데이터 사용
```

평균 접근시간은 Hit 시간뿐 아니라 Miss 비율과 Miss 처리 비용의 영향을 받는다. 캐시가 커져도 Hit 시간이 길어지거나 계층 관리 비용이 증가할 수 있으므로 무조건 큰 캐시가 좋은 것은 아니다.

여기서부터 Cache를 실제로 운영하기 위한 세 가지 질문이 자연스럽게 나온다.

```text
새 데이터를 Cache에 가져왔다.
        ↓
어디에 넣을까?
→ Mapping
        ↓
그 위치가 이미 차 있다면?
→ Replacement
        ↓
CPU가 값을 수정했다면?
→ Write Policy
```

## 4. 캐시 매핑 방식

주기억장치의 블록을 캐시의 어느 위치에 저장할지를 결정하는 방식이다.

### Direct Mapping

각 메모리 블록이 들어갈 Cache Line이 하나로 고정된다.

```text
Cache Line = Memory Block mod Cache Line 수
```

장점은 단순하고 빠르지만, 서로 다른 블록이 같은 Line을 계속 차지하려 하면 다른 Line이 비어 있어도 Conflict Miss가 발생할 수 있다.

### Fully Associative Mapping

메모리 블록을 캐시의 어느 Line에든 저장할 수 있다. 충돌은 줄지만 요청한 블록이 어디 있는지 여러 Tag를 동시에 비교해야 하므로 하드웨어가 복잡해진다.

### Set Associative Mapping

Direct와 Fully Associative의 절충이다. 메모리 블록이 들어갈 Set은 정해지지만, 해당 Set 내부의 여러 Way 중 하나에 저장할 수 있다.

```text
Memory Block
   ↓
Mapping 방식
   ├─ Direct Mapping
   │   └─ 특정 Line 1곳
   │      장점: 단순·빠름
   │      단점: Conflict Miss 증가
   │
   ├─ Fully Associative Mapping
   │   └─ Cache 어디든 저장 가능
   │      장점: 충돌 최소
   │      단점: 비교 회로 복잡
   │
   └─ Set Associative Mapping
       └─ 특정 Set 내부 여러 Way
          성능과 복잡도의 절충
```

실제 CPU 캐시는 Set Associative가 일반적으로 사용된다.

## 5. 교체 정책

Set Associative나 Fully Associative에서 후보 위치가 모두 차 있으면 어떤 Cache Line을 제거할지 결정해야 한다.

- LRU(Least Recently Used): 가장 오랫동안 사용되지 않은 Line 제거
- FIFO: 가장 먼저 들어온 Line 제거
- Random: 임의의 Line 제거

LRU는 시간 지역성을 활용한다는 점에서 직관적이지만, Way 수가 증가할수록 정확한 사용 순서를 추적하는 비용이 커져 실제 하드웨어에서는 Pseudo-LRU와 같은 근사 방식도 사용한다.

```text
새 Cache Line 적재 필요
        ↓
빈 Way 존재?
 ├─ Yes → 빈 Way에 저장
 └─ No  → 교체 대상 선택
          ├─ LRU
          ├─ FIFO
          └─ Random / Pseudo-LRU
```

Direct Mapping은 들어갈 위치가 하나뿐이므로 별도의 교체 후보 선택이 필요하지 않는다.

## 6. 쓰기 정책

### Write-through

캐시와 하위 메모리에 동시에 기록한다.

- 장점: 하위 메모리가 항상 최신 상태에 가깝고 일관성 관리가 단순하다.
- 단점: 쓰기 트래픽과 지연이 증가한다.
- 보완: Write Buffer로 CPU의 대기를 줄인다.

### Write-back

먼저 캐시에만 기록하고 변경된 Line을 교체할 때 하위 메모리에 반영한다.

- 장점: 반복 쓰기를 합쳐 메모리 트래픽을 줄인다.
- 단점: Dirty Line 관리가 필요하고 장애 시 최신 데이터가 캐시에만 남을 수 있다.

```text
CPU Write
   ↓
Write Policy
   ├─ Write-through
   │    → Cache 갱신
   │    → Memory 즉시 갱신
   │
   └─ Write-back
        → Cache만 갱신
        → Dirty Bit = 1
        → Line 교체 시 Memory에 Write-back
```

Write-back에서는 Dirty Bit가 "이 Line의 값이 하위 메모리와 다르다"는 것을 표시한다. Dirty Line을 교체할 때는 먼저 하위 메모리에 변경 내용을 기록해야 한다.

### Write-allocate와 No-write-allocate

Write Miss가 발생했을 때 Line을 캐시로 가져올지 결정한다.

- Write-allocate: 가져온 뒤 캐시에 기록한다. Write-back과 자주 조합된다.
- No-write-allocate: 캐시에 넣지 않고 하위 메모리에 직접 기록한다. Write-through와 자주 조합된다.

## 7. 멀티코어가 되면서 새로운 문제가 생긴다

지금까지의 Mapping, Replacement, Write Policy는 주로 **하나의 Cache를 어떻게 효율적으로 관리할 것인가**에 대한 문제였다.

하지만 CPU가 멀티코어가 되고 각 Core가 자신의 Cache를 가지면 새로운 문제가 생긴다.

```text
                Main Memory
                  A = 10
                 /      \
                /        \
        Core 1 Cache    Core 2 Cache
           A = 10          A = 10
```

두 Cache가 같은 Memory 주소 `A`의 복제본을 가지고 있는 상태에서 Core 1이 값을 변경하면 다음과 같은 상황이 가능하다.

```text
Core 1이 A = 20으로 변경
        ↓
Core 1 Cache : A = 20
Core 2 Cache : A = 10
        ↓
같은 Memory 주소의 복제본이 서로 다른 값
```

즉 Cache는 CPU-Memory 속도 차이를 해결했지만, **멀티코어에서는 동일 데이터가 여러 Cache에 복제되면서 새로운 일관성 문제가 생긴다.**

```text
CPU-Memory 속도 차이
        ↓
Cache로 해결
        ↓
멀티코어 + Core별 Cache
        ↓
같은 데이터의 복제본 증가
        ↓
복제본이 서로 다른 값을 가질 수 있음
        ↓
Cache Coherence 필요
```

## 8. Cache Coherence

여러 코어의 캐시에 같은 메모리 값이 복제되면 한 코어의 변경을 다른 코어가 모를 수 있다.

```text
RAM       : A = 10
Core 1    : A = 20
Core 2    : A = 10
```

이 상태에서 Core 2가 자신의 캐시만 보고 A를 읽으면 오래된 값을 사용할 수 있다. Cache Coherence는 동일 주소의 복제본이 모순되지 않도록 조정한다.

### MESI Protocol

MESI는 Cache Line을 네 가지 상태로 관리한다.

- M(Modified): 내가 가진 값이 최신이고 하위 메모리와 다르다.
- E(Exclusive): 하위 메모리와 값이 같고 이 Line을 가진 캐시는 나뿐이다.
- S(Shared): 다른 캐시에도 같은 값의 복제본이 존재한다.
- I(Invalid): 더 이상 유효하지 않아 사용할 수 없는 Line이다.

상태 변화는 복잡하지만 핵심 흐름만 보면 다음과 같다.

```text
I (Invalid)
├─ Read, 다른 캐시에 없음 → E
└─ Read, 다른 캐시에도 있음 → S

E (Exclusive)
├─ Local Write → M
└─ 다른 Core가 Read → S

S (Shared)
├─ Local Write
│   → 다른 복제본 Invalidate
│   → M
└─ 다른 Core가 Write → I

M (Modified)
├─ 다른 Core가 Read
│   → 최신값 제공
│   → S
├─ 다른 Core가 Write → I
└─ Eviction
    → Memory에 Write-back
    → I
```

예를 들어 두 코어가 같은 Line을 Shared 상태로 가지고 있을 때 한 코어가 값을 변경하려면 다른 코어의 복제본을 Invalid로 만들고 자신이 쓰기 권한을 얻는다.

```text
Memory A = 10
   ↓
Core 1 Cache : A=10, Shared
Core 2 Cache : A=10, Shared

Core 1이 A=20 Write 요청
   ↓
Core 2의 A Line Invalidate
   ↓
Core 2 : Invalid
Core 1 : A=20, Modified
```

이렇게 다른 캐시에 남아 있는 오래된 복제본을 사용하지 못하게 만들어 일관성을 유지한다.

## 9. Coherence와 Consistency 구분

한국어로는 둘 다 일관성이라고 번역되기 쉬워 헷갈린다. 하지만 질문의 초점이 다르다.

```text
Coherence
= 같은 주소의 복제본들이 서로 모순되지 않게 하는 문제

Consistency
= 여러 메모리 연산의 순서가 다른 코어에 어떻게 보이는가의 문제
```

예를 들어 `A`라는 같은 주소가 Core 1 Cache에는 `20`, Core 2 Cache에는 `10`으로 보이면 Coherence 문제다. 같은 주소의 복제본들이 서로 다른 값을 보고 있기 때문이다.

반면 `A=1`을 먼저 쓰고 `B=1`을 나중에 썼는데, 다른 코어가 그 순서를 어떻게 관찰하는지는 Consistency 문제다. 즉 **Coherence는 같은 주소의 값 문제**, **Consistency는 여러 연산의 관찰 순서 문제**에 가깝다.

```text
Cache Coherence
"A라는 같은 주소를 여러 Core가 볼 때
 서로 모순된 값을 사용하지 않는가?"

Memory Consistency
"A, B 등 여러 Memory 연산이
 다른 Core에게 어떤 순서로 보이는가?"
```

두 개념은 관련 있지만 동일하지 않다. MESI 같은 Cache Coherence Protocol은 주로 같은 주소의 복제본 문제를 해결하고, Memory Consistency Model은 여러 메모리 연산의 순서가 어떻게 보장되는지를 정의한다.

## 10. 연결해서 기억할 흐름

```text
CPU와 Memory 속도 차이
        ↓
Cache 도입
        ↓
지역성 활용
        ↓
Cache Line / Hit / Miss
        ↓
어디에 넣을까?
→ Mapping
        ↓
자리가 없으면?
→ Replacement
        ↓
CPU가 수정하면?
→ Write Policy
        ↓
멀티코어 + Core별 Cache
        ↓
같은 데이터가 여러 Cache에 복제
        ↓
한 Core가 값을 바꾸면?
→ Cache Coherence
        ↓
MESI
        ↓
같은 주소가 아니라
여러 연산의 관찰 순서까지 보면?
→ Memory Consistency
```

즉 다음 질문 순서로 기억하면 된다.

1. 왜 캐시가 필요한가? → CPU와 메모리의 속도 차이
2. 왜 작은 캐시가 효과적인가? → 지역성
3. 어디에 저장하는가? → Mapping
4. 자리가 없으면 누구를 버리는가? → Replacement
5. 수정된 값을 언제 메모리에 반영하는가? → Write Policy
6. 왜 멀티코어에서 문제가 추가되는가? → 같은 데이터가 여러 Core Cache에 복제
7. 여러 코어의 같은 주소 값이 달라지면 어떻게 하는가? → Cache Coherence / MESI
8. 여러 메모리 연산의 순서가 어떻게 보이는가? → Memory Consistency

## 11. 기술사 답안 포인트

캐시는 성능 장치이지만 용량·계층 증가가 지연과 복잡도를 만든다. 답안에서는 지역성, Mapping·교체·쓰기 정책, Hit/Miss 지표, 멀티코어 일관성을 하나의 흐름으로 연결한다.

특히 단순 용어 나열보다 다음 Trade-off를 보여주는 것이 좋다.

- Direct Mapping: 빠르고 단순하지만 Conflict Miss 증가
- Associativity 증가: Conflict Miss 감소, 비교 회로 복잡도 증가
- Write-through: 일관성 관리 용이, 메모리 트래픽 증가
- Write-back: 성능 향상, Dirty Line 및 일관성 관리 복잡도 증가
- 멀티코어 Cache: 접근 성능 향상, Cache Coherence 문제 발생
