## 1. 전체 학습 지도

```text
LLM 동작 원리
├─ Token
├─ Embedding
├─ Transformer
└─ Attention
      │
      ├──────────────→ Fine-tuning
      │                  ├─ SFT
      │                  └─ PEFT
      │                      └─ LoRA
      │
      ↓
Context 제어
├─ System Prompt
├─ Few-shot
├─ Structured Output
└─ Tool Calling
      │
      ├──────────────→ RAG / Vector Search
      │                  ├─ Chunking
      │                  ├─ Embedding
      │                  ├─ Vector DB
      │                  └─ Re-ranking
      │
      └──────────────→ Agent
                         ├─ Tool
                         ├─ Runtime
                         ├─ Memory
                         └─ MCP

RAG + Context 제어
        ↓
Text2SQL에도 활용 가능
├─ Metadata Retrieval
├─ Schema Linking
├─ SQL Generation
└─ Validation
```

가장 큰 구분:

```text
LLM을 원하는 방향으로 사용
│
├─ Model Parameter를 안 바꿈
│   └─ Context를 바꿈
│       ├─ System Prompt
│       ├─ Few-shot
│       ├─ RAG
│       └─ Tool 결과
│
└─ Model Parameter를 바꿈
    └─ Training
        └─ Fine-tuning
```

## 2. LLM이 답변을 만드는 흐름

```text
사용자 문장
   ↓
Tokenization
   ↓
Token ID
   ↓
Token Embedding
   ↓
Transformer Layers
   ↓
Self-Attention으로 문맥 반영
   ↓
다음 Token 확률분포
   ↓
Decoding으로 Token 하나 선택
   ↓
선택한 Token을 Context에 추가
   ↓
종료 조건인가?
   ├─ 아니오 → Transformer로 돌아가 다음 Token 생성
   └─ 예     → 최종 답변
```

핵심은 완성된 문장을 먼저 만드는 것이 아니라 **생성한 Token을 다시 Context에 넣고 다음 Token을 반복 예측한다는 것**이다.

상세: `LLM의-동작원리.md`

## 3. Training과 Inference

```text
[Training]
Text
 ↓
다음 Token 예측
 ↓
정답 Token과 비교
 ↓
Loss
 ↓
Backpropagation
 ↓
Model Weight 수정

[Inference]
사용자 Context
 ↓
학습된 Weight 사용
 ↓
다음 Token 생성
 ↓
Context에 추가
 ↓
다음 Token 반복 생성
```

- Training: Weight를 학습한다.
- Inference: 학습된 Weight를 사용한다.

## 4. System Prompt · Few-shot · RAG 관계

```text
System Prompt ── 규칙·역할 ───────┐
Few-shot ────── 입력-출력 예제 ───┤
RAG ─────────── 검색된 외부 지식 ─┤
Tool 결과 ───── 실제 실행 결과 ───┤
User Prompt ─── 사용자 질문 ──────┤
                                  ↓
                           Context Window
                                  ↓
                             LLM Inference
```

모두 LLM 입장에서는 현재 요청에 들어온 Token이다.

- System Prompt: 어떻게 행동할지
- Few-shot: 어떻게 풀지 예제로 보여주기
- RAG: 무엇을 참고할지
- Tool 결과: 외부에서 실제로 확인한 결과

상세: `LLM-프롬프트와-Context-제어.md`

## 5. RAG 구축과 질문 처리

```text
[사전 구축]
원문 문서
 ↓
Chunking
 ↓
검색용 Embedding Model
 ↓
Chunk Vector
 ↓
Vector DB
 ├─ Vector
 ├─ 원문 Chunk
 └─ Metadata · 출처 · 권한

[질문 시]
사용자 질문
 ↓
같은 Embedding Model
 ↓
Query Vector
 ↓
Vector Search
 ↓
필요 시 Re-ranking
 ↓
관련 Chunk Top-K
 ↓
질문 + 검색 원문으로 Context 구성
 ↓
LLM
 ↓
답변
```

검색용 Vector는 **문서를 찾기 위한 것**이고, LLM이 실제 답변에 참고하는 것은 검색된 **원문 Text**다.

상세: `임베딩-벡터검색-RAG.md`

## 6. 긴 Chunk가 Vector 하나가 되는 흐름

```text
긴 Chunk
 ↓
Tokenization
 ↓
여러 Token Vector
 ↓
Embedding Model의 Transformer
 ↓
문맥화된 Token 표현들
 ↓
Pooling / 집약
 ↓
고정 길이 Chunk Vector 하나
```

이 Vector는 원문을 복원하는 압축 파일이 아니라 **검색에 필요한 의미적 특징을 대표하는 좌표**다.

## 7. HNSW와 IVF

```text
대규모 Vector Search
│
├─ 모든 Vector 전수 비교
│   └─ Exact Search
│       └─ 정확하지만 데이터가 커지면 비용 증가
│
└─ 일부 후보만 효율적으로 탐색
    └─ ANN
        ├─ HNSW
        │   └─ Graph를 따라 가까운 Node 탐색
        │
        └─ IVF / IVFFlat
            └─ Vector 공간을 Cluster로 나누고
               가까운 Cluster만 검색
```

- HNSW: Graph 기반 ANN
- IVF: Cluster 기반 ANN

## 8. Fine-tuning 분류축

`Fine-tuning → SFT → PEFT → LoRA`를 일렬 계층으로 외우면 부정확하다.

```text
Fine-tuning
│
├─ [학습 Data / 목표 관점]
│   └─ SFT
│       └─ 입력-정답 Pair로 지도학습
│
└─ [Parameter 효율 관점]
    ├─ Full / 많은 Parameter 학습
    └─ PEFT
        └─ LoRA

SFT Data + LoRA 방식
→ 함께 사용 가능
```

즉 **SFT는 학습 신호 관점**, **PEFT/LoRA는 Parameter를 어떻게 효율적으로 학습하느냐의 관점**이다.

상세: `Fine-tuning과-PEFT-LoRA.md`

## 9. RAG · Few-shot · Fine-tuning 선택 지도

```text
무엇을 해결하려는가?
│
├─ 최신·사내 지식이 필요한가?
│   └─ YES → RAG
│
├─ 몇 개 예제로 Pattern을 보여주면 되는가?
│   └─ YES → Few-shot
│
├─ 반복적인 Model 행동 자체를 조정해야 하는가?
│   └─ YES → Fine-tuning 검토
│
└─ 역할·규칙을 지정하면 되는가?
    └─ System Prompt / Prompt 설계
```

이 선택지는 배타적이지 않다. 실제 시스템에서는 함께 사용할 수 있다.

## 10. Agent Loop

```text
사용자 목표
 ↓
LLM 판단
 ↓
다음 행동이 필요한가?
 ├─ 아니오 → 최종 답변 / 작업 완료
 │
 └─ 예
     ↓
   Tool Call 생성
     ↓
   Agent Runtime이 실제 Tool 실행
     ↓
   Observation / Tool 결과
     ↓
   결과를 Context에 추가
     ↓
   LLM 재판단
     └────────────── 반복
```

역할:

```text
LLM
= 무엇을 할지 판단

Agent Runtime / Harness
= Tool 실행과 Loop 관리

Tool
= 파일·Shell·DB·API 등 실제 작업
```

상세: `에이전트와-MCP.md`

## 11. Coding Agent와 Context 관리

일반 질문과 대형 Code Base 작업은 필요한 Context 규모가 크게 다르다.

```text
[일반 질문]
짧은 질문
+
학습된 Weight
→ LLM
→ 답변

[Coding Agent]
사용자 요청
+
현재 Project의 관련 Code
+
참조·구현 관계
+
Error Log / Test 결과
+
Architecture·Project 규칙
→ LLM
→ 다음 행동 또는 Patch
```

Project 전체를 항상 Context Window에 넣는 것은 현실적이지도 않고 효율적이지도 않다. Coding Agent는 전체 Code Base를 외부 저장소처럼 두고 **현재 작업에 필요한 Working Set을 계속 구성**한다.

```text
전체 Code Base
     ↓
Agent / Harness
├─ 파일 탐색
├─ 문자열 검색
├─ Symbol·Reference 검색
├─ Project 지침 확인
└─ Build / Test 실행
     ↓
현재 작업에 필요한 Context
     ↓
LLM
     ↓
부족한 정보가 있으면 다시 탐색
```

문서 RAG와 철학적으로 비슷하다.

```text
문서 RAG
많은 문서 → 관련 Chunk 선택 → LLM Context

Coding Agent
큰 Code Base → 관련 Code·설계 맥락 선택 → LLM Context
```

다만 Code는 정확한 이름과 구조적 관계가 중요하므로 Embedding 검색만이 아니라 파일 구조, 문자열 검색, Symbol 정의·참조, LSP/AST 계열의 Code Intelligence가 중요할 수 있다.

상세: `LLM의-동작원리.md`, `에이전트와-MCP.md`

## 12. MCP는 Agent와 외부 기능 사이의 '지도 + 규격'

```text
                   Agent / AI Client
                          │
                         MCP
          ┌───────────────┼───────────────┐
          ↓               ↓               ↓
       Serena          Context7       사내 MCP Server
    Code 구조 탐색    Library 문서       │
                                         ├─ 기존 API
                                         └─ DB
```

MCP가 없어도 가능하다.

```text
[MCP 없음]
Agent A → 사내 API 전용 연동
Agent B → 사내 API 전용 연동

[MCP 사용]
Agent A ─┐
Agent B ─┼→ MCP Server → 사내 API / DB / Tool
Agent C ─┘
```

MCP는 기능 자체보다 **Tool·Resource를 어떻게 발견하고 호출할지 표준화**하는 역할이다.

## 13. RAG와 MCP는 계층이 다르다

```text
Agent
 ↓
MCP
 ↓
search_metadata Tool
 ↓
Embedding
 ↓
Vector DB
 ↓
관련 Metadata 반환
 ↓
Agent
```

이 구조에서는:

- 바깥 Interface는 MCP
- Tool 내부 검색 방식은 RAG

즉:

> **RAG = 관련 정보를 어떻게 찾을 것인가**
>
> **MCP = 그 기능을 Agent에게 어떻게 표준적으로 제공할 것인가**

## 14. Text2SQL은 LLM보다 상위의 문제 영역이다

```text
Text2SQL
= 자연어 → SQL이라는 Task
│
├─ Rule / Template 기반
├─ 전용 ML / Seq2Seq 기반
└─ LLM 기반
    │
    ├─ Schema가 작음
    │   └─ 질문 + 전체 Schema → LLM → SQL
    │
    └─ Schema가 큼
        └─ Metadata Retrieval
            ↓
          Schema Linking
            ↓
          SQL Generation
            ↓
          Validation
```

LLM은 Text2SQL을 구현하는 방법 중 하나일 뿐이다.

상세: `Text2SQL과-스키마-링킹.md`

## 15. LLM 기반 대규모 Text2SQL

```text
자연어 질문
 ↓
Metadata / Schema Retrieval
 ↓
관련 Table · Column · 업무용어 후보
 ↓
Schema Linking
 ├─ Table Linking
 ├─ Column Linking
 ├─ Value Linking
 └─ Join Path Linking
 ↓
관련 Context 구성
 ↓
SQL Generation
 ↓
Validation
 ├─ 오류 → 오류 정보로 수정 → SQL 재생성
 └─ 통과
      ↓
제한된 환경에서 실행
 ↓
결과 설명
```

Schema Linking은 특정 Model 이름이 아니라 **질문의 개념을 실제 DB 요소와 연결하는 Task**다.

## 16. 전체 기억 흐름

```text
                       LLM
                 다음 Token 예측
                  /           \
                 /             \
          Context 제어       Fine-tuning
          Weight 유지         Weight 변경
          /       \
         /         \
       RAG        Agent ───── MCP
       │            │          │
   외부 지식      Tool 실행   외부 Tool 지도
                    │
                    └─ Coding Agent
                       └─ 필요한 Code·설계 맥락을
                          동적으로 Context에 구성
       │
       └──────────────→ Text2SQL 등에 활용
```

마지막으로:

> **LLM은 Context를 보고 다음 Token을 반복 예측한다.**
>
> **자연어와 Code 생성·수정도 같은 Transformer의 Token 생성 과정으로 처리할 수 있다.**
>
> **RAG는 외부 지식을 검색해 Context에 공급한다.**
>
> **Fine-tuning은 Context가 아니라 학습 Parameter를 변경한다.**
>
> **Agent는 LLM 판단을 Tool 실행으로 연결하고, 필요한 Working Context를 계속 구성한다.**
>
> **MCP는 Agent가 외부 Tool·Resource를 표준 방식으로 발견하고 호출하도록 연결한다.**
>
> **Text2SQL은 자연어를 SQL로 바꾸는 Task이며 LLM은 그 구현 방식 중 하나다.**
