## 1. 가장 먼저 볼 전체 지도: AI는 LLM보다 크다

지금까지 학습한 RAG·Agent·MCP가 모두 LLM 중심이라 `AI = LLM`처럼 느껴질 수 있다. 하지만 LLM은 AI 전체가 아니라 **언어 영역에서 크게 성공한 Foundation Model 계열**이다.

```text
AI
│
├─ 전통적 / Task 특화 AI
│   ├─ 분류
│   ├─ 회귀·예측
│   ├─ 추천
│   ├─ 이상 탐지
│   ├─ Object Detection
│   └─ 기타 Domain Model
│
└─ 생성형 AI(Generative AI)
    │
    ├─ Text
    │   └─ LLM
    │       └─ 대표 생성 방식: Autoregressive Token 생성
    │
    ├─ Image
    │   ├─ GAN 계열
    │   └─ Diffusion 계열
    │
    ├─ Audio / Speech
    │   ├─ STT
    │   ├─ TTS
    │   └─ Audio 생성
    │
    ├─ Video
    │   └─ 공간 구조 + 시간적 일관성
    │
    └─ Multimodal
        └─ Text · Image · Audio · Video를 함께 연결
```

상세: `생성형-AI와-멀티모달.md`

## 2. 서로 다른 분류축을 섞지 않는다

LLM, GAN, Diffusion, Multimodal, Foundation Model은 같은 계층의 용어가 아니다.

```text
[무엇을 다루는가? = Modality]
Text / Image / Audio / Video

[어떤 구조로 처리하는가? = Architecture]
CNN / RNN / Transformer 등

[어떤 생성 원리를 사용하는가?]
Autoregressive / GAN / Diffusion 등

[얼마나 범용적으로 재사용하는가?]
Task-specific Model / Foundation Model

[몇 가지 Modality를 함께 다루는가?]
Unimodal / Multimodal

[만들어진 Model을 어떻게 활용하는가?]
Prompt / RAG / Fine-tuning / Tool / Agent / MCP
```

따라서 다음처럼 일렬 발전 단계로 외우면 안 된다.

```text
LLM → GAN → Diffusion → Multimodal   X
```

예를 들어 Diffusion 기반 Image Model도 Foundation Model 규모로 발전할 수 있고, LLM을 중심으로 Vision·Audio를 연결한 Multimodal Foundation Model도 존재할 수 있다.

다만 **분류축이 다르다는 말이 실제 시스템에서 서로 따로 논다는 뜻은 아니다.** 현대 GPT류 LLM은 여러 축이 한 시스템 안에서 결합된 사례다.

```text
GPT류 LLM
= Text Modality를 다루는 Language Model
+ Transformer Architecture
+ Autoregressive Generation
+ 대규모 사전학습
```

즉 Transformer와 Autoregressive는 같은 계층의 경쟁 용어가 아니다. 하지만 실제 LLM 생성 과정에서는 **Autoregressive Generation이라는 전체 생성 방식 안에서 Transformer가 다음 Token 후보 분포를 계산하는 핵심 구조로 사용**된다.

```text
Autoregressive Generation 한 Step

현재 Context
 ↓
Transformer
 ↓
다음 Token 후보 분포
 ↓
Decoding
 ↓
Token 하나 선택
 ↓
선택 Token을 Context에 추가
 ↓
다음 Step 반복
```

## 3. Foundation Model이라는 또 다른 축

Foundation Model은 대규모 Data로 먼저 학습하고 여러 Downstream Task에 재사용할 수 있는 범용 기반 Model이다.

```text
Foundation Model
│
├─ Language Foundation Model
│   └─ LLM
│
├─ Vision Foundation Model
│
├─ Multimodal Foundation Model
│
└─ Domain Foundation Model
```

LLM이 특히 주목받는 이유는 하나의 범용 Model이 질의응답·요약·번역·코딩·분석·Tool 사용 등 매우 넓은 Task를 처리할 수 있게 되었기 때문이다.

```text
                     LLM
                      │
      ┌───────────────┼───────────────┐
      ↓               ↓               ↓
    질의응답           코딩             분석
      ↓               ↓               ↓
     요약            SQL 생성          Tool 사용
      ↓               ↓               ↓
     번역            Agent           업무 자동화
```

상세: `Foundation-Model과-AI-활용계층.md`

## 4. Model을 만드는 층과 활용하는 층

최근 LLM 생태계를 이해할 때 매우 중요한 구분이다.

```text
[Foundation Model을 만드는 층]

대규모 Data
   ↓
Pre-training
   ↓
Foundation Model / LLM
   ↓
Post-training / Fine-tuning
   ↓
대규모 Model Serving

────────────────────────────────

[만들어진 Model을 활용하는 층]

                   LLM
                    │
       ┌────────────┼────────────┐
       ↓            ↓            ↓
    지시·Context     외부 지식       행동
       │            │            │
Prompt / Few-shot   RAG        Tool Calling
System Prompt       │            │
                    │          Agent
                    │            │
                    │           MCP
       └────────────┼────────────┘
                    ↓
              실제 업무 Service
```

최상위 Foundation Model의 Training과 대규모 Serving은 막대한 Compute·Infrastructure를 필요로 할 수 있다. 그래서 많은 기업에서는 Model을 처음부터 만드는 것보다 **기존 Foundation Model을 자기 Data·Context·Tool·Workflow에 연결하는 활용 전략**이 현실적으로 중요하다.

## 5. LLM 내부 동작

LLM 활용 기술을 이해하려면 중심의 LLM이 무엇을 하는지 먼저 알아야 한다.

```text
사용자 문장
   ↓
Tokenization
   ↓
Token ID
   ↓
Token Embedding
   ↓
Transformer Layers
   ↓
Self-Attention으로 문맥 반영
   ↓
다음 Token 확률분포
   ↓
Decoding으로 Token 하나 선택
   ↓
선택한 Token을 Context에 추가
   ↓
종료 조건인가?
   ├─ 아니오 → 다음 Token 생성 반복
   └─ 예     → 최종 출력
```

핵심은 완성된 문장을 먼저 만드는 것이 아니라 **생성한 Token을 다시 Context에 넣고 다음 Token을 반복 예측한다는 것**이다. 이 전체 반복 방식이 Autoregressive Generation이다.

자연어뿐 아니라 Code 생성·수정도 같은 Transformer 기반 Token 생성 과정으로 처리할 수 있다.

상세: `LLM의-동작원리.md`

```text
 ↓

 ↓

 ↓
```

```text

```

```text

                      │

        ↓             ↓             ↓
     잘 지시        지식 공급        행동 연결
```

## 8. System Prompt · Few-shot · RAG 관계

```text
System Prompt ── 규칙·역할 ───────┐
Few-shot ────── 입력-출력 예제 ───┤
RAG ─────────── 검색된 외부 지식 ─┤
Tool 결과 ───── 실제 실행 결과 ───┤
User Prompt ─── 사용자 질문 ──────┤
                                  ↓
                           Context Window
                                  ↓
                             LLM Inference
```

모두 Weight를 직접 바꾸지 않고 현재 Context를 구성한다.

- System Prompt: 어떻게 행동할지
- Few-shot: 어떻게 풀지 예제로 보여주기
- RAG: 무엇을 참고할지
- Tool 결과: 외부에서 실제로 확인한 결과

상세: `LLM-프롬프트와-Context-제어.md`

## 12. Fine-tuning 분류축

`Fine-tuning → SFT → PEFT → LoRA`를 일렬 계층으로 외우면 부정확하다.

```text
Fine-tuning
│
├─ [학습 Data / 목표 관점]
│   └─ SFT
│       └─ 입력-정답 Pair로 지도학습
│
└─ [Parameter 효율 관점]
    ├─ Full Fine-tuning
    └─ PEFT
        └─ LoRA

SFT Data + LoRA 방식
→ 함께 사용 가능
```

즉 **SFT는 학습 신호 관점**, **PEFT/LoRA는 Parameter를 어떻게 효율적으로 학습하느냐의 관점**이다.

상세: `Fine-tuning과-PEFT-LoRA.md`

## 13. RAG · Few-shot · Fine-tuning 선택 지도

```text
무엇을 해결하려는가?
│
├─ 최신·사내 지식이 필요한가?
│   └─ YES → RAG
│
├─ 몇 개 예제로 Pattern을 보여주면 되는가?
│   └─ YES → Few-shot
│
├─ 반복적인 Model 행동 자체를 조정해야 하는가?
│   └─ YES → Fine-tuning 검토
│
└─ 역할·규칙을 지정하면 되는가?
    └─ System Prompt / Prompt 설계
```

이 선택지는 배타적이지 않다. 실제 시스템에서는 함께 사용할 수 있다.

## 15. Coding Agent와 Context 관리

일반 질문과 대형 Code Base 작업은 필요한 Context 규모가 크게 다르다.

```text
[일반 질문]
짧은 질문
+
학습된 Weight
→ LLM
→ 답변

[Coding Agent]
사용자 요청
+
현재 Project의 관련 Code
+
참조·구현 관계
+
Error Log / Test 결과
+
Architecture·Project 규칙
→ LLM
→ 다음 행동 또는 Patch
```

Project 전체를 항상 Context Window에 넣는 대신 Agent가 현재 작업에 필요한 Working Set을 계속 구성한다.

```text
전체 Code Base
     ↓
Agent / Harness
├─ 파일 탐색
├─ 문자열 검색
├─ Symbol·Reference 검색
├─ Project 지침 확인
└─ Build / Test 실행
     ↓
현재 작업에 필요한 Context
     ↓
LLM
     ↓
부족하면 다시 탐색
```

문서 RAG와 철학적으로 비슷하지만 Code는 정확한 이름과 구조적 관계가 중요하므로 파일 구조, 문자열 검색, Symbol 정의·참조, LSP/AST 계열의 Code Intelligence가 중요할 수 있다.

상세: `LLM의-동작원리.md`, `에이전트와-MCP.md`

## 16. MCP는 Agent와 외부 기능 사이의 지도와 규격

```text
                   Agent / AI Client
                          │
                         MCP
          ┌───────────────┼───────────────┐
          ↓               ↓               ↓
       Serena          Context7       사내 MCP Server
    Code 구조 탐색    Library 문서       │
                                         ├─ 기존 API
                                         └─ DB
```

MCP가 없어도 Agent와 외부 기능을 직접 연동할 수 있다. MCP는 **Tool·Resource를 어떻게 발견하고 호출할지 공통 방식으로 제공하는 Protocol**이다.

## 18. Text2SQL은 LLM보다 상위의 문제 영역이다

```text
Text2SQL
= 자연어 → SQL이라는 Task
│
├─ Rule / Template 기반
├─ 전용 ML / Seq2Seq 기반
└─ LLM 기반
    │
    ├─ Schema가 작음
    │   └─ 질문 + 전체 Schema → LLM → SQL
    │
    └─ Schema가 큼
        └─ Metadata Retrieval
            ↓
          Schema Linking
            ↓
          SQL Generation
            ↓
          Validation
```

LLM은 Text2SQL을 구현하는 방법 중 하나일 뿐이다.

상세: `Text2SQL과-스키마-링킹.md`

## 19. LLM 기반 대규모 Text2SQL

```text
자연어 질문
 ↓
Metadata / Schema Retrieval
 ↓
관련 Table · Column · 업무용어 후보
 ↓
Schema Linking
 ├─ Table Linking
 ├─ Column Linking
 ├─ Value Linking
 └─ Join Path Linking
 ↓
관련 Context 구성
 ↓
SQL Generation
 ↓
Validation
 ├─ 오류 → 오류 정보로 수정 → SQL 재생성
 └─ 통과
      ↓
제한된 환경에서 실행
 ↓
결과 설명
```

Schema Linking은 특정 Model 이름이나 LLM에 종속된 개념이 아니다. **자연어의 의미를 실제 DB의 Table·Column·Value·Join 관계에 연결하는 문제**이며 Rule·전용 ML·LLM 기반 Text2SQL 모두에서 나타날 수 있다.

대규모 Schema에서는 전체 Metadata를 매번 LLM에 넣기보다 먼저 관련 후보를 검색해 Context를 줄이는 구조가 중요할 수 있다.

## 20. 전체 흐름 다시 보기

```text
AI 전체
 ↓
생성형 AI / Foundation Model
 ↓
LLM의 내부 동작
Token → Embedding → Transformer → 다음 Token 생성
 ↓
만들어진 LLM 활용
Prompt / Context
├─ 외부 지식 → RAG
├─ 행동 → Tool / Agent / MCP
└─ Parameter 조정 → Fine-tuning
 ↓
실제 업무 문제에 적용
예: Text2SQL
```

가장 중요한 것은 모든 용어를 하나의 선형 계보로 외우지 않는 것이다. **Model 구조, 생성 방식, Training, Inference Context, Retrieval, Tool 연결, 업무 Task는 서로 다른 층과 분류축**이다.

다만 서로 다른 분류축은 실제 시스템 안에서 조합될 수 있다. GPT류 LLM은 `Text Modality + Transformer Architecture + Autoregressive Generation + 대규모 사전학습`이 결합된 대표 사례다.

> **새로운 AI 용어를 만나면 먼저 “이 용어는 Model 자체, Architecture, 생성 방식, 학습 방식, 추론 시 Context, 검색, 실행 연결, 업무 Task 중 어디에 위치하는가?”를 묻는다. 그 위치를 잡은 뒤 실제 시스템에서 어떤 축과 조합되는지 연결하면 개념이 덜 섞인다.**
