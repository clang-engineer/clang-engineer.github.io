# 인공지능 세부학습 개념지도

이 문서는 `09-인공지능`의 세부 문서를 읽기 전에 **전체 개념의 위치와 관계를 Mermaid Diagram으로 먼저 잡기 위한 지도**다.

장문 설명을 대체하는 문서가 아니라, 각 상세 문서에서 배운 개념이 어디에 연결되는지 빠르게 복습하는 용도다.

---

## 1. 전체 학습 지도

```mermaid
flowchart TD
    A[LLM 동작 원리] --> B[Context 제어]
    B --> C[RAG · Vector Search]
    A --> D[Fine-tuning]
    B --> E[Agent · Tool Calling]
    C --> E
    E --> F[MCP]
    B --> G[Text2SQL]
    C --> G
    D --> G

    A1[Token · Embedding · Transformer · Attention] --> A
    B1[System Prompt · Few-shot · Structured Output] --> B
    C1[Chunking · Embedding · Vector DB · Re-ranking] --> C
    D1[SFT · PEFT · LoRA] --> D
    E1[Tool · Runtime · Memory · Agent Loop] --> E
    F1[Tool · Resource 발견/호출 규격] --> F
    G1[Metadata Retrieval · Schema Linking · SQL Validation] --> G
```

가장 중요한 큰 구분은 다음이다.

```mermaid
flowchart LR
    A[LLM을 원하는 방향으로 바꾸기] --> B{Model Parameter를 바꾸는가?}
    B -->|아니오| C[Context를 바꿈]
    B -->|예| D[Training 수행]

    C --> C1[System Prompt]
    C --> C2[Few-shot]
    C --> C3[RAG]
    C --> C4[Tool 결과]

    D --> D1[Fine-tuning]
    D1 --> D2[SFT 가능]
    D1 --> D3[PEFT 가능]
    D3 --> D4[LoRA]
```

## 2. LLM이 답변을 한 Token씩 만드는 흐름

```mermaid
flowchart TD
    A[사용자 문장] --> B[Tokenization]
    B --> C[Token ID]
    C --> D[Token Embedding]
    D --> E[Transformer Layers]
    E --> F[Self-Attention으로 문맥 반영]
    F --> G[다음 Token 확률분포]
    G --> H[Decoding으로 Token 하나 선택]
    H --> I[선택 Token을 Context에 추가]
    I --> J{종료 조건?}
    J -->|아니오| E
    J -->|예| K[최종 답변]
```

핵심은 **완성된 문장을 먼저 만드는 것이 아니라 생성된 Token을 다시 Context에 넣고 다음 Token을 반복 예측한다는 것**이다.

상세: `LLM의-동작원리.md`

## 3. Training과 Inference

```mermaid
flowchart LR
    subgraph Training
        A1[Text] --> A2[다음 Token 예측]
        A2 --> A3[정답 Token과 비교]
        A3 --> A4[Loss]
        A4 --> A5[Backpropagation]
        A5 --> A6[Model Weight 수정]
    end

    subgraph Inference
        B1[사용자 Context] --> B2[학습된 Weight 사용]
        B2 --> B3[다음 Token 생성]
        B3 --> B4[Context에 추가]
        B4 --> B2
    end
```

- Training: Weight를 학습한다.
- Inference: 학습된 Weight를 사용한다.

## 4. System Prompt · Few-shot · RAG 관계

```mermaid
flowchart LR
    S[System Prompt<br/>규칙·역할] --> C[Context Window]
    F[Few-shot<br/>입력-출력 예제] --> C
    R[RAG<br/>검색된 외부 지식] --> C
    T[Tool 결과<br/>실제 외부 실행 결과] --> C
    U[User Prompt] --> C
    C --> L[LLM Inference]
```

모두 LLM 입장에서는 결국 **현재 요청에 들어온 Token**이다.

차이는 무엇을 넣느냐이다.

- System Prompt: 어떻게 행동할지
- Few-shot: 어떻게 풀지 예제로 보여주기
- RAG: 무엇을 참고할지
- Tool 결과: 외부에서 실제로 확인한 결과

상세: `LLM-프롬프트와-Context-제어.md`

## 5. RAG 구축과 질문 처리

```mermaid
flowchart TD
    subgraph Indexing[사전 구축]
        A[원문 문서] --> B[Chunking]
        B --> C[검색용 Embedding Model]
        C --> D[Chunk Vector]
        D --> E[(Vector DB)]
        B --> E
        M[Metadata · 출처 · 권한] --> E
    end

    subgraph Retrieval[질문 시]
        Q[사용자 질문] --> QE[같은 Embedding Model]
        QE --> QV[Query Vector]
        QV --> VS[Vector Search]
        E --> VS
        VS --> RR[필요 시 Re-ranking]
        RR --> K[관련 Chunk Top-K]
        K --> CTX[질문 + 검색 원문을 Context에 구성]
        CTX --> LLM[LLM]
        LLM --> ANS[답변]
    end
```

여기서 검색용 Vector는 **문서를 찾기 위한 것**이고, LLM이 실제 답변에 참고하는 것은 검색된 **원문 Text**다.

상세: `임베딩-벡터검색-RAG.md`

## 6. 긴 Chunk가 Vector 하나가 되는 흐름

```mermaid
flowchart LR
    A[긴 Chunk] --> B[Tokenization]
    B --> C[여러 Token Vector]
    C --> D[Embedding Model의 Transformer]
    D --> E[문맥화된 Token 표현들]
    E --> F[Pooling / 집약]
    F --> G[고정 길이 Chunk Vector 하나]
```

이 Vector는 원문을 복원하는 압축 파일이 아니다. **검색에 필요한 의미적 특징을 대표하는 좌표**다.

## 7. HNSW와 IVF

```mermaid
flowchart TD
    A[대규모 Vector Search] --> B{모든 Vector 전수 비교?}
    B -->|예| C[Exact Search<br/>정확하지만 대규모에서 비용 증가]
```

## 8. Fine-tuning 분류를 한 줄로 외우면 안 되는 이유

`Fine-tuning → SFT → PEFT → LoRA`를 일렬 계층으로 외우면 부정확하다.

```mermaid
flowchart TD
    A[Fine-tuning] --> B[학습 Data / 목표 관점]
    A --> C[Parameter 효율 관점]

    B --> B1[SFT<br/>입력-정답 Pair로 지도학습]

    C --> C1[Full / 많은 Parameter 학습]
    C --> C2[PEFT<br/>일부 Parameter만 효율적으로 학습]
    C2 --> C3[LoRA]

    B1 -. 함께 사용 가능 .-> C3
```

즉 **SFT는 학습 신호 관점**, **PEFT/LoRA는 Parameter를 어떻게 효율적으로 학습하느냐의 관점**이다.

상세: `Fine-tuning과-PEFT-LoRA.md`

## 9. RAG · Few-shot · Fine-tuning 선택 지도

```mermaid
flowchart TD
    A[무엇을 해결하려는가?] --> B{최신·사내 지식이 필요한가?}
    B -->|예| R[RAG]
    B -->|아니오| C{몇 개 예제로 패턴을 보여주면 되는가?}
    C -->|예| F[Few-shot]
    C -->|아니오| D{반복적인 Model 행동 자체를 조정해야 하는가?}
    D -->|예| FT[Fine-tuning 검토]
    D -->|아니오| SP[System Prompt / Prompt 설계]
```

이 선택지는 배타적이지 않다. 실제 시스템에서는 RAG + Few-shot + Fine-tuning을 함께 사용할 수도 있다.

## 10. Agent Loop

```mermaid
flowchart TD
    U[사용자 목표] --> L[LLM 판단]
    L --> A{다음 행동 필요?}
    A -->|예| T[Tool Call 생성]
    T --> R[Agent Runtime이 실제 Tool 실행]
    R --> O[Observation / Tool 결과]
    O --> C[결과를 Context에 추가]
    C --> L
```

```mermaid
    T --> H
    H --> L
```

## 11. MCP는 Agent와 외부 기능 사이의 '지도 + 규격'

```mermaid
flowchart LR
    A[Agent / AI Client] --> M[MCP]
    M --> S1[Serena<br/>Code 탐색]
    M --> S2[Context7<br/>Library 문서]
    M --> S3[DB MCP Server]
    M --> S4[사내 MCP Server]

    S3 --> DB[(Database)]
    S4 --> API[기존 사내 API]
```

MCP가 없어도 Agent마다 전용 연동을 직접 구현할 수 있다.

```mermaid
flowchart TD
    subgraph 직접연동[MCP가 없을 때]
        A1[Agent A] --> X1[사내 API 전용 연동]
        A2[Agent B] --> X2[사내 API 전용 연동]
    end

    subgraph 표준화[MCP 사용]
        B1[Agent A] --> M[MCP Server]
        B2[Agent B] --> M
        M --> API[사내 API / DB / Tool]
    end
```

MCP는 기능 그 자체보다 **Tool·Resource를 어떻게 발견하고 호출할지 표준화**하는 역할이다.

## 12. RAG와 MCP는 계층이 다르다

```mermaid
flowchart LR
    A[Agent] --> M[MCP]
    M --> T[search_metadata Tool]
    T --> E[Embedding]
    E --> V[(Vector DB)]
    V --> R[관련 Metadata 반환]
    R --> A
```

이 구조에서는:

- 바깥 Interface는 MCP
- Tool 내부 검색 방식은 RAG

따라서:

> **RAG = 관련 정보를 어떻게 찾을 것인가**
>
> **MCP = 그 기능을 Agent에게 어떻게 표준적으로 제공할 것인가**

## 13. Text2SQL은 LLM보다 상위의 문제 영역이다

```mermaid
flowchart TD
    A[Text2SQL<br/>자연어 → SQL Task] --> B[Rule / Template 기반]
    A --> C[전용 ML / Seq2Seq 기반]
    A --> D[LLM 기반]

    D --> E{Schema 규모가 큰가?}
    E -->|작음| F[질문 + 전체 Schema → LLM → SQL]
    E -->|큼| G[Metadata Retrieval]
    G --> H[Schema Linking]
    H --> I[LLM SQL Generation]
    I --> J[Validation]
```

LLM은 Text2SQL을 구현하는 방법 중 하나일 뿐이다.

상세: `Text2SQL과-스키마-링킹.md`

## 14. LLM 기반 대규모 Text2SQL 상세 흐름

```mermaid
flowchart TD
    Q[자연어 질문] --> R[Metadata / Schema Retrieval]
    R --> S[관련 Table · Column · 업무용어 후보]
    S --> L[Schema Linking]

    L --> T[Table Linking]
    L --> C[Column Linking]
    L --> V[Value Linking]
    L --> J[Join Path Linking]

    T --> X[관련 Context 구성]
    C --> X
    V --> X
    J --> X

    X --> G[SQL Generation]
    G --> VAL[Validation]
    VAL -->|오류| FIX[오류 정보로 수정]
    FIX --> G
    VAL -->|통과| EXE[제한된 환경에서 실행]
    EXE --> ANS[결과 설명]
```

Schema Linking은 특정 Model 이름이 아니라 **질문의 개념을 실제 DB 요소와 연결하는 Task**다.

## 15. 전체 기억 흐름

```mermaid
flowchart LR
    LLM[LLM<br/>다음 Token 예측] --> CTX[Context 제어]
    LLM --> FT[Fine-tuning]
    CTX --> RAG[RAG]
    CTX --> AG[Agent]
    RAG --> AG
    AG --> MCP[MCP]
    CTX --> T2S[Text2SQL]
    RAG --> T2S

    LLM -. Weight 기반 추론 .-> CTX
    FT -. Weight 변경 .-> LLM
    RAG -. 외부 지식 .-> CTX
    MCP -. 외부 Tool 지도 .-> AG
```

마지막으로 가장 중요한 문장만 묶으면:

> **LLM은 Context를 보고 다음 Token을 예측하는 Model이다.**
>
> **RAG는 외부 지식을 검색해서 Context에 넣는다.**
>
> **Fine-tuning은 Model Parameter를 실제로 학습한다.**
>
> **Agent는 LLM 판단을 Tool 실행과 반복 Loop로 확장한다.**
>
> **MCP는 Agent가 외부 Tool·Resource를 표준 방식으로 발견하고 호출하도록 연결한다.**
>
> **Text2SQL은 자연어를 SQL로 바꾸는 Task이며 LLM은 그 구현 방식 중 하나다.**
