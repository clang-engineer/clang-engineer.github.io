# 인공지능 세부학습 개념지도

이 문서는 `09-인공지능`의 상세 문서를 읽기 전에 **전체 개념의 위치·관계·흐름을 빠르게 잡는 지도**다.

세부 Algorithm, 구현 방법, Parameter, 예제는 각 세부학습 문서에서 다룬다. 여기서는 새로운 용어를 만났을 때 **AI 전체에서 어디에 놓이는지**를 잃지 않는 것을 우선한다.

GitHub 모바일 앱, Obsidian, Terminal 등 어떤 Markdown Viewer에서도 바로 읽을 수 있도록 Mermaid에 의존하지 않고 Text/ASCII Diagram을 기본으로 한다.

---

## 1. 가장 먼저 볼 전체 지도: AI는 LLM보다 크다

RAG·Agent·MCP를 중심으로 공부하면 `AI = LLM`처럼 느껴질 수 있다. 하지만 LLM은 AI 전체가 아니라 **언어 영역에서 크게 성공한 Foundation Model 계열**이다.

```text
AI
│
├─ Task 특화 AI
│   ├─ 분류 · 회귀 · 예측
│   ├─ 추천 · 이상 탐지
│   └─ Vision / Domain Model 등
│
└─ 생성형 AI
    ├─ Text
    │   └─ LLM
    ├─ Image
    │   └─ GAN / Diffusion 등
    ├─ Audio / Video
    └─ Multimodal
        └─ 여러 Modality를 함께 처리
```

상세: `생성형-AI와-멀티모달.md`

---

## 2. AI 용어는 같은 한 줄의 발전 단계가 아니다

AI에서 가장 먼저 잡아야 할 습관은 **분류축을 섞지 않는 것**이다.

```text
[무엇을 다루는가?]
Modality
→ Text / Image / Audio / Video

[어떤 구조로 처리하는가?]
Architecture
→ CNN / RNN / Transformer 등

[어떤 방식으로 생성하는가?]
Generation
→ Autoregressive / GAN / Diffusion 등

[얼마나 범용적으로 재사용하는가?]
Model 범용성
→ Task-specific / Foundation Model

[만들어진 Model을 어떻게 활용하는가?]
Application
→ Prompt / RAG / Fine-tuning / Tool / Agent / MCP
```

따라서 다음처럼 외우면 안 된다.

```text
LLM → GAN → Diffusion → Multimodal   X
CNN → RNN → GAN → Transformer       X
```

실제 시스템에서는 서로 다른 축이 조합된다.

```text
GPT류 LLM
= Text를 다루는 Language Model
+ Transformer Architecture
+ Autoregressive Generation
+ 대규모 사전학습
```

상세: `딥러닝-대표구조-CNN-RNN-Transformer-GAN.md`, `생성형-AI와-멀티모달.md`

## 3. Foundation Model: Model을 만드는 층과 활용하는 층

Foundation Model은 대규모 Data로 먼저 학습한 뒤 여러 Downstream Task에 재사용할 수 있는 범용 기반 Model이다.

```text
Foundation Model
├─ Language Foundation Model
│   └─ LLM
├─ Vision Foundation Model
├─ Multimodal Foundation Model
└─ Domain Foundation Model
```

최근 AI 생태계는 크게 두 층으로 볼 수 있다.

```text
[Model을 만드는 층]
대규모 Data
 ↓
Pre-training
 ↓
Foundation Model / LLM
 ↓
Post-training / Fine-tuning
 ↓
Model Serving

────────────────────────

[Model을 활용하는 층]
Foundation Model / LLM
 ↓
Prompt · Context
├─ 외부 지식 연결 → RAG
├─ 행동 연결      → Tool / Agent / MCP
└─ 업무 Task 적용 → Text2SQL 등
```

많은 기업과 개발자에게는 Foundation Model 자체를 처음부터 만드는 것보다 **이미 만들어진 Model을 자기 Data·Context·Tool·Workflow와 연결하는 층**이 현실적인 개발 영역이 된다.

상세: `Foundation-Model과-AI-활용계층.md`

## 4. LLM의 중심 흐름: Training과 Inference

LLM의 내부를 가장 크게 보면 `Weight를 만드는 과정`과 `만들어진 Weight를 사용하는 과정`으로 나뉜다.

```text
[Training]
학습 Data
 ↓
다음 Token 예측
 ↓
Loss
 ↓
Backpropagation
 ↓
Weight 수정

[Inference]
현재 Context
 ↓
학습된 Weight를 가진 LLM
 ↓
다음 Token 후보 계산
 ↓
Token 선택
 ↓
Context에 추가
 ↓
반복
```

핵심 구분:

```text
Weight
= Training으로 Model에 학습된 능력

Context
= 현재 Inference에서 Model에게 보여주는 작업 자료
```

LLM의 대표적인 생성 흐름은 다음과 같다.

```text
Text
 ↓
Tokenization
 ↓
Embedding
 ↓
Transformer / Attention
 ↓
다음 Token 후보
 ↓
Decoding
 ↓
Token 생성
 ↓
다시 Context에 추가하여 반복
```

즉 Transformer는 Token을 처리하는 핵심 Architecture이고, Autoregressive Generation은 **생성한 Token을 다시 입력에 포함해 다음 Token을 계속 생성하는 전체 방식**이다.

상세: `LLM의-동작원리.md`, `LLM-추론과-Token-생성.md`, `LLM-내부운영과-GPU-메모리.md`

## 5. 만들어진 LLM을 활용하는 세 갈래

Model을 직접 다시 만드는 것과 이미 만들어진 Model을 활용하는 방법을 구분한다.

```text
                         LLM
                          │
          ┌───────────────┼───────────────┐
          ↓               ↓               ↓
       지시·Context       외부 지식          행동
          │               │               │
   System Prompt          RAG          Tool Calling
   Prompt / Few-shot       │               │
          │          Embedding/Search     Agent
          │                               │
          └───────────────┬───────────────┘
                          ↓
                       업무 Service
```

여기에 **Model 행동 자체를 반복적으로 조정해야 할 때 Fine-tuning**을 검토한다.

```text
Prompt / Few-shot / RAG
→ Inference Context를 바꿈
→ 기본 Model Weight는 그대로

Fine-tuning
→ 추가 Training
→ 학습 대상 Parameter가 바뀜
```

선택 기준을 거칠게 잡으면 다음과 같다.

```text
규칙·역할을 지정          → Prompt / System Prompt
몇 개 예제로 Pattern 제시 → Few-shot
최신·사내 지식 공급       → RAG
반복 행동 자체 조정       → Fine-tuning
외부 세계에서 행동        → Tool / Agent
```

이 방법들은 배타적이지 않으며 한 시스템에서 함께 사용할 수 있다.

상세: `LLM-프롬프트와-Context-제어.md`, `Fine-tuning과-PEFT-LoRA.md`

## 6. RAG의 위치: 외부 지식을 Context에 넣는 방법

RAG의 핵심은 **필요한 외부 정보를 먼저 찾고, 검색된 원문을 LLM Context에 넣는 것**이다.

```text
[사전 준비]
문서
 ↓
Chunking
 ↓
검색용 Embedding
 ↓
Vector / 원문 / Metadata 저장

[질문 시]
질문
 ↓
Retrieval
 ↓
관련 Chunk
 ↓
질문 + 검색 원문
 ↓
LLM Context
 ↓
답변
```

여기서 Vector는 원문을 압축해 LLM에 전달하기 위한 것이 아니라 **관련 원문을 찾기 위한 검색 표현**이다.

Vector Search가 커지면 Exact Search 대신 ANN을 사용할 수 있고, HNSW와 IVF는 그 구현 선택지다. 이 정도의 위치만 개념지도에서 잡고, Chunk Vector 생성·Index·Re-ranking 등의 세부는 RAG 문서에서 본다.

상세: `임베딩-벡터검색-RAG.md`

## 7. Agent · Harness · MCP의 위치: LLM에 행동을 붙인다

일반 LLM 호출은 답변 생성으로 끝날 수 있지만 Agent는 Tool 실행 결과를 다시 관찰하며 반복한다.

```text
사용자 목표
 ↓
LLM 판단
 ↓
Tool 호출
 ↓
실제 Tool 실행
 ↓
결과 Observation
 ↓
Context에 반영
 ↓
LLM 재판단
 └──────── 반복
```

역할을 나누면 다음처럼 볼 수 있다.

```text
LLM
= 무엇을 할지 판단

Tool
= 파일 · Shell · DB · API 등 실제 능력

Agent
= LLM이 Tool과 Observation을 반복하며 목표 수행

Harness
= Agent를 둘러싼 Context · Rule · Skill · Hook · Workflow ·
  Tool/Permission · Orchestration 등의 운용 체계

MCP
= 외부 Tool · Resource 등을 발견하고 호출하는 공통 Protocol
```

개념적으로는 다음 관계가 중요하다.

```text
Harness
└─ Agent를 어떤 방식으로 굴릴지 구성
      ↓
    Agent Loop
      ↓
    Tool 사용
      ↓
MCP를 통해 Tool을 제공할 수도 있음
      ↓
실제 API / DB / File / 외부 System
```

MCP가 없어도 Agent가 API나 Tool을 직접 연동할 수 있다. MCP는 **Agent 자체도, Tool 자체도, RAG 자체도 아니다.**

상세: `에이전트와-MCP.md`, `Agent-Harness.md`

## 8. RAG와 MCP처럼 계층이 다른 개념을 구분한다

RAG와 MCP는 경쟁 기술이 아니다.

```text
Agent
 ↓
MCP
 ↓
search_metadata Tool
 ↓
Embedding / Retrieval
 ↓
Vector DB
 ↓
관련 Metadata 반환
 ↓
Agent
```

이 구조에서:

```text
RAG
= 관련 정보를 어떻게 찾고 Context에 공급할 것인가

MCP
= 그 기능을 Agent에게 어떤 공통 방식으로 제공할 것인가
```

즉 **한 Tool의 내부 구현이 RAG이고, 그 Tool을 MCP로 Agent에 노출하는 구조**도 가능하다.

상세: `에이전트와-MCP.md`

## 9. Text2SQL: AI 기술을 실제 업무 Task에 조합하는 예

Text2SQL은 LLM 자체가 아니라 **자연어를 SQL로 바꾸는 문제 영역(Task)**이다.

```text
Text2SQL
├─ Rule / Template 기반
├─ 전용 ML Model 기반
└─ LLM 기반
```

LLM 기반 Text2SQL에서 Schema가 커지면 지금까지 본 기술들이 하나의 시스템 안에서 조합될 수 있다.

```text
자연어 질문
 ↓
Metadata / Schema Retrieval
 ↓
관련 Schema 후보
 ↓
Schema Linking
 ↓
LLM Context 구성
 ↓
SQL Generation
 ↓
Validation / 실행
```

여기서도 층을 구분한다.

```text
Text2SQL      = 해결하려는 업무 Task
Schema Linking = 자연어와 DB 구조를 연결하는 문제
RAG/Retrieval = 필요한 Schema Context를 찾는 방법
LLM           = SQL을 생성하는 구현 수단 중 하나
Agent         = 검색·검증·재시도를 동적으로 반복하게 할 수 있는 실행 방식
```

상세: `Text2SQL과-스키마-링킹.md`

## 10. 전체 흐름 다시 보기

```text
AI
 ↓
생성형 AI / Foundation Model
 ↓
LLM
├─ 만드는 관점
│   └─ Training → Weight
│
└─ 사용하는 관점
    └─ Inference → Context → Token 생성
         │
         ├─ 지시·예제 → Prompt / Few-shot
         ├─ 외부 지식 → RAG
         ├─ 행동      → Tool / Agent / MCP
         └─ 행동 조정 → Fine-tuning은 별도 Training으로 Weight 조정

이 기술들을 실제 Task에 조합
 ↓
Text2SQL · Coding Agent · 업무 AI Service 등
```

가장 중요한 것은 모든 용어를 하나의 선형 계보로 외우지 않는 것이다.

> **새로운 AI 용어를 만나면 먼저 “이것은 Model 자체인가, Architecture인가, 생성 방식인가, Training 방식인가, Inference Context인가, Retrieval인가, 실행 연결인가, 업무 Task인가?”를 묻는다. 위치를 잡은 뒤 다른 축과 어떻게 조합되는지 연결한다.**
