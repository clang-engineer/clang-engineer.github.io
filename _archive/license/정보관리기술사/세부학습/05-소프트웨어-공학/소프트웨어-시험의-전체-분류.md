# 소프트웨어 시험의 전체 분류

## 왜 분류가 여러 개인가

소프트웨어 시험은 하나의 기준으로만 나뉘지 않는다. 실행 여부, 내부구조 사용 여부, 시험 단계, 확인하려는 목적이 서로 다른 분류 기준이다. 블랙박스·화이트박스와 정적·동적 시험을 같은 축으로 놓으면 혼동하기 쉽다.

## 1. 실행 여부

### 정적 시험

소프트웨어를 실행하지 않고 산출물과 코드를 확인한다.

- 리뷰: 산출물을 사람이 검토하는 넓은 활동
- 워크스루: 작성자가 내용을 설명하고 참여자가 결함과 개선점을 찾음
- 인스펙션: 역할·절차·체크리스트·기록이 정해진 공식 검토
- 정적 분석: 도구로 Coding Rule, Data Flow, 복잡도, 취약점 등을 분석

정적 시험은 요구·설계·코딩 단계에서 결함을 일찍 찾으므로 수정 비용을 줄인다. 실행 결과를 확인하지 않으므로 실제 성능·동작 결함은 별도 동적 시험이 필요하다.

### 동적 시험

실행 가능한 소프트웨어에 입력을 주고 실제 결과를 확인한다.

## 2. 시험 설계에서 내부구조 사용 여부

### 명세 기반 시험

요구사항과 입출력 명세를 기준으로 Test Case를 설계한다. 내부 코드를 몰라도 되므로 블랙박스 시험이라고도 한다.

- 동등분할
- 경계값 분석
- 결정표
- 상태전이
- Use Case 기반 시험

### 구조 기반 시험

코드의 Statement, Branch, Condition, Path 등 내부구조를 기준으로 Test Case를 설계한다. 화이트박스 시험이라고도 한다.

Coverage가 높아도 요구사항 누락과 결함 부재를 보장하지는 않는다. 실행하지 않은 구조를 찾는 지표로 사용한다.

### 경험 기반 시험

Tester의 지식과 과거 결함 경험을 사용한다.

- Error Guessing
- Exploratory Testing
- Checklist 기반 시험

따라서 화이트박스가 정적 시험인 것은 아니다. 코드를 보더라도 실제 실행 결과를 확인하면 동적·구조 기반 시험이다.

## 3. 시험 단계

- Unit Test: 함수·Class·Module 등 작은 단위 확인
- Integration Test: Module·Interface 결합 확인
- System Test: 전체 시스템이 기능·품질 요구를 만족하는지 확인
- Acceptance Test: 사용자·발주자 관점에서 업무 목적과 인수 조건 확인

시험 단계는 정적·동적 또는 블랙박스·화이트박스와 별개의 축이다. Unit Test에서도 명세 기반과 구조 기반 기법을 모두 사용할 수 있다.

## 4. 검증과 확인

- Verification: 명세와 설계대로 올바르게 만들고 있는가
- Validation: 사용자가 필요로 하는 제품을 만들었는가

Verification은 리뷰·정적 분석·시험 등 여러 활동에 적용된다. Validation은 완성된 제품이나 Increment가 실제 사용 목적에 맞는지 확인한다. 두 개념을 단순히 정적 대 동적으로 대응시키면 안 된다.

## 전체 관계

품질 목표와 요구사항
→ 정적 검토로 문서·설계·코드 결함 조기 발견
→ 동적 시험 수행
   ├─ 명세 기반
   ├─ 구조 기반
   └─ 경험 기반
→ Unit·Integration·System·Acceptance 단계별 확인
→ Verification·Validation 관점에서 증거 종합
→ 결함 원인과 프로세스 개선

## 기술사 답안 포인트

답안에서는 먼저 분류 축을 명시한다.

- 실행 여부: 정적·동적
- 설계 기준: 명세·구조·경험 기반
- 시험 수준: 단위·통합·시스템·인수
- 목적: Verification·Validation

각 축을 섞지 않고 관계를 그리면 대부분의 시험 비교 문제를 안정적으로 설명할 수 있다.
