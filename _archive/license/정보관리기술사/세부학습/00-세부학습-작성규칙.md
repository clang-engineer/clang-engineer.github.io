# 정보관리기술사 세부학습 작성 규칙

> 문체·용어·약어·한영 표기는 [문서 공통 문체·표기 원칙](../문서-공통-문체-표기원칙.md)을 따른다.

이 문서는 `_archive/license/정보관리기술사/세부학습/` 아래에 작성하는 세부학습 문서의 공통 기준이다.

세부학습 문서의 목적은 **시험 직전 암기용 요약본이 아니라, 학습 과정에서 이해한 내용을 나중에 다시 읽었을 때 그 이해가 복원되는 문서**를 만드는 것이다.

특히 모바일 GitHub 앱, Obsidian, Terminal, 일반 Markdown Viewer 등 여러 환경에서 읽는 것을 고려하여 **표준 Markdown과 Text/ASCII Diagram을 기본 표현 수단으로 사용한다.**

```text
학습지도 / 교재 / 기출
        ↓
무엇을 볼지와 중요도 결정
        ↓
세부학습 문서
        ↓
왜 그런가 · 어떻게 동작하는가
        ↓
개념 이해
        ↓
답안 정리 · 암기
```

---

# 1. 세부학습 문서의 역할

세부학습 문서는 다음 질문에 답할 수 있어야 한다.

```text
이 개념은 왜 필요한가?
무엇을 해결하는가?
내부적으로 어떻게 동작하는가?
앞뒤 개념과 어떤 관계인가?
비슷한 개념과 무엇이 다른가?
실제 시스템에서는 어디에 위치하는가?
내가 처음 배울 때 왜 헷갈렸는가?
```

단순 키워드 나열은 지양한다.

```text
RAG
- Embedding
- Vector DB
- LLM
```

대신 인과관계를 남긴다.

```text
LLM에 모든 사내 문서를 넣을 수 없음
        ↓
질문과 관련 있는 부분만 먼저 찾아야 함
        ↓
문서를 검색 가능한 Vector로 표현
        ↓
Vector Search로 관련 Chunk 검색
        ↓
검색된 원문을 LLM Context에 전달
        ↓
RAG
```

> **세부학습 문서는 키워드를 저장하는 곳이 아니라 키워드 사이의 연결을 저장하는 곳이다.**

---

# 2. 이해가 됐던 설명을 버리지 않는다

대화나 학습 과정에서 처음에는 이해되지 않던 개념이 특정 설명·비유·예제를 통해 이해됐다면 그 부분을 우선 보존한다.

예를 들어 다음 정의만 남기는 것은 부족할 수 있다.

```text
MCP는 AI Application과 Tool 간 표준 Protocol이다.
```

실제로 이해에 도움이 됐던 설명이 다음이라면 함께 남긴다.

```text
Agent가 외부 Tool을 사용하려면
- 어떤 Tool이 있는지
- 무슨 기능인지
- 어떤 Parameter가 필요한지
- 어떻게 호출하는지
알아야 한다.

MCP는 이 'Tool 지도와 사용법'을 공통 규격으로 제공한다.
```

즉 **대화에서 “아, 이제 이해됐다”가 나온 설명은 압축 과정에서 우선적으로 보존한다.**

---

# 3. 정의보다 `왜 → 어떻게 → 그래서`를 우선한다

```text
왜 필요한가
 ↓
어떤 문제가 있었는가
 ↓
어떻게 해결하는가
 ↓
내부적으로 어떻게 동작하는가
 ↓
그래서 어떤 장단점이 생기는가
 ↓
다른 개념과 어떻게 연결되는가
```

예를 들어 HNSW라면 다음 순서가 자연스럽다.

1. Vector 전수 비교가 왜 느린가
2. ANN이 왜 필요한가
3. HNSW는 어떤 아이디어로 탐색 범위를 줄이는가
4. 왜 빠르고 Recall이 높은가
5. 왜 Memory와 Index 구축 비용이 커지는가
6. IVF와 무엇이 다른가

# 4. 문서의 권장 기본 구조

모든 문서를 같은 Template으로 강제하지는 않지만 다음을 기본으로 한다.

```text
# 주제

이 문서에서 무엇을 이해하려는지 2~4문장

## 1. 왜 필요한가 / 가장 먼저 잡을 핵심

## 2. 전체 흐름

## 3. 핵심 구성요소 또는 내부 동작

## 4. 처음 헷갈리기 쉬운 부분

## 5. 유사 개념과 비교

## 6. 실제 적용 또는 예제

## 7. 장단점 · Trade-off · 운영 고려사항

## 8. 기억 흐름
```

주제에 따라 Section은 생략하거나 변경한다.

# 5. 큰 그림에서 세부로 내려간다

새로운 개념을 세부 용어부터 시작하지 않는다.

```text
[지양]
Q/K/V 정의
→ Scaled Dot Product
→ Multi-head
→ ...

[권장]
Transformer의 목적
→ Token Vector에 문맥 반영
→ 핵심 Mechanism인 Attention
→ Attention 계산을 위한 Q/K/V
```

기본 순서:

```text
전체 목적
 ↓
전체 처리 흐름
 ↓
핵심 Mechanism
 ↓
세부 구성요소
 ↓
Algorithm · Parameter
```

# 6. 처리 과정은 `입력 → 처리 → 출력`으로 표현한다

동작 원리를 설명할 수 있는 주제에서는 단계별 흐름을 적극 사용한다.

```text
사용자 질문
 ↓
Query Embedding
 ↓
Vector Search
 ↓
Re-ranking
 ↓
관련 Chunk
 ↓
LLM Context
 ↓
답변
```

각 단계가 **무엇을 입력받고 무엇을 출력하는지**가 보이도록 한다.

# 7. 비슷한 개념은 반드시 경계를 설명한다

예:

```text
LLM 내부 Embedding vs 검색용 Embedding
RAG vs Fine-tuning
Few-shot vs SFT
API vs MCP
RAG vs MCP
HNSW vs IVF
Verification vs Validation
```

가능하면 다음을 사용한다.

- 비교 Table
- 같은 흐름에서 위치 비교
- `A는 무엇 / B는 무엇` 설명
- Text 관계도

같은 단어를 사용하지만 역할이 다른 개념은 특히 명확히 구분한다.

```text
Model Weight
≠
Attention Weight
```

---

# 8. 분류축이 다른 개념을 억지로 한 줄에 세우지 않는다

예를 들어 다음은 기억하기 쉽지만 정확하지 않다.

```text
Fine-tuning → SFT → PEFT → LoRA
```

SFT와 PEFT는 분류 기준이 다르다.

```text
Fine-tuning
│
├─ [학습 신호 관점]
│   └─ SFT
│       └─ 입력-정답 Pair
│
└─ [Parameter 효율 관점]
    ├─ Full Fine-tuning
    └─ PEFT
        └─ LoRA
```

따라서 문서를 작성할 때 **상위/하위 관계인지, 비교 관계인지, 서로 다른 분류축인지 먼저 확인한다.**

# 9. 학습 중 실제로 생긴 질문을 문서에 반영한다

다음과 같은 질문은 삭제할 초보 질문이 아니라 개념의 경계를 정확하게 만드는 좋은 학습 자료다.

```text
"문장 조합은 무한한데 Embedding Model이 Vector를 어떻게 만들지?"

"MCP 없이도 API 직접 호출하면 되는 것 아닌가?"

"Serena가 Code Base 탐색하는데 왜 중간에 필요한가?"

"Text2SQL이 꼭 LLM을 사용해야 하나?"
```

문서에는 자연스럽게 Section으로 녹인다.

```text
## MCP가 없어도 Agent를 만들 수 있는가

가능하다. ...
```

# 10. 예제와 비유

추상적인 정의만으로 이해하기 어려우면 작은 예제를 적극 사용한다.

```text
"출장 가면 호텔값 얼마까지 나와?"
        ↓
Query Embedding
        ↓
"국내 출장 숙박비는 최대 10만원" Chunk 검색
```

비유는 실제 기술과 동일시하지 않는다.

```text
비유:
MCP는 Agent에게 Tool 지도를 주는 것과 비슷하다.

정확한 의미:
AI Client가 Tool·Resource 등을 발견하고 호출하기 위한 Protocol이다.
```

# 11. Diagram 작성 규칙: Text/ASCII가 기본

## 기본 원칙

> **어디서든 읽히는 Text/ASCII Diagram을 기본으로 하고 Mermaid는 선택적으로만 사용한다.**

GitHub 모바일 앱처럼 Mermaid Rendering이 제한되는 환경에서도 핵심 내용을 잃지 않아야 한다.

### 짧은 Pipeline

```text
질문
 ↓
Embedding
 ↓
Vector Search
 ↓
Chunk
 ↓
LLM
```

### 계층·분류

```text
Fine-tuning
├─ Full Fine-tuning
└─ PEFT
    └─ LoRA
```

### 반복 Loop

```text
LLM 판단
 ↓
Tool 실행
 ↓
결과 Observation
 ↓
LLM 재판단
 └──────── 반복
```

### Architecture 비교

```text
[일반 RAG]
질문 → 검색 → LLM → 답변

[Agentic RAG]
질문 → Agent 판단 → 검색 Tool
             ↑         ↓
             └── 결과 ─┘
                  ↓
               최종 답변
```

# 12. Mermaid는 언제 사용하는가

Mermaid 자체를 금지하지는 않는다. 다음 조건을 모두 만족할 때 선택적으로 사용한다.

- Branch나 관계가 복잡해 Text Diagram보다 확실히 이해하기 쉬움
- 해당 Viewer에서 Mermaid를 볼 수 없어도 본문만으로 내용을 이해할 수 있음
- 동일 내용을 ASCII와 Mermaid로 반복해서 문서를 불필요하게 늘리지 않음
- 시각화 자체가 학습 가치가 있음

즉 Mermaid는 **추가 시각화**이지 문서 이해를 위한 필수 의존성이 되어서는 안 된다.

### 사용을 지양하는 경우

- 단순 정의 하나를 그림으로 바꾼 경우
- `A → B → C` 정도의 짧은 흐름
- Mermaid가 Text보다 복잡한 경우
- 모바일에서 Diagram이 보이지 않으면 핵심 설명이 사라지는 경우

# 13. 기존 문서를 먼저 보강한다

새 파일을 만들기 전에 확인한다.

```text
기존 문서의 핵심 주제와 같은가?
→ YES: 기존 문서 보강

독립적으로 반복 복습할 가치가 있는 큰 개념인가?
→ YES: 별도 문서 고려
```

반대로 하나의 문서에 서로 독립적인 큰 개념을 억지로 몰아넣지도 않는다.

---

# 14. 개념지도와 상세 문서 역할을 분리한다

세부 문서가 많아지면 `00-...-개념지도.md` 같은 입구 문서를 둘 수 있다.

```text
00-개념지도
├─ 상세 문서 A
├─ 상세 문서 B
├─ 상세 문서 C
└─ 상세 문서 D
```

개념지도:
- 전체 관계
- 학습 순서
- 큰 Pipeline
- 주요 비교

상세 문서:
- 왜 필요한지
- 내부 동작
- 헷갈렸던 지점
- 예제
- Trade-off

개념지도에 상세 내용을 중복해서 모두 넣지 않는다.

---

# 15. 기술사 답안과 세부학습 문서를 동일하게 만들지 않는다

세부학습 문서는 **이해용**, 기술사 답안은 **제한된 시간에 구조화해 쓰는 출력용**이다.

```text
세부학습
왜? → 어떻게? → 비교 → 예제 → Trade-off
        ↓
       이해
        ↓
답안 작성
정의 → 구성/절차 → 특징 → 비교 → 고려사항
```

세부학습을 답안 분량으로 억지로 압축하지 않는다.

---

# 16. 출처와 근거 사용 규칙

특정 교재·학습지도·기출문제를 기반으로 작성하는 경우 **원자료의 구조와 범위를 먼저 존중한다.**

### Source 기반 내용

자료가 직접 설명하는 내용은 해당 자료의 용어와 분류를 우선한다.

### 이해 보강 설명

자료를 이해하기 위해 추가한 비유, 작은 예제, 연결 설명, 일반 구현 예는 학습 보조 설명으로 사용한다.

### 외부 확장

최신 동향, 제품 구현, 추가 Algorithm처럼 원자료 밖의 내용은 확장 내용임을 구분한다.

원자료와 외부 지식이 충돌할 때 조용히 원자료를 고쳐 쓰지 않는다.

# 17. 용어 정확성을 유지한다

이해하기 쉽게 쓰되 기술적 경계를 무너뜨리지 않는다.

예:

```text
X: Embedding = Vector

O: Embedding은 Vector 표현을 만드는 개념이며,
   결과 Vector 자체도 실무에서 Embedding이라고 부르기도 한다.
```

```text
X: MCP = API

O: MCP Server 내부에서 기존 API를 사용할 수 있지만,
   MCP는 AI Client와 Tool·Resource 사이의 발견·호출 규격이다.
```

쉽게 설명한 뒤 정확한 정의로 다시 연결한다.

---

# 18. 상세함과 중복을 구분한다

상세하게 쓴다는 것은 같은 정의를 여러 번 반복한다는 뜻이 아니다.

좋은 상세화:

```text
정의
→ 왜 필요한가
→ 동작 과정
→ 예제
→ 헷갈리는 개념과 비교
→ Trade-off
```

나쁜 상세화:

```text
같은 정의
→ 표현만 바꿔 다시 설명
→ 다시 요약
→ 같은 Diagram 반복
```

# 20. 한 문장 원칙

> **세부학습 문서는 시험 키워드를 압축해 저장하는 문서가 아니라, 내가 한 번 이해한 개념을 미래의 내가 다시 이해할 수 있도록 사고의 연결을 보존하는 문서다.**
