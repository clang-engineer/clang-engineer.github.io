# 정보관리기술사 세부학습 작성 규칙

> 문체·용어·약어·한영 표기는 [문서 공통 문체·표기 원칙](../문서-공통-문체-표기원칙.md)을 따른다.

이 문서는 `_archive/license/정보관리기술사/세부학습/` 아래에 작성하는 세부학습 문서의 공통 기준이다.

세부학습 문서의 목적은 **시험 직전 암기용 요약본이 아니라, 학습 과정에서 이해한 내용을 나중에 다시 읽었을 때 그 이해가 복원되는 문서**를 만드는 것이다.

특히 모바일 GitHub 앱, Obsidian, Terminal, 일반 Markdown Viewer 등 여러 환경에서 읽는 것을 고려하여 **표준 Markdown과 Text/ASCII Diagram을 기본 표현 수단으로 사용한다.**

```text
학습지도 / 교재 / 기출
        ↓
무엇을 볼지와 중요도 결정
        ↓
세부학습 문서
        ↓
왜 그런가 · 어떻게 동작하는가
        ↓
개념 이해
        ↓
답안 정리 · 암기
```

---

# 1. 세부학습 문서의 역할

세부학습 문서는 다음 질문에 답할 수 있어야 한다.

```text
이 개념은 왜 필요한가?
무엇을 해결하는가?
내부적으로 어떻게 동작하는가?
앞뒤 개념과 어떤 관계인가?
비슷한 개념과 무엇이 다른가?
실제 시스템에서는 어디에 위치하는가?
내가 처음 배울 때 왜 헷갈렸는가?
```

단순 키워드 나열은 지양한다.

```text
RAG
- Embedding
- Vector DB
- LLM
```

대신 개념 사이의 관계를 남긴다.

```text
LLM에 모든 사내 문서를 넣을 수 없음
        ↓
질문과 관련 있는 부분만 먼저 찾아야 함
        ↓
문서를 검색 가능한 Vector로 표현
        ↓
Vector Search로 관련 Chunk 검색
        ↓
검색된 원문을 LLM Context에 전달
        ↓
RAG
```

> **세부학습 문서는 키워드를 저장하는 곳이 아니라 키워드 사이의 연결을 저장하는 곳이다.**

---

# 2. 이해가 됐던 설명을 버리지 않는다

대화나 학습 과정에서 처음에는 이해되지 않던 개념이 특정 설명·비유·예제를 통해 이해됐다면 그 부분을 우선 보존한다.

예를 들어 다음 정의만 남기는 것은 부족할 수 있다.

```text
MCP는 AI Application과 Tool 간 표준 Protocol이다.
```

실제로 이해에 도움이 됐던 설명이 다음이라면 함께 남긴다.

```text
Agent가 외부 Tool을 사용하려면
- 어떤 Tool이 있는지
- 무슨 기능인지
- 어떤 Parameter가 필요한지
- 어떻게 호출하는지
알아야 한다.

MCP는 이 'Tool 지도와 사용법'을 공통 규격으로 제공한다.
```

즉 **대화에서 “아, 이제 이해됐다”가 나온 설명은 압축 과정에서 우선적으로 보존한다.**

# 3. 정의보다 `왜 → 어떻게 → 그래서`를 우선한다

인과관계가 실제로 존재하는 주제에서는 다음 흐름을 우선한다.

```text
왜 필요한가
 ↓
어떤 문제가 있었는가
 ↓
어떻게 해결하는가
 ↓
내부적으로 어떻게 동작하는가
 ↓
그래서 어떤 장단점이 생기는가
 ↓
다른 개념과 어떻게 연결되는가
```

특히 여러 개념이 하나의 문제 해결 과정으로 이어진다면 다음과 같은 **문제 → 해결 → 새 문제 → 다음 해결**의 연쇄를 적극적으로 살린다.

```text
문제 A
 ↓
개념 A로 해결
 ↓
그 결과 드러나는 한계 / 새 문제 B
 ↓
개념 B 필요
 ↓
개념 B로 해결
 ↓
새 문제 C
 ↓
...
```

예를 들어 Transaction 동시성은 다음처럼 자연스럽게 이어진다.

```text
동시 Transaction
      ↓
동시성 이상 현상
      ↓
Isolation Level
= 어디까지 격리할 것인가
      ↓
Concurrency Control
= 그 보장을 어떻게 구현할 것인가
      ↓
Lock / MVCC
```

HNSW라면 다음 순서가 자연스럽다.

1. Vector 전수 비교가 왜 느린가
2. ANN이 왜 필요한가
3. HNSW는 어떤 아이디어로 탐색 범위를 줄이는가
4. 왜 빠르고 Recall이 높은가
5. 왜 Memory와 Index 구축 비용이 커지는가
6. IVF와 무엇이 다른가

단, **실제 인과관계가 없는 개념에 이 형식을 억지로 적용하지 않는다.** 이에 대한 기준은 뒤의 `관계 구조를 먼저 선택한다` 원칙을 따른다.

# 4. 문서의 권장 기본 구조

모든 문서를 같은 Template으로 강제하지는 않지만 다음을 기본으로 한다.

```text
# 주제

이 문서에서 무엇을 이해하려는지 2~4문장

## 1. 왜 필요한가 / 가장 먼저 잡을 핵심

## 2. 전체 흐름 또는 전체 관계

## 3. 핵심 구성요소 또는 내부 동작

## 4. 처음 헷갈리기 쉬운 부분

## 5. 유사 개념과 비교

## 6. 실제 적용 또는 예제

## 7. 장단점 · Trade-off · 운영 고려사항

## 8. 기억 흐름
```

주제에 따라 Section은 생략하거나 변경한다.

# 5. 큰 그림에서 세부로 내려간다

새로운 개념을 세부 용어부터 시작하지 않는다.

```text
[지양]
Q/K/V 정의
→ Scaled Dot Product
→ Multi-head
→ ...

[권장]
Transformer의 목적
→ Token Vector에 문맥 반영
→ 핵심 Mechanism인 Attention
→ Attention 계산을 위한 Q/K/V
```

기본 순서:

```text
전체 목적
 ↓
전체 처리 흐름 / 관계
 ↓
핵심 Mechanism
 ↓
세부 구성요소
 ↓
Algorithm · Parameter
```

# 6. 처리 과정은 `입력 → 처리 → 출력`으로 표현한다

동작 원리를 설명할 수 있는 주제에서는 단계별 흐름을 적극 사용한다.

```text
사용자 질문
 ↓
Query Embedding
 ↓
Vector Search
 ↓
Re-ranking
 ↓
관련 Chunk
 ↓
LLM Context
 ↓
답변
```

각 단계가 **무엇을 입력받고 무엇을 출력하는지**가 보이도록 한다.

# 7. 비슷한 개념은 반드시 경계를 설명한다

예:

```text
LLM 내부 Embedding vs 검색용 Embedding
RAG vs Fine-tuning
Few-shot vs SFT
API vs MCP
RAG vs MCP
HNSW vs IVF
Verification vs Validation
```

가능하면 다음을 사용한다.

- 비교 Table
- 같은 흐름에서 위치 비교
- `A는 무엇 / B는 무엇` 설명
- Text 관계도

같은 단어를 사용하지만 역할이 다른 개념은 특히 명확히 구분한다.

```text
Model Weight
≠
Attention Weight
```

# 8. 분류축이 다른 개념을 억지로 한 줄에 세우지 않는다

예를 들어 다음은 기억하기 쉽지만 정확하지 않다.

```text
Fine-tuning → SFT → PEFT → LoRA
```

SFT와 PEFT는 분류 기준이 다르다.

```text
Fine-tuning
│
├─ [학습 신호 관점]
│   └─ SFT
│       └─ 입력-정답 Pair
│
└─ [Parameter 효율 관점]
    ├─ Full Fine-tuning
    └─ PEFT
        └─ LoRA
```

마찬가지로 다음처럼 쓰지 않는다.

```text
CNN → RNN → GAN → Transformer   X
```

CNN·RNN·Transformer는 주로 Network Architecture 관점이고, GAN은 생성·학습 구조 관점이므로 같은 축의 발전 단계가 아니다.

따라서 문서를 작성할 때 **상위/하위 관계인지, 비교 관계인지, 서로 다른 분류축인지 먼저 확인한다.**


# 12. Mermaid는 언제 사용하는가

Mermaid 자체를 금지하지는 않는다. 다음 조건을 모두 만족할 때 선택적으로 사용한다.

- Branch나 관계가 복잡해 Text Diagram보다 확실히 이해하기 쉬움
- 해당 Viewer에서 Mermaid를 볼 수 없어도 본문만으로 내용을 이해할 수 있음
- 동일 내용을 ASCII와 Mermaid로 반복해서 문서를 불필요하게 늘리지 않음
- 시각화 자체가 학습 가치가 있음

즉 Mermaid는 **추가 시각화**이지 문서 이해를 위한 필수 의존성이 되어서는 안 된다.

### 사용을 지양하는 경우

- 단순 정의 하나를 그림으로 바꾼 경우
- `A → B → C` 정도의 짧은 흐름
- Mermaid가 Text보다 복잡한 경우
- 모바일에서 Diagram이 보이지 않으면 핵심 설명이 사라지는 경우

# 13. 기존 문서를 먼저 보강한다

새 파일을 만들기 전에 확인한다.

```text
기존 문서의 핵심 주제와 같은가?
→ YES: 기존 문서 보강

독립적으로 반복 복습할 가치가 있는 큰 개념인가?

```

반대로 하나의 문서에 서로 독립적인 큰 개념을 억지로 몰아넣지도 않는다.

# 14. 문서 경계와 통합·분리 원칙

세부학습 문서의 파일 단위를 개별 키워드 수로 결정하지 않는다. **한 번에 이해해야 하는 개념 흐름**을 기본 문서 경계로 삼는다.

```text
[키워드 중심 — 지양]
A.md
B.md
C.md

[이해 흐름 중심 — 권장]
A가 왜 필요한가
      ↓
A를 적용하면 B라는 문제가 생김
      ↓
B를 해결하기 위해 C가 필요

→ A → B → C가 하나의 이해 흐름이면 통합 후보
```

### 통합을 우선하는 경우

다음 조건이 강할수록 하나의 문서로 통합한다.

1. **인과 연결성**: 앞 개념이 뒤 개념의 필요성을 직접 만든다.
2. **동시 이해 필요성**: 한 개념을 제대로 이해하려면 다른 개념을 함께 봐야 한다.
3. **반복 왕복 여부**: 별도 문서를 읽을 때 앞 문서를 계속 다시 열어야 이해된다.
4. **하나의 핵심 질문**: 여러 개념이 결국 같은 질문을 단계적으로 풀고 있다.

예:

```text
동시 Transaction
→ Conflict
→ 이상 현상
→ Isolation Level
→ Lock / MVCC
→ S/X · Row/Range · 2PL

→ "Transaction 동시성을 어떻게 안전하게 제어하는가?"라는
   하나의 이해 흐름으로 묶을 수 있음
```

### 분리를 우선하는 경우

다음 조건이 강할수록 별도 문서로 분리한다.

1. **독립 답안성**: 정보관리기술사에서 별도 주제로 충분한 구조를 갖고 서술할 수 있다.
2. **독립 학습성**: 앞 문서에서는 존재와 연결점만 알면 되고, 이후 내용은 독립적으로 이해할 수 있다.
3. **깊이 차이**: 구현체·제품·Algorithm 상세로 내려가면서 원래 문서의 학습 깊이를 크게 벗어난다.
4. **본선 흐름 방해**: 해당 내용을 포함하면 핵심 인과 흐름이 끊기거나 문서가 여러 독립 줄기로 갈라진다.

```text
A 핵심 흐름
   │
   └─ B와 연결됨
       ↓
     B 내부 구조
     B 구현 상세
     B 운영 이슈

→ A에서는 B의 존재와 연결점까지만 설명
→ B의 독립 흐름은 별도 문서
```

예를 들어 MVCC를 이해하면서 PostgreSQL `VACUUM`의 존재 이유까지 연결할 수 있지만, VACUUM의 상세 동작은 PostgreSQL 구현 주제로 별도 분리할 수 있다.

### 통합·분리 판단 질문

```text
Q1. 앞 개념이 뒤 개념의 필요성을 만드는가?
 ├─ YES → 통합 쪽
 └─ NO  → Q2

Q2. 분리했을 때 앞 문서를 계속 왕복해야 이해되는가?
 ├─ YES → 통합 쪽
 └─ NO  → Q3

Q3. 뒤 개념만으로 독립적인 학습 흐름이나 답안 구조가 생기는가?
 ├─ YES → 분리 쪽
 └─ NO  → 통합 쪽

Q4. 합쳤을 때 본선보다 가지 설명이 더 커지는가?
 ├─ YES → 가지를 분리
 └─ NO  → 통합 유지
```

> **토픽 하나 = 파일 하나가 아니라, 한 번에 이해해야 하는 개념 사슬 = 문서 하나를 기본으로 한다.**

통합은 문서 수를 줄이는 것이 목적이 아니다. **앞 개념에서 생긴 질문이 뒤 개념으로 자연스럽게 이어지는 사고 흐름을 보존하는 것**이 목적이다.

# 15. 개념지도와 상세 문서 역할을 분리한다

세부 문서가 많아지면 `00-...-개념지도.md` 같은 입구 문서를 둘 수 있다.

```text
00-개념지도
├─ 상세 문서 A
├─ 상세 문서 B
├─ 상세 문서 C
└─ 상세 문서 D
```

개념지도:
- 전체 관계
- 학습 순서
- 큰 Pipeline
- 주요 비교

상세 문서:
- 왜 필요한지
- 내부 동작
- 헷갈렸던 지점
- 예제
- Trade-off

개념지도에 상세 내용을 중복해서 모두 넣지 않는다.

---

# 16. 기술사 답안과 세부학습 문서를 동일하게 만들지 않는다

세부학습 문서는 **이해용**, 기술사 답안은 **제한된 시간에 구조화해 쓰는 출력용**이다.

```text
세부학습
왜? → 어떻게? → 비교 → 예제 → Trade-off
        ↓
       이해
        ↓
답안 작성
정의 → 구성/절차 → 특징 → 비교 → 고려사항
```

세부학습을 답안 분량에 맞춰 과도하게 압축하지 않는다. 반대로 세부학습 문서의 모든 내용을 실제 답안에 그대로 넣으려 하지 않는다.

> **세부학습은 이해를 복원하기 위한 입력 자료이고, 답안은 그 이해를 시험 형식에 맞게 압축한 출력물이다.**

---

# 17. 먼저 `관계 구조`를 선택하고, 그에 맞는 흐름을 만든다

세부학습은 흐름을 중시하지만 **모든 개념을 하나의 인과 사슬로 만들지는 않는다.**

먼저 해당 주제에서 개념들이 실제로 어떤 관계인지 판단한다.

```text
① 인과형
문제 → 해결 → 한계 → 다음 해결

② 처리형
입력 → 처리 → 출력

③ 분류·좌표형
상위 개념 → 분류축 → 하위 개념

④ 연결·Bridge형
독립된 개념 A ↔ 만나는 지점 ↔ 독립된 개념 B

⑤ 비교형
같은 문제를 푸는 A / B의 차이와 Trade-off
```

### 17.1 인과형

앞 개념의 문제나 한계가 다음 개념을 직접 필요하게 만드는 경우다.

```text
동시 Transaction
→ 이상 현상
→ Isolation Level
→ Concurrency Control
→ Lock / MVCC
```

이 경우에는 **문제 → 해결 → 새 문제 → 다음 해결** 흐름을 적극적으로 사용한다.

### 17.2 처리형

동작 과정 자체가 핵심인 경우다.

```text
질문
→ Embedding
→ Vector Search
→ 관련 Chunk
→ LLM Context
→ 답변
```

이 경우 각 단계의 입력과 출력이 보이게 한다.

### 17.3 분류·좌표형

서로 다른 종류의 개념을 비교하거나 전체 위치를 잡아야 하는 경우다.

```text
Deep Learning Architecture
├─ CNN
├─ RNN
└─ Transformer

생성 방식
├─ Autoregressive
├─ GAN
└─ Diffusion
```

이 관계를 억지로 다음처럼 만들지 않는다.

```text
CNN → RNN → GAN → Transformer   X
```

**화살표는 인과관계나 처리 순서가 실제로 있을 때만 사용한다.**

### 17.4 연결·Bridge형

두 개념이 관련은 깊지만 서로 다른 Layer, 제어 주체, 분류축에 속해 독립 문서로 유지하는 것이 좋은 경우다.

```text
VLAN
= L2에서 Broadcast Domain 경계를 만듦
        ↓ 연결 지점
다른 VLAN 간 통신에는 L3 Routing 필요
        ↓
Subnet
= L3에서 IP Network 경계를 정의
```

이때 `VLAN = Subnet`처럼 합치지 않고 **어디에서 만나며 무엇이 다른지**를 설명한다.

### 17.5 비교형

같은 문제를 서로 다른 방식으로 해결하는 기술은 공통 기준을 먼저 잡고 비교한다.

```text
HNSW vs IVF
Lock vs MVCC
RAG vs Fine-tuning
```

단순 특징 나열보다 다음을 우선한다.

```text
무엇을 해결하는가
→ 접근 방식은 무엇인가
→ 어떤 상황에서 강한가
→ 어떤 비용을 치르는가
```

> **흐름을 만든다는 것은 모든 개념을 화살표로 잇는 것이 아니다. 실제 관계를 찾아 그 관계를 따라 학습할 수 있게 만드는 것이다.**

---

# 18. 문서를 분리했다면 Bridge를 남긴다

관련 개념을 독립 문서로 분리해도 학습 흐름까지 끊어서는 안 된다.

다음 중 하나 이상을 각 문서에 남긴다.

```text
A는 무엇을 설명하는가?
B는 무엇을 설명하는가?
A의 결과가 어디에서 B와 만나는가?
둘을 혼동하면 안 되는 경계는 무엇인가?
다음에 어느 문서를 읽으면 자연스러운가?
```

예를 들어 VLAN과 IP/Subnet은 다음처럼 연결한다.

```text
[VLAN 문서]
L2에서 왜 망을 나누는가?
→ Broadcast Domain
→ VLAN
→ 다른 VLAN 간에는 L3 Routing 필요
             ↓
          연결 지점
             ↓
[IP 문서]
L3에서는 같은 Network인지 어떻게 판단하는가?
→ IP + Prefix
→ Subnet
→ CIDR / VLSM
```

TCP 혼잡제어와 QoS도 같은 `혼잡`이라는 단어를 쓰지만 제어 주체가 다르다는 Bridge를 둔다.

```text
TCP Congestion Control
= End Host가 "내가 얼마나 보낼까?" 조절

QoS
= Network 장비가 "누구를 먼저 / 얼마나 보낼까?" 조절
```

즉 문서를 분리하는 것은 **학습 관계를 끊는 것**이 아니라 **문서의 책임 범위를 나누는 것**이다.

> **문서 내부에서는 실제 관계에 맞는 흐름을 만들고, 문서 사이에서는 Bridge로 흐름을 이어간다.**
