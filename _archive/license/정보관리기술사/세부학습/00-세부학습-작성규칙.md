# 정보관리기술사 세부학습 작성 규칙

> 문체·용어·약어·한영 표기는 [문서 공통 문체·표기 원칙](../문서-공통-문체-표기원칙.md)을 따른다.

이 문서는 `_archive/license/정보관리기술사/세부학습/` 아래에 작성하는 세부학습 문서의 공통 기준이다.

세부학습 문서의 목적은 **시험 직전 암기용 요약본이 아니라, 학습 과정에서 이해한 내용을 나중에 다시 읽었을 때 그 이해가 복원되는 문서**를 만드는 것이다.

## 상위 학습 자료와의 역할 분리

정보관리기술사 학습 자료는 다음 세 역할을 구분한다.

```text
학습등급표
= 교재·기출·공식 출제기준을 바탕으로
  무엇을 얼마나 우선해서 공부할지 정한다.
  A/B/C, 회독 우선순위, 범위 판단을 담당한다.

        ↓ 학습할 Topic 공급

학습지도
= Topic을 상위·하위·인접·비교·의존 관계로 재배치한다.
  하나의 개념을 잡고 주변 개념으로 파고들 수 있게 한다.
  단순 목차나 완벽한 분류체계보다 '다음에 무엇을 공부할지'를 찾는 것이 목적이다.

        ↓ 학습할 꼭지 선택

세부학습
= 선택한 꼭지를 깊게 이해한다.
  왜 필요한가, 어떻게 동작하는가, 무엇과 다른가,
  실제 시스템에서 어디에 위치하는가를 복원할 수 있게 기록한다.
```

학습지도의 Node와 세부학습 파일은 1:1일 필요가 없다. 예를 들어 `RAG → Vector Search → ANN → HNSW / IVF`가 학습지도에 모두 보이더라도 HNSW와 IVF를 각각 별도 파일로 만들 필요는 없다. 하나의 이해 흐름이면 `임베딩-벡터검색-RAG.md` 안에서 함께 다룰 수 있다.

학습지도는 세부 내용을 설명하는 교재가 아니다. 다만 **학습할 가치가 있는 하위 꼭지는 삭제하지 않는다.** Algorithm 내부 계산, Parameter 상세, 긴 예제는 세부학습으로 내리되 `어떤 개념 아래에 있고 무엇과 연결되는가`는 지도에 남긴다.

세부학습 문서에서 내용을 덜어내거나 다른 문서로 이동할 때는 동일 내용이 다른 적절한 세부학습 문서에 충분히 보존되어 있는지 먼저 확인한다. 없다면 먼저 해당 세부학습 문서를 보강한 뒤 중복을 정리한다.

---

# 1. 세부학습 문서의 역할

세부학습 문서는 다음 질문에 답할 수 있어야 한다.

```text
이 개념은 전체 주제에서 어디에 위치하는가?
주변 개념과 어떤 관계인가?
이 개념은 왜 필요한가?
무엇을 해결하는가?
내부적으로 어떻게 동작하는가?
비슷한 개념과 무엇이 다른가?
실제 시스템에서는 어디에 위치하는가?
내가 처음 배울 때 왜 헷갈렸는가?
```

단순 키워드 나열은 지양한다.

> **세부학습 문서는 키워드를 저장하는 곳이 아니라 키워드 사이의 연결을 저장하는 곳이다.**

---

# 2. 이해가 됐던 설명을 버리지 않는다

대화나 학습 과정에서 처음에는 이해되지 않던 개념이 특정 설명·비유·예제를 통해 이해됐다면 그 부분을 우선 보존한다.

즉 **대화에서 “아, 이제 이해됐다”가 나온 설명은 압축 과정에서 우선적으로 보존한다.**

---

# 3. 정의보다 `왜 → 어떻게 → 그래서`를 우선한다

인과관계가 실제로 존재하는 주제에서는 다음 흐름을 우선한다.

```text
왜 필요한가
 ↓
어떤 문제가 있었는가
 ↓
어떻게 해결하는가
 ↓
내부적으로 어떻게 동작하는가
 ↓
그래서 어떤 장단점이 생기는가
 ↓
다른 개념과 어떻게 연결되는가
```

실제 인과관계가 없는 개념에 이 형식을 억지로 적용하지 않는다.

---

# 4. 문서의 권장 기본 구조

모든 문서를 같은 Template으로 강제하지는 않지만 다음을 기본으로 한다.

```text
# 주제

이 문서에서 무엇을 이해하려는지 2~4문장

## 1. 가장 먼저 잡을 큰 그림 / 현재 위치 / 핵심
## 2. 전체 흐름 또는 전체 관계
## 3. 왜 필요한가 / 해결하려는 문제
## 4. 핵심 구성요소 또는 내부 동작
## 5. 처음 헷갈리기 쉬운 부분
## 6. 유사 개념과 비교·경계
## 7. 실제 적용 또는 예제
## 8. 장단점 · Trade-off · 운영 고려사항
## 9. 기억 흐름
```

주제에 따라 Section은 생략하거나 변경한다. 핵심은 **세부로 들어가기 전에 독자가 현재 개념의 좌표를 잃지 않게 하는 것**이다.

---

# 5. 큰 그림 → 현재 위치 → 관계 → 세부로 내려간다

```text
큰 그림
 ↓
현재 개념의 위치
 ↓
주변 개념과의 관계·경계
 ↓
왜 필요한가
 ↓
전체 처리 흐름 / Mechanism
 ↓
세부 구성요소
 ↓
Algorithm · Parameter
```

큰 그림을 보여준다는 이유로 관련 없는 주변 지식을 과도하게 확장하지 않는다.

---

# 6. 처리 과정은 `입력 → 처리 → 출력`으로 표현한다

동작 원리를 설명할 수 있는 주제에서는 단계별 흐름을 적극 사용한다.

각 단계가 **무엇을 입력받고 무엇을 출력하는지**가 보이도록 한다.

---

# 7. 비슷한 개념은 반드시 경계를 설명한다

예:

```text
LLM 내부 Embedding vs 검색용 Embedding
RAG vs Fine-tuning
Few-shot vs SFT
API vs MCP
RAG vs MCP
HNSW vs IVF
Verification vs Validation
```

같은 단어를 사용하지만 역할이 다른 개념은 특히 명확히 구분한다.

---

# 8. 분류축이 다른 개념을 억지로 한 줄에 세우지 않는다

상위/하위 관계인지, 비교 관계인지, 서로 다른 분류축인지 먼저 확인한다.

```text
Fine-tuning
│
├─ [학습 신호 관점]
│   └─ SFT
└─ [Parameter 효율 관점]
    ├─ Full Fine-tuning
    └─ PEFT
        └─ LoRA
```

`CNN → RNN → GAN → Transformer`처럼 서로 다른 축을 하나의 발전 단계로 만들지 않는다.

---

# 9. 학습 중 실제로 생긴 질문을 문서에 반영한다

학습 중 생긴 질문은 개념의 경계를 정확하게 만드는 좋은 자료다. 자연스러운 Section으로 녹여 보존한다.

---

# 10. 예제와 비유

추상적인 정의만으로 이해하기 어려우면 작은 예제를 적극 사용한다. 비유는 실제 기술과 동일시하지 않는다.

---

# 11. Diagram 작성 규칙: Text/ASCII가 기본

> **어디서든 읽히는 Text/ASCII Diagram을 기본으로 하고 Mermaid는 선택적으로만 사용한다.**

짧은 Pipeline, 계층·분류, 반복 Loop, Architecture 비교는 우선 Text Diagram으로 표현한다.

---

# 12. Mermaid는 언제 사용하는가

Branch나 관계가 복잡해 Text Diagram보다 확실히 이해하기 쉽고, Mermaid가 보이지 않아도 본문만으로 이해할 수 있을 때 선택적으로 사용한다.

---

# 13. 기존 문서를 먼저 보강한다

새 파일을 만들기 전에 기존 문서의 핵심 주제와 같은지 확인한다. 같은 이해 흐름이면 기존 문서를 보강한다.

---

# 14. 문서 경계와 통합·분리 원칙

세부학습 문서의 파일 단위를 개별 키워드 수로 결정하지 않는다. **한 번에 이해해야 하는 개념 흐름**을 기본 문서 경계로 삼는다.

통합은 인과 연결성, 동시 이해 필요성, 반복 왕복 여부, 하나의 핵심 질문을 기준으로 판단한다. 독립 답안성, 독립 학습성, 깊이 차이, 본선 흐름 방해가 크면 분리를 우선한다.
