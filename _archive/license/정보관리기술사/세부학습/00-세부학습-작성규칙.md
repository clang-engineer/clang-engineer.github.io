# 정보관리기술사 세부학습 작성 규칙

> 문체·용어·약어·한영 표기는 [문서 공통 문체·표기 원칙](../문서-공통-문체-표기원칙.md)을 따른다.

이 문서는 `_archive/license/정보관리기술사/세부학습/` 아래에 작성하는 세부학습 문서의 공통 기준이다.

세부학습 문서의 목적은 **시험 직전 암기용 요약본이 아니라, 학습 과정에서 이해한 내용을 나중에 다시 읽었을 때 그 이해가 복원되는 문서**를 만드는 것이다.

특히 모바일 GitHub 앱, Obsidian, Terminal, 일반 Markdown Viewer 등 여러 환경에서 읽는 것을 고려하여 **표준 Markdown과 Text/ASCII Diagram을 기본 표현 수단으로 사용한다.**

```text
학습지도 / 교재 / 기출
        ↓
무엇을 볼지와 중요도 결정
        ↓
세부학습 문서
        ↓
큰 그림에서 현재 위치 확인
        ↓
주변 개념과 관계·경계 파악
        ↓
왜 그런가 · 어떻게 동작하는가
        ↓
개념 이해
        ↓
답안 정리 · 암기
```

---

# 1. 세부학습 문서의 역할

세부학습 문서는 다음 질문에 답할 수 있어야 한다.

```text
이 개념은 전체 주제에서 어디에 위치하는가?
주변 개념과 어떤 관계인가?
이 개념은 왜 필요한가?
무엇을 해결하는가?
내부적으로 어떻게 동작하는가?
비슷한 개념과 무엇이 다른가?
실제 시스템에서는 어디에 위치하는가?
내가 처음 배울 때 왜 헷갈렸는가?
```

단순 키워드 나열은 지양한다.

```text
RAG
- Embedding
- Vector DB
- LLM
```

대신 개념 사이의 관계를 남긴다.

```text
LLM에 모든 사내 문서를 넣을 수 없음
        ↓
질문과 관련 있는 부분만 먼저 찾아야 함
        ↓
문서를 검색 가능한 Vector로 표현
        ↓
Vector Search로 관련 Chunk 검색
        ↓
검색된 원문을 LLM Context에 전달
        ↓
RAG
```

> **세부학습 문서는 키워드를 저장하는 곳이 아니라 키워드 사이의 연결을 저장하는 곳이다.**

---

# 2. 이해가 됐던 설명을 버리지 않는다

대화나 학습 과정에서 처음에는 이해되지 않던 개념이 특정 설명·비유·예제를 통해 이해됐다면 그 부분을 우선 보존한다.

예를 들어 다음 정의만 남기는 것은 부족할 수 있다.

```text
MCP는 AI Application과 Tool 간 표준 Protocol이다.
```

실제로 이해에 도움이 됐던 설명이 다음이라면 함께 남긴다.

```text
Agent가 외부 Tool을 사용하려면
- 어떤 Tool이 있는지
- 무슨 기능인지
- 어떤 Parameter가 필요한지
- 어떻게 호출하는지
알아야 한다.

MCP는 이 'Tool 지도와 사용법'을 공통 규격으로 제공한다.
```

즉 **대화에서 “아, 이제 이해됐다”가 나온 설명은 압축 과정에서 우선적으로 보존한다.**

# 3. 정의보다 `왜 → 어떻게 → 그래서`를 우선한다

인과관계가 실제로 존재하는 주제에서는 다음 흐름을 우선한다.

```text
왜 필요한가
 ↓
어떤 문제가 있었는가
 ↓
어떻게 해결하는가
 ↓
내부적으로 어떻게 동작하는가
 ↓
그래서 어떤 장단점이 생기는가
 ↓
다른 개념과 어떻게 연결되는가
```

특히 여러 개념이 하나의 문제 해결 과정으로 이어진다면 다음과 같은 **문제 → 해결 → 새 문제 → 다음 해결**의 연쇄를 적극적으로 살린다.

```text
문제 A
 ↓
개념 A로 해결
 ↓
그 결과 드러나는 한계 / 새 문제 B
 ↓
개념 B 필요
 ↓
개념 B로 해결
 ↓
새 문제 C
 ↓
...
```

예를 들어 Transaction 동시성은 다음처럼 자연스럽게 이어진다.

```text
동시 Transaction
      ↓
동시성 이상 현상
      ↓
Isolation Level
= 어디까지 격리할 것인가
      ↓
Concurrency Control
= 그 보장을 어떻게 구현할 것인가
      ↓
Lock / MVCC
```

HNSW라면 다음 순서가 자연스럽다.

1. Vector 전수 비교가 왜 느린가
2. ANN이 왜 필요한가
3. HNSW는 어떤 아이디어로 탐색 범위를 줄이는가
4. 왜 빠르고 Recall이 높은가
5. 왜 Memory와 Index 구축 비용이 커지는가
6. IVF와 무엇이 다른가

단, **실제 인과관계가 없는 개념에 이 형식을 억지로 적용하지 않는다.** 이에 대한 기준은 뒤의 `관계 구조를 먼저 선택한다` 원칙을 따른다.

# 4. 문서의 권장 기본 구조

모든 문서를 같은 Template으로 강제하지는 않지만 다음을 기본으로 한다.

```text
# 주제

이 문서에서 무엇을 이해하려는지 2~4문장

## 1. 가장 먼저 잡을 큰 그림 / 현재 위치 / 핵심

## 2. 전체 흐름 또는 전체 관계

## 3. 왜 필요한가 / 해결하려는 문제

## 4. 핵심 구성요소 또는 내부 동작

## 5. 처음 헷갈리기 쉬운 부분

## 6. 유사 개념과 비교·경계

## 7. 실제 적용 또는 예제

## 8. 장단점 · Trade-off · 운영 고려사항

## 9. 기억 흐름
```

주제에 따라 Section은 생략하거나 변경한다. 핵심은 Section 이름을 통일하는 것이 아니라 **세부로 들어가기 전에 독자가 현재 개념의 좌표를 잃지 않게 하는 것**이다.

# 5. 큰 그림 → 현재 위치 → 관계 → 세부로 내려간다

세부학습 문서의 기본 진입 순서는 다음과 같다.

```text
큰 그림
 ↓
현재 개념의 위치
 ↓
주변 개념과의 관계·경계
 ↓
왜 필요한가
 ↓
전체 처리 흐름 / Mechanism
 ↓
세부 구성요소
 ↓
Algorithm · Parameter
```

새로운 개념을 세부 용어부터 시작하지 않는다.

```text
[지양]
Q/K/V 정의
→ Scaled Dot Product
→ Multi-head
→ ...

[권장]
LLM / Transformer라는 큰 그림
→ Transformer가 Token Vector를 문맥화하는 위치
→ 핵심 Mechanism인 Attention
→ Attention 계산을 위한 Q/K/V
```

가능하면 상세 설명 전에 **현재 배우는 개념이 전체 지도에서 어디에 있는지** 짧게 보여준다.

예를 들어 HNSW를 설명한다면 바로 Graph Algorithm 상세로 들어가기보다 먼저 다음 좌표를 보여줄 수 있다.

```text
Vector Search
├─ Exact Search
└─ ANN
    ├─ HNSW   ← 현재 배우는 위치
    └─ IVF
```

이 좌표는 거대한 분류표일 필요가 없다. 현재 개념의 상위 개념, 인접 개념, 비교 대상이 보일 정도면 충분하다.

또한 큰 그림을 보여준다는 이유로 관련 없는 주변 지식을 과도하게 확장하지 않는다. **현재 개념을 이해하는 데 필요한 범위의 지도만 먼저 보여주고 세부로 내려간다.**

> **세부사항을 설명하기 전에 “지금 전체 중 어디를 보고 있는가?”에 답할 수 있게 한다.**

# 6. 처리 과정은 `입력 → 처리 → 출력`으로 표현한다

동작 원리를 설명할 수 있는 주제에서는 단계별 흐름을 적극 사용한다.

```text
사용자 질문
 ↓
Query Embedding
 ↓
Vector Search
 ↓
Re-ranking
 ↓
관련 Chunk
 ↓
LLM Context
 ↓
답변
```

각 단계가 **무엇을 입력받고 무엇을 출력하는지**가 보이도록 한다.

# 7. 비슷한 개념은 반드시 경계를 설명한다

예:

```text
LLM 내부 Embedding vs 검색용 Embedding
RAG vs Fine-tuning
Few-shot vs SFT
API vs MCP
RAG vs MCP
HNSW vs IVF
Verification vs Validation
```

가능하면 다음을 사용한다.

- 비교 Table
- 같은 흐름에서 위치 비교
- `A는 무엇 / B는 무엇` 설명
- Text 관계도

같은 단어를 사용하지만 역할이 다른 개념은 특히 명확히 구분한다.

```text
Model Weight
≠
Attention Weight
```

# 8. 분류축이 다른 개념을 억지로 한 줄에 세우지 않는다

예를 들어 다음은 기억하기 쉽지만 정확하지 않다.

```text
Fine-tuning → SFT → PEFT → LoRA
```

SFT와 PEFT는 분류 기준이 다르다.

```text
Fine-tuning
│
├─ [학습 신호 관점]
│   └─ SFT
│       └─ 입력-정답 Pair
│
└─ [Parameter 효율 관점]
    ├─ Full Fine-tuning
    └─ PEFT
        └─ LoRA
```

마찬가지로 다음처럼 쓰지 않는다.

```text
CNN → RNN → GAN → Transformer   X
```

CNN·RNN·Transformer는 주로 Network Architecture 관점이고, GAN은 생성·학습 구조 관점이므로 같은 축의 발전 단계가 아니다.

따라서 문서를 작성할 때 **상위/하위 관계인지, 비교 관계인지, 서로 다른 분류축인지 먼저 확인한다.**

# 9. 학습 중 실제로 생긴 질문을 문서에 반영한다

다음과 같은 질문은 삭제할 초보 질문이 아니라 개념의 경계를 정확하게 만드는 좋은 학습 자료다.

```text
"문장 조합은 무한한데 Embedding Model이 Vector를 어떻게 만들지?"

"MCP 없이도 API 직접 호출하면 되는 것 아닌가?"

"Serena가 Code Base 탐색하는데 왜 중간에 필요한가?"

"Text2SQL이 꼭 LLM을 사용해야 하나?"
```

문서에는 자연스럽게 Section으로 녹인다.

```text
## MCP가 없어도 Agent를 만들 수 있는가

가능하다. ...
```

# 10. 예제와 비유

추상적인 정의만으로 이해하기 어려우면 작은 예제를 적극 사용한다.

```text
"출장 가면 호텔값 얼마까지 나와?"
        ↓
Query Embedding
        ↓
"국내 출장 숙박비는 최대 10만원" Chunk 검색
```

비유는 실제 기술과 동일시하지 않는다.

```text

정확한 의미:
AI Client가 Tool·Resource 등을 발견하고 호출하기 위한 Protocol이다.
```

# 12. Mermaid는 언제 사용하는가

Mermaid 자체를 금지하지는 않는다. 다음 조건을 모두 만족할 때 선택적으로 사용한다.

- Branch나 관계가 복잡해 Text Diagram보다 확실히 이해하기 쉬움
- 해당 Viewer에서 Mermaid를 볼 수 없어도 본문만으로 내용을 이해할 수 있음
- 동일 내용을 ASCII와 Mermaid로 반복해서 문서를 불필요하게 늘리지 않음
- 시각화 자체가 학습 가치가 있음

즉 Mermaid는 **추가 시각화**이지 문서 이해를 위한 필수 의존성이 되어서는 안 된다.

### 사용을 지양하는 경우

- 단순 정의 하나를 그림으로 바꾼 경우
- `A → B → C` 정도의 짧은 흐름
- Mermaid가 Text보다 복잡한 경우
- 모바일에서 Diagram이 보이지 않으면 핵심 설명이 사라지는 경우

# 13. 기존 문서를 먼저 보강한다

새 파일을 만들기 전에 확인한다.

```text
기존 문서의 핵심 주제와 같은가?
→ YES: 기존 문서 보강

독립적으로 반복 복습할 가치가 있는 큰 개념인가?
→ YES: 별도 문서 고려
```

반대로 하나의 문서에 서로 독립적인 큰 개념을 억지로 몰아넣지도 않는다.

# 14. 문서 경계와 통합·분리 원칙

세부학습 문서의 파일 단위를 개별 키워드 수로 결정하지 않는다. **한 번에 이해해야 하는 개념 흐름**을 기본 문서 경계로 삼는다.

```text
[키워드 중심 — 지양]
A.md
B.md
C.md

[이해 흐름 중심 — 권장]
A가 왜 필요한가
      ↓
A를 적용하면 B라는 문제가 생김
      ↓
B를 해결하기 위해 C가 필요

→ A → B → C가 하나의 이해 흐름이면 통합 후보
```

### 통합을 우선하는 경우

다음 조건이 강할수록 하나의 문서로 통합한다.

1. **인과 연결성**: 앞 개념이 뒤 개념의 필요성을 직접 만든다.
2. **동시 이해 필요성**: 한 개념을 제대로 이해하려면 다른 개념을 함께 봐야 한다.
3. **반복 왕복 여부**: 별도 문서를 읽을 때 앞 문서를 계속 다시 열어야 이해된다.
4. **하나의 핵심 질문**: 여러 개념이 결국 같은 질문을 단계적으로 풀고 있다.

예:

```text
동시 Transaction
→ Conflict
→ 이상 현상
→ Isolation Level
→ Lock / MVCC
→ S/X · Row/Range · 2PL

→ "Transaction 동시성을 어떻게 안전하게 제어하는가?"라는
   하나의 이해 흐름으로 묶을 수 있음
```

### 분리를 우선하는 경우

다음 조건이 강할수록 별도 문서로 분리한다.

1. **독립 답안성**: 정보관리기술사에서 별도 주제로 충분한 구조를 갖고 서술할 수 있다.
2. **독립 학습성**: 앞 문서에서는 존재와 연결점만 알면 되고, 이후 내용은 독립적으로 이해할 수 있다.
3. **깊이 차이**: 구현체·제품·Algorithm 상세로 내려가면서 원래 문서의 학습 깊이를 크게 벗어난다.
4. **본선 흐름 방해**: 해당 내용을 포함하면 핵심 인과 흐름이 끊기거나 문서가 여러
