# 성능과 신뢰성 개념지도

이 문서는 [[00-전체|컴퓨터 구조 전체 개념지도]]에서 **성능과 신뢰성** 가지를 선택했을 때, 시스템을 `얼마나 잘 처리하는가`와 `얼마나 안정적으로 서비스를 지속하는가`라는 두 평가축으로 파고들기 위한 지도다.

성능과 신뢰성은 하나의 발전 순서가 아니다. **성능은 측정 → 병목 → 개선 → 한계**, **신뢰성·가용성은 고장 → 복구 → 장애 영향 축소**의 흐름으로 각각 본다.

## 먼저 알아둘 용어

```text
CPI(Cycles Per Instruction)
= 명령 하나를 처리하는 데 필요한 평균 Clock Cycle 수

SPEC(Standard Performance Evaluation Corporation)
= 컴퓨터 시스템 성능을 비교하기 위한 대표 Benchmark를 만드는 단체와 그 Benchmark 계열

Amdahl 법칙
= 일부 구간만 개선할 때 전체 성능 향상에는 상한이 있음을 보여주는 법칙

MTBF(Mean Time Between Failures)
= 고장과 다음 고장 사이의 평균 시간

MTTR(Mean Time To Repair)
= 장애 발생 후 평균 복구 시간

Watchdog
= 시스템 응답을 감시하다 문제가 생기면 Reset이나 복구 동작을 유도하는 Mechanism
```

처음에는 `성능 = 얼마나 잘 처리하는가`, `신뢰성·가용성 = 얼마나 안정적으로 지속하는가`라는 두 축부터 구분하면 된다.

## 1. 전체 좌표

```text
시스템을 평가해야 함
│
├─ [성능]
│   얼마나 잘 처리하는가?
│       ↓
│   처리량 / 응답시간 / 이용률 / CPI
│       ↓
│   병목 식별과 구조 개선
│       ↓
│   Amdahl 법칙으로 개선 효과의 상한 확인
│       ↓
│   SPEC 등 Benchmark로 시스템 수준 비교
│
└─ [신뢰성·가용성]
    얼마나 안정적으로 서비스를 지속하는가?
        ↓
    MTBF / MTTR
        ↓
    Watchdog 등 장애 탐지·복구 Mechanism
```

두 축은 별개지만 실제 시스템 설계에서는 함께 판단한다. 빠르더라도 장애가 잦으면 좋은 시스템이라고 보기 어렵고, 안정적이어도 필요한 성능을 충족하지 못하면 목적을 달성하기 어렵다.

## 2. 성능: 먼저 무엇을 측정할 것인가

성능은 하나의 숫자로 표현되지 않는다.

```text
처리량(Throughput)
→ 단위 시간에 얼마나 많은 작업을 처리하는가

응답시간(Response Time)
→ 하나의 요청이 완료되기까지 얼마나 걸리는가

이용률(Utilization)
→ 자원이 얼마나 바쁘게 사용되는가

CPI
→ 명령 하나를 처리하는 데 필요한 평균 Clock Cycle 수
```

같은 시스템이라도 어떤 지표를 보느냐에 따라 평가가 달라질 수 있으므로 Workload와 목표를 먼저 정해야 한다.

## 3. 성능: 병목을 찾고 개선한다

```text
Workload 정의
        ↓
성능 지표 측정
        ↓
병목 구간 식별
        ↓
구조 개선
├─ 파이프라이닝 / 병렬처리
├─ 캐시 / 메모리 계층
├─ DMA
└─ RAID 등
        ↓
개선 효과 재측정
```

부분 최적화가 전체 시스템 성능 향상으로 그대로 이어지는 것은 아니다.

## 4. 성능: Amdahl 법칙으로 개선 효과의 상한을 본다

```text
전체 작업
├─ 개선 가능한 부분
└─ 개선되지 않는 부분
        ↓
개선 가능한 부분만 계속 빨라져도
나머지 구간이 전체 성능을 제한
        ↓
Amdahl 법칙
```

따라서 병렬 자원이나 특정 장치 성능을 계속 높여도 전체 속도가 비례해서 증가하지 않는다.

Amdahl 법칙은 CPU 병렬성에서도 중요하지만, 더 넓게는 **부분 개선이 전체 시스템에 미치는 최대 효과를 판단하는 법칙**으로 본다.

## 5. 성능: Benchmark로 시스템 수준에서 비교한다

SPEC은 대표적인 시스템 성능 Benchmark 계열이다.

개별 Clock이나 부품 사양만 비교하지 않고 실제 Workload에 가까운 Benchmark를 통해 시스템 수준의 성능을 비교한다는 위치를 이해한다.

```text
부품 사양
≠ 실제 시스템 성능 전체
        ↓
대표 Workload 실행
        ↓
Benchmark 결과 비교
```

기술사 관점에서는 세부 Benchmark 항목 암기보다 **무엇을 어떤 Workload로 측정했는가**를 먼저 본다.

## 6. 신뢰성·가용성: 고장과 복구를 함께 본다

성능이 높아도 장애가 잦거나 복구가 늦으면 서비스 품질은 떨어진다.

```text
고장이 얼마나 드문가?
→ MTBF
→ 고장과 고장 사이의 평균 시간

고장 후 얼마나 빨리 복구하는가?
→ MTTR
→ 장애 발생 후 평균 복구 시간
```

```text
가용성을 높이려면
├─ 고장 빈도를 줄임 → MTBF 증가
└─ 복구 시간을 줄임 → MTTR 감소
```

## 7. 신뢰성·가용성: 장애 영향을 줄인다

Watchdog은 시스템이 정상적으로 동작하는지 감시하다가 정해진 시간 안에 응답이 없으면 Reset이나 복구 동작을 유도하는 Mechanism이다.

```text
시스템 동작
        ↓
정상 응답 여부 감시
        ↓
응답 없음 / Hang
        ↓
Watchdog Timeout
        ↓
Reset / 복구 동작
```

Watchdog은 장애 자체를 없애는 기술이 아니라 **장애를 탐지하고 복구를 빠르게 시작해 영향 시간을 줄이는 기술**로 본다.

## 8. 기억 흐름

```text
시스템 평가
│
├─ [성능]
│   목표·Workload 정의
│       ↓
│   처리량 / 응답시간 / 이용률 / CPI 측정
│       ↓
│   병목 식별 → 구조 개선 → 재측정
│       ↓
│   Amdahl 법칙으로 개선 한계 확인
│       ↓
│   Benchmark로 시스템 수준 비교
│
└─ [신뢰성·가용성]
    고장과 복구를 평가
        ↓
    MTBF / MTTR
        ↓
    Watchdog 등으로 장애 영향 축소
```

성능 개선 뒤에 신뢰성이 순서대로 따라오는 것이 아니다. **서로 다른 평가축을 함께 보면서 시스템의 전체 품질을 판단하는 것이 핵심**이다.
