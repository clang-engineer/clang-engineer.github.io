# 데이터베이스 개념지도

> 데이터베이스는 데이터를 단순히 저장하는 기술이 아니라, **업무의 의미를 구조로 만들고 → 정확하게 공유·변경하며 → 장애와 동시 접근에서도 신뢰성을 지키고 → 규모가 커져도 빠르게 활용할 수 있게 관리하는 체계**다.

## 1. 가장 먼저 잡을 큰 그림

데이터베이스의 큰 흐름은 **데이터를 어떻게 공동 관리할 것인가**에서 시작해, 구조·사용·신뢰성·성능·확장 문제를 차례로 만나는 과정으로 볼 수 있다.

```text
Application마다 File을 따로 관리
        ↓
중복 · 불일치 · 공유·통제 어려움
        ↓
DBMS
= 데이터를 공통으로 관리
        ↓
그런데 무엇을 어떤 구조로 저장하지?
        ↓
데이터 모델링 · Schema · Key · 제약조건
        ↓
한 Table에 반복해서 넣으면?
        ↓
중복 · 삽입/수정/삭제 이상
        ↓
정규화 ↔ 반정규화
        ↓
구조화한 데이터를 어떻게 다루지?
        ↓
관계형 모델 · SQL · View
        ↓
여러 사용자가 동시에 바꾸면 결과가 꼬일 수 있다
        ↓
Transaction · ACID
        ├─ 동시에 실행해도 맞아야 함 → 동시성 제어
        └─ 처리 중 장애가 나도 복원해야 함 → 회복
        ↓
데이터가 많아지면 전체를 매번 읽을 수 없다
        ↓
저장 구조 · Index · Partition · Tuning
        ↓
한 서버의 용량·처리량·가용성 한계를 넘으면?
        ↓
Replication · Sharding · 분산 DB
```

이 Spine에 모든 DB 개념을 억지로 넣지는 않는다. `보안·권한·감사`, `데이터 품질·표준·Metadata·거버넌스`는 특정 단계의 다음 기술이 아니라 **전체를 가로지르는 횡단축**이고, `DW·OLAP·BI`는 운영 DB의 다음 발전 단계가 아니라 **저장한 데이터를 분석에 활용하는 별도 목적의 가지**다.

## 2. 데이터를 왜 DBMS로 공동 관리할까?

```text
File 중심 관리
├─ Application별 데이터 중복
├─ 같은 데이터의 값 불일치 가능
├─ 공유와 동시 접근 통제 어려움
└─ 구조 변경이 Application에 직접 영향
        ↓
DBMS
├─ 데이터 구조와 제약조건을 중앙에서 관리
├─ 여러 사용자의 저장·조회·변경을 통제
├─ Transaction·회복·보안 등을 제공
└─ 데이터 독립성을 통해 변경 영향을 줄임
```

DBMS를 사용해도 어떤 데이터를 어떤 구조로 관리할지는 자동으로 정해지지 않는다. 그래서 다음 문제는 **현실의 업무를 데이터 구조로 표현하는 것**이다.

## 3. 데이터의 의미와 구조를 어떻게 정할까?

```text
현실의 업무
  ↓ 추상화
데이터 모델링
├─ 개념 모델
│   └─ Entity · Attribute · Relationship
├─ 논리 모델
│   ├─ Relation(Table)
│   ├─ Tuple(Row) / Attribute(Column)
│   ├─ Key
│   │   ├─ Candidate Key
│   │   ├─ Primary Key
│   │   └─ Foreign Key
│   └─ 무결성 제약조건
└─ 물리 모델
    └─ 실제 저장 구조 · Index · Partition 등
```

DBMS는 이 구조를 바탕으로 여러 사용자가 데이터를 저장·조회·변경하도록 관리한다.

```text
사용자 / Application
        ↓
외부 Schema
        ↓
개념 Schema
        ↓
내부 Schema
        ↓
물리 저장장치
```

`ANSI/SPARC 3-Schema`의 핵심은 계층 자체를 외우는 것이 아니라 **논리적·물리적 데이터 독립성**을 통해 하위 구조 변경이 상위 사용 방식에 미치는 영향을 줄이는 데 있다.

구조를 만들었다고 끝나지는 않는다. 같은 사실을 여러 곳에 반복 저장하면 새로운 문제가 생긴다.

## 4. 구조를 만들었는데 왜 정규화가 필요할까?

한 Table에 관련 데이터를 반복해서 넣으면 중복이 커지고 삽입·수정·삭제 이상이 생긴다.

```text
중복된 데이터 구조
        ↓
함수 종속성(Function Dependency) 확인
        ↓
정규화
├─ 1NF
├─ 2NF
├─ 3NF
└─ BCNF
        ↓
중복·이상현상 감소 / 무결성 향상
```

정규화가 항상 최종 물리 구조를 의미하지는 않는다.

```text
정규화된 구조
        ↓ 성능·조회 패턴과 Trade-off
반정규화(Denormalization)
        ↓
중복을 일부 허용해 Join 비용 등을 줄일 수 있음
```

`정규화 ↔ 반정규화`는 옳고 그름이 아니라 **무결성·변경 비용 ↔ 조회 성능·단순성**의 선택 문제다.

이렇게 구조와 규칙을 정했다면 실제 Application은 그 데이터를 조회하고 변경해야 한다.

## 5. 관계형 DB에서는 데이터를 어떻게 다룰까?

```text
관계형 모델
├─ Relation
├─ Key / 무결성 제약조건
└─ 관계 연산
     ├─ Selection
     ├─ Projection
     └─ Join
          ↓
         SQL
          ├─ DDL : 구조 정의
          ├─ DML : 데이터 조회·변경
          └─ DCL : 권한 통제
```

`View`는 실제 데이터를 별도로 저장하는 Table과 달리 질의 결과를 논리적인 Table처럼 제공해 **복잡성 은닉·보안·논리적 독립성**에 활용한다.

한 사용자만 데이터를 다룬다면 여기까지로도 단순하다. 실제 DB에서는 여러 사용자의 작업이 동시에 겹치므로 **하나의 논리적 업무를 어디까지 하나로 보장할 것인가**가 중요해진다.

## 6. 여러 사용자가 동시에 바꾸면 어떻게 정확성을 지킬까?

핵심 출발점은 `Transaction`이다.

```text
Transaction
└─ ACID
   ├─ Atomicity   : 전부 수행하거나 전부 취소
   ├─ Consistency : 일관된 상태 유지
   ├─ Isolation   : 동시 실행의 간섭 통제
   └─ Durability  : Commit 결과 보존
```

여기서 서로 다른 두 문제가 갈라진다.

```text
[동시 실행 문제]
여러 Transaction이 겹침
        ↓
Lost Update · Dirty Read · Non-repeatable Read · Phantom Read
        ↓
동시성 제어
├─ Lock
│   └─ 2PL(Two-Phase Locking)
├─ 직렬성(Serializability)
├─ 격리수준(Isolation Level)
├─ MVCC(Multi-Version Concurrency Control)
└─ Deadlock 탐지·회피·복구

[장애 문제]
Transaction 처리 중 장애
        ↓
일부 변경만 남을 위험
        ↓
회복(Recovery)
├─ Log
├─ Undo / Redo
└─ Checkpoint
```

`동시성 제어`와 `회복`은 모두 Transaction 신뢰성을 지키지만 해결하는 문제가 다르다.

또한 `Backup`은 장기 보존본에서 데이터를 복원하는 수단으로, Transaction Log 기반 회복과 목적·시간 범위가 다르다.

- [[트랜잭션-동시성-격리수준-Lock-MVCC]]

정확하게 처리할 수 있어도 데이터가 커지면 또 다른 문제가 나타난다. 원하는 Record를 찾기 위해 전체 Table을 계속 읽을 수는 없다.

## 7. 데이터가 많아지면 어떻게 빨리 찾을까?

```text
느린 질의
  ↓
먼저 측정
├─ 실행계획
├─ I/O
└─ Lock·대기시간
  ↓
병목에 맞는 접근 구조와 질의 개선
├─ Index
│   ├─ B-Tree 계열
│   │   └─ B+Tree
│   ├─ Hash
│   └─ Clustered ↔ Nonclustered
├─ Partition
└─ SQL / Schema / DB 설정 Tuning
  ↓
재측정
```

Index는 별도 탐색 구조를 유지하는 대신 전체 Table을 매번 읽지 않고 원하는 Record에 빠르게 접근하게 한다.

```text
탐색 구조 관점

B-Tree 계열
├─ B-Tree
├─ B+Tree
├─ B*Tree
└─ T-Tree

저장·Locator 관점
├─ Clustered Index
└─ Nonclustered Index
```

두 분류축을 섞지 않는다. `B+Tree`는 탐색 구조이고 `Clustered / Nonclustered`는 Index Entry와 실제 데이터 배치·Locator 관계를 설명하는 관점이다.

- [[탐색트리와-DB인덱스-BTree-BPlusTree-BStarTree-TTree]]
- [[BTree-클러스터드-넌클러스터드-인덱스]]

단일 DB 안에서 병목을 줄여도 결국 한 서버가 감당할 수 있는 용량·처리량·가용성에는 한계가 있다. 그때 분산을 검토한다.

## 8. 한 서버의 한계를 넘으면 어떻게 확장할까?

```text
단일 DB
  ↓ 용량·처리량·가용성 한계
분산을 검토
├─ Replication
│   └─ 같은 데이터를 복제 → 가용성·읽기 확장
├─ Sharding
│   └─ 데이터를 분할 → 저장·처리 부하 분산
└─ 분산 DB
    └─ 여러 Node를 하나의 데이터 시스템으로 운영
```

분산은 공짜 확장이 아니다.

```text
확장성·가용성 향상
        ↕ Trade-off
일관성 · 분산 Transaction · 장애 처리 · 운영 복잡성
```

`Replication`과 `Sharding`도 같은 개념이 아니다. 전자는 **복제**, 후자는 **분할**이 핵심이다.

## 9. Spine 전체를 가로지르는 횡단 좌표

다음은 앞 단계 뒤에 순서대로 오는 기능이 아니라 데이터의 설계·저장·변경·활용 전체에 적용되는 관리 관점이다.

```text
                 [DB의 주 Spine]
DBMS → 모델링 → 정규화 → SQL → Transaction → 성능 → 분산
  │       │          │       │          │          │       │
  └───────┴──────────┴───────┴──────────┴──────────┴───────┘
                          ↑
                    [횡단 관리]
       보안 · 권한 · 감사
       데이터 품질 · 표준 · Metadata · 거버넌스
```

```text
횡단 관리
├─ 보안
│   ├─ 인증 · 권한
│   ├─ 암호화
│   └─ 감사
├─ 데이터 품질
│   └─ 정확성 · 완전성 · 일관성 등
├─ 데이터 표준
├─ Metadata
└─ 데이터 거버넌스
    └─ 의사결정권 · 책임 · 정책 · 통제
```

## 10. 저장한 데이터를 어떻게 활용할까?

운영 Transaction 처리와 분석은 목적과 처리 패턴이 다르다. 따라서 분석 영역을 주 Spine의 마지막 단계로 이어 붙이지 않고 별도 활용 가지로 본다.

```text
데이터 활용
├─ OLTP
│   └─ 짧고 빈번한 Transaction 중심
└─ 분석
    ├─ DW(Data Warehouse)
    ├─ OLAP
    ├─ BI
    └─ 데이터 마이닝
```

`OLTP → DW → OLAP`을 DB 자체의 발전 단계로 보지 않는다. 운영 데이터 처리와 분석 데이터 활용이라는 서로 다른 목적을 구분한다.

## 11. 기억할 핵심 경계

| 헷갈리기 쉬운 개념 | 핵심 경계 |
|---|---|
| Schema ↔ Instance | 구조 정의 ↔ 특정 시점의 실제 데이터 |
| 논리적 ↔ 물리적 데이터 독립성 | 외부-개념 구조 변경 영향 최소화 ↔ 개념-내부 저장 변경 영향 최소화 |
| 정규화 ↔ 반정규화 | 중복·이상 감소 ↔ 성능 등을 위해 중복 일부 허용 |
| Transaction ↔ 동시성 제어 | 논리적 작업 단위 ↔ 여러 Transaction의 간섭 통제 |
| 동시성 제어 ↔ 회복 | 동시 실행 문제 ↔ 장애 문제 |
| Recovery ↔ Backup | Transaction 상태 복원 ↔ 별도 보존본에서 복원 |
| B+Tree ↔ Clustered Index | 탐색 자료구조 ↔ 데이터 배치·Locator 관계 |
| Replication ↔ Sharding | 데이터 복제 ↔ 데이터 분할 |
| OLTP ↔ OLAP | 운영 Transaction 처리 ↔ 분석 질의 처리 |

```text
     모델링
        ↓
중복·이상현상을 줄이려면?
        ↓
정규화 ↔ 반정규화
        ↓
구조화한 데이터를 다루려면?
        ↓
관계형 모델 · SQL · View
        ↓
동시 실행과 장애에서도 정확하려면?
        ↓
Transaction · ACID
   ├─ 동시성 → Lock · 2PL · 격리수준 · MVCC
   └─ 장애   → Log · Undo/Redo · Checkpoint
        ↓

        ↓

        ↓

        ↓
Replication · Sharding · 분산 DB

──────────── 전체를 가로지름 ────────────
보안 · 품질 · 표준 · Metadata · 거버넌스

──────────── 별도 활용 가지 ────────────
OLTP ↔ DW · OLAP · BI · 데이터 마이닝
```

> **공동 관리가 필요해 DBMS를 두고 → 업무를 데이터 구조로 만들고 → 중복과 이상을 통제하고 → SQL로 사용하며 → 동시성과 장애에서도 Transaction을 지키고 → 규모가 커지면 접근 구조를 최적화하고 → 단일 서버의 한계를 넘을 때 분산한다. 보안·품질·거버넌스는 이 전체를 가로지른다.**
