# 데이터베이스 개념지도

> 데이터베이스는 데이터를 단순히 저장하는 기술이 아니라, **업무의 의미를 구조로 만들고 → 정확하게 공유·변경하며 → 장애와 동시 접근에서도 신뢰성을 지키고 → 규모가 커져도 빠르게 활용할 수 있게 관리하는 체계**다.

## 1. 가장 먼저 잡을 큰 그림

```text
업무에서 관리할 데이터가 있다
        ↓
무엇을 어떤 구조로 저장할까?
        ↓
데이터 모델링 · Schema · Key · 제약조건
        ↓
중복과 이상현상을 어떻게 줄일까?
        ↓
정규화 ↔ 반정규화
        ↓
관계형 DB에서 어떻게 다룰까?
        ↓
SQL · 관계 연산 · View
        ↓
여러 사용자가 동시에 바꾸어도 정확해야 한다
        ↓
Transaction · ACID
        ├─ 동시 실행 문제 → 동시성 제어
        └─ 장애 문제     → 회복
        ↓
데이터가 커져도 빨라야 한다
        ↓
저장 구조 · Index · Partition · Tuning
        ↓
한 서버의 한계를 넘으면?
        ↓
Replication · Sharding · 분산 DB
```

이 흐름 전체에 `보안·권한·감사`, `데이터 품질·표준·Metadata·거버넌스`가 횡단한다.

## 2. 데이터의 의미와 구조를 어떻게 정할까?

```text
현실의 업무
  ↓ 추상화
데이터 모델링
├─ 개념 모델
│   └─ Entity · Attribute · Relationship
├─ 논리 모델
│   ├─ Relation(Table)
│   ├─ Tuple(Row) / Attribute(Column)
│   ├─ Key
│   │   ├─ Candidate Key
│   │   ├─ Primary Key
│   │   └─ Foreign Key
│   └─ 무결성 제약조건
└─ 물리 모델
    └─ 실제 저장 구조 · Index · Partition 등
```

DBMS는 이 구조를 바탕으로 여러 사용자가 데이터를 저장·조회·변경하도록 관리한다.

```text
사용자 / Application
        ↓
외부 Schema
        ↓
개념 Schema
        ↓
내부 Schema
        ↓
물리 저장장치
```

`ANSI/SPARC 3-Schema`의 핵심은 계층 자체를 외우는 것이 아니라 **논리적·물리적 데이터 독립성**을 통해 하위 구조 변경이 상위 사용 방식에 미치는 영향을 줄이는 데 있다.

## 3. 구조를 만들었는데 왜 정규화가 필요할까?

한 Table에 관련 데이터를 반복해서 넣으면 중복이 커지고 삽입·수정·삭제 이상이 생긴다.

```text
중복된 데이터 구조
        ↓
함수 종속성(Function Dependency) 확인
        ↓
정규화
├─ 1NF
├─ 2NF
├─ 3NF
└─ BCNF
        ↓
중복·이상현상 감소 / 무결성 향상
```

정규화가 항상 최종 물리 구조를 의미하지는 않는다.

```text
정규화된 구조
        ↓ 성능·조회 패턴과 Trade-off
반정규화(Denormalization)
        ↓
중복을 일부 허용해 Join 비용 등을 줄일 수 있음
```

`정규화 ↔ 반정규화`는 옳고 그름이 아니라 **무결성·변경 비용 ↔ 조회 성능·단순성**의 선택 문제다.

## 4. 관계형 DB에서는 데이터를 어떻게 다룰까?

```text
관계형 모델
├─ Relation
├─ Key / 무결성 제약조건
└─ 관계 연산
     ├─ Selection
     ├─ Projection
     └─ Join
          ↓
         SQL
          ├─ DDL : 구조 정의
          ├─ DML : 데이터 조회·변경
          └─ DCL : 권한 통제
```

`View`는 실제 데이터를 별도로 저장하는 Table과 달리 질의 결과를 논리적인 Table처럼 제공해 **복잡성 은닉·보안·논리적 독립성**에 활용한다.

## 5. 여러 사용자가 동시에 바꾸면 어떻게 정확성을 지킬까?

핵심 출발점은 `Transaction`이다.

```text
Transaction
└─ ACID
   ├─ Atomicity   : 전부 수행하거나 전부 취소
   ├─ Consistency : 일관된 상태 유지
   ├─ Isolation   : 동시 실행의 간섭 통제
   └─ Durability  : Commit 결과 보존
```

여기서 서로 다른 두 문제가 갈라진다.

```text
[동시 실행 문제]
여러 Transaction이 겹침
        ↓
Lost Update · Dirty Read · Non-repeatable Read · Phantom Read
        ↓
동시성 제어
├─ Lock
│   └─ 2PL(Two-Phase Locking)
├─ 직렬성(Serializability)
├─ 격리수준(Isolation Level)
├─ MVCC(Multi-Version Concurrency Control)
└─ Deadlock 탐지·회피·복구

[장애 문제]
Transaction 처리 중 장애
        ↓
일부 변경만 남을 위험
        ↓
회복(Recovery)
├─ Log
├─ Undo / Redo
└─ Checkpoint
```

`동시성 제어`와 `회복`은 모두 Transaction 신뢰성을 지키지만 해결하는 문제가 다르다.

또한 `Backup`은 장기 보존본에서 데이터를 복원하는 수단으로, Transaction Log 기반 회복과 목적·시간 범위가 다르다.

## 6. 데이터가 많아지면 어떻게 빨리 찾을까?

```text
느린 질의
  ↓
먼저 측정
├─ 실행계획
├─ I/O
└─ Lock·대기시간
  ↓
병목에 맞는 접근 구조와 질의 개선
├─ Index
│   ├─ B-Tree 계열
│   │   └─ B+Tree
│   ├─ Hash
│   └─ Clustered ↔ Nonclustered
├─ Partition
└─ SQL / Schema / DB 설정 Tuning
  ↓
재측정
```

Index는 별도 탐색 구조를 유지하는 대신 전체 Table을 매번 읽지 않고 원하는 Record에 빠르게 접근하게 한다.

```text
탐색 구조 관점

B-Tree 계열
├─ B-Tree
├─ B+Tree
├─ B*Tree
└─ T-Tree

저장·Locator 관점
├─ Clustered Index
└─ Nonclustered Index
```

두 분류축을 섞지 않는다. `B+Tree`는 탐색 구조이고 `Clustered / Nonclustered`는 Index Entry와 실제 데이터 배치·Locator 관계를 설명하는 관점이다.

## 7. 한 서버의 한계를 넘으면 어떻게 확장할까?

```text
단일 DB
  ↓ 용량·처리량·가용성 한계
분산을 검토
├─ Replication
│   └─ 같은 데이터를 복제 → 가용성·읽기 확장
├─ Sharding
│   └─ 데이터를 분할 → 저장·처리 부하 분산
└─ 분산 DB
    └─ 여러 Node를 하나의 데이터 시스템으로 운영
```

분산은 공짜 확장이 아니다.

```text
확장성·가용성 향상
        ↕ Trade-off
일관성 · 분산 Transaction · 장애 처리 · 운영 복잡성
```

`Replication`과 `Sharding`도 같은 개념이 아니다. 전자는 **복제**, 후자는 **분할**이 핵심이다.

## 8. 데이터베이스 전체를 가로지르는 횡단 좌표

다음은 앞 단계 뒤에 순서대로 오는 기능이 아니라 DB 생명주기 전체에 적용되는 관리 관점이다.

```text
데이터 생명주기 전체
├─ 보안
│   ├─ 인증 · 권한
│   ├─ 암호화
│   └─ 감사
├─ 데이터 품질
│   └─ 정확성 · 완전성 · 일관성 등
├─ 데이터 표준
├─ Metadata
└─ 데이터 거버넌스
    └─ 의사결정권 · 책임 · 정책 · 통제
```

## 9. 저장한 데이터를 어떻게 활용할까?

운영 Transaction 처리와 분석은 목적과 처리 패턴이 다르다.

```text
데이터 활용
├─ OLTP
│   └─ 짧고 빈번한 Transaction 중심
└─ 분석
    ├─ DW(Data Warehouse)
    ├─ OLAP
    ├─ BI
    └─ 데이터 마이닝
```

`OLTP → DW → OLAP`을 DB 자체의 발전 단계로 보지 않는다. 운영 데이터 처리와 분석 데이터 활용이라는 서로 다른 목적을 구분한다.

## 10. 기억할 핵심 경계

| 헷갈리기 쉬운 개념 | 핵심 경계 |
|---|---|
| Schema ↔ Instance | 구조 정의 ↔ 특정 시점의 실제 데이터 |
| 논리적 ↔ 물리적 데이터 독립성 | 외부-개념 구조 변경 영향 최소화 ↔ 개념-내부 저장 변경 영향 최소화 |
| 정규화 ↔ 반정규화 | 중복·이상 감소 ↔ 성능 등을 위해 중복 일부 허용 |
| Transaction ↔ 동시성 제어 | 논리적 작업 단위 ↔ 여러 Transaction의 간섭 통제 |
| 동시성 제어 ↔ 회복 | 동시 실행 문제 ↔ 장애 문제 |
| Recovery ↔ Backup | Transaction 상태 복원 ↔ 별도 보존본에서 복원 |
| B+Tree ↔ Clustered Index | 탐색 자료구조 ↔ 데이터 배치·Locator 관계 |
| Replication ↔ Sharding | 데이터 복제 ↔ 데이터 분할 |
| OLTP ↔ OLAP | 운영 Transaction 처리 ↔ 분석 질의 처리 |

## 11. 한 번에 다시 떠올리기

```text
데이터베이스
│
├─ 의미와 구조
│   └─ 모델링 → Schema → Key·제약조건 → 정규화
│
├─ 사용
│   └─ 관계형 모델 → SQL → View
│
├─ 신뢰성
│   └─ Transaction · ACID
│       ├─ 동시성 → Lock · 2PL · 격리수준 · MVCC · Deadlock
│       └─ 장애   → Log · Undo/Redo · Checkpoint
│
├─ 성능
│   └─ 측정 → Index · Partition · Tuning → 재측정
│
├─ 확장
│   └─ Replication · Sharding · 분산 DB
│
├─ 횡단 관리
│   └─ 보안 · 품질 · 표준 · Metadata · 거버넌스
│
└─ 활용
    └─ OLTP ↔ DW · OLAP · BI · Mining
```

> **구조를 정하고 → 정확하게 처리하고 → 장애와 동시성에서도 지키고 → 빠르게 찾고 → 필요하면 분산하며 → 전 과정의 품질·보안·거버넌스를 관리한다.**
