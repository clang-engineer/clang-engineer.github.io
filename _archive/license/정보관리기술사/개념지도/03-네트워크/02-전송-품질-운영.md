# 전송·품질·운영 개념지도

이 지도는 **목적지까지 간 데이터를 어느 프로그램에 넘기고, 제대로 전달되게 하며, Traffic이 몰릴 때 품질을 관리하고, Network 상태를 운영자가 확인하는 흐름**을 함께 본다.

먼저 다음 질문을 잡는다.

```text
목적지 Host까지 도착한 뒤 어느 프로그램에 넘기지?
  ↓
Port / TCP / UDP

데이터가 빠지거나 너무 많이 보내면?
  ↓
오류 제어 / 흐름 제어 / 혼잡 제어

여러 Traffic이 한정된 Network를 같이 쓰면?
  ↓
QoS / QoE

Network가 정상인지 어떻게 계속 확인하지?
  ↓
NMS / SNMP
```

이 질문 아래에서 세부학습을 다시 떠올릴 핵심 Node를 함께 남긴다.

## 1. Host까지 가는 것과 Process까지 가는 것은 다르다

```text
IP
= 목적지 Host까지 Packet 전달
  ↓
Transport
= Host 안의 목적 Process까지 전달 특성 제공
  ↓
Port
= Process 식별
```

Transport Layer의 대표 선택은 TCP와 UDP다.

```text
Transport
├─ TCP
│   ├─ 연결 상태 유지
│   ├─ 신뢰성 있는 Byte Stream
│   ├─ 순서 보장
│   └─ 오류·흐름·혼잡 제어
└─ UDP
    ├─ 연결 상태 없음
    └─ Datagram 단위 전달
```

## 2. TCP는 세 가지 문제를 구분해서 본다

```text
연결을 만든다
3-Way Handshake
  ↓
연결을 끝낸다
FIN / 일반적인 4-Way 종료 흐름
  ↓
데이터가 제대로 갔는가?
오류 제어
  ↓
수신자가 감당할 수 있는가?
흐름 제어
  ↓
Network가 감당할 수 있는가?
혼잡 제어
```

복습할 때는 이 경계를 먼저 떠올린다.

```text
오류 제어
= 전달 정확성·손실 대응

흐름 제어
= Sender가 Receiver 처리 능력을 넘지 않도록 조절

혼잡 제어
= Sender가 Network 수용 능력을 넘지 않도록 조절
```

세부학습에서는 `Sequence / ACK`, `Sliding Window`, `rwnd`, `cwnd`, Slow Start, Congestion Avoidance 등의 동작을 다시 연결한다.

→ [[TCP-연결-종료-흐름-혼잡제어]]

## 3. TCP 연결을 다시 쓰는 것은 상위 계층의 문제다

```text
TCP Connection
  ↓
HTTP Request / Response
  ↓
매번 새 TCP 연결 생성 시 비용 발생
  ↓
Persistent Connection
  └─ HTTP Keep-Alive

Application / Server
  ↓
여러 TCP Connection 생성 비용 감소 필요
  ↓
Connection Pool
```

HTTP Keep-Alive와 Connection Pool을 TCP 자체 기능으로 놓지 않는다. 둘은 **TCP Connection을 상위 계층에서 재사용하는 방법**이다.

## 4. 한 Sender의 혼잡 대응과 Network 전체의 품질 정책은 다르다

```text
Traffic 증가
  ↓
Queue 증가
  ↓
Delay / Jitter 증가
  ↓
Packet Loss
  ↓
재전송·Throughput 저하
```

여기서 두 관점을 구분한다.

```text
TCP 혼잡 제어
= 개별 TCP Sender가 Network 혼잡에 적응

QoS
= Network가 여러 Traffic에 자원을 정책적으로 배분
```

QoS는 회선 용량 자체를 늘리는 기술이 아니다.

## 5. QoS는 Traffic을 구분하고 자원을 다르게 배분한다

복습할 핵심 처리 흐름은 다음과 같다.

```text
Traffic 유입
  ↓
Classification
  ↓
Marking
  ↓
속도 정책
├─ Policing
└─ Shaping
  ↓
Queueing
  ↓
Scheduling
  ↓
Delay / Jitter / Loss 측정
```

QoS와 QoE도 같은 축이 아니다.

```text
QoS
= Network 관점의 기술적 품질과 정책

QoE
= 사용자가 실제로 체감하는 Service 품질
```

QoS는 QoE에 영향을 주지만 Server, Application, Codec, 단말 상태도 QoE에 영향을 준다.

→ [[QoS와-QoE]]

## 6. 품질을 운영하려면 Network 상태를 계속 봐야 한다

```text
Network 상태 변화
  ↓
Metric / Event 수집
  ↓
NMS
├─ 저장
├─ 임계치 판단
├─ Alert
└─ 운영자에게 가시화
```

NMS와 SNMP를 같은 개념으로 놓지 않는다.

```text
NMS
= 여러 Network 장비를 중앙에서 통합 관리하는 시스템

SNMP
= NMS와 장비 Agent가 관리 정보를 주고받을 때 사용하는 대표 Protocol
```

## 7. Polling과 Event 통지는 서로 보완한다

```text
정상 상태와 추세
Manager ── Polling ──→ Agent

즉시 알려야 할 Event
Manager ←─ Trap / Inform ─ Agent
```

복습할 때는 다음 경계를 기억한다.

```text
Polling
= Manager가 주기적으로 상태를 물어봄

Trap / Inform
= Agent가 Event를 먼저 알림
```

둘은 대체 관계보다 보완 관계로 본다.

→ [[NMS와-SNMP]]

## 8. 복습용 핵심 좌표

```text
Transport
├─ TCP ↔ UDP
└─ Port

TCP
├─ 3-Way Handshake / 종료
├─ 오류 제어
├─ 흐름 제어 → rwnd
└─ 혼잡 제어 → cwnd

품질
├─ TCP 혼잡 제어
├─ QoS
│   ├─ Classification / Marking
│   ├─ Policing / Shaping
│   └─ Queueing / Scheduling
└─ QoE

운영
├─ NMS
└─ SNMP
    ├─ Polling
    └─ Trap / Inform
```

이 Node를 보고 세부 Algorithm과 차이를 떠올릴 수 있으면 된다. TCP 상태 전이 전체, 혼잡 제어 Algorithm 세부, QoS Scheduling Algorithm, SNMP PDU와 OID 상세는 세부학습에서 복원한다.
