# 서비스·가상화·제약환경 개념지도

이 지도는 **기본 전달 기능 위에서 서비스 요구를 어떻게 충족하고, 네트워크 운영을 어떻게 소프트웨어화하며, 제약된 환경에서는 어떤 문제가 추가되는지**를 중심으로 본다.

## 1. 기본 전달 위에 서비스 요구가 올라간다

```text
기본 Network 전달
  ↓
Service 요구
├─ Web 요청·응답          → HTTP
├─ 실시간 Media 전달      → RTP / RTCP
├─ 가까운 위치에서 전달    → CDN
└─ 사설 연결·보호          → VPN
```

이 기술들은 하나의 발전 순서가 아니다. 같은 Network 위에서 **서비스 목적에 따라 서로 다른 문제를 해결하는 병렬 축**이다.

## 2. HTTP의 위치

```text
Application
  ↓
HTTP Request / Response
  ↓
Transport
  └─ TCP 등
  ↓
IP Network
```

HTTP는 Network Layer나 Transport Layer의 기능이 아니다. 응용 계층에서 Request와 Response의 의미를 정의하고, 하위 Transport의 연결을 이용한다.

연결을 반복해서 만드는 비용이 문제라면 Persistent Connection과 Keep-Alive 같은 연결 재사용 개념으로 이어진다.

## 3. 실시간 Media는 요구 특성이 다르다

```text
일반 Data
= 정확한 전달이 중요

실시간 Voice / Video
= Delay · Jitter · Loss의 영향이 큼
```

따라서 실시간 Media에서는 RTP / RTCP 같은 전달·제어 개념과 함께 QoS·QoE를 연결해서 본다.

```text
실시간 Media
  ↓
RTP / RTCP
  ↓
Delay · Jitter · Loss 관리 필요
  ↓
QoS
  ↓
사용자 체감
  ↓
QoE
```

## 4. 다수 사용자에게 같은 Content를 전달하면

```text
Origin에 요청 집중
  ↓
거리 증가·Backbone Traffic 증가
  ↓
사용자 가까운 지점에 Content 배치
  ↓
CDN
```

CDN은 Routing Protocol의 대체 기술이 아니다. IP Routing 위에서 **Content를 어디에서 제공할지 최적화하는 서비스 전달 구조**다.

Multicast도 다수 수신자 전달 비용을 줄이려는 문제와 연결되지만, CDN과는 동작 위치와 방식이 다르다.

```text
Multicast
= Network가 하나의 Traffic을 여러 수신자에게 복제·전달

CDN
= 여러 위치에 Content를 배치하고 가까운 제공 지점을 선택
```

## 5. 사설 연결과 보호

```text
공용 Network를 사용
  ↓
조직 간 또는 사용자-조직 간 사설 통신 필요
  ↓
VPN
```

VPN은 단순히 암호화 하나를 뜻하지 않는다. 공용 Network 위에 논리적인 사설 연결을 구성하는 큰 개념으로 본다.

세부 Tunnel 방식과 보안 Protocol은 보안 영역의 세부학습과 연결한다.

## 6. 장비별 수동 운영의 한계

```text
Network 장비 증가
  ↓
장비마다 개별 설정
  ↓
정책 변경이 느리고 일관성 유지가 어려움
  ↓
제어를 소프트웨어에서 다루고 싶음
  ↓
SDN
```

SDN의 핵심 좌표는 다음과 같다.

```text
Control Plane
= 경로·정책을 결정

Data Plane
= 실제 Packet을 전달

SDN
= 제어와 전달을 분리해 중앙 정책화·자동화를 강화
```

## 7. Network 기능 자체도 소프트웨어화한다

```text
전용 Network Appliance
Firewall / Router / Load Balancer 등
  ↓
전용 장비 의존과 증설 부담
  ↓
Network 기능을 범용 Computing 자원에서 SW로 실행
  ↓
NFV
```

SDN과 NFV는 자주 같이 쓰이지만 같은 개념은 아니다.

```text
SDN
= Network 제어 방식을 소프트웨어 중심으로 재구성

NFV
= Network 기능 자체를 소프트웨어로 구현·실행
```

둘은 함께 적용되어 자동화와 탄력성을 높일 수 있다.

## 8. 제약 환경으로 확장

```text
일반 Network
  ↓
저전력·저성능·불안정 Link·대규모 단말 환경
  ↓
Sensor Network
  ↓
IoT
```

IoT는 단순히 작은 장비를 Internet에 연결하는 것으로 끝나지 않는다.

```text
IoT 환경
├─ 제한된 전력
├─ 제한된 CPU / Memory
├─ 다양한 Link
├─ 대규모 단말 관리
└─ 보안·운영 문제
```

따라서 일반 Network의 주소·전송·보안·운영 개념을 그대로 사용하되, **자원 제약과 규모 문제**가 추가된 환경으로 본다.

## 9. 서로 다른 축을 섞지 않는다

```text
[응용 전달]
HTTP / RTP / CDN

[사설 연결]
VPN

[운영 자동화]
SDN

[Network 기능 가상화]
NFV

[제약 환경]
Sensor Network / IoT
```

`HTTP → CDN → VPN → SDN → NFV → IoT` 같은 발전 사슬로 그리지 않는다. 각각 해결하려는 문제가 다르며 실제 시스템에서는 필요에 따라 조합된다.

## 10. 학습 이동 경로

```text
기본 Network 위에서 Service는 무엇을 요구하는가?
  ↓
Web·실시간 Media·대규모 Content 전달은 무엇이 다른가?
  ↓
공용 Network 위에 사설 연결은 어떻게 구성하는가?
  ↓
Network가 커지면 장비별 수동 운영은 왜 한계가 생기는가?
  ↓
제어를 소프트웨어화하면 무엇이 달라지는가?
  ↓
Network 기능 자체를 소프트웨어화하면 무엇이 달라지는가?
  ↓
저전력·대규모 단말 환경에서는 어떤 제약이 추가되는가?
```

개별 Protocol Header, VPN Tunnel 상세, SDN Interface, NFV 배치 구조, IoT 개별 규격은 세부학습으로 내려간다.
