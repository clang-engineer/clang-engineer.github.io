# 소프트웨어 공학 개념지도

> 소프트웨어 공학은 **불확실한 요구를 운영 가능한 소프트웨어로 바꾸고, 변경·품질·일정·비용의 위험을 전체 생명주기에서 통제하는 방법**을 다룬다.

## 1. 가장 먼저 잡을 큰 그림

소프트웨어를 만드는 활동에는 **제품을 만들어 가는 흐름**과 **그 흐름 전체를 계속 통제하는 활동**이 함께 존재한다. 모든 개념을 하나의 순서로 억지로 연결하지 않는다.

```text
문제와 사용자 요구를 파악
        ↓
무엇을 만들어야 하지?
        ↓
요구공학
도출 → 분석 → 명세 → 검증
        ↓
어떤 구조로 만들지?
        ↓
Architecture · 설계
        ↓
구현 · 통합
        ↓
제대로 만들었고 실제 목적에도 맞나?
        ↓
검토 · V&V · Test
        ↓
사용할 수 있게 전달
        ↓
Release · Deployment
        ↓
운영 · 유지보수
        ↓
새로운 문제와 요구
        └──────────────→ 앞 단계로 Feedback
```

실제 개발에서는 이 활동들이 한 번씩 순서대로 끝나는 것이 아니라 반복·병렬·점진적으로 수행된다.

```text
             [제품을 만드는 흐름 전체]
요구 → Architecture·설계 → 구현 → 검증 → 배포 → 운영
 │            │             │       │       │       │
 └────────────┴─────────────┴───────┴───────┴───────┘
                         ↑
                  [전 과정 통제]
       개발 방식 · 형상/변경관리 · 품질관리
       프로젝트 관리 · 표준 · OSS License/IP
```

## 2. 왜 소프트웨어 개발을 공학적으로 관리할까?

소프트웨어 규모와 복잡성이 커지면 개인의 코딩 능력만으로 요구·변경·품질·일정·비용을 안정적으로 통제하기 어렵다.

```text
규모·복잡성 증가
├─ 요구 누락·오해
├─ 변경 영향 확산
├─ 품질 문제
├─ 일정·비용 초과
└─ 사람에 따른 개발 방식 편차
        ↓
Software Crisis
        ↓
Software Engineering
        ↓
반복 가능한 Process · Method · Tool로 개발 활동을 공학화
```

전체 활동의 위치를 잡는 기본 좌표가 `SDLC(Software Development Life Cycle)`다.

## 3. 무엇을 만들어야 하는지 어떻게 명확하게 할까?

잘못된 요구를 정확하게 구현해도 올바른 제품이 되지는 않는다. 그래서 구현보다 먼저 **무엇을 만들어야 하는지 검증 가능한 형태로 정리**한다.

```text
사용자 · 이해관계자의 필요
        ↓
요구공학
├─ 도출(Elicitation)
├─ 분석(Analysis)
├─ 명세(Specification)
├─ 검증(Validation)
└─ 변경관리
        ↓
요구사항
├─ 기능 요구
└─ 비기능 요구 / 품질 요구
    └─ 성능 · 가용성 · 보안 · 변경 용이성 등
```

요구는 이후 설계·구현·시험과 끊어져서는 안 된다.

```text
요구사항
  ↓ Traceability
Architecture / 설계
  ↓
구현
  ↓
시험 Case와 결과
```

`추적성(Traceability)`은 요구가 실제 구현과 검증까지 빠짐없이 이어졌는지 확인하는 핵심 연결점이다.

## 4. 요구를 어떤 구조로 구현할까?

요구가 정리되면 시스템의 큰 구조와 구성요소의 책임·관계를 결정한다.

```text
요구사항
  ↓ 특히 품질 요구가 Architecture 결정에 영향
Architecture
├─ 시스템의 큰 구조
├─ Component의 책임
├─ Component 사이 관계
└─ 주요 기술적 Trade-off
        ↓
상세 설계
├─ 모듈화
├─ 정보 은닉
├─ 응집도 ↑ / 결합도 ↓
├─ 객체지향 원칙
└─ Design Pattern
        ↓
구현
```

`UML`과 여러 Architecture View는 설계 자체라기보다 **구조와 관계를 이해관계자에게 표현하는 수단**으로 본다.

모듈화의 핵심은 단순히 파일을 나누는 것이 아니라 **변경 영향이 불필요하게 전체 시스템으로 퍼지지 않도록 책임과 경계를 나누는 것**이다.

## 5. 개발 방식은 왜 여러 가지일까?

생명주기 모델과 개발 방법론은 하나의 정답을 고르는 문제가 아니다. 요구의 안정성, 기술 위험, 피드백 필요성에 따라 반복 크기와 확인 시점을 다르게 잡는다.

```text
[생명주기 모델 선택]
요구가 안정적이고 단계별 통제가 중요한가?
├─ Yes → Waterfall 계열 검토
└─ No
    ↓
일찍 일부 기능을 제공하며 Feedback을 받을 것인가?
├─ Yes → Incremental / Iterative
└─ 위험이 크고 위험 제거가 핵심인가?
    └─ Spiral
```

현대 개발에서는 짧은 Feedback을 중심으로 여러 실천법이 조합된다.

```text
Feedback을 빨리 받기
├─ Agile
│   ├─ Scrum
│   ├─ XP
│   └─ Kanban
├─ TDD
└─ CI · 자동 Build · 자동 Test
        ↓
Release · Deployment
        ↓
DevOps
└─ 개발과 운영의 Feedback 연결
```

`Agile → Scrum → DevOps`를 하나의 발전 단계로 보지 않는다. Agile은 가치와 개발 접근, Scrum·XP·Kanban은 서로 다른 방법·실천 체계, DevOps는 개발·전달·운영을 연결하는 문화와 운영 방식에 가깝다.

## 6. 제대로 만들었는지 어떻게 확인할까?

품질은 마지막 Test 단계에서 갑자기 만들어지는 것이 아니다. 요구에서 품질 목표를 정하고 설계·구현·검증 전 과정에서 확인한다.

```text
품질 목표
  ↓
검증 가능한 품질 요구
  ↓
Review · Inspection
  ↓
V&V
├─ Verification
│   └─ 명세대로 만들었는가?
└─ Validation
    └─ 실제 사용자 목적에 맞는가?
        ↓
Test
├─ Unit
├─ Integration
├─ System
└─ Acceptance
        ↓
결함 · Coverage · 품질 지표
        ↓
원인 분석 · 개선
```

시험 수준과 시험 기법은 다른 분류축이다. Unit·Integration·System·Acceptance는 **어느 범위를 시험하는가**, Black-box·White-box 등은 **어떤 관점과 방법으로 시험하는가**를 나타낸다.

`Coverage`가 높다는 사실만으로 요구 충족이나 결함 부재가 증명되는 것은 아니다.

## 7. 계속 바뀌는 산출물과 버전을 어떻게 통제할까?

개발이 진행되면 요구·설계·Code·Test·배포 산출물이 계속 변경된다. 어느 버전이 기준인지 알 수 없으면 재현과 추적이 어려워진다.

```text
변경되는 산출물
        ↓
Software Configuration Management
├─ Configuration Item 식별
├─ Version 관리
├─ Baseline 설정
├─ 변경 통제
└─ 상태 기록·감사
```

`Baseline`은 관계자들이 공식적으로 합의한 기준 버전이다. 형상관리는 특정 개발 단계가 아니라 요구부터 운영까지 전 과정에 적용된다.

## 8. 일정·비용·위험은 어떻게 통제할까?

소프트웨어를 올바르게 만드는 것과 프로젝트를 제한된 자원 안에서 완료하는 것은 서로 다른 문제다.

```text
Project Management
├─ Scope
│   └─ WBS
├─ Schedule
│   └─ CPM 등
├─ Cost
│   └─ EVM 등
├─ Risk
├─ Quality
└─ Stakeholder
```

```text
Project
↓ 관련 Project를 함께 조정
Program
↓ 전략 목표에 맞춰 투자·우선순위 관리
Portfolio
```

`PMO`는 여러 프로젝트의 표준·지원·통제를 조직 차원에서 제공하는 역할로 본다.

CPM·EVM의 계산 자체보다 **무엇을 측정하고 어떤 관리 판단에 쓰는지**를 먼저 이해한다.

## 9. 외부에서 가져온 소프트웨어와 표준은 어떻게 다룰까?

개발팀이 직접 작성한 Code만 관리하는 것이 아니다. OSS와 외부 Component를 사용하면 라이선스·지식재산권·공급망 위험이 생긴다.

```text
외부 Software 사용
├─ OSS
│   ├─ License 의무
│   ├─ 사용·수정·배포 조건
│   └─ OSS Governance / 공급망 통제
└─ IP(Intellectual Property)
    └─ 저작권 · 특허 등
```

표준은 특정 기술 이름을 암기하기보다 **무엇을 평가·관리하기 위한 표준인지**를 관계 중심으로 본다.

```text
표준·모델
├─ SW 품질 모델
├─ 생명주기 Process
├─ Process 평가·개선
├─ 기능 안전
└─ 서비스 품질
```

표준과 라이선스는 개정·폐지·버전에 따라 내용이 달라질 수 있으므로 실제 적용 시 최신 공식 자료를 확인한다.

## 10. 전체 흐름을 가로지르는 핵심 관점

```text
소프트웨어 공학
│
├─ 추적성
│   └─ 요구 ↔ 설계 ↔ 구현 ↔ 시험
│
├─ Feedback
│   └─ 결과를 빨리 확인해 잘못된 방향의 비용을 줄임
│
├─ 모듈화
│   └─ 책임과 경계를 나눠 변경 영향 확산을 줄임
│
├─ 위험 기반 선택
│   └─ 상황에 맞는 생명주기·개발 방식을 선택
│
└─ 품질 내재화
    └─ 품질을 마지막 Test가 아니라 요구부터 운영까지 관리
```

이 관점들은 하나의 개발 단계에 속하지 않고 여러 개념을 연결한다.

## 11. 기억할 핵심 경계

| 헷갈리기 쉬운 개념 | 핵심 경계 |
|---|---|
| SDLC ↔ 생명주기 모델 | 전체 개발 생명주기 ↔ 생명주기를 구성·진행하는 방식 |
| 요구공학 ↔ 요구사항 | 요구를 찾아·분석·명세·관리하는 활동 ↔ 그 활동의 핵심 산출물 |
| Architecture ↔ 상세 설계 | 시스템 전체의 큰 구조·책임·Trade-off ↔ 내부 Component·Module 수준 구체화 |
| Architecture ↔ UML | 구조와 주요 결정 ↔ 구조 등을 표현하는 Modeling 언어 |
| Verification ↔ Validation | 명세대로 만들었는가 ↔ 실제 목적에 맞는가 |
| Test Level ↔ Test Technique | 시험 범위 ↔ 시험 관점·방법 |
| Release ↔ Deployment | 제공할 변경 단위 확정 ↔ 실행 환경에 실제 적용 |
| 형상관리 ↔ Project 관리 | 제품·산출물의 버전과 변경 통제 ↔ 범위·일정·비용·위험 통제 |
| Agile ↔ Scrum | 가치·원칙 중심의 개발 접근 ↔ Agile을 실천하는 Framework 중 하나 |
| CI ↔ DevOps | 변경을 지속 통합·검증하는 Practice ↔ 개발·전달·운영을 연결하는 더 넓은 문화·운영 방식 |

## 12. 한 번에 다시 떠올리기

```text
복잡한 SW 개발을 개인 역량만으로 통제하기 어렵다
        ↓
Software Engineering · SDLC
        ↓
무엇을 만들지?
        ↓
요구공학
도출 → 분석 → 명세 → 검증
        ↓ Traceability
어떤 구조로 만들지?
        ↓
Architecture → 상세 설계 → 구현
        ↓
제대로 만들었나? 실제 목적에 맞나?
        ↓
Review · Verification · Validation · Test
        ↓
Release → Deployment → 운영
        ↓
운영 Feedback ─────────────→ 요구·설계·개발로 환류

──────────── 전체를 가로지름 ────────────
개발 방식 · 형상/변경관리 · 품질관리
Project 관리 · 표준 · OSS License/IP

──────────── 반복해서 떠올릴 관점 ────────────
추적성 · Feedback · 모듈화 · 위험 기반 선택 · 품질 내재화
```

> **무엇을 만들지 요구로 명확히 하고 → 변경에 견딜 구조를 설계하고 → 구현·검증·배포·운영하며 → 결과를 다시 앞 단계로 Feedback한다. 개발 방식·형상·품질·프로젝트·외부 제약은 이 전체 흐름을 계속 통제한다.**
