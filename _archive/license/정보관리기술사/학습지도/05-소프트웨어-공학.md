# Vol. 5 소프트웨어 공학 학습지도

> 기준: 정보관리기술사 단독 대비를 위한 1차 학습지도다. 먼저 개념이 왜 필요하고 서로 어떻게 이어지는지 이해한 뒤, 중요도에 따라 학습 깊이를 다르게 한다. A는 답안으로 작성할 핵심, B는 역할과 관계를 이해할 내용, C는 이름과 위치만 확인할 내용이다. 실제 기출을 확인한 뒤 등급을 보정한다.

## 이 권의 역할

소프트웨어 공학은 불확실한 요구를 운영 가능한 제품으로 바꾸고, 변경·품질·일정·비용 위험을 생명주기 전체에서 통제하는 방법을 제공한다.

핵심 질문은 세 가지다.

1. 요구에서 설계·구현·검증·운영까지 추적 가능한 흐름을 어떻게 만드는가?
2. 개발 방식과 아키텍처를 상황에 맞게 선택하고 변경 비용을 어떻게 낮추는가?
3. 품질·일정·비용·라이선스·표준 위험을 어떻게 측정하고 통제하는가?

## 권 내부 큰 그림

SW공학에는 두 종류의 개념이 있다. 하나는 제품을 만드는 흐름에 놓이는 개념이고, 다른 하나는 그 흐름 전체를 계속 통제하는 개념이다.

- **제품 생명주기**: 무엇을 만들지 정하고, 설계하고, 구현·시험·배포·운영하는 흐름
- **횡단 통제**: 어느 한 단계에서만 하는 것이 아니라 전 과정에 적용되는 관리 활동

모든 토픽을 억지로 한 줄에 놓지 말고, 먼저 두 종류 중 어디에 속하는지 구분한다.

```text
[제품을 만드는 흐름]

해결할 문제와 사용자 요구 파악
→ 요구 도출·분석·명세·검증
→ 아키텍처·설계: 전체 구조와 구성요소의 책임 결정
→ 구현·통합: 코드를 만들고 구성요소를 결합
→ 검증·시험: 요구대로 만들었고 실제 목적에 맞는지 확인
→ 릴리스·배포: 검증된 변경을 사용할 수 있는 상태로 전달
→ 운영·유지보수
→ 운영에서 얻은 문제와 요구를 앞 단계로 환류

※ 실제 개발에서는 위 활동이 한 번씩 순서대로 끝나는 것이 아니라 반복·병렬·점진적으로 수행된다.

[전 과정에 적용되는 통제]

● 개발 방식: 불확실성과 위험에 맞춰 반복 크기와 피드백 주기를 정한다.
● 형상·변경관리: 무엇이 바뀌었고 어떤 버전이 기준인지 통제한다.
● 품질관리: 품질 목표를 세우고 검토·Test·지표로 확인한다.
● 프로젝트 관리: 범위·일정·비용·위험·이해관계자를 통제한다.
● 외부 제약: 표준, OSS License, 지식재산권(IP) 준수 여부를 확인한다.
```

중심은 다음 다섯 가지다.

- **추적성**: 요구가 설계·코드·시험까지 빠짐없이 연결됐는지 확인한다.
- **피드백**: 결과를 빨리 확인해 잘못된 방향으로 오래 개발하는 위험을 줄인다.
- **모듈화**: 책임을 나누고 결합을 줄여 변경이 전체로 퍼지는 것을 막는다.
- **위험 기반 선택**: 정답처럼 하나의 방법론을 쓰지 않고 상황에 맞는 방식을 고른다.
- **품질 내재화**: 마지막에 시험만 하는 것이 아니라 요구·설계·구현부터 품질을 만든다.

### 먼저 알아둘 용어

| 용어 | 쉬운 뜻 |
|---|---|
| SDLC(Software Development Life Cycle, 소프트웨어 개발 생명주기) | 소프트웨어를 구상하고 개발·운영·폐기하기까지의 전체 흐름 |
| 요구공학 | 사용자가 정말 필요로 하는 것을 찾아 명확히 기록하고 변경을 관리하는 활동 |
| 아키텍처 | 시스템의 큰 구조와 구성요소의 책임·관계를 정한 것 |
| 추적성 | 하나의 요구가 설계·코드·시험 결과까지 이어지는 관계 |
| 형상관리 | 산출물의 버전과 변경 이력을 식별하고 통제하는 활동 |
| 기준선(Baseline) | 관계자들이 공식적으로 합의한 기준 버전 |
| 검증(Verification) | 정해진 명세와 절차에 맞게 만들었는지 확인 |
| 확인(Validation) | 완성된 제품이 실제 사용자 목적에 맞는지 확인 |
| 릴리스 | 배포할 기능과 변경사항을 하나의 제공 단위로 확정하는 활동 |
| 배포 | 확정된 소프트웨어를 실제 실행 환경에 설치·적용하는 활동 |

## 권장 학습 순서

전체 학습 흐름: `개인 개발을 조직적인 공학 활동으로 전환 → 요구 파악 → 구조와 설계 결정 → 짧은 주기로 개발·전달 → 품질 검증 → 일정·비용 통제 → 표준·라이선스 확인`

아래 화살표는 인과 관계가 아니라 **이것을 먼저 이해하면 다음 내용을 배우기 쉽다는 선행 순서**다. 이 순서가 위의 개념 구조를 대체하지 않는다.

### 1단계: 공학화와 생명주기

`SW 위기·공학 → SDLC → 모델 선정 → 검토·Inspection·Walkthrough → Baseline·형상통제`

개발이 개인 코딩이 아니라 반복 가능한 조직 활동이어야 하는 이유부터 잡는다. 폭포수·증분·나선형은 암기 목록이 아니라 요구 안정성, 위험, 피드백 주기에 따른 선택지로 비교한다.

### 2단계: 요구·설계·아키텍처

`요구공학 → 기능·품질 요구 → 아키텍처 결정 → View·Model로 표현 → 모듈화·객체지향 설계`

요구가 모호하거나 계속 바뀌면 잘못된 제품을 만들기 쉽다. 먼저 요구를 검증 가능한 형태로 정리하고, 성능·가용성·변경 용이성 같은 품질 요구를 기준으로 전체 구조를 결정한다. View와 UML은 이 구조를 이해관계자별로 설명하는 표현 수단이다. Java 코드 변환은 표기 의미를 확인하는 보조 실습이지 정보관리 답안의 목표가 아니다.

### 3단계: 개발 방법과 전달 흐름

`전통 개발 → Agile·Scrum·XP·Kanban → TDD → CI·자동 Build·Test → Release·배포 → DevOps·운영 피드백`

결과를 자주 확인하면 요구를 잘못 이해했거나 코드가 깨진 사실을 빨리 발견할 수 있다. Agile은 작업 단위와 피드백 주기를 짧게 하고, CI와 자동시험은 변경을 반복 검증하며, DevOps는 개발·배포·운영의 책임과 피드백을 연결한다. 행사나 도구 이름보다 이 관계를 먼저 이해한다.

### 4단계: 품질과 시험

`품질 목표 → 검증 가능한 요구 → 검토 → V&V·Test 설계 → Coverage·결함 지표 → 원인분석·개선`

먼저 원하는 품질을 측정 가능한 요구로 바꾼다. 문서와 설계는 검토로 확인하고, 실행 가능한 제품은 적절한 시험 수준과 기법으로 검증한다. 코드 Coverage는 코드가 얼마나 실행됐는지를 보여주는 지표일 뿐, 요구 충족이나 결함 부재를 증명하지는 않는다.

### 5단계: 프로젝트 통제

`프로젝트·Program·포트폴리오 → PM Process·PMO → 범위·WBS → Schedule·CPM → 위험·이해관계자 → EVM`

범위가 작업과 일정·원가 기준선을 만들고, 실적 데이터가 예측과 시정조치로 이어지는 구조를 익힌다. CPM·EVM 계산은 지표 의미를 설명할 수 있을 만큼만 손으로 확인한다.

### 6단계: 생태계·표준

`OSS·License·IP → SW 품질모델 → 생명주기·프로세스 평가 표준 → 기능안전·서비스 품질`

라이선스는 사용·수정·배포 조건과 공급망 통제로, 표준은 목적·적용 대상·산출물 관계로 학습한다. 표준은 개정·폐지·대체 여부를 최신 공식 문서에서 확인하고, 라이선스는 해당 소프트웨어에 실제 적용된 버전의 원문을 확인한다.

## 토픽 간 연결

```text
요구가 불완전하고 변경됨
→ 짧은 피드백과 Prototype·Increment 필요
→ 변경이 구조 전체로 전파될 위험
→ 모듈화·정보은닉·낮은 결합·아키텍처 View 적용
→ 변경 단위를 형상항목과 Baseline으로 통제
→ 자동 Build·테스트로 회귀 위험 관측
→ 운영 결과를 다음 요구와 Backlog에 환류
```

```text
품질 목표 정의
→ 요구의 검증 가능 조건으로 구체화
→ 검토로 정적 결함 예방
→ Test 수준·기법·Oracle 설계
→ Coverage·결함·운영 지표 측정
→ 위험이 큰 영역에 시험 집중
→ 원인 분석과 Process 개선
```

```text
승인된 범위
→ WBS·Activity·의존관계
→ Schedule·Cost Baseline
→ 수행 실적 PV·EV·AC 수집
→ SV·CV·SPI·CPI로 편차 진단
→ 원인·예측·시정조치·변경통제
```

## 1차 회독 통과 경로

첫 회독에서는 174개 토픽을 모두 외우지 않는다. 다음 여섯 관계를 쉬운 말로 설명할 수 있으면 된다.

1. 요구가 불확실하므로 상황에 맞는 생명주기와 피드백 주기를 선택한다.
2. 요구와 품질 목표가 아키텍처·설계·시험의 근거가 되고, 추적성이 그 연결을 증명한다.
3. 모듈화와 낮은 결합도는 변경이 시스템 전체로 퍼지는 것을 막는다.
4. 형상관리로 변경을 승인하고, 자동 Build·Test·배포로 안전하게 전달한다.
5. 검토는 실행 전에 산출물을 확인하고, Test는 실행 결과로 결함과 요구 충족을 확인한다.
6. 범위를 WBS·일정·원가 기준선으로 바꾸고 EVM으로 계획과 실적의 차이를 통제한다.

## 보정 기록

### 3단계(현행성 보정)

- `DevOps`, `Agile`, `Scrum`, `TDD`는 분리된 도구명이 아니라 `요구 변경 → 피드백 → 회귀 통제` 흐름으로 묶어 정리한다.
- `[현행]` 표기가 붙은 `Java·JVM` 계열은 API 상세보다 런타임 제약, 배포 안정성, 보안 경계의 책임 분리 문장으로 정리한다.
- `ISO/IEC/IEEE 12207:2017`은 폐지되고 `12207:2026`으로 교체되었다. 버전 암기보다 전체 생명주기와 프로세스·산출물·적용 대상의 관계를 본다.
- 아키텍처 Description은 `ISO/IEC/IEEE 42010:2022`, PM은 `PMBOK Guide 제8판(2025)`을 기준으로 보정한다. 버전 자체보다 책임 주체와 산출물의 연결을 본다.

아직 공식 출제기준과 최근 기출을 반영하지 않은 1차 분류다.

- 요구·아키텍처·Agile/DevOps·Test·PM이 결합된 사례형 질문은 구성 요소별 깊이를 함께 승급한다.
- PMBOK, ISO/IEC, IEEE, 품질모델, License는 출제 시점의 최신 공식 판과 대체 관계를 확인한다.
- 코드 작성·Diagram 변환·CPM/EVM 계산은 반복 출제된 형식만 최소 실습으로 승급한다.
- 구형 표준은 역사적 개념 가치와 현재 적용 가능성을 분리하고, 폐지·대체 사실을 답안에 명시한다.
- 변경 시 `기존 등급 → 새 등급`, 근거 회차, 질문 형태를 기록한다.
