# Vol. 8 데이터베이스 학습지도

> 기준: 정보관리기술사 단독 대비를 위한 1차 학습지도다. 먼저 데이터베이스가 해결하는 문제와 개념 사이의 관계를 이해하고, 중요도에 따라 학습 깊이를 다르게 한다. A는 답안으로 작성할 핵심, B는 역할과 관계를 이해할 내용, C는 이름과 위치만 확인할 내용이다. 실제 기출을 확인한 뒤 등급을 조정한다.

## 이 권의 역할

데이터베이스는 흩어진 데이터를 일정한 구조와 규칙으로 저장하고, 여러 사용자가 빠르고 안전하게 이용할 수 있도록 관리한다. 단순한 저장소가 아니라 **데이터의 의미·정확성·동시 사용·장애 복구·성능·보안과 품질을 함께 책임지는 체계**다.

핵심 질문은 세 가지다.

1. 업무에서 사용하는 데이터를 어떤 구조와 규칙으로 표현할 것인가?
2. 여러 사용자가 동시에 접근하거나 장애가 발생해도 정확한 데이터를 어떻게 유지할 것인가?
3. 데이터가 많아져도 빠르고 안전하게 처리하려면 저장·검색·분산·보안 방식을 어떻게 선택할 것인가?

## 권 내부 큰 그림

DB 개념은 모두 한 줄로 이어지지 않는다. 먼저 데이터의 의미와 구조를 정한 뒤, 세 가지 다른 문제를 해결한다.

- **정확성**: 잘못된 값과 중복·누락을 어떻게 막을 것인가?
- **트랜잭션 신뢰성**: 여러 사용자가 동시에 접근하거나 장애가 나도 올바른 결과를 어떻게 보장할 것인가?
- **성능·확장성**: 데이터가 많아져도 원하는 정보를 빠르게 찾고 처리하려면 어떻게 할 것인가?

보안·품질·메타데이터·거버넌스는 마지막 단계가 아니라 이 전 과정에 적용된다.

```text
[데이터의 의미와 구조를 정하는 흐름]

업무에서 필요한 정보 파악
→ 개념 모델: 어떤 대상과 관계를 관리할지 표현
→ 논리 모델: Table·Column·Key·제약조건으로 구체화
→ 정규화: 중복과 삽입·수정·삭제 이상을 줄임
→ 물리 설계: 저장 구조·인덱스·파티션을 결정
→ SQL로 저장·조회·변경

[정확한 처리를 보장하는 두 갈래]

Transaction·ACID
├─ 동시성 제어: 여러 사용자가 동시에 접근해도 잘못된 결과를 막음
│  └─ Lock·직렬성·격리수준·Deadlock
└─ 장애 회복: 처리 도중 장애가 나도 일관된 상태로 되돌림
   └─ Log·Undo/Redo·Checkpoint

※ Backup은 장기 보존본에서 복원하는 수단이고, Transaction 회복과 목적·시간 범위가 다르다.

[빠른 처리와 확장을 위한 흐름]

질의와 업무 처리 패턴 파악
→ 실행계획·I/O·대기시간 측정
→ Index·Hash·Partition 등 접근 구조 선택
→ 질의·Schema·설정 Tuning
→ 한 서버의 한계를 넘으면 Replication·Sharding·분산 DB 검토

[전 과정에 적용]

보안·권한·감사 / 데이터 품질·표준·메타데이터 / 데이터 거버넌스

[데이터 활용]

DW·OLAP·BI / 분석·마이닝 / 스트리밍·분산 데이터 서비스
```

DB 설계에서 중요한 것은 다음 개념이 왜 필요한지 이해하는 것이다.

- 업무 용어가 제각각이면 같은 데이터를 서로 다르게 해석한다. 그래서 **표준·메타데이터·개념 모델**이 필요하다.
- 한 Table에 모든 값을 넣으면 중복과 이상현상이 생긴다. 그래서 **Key·제약조건·정규화**가 필요하다.
- 여러 사용자가 동시에 값을 바꾸면 결과가 꼬일 수 있다. 그래서 **Transaction·동시성 제어**가 필요하다.
- 처리 도중 장애가 나면 일부 변경만 남을 수 있다. 그래서 **Log·Undo/Redo·회복**이 필요하다.
- 데이터가 늘면 전체를 매번 읽을 수 없다. 그래서 **Index·Partition·Tuning**이 필요하다.
- 한 서버로 감당하기 어렵다면 복제·샤딩·분산 DB를 검토하지만, 일관성과 운영 복잡성이라는 대가가 생긴다.

### 먼저 알아둘 용어

| 용어 | 쉬운 뜻 |
|---|---|
| 스키마(Schema) | 데이터의 구조·관계·제약조건을 정의한 설계도 |
| 인스턴스(Instance) | 특정 시점에 DB에 실제로 저장된 데이터 |
| 데이터 독립성 | 저장 방식이나 구조 일부가 바뀌어도 응용프로그램의 변경을 줄이는 성질 |
| 엔터티(Entity) | 업무에서 따로 관리할 가치가 있는 사람·사물·사건 등의 대상 |
| Key | 행을 식별하거나 Table 사이의 관계를 연결하는 속성 |
| 정규화 | 중복과 삽입·수정·삭제 이상을 줄이도록 Table을 분해하는 과정 |
| Transaction | 하나의 논리적 업무로 함께 성공하거나 실패해야 하는 작업 단위 |
| ACID(Atomicity·Consistency·Isolation·Durability) | Transaction이 안전하게 처리되기 위한 원자성·일관성·격리성·지속성 |
| 직렬성 | 동시에 실행한 결과가 어떤 순서로 하나씩 실행한 결과와 같아지는 성질 |
| 회복(Recovery) | 장애 후 DB를 올바르고 일관된 상태로 되돌리는 활동 |
| Index | 전체 Table을 읽지 않고 원하는 행을 빨리 찾기 위한 별도 접근 구조 |
| Partition | 하나의 큰 Table이나 Index를 일정 기준으로 나누어 관리하는 방식 |
| Sharding | 데이터를 여러 독립 DB에 나누어 저장하고 처리 부하를 분산하는 방식 |
| Metadata | 데이터의 의미·형식·소유자·위치·변경 이력 등을 설명하는 데이터 |
| 데이터 거버넌스 | 데이터에 관한 의사결정권·책임·표준·품질·보안 원칙을 정하는 체계 |
| DBMS(Database Management System, 데이터베이스 관리시스템) | 여러 사용자가 데이터를 안전하게 저장·조회·변경하도록 관리하는 소프트웨어 |
| SQL(Structured Query Language, 구조화 질의어) | 관계형 DB의 구조와 데이터를 정의·조회·변경·통제하는 언어 |
| 2PL(Two-Phase Locking, 2단계 잠금) | Lock을 얻는 단계와 해제하는 단계를 나누어 직렬성을 보장하는 방식 |

## 권장 학습 순서

아래 구분은 관련 주제를 함께 공부하기 위한 권장 순서다. 실제 기술·업무의 처리 절차를 뜻하지 않으며, 선행관계가 약한 단계는 병행해도 된다.

전체 학습 흐름: `DBMS 기본·데이터 독립성 → 모델링·정규화 → SQL·질의 → 무결성·동시성·회복 → 저장·인덱스·성능 → (선택) 분산·DB 유형 → (활용) DW·BI`

4단계(처리 신뢰성)와 5단계(성능·확장성)는 서로 목적이 다른 영역이다. 분산 DB와 DW·BI도 필요할 때 보강하는 영역이므로 반드시 마지막까지 순서대로 이어지는 것은 아니다.

### 1단계: 데이터와 DBMS 기본

`DB 정의(2~4) → ANSI/SPARC(5·12) → DBMS 정의·역할(7) → 생명주기(10) → 데이터 독립성(13) → 스키마/인스턴스(8)`

데이터 독립성·스키마 개념 없이 쿼리나 트랜잭션을 본다면 설계/운영 판단 근거가 약해진다.

### 2단계: 모델링 기반 구조 정리

`데이터 모델링 절차(16) → ER 표기(17) → EER/일반화(21) → 정규화(29~34) → 반정규화(41~43)`

표기와 관계 제약을 먼저 정리하면 정규화·반정규화가 무슨 비용-이득을 갖는지 설명할 수 있다.

### 3단계: SQL과 질의 모델

`SQL 3언어(44) → 질의 작성 45~54 → 관계 연산/조인 개념(23~24) → 뷰(54)`

질의 작성은 문법 암기가 아니라 **무엇을 걸러내고 집계·결합하는지가 문제 해결에 맞는지**를 본다.

### 4단계: 트랜잭션·동시성·회복

`공통 기반: Transaction·ACID(61)`

`동시 실행 문제: 동시성 이상(62~70) → Lock·2PL·직렬성·Deadlock(71~77)`

`장애 문제: 장애 회복(55~59) → Log·Undo/Redo·Checkpoint → Backup(60)과 회복 범위 비교`

동시성 제어와 회복은 ACID를 함께 지키지만 해결하는 문제가 다르다. 동시성 제어는 여러 작업이 겹쳐 생기는 잘못된 결과를 막고, 회복은 장애로 일부 변경만 남는 문제를 해결한다. Backup은 별도 보존본에서 복원하는 수단이므로 Transaction Log를 이용한 회복과 구분한다.

### 5단계: 성능·저장·확장성

`단일 DB 성능: 질의·업무 패턴 → 성능 계측(122~123) → 병목 확인 → Index·Hash·Partition·질의 Tuning(78~83·124~139) → 재측정`

`규모 확장: 한 서버의 한계 확인 → Replication·Sharding·분산 DB(109~113·124~127) 검토`

두 흐름을 구분한다. 먼저 느린 질의와 I/O·Lock 대기 등 병목을 측정하고 단일 DB 안에서 개선한 뒤 다시 측정한다. 한 서버의 처리량·용량·가용성 한계를 넘을 때 복제·샤딩·분산 DB를 검토하며, 이때 일관성과 운영 복잡성이라는 비용이 생긴다. 보안·품질·거버넌스는 설계와 운영 전체에 적용한다.

### 선택 보강

기출에서 빅데이터·데이터 엔지니어링이 붙으면 `DW·데이터 마이닝(84~97)`과 `분산 DB(109~113)`를 집중 보강한다.

## 토픽 간 연결

### 설계에서 무결성으로

```text
요구사항 분해
→ ER 모델(엔터티·관계)
→ 정규화 및 Key 제약
→ SQL 질의의 정확성 확보
→ 동시성·회복 통제로 일관성 유지
→ 감사·품질 지표로 운영 상태 확인
```

설계 단계에서 빠진 제약은 트랜잭션 이상으로 돌아온다.

### 성능과 저장 구조

```text
질의·업무 패턴
→ 실행계획·I/O·Lock 대기 등 측정
→ 병목 원인 확인
→ 인덱스·해시·파티션·질의 개선 선택
→ 개선 결과 재측정
→ 단일 DB의 한계를 넘을 때 복제·샤딩·분산 DB 검토
→ 품질 지표와 운영 규칙 갱신
```

성능은 초당 처리 건수만으로 판단하지 않는다. 장애 복구에 걸리는 시간과 감사 기록을 남기는 비용도 함께 고려한다.

### 분산·클라우드로 확장

```text
단일 DB나 기존 운영 방식의 한계
├─ 읽기 부하·가용성: Replication 검토
├─ 쓰기 부하·데이터 규모: Sharding·분산 DB 검토
├─ 변경 데이터 전달: CDC 검토
└─ 다수 고객의 자원 공유: 멀티테넌시 검토
→ 선택한 구조에 맞춰 일관성·보안·책임 경계 결정
→ 감사·품질·운영 지표로 관리
```

## 1단계 보강 반영(Vol.8)

### 핵심 템플릿

`업무에서 필요한 데이터 → 구조와 관계를 나타낸 모델 → 정확성을 지키는 규칙 → 동시 접근과 장애에 대한 통제 → 성능·보안·품질 측정` 순서로 설명한다. 클라우드나 분산 환경이 제시된 경우에만 공급자와 사용자의 책임 경계를 추가한다.

### Vol.8 + Vol.9 연계 정리

- 데이터 설계는 AI 학습 데이터의 편향·누락이 지표로 바로 들어오므로, `데이터 표준화`, `메타데이터`, `품질(정확성·완전성·일관성)`을 먼저 점검한다.
- 모델 보안 질문은 `XAI`보다 앞서 `학습 데이터 수집/라벨링·품질 통제`가 선행되어야 한다는 흐름으로 정리한다.

### Vol.8 + Vol.10 연계 정리

- CDC, 샤딩, 분산 DB는 멀티테넌시 환경에서 `RTO/RPO`, `책임 분리`, `감사 추적성`이 함께 언급되어야 한다.
- Multi/Hybrid 전환은 성능 비교보다 `이동 데이터량`, `규제 적용 구간`, `운영권한 변경점`을 우선 확인한다.
