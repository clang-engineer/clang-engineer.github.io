# Vol. 10 클라우드 학습지도

> 기준: 정보관리기술사 단독 대비를 위한 1차 분류다. 출제 여부를 고정값으로 두지 않고, 공식 출제기준·최신 기출을 보며 A/B/C를 보정한다.

## 이 권의 역할

클라우드는 서버·스토리지·네트워크를 직접 구매해 소유하는 대신, 필요할 때 서비스로 빌려 쓰는 운영 방식이다. 자원을 빨리 준비하고 사용량에 맞게 늘리거나 줄일 수 있지만, 공급자에게 넘기는 책임과 직접 관리해야 할 책임을 분명히 해야 한다.

핵심 질문은 세 가지다.

1. 어떤 시스템을 클라우드로 옮기고 어떤 것은 내부에 남길 것인가?
2. 어느 기능까지 공급자에게 맡기고, 성능·비용·가용성을 어떻게 맞출 것인가?
3. 여러 사용자가 자원을 공유하는 환경에서 보안·법규·장애 대응 책임을 어떻게 나눌 것인가?

## 권 내부 큰 그림

`→`는 설계·생명주기 순서, `├─`는 병렬 설계 축, `[횡단]`은 전 과정에 적용하는 통제를 나타낸다. 배치·서비스·실행은 단계라서가 아니라 **함께 결정해야 하는 독립적인 설계 축**이며, 보안·규제·SLA는 마지막 단계가 아니라 초기부터 설계를 제약한다.

```text
사업 목표·워크로드·기존 자산 + 규제·데이터 주권·SLA/SLO·비용·복구 목표
→ 목표 운영모델과 공유 책임 경계 (제약이 초기 설계를 좌우)

[병렬 설계 축]

├─ 배치 위치 선택: Public / Private / Hybrid / Multi / Sovereign / Edge
├─ 서비스 유형 선택: IaaS / PaaS / SaaS / Serverless / XaaS
└─ 실행 방식 선택: Bare Metal / VM / Container / 관리형 플랫폼

→ 아키텍처 구성(컴퓨팅·네트워크·스토리지, 클라우드 네이티브·MSA·Kubernetes)
→ 전환: 대상 선정 → 검증 → 이전 → 전환/롤백
→ 운영: 관측 → 용량·확장(자동 확장) → 장애·DR 대응
→ 비용·성능·보안 KPI 평가로 환류

[횡단 통제: 전 과정에 교차]
보안·IAM·격리, 규제·감사, SLA/SLO, 비용 관리

[병렬 대안]
HCI·Open스택·Converged Infrastructure·VDI — 운영 방식·도입 대안
```

클라우드는 기술 이름의 모음이 아니다. 무엇을 직접 관리하고 무엇을 공급자에게 맡길지 정하는 운영 방식으로 이해해야 한다.

### 먼저 알아둘 약어

| 약어 | 원어·쉬운 뜻 |
|---|---|
| SLA·SLO | Service Level Agreement·Service Level Objective, 합의한 서비스 수준과 이를 판단하는 구체적인 목표 |
| IaaS | Infrastructure as a Service, 서버·스토리지·네트워크 기반을 빌려 쓰는 서비스 |
| PaaS | Platform as a Service, 애플리케이션 개발·실행 환경까지 제공받는 서비스 |
| SaaS | Software as a Service, 완성된 소프트웨어를 서비스로 이용하는 방식 |
| VM | Virtual Machine, 물리 장비의 자원을 나누어 만든 독립적인 가상 실행환경 |
| IAM | Identity and Access Management, 사용자 신원과 접근권한을 관리하는 체계 |
| DR | Disaster Recovery, 재해로 중단된 시스템과 데이터를 복구하는 활동 |
| HCI | Hyper-Converged Infrastructure, 컴퓨팅·스토리지·네트워크 관리를 하나의 기반으로 통합한 구조 |
| VDI | Virtual Desktop Infrastructure, 중앙 서버에서 가상 Desktop을 제공하는 기반 |

## 권장 학습 순서

아래 구분은 관련 주제를 함께 공부하기 위한 권장 순서다. 실제 기술·업무의 처리 절차를 뜻하지 않으며, 선행관계가 약한 단계는 병행해도 된다.

전체 학습 흐름: `클라우드의 가치와 제약 → 서비스 유형 선택(IaaS·PaaS·SaaS·Serverless) → 실행 방식 선택(가상머신·컨테이너) → 네트워크·스토리지 구성 → 보안·책임 기준 적용 → 운영·확장·전환`

아래 화살표는 선행 학습 순서다. 배치·서비스·실행은 단계별 인과가 아니라 **함께 결정해야 할 병렬 설계 축**이며, 보안·규제·SLA는 마지막 단계가 아니라 초기부터 제약으로 적용한다.

### 1단계: 클라우드 가치·유형·제약

`클라우드 개요·가치(1~6) → 배치 유형(7~16) → SLA·규제·데이터 주권(13·15·33) → 계산 패러다임(17~20)`

보안·규제·SLA·복구 목표를 초기 설계 제약으로 두어야 이후 책임 경계가 고정된다.

### 2단계: 서비스 유형과 책임 범위

`IaaS/PaaS/SaaS(23·30) → XaaS·BaaS(25~29) → 클라우드 SLA 유형(33) → Serverless(34)`

서비스 유형을 고를 때는 가격뿐 아니라 사용자가 어디까지 볼 수 있고 관리할 수 있는지 확인해야 한다. 서버리스는 가상머신이나 컨테이너의 다음 세대가 아니라, 실행환경 관리를 공급자에게 더 많이 맡기는 별도의 서비스 방식이다.

### 3단계: 실행 방식(가상화·컨테이너)

`가상화 원리·유형(35~37) → 서버·데스크톱·스토리지 가상화(38~49) → 하이퍼바이저·VM/Container(50~55) → Thin/Zero Client(56~58)`

같은 업무라도 가상머신·컨테이너·관리형 서비스를 무엇으로 실행하느냐에 따라 배포와 운영의 어려움, 장애가 퍼지는 범위가 달라진다.

### 4단계: 기반 구성(네트워크·스토리지)

`SDN·NFV(59~61) → 인프라 아키텍처·Spine-Leaf(62~70) → 스토리지 티어링·유형·RAID(71~86)`

네트워크와 저장장치가 늘어난 부하를 감당하지 못하면 컴퓨팅 자원만 자동으로 늘려도 성능은 좋아지지 않고 비용만 커질 수 있다.

### 5단계: 전 과정의 보안·책임 기준

`클라우드 보안·멀티테넌시(87·89) → SECaaS(88) → 인증·ISO(90~92) → CASB·포렌식·BYOD(93~96)`

보안 항목은 항상 SLA·감사 근거로 되돌아간다.

### 6단계: 운영·확장·전환

`관측·용량 → 자동 확장(97~99) → 클라우드 네이티브·MSA·Kubernetes(100~104) → 병렬 대안(HCI·Open스택·VDI: 107~114) → 전환·조직(110·115~116)`

자동화가 목적이 아니라 실패·확대·통제 관측이 가능한 운영 구조를 확보하는 데 목적이 있다. 자동 확장은 HA·DR·백업을 대체하지 않는다.

## 토픽 간 연결

### 자원 경계와 운영 책임

```text
사업 목표·워크로드 + 규제·SLA·복구 목표 (제약 선행)
→ 목표 운영모델·공유 책임 경계
→ 병렬 설계 축
│  ├─ 배치: 유형(7~16)
│  ├─ 서비스: IaaS/PaaS/SaaS·Serverless(21~34)
│  └─ 실행: 가상화·VM/Container(35~58)
→ 네트워크·스토리지 정책(59~86)
→ 보안·감사 통제(87~96)
→ 자동확장·운영·전환(97~116)
```

초기 설계에서 경계를 확정하지 않으면 SLA와 책임 분할이 무너진다.

### 신뢰성 설계 흐름

```text
워크로드·SLO 요구
→ 아키텍처·용량 설계(서버/스토리지/네트워크 선택)
→ 관측 지표 설정
→ 자동 확장 정책으로 부하 대응
→ HA/DR/백업 정책(다른 권과 연결)
→ 모니터링·감사 로그·인시던트 대응
```

클라우드에서 성능은 비용, 보안은 법규/책임 분리와 함께 판단해야 한다. 자동 확장은 인프라·용량 설계 뒤에 오며 HA·DR·백업을 대체하지 않는다.

### 전환 의사결정

```text
현재 전산실 구조 진단
→ 분할/적용 대상 선정
→ HCI/VDI/컨버지드 도입대안 비교
→ 이전 계획과 테스트·롤백
→ 운영 KPI/보안 KPI로 성과 환류
```

## 1단계 보강 반영(Vol.10)

### 핵심 템플릿

`요청(서비스 변화)` → `클라우드 경계 설정` → `보안/규제 제약` → `운영 자동화` → `감사·KPI 회귀` 순으로 답안의 기본 뼈대를 둔다.

### Vol.8 연계 정리

- 분산 DB/ CDC·샤딩 언급 시 성능 비교 이전에 `데이터 이동 비용`, `오류 전파 범위`, `책임 전이(공유 책임)`를 먼저 제시한다.
- 데이터 거버넌스 중심 질문은 `메타데이터·품질 지표·권한 모델`의 3축으로 축약해 DB·AI와 연결한다.

### Vol.9 연계 정리

- AI 오퍼레이션 질문이 나오면 인프라 답안에서 `MLOps` 이전에 `개인정보/보안 경계`, `모니터링 체계`, `실시간 대응 절차`를 먼저 적는다.
- XAI·보안 취약점 문항에서는 `모델 성능`과 `비즈니스 임계치`를 함께 검토한다.

## 1차 회독 통과 기준

첫 회독에서는 다음 흐름만 설명할 수 있으면 된다.

1. 업무 특성·법규·비용·복구 목표를 보고 클라우드로 옮길 대상을 정한다.
2. Public·Private·Hybrid는 어디에 배치할지, IaaS·PaaS·SaaS는 어디까지 공급자에게 맡길지 정하는 선택이다.
3. 가상머신·컨테이너·서버리스는 실행환경의 격리와 관리 책임이 서로 다르다.
4. 자동확장은 부하 변화에 대응하지만 고가용성·재해복구·백업을 대신하지 않는다.
5. 클라우드에서도 보안·비용·성능·장애 대응 책임을 사용자와 공급자가 나누어 관리한다.

## 보정 기록

- 클라우드·AI·데이터·보안의 통합형 질문에 대비해 서비스 모델→가상화→보안 흐름으로 압축한다.
- Multi-Cloud/Hybrid/Serverless는 공식 기출의 반복 여부를 확인해 A 우선순위를 유지하거나 조정한다.
- Docker/Kubernetes/CI/CD는 과거 구현 스택보다 운영 책임 분리와 모니터링 관점으로 서술한다.
- ISO/IEC 27017/27018, VDI, HCI 등은 최신 제도·지원 환경 여부를 기출 회차마다 갱신한다.
- `기존 등급 → 새 등급`, 근거 회차, 질문 형태를 남겨 누락과 역전 위험을 줄인다.

- 컨테이너·오케스트레이션·배포 자동화 항목(`Docker`, `Kubernetes`, `CI/CD`)은 배포 문법보다 `공유 책임, SLI/SLO, 침해 대응` 문장 3축으로 통일해 정렬한다.
- `Multi-Cloud/Hybrid/Serverless`는 장점 나열이 아니라 `책임 경계 전이 비용`과 `관측성`을 함께 제시하면 배점이 안정적이다.
- `VM/Container`, `Open스택`, `HCI`는 성능 비교보다 `마이그레이션 가드레일`(롤백·격리·권한 상속) 중심으로 보정한다.
- `[현행]` 표기는 제품명 교체보다 현행 보안 규정·감사 요건 변화에 맞춰 업데이트한다.
