SPA의 첫 화면에는 앱이 준비되기 **전** 잠깐 나타나는 로딩 표시가 있다. HTML의 `#root` 안에 들어 있는 정적 마크업과 CSS가 먼저 보이고, JavaScript 번들이 로드되면 React가 같은 자리에 앱을 렌더링한다. 기능은 정상인데 색이나 배치가 어색해도 실제 앱에서는 순식간에 지나가 육안으로 확인하기 어렵다.

2026년 7월, 이 순간을 검토하기 위해 앱의 시작을 늦추는 대신 **부트 마크업만 독립 HTML로 띄우는 방식**을 택했다. 전제는 초기 로더가 JavaScript 없이도 표시되는 순수 HTML/CSS라는 것이다. 앱 자체를 재현하는 도구가 아니라, 첫 프레임을 길게 붙잡아 두는 관찰 도구다.

## 문제: 빠른 화면을 캡처하려고 앱 전체를 느리게 만들 필요는 없다

개발자 도구에서 네트워크를 느린 속도로 제한하면 번들이 로드되기 전 화면을 더 오래 볼 수 있다. 그러나 CSS를 조금씩 조정하며 반복 확인할 때마다 네트워크·캐시·브라우저 실행 상태에 결과가 흔들린다. 초기 화면이 앱의 상태나 API 응답과 무관하다면 번들을 실행할 이유도 없다.

그렇다고 로더 HTML과 CSS를 미리보기 파일에 **복사**하면 또 다른 문제가 생긴다. 실제 `index.html`에서 색이나 DOM 구조를 바꿔도 미리보기는 옛 내용을 보여 준다. 그러면 가장 확인해야 할 대상인 실제 초기 화면과 검토 화면이 서로 어긋난다.

## 선택: 원본을 읽어서 매번 미리보기를 만든다

[devkit의 `preview-loader.sh`](https://github.com/clang-engineer/devkit/blob/main/templates/preview-loader.sh)는 `index.html` 경로를 받아 세 가지만 한다.

1. HTML에서 stylesheet 링크를 골라 실제 CSS 파일을 가리키도록 경로를 바꾼다.
2. `#root`의 초기 `<div>` 블록을 추출해 임시 HTML에 넣는다.
3. JavaScript 번들을 넣지 않고 그 파일을 브라우저에서 연다.

따라서 **스타일의 소스는 실제 CSS**, **마크업의 소스는 실제 앱 진입 HTML**이다. 임시 파일은 산출물이지 편집 원본이 아니다. 예를 들어 부트 화면의 색을 바꿨다면 미리보기를 다시 생성하는 것만으로 반영된다.

```bash
bash preview-loader.sh path/to/index.html
# 브라우저를 열지 않고 출력 HTML 경로만 확인하려면:
bash preview-loader.sh path/to/index.html --print
```

스크립트는 당시 `#root`가 단순한 중첩 `<div>` 구조인 페이지를 겨냥했다. 여는 `<div>`와 닫는 `</div>`의 누적 개수를 맞춰 블록 끝을 찾는 방식이므로 HTML 파서가 아니다. 속성 표기, 한 줄에 몰린 태그, `<div>`가 아닌 중첩 요소, 주석·스크립트 속 문자열 등이 달라지면 추출 결과를 신뢰할 수 없다. 다른 앱에 적용할 때는 **생성한 HTML의 실제 마크업을 먼저 확인**하고, 구조가 복잡하면 DOM 파서 기반 미리보기나 별도의 정적 엔트리 페이지를 사용해야 한다.

## `file://`는 빠르지만 같은 앱 환경은 아니다

로컬 파일을 브라우저에서 열면 macOS의 `open`이나 Linux의 `xdg-open`으로 서버 없이 확인할 수 있다. 그러나 `file://` 주소는 그 기계의 파일 경로에 묶인다. CSS에서 참조한 상대 경로 이미지·폰트, 리소스 정책, HTTP 서버에서만 성립하는 경로·CORS·보안 동작은 실제 앱과 다를 수 있다. 미리보기가 제대로 보였다고 배포된 앱의 네트워크와 번들 로딩까지 검증된 것은 아니다.

이 방법을 택할 기준은 명확하다. 로더가 **순수 HTML/CSS이고**, CSS 파일을 독립적으로 읽을 수 있으며, 확인하려는 것이 색·배치·애니메이션처럼 번들 마운트 전 시각 상태라면 유용하다. 서버 리소스나 JavaScript 실행 결과에 의존한다면 실제 앱에서 느린 네트워크·브라우저 개발자 도구로 확인한다.

당시 로더에는 팩맨이 점을 먹는 것처럼 보이는 작은 연출도 있었다. 복잡한 애니메이션 코드를 추가한 것이 아니라, **DOM의 그리기 순서**에서 앞의 점을 뒤의 입 모양이 덮도록 배치한 효과였다. 이런 시각 효과는 멈춘 상태로 보아야 원인을 짚기 쉽다. 결론은 특정 스크립트보다 **빠르게 사라지는 상태를 검토할 때 원본과 독립 미리보기 사이의 연결을 끊지 말자**는 것이다.
