새 도구를 도입할 때 GitHub 별 수가 가장 먼저 보인다. 그런데 별은 수년 동안 쌓인 **인지도의 재고(stock)**이지 최근에 얼마나 개발되고 실제로 쓰이는지의 흐름(flow)이 아니다. 한때 인기 있던 도구와 지금 활발히 유지되는 도구를 같은 숫자로 정렬하면 판단이 어긋난다.

## 지표를 한 점수로 합치지 않는다

| 신호 | 대답할 수 있는 질문 | 대답할 수 없는 질문 |
|---|---|---|
| 누적 별 | 지금까지 얼마나 알려졌나 | 올해 신규 사용자가 늘었나 |
| 최근 릴리스·커밋 | 유지보수가 움직이는가 | 사람이 실제로 정착했나 |
| 상위 기여자 집중 | 특정 인력에 얼마나 의존하나 | 코드 품질과 인수 가능성은 어떤가 |
| 독립적인 장기 사용 후기 | 특정 상황에서 계속 쓰는가 | 모든 사용자에게 맞는가 |

예를 들어 2026년 7월 tmux 세션 매니저를 비교했을 때, 별이 많은 오래된 도구와 최근 커밋이 많은 1인 유지 도구는 **서로 다른 리스크**였다. 저장소 활동만 보고 사용자 유입을 추정할 수 없고, 별 수만 보고 제품의 안정성을 말할 수도 없다. 과거의 특정 별·커밋 수는 지금의 순위가 아니므로 그대로 추천표에 옮기지 않는다.

[GitHub REST API의 저장소 정보](https://docs.github.com/en/rest/repos/repos#get-a-repository)에서 별·생성일을, [릴리스 목록](https://docs.github.com/en/rest/releases/releases#list-releases)에서 최근 배포 기록을, [기여자 목록](https://docs.github.com/en/rest/repos/repos#list-repository-contributors)에서 기여 분포를 각각 확인할 수 있다. `per_page=100`으로 받으면 그 뒤 페이지가 빠질 수 있고, 커밋 검색 결과에는 검색 조건과 API 사용 한도가 따른다. 최근 몇 달의 커밋 개수는 유지보수 신호이되 채택자 수로 쓰지 않는다.

## 실제 선택에서는 기능 정의와 평판을 분리한다

“tmux 키를 쉽게 발견한다”는 문장에도 두 과제가 있다. **내가 직접 바인딩한 키를 기억하려는가**, 아니면 **tmux가 원래 제공하는 기능을 메뉴에서 찾아보려는가**. 앞쪽에는 자신의 키맵을 반영하는 도구가, 뒤쪽에는 내장 기능의 메뉴가 맞다. 전자는 후자를 자동으로 해결하지 않는다. 두 후보가 해결하는 과제부터 구분해야 별과 커밋 비교가 의미를 갖는다.

사용 후기의 출처도 역추적한다. 한 도구에 붙은 호평이 실제로는 경쟁 도구에 관한 글일 수 있고, 커뮤니티 논의가 거의 없다면 **자료가 부족하다**는 것이 결론이다. awesome-list 등재는 발견 가능성·큐레이션 신호이지 독립적인 사용 만족도 조사도 아니다. 마지막 판단은 *현재 필요 → 후보별 역할 → 유지보수 리스크 → 대표 작업으로 시험 → 쉽게 제거할 수 있는가* 순으로 하는 편이 오래 간다.

짧은 조사에서는 `gh api 'repos/OWNER/REPO' --jq '{stars: .stargazers_count, created: .created_at}'`와 `gh api 'repos/OWNER/REPO/releases?per_page=100'`로 **누적 인지도와 최근 배포**를 서로 다른 열에 기록할 수 있다. 커밋 활동은 `gh api -X GET search/commits -f q='repo:OWNER/REPO committer-date:>=2026-08-18' --jq .total_count`처럼 조회하되, 조회일 기준 기간을 매번 갱신한다. 검색 API 제한·봇 커밋·merge 정책 때문에 이 숫자도 그대로 개발자 수로 치환할 수 없다.
