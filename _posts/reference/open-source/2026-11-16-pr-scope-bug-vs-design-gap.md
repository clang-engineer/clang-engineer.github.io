버그 하나를 추적하다 보면 옆에 또 다른 문제가 드러난다. 둘 다 고칠 수 있다고 해서 같은 PR에 넣는 게 항상 좋은 선택은 아니다. 유지보수자는 코드만 아니라 **어떤 결정을 한 번에 수락해야 하는가**를 리뷰한다. 명백한 수정과 논쟁 가능한 설계 변경을 묶으면, 후자에 관한 합의가 지연되는 동안 전자까지 멈춘다.

## 먼저 확신의 종류를 나눈다

예컨대 이벤트 훅에서 현재 창의 ID 대신 이미 닫힌 창의 ID를 참조한다면 잘못된 대상이라는 재현·수정 범위가 명확하다. 반면 해당 이벤트를 더 자주 발생하는 다른 훅으로 바꾸면 새 사례까지 포착하지만 처리 횟수가 늘 수 있다. 전자는 **동작이 의도와 어긋난 버그**, 후자는 **커버리지와 비용의 교환**이다.

| 질문 | 별도 PR에 유리 | 같은 PR에 유리 |
|---|---|---|
| 한쪽만 머지해도 의미 있는가 | 각각 독립적으로 문제를 해결 | 큰 수정이 작은 수정을 흡수 |
| 코드 수정 지점 | 다른 함수·다른 책임 | 같은 분기·같은 한 줄 |
| 리뷰 쟁점 | 버그는 즉시 검증, 설계는 토론 필요 | 분리하면 뒤 PR이 앞 PR을 반복 수정 |

독립적이면 **버그 수정 PR을 먼저** 제출하고, 설계 개선은 재현·성능·대안 비교를 갖춘 별도 PR로 보낸다. 결합이 강하면 억지로 stacked PR을 만들지 말고 한 PR의 본문에 발견 순서를 기록한다: 원래 버그 → 수정 후 남는 사례 → 공통 원인 → 더 넓은 수정의 필요성. 단순 버그 수정만으로 충분한지 리뷰어가 판단할 수 있도록 한다.

## 단일 PR의 위험을 미리 드러낸다

하나로 묶은 뒤 설계 변경의 발화 빈도나 호환성에서 이견이 생기면 “그 지점이 부담이라면 명백한 버그 부분만 남기고 범위 개선은 후속으로 분리하겠습니다”라는 **축소 가능한 선택지**를 제시한다. 리뷰가 시작되기 전에 코드를 수차례 갈아엎는 것보다 합의 가능한 최소 단위를 선명히 해준다.

어느 방식이든 버그의 재현 조건과 설계 변경의 새 동작·비용을 섞어 설명하지 말자. PR 범위의 목적은 커밋 수 최소화가 아니라 **서로 다른 확신을 별도로 수락하거나 거절할 수 있게 만드는 것**이다. 키 바인딩·훅처럼 이벤트 비용이 있는 도구일수록 이 경계가 유용하다.
