디자인 패턴을 "23개 이름 외우기"로 접근하면 금방 지친다. 이 로드맵의 목표는 하나 — **패턴을 갈래별로 이해하고, 쉬운 것부터 쌓아 실제로 골라 쓸 수 있게** 되는 것이다.

학습 척추는 두 축이 겹쳐 있다. 큰 갈래는 GoF가 나눈 **생성 → 구조 → 행위** 세 분류이고(1994년 『Design Patterns』 이래 거의 모든 교재가 따르는 틀), 각 갈래 안에서는 **입문 → 중급** 난이도 순으로 읽는다. 갈래를 가로질러 "무엇 다음에 무엇"을 이어 주는 실제 읽기 순서는 아래 **학습 순서**에 정리했다.

패턴을 익힌 뒤 참고로 꺼내 보는 것들 — **자주 헷갈리는 쌍**(닮은 패턴을 목적으로 가르는 대조표)과 **빈도 낮은 패턴 묶음** — 은 학습 척추와 결이 다른 **부록**으로 뒤에 뒀다.

## 한눈에 보기

큰 갈래 셋이 학습 척추다. 한 단어로 외우면:

| 분류 | 한 단어 | 무엇을 다루나 |
|------|---------|---------------|
| **생성 (Creational)** | 만들기 | 객체를 *어떻게 만드느냐* — 생성 과정을 캡슐화 |
| **구조 (Structural)** | 엮기 | 객체·클래스를 *어떻게 조합하느냐* — 더 큰 구조로 |
| **행위 (Behavioral)** | 주고받기 | 객체 간 *책임 분배와 상호작용* — 알고리즘·흐름 |

각 갈래를 입문 → 중급으로 훑은 뒤 **학습 순서**로 갈래를 가로지르는 읽기 순서를 잡는다. **자주 헷갈리는 쌍**과 **빈도 낮은 패턴 묶음**은 학습을 끝낸 뒤 필요할 때 찾아보는 부록이다. GoF 23개를 모두 다룬다(빈도 낮은 셋은 묶음 글로).

## 생성 — 만들기

객체 생성의 책임과 절차를 캡슐화해, 무엇을·어떻게 만드는지를 클라이언트로부터 분리한다.

| 패턴 | 난이도 | 한 줄 요약 |
|------|--------|-----------|
| [Factory](/posts/design-pattern/2025-04-11-factory/) | 입문 | 생성 책임을 팩토리로 옮겨 결합도를 낮춘다. Simple / Factory Method / Abstract Factory |
| [Builder](/posts/design-pattern/2026-06-18-builder/) | 입문 | 인자·선택 항목이 많은 객체를 단계별로 조립. 텔레스코핑 생성자 대체 |
| [Singleton](/posts/design-pattern/2026-06-18-singleton/) | 입문 | 인스턴스를 하나로 보장하고 전역 접근점 제공. 안티패턴 비판과 DI 대안도 함께 |
| [Prototype](/posts/design-pattern/2026-06-19-prototype/) | 입문 | 견본 객체를 복제해 생성. 생성 비용이 크거나 구체 타입을 숨길 때 |

## 구조 — 엮기

객체를 감싸거나 합쳐 더 큰 구조를 만든다. 핵심은 **위임(composition)** 으로 상속의 경직성을 피하는 것.

| 패턴 | 난이도 | 한 줄 요약 |
|------|--------|-----------|
| [Adapter](/posts/design-pattern/2025-04-12-adapter/) | 입문 | 기존 클래스를 원하는 인터페이스로 변환. 모양을 바꿔 끼운다 |
| [Decorator](/posts/design-pattern/2025-03-07-decorator/) | 입문 | 객체를 감싸 기능을 동적으로 덧댄다. 클래스 폭발 없이 조합 |
| [Proxy](/posts/design-pattern/2025-03-07-proxy/) | 중급 | 대리자가 실제 객체 접근을 가로채 제어. 가상/보호/원격 |
| [Composite](/posts/design-pattern/2026-06-18-composite/) | 중급 | 단일과 묶음을 같은 인터페이스로. 트리 구조의 본체 |
| [Facade](/posts/design-pattern/2026-06-18-facade/) | 중급 | 복잡한 서브시스템 앞 단순한 진입점. 결합도를 낮춘다 |
| [Bridge](/posts/design-pattern/2026-06-19-rarely-used/) | 참고 | 추상·구현 두 축을 분리해 클래스 폭발을 막는다 *(묶음 글)* |
| [Flyweight](/posts/design-pattern/2026-06-19-rarely-used/) | 참고 | 공통 상태를 공유해 대량 객체의 메모리를 절약 *(묶음 글)* |

## 행위 — 주고받기

객체 사이의 책임 분배와 상호작용, 알고리즘의 흐름을 다룬다.

| 패턴 | 난이도 | 한 줄 요약 |
|------|--------|-----------|
| [Strategy](/posts/design-pattern/2025-03-07-strategy/) | 입문 | 알고리즘을 객체로 캡슐화해 런타임에 갈아끼운다 |
| [Observer](/posts/design-pattern/2025-04-11-observer/) | 입문 | 상태 변화를 구독자들에게 통지하는 일대다 관계 |
| [Iterator](/posts/design-pattern/2026-06-18-iterator/) | 입문 | 내부 구조를 감추고 원소를 순서대로 꺼낸다 |
| [State](/posts/design-pattern/2025-03-07-state/) | 중급 | 상태별 분기 대신 상태를 객체로. 동작이 상태 따라 바뀐다 |
| [Template Method](/posts/design-pattern/2025-03-07-template-method/) | 중급 | 상위가 알고리즘 골격, 하위가 빈칸을 채운다 |
| [Command](/posts/design-pattern/2025-04-12-command/) | 중급 | 요청을 객체로 캡슐화. 큐잉·로그·취소가 자연스러워진다 |
| [Chain of Responsibility](/posts/design-pattern/2026-06-18-chain-of-responsibility/) | 중급 | 핸들러를 사슬로 연결해 차례로 시도. 미들웨어의 본체 |
| [Mediator](/posts/design-pattern/2026-06-19-mediator/) | 중급 | 객체 간 통신을 중재자 한 곳으로. 다대다 결합을 푼다 |
| [Visitor](/posts/design-pattern/2026-06-19-visitor/) | 중급 | 구조는 그대로 두고 연산을 분리. AST 순회의 본체 |
| [Memento](/posts/design-pattern/2026-06-19-memento/) | 중급 | 상태를 스냅샷으로 저장해 되돌린다. undo/redo의 본체 |
| [Interpreter](/posts/design-pattern/2026-06-19-rarely-used/) | 참고 | 문법 규칙을 클래스로 표현해 문장을 해석 *(묶음 글)* |

## 학습 순서

각 글의 **선행** 표기를 따라가면 이런 흐름이 된다. 먼저 선행이 없는 입문 패턴으로 감을 잡고, 그 위에 중급을 얹는다.

**1단계 — 선행 없이 시작 (입문)**
Strategy · Factory · Decorator · Adapter · Observer · Iterator · Singleton

**2단계 — 입문 위에 쌓기**
- Strategy → **State** (상태 vs 알고리즘) · **Template Method** (상속판 Strategy) · **Command** (요청을 객체로) — 셋 다 Strategy만 선행이라 나란히 읽어도 된다. 이어서 **Command** → **Memento** (상태를 스냅샷으로)
- Decorator → **Proxy** (감싸기지만 목적이 다름) · **Chain of Responsibility** (감싸기를 사슬로) — 둘 다 Decorator가 선행인 형제 패턴
- Factory → **Builder** (생성을 단계로) · **Prototype** (생성을 복제로)
- Adapter → **Facade** (변환에서 단순화로)
- Observer → **Mediator** (브로드캐스트에서 조율로)
- Composite (선행 없는 중급 — 여기서 바로 시작) → **Visitor** (트리 위에 연산을 얹기)

## 부록 — 자주 헷갈리는 쌍 (다른 축)

학습 단계가 아니라, 닮은 패턴 앞에서 막혔을 때 찾아보는 대조표다. 분류가 다르거나 구조가 닮아 헷갈리기 쉬운 조합을 목적의 차이로 가른다.

| 비교 | 닮은 점 | 가르는 기준 |
|------|---------|-------------|
| [Strategy](/posts/design-pattern/2025-03-07-strategy/) vs [State](/posts/design-pattern/2025-03-07-state/) | 둘 다 행위를 객체로 캡슐화 | Strategy는 *클라이언트가* 고른다, State는 *스스로* 전이한다 |
| [Decorator](/posts/design-pattern/2025-03-07-decorator/) vs [Proxy](/posts/design-pattern/2025-03-07-proxy/) | 둘 다 같은 인터페이스로 감싼다 | Decorator는 기능 *추가*, Proxy는 접근 *제어* |
| [Adapter](/posts/design-pattern/2025-04-12-adapter/) vs [Facade](/posts/design-pattern/2026-06-18-facade/) | 둘 다 다른 인터페이스를 앞에 둔다 | Adapter는 모양 *변환*, Facade는 *단순화* |
| [Factory Method](/posts/design-pattern/2025-04-11-factory/) vs [Template Method](/posts/design-pattern/2025-03-07-template-method/) | 둘 다 하위가 빈칸을 채운다 | 채우는 게 *객체 생성*이면 Factory Method, *알고리즘 단계*면 Template Method |
| [Factory](/posts/design-pattern/2025-04-11-factory/) vs [Prototype](/posts/design-pattern/2026-06-19-prototype/) | 둘 다 생성을 다룬다 | Factory는 *타입으로 새로* 생성, Prototype은 *기존 인스턴스를 복제* |
| [Observer](/posts/design-pattern/2025-04-11-observer/) vs [Mediator](/posts/design-pattern/2026-06-19-mediator/) | 둘 다 직접 호출을 끊는다 | Observer는 *일대다 브로드캐스트*, Mediator는 *다대다 조율* |
| [Command](/posts/design-pattern/2025-04-12-command/) vs [Memento](/posts/design-pattern/2026-06-19-memento/) | 둘 다 undo를 푼다 | Command는 *역연산*으로 되돌림, Memento는 *상태 스냅샷*으로 복원 |

## 부록 — 빈도 낮은 패턴은 모아서

Bridge · Flyweight · Interpreter는 각각 한 페이지를 채울 만큼 할 얘기가 없어 [자주 안 쓰는 GoF 패턴](/posts/design-pattern/2026-06-19-rarely-used/) 한 글에 모아 짧게 다뤘다. 위 표의 *(묶음 글)* 표시가 그것.

Abstract Factory·Factory Method는 [Factory](/posts/design-pattern/2025-04-11-factory/) 글에서 함께 다룬다.

## 경계 — 패턴은 목적이 아니라 도구

패턴을 배우고 나면 모든 문제에 끼워 맞추고 싶어진다. 그게 가장 흔한 함정이다. 이 로드맵은 "언제 쓰나"만큼 "언제 쓰지 말아야 하나"도 중요하게 본다 — 각 패턴 글 끝의 **안티패턴 / 주의** 섹션이 그 경계선이다. 새 패턴을 도입하기 전에 그 섹션부터 읽어, 지금 문제가 정말 그 패턴을 부르는지 되묻는 습관을 들이자.

특히 [Singleton](/posts/design-pattern/2026-06-18-singleton/)은 자주 쓰이면서도 안티패턴 비판이 큰 대표 사례라, 그 글에서 비판과 DI 대안을 함께 다룬다.

또 하나, 많은 패턴이 겨냥하는 근본 목표는 대개 **OCP(개방-폐쇄 원칙)** 하나로 모인다 — 기존 코드를 건드리지 않고 새 동작을 더하는 것. [Strategy](/posts/design-pattern/2025-03-07-strategy/)·[Factory](/posts/design-pattern/2025-04-11-factory/)·[Observer](/posts/design-pattern/2025-04-11-observer/)·[Chain of Responsibility](/posts/design-pattern/2026-06-18-chain-of-responsibility/) 글이 모두 "OCP 위반 → 패턴으로 해소" 흐름으로 문제를 연다. 패턴 이름을 외우기보다 이 목표를 먼저 붙잡으면 어떤 패턴을 언제 꺼낼지가 자연스럽게 잡힌다.

---

패턴은 이렇게 읽으면 된다:

- **처음이라면** 각 갈래의 입문 패턴(Strategy·Factory·Decorator·Adapter·Observer·Iterator·Singleton)으로 감을 잡는다.
- **그다음** 학습 순서의 화살표를 따라 입문 위에 중급을 얹는다 — Strategy → State, Decorator → Proxy처럼.
- **닮은 패턴이 헷갈리면** 부록의 대조표에서 목적의 차이로 가른다.

이로써 GoF 23개 패턴이 이 블로그에서 모두 최소 한 문단씩 설명된다 — 이름만 있고 설명 없는 칸은 없다.
