## 한 줄 요약

코루틴은 **실행 도중 멈췄다가(suspend) 나중에 그 지점부터 다시 이어서 실행(resume)할 수 있는 함수**다. Go의 goroutine, Rust·C++·Python·Kotlin의 async가 전부 이 하나의 개념을 각자 구현한 것이다.

## 흔한 오해부터 — 코루틴은 특정 언어 것이 아니다

"코루틴은 Kotlin 개념 아니야?"라는 오해가 흔하다. Kotlin이 이름을 전면에 내세워 마케팅했기 때문인데, 사실 코루틴은 **1963년 Melvin Conway**가 명명한, 현존하는 거의 모든 언어보다 먼저 나온 개념이다.

Kotlin은 오래된 개념의 **구현체 하나**일 뿐이다. "람다는 Java 8 개념 아니야?"라는 오해와 똑같다 — 람다도 1930년대 람다 대수에서 왔고 Java는 한참 뒤에 받아들였다. 그래서 이 글은 특정 언어가 아니라 **개념 자체**를 정리하고, 언어별 구현은 뒤에서 대응만 시킨다.

## 1. 일반 함수 vs 코루틴 — suspend / resume

일반 함수는 호출되면 **끝까지 실행되고 반환하면 끝**이다. 반환하는 순간 그 함수의 지역 변수와 실행 위치는 전부 사라진다.

```
일반 함수:   호출 → 실행 ─────────────▶ return (끝, 상태 소멸)
코루틴:      호출 → 실행 → suspend(상태 보존) ⇢ resume → 실행 → ... → return
```

코루틴은 중간에 "잠깐 멈추고 제어권을 넘긴 뒤, 다시 불리면 멈춘 그 줄부터" 재개한다. 즉 **함수의 실행 상태(지역 변수 + 실행 위치)가 호출 사이에 보존**된다.

```python
# Python generator — 코루틴의 가장 익숙한 형태
def numbers():
    n = 0
    while True:
        yield n     # ★ 여기서 멈추고 값을 반환. 다음 호출 때 이 줄부터 재개
        n += 1

gen = numbers()
next(gen)  # 0
next(gen)  # 1  ← n이 살아있다. 함수를 처음부터 다시 도는 게 아니다
next(gen)  # 2
```

`yield`에서 함수가 얼어붙었다가, 다음 `next()`에서 **그 지점부터** 깨어난다. `n`이 매번 유지되는 게 핵심이다. 일반 함수라면 매 호출마다 `n = 0`부터 다시 시작했을 것이다.

## 2. 스레드 vs 코루틴 — cooperative vs preemptive

"둘 다 여러 작업을 동시에 돌리는 거 아니야?"에서 갈린다. 결정적 차이는 **누가 언제 전환을 결정하느냐**다.

| | 스레드 | 코루틴 |
|---|---|---|
| 전환 방식 | 보통 **선점형(preemptive)** — OS가 임의 시점에 강제 전환 | 구현에 따라 협력형 또는 런타임 선점 — `yield`/`await`은 명시적 중단 지점 |
| 전환 비용 | 비쌈 (커널 개입, 컨텍스트 스위치) | 쌈 (커널 없이 함수 호출 수준) |
| 개수 | 수백~수천이 한계 | 수십만 개도 가능 |
| 데이터 레이스 | 언제든 끊길 수 있어 락 필요 | 양보 지점 사이는 원자적 → 단일 스레드면 락 불필요 |
| 함정 | 락·데드락 | 하나가 양보 안 하면 **전부 멈춤** |

단일 스레드의 협력형 이벤트 루프에서는 **양보 지점이 코드에 명시적으로 보인다**는 장점이 있다. 그 환경에서는 `yield`/`await` 사이에 다른 코루틴이 끼어들지 않는다. 하지만 Go처럼 런타임이 선점하거나 여러 스레드에서 실행하는 구현에는 이 보장을 일반화할 수 없다. 공유 데이터의 동기화 필요성은 실제 스케줄러와 실행 스레드 모델로 판단해야 한다.

> 스레드와 코루틴은 대립하지 않는다. 실전에서는 **소수의 스레드 위에 수많은 코루틴을 얹는(M:N)** 구조가 흔하다. Go 런타임이 정확히 이렇게 동작한다.

### "락이 필요 없다"가 깨지는 지점

"코루틴은 락이 덜 필요하다"는 두 가지 전제에서만 성립한다.

첫째, **양보 지점(`await`) 사이만 원자적**이다. `await`을 낀 read-modify-write는 원자적이지 않다 — 그 틈에 다른 코루틴이 끼어들어 같은 데이터를 바꿀 수 있다.

```python
x = shared.count
await something()     # ← 여기서 양보. 그 사이 count가 바뀔 수 있다
shared.count = x + 1  # 낡은 x로 덮어쓸 위험
```

그래서 `asyncio.Lock` 같은 게 존재한다. **위험한 지점이 `await`으로 코드에 명시적으로 보인다**는 게 스레드 대비 이점이지, 위험이 사라진 건 아니다.

둘째, **단일 스레드일 때만** 그렇다. 멀티스레드 위에 코루틴을 얹으면(`Go`, Kotlin의 멀티 디스패처) `await` 전후로 **다른 스레드에서 재개**될 수 있어 공유 데이터에 락이 다시 필요하다. Node.js·Python asyncio가 편한 건 스레드가 1개라서다. Go가 `sync.Mutex`와 race detector를 두는 것도 이 때문이다.

> 여기서 "여러 실행 흐름이 데이터를 어떻게 안전하게 나눠 쓰나"(공유 상태+락 vs 채널 vs 소유권)는 이 글의 범위 밖 — 코루틴의 **조율 반쪽**으로 [동시성 조율 모델 — 공유 상태 vs 메시지 전달](/posts/concept/2026-07-12-concurrency-coordination-models/)에 따로 정리했다.

## 3. 코루틴은 보존된 상태와 실행 정책의 조합이다

프로세스·스레드는 OS가 직접 스케줄링하지만, 코루틴은 중단 시점의 **지역 상태와 실행 위치를 보존**하고 런타임·실행기·호출자가 재개한다. 흔한 stackless 구현은 이 상태를 구조체 같은 프레임으로 표현하지만, 그 프레임이 반드시 힙에 놓이는 것은 아니다. escape 분석, 인라이닝, 할당 생략에 따라 스택이나 호출자 객체 안에 둘 수도 있다.

> **C++ 개발자라면 바로 드는 질문 — "프레임은 누가 쥐고 누가 해제하나?"** C++20에서는 코루틴의 promise/반환 타입이 소유 정책을 정한다. 저수준 타입은 `std::coroutine_handle`을 노출할 수 있고, 이 경우 보통 `task<T>` 같은 RAII 타입이 프레임을 소유해 적절한 시점에 `.destroy()`한다. 다만 표준은 동적 할당이 호출자 저장공간에 포함되거나 생략되는 것도 허용한다. 핵심은 **힙 여부가 아니라 중단 뒤에도 프레임 수명이 유지되고 소유자가 명확해야 한다는 것**이다.

```
보존된 상태: [코루틴 A] [코루틴 B] [코루틴 C]   ← 저장 위치는 구현에 따라 다름

스레드:  while (true) { 큐에서 코루틴 꺼내 resume() }   ← 이게 CPU를 받는다
```

이런 루프가 **이벤트 루프**다. stackless 코루틴 만 개는 일반적으로 스레드 만 개의 고정 스택보다 훨씬 작은 상태 프레임 만 개를 유지한다. 정확한 크기와 저장 위치는 언어·런타임·최적화에 따라 달라진다.

세 개를 한 축으로 세우면 차이가 분명해진다.

| | 주소공간 | 실행 상태 저장 | 스케줄링 |
|---|---|---|---|
| **프로세스** | 자기 것 | 자기 스택 | OS |
| **스레드** | 공유 | 자기 스택 | OS |
| **코루틴** | 프로세스 안에서 실행 | 프레임 또는 전용 스택(저장 위치는 구현 의존) | 런타임·실행기·호출자 |

스레드는 OS가 레지스터와 스택을 저장·복원해 전환한다. 코루틴은 언어 런타임이나 라이브러리가 필요한 상태만 저장·복원하므로 대체로 생성과 전환이 더 가볍다. 이 차이는 **상태 표현과 스케줄링 정책**에서 나오며, 단순히 "스택을 힙으로 옮겼기 때문"이라고 설명할 수는 없다.

> 런타임이 프레임을 이동 가능한 작업으로 관리하면 **다른 스레드가 이어받을 수도** 있다. Go의 work-stealing이 대표적이다. 단 한 코루틴을 두 스레드가 동시에 재개하지 않도록 런타임이 실행을 조율한다.

## 4. async/await은 스레드를 만들지 않는다

가장 흔한 오해가 "`await`하면 그 사이 별도 스레드가 생겨서 기다린다"는 것이다. **아니다.** 만든다면 요청 만 개 = 스레드 만 개 = 10GB가 되어, 코루틴을 쓸 이유 자체가 사라진다.

`await`할 때 실제로 벌어지는 일:

```js
async function A() {
  const data = await fetch(url);   // 2초 걸리는 요청
  console.log(data);
}
```

1. `fetch`가 OS에 "이 소켓에 데이터 오면 알려줘"라고 **등록만** 하고 즉시 리턴한다.
2. **A는 여기서 호출자에게 제어권을 돌려준다.** A의 상태 `{ url, 어디까지: 1번째 줄 }`는 프레임에 보존된다.
3. 스레드는 자유. 그 사이 다른 코루틴(B, C)을 돌린다.
4. 2초 뒤 응답 도착 → 실행기가 A를 재개해 **2번째 줄부터** 이어서 실행.

**기다리는 주체가 없다.** 기다리는 건 OS와 네트워크 카드다(CPU 없이 일한다). 그럼 "응답 온 걸 어떻게 아느냐" — 이벤트 루프가 `epoll_wait`(리눅스)·`kqueue`(맥)·`IOCP`(윈도우)로 **소켓 만 개를 스레드 하나로 감시**한다.

```
등록표: { socket_A → 코루틴 A }   ← await 시점에 (소켓→핸들) 매핑을 등록
       { socket_B → 코루틴 B }

루프:
  준비된 = epoll_wait()   // "A, C 왔음". 할 일 없을 때만 여기서 잠든다
  for (소켓 : 준비된) { 테이블[소켓].resume() }   // 해당 코루틴만 깨움
```

블로킹 I/O는 소켓 1개당 스레드 1개가 잠들지만, epoll은 소켓 만 개를 스레드 1개가 감시하다 준비된 것만 깨운다. **"블로킹을 없앤 게 아니라, 만 개의 블로킹을 하나로 합친 것"**이 정확하다.

> **식당 웨이터 비유.** 주문받아 주방에 넣고 **주방 앞에서 기다리지 않는다** — 다른 테이블을 받으러 간다. 음식 나오면 주방이 **벨**을 울리고, 웨이터가 가져간다. 웨이터=스레드(한 명), 주문서=보존된 코루틴 상태, 주방=OS/커널(진짜로 기다림), 벨=epoll, `await`="주문 넣고 자리 뜬다". 웨이터가 주방 앞에서 기다리면 테이블 10개에 웨이터 10명(=스레드 방식). **`await`은 스레드를 만드는 게 아니라 놓아주는 것이다.**

**CPU 계산**은 코루틴만으로 병렬화되지 않는다. `await asyncio.to_thread(heavy_compute)`처럼 스레드 풀이나 프로세스를 써야 여러 코어를 활용한다. 다만 코루틴은 I/O뿐 아니라 generator, 파서, 파이프라인, 협력형 상태 머신에도 유용하다.

## 5. 구현의 갈림길 — stackful vs stackless

같은 코루틴이라도 **"멈춘 상태를 어떻게 저장하느냐"**에서 두 갈래로 나뉜다. 언어별 특성과 제약이 대부분 여기서 갈리므로 이해해 둘 가치가 있다.

### Stackful — 자기 스택을 통째로 가진다

각 코루틴이 **독립된 스택**을 하나씩 갖는다. 그래서 **아무리 깊이 중첩된 함수 호출 안에서도** 멈출 수 있다.

```
coroutine A의 스택:  main() → parse() → readToken() ← 여기서 suspend 가능
```

- **장점**: 어디서든 멈출 수 있어 직관적. 일반 함수와 코루틴을 문법적으로 구분할 필요가 거의 없다.
- **단점**: 코루틴마다 스택 메모리가 필요해 상대적으로 무겁다.
- **예**: Lua 코루틴, Go goroutine, Boost.Coroutine

### Stackless — 상태 기계로 변환된다

자기 전용 호출 스택이 없다. 대신 컴파일러가 코루틴 함수를 **상태 기계(state machine)**로 변환해, 멈출 때 필요한 지역 변수와 실행 위치를 프레임에 담는다. 프레임의 실제 저장 위치는 구현과 escape 여부에 따라 달라진다.

- **장점**: 메모리가 매우 작다. 수백만 개를 띄워도 부담이 적다.
- **단점**: **코루틴 함수 자신의 최상위**에서만 멈출 수 있다. 중첩 호출된 일반 함수 안에서는 못 멈춘다. 그래서 `async`가 호출 사슬을 타고 전파되는 **"함수 색칠(function coloring)"** 문제가 생긴다 — async 함수를 부르려면 나도 async여야 한다.
- **예**: Rust `async`, C++20 코루틴, Python `async`, Kotlin `suspend`, JavaScript `async`

| | Stackful | Stackless |
|---|---|---|
| 멈출 수 있는 위치 | 중첩된 어디서든 | 코루틴 함수 최상위만 |
| 메모리 | 스택만큼 (상대적으로 큼) | 필요한 변수만 (작음) |
| async 전파(색칠) | 없음 | 있음 (`async`가 번짐) |
| 대표 | Go, Lua | Rust, C++20, Python, Kotlin, JS |

### 이름의 함정 — 힙/스택 저장 위치 구분이 아니다

`stackful`/`stackless`는 "힙이냐 스택이냐"의 구분이 **아니다.** 갈리는 것은 코루틴이 **독립된 호출 스택을 보존하는가**, 아니면 컴파일러가 **필요한 상태만 프레임으로 바꾸는가**다. 어느 저장 영역에 놓일지는 구현 세부사항이다.

혼동의 뿌리는 "스택"이라는 말이 두 가지를 가리키기 때문이다.

1. **스택 = 메모리 영역** — OS가 스레드마다 주는 그 영역. "함수 끝나면 SP를 되돌려 자동 소멸"이 규칙이다.
2. **스택 = 자료구조** — `f() → g() → h()`처럼 호출을 쌓는 LIFO 구조.

Stackful 구현은 멈춰 있는 동안 `f→g→h` 호출 사슬을 보존할 전용 스택 공간이 필요하다. 이 공간은 런타임이 별도로 할당·관리하며, 반드시 일반 힙 할당이라고 단정할 수는 없다. Stackless 구현은 호출 스택 전체 대신 컴파일러가 골라낸 상태만 프레임에 보존한다.

- **Stackful** = 전용 **호출 스택을 통째로** 보존한다 → 깊이 중첩된 곳에서도 멈출 수 있지만 상대적으로 무겁다.
- **Stackless** = 컴파일러가 **필요한 변수와 실행 위치**를 프레임으로 바꾼다 → 중단 가능한 함수가 구분되고 호출 사슬에 `async`가 전파되는 function coloring이 생긴다.

이름을 다시 짓자면 stackful = "전용 호출 스택 있음", stackless = "전용 호출 스택 없이 상태 프레임만"이다. 클로저와 공통점은 저장 위치가 아니라 **호출 경계를 넘어 필요한 상태의 수명을 보존한다는 것**이다.

## 6. 언어별 구현 한눈에

같은 개념이 언어마다 어떻게 나타나는지 대응시킨 표다. 세부는 각 언어 로드맵에서 다룬다.

| 언어 | 문법 | 방식 | 특징 |
|---|---|---|---|
| **Go** | `go f()` + channel | stackful (M:N 스케줄) | 런타임이 스케줄링. 가장 가볍게 시작 |
| **Rust** | `async` / `.await` | stackless | 실행기(tokio 등)가 필요. `.await`가 suspend 지점 |
| **C++20** | `co_await` / `co_yield` / `co_return` | stackless | 컴파일러가 상태 기계로 변환. 저수준·복잡 |
| **Python** | `yield`, `async` / `await` | stackless | generator가 입문용으로 가장 쉬움 |
| **Kotlin** | `suspend fun` | stackless | continuation-passing으로 변환. Android 표준 |
| **Lua** | `coroutine.create/resume/yield` | stackful | 코루틴을 언어 핵심으로 삼은 고전 |

### Go의 goroutine은 정확히 코루틴인가?

엄밀히는 **코루틴 아이디어 + 런타임 스케줄러**라서 "그린 스레드(green thread)"에 더 가깝다. 순수 코루틴은 개발자가 `resume`을 직접 호출해 제어권을 넘기지만, goroutine은 Go 런타임이 알아서 스케줄링하고(오래 도는 goroutine은 런타임이 선점하기도 한다) 서로 channel로 통신한다. 그래도 "경량 실행 단위를 스레드보다 값싸게 수만 개 돌린다"는 목적은 코루틴의 것과 같다.

> Go 상세: [Go 학습 로드맵 — ⑤ 동시성](/posts/go/2026-07-12-go-roadmap/)

## 7. C++로 파고들기 — `std::async` ≠ `co_await`

C++은 코루틴을 이해하기 가장 까다로우면서도, 그래서 개념이 가장 선명하게 드러나는 언어다. 다른 언어가 숨겨주는 배선을 전부 손에 쥐여주기 때문이다.

**먼저 이름의 함정.** C++에는 `async`/`await` 키워드가 **없다.** 헷갈리는 두 물건을 구분해야 한다.

- **`std::async`** (C++11) — 이건 코루틴이 **아니다. 진짜 스레드를 만든다.** `auto fut = std::async(std::launch::async, work); fut.get();`은 스레드를 붙잡고 앉아 블로킹으로 기다린다. 우리가 얘기한 것과 정반대다.
- **`co_await` / `co_return` / `co_yield`** (C++20) — 이게 진짜 코루틴이다. Python의 `await`에 해당한다. 함수 몸통에 `co_` 뭔가가 있으면 컴파일러가 그 함수를 코루틴으로 취급한다(`async` 같은 표시가 없다).

```cpp
Task f() {           // async 표시 없음 — co_await이 있어서 코루틴
  co_await something;
}
```

**메커니즘은 주되 정책은 안 준다.** Python·JS·Go는 이벤트 루프가 내장이라 `asyncio.run()` 한 줄이면 끝이다. C++20은 **코루틴 문법만** 주고 이벤트 루프도, epoll 배선도, 스케줄러도 주지 않는다. `co_await`이 뭘 할지, 누가 `resume()`을 부를지 전부 직접 짜야 한다(그래서 튜토리얼이 `promise_type`·`awaiter`·`coroutine_handle`로 시작한다). 현실적으로는 **Boost.Asio**(epoll을 감싼 사실상 표준 이벤트 루프)를 쓴다.

```cpp
asio::awaitable<void> f() {
  co_await asio::async_read(socket, buf, asio::use_awaitable);  // Asio가 epoll 관리
}
io_context.run();   // 이게 이벤트 루프 — asyncio.run()과 같은 역할
```

앞에서 프레임의 저장·소유 정책을 라이브러리에 맡긴 것과 같은 태도다 — **"제어권은 준다"**.

**클로저의 댕글링 함정이 그대로 재현된다.** 컴파일러가 지역변수를 코루틴 프레임에 보존하지만, **참조가 가리키는 대상의 수명은 연장하지 않는다.**

```cpp
Task f() {
   int n = 0;            // 코루틴 프레임에 보존된다. 안전
  co_await something;   // 중단
  use(n);               // 돌아와도 n 멀쩡
}

Task g(const std::string& s) {   // 위험
  co_await something;            // 중단된 사이 호출자가 죽으면
  use(s);                        // 댕글링 — C++ 코루틴의 가장 흔한 버그
}
```

`n`은 중단 뒤에도 프레임에 보존된다. 반면 `s`가 가리키는 대상의 수명은 연장되지 않고 프레임엔 참조만 남는다. → 비동기 수명이 호출자를 넘어간다면 값을 소유하거나 `shared_ptr` 등으로 명시적으로 수명을 공유해야 한다.

<details markdown="1">
<summary>C++20 이전엔 어떻게 했나 — 유사 구현 네 가지</summary>

| 방식 | 지역변수 | 중첩 호출에서 중단 | 비용 |
|---|---|---|---|
| 수동 상태 머신(`switch`) | ❌ 구조체 멤버로 빼야 | ❌ | 최소 |
| Protothreads(Duff's device 매크로) | ❌ | ❌ | 최소 |
| 스택풀(ucontext, Boost.Coroutine) | ✅ | ✅ | KB 단위 |
| **C++20 stackless** | ✅ | ❌ | 바이트 단위 |

- **수동 상태 머신**: 코루틴 프레임을 손으로 구조체로 만들고 "어디까지 했는지"를 필드로 든다. 콜백/이벤트 루프 비동기 코드가 전부 이 형태다 — 동작은 같고 제어 흐름이 `switch`로 찢겨 코드가 지옥이 된다.
- **C++20이 한 일**: 그 수동 상태 머신의 성능에, 스택풀의 문법(그냥 지역변수처럼 쓰기)을 얹었다. 컴파일러가 중단 뒤 필요한 지역변수를 프레임 필드로 자동 변환한다.

</details>

## 코루틴 ≠ 클로저 (자주 같이 나오는 이유) — 그러나 뿌리는 같다

둘은 **하나의 질문**에서 나온 형제다.

> **"함수가 끝났는데, 그 안에 있던 게 살아남아야 한다면?"**

일반 호출의 지역 상태는 반환하면 끝난다. 클로저와 코루틴은 필요한 상태가 호출 경계를 넘어 살아남도록 **별도 환경이나 프레임에 보존**한다. 그 저장 위치가 항상 힙인 것은 아니다.

| | 클로저 | 코루틴 |
|---|---|---|
| 무엇이 살아남나 | 캡처한 **변수** | **프레임 전체**(지역 상태 + 실행 위치) |
| 어디에 보존되나 | 캡처 환경(저장 위치는 escape/구현 의존) | 코루틴 프레임(저장 위치는 구현 의존) |
| 재개(resume) 개념 | 없음 (매번 처음부터 실행) | 있음 (멈춘 지점부터 재개) |

**클로저는 캡처 환경을, 코루틴은 지역 상태와 실행 위치를 보존**한다. 둘 다 참조가 가리키는 외부 객체의 수명을 자동으로 연장한다고 볼 수 없으므로, C++에서는 **"이 참조가 원본보다 오래 사는가?"**를 따져야 한다.

클로저로 "다음 값을 뱉는 함수"를 만들면 generator처럼 보이지만, 함수를 매번 처음부터 다시 도는 것이라 **중간에서 멈췄다 재개하는 진짜 코루틴이 아니다.** → [클로저란 무엇인가](/posts/concept/2026-07-12-closure/)

## 스스로 점검

**1. 일반 함수와 코루틴의 결정적 차이 한 가지는?**

<details markdown="1">
<summary>답</summary>

코루틴은 **suspend/resume**가 된다. 실행 도중 멈췄다가 그 지점부터 재개할 수 있고, 그 사이 지역 변수와 실행 위치가 보존된다. 일반 함수는 반환하면 상태가 사라져 매 호출이 처음부터 시작한다.

</details>

**2. 코루틴이 스레드보다 데이터 레이스에 강한 이유는?**

<details markdown="1">
<summary>답</summary>

**단일 스레드 협력형 런타임에서는** `yield`/`await`이 아닌 구간에 다른 코루틴이 끼어들지 않는다. 양보 지점이 코드에 명시적으로 보이는 이점이 있지만, 여러 스레드에서 실행하거나 런타임이 선점하는 구현에는 일반화할 수 없다. 그때는 실제 스케줄러와 공유 상태에 맞는 동기화가 필요하다.

</details>

**3. Rust `async`가 중첩 함수 안에서는 못 멈추고, Go goroutine은 어디서든 멈출 수 있는 이유는?**

<details markdown="1">
<summary>답</summary>

Rust는 **stackless**라 코루틴 함수를 상태 기계로 변환하고, 자기 스택이 없어 최상위의 `.await`에서만 멈춘다(그래서 async가 호출 사슬을 타고 번진다 — function coloring). Go goroutine은 **stackful**이라 자기 스택을 통째로 가지므로 깊이 중첩된 호출 안에서도 멈출 수 있다.

</details>

**4. `await fetch(url)`로 응답을 기다리는 2초 동안, 스레드는 무엇을 하고 있나?**

<details markdown="1">
<summary>답</summary>

**다른 일을 한다(다른 코루틴을 돌린다).** `await`은 별도 스레드를 만들지 않는다 — `fetch`는 OS에 소켓을 등록하고 호출자에게 제어권을 돌려주며, 상태는 코루틴 프레임에 보존된다. 기다리는 건 OS·네트워크 카드고, 이벤트 루프가 `epoll`로 소켓 만 개를 한 스레드로 감시하다 준비된 것만 재개한다. **`await`은 스레드를 만드는 게 아니라 놓아주는 것.**

</details>

**5. C++의 `std::async`와 `co_await`은 무엇이 다른가?**

<details markdown="1">
<summary>답</summary>

정반대 물건이다. `std::async`(C++11)는 **진짜 스레드를 만들어** 블로킹으로 기다리는 헬퍼로, 코루틴이 아니다. `co_await`(C++20)이 진짜 코루틴으로, 스레드를 만들지 않고 함수가 return했다가 나중에 이어간다. C++엔 `async`/`await` 키워드가 없고, 몸통에 `co_await`/`co_return`/`co_yield`가 있으면 컴파일러가 코루틴으로 취급한다.

</details>
