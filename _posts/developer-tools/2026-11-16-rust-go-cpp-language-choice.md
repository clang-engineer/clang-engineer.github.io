C++를 쓰던 개발자가 새 터미널 도구를 만들면 “성능은 Rust냐 C++냐”부터 묻기 쉽다. 하지만 대부분의 선택은 벤치마크 숫자보다 **이미 가진 코드·팀의 학습 비용·배포 대상·메모리 안전 요구**가 먼저 결정한다. Go와 Rust 모두 강력한 CLI·TUI 선택지이고, C++도 특정 자산이 있다면 여전히 가장 작은 변경일 수 있다.

## 같은 네이티브 바이너리, 다른 비용 구조

| 질문 | Go | Rust | C++ |
|---|---|---|---|
| 메모리 모델 | GC로 관리·운영 단순 | 소유권/빌림 검사로 GC 없는 메모리 안전 | 관리 책임과 표현 자유가 큼 |
| 팀 진입 비용 | 문법과 표준 도구가 단순한 편 | 빌림·수명 모델 학습 필요 | 기존 C++ 자산·숙련 활용 가능 |
| 적합한 출발점 | 네트워크 서비스·운영 도구 | 시스템 경계·파서·성능/안전 동시 요구 | 기존 ABI·라이브러리·엔진 연동 |

2026년의 터미널 도구 가운데 ripgrep·fd·bat·yazi 등 Rust로 작성한 사례가 많다. ratatui 같은 생태계가 TUI 작성의 매력을 높인다. 그렇다고 “터미널 앱의 유일한 표준은 Rust”라거나 “Go의 GC는 모든 TUI에서 눈에 띄는 병목”이라고 일반화할 수 없다. Go에는 Bubble Tea 같은 TUI 생태계가 있으며, 도구 규모에서 GC의 비용은 구체적인 지연 요구를 측정하고 판단해야 한다.

## 결정은 먼저 버릴 수 없는 조건에서

- **기존 C++ 코드·라이브러리·ABI가 설계를 지배한다면** C++를 유지할 실익이 크다. 게임 엔진·임베디드·브라우저·데이터베이스 코어처럼 이미 축적된 구현의 경계가 있는 영역을 “신규 코드는 모두 다른 언어”로 치환하면 이행 비용을 숨기게 된다.
- **짧은 시간에 서비스·운영 도구를 배포하고 팀이 쉽게 수정해야 한다면** Go를 먼저 검토한다. 단순한 빌드·배포와 배우기 쉬운 규칙의 이득이 최대 성능보다 클 수 있다.
- **GC 없는 메모리 안전과 정밀한 자원 수명이 실제 요구라면** Rust를 검토한다. borrow checker와 명시적 타입 설계의 학습 비용을 치르고 런타임에서 발견하던 오류 일부를 컴파일 시점으로 앞당긴다.

C++ 경험자에게 Go는 빠른 생산성 경험을 주고 Rust는 포인터·소유권 감각을 재사용할 수 있다. “Go 먼저, Rust 나중”은 가능한 학습 경로일 뿐 모두에게 강제할 순서가 아니다. 첫 프로젝트는 벤치마크 언어 전쟁보다 **자신이 풀 문제의 짧은 실험과 유지보수할 사람**을 기준으로 고르는 편이 낫다.
