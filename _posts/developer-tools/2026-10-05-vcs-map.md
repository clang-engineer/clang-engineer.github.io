버전 관리 도구는 **VCS 자체와 그 인터페이스를 분리해서** 봐야 관계가 선명해진다.

## 전체 레이어

```text
Version Control System
├─ SVN
│  └─ svn CLI
│
├─ Git
│  ├─ git CLI
│  └─ lazygit TUI
│
└─ Jujutsu
   ├─ jj CLI
   └─ jjui TUI
```

즉 대응 관계는 다음과 같다.

```text
SVN      ↔ Git      ↔ Jujutsu     VCS 레이어
svn      ↔ git      ↔ jj          CLI 레이어
           lazygit  ↔ jjui         TUI 레이어
```

## 모델의 변화

```text
SVN
중앙 repository 중심
      ↓

Git
분산 repository + commit graph
branch / HEAD / index
      ↓

Jujutsu
분산 revision graph
change / revision / bookmark
Git backend 사용 가능
```

Jujutsu가 Git 저장소를 backend로 사용할 수 있다는 점 때문에 Git의 UI처럼 보이기 쉽지만, 사용자가 다루는 모델은 별도 VCS에 가깝다.

## SVN

SVN은 중앙 서버의 repository가 중심이다.

```text
Central SVN Repository
        ↕
 Working Copy
```

장점은 모델이 단순하고 중앙 통제가 명확하다는 점이다. 반면 브랜치·오프라인 작업·로컬 히스토리 조작은 Git 계열보다 유연하지 않다.

## Git

Git은 각 로컬 clone이 repository를 가진다.

```text
Remote
  ↕
Local Git Repository
  ↕
Working Tree
```

강점은 압도적인 생태계와 GitHub/GitLab 같은 hosting 플랫폼이다. 대신 branch, HEAD, index/staging, rebase 같은 개념이 겹쳐 학습 비용이 생긴다.

## Jujutsu

Jujutsu는 revision graph를 중심으로 작업한다. Git backend를 사용하면 기존 Git repository와 GitHub 흐름을 유지하면서 다른 작업 모델을 사용할 수 있다.

```text
Git repository format
        ↑ backend
     Jujutsu
     ├─ jj
     └─ jjui
```

대표적인 차이:

| Git | Jujutsu |
|---|---|
| branch가 작업 흐름의 중심 | revision/change가 중심 |
| staging/index가 중요 | working-copy commit 모델 |
| 충돌을 해결해야 진행하는 경우가 많음 | conflict 상태도 revision으로 다룰 수 있음 |
| reflog 등으로 복구 | operation log를 적극적으로 사용 |
| branch | bookmark |

## lazygit과 jjui

둘은 같은 UI 레이어에서 비교할 수 있다.

```text
Git                 Jujutsu
│                   │
├─ git CLI          ├─ jj CLI
└─ lazygit          └─ jjui
```

- **lazygit**: Git을 조작하는 TUI
- **jjui**: Jujutsu를 조작하는 TUI

따라서 `jjui`를 Git용 TUI로 보면 안 되고, Jujutsu를 쓸 때 비로소 의미가 있다.

## 선택 기준

- 기존 Git/GitHub 흐름에 불편이 없다 → Git 유지가 기본값
- rebase·squash·과거 revision 수정이 일상적이고 Git의 상태 모델이 번거롭다 → Jujutsu를 시험할 이유가 생김
- 중앙집중형 repository 모델이 필요한 기존 조직/시스템 → SVN이 여전히 존재할 수 있음

핵심은 "어떤 TUI가 더 좋은가"보다 **어떤 VCS 모델을 사용할 것인가**를 먼저 정하는 것이다.
