tmux 설정은 필요한 옵션과 [플러그인을 직접 조립하는 길](./2026-07-11-tmux-plugins-beyond-essentials.md)도 있고, **잘 짜인 `.tmux.conf`를 통째로 상속하는 길**도 있다. **Oh My Tmux!**(OMT, [`gpakosz/.tmux`](https://github.com/gpakosz/.tmux))는 후자에 속하는 완성형 config 배포판이다. 플러그인 하나를 추가하는 것과 달리 키맵·상태바·플러그인 관리 방식까지 함께 받는다.

이 글은 **무엇을 상속하고 어디까지 내 책임으로 남는지**를 설명한다. 직접 조립과 상속 중 무엇을 택할지 판단한 뒤, 세 가지 커스터마이징 레버와 충돌 지점을 살펴본다. 범용 명령·TERM/RGB/Tc 설정은 [tmux 정본](https://github.com/clang-engineer/devkit/blob/main/reference/cheatsheets/tmux.md)을 참고한다.

## 구조 — 건드리는 파일과 안 건드리는 파일

OMT의 설계는 딱 2파일로 갈린다.

- **`.tmux.conf`** — 엔진. **직접 편집하지 않는다.** upstream이 관리하고, 업데이트로 갱신된다.
- **`.tmux.conf.local`** — 내 override. 모든 커스터마이징이 여기로 간다.

공식 설치는 리포를 `~/.tmux`에 클론하고 심링크를 거는 형태다.

```sh
cd
git clone https://github.com/gpakosz/.tmux.git
ln -s -f .tmux/.tmux.conf   # ~/.tmux.conf → ~/.tmux/.tmux.conf
cp .tmux/.tmux.conf.local .  # 여기부터 내가 편집
```

`.tmux.conf`가 `.tmux.conf.local`을 어떻게 찾는지가 중요하다 — 하드코딩이 아니라 **자기 위치를 자동 감지**한다.

```sh
# .tmux.conf 하단: TMUX_CONF를 아래 순서로 탐색한 뒤
#   "$HOME/.tmux.conf"  "$XDG_CONFIG_HOME/tmux/tmux.conf"  "$HOME/.config/tmux/tmux.conf"
# TMUX_CONF_LOCAL = "$TMUX_CONF.local" 로 잡고 source 한다
```

덕분에 `~/.tmux.conf`(홈)든 `~/.config/tmux/tmux.conf`(XDG)든, 같은 자리에 `.local`만 두면 알아서 물린다. 심링크 레이아웃을 강제하지 않으므로, dotfiles 매니저로 엔진을 `~/.tmux.conf`에 바로 떨궈도 동작한다.

## 채택할 것인가

이 블로그의 기본 노선은 필요한 것만 손으로 얹는 **직접 조립**이다. 이미 손수 다듬은 `.tmux.conf`가 있다면 통째 상속은 오히려 후퇴일 수 있다. 안 쓰는 기능까지 따라오고, 커스텀을 OMT의 override 방식에 다시 맞춰야 하며, 스스로 조립하며 배우는 과정도 줄어든다. 통째로 채택하지 않고 엔진을 레퍼런스로 읽으며 **SSH/Mosh 원격 정보 표시**나 **prefix/mouse/synchronize-panes 표시등**만 가져오는 선택도 가능하다.

반대로 상태바와 관리 기능을 직접 유지하고 싶지 않다면 **규율 있는 상속**이 대안이다. [chezmoi](https://chezmoi.io)의 `.chezmoiexternal`로 엔진을 upstream의 **특정 커밋에 고정**하면 재현 가능하고 `apply` 때 예고 없는 변경을 막는다. `~/.tmux.conf`는 그 엔진의 심링크로 두고, 커스텀과 `@plugin` 선언은 `.tmux.conf.local` 하나로 격리한다. 엔진 수정과 개인 설정이 섞이지 않아 업데이트 차이를 추적하기 쉽다([dotfiles 로드맵](../shell/2026-07-08-00-dotfiles-roadmap.md) 참고). 고정은 업데이트를 포기하는 것이 아니라 변경을 검토한 뒤 커밋을 올리는 방식이다.

## 커스터마이징 워크플로 — 3가지 레버

모든 편집은 `.tmux.conf.local`에서, 세 가지 방식으로 한다.

### 1. `tmux_conf_*` 노브 (준비된 스위치)

자주 바꾸는 건 이미 변수로 노출돼 있다. 주석 처리된 값을 켜거나 바꾸면 된다.

```sh
tmux_conf_new_window_retain_current_path=true   # 새 창을 현재 경로에서
tmux_conf_new_pane_retain_current_path=true     # 새 pane도 (기본 true)
tmux_conf_copy_to_os_clipboard=true             # 복사 → 시스템 클립보드
# 테마 색: tmux_conf_theme_colour_1 … _17, tmux_conf_theme_status_left/right …
```

노브의 값은 이렇게 하는 게 아니라 **OMT한테 "이런 바인딩·설정을 대신 만들어라"고 지시하는 스위치**다. 예를 들어 `retain_current_path=true`를 적으면 OMT가 `new-window -c '#{pane_current_path}'` 바인딩을 자동으로 생성한다. vanilla였다면 그 `bind` 줄을 직접 써야 하는 걸, 참/거짓 한 글자로 추상화해 주는 게 노브의 정체다.

#### OMT가 노출하는 노브 — 전체 카탈로그

"무엇을 상속하는지"의 나머지 절반이 이 목록이다. 3~4개 예시 너머로, OMT가 `tmux_conf_*` 스위치로 열어 둔 설정을 그룹별로 정리한다(2026-07 기준). 각 노브는 `.tmux.conf.local`에 주석으로 이미 들어 있으니, 켜고 싶은 줄의 주석만 풀면 된다.

| 그룹 | 노브 | 켜고/끄는 것 |
|---|---|---|
| **생성 동작** | `new_session_prompt` | 새 세션 만들 때 이름을 물어볼지 (기본 false → 자동 번호) |
| | `new_session_retain_current_path` | 새 세션 시작 경로를 현재 경로로 (기본 false) |
| | `new_window_retain_current_path` | 새 창 시작 경로를 현재 pane 경로로 (기본 **false**) |
| | `new_pane_retain_current_path` | 새 pane(split) 시작 경로를 현재 pane 경로로 (기본 **true**) |
| | `new_window_reconnect_ssh` · `new_pane_reconnect_ssh` | 새 창/pane에서 직전 SSH 세션 자동 재접속 (기본 false) |
| **복사·색** | `copy_to_os_clipboard` | 복사 시 OS 클립보드까지 (기본 false) |
| | `24b_colour` | 24비트 트루컬러 감지·주입 (기본 `auto` — `COLORTERM` → `tput colors` 폴백) |
| **플러그인 자동관리** | `update_plugins_on_launch` | 첫 실행 시 미설치 플러그인 자동 설치 (기본 true — `prefix + I` 대체) |
| | `update_plugins_on_reload` | 리로드 때 플러그인 업데이트 (기본 true — `prefix + U` 대체) |
| | `uninstall_plugins_on_reload` | `@plugin`에서 지운 플러그인을 리로드 때 삭제 (기본 false) |
| **키맵** | `preserve_stock_bindings` | OMT 키맵 대신 vanilla stock 바인딩 유지 (기본 false — 아래 전용 섹션) |
| **테마 골격** | `theme` | 테마 프리셋 on/off (`enabled`/비움) |
| | `theme_colour_1` … `_17` | 16색 팔레트 + 강조색을 직접 지정 |
| | `theme_status_left` · `theme_status_right` | 상태바 좌/우에 무엇을 어떤 순서로 |
| | `theme_left_separator_main/sub` · `theme_right_separator_*` | powerline 구분자 글리프 |
| | `theme_terminal_title` | 터미널 창 제목 포맷 |
| **테마 요소별 색** | `theme_{window,pane,message,mode,clock,prefix,mouse,root,pairing,synchronized,focused,highlight}_*` | 각 요소의 `fg`/`bg`/`attr`를 개별 지정 |
| **배터리 표시등** | `battery_bar_length` · `battery_bar_palette` · `battery_{v,h}bar_palette` · `battery_bar_symbol_{full,empty}` · `battery_status_{charging,discharging}` | 상태바 배터리 게이지의 길이·색·글리프 |

> **`retain_current_path`의 함정 — 새 창은 "어디서" 열리나.** 위 표에서 창은 기본 `false`, pane은 기본 `true`라 **둘이 다르게 움직인다.** `false`일 때 새 창은 "홈"도 "지금 보던 pane의 경로"도 아닌 **그 세션을 처음 `tmux new-session` 한 디렉토리**에서 열린다(이후 `cd`로 돌아다닌 건 무시). 이건 tmux 고유 동작이다 — tmux **1.9**(2014)가 옛 `default-path` 옵션을 없애면서 "현재 경로에서 열고 싶으면 `-c '#{pane_current_path}'`를 직접 써라"로 바꿨고, 이 노브는 그 `-c` 플래그를 대신 끼워 주는 래퍼다. 창도 pane처럼 현재 경로에서 열리길 원하면 `new_window_retain_current_path=true` 한 줄이면 된다.
{: .prompt-warning }

테마 관련 노브가 압도적으로 많지만(팔레트·요소별 색·배터리 게이지), 실전에서 자주 손대는 건 **생성 동작**과 **플러그인 자동관리** 쪽이다. 테마는 프리셋을 그대로 두고 `theme_colour_*`로 색만 맞추는 걸 권한다(아래 tip).

#### 같은 걸 vanilla tmux로 하려면

노브가 "감춘 것"을 드러내면 OMT가 뭘 대신 해 주는지가 선명해진다. 아래는 대표 노브를 껐다 켜는 대신, `.tmux.conf`에 **직접 써야 하는 원본 tmux 명령**이다.

| OMT 노브 | vanilla tmux로 직접 |
|---|---|
| `new_window_retain_current_path=true` | `bind c new-window -c '#{pane_current_path}'` |
| `new_pane_retain_current_path=true` | `bind '"' split-window -c '#{pane_current_path}'`<br>`bind % split-window -h -c '#{pane_current_path}'` |
| `new_session_retain_current_path=true` | 새 세션 명령에 `-c '#{pane_current_path}'` 추가 |
| `new_session_prompt=true` | 새 세션 키를 `command-prompt -p 'session name:' 'new-session -s "%%"'`로 |
| `copy_to_os_clipboard=true` | `set -g set-clipboard on` (OSC52) — [클립보드 편](../terminal/2026-06-10-terminal-clipboard.md) |
| `24b_colour`(강제 on) | 바깥 터미널이 RGB를 지원하는지 확인한 뒤 해당 TERM 패턴에 `terminal-features`의 `RGB`(tmux 3.2+) 또는 `terminal-overrides`의 `Tc` 지정. `default-terminal` 변경은 내부 TERM 설정이라는 별개 책임 |
| `update_plugins_on_launch/reload` 등 | tpm 기본대로 `prefix + I`(설치)·`prefix + U`(업데이트)·`prefix + alt+u`(삭제)를 손으로 |
| `preserve_stock_bindings` | vanilla 자체가 stock이라 **해당 없음** — 이 노브는 "OMT를 쓰되 키맵만 vanilla로"일 때만 의미 |
| `theme_*` (일체) | `set -g status-left/-right …` + `#{}` 포맷 문자열 수십 줄. powerline 구분자·SSH 인식·표시등을 손으로 조립 |

마지막 `theme_*` 행이 OMT의 존재 이유를 압축한다 — 상태바 하나를 vanilla로 저 수준까지 만들려면 포맷 문자열과 씨름하는 수십 줄이 필요하다. 노브는 그 결과물을 통째로 상속하고 색만 바꾸게 해 준다.

### 2. `-- user customizations` 자유 영역 (raw 명령)

노브에 없는 건 이 섹션에 tmux 명령을 날것으로 적는다 — 커스텀 `bind`, `set`, `set-hook` 등.

```sh
# -- user customizations -------------------------------------------------------
set -g mouse on          # 시작부터 마우스 on
set -g history-limit 10000
bind w choose-tree -Zw -O name   # session/window tree를 이름순으로
bind s choose-tree -Zs -O name   # session tree를 이름순으로
```

여기서 함정 하나: OMT는 리로드 때 자기 바인딩을 다시 적용한다. **OMT가 특정 바인딩·설정을 건드리지 못하게 막으려면 줄 끝에 `#!important`를 붙인다.**

```sh
bind c new-window -c '#{pane_current_path}' #!important
```

### 3. `set -g @plugin` (플러그인)

TPM(Tmux Plugin Manager) 문법 그대로 선언하되, **tpm 자체는 선언하지 않는다** — OMT가 tpm 설치·갱신·플러그인 설치까지 대신 한다(`~/.tmux/plugins`에 설치).

```sh
# /!\ do not add: set -g @plugin 'tmux-plugins/tpm'
# /!\ do not add: run '~/.tmux/plugins/tpm/tpm'
set -g @plugin 'christoomey/vim-tmux-navigator'
set -g @plugin 'tmux-plugins/tmux-resurrect'
```

`tmux_conf_update_plugins_on_launch=true`(기본)이라, 첫 실행 시 플러그인이 자동으로 깔린다 — vanilla + tpm에서 익숙한 `prefix + I`를 손으로 누를 필요가 없다.

> **테마는 OMT 기본을 그대로 쓰는 걸 권한다.** "보기 좋게"가 목적이라면 OMT의 powerline이 이미 정석이고, 색만 바꾸고 싶으면 `tmux_conf_theme_colour_*` 노브로 충분하다. 굳이 별도 테마 플러그인(catppuccin 등)을 얹으면 OMT 상태바와 충돌한다.
{: .prompt-tip }

## vanilla tmux 대비 무엇을 바꾸나

OMT가 기본으로 켜 주는 것들(=내가 안 적어도 되는 것) 중 체감 큰 것만.

| 항목 | vanilla | OMT 기본 |
|---|---|---|
| 보조 prefix | `C-b`만 | `C-b` + **`C-a`** (GNU Screen 호환, `prefix2`) |
| 인덱스 | 0부터 | `base-index 1`·`pane-base-index 1`·`renumber-windows on` |
| 복사 모드 | emacs 키 | **vi 키** (하드코딩) |
| 트루컬러 | 바깥 터미널 능력 확인 필요 | `tmux_conf_24b_colour=auto` — 감지·주입 조건은 [색상 심화](#색상-심화--auto가-감지하고-주입하는-것) 참고 |
| 상태바 | 밋밋 | **powerline 테마** — prefix·mouse·synchronize 토글 표시등, 배터리·시계, 그리고 **SSH/Mosh 접속 시 원격 호스트·유저 자동 표시**(로컬일 땐 숨김) |
| 마우스 | off | off이되 **`prefix + m`으로 토글**(상태바에 on/off 표시) |
| 분할 | `"` 세로 · `%` 가로 | **`-` 세로 · `_` 가로** |

특히 상태바의 **SSH/Mosh 인식**이 OMT의 시그니처다 — `#{hostname_ssh}`·`#{username_ssh}` 변수가 원격 접속일 때만 값을 채워, "지금 이 pane이 로컬인지 원격 서버인지"가 한눈에 구분된다. (흔히 OMT의 기능으로 오해되는 *중첩 세션 dimming*은 사실 samoshkin의 F12 토글이다. OMT는 dimming이 아니라 **원격 정보 표시** 쪽이다.)

### 상태바 인디케이터 범례

status-right에 뜨는 한 글자 표시등들. 각 아이콘은 **현재 상태를 켜졌을 때만** 보여준다(꺼지면 사라짐). `tmux_conf_theme_*` 노브로 글리프를 바꿀 수 있다.

| 글리프 | 의미 | 조건 |
|---|---|---|
| `⌨` (U+2328) | **prefix 대기 중** | `prefix` 키를 누른 직후 |
| `↗` (U+2197) | **마우스 모드 ON** — 마우스 커서 형상화 | `prefix + m`으로 토글 |
| `↑` / `↓` (U+2191/2193) | **배터리 충전 / 방전** — 전기가 배터리로 들어오면 위, 소모되면 아래 | 어댑터 연결 여부 |
| `⚏` (U+268F) | **pane 동기화 ON** — 한 입력이 모든 pane에 복제 | `:setw synchronize-panes` (OMT는 키 미지정) |
| `⚇` (U+2687) | **세션 pairing** — 여러 클라이언트가 같은 세션에 attach | 다중 attach 시 |
| `!` | **root 셸** — 위험 경고(bold+blink) | 루트로 tmux 실행 시 |

> 배터리 `↑`/`↓`가 특히 직관적이다 — 스크롤·스크린샷 없이 "지금 충전 중인지"가 방향 하나로 읽힌다.

## 기본 키맵 요점

vanilla와 달라 헷갈리기 쉬운 것 위주로. (전체는 리포 README 또는 `.tmux.conf`의 `bind` 줄 참고.)

### session 순서는 swap하지 않는다

OMT의 `prefix + w`는 별도 세션 관리 UI가 아니라 tmux 기본 `choose-tree -Zw`다. 그래서 pane은 `swap-pane`, window는 `swap-window`로 위치를 바꿀 수 있지만 session에는 대응하는 `swap-session` 명령이 없다.

`choose-tree` 안에서는 `O`로 정렬 기준을 바꾸고 `r`로 역순을 토글할 수 있다. 항상 이름순으로 열고 싶다면 `.tmux.conf.local`에 다음처럼 바인딩할 수 있다.

```tmux
bind w choose-tree -Zw -O name #!important
```

다만 최소 커스텀을 선호한다면 굳이 바인딩을 추가하지 않고 기본 `choose-tree`를 그대로 쓰는 편이 OMT의 의도와도 잘 맞는다. session 이름에 `01-main`, `02-work`처럼 prefix를 붙이는 방식은 이름순 정렬과 함께 쓸 때만 “순서”가 된다.

| 키 | stock(vanilla) | OMT 동작 | 왜 (편의) |
|---|---|---|---|
| `prefix + e` | 미배정 | `.tmux.conf.local`을 `$EDITOR`로 열고 저장 시 리로드 | 설정 편집→소싱을 한 키로 (파일 탐색·수동 리로드 불필요) |
| `prefix + r` | `refresh-client` | 설정 리로드 | 잦은 리로드를 한 키로 |
| `prefix + m` | `select-pane -m` (pane 마크) | 마우스 on/off 토글 | 네이티브 선택 ↔ 휠·클릭·리사이즈를 순간 전환 (아래 tip) |
| `prefix + -` / `prefix + _` | `-`=`delete-buffer` · `_`=미배정 | 세로 / 가로 분할 | 방향과 무관한 stock `"`/`%` 대신 인접한 `-`/`_` 한 쌍 → 기억 부담↓ |
| `prefix + h/j/k/l` | `l`=마지막 창 · `hjk`=미배정 | pane 이동 (vi 방향) | vim 손버릇 그대로 (stock은 화살표·`o` 순환) |
| `prefix + H/J/K/L` | `L`=직전 클라이언트 · `HJK`=미배정 | pane 크기 조절 (반복 가능) | 소문자=이동 / 대문자=리사이즈 짝으로 묶음 |
| `prefix + < / >` | window / pane 메뉴 (`display-menu`) | pane 순서 swap | 화살표가 좌/우 이동 방향을 암시 |
| `prefix + C-h / C-l` | 미배정 | 이전 / 다음 창 | 창 이동도 방향성 있게 (stock `n`/`p` 대신) |
| `prefix + Tab` | 미배정 | 마지막 창 | 에디터 탭 전환 관습(직전 것으로 토글) |
| `prefix + Enter` | 미배정 | 복사 모드 진입 (`v` 선택, `y` 복사, `C-v` 사각 선택) | vim visual 흐름 그대로 |

> **실전 함정 — `C-l` 충돌.** OMT는 루트 테이블에 `bind -n C-l`(화면 클리어 + `clear-history`)을 건다. `vim-tmux-navigator`도 pane 이동에 `C-l`을 쓰므로, 둘을 같이 쓰면 로드 순서에 따라 한쪽이 먹힌다. nvim↔tmux를 `C-hjkl`로 넘나든다면 이 지점을 반드시 확인하라. (이것과 별개로, **창 전환 직후에만 pane 이동이 씹히는** 증상이라면 원인은 clear-screen이 아니라 `bind -r`의 repeat 창이다 → [tmux -r가 다음 키를 삼킨다](../reference/troubleshooting/2026-07-14-repeat-pane-navigation.md))
{: .prompt-warning }

> **왜 마우스는 "설정"이 아니라 "토글"인가.** tmux 마우스를 ON으로 켜면 tmux가 마우스 이벤트를 가로채, 터미널 자신의 **드래그 선택 → OS 클립보드 복사**와 **pane를 가로지르는 선택**(선택이 한 pane 안으로 클리핑된다)이 죽는다. 반대로 ON이면 휠 스크롤백·클릭 pane 전환·드래그 리사이즈가 편하다. 둘이 배타적이라 고정값으로 둘 수 없고 **순간 뒤집는 스위치**가 되는 것 — 평소 ON으로 쓰다 로그·경로를 긁어 복사할 때만 `prefix + m`으로 껐다 켠다(상태바 `↗` 인디케이터로 현재 모드 확인). 터미널이 Shift(iTerm2는 Option) 드래그로 tmux 마우스를 우회해주면 덜 필요하지만, 그 modifier는 터미널마다 달라 이식성이 없다 — OMT는 어느 터미널에서든 되는 범용 탈출구로 토글을 기본 제공한다.
{: .prompt-info }

## stock 키맵을 지키려면 — `preserve_stock_bindings`

위 키맵 표의 이면엔 함정이 하나 있다 — **OMT의 키 상당수가 vanilla tmux의 stock 바인딩을 덮어쓴다.** 다른 서버·머신에서 익힌 손버릇이 그만큼 깨진다.

| 키 | vanilla(stock) | OMT | 왜 (편의) |
|---|---|---|---|
| `n` | 다음 창 | **언바운드** (창 이동은 `C-l`) | 창 이동을 방향성 있는 `C-h`/`C-l` 한 쌍으로 통일 |
| `p` | 이전 창 | **paste-buffer** | `p`=paste 니모닉 (vim·셸과 동일) |
| `m` | pane 마크(`select-pane -m`) | **마우스 토글** | 마우스 on/off 순간 전환 (위 tip) |
| `l` | 마지막 창 | **pane 오른쪽 이동** | vim `hjkl` 패널 이동 |

(`"`/`%` 분할, `c` 새 창, `s`/`w` 트리 등은 그대로다. `_`는 신규 키지만 `-`는 기존 `delete-buffer`를 덮어쓴다. 두 분할 키를 같이 추가한 것으로 오해하면 안 된다.)

`prefix + n`을 눌렀는데 아무 일도 안 일어나거나 `prefix + p`가 난데없이 버퍼를 붙여넣는다면 이 때문이다. **stock 키맵을 그대로 쓰고 싶다면** `.tmux.conf.local` 최상단의 노브 하나면 된다.

```sh
tmux_conf_preserve_stock_bindings=true
```

`true`면 OMT는 **stock 바인딩을 보존하고 충돌하지 않는 확장만 얹는다** — 별도 probe 서버를 띄워 vanilla 바인딩을 떠온 뒤 병합하는 방식이다. 테마·상태바·플러그인 자동 관리 같은 OMT의 실제 가치는 그대로 챙기면서 키맵만 vanilla로 되돌린다.

> **실익 판단.** OMT 키맵의 이득(`hjkl` pane 이동·`r`/`e` 편의)과 stock 키맵의 이득(다른 서버에서도 이어지는 손버릇)을 비교하자. SSH로 다른 서버를 자주 쓴다면 stock 보존의 가치가 크다. 다만 앞에서 설명한 **root 테이블의 bare `C-l` 충돌**은 prefix 키맵과 별개이므로 이 노브만 켜서 사라졌다고 가정하지 말고 최종 바인딩을 확인한다.
{: .prompt-tip }


## 상속한 설정을 검증할 때 — running 서버를 순정으로 착각하지 않기

OMT 키맵과 tmux 기본 키맵을 비교하려면 이미 여러 차례 `source-file`한 서버에서 `list-keys`만 실행하면 안 된다. 설정에서 삭제된 바인딩은 현재 서버에 남을 수 있고, `tmux -f /dev/null`도 기존 기본 소켓에 연결하면 시작 설정을 되돌리지 못한다. 별도 소켓에 순정 설정으로 새 세션을 만든 뒤 **같은 호출 안에서** 바인딩을 확인한다.

```sh
tmux -L "stock_$$" -f /dev/null new-session -d \; \
  list-keys -T prefix \; kill-server
```

2026년 8월의 tmux 3.7b 대조에서는 `prefix + n` 해제, `p`의 paste 재배정처럼 기존 키를 덮는 항목과, 새로운 `prefix + _`처럼 빈 키에 덧붙이는 항목이 섞여 있었다. `prefix + -`도 기본 `delete-buffer`에 대한 재배정이었다. 반면 `"`와 `%`는 분할 키로 남았다. **이것은 당시 버전의 OMT·tmux 조합에서 관찰한 delta**이지 최신 버전의 불변 키맵이 아니다. `tmux_conf_preserve_stock_bindings=true`도 OMT 키를 전부 끄는 스위치는 아니므로 실제 서버의 `list-keys`로 결과를 확인한다.

## 테마 충돌보다 덜 침습적인 색상 위임

OMT의 상태바를 유지하면서 터미널 테마에 맞추려면 색의 소유권을 구별한다. hex 색은 터미널 팔레트와 무관한 고정값이고 `colour0`~`colour15`는 16색 팔레트에 매핑된다. `.tmux.conf.local`의 `tmux_conf_theme_colour_*` 값을 터미널의 ANSI 색에 맞추면 **상태바 레이아웃의 소유자는 OMT 그대로**, 팔레트의 소유자는 터미널로 남는다. Neovim 자체 truecolor 테마까지 자동으로 바뀐다는 뜻은 아니다.

별도의 tmux 테마 플러그인을 OMT 위에 올리면 양쪽이 `status-left/right`·`window-status-format` 같은 동일 옵션을 설정할 수 있다. 색만 바꾸려던 일이 상태바 레이아웃 전체의 last-wins 경쟁이 되므로 OMT 테마와 외부 테마 중 하나를 골라야 한다.

## `C-l`만 동작하지 않을 때

Neovim과 tmux 사이를 `vim-tmux-navigator`로 이동하는데 `C-h/j/k`만 되고 `C-l`에서 화면만 지워진다면 두 도구가 **root 테이블의 같은 키**를 선언했는지 확인한다. OMT의 clear-history/clear-screen 경로와 navigator의 오른쪽 이동이 로드 순서에 따라 경쟁할 수 있다. `tmux list-keys -T root`의 `C-l` 결과가 실제 승자다. 한 번 `source-file`해서 고쳐졌다는 것만으로 재기동 후에도 같은 결과라고 단정하지 않는다. 새 세션에서 실제 바인딩을 비교하고 플러그인 hook 등록 여부뿐 아니라 hook 실행 뒤 키의 최종 값을 확인한다. 이 충돌과 `prefix + C-l`의 창 전환은 **다른 키 테이블**의 문제다.

키맵을 스크립트로 diff할 때도 출력의 `\"`·`\%` 같은 특수 키를 `awk -v key=\"$key\"`로 비교하면 이스케이프가 바뀌어 실제로 남아 있는 `\"`/`%` 분할 키를 **가짜 제거**로 분류할 수 있다. 탭으로 구분한 정렬된 `key<TAB>command` 목록을 두 개 만든 뒤 `join`으로 키 문자열을 그대로 비교하면 안전하다. 단순 문자 키만 일치했다고 특수 키까지 맞는다고 추측하지 않는다.

순정 복사 모드도 **복사 여부만** 비교하면 놓친다. `copy-selection-no-clear`와 `copy-pipe-and-cancel`은 선택 후 copy mode에 계속 머무는지에서 다르다. 후자로 폴백하면 복사 뒤 남은 선택을 다시 사용하는 키 동작이 깨질 수 있다. 키 제거 전에 현재 설정과 순정 서버의 **실제 명령 전체**를 비교해야 하는 이유다.

## 색상 심화 — auto가 감지하고 주입하는 것

상태바 팔레트의 소유권과 **24비트 색을 바깥 터미널까지 전달하는 능력**은 별개다. `tmux_conf_24b_colour`는 `true`면 감지 없이 활성화하고, `false`면 이 자동 주입을 하지 않으며, 기본 `auto`면 환경을 확인한다. `false`가 이미 존재하는 RGB 설정까지 제거하는 스위치라는 뜻은 아니다.

2026-11-18 확인한 [upstream `.tmux.conf`](https://github.com/gpakosz/.tmux/blob/master/.tmux.conf)의 `_apply_24b()` 핵심은 다음과 같다. 엔진에 셸 코드가 주석 형태로 들어 있고, `run 'cut -c3- "$TMUX_CONF" | sh -s _apply_configuration'`으로 실행한다. `_apply_configuration`은 `_apply_tmux_256color`를 먼저 호출한 뒤 `_apply_24b`를 실행한다.

```sh
# _apply_24b()의 감지·주입 핵심 (upstream 주석 접두부 생략)
if [ "$tmux_conf_24b_colour" = "auto" ]; then
  case "$COLORTERM" in
    truecolor|24bit) apply_24b=true ;;
  esac
  if [ "$apply_24b" = "" ] && [ "$(tput colors 2>/dev/null)" = "16777216" ]; then
    apply_24b=true
  fi
elif _is_true "$tmux_conf_24b_colour"; then
  apply_24b=true
fi
if [ "$apply_24b" = "true" ]; then
  case "$TERM" in
    screen-*|tmux-*) ;;
    *)
      if [ "$(_tmux_version)" -ge 3200 ]; then
        tmux set -sa terminal-features ",*256col*:RGB"
      else
        tmux set -ga terminal-overrides ",*256col*:Tc"
      fi
      ;;
  esac
fi
```

첫 판단은 `COLORTERM=truecolor` 또는 `24bit`라는 [관례](https://github.com/termstandard/colors)다. 여기에 맞지 않으면 `tput colors`가 `16777216`(2²⁴)을 반환하는지 확인한다. 따라서 단순히 `256`이 나오는 terminfo는 이 폴백을 켜지 않는다. 현재 upstream은 **tmux 3.2 이상에서 `RGB` terminal feature**, 그보다 오래된 버전에서 **`Tc` override**를 추가한다. 예전 원문처럼 “항상 Tc를 주입한다”고 설명하면 현재 코드와 다르다.

### pane의 TERM과 감지 셸의 TERM을 혼동하지 않기

위 `$TERM`·`$COLORTERM`과 `tput`은 **tmux의 `run-shell` 경로에서 실행되는 셸 환경**을 본다. pane 안에서 `echo "$TERM"`으로 본 값만으로 그 함수의 분기를 단정할 수 없다. 서버·세션 환경과 시작·리로드 맥락을 함께 봐야 한다. `_apply_tmux_256color`가 바꾸는 `default-terminal`도 새 pane에 광고할 터미널 설명이지, 현재 실행 중인 감지 셸의 `$TERM`을 바꾸는 셸 대입문은 아니다.

감지 셸의 TERM이 `screen-*`나 `tmux-*`라면, 예를 들어 tmux 안에서 또 tmux 서버를 시작한 맥락이라면, 활성화 판정 뒤에도 추가 주입은 건너뛴다. **이는 코드의 중첩 환경 분기이지, 해당 terminfo에 RGB가 이미 들어 있다는 증거가 아니다.** `true`로 강제해도 이 분기는 그대로 적용된다. 또한 주입 패턴은 `*256col*`뿐이므로 모든 바깥 TERM에 적용되는 만능 설정도 아니다.

원문에서 관찰한 `COLORTERM=truecolor`, pane의 `TERM=tmux-256color`, 정상적인 색 출력은 유효한 관찰이다. 하지만 그 값만으로 “OMT가 주입을 스킵했고 내장 RGB 덕에 성공했다”는 인과까지 확인한 것은 아니다. 실제 로컬 `infocmp -x tmux-256color` 확인에서도 `RGB`가 없었다. terminfo 항목의 존재와 RGB 능력 포함 여부를 구별해야 한다.

[tmux 공식 FAQ](https://github.com/tmux/tmux/wiki/FAQ#how-do-i-use-rgb-colour)는 **바깥 터미널이 RGB를 지원한다는 사실을 `RGB` 또는 `Tc`로 tmux에 알려야 한다**고 명시한다. `RGB`는 공식 플래그이고 `Tc`는 tmux 확장이다. 내부 `TERM=tmux-256color`가 바깥 RGB를 자동 보장하거나 교정하지 않는다. 바깥 `xterm-256color`를 이 문제 때문에 `tmux-256color`로 바꾸어서도 안 된다. 바깥 TERM은 실제 터미널을, 안쪽 TERM은 tmux가 제공하는 터미널을 설명한다. 범용 설정 예와 TERM 패턴 선택은 [tmux 정본](https://github.com/clang-engineer/devkit/blob/main/reference/cheatsheets/tmux.md)에서 다룬다.

### 출력과 설정을 나눠 검증하기

tmux 밖과 안에서 각각 `printf '%s\n' "$TERM" "$COLORTERM"`을 보고, 안에서는 `tmux show-options -s terminal-features`와 `tmux show-options -s terminal-overrides`를 확인한다. 감지 실행 환경이 필요하면 같은 서버에서 `run-shell`로 TERM·COLORTERM·`tput colors`를 출력하게 해 pane 셸과 구별한다. 지원 버전에 따라 `terminal-features` 옵션이 없을 수 있다.

출력 확인은 내려받은 스크립트를 바로 실행하지 않고, 아래처럼 직접 RGB escape를 보내도 된다. 같은 예를 tmux 밖과 안에서 비교한다.

```sh
i=0
while [ "$i" -lt 256 ]; do
  printf '\033[48;2;%s;%s;%sm ' "$i" "$((255 - i))" 128
  i=$((i + 1))
done
printf '\033[0m\n'
```

매끈한 그라디언트와 뚜렷한 banding 차이는 전달 경로를 살피는 단서다. 화면이 좋아 보인다는 사실만으로 어느 설정이 원인이었는지 확정하지 않는다. 바깥 능력, 서버 옵션, 감지 셸 환경을 함께 확인해야 “auto가 해 줬다”와 “다른 설정으로 이미 됐다”를 구별할 수 있다.
