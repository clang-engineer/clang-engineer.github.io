여러 ID를 한 번에 검사할 때는 조회 대상 목록과 실제 테이블의 데이터를 비교해야 한다. 이때 목록 자체를 SQL 안에서 테이블처럼 다루면 쿼리를 읽기 쉬워진다.

## 1. 대상 목록을 테이블처럼 만들기

```sql
WITH target(id) AS (
    SELECT UNNEST(ARRAY['001', '002', '003']::varchar[])
)
SELECT * FROM target;
```

결과:

| id |
| --- |
| 001 |
| 002 |
| 003 |

`ARRAY`는 값들을 배열로 묶고, PostgreSQL의 `UNNEST`는 배열 원소를 각각의 행으로 펼친다. `::varchar[]`는 문자열 배열로 타입을 지정하는 PostgreSQL 문법이다.

여기서 `WITH target(id) AS (...)`의 의미는 다음과 같다.

- `WITH`: CTE 정의 시작
- `target`: 이후 쿼리에서 테이블처럼 참조할 이름
- `(id)`: CTE 결과의 첫 번째 컬럼 이름
- `AS (...)`: 결과를 만드는 쿼리

다음처럼 `SELECT` 안에서 컬럼 이름을 지정해도 된다.

```sql
WITH target AS (
    SELECT UNNEST(ARRAY['001', '002', '003']::varchar[]) AS id
)
SELECT target.id FROM target;
```

## 2. CTE는 무엇인가?

CTE(Common Table Expression)는 한 SQL 문 안에서 이름을 붙여 참조하는 결과 집합이다. 실제 영구 테이블을 생성하지 않으며, 같은 SQL 문 안의 후속 쿼리에서 사용할 수 있다.

서브쿼리를 `FROM`에 직접 넣는 방식과 비교하면 구조가 잘 보인다.

```sql
-- FROM 서브쿼리
SELECT *
FROM (SELECT id FROM users WHERE active = true) AS target;

-- CTE
WITH target AS (
    SELECT id FROM users WHERE active = true
)
SELECT * FROM target;
```

두 예제는 같은 행을 조회한다. 다만 **CTE라고 해서 항상 더 빠른 것은 아니다.** PostgreSQL은 조건에 따라 CTE를 상위 쿼리에 통합하거나 결과를 Materialize할 수 있으므로, 성능은 실행 계획으로 판단해야 한다.

## 3. 여러 CTE를 연결해 누락 데이터 확인하기

```sql
WITH target(id) AS (
    SELECT UNNEST(ARRAY['001', '002', '003']::varchar[])
),
target_rows AS (
    SELECT
        target.id AS target_id,
        outcomes.id AS found_id,
        outcomes.cci_score,
        CASE
            WHEN outcomes.id IS NULL THEN 'MISSING'
            ELSE 'FOUND'
        END AS status
    FROM target
    LEFT JOIN postoperative_outcomes AS outcomes
        ON outcomes.id = target.id
)
SELECT *
FROM target_rows
ORDER BY target_id;
```

위 예제의 `postoperative_outcomes`는 설명을 위한 테이블 이름이다.

쿼리는 다음 순서로 읽으면 된다.

```text
target: 조회할 ID 목록 생성
  ↓ (다음 CTE가 target을 참조)
target_rows: 실제 테이블과 LEFT JOIN
  ↓ (최종 SELECT가 target_rows를 참조)
ID별 존재 여부와 CCI Score 출력
```

`LEFT JOIN`은 왼쪽의 `target` 행을 유지하므로 실제 테이블에 없는 ID도 결과에 남는다.

가령 다음과 같은 결과가 나올 수 있다.

| target_id | found_id | cci_score | status |
| --- | --- | --- | --- |
| 001 | 001 | 12.34 | FOUND |
| 002 | NULL | NULL | MISSING |
| 003 | 003 | NULL | FOUND |

여기서 `MISSING`은 행을 찾지 못했다는 뜻이다. `FOUND`인데 `cci_score`가 `NULL`이면 행은 있지만 점수 값이 비어 있다는 뜻이다. 둘을 구분해야 한다.

점수 입력 여부까지 분류하려면 다음처럼 바꿀 수 있다.

```sql
CASE
    WHEN outcomes.id IS NULL THEN 'MISSING'
    WHEN outcomes.cci_score IS NULL THEN 'CCI_NULL'
    ELSE 'CCI_EXISTS'
END AS status
```

단, `outcomes.id`가 유일하지 않다면 하나의 대상 ID에서 결과 행이 여러 개 나올 수 있다. 이 쿼리는 조회만 수행하며 데이터를 변경하지 않는다.

## 4. 언제 유용한가?

- 조회 대상 ID 목록을 실제 테이블과 비교할 때
- 여러 단계의 조회를 의미 있는 이름으로 나눌 때
- 같은 중간 결과를 한 SQL 문 안에서 재참조할 때

핵심은 **CTE가 테이블을 새로 만드는 문법이 아니라, 쿼리 결과에 이름을 붙여 다른 쿼리 부분에서 테이블처럼 참조하도록 하는 문법**이라는 점이다.

PostgreSQL에서 실행 방식이 궁금하다면 [EXPLAIN 노드·필드 사전](./2026-07-03-postgresql-explain-node-reference.md)의 `CTE Scan` 항목을 함께 참고할 수 있다.
