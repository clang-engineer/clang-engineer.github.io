브라우저에서 `fetch()` 요청이 실패할 때 CORS부터 떠올리기 쉽지만, 먼저 **누가 무엇을 제한하는지**를 구분해야 한다.

```text
웹 페이지 JavaScript
      ↓ Cross-Origin 요청
Browser
      ↓ 요청은 전송될 수도 있음
Server
      ↓ 응답 + CORS Header
Browser
      ↓ SOP/CORS 정책 검사
JavaScript가 응답을 읽을 수 있는가?
```

핵심은 CORS가 서버 간 네트워크 연결을 열어주는 기능이 아니라 **브라우저가 Cross-Origin 응답을 JavaScript에 노출할지 결정할 수 있도록 서버가 허용 의사를 표현하는 HTTP 메커니즘**이라는 점이다.

## 1. Origin은 scheme + host + port다

Origin은 다음 세 요소로 판단한다.

```text
scheme + host + port
```

| URL A | URL B | Same Origin? |
|---|---|---|
| `http://example.com` | `http://example.com` | yes |
| `http://example.com` | `http://example.com:8080` | no |
| `http://example.com` | `https://example.com` | no |
| `http://example.com` | `http://sub.example.com` | no |

하나라도 다르면 Cross-Origin이다.

## 2. SOP — 다른 Origin과의 상호작용을 제한하는 브라우저 정책

Same-Origin Policy(SOP)는 한 Origin에서 실행된 문서나 Script가 다른 Origin의 리소스와 상호작용할 수 있는 범위를 제한하는 브라우저 보안 경계다.

중요한 점은:

```text
Cross-Origin 요청 자체가 항상 전송 금지
```

가 아니라는 것이다.

예를 들어 HTML의 `<img>`나 `<form>`처럼 Cross-Origin으로 리소스를 요청하거나 전송할 수 있는 동작도 있다. 하지만 JavaScript가 다른 Origin의 응답 내용을 자유롭게 읽는 것은 SOP의 제한을 받는다.

SOP는 웹 보안의 중요한 기본 경계지만 **CSRF나 XSS를 모두 막아주는 단일 방어책은 아니다.**

- CSRF는 Cross-Origin 요청이 실제로 전송될 수 있다는 성질을 이용할 수 있어 SameSite Cookie, CSRF Token 등의 별도 방어가 필요하다.
- XSS는 공격 Script가 신뢰된 Origin 안에서 실행되는 문제이므로 CSP, 출력 Encoding, 입력 처리 등 별도 방어가 필요하다.

## 3. CORS — 서버가 Cross-Origin 읽기를 허용하는 방식

CORS(Cross-Origin Resource Sharing)는 서버가 HTTP 응답 Header를 통해 특정 Origin의 브라우저 JavaScript에 응답 접근을 허용할 수 있게 한다.

가장 기본적인 Header는:

```http
Access-Control-Allow-Origin: https://app.example.com
```

이다.

`Access-Control-Allow-Origin`은 일반적으로 **응답 하나에 하나의 Origin 값 또는 `*`**를 사용한다. 여러 Origin을 쉼표로 나열하는 방식이 아니다.

여러 Origin을 허용하려면 Server가 요청의 `Origin`을 허용 목록과 비교한 뒤 허용된 경우 그 Origin 값을 응답에 넣는 식으로 처리한다.

```text
Origin: https://app.example.com
        ↓
Server Allowlist 확인
        ↓ allowed
Access-Control-Allow-Origin: https://app.example.com
```

대표 Header:

| Header | 역할 |
|---|---|
| `Access-Control-Allow-Origin` | 응답 접근을 허용할 Origin |
| `Access-Control-Allow-Methods` | Preflight에서 허용할 Method |
| `Access-Control-Allow-Headers` | Preflight에서 허용할 Request Header |
| `Access-Control-Allow-Credentials` | Credential 포함 요청 허용 여부 |
| `Access-Control-Expose-Headers` | JavaScript에 추가로 노출할 Response Header |
| `Access-Control-Max-Age` | Preflight 결과 Cache 시간 |

## 4. Simple Request와 Preflight는 요청의 위험도가 아니라 형식으로 갈린다

Cross-Origin 요청이라고 항상 `OPTIONS`가 먼저 나가는 것은 아니다.

CORS 규격의 safelisted 조건을 만족하면 Browser는 실제 요청을 바로 보낼 수 있다. 이를 흔히 Simple Request라고 부른다.

대표 조건:

- Method가 `GET`, `HEAD`, `POST` 중 하나
- Script가 설정한 Request Header가 CORS-safelisted 범위 안
- `Content-Type`을 직접 지정한다면 `application/x-www-form-urlencoded`, `multipart/form-data`, `text/plain` 중 하나 등 safelist 조건을 만족

반대로 다음은 대표적으로 Preflight를 유발한다.

```text
PUT / PATCH / DELETE
Authorization 같은 non-safelisted Header
application/json Content-Type
```

흐름은:

```text
Browser
  ↓ OPTIONS
Preflight Request
  ↓
Server가 Method/Header/Origin 허용 여부 응답
  ↓ 허용
Browser
  ↓
실제 Request
```

예:

```http
OPTIONS /api/orders HTTP/1.1
Origin: https://app.example.com
Access-Control-Request-Method: POST
Access-Control-Request-Headers: authorization, content-type
```

Server가 적절한 CORS Header를 반환해야 Browser가 실제 요청을 이어서 보낸다.

## 5. Preflight가 없는 요청도 CORS 검사는 끝나지 않았다

Simple Request는 Preflight가 없다는 뜻이지 SOP/CORS 검사를 받지 않는다는 뜻이 아니다.

```text
Simple Request
→ 실제 Request 바로 전송
→ Response의 CORS Header 검사
→ 허용되지 않으면 JavaScript가 Response를 읽지 못함
```

이 점 때문에 Network 탭에서는 Server가 `200`을 반환한 것처럼 보이는데 JavaScript에서는 CORS Error가 날 수 있다.

## 6. Credential 포함 요청

Cookie나 HTTP 인증 정보 등 Credential을 포함한 Cross-Origin 요청에서는 Client와 Server 양쪽 설정이 맞아야 한다.

Client 예:

```javascript
fetch('https://api.example.com/orders', {
  credentials: 'include'
});
```

Server:

```http
Access-Control-Allow-Origin: https://app.example.com
Access-Control-Allow-Credentials: true
```

Credential을 사용하는 요청에서는 `Access-Control-Allow-Origin: *`를 사용할 수 없다. 허용된 구체적인 Origin을 반환해야 한다.

또한 Cookie 전송 여부는 CORS 설정만으로 결정되지 않는다. Cookie의 Domain/Path/Secure/SameSite 정책도 별도로 적용된다.

```text
Cookie가 전송되는가?
→ Cookie 정책

JavaScript가 Cross-Origin 응답을 읽을 수 있는가?
→ SOP + CORS
```

두 축을 섞지 않는다.

## 7. CORS는 Browser 보안 모델이다

`curl`, Postman, Backend Server-to-Server 호출은 Browser의 SOP 집행 대상이 아니다.

따라서:

```text
Postman에서는 성공
Browser에서는 CORS Error
```

는 충분히 가능한 상황이다.

이때 Server API 자체의 연결 장애가 아니라 **Browser에 반환되는 CORS 정책**을 확인한다.

## 8. 흔한 장애를 흐름으로 진단한다

### `No 'Access-Control-Allow-Origin' header`

응답에 허용 Origin Header가 없거나, Error 응답 경로에서 CORS Filter가 적용되지 않았을 수 있다.

```text
Request가 Server에 도달했는가?
→ Response Status 확인
→ Error Response에도 CORS Header가 붙는가?
```

### Preflight가 401/403

인증 Filter가 `OPTIONS`를 실제 API Request처럼 막고 있을 수 있다.

```text
OPTIONS
  ↓
CORS 처리
  ↓
실제 Request에 대한 인증/인가
```

Framework에서는 CORS 처리와 Security Filter 순서를 확인한다.

### Origin 불일치

Origin 비교는 scheme, host, port까지 포함한다.

```text
http://localhost:3000
≠
http://localhost:8080
```

### Response Header가 있는데 JavaScript에서 안 보임

기본 노출 범위 밖의 Header라면:

```http
Access-Control-Expose-Headers: X-Total-Count
```

처럼 별도로 노출해야 할 수 있다.

## 정리

SOP와 CORS 관계를 한 줄로 보면:

```text
SOP
→ Browser의 기본 Cross-Origin 보안 경계

CORS
→ Server가 그 경계 안에서 특정 Cross-Origin 접근을 허용한다고 표현하는 HTTP 규칙
```

진단할 때는 다음 순서가 좋다.

```text
1. 두 URL의 Origin이 실제로 다른가?
2. Preflight가 필요한 요청인가?
3. OPTIONS가 성공하는가?
4. 실제 Response에 올바른 Allow-Origin이 있는가?
5. Credential/Cookie 정책이 별도로 맞는가?
6. JavaScript가 필요한 Response Header를 읽을 수 있는가?
```

**CORS 문제는 "서버가 요청을 받았느냐"와 "브라우저가 응답을 Script에 공개하느냐"를 분리해서 보는 것이 핵심이다.**
