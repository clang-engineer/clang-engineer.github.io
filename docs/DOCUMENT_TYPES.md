# 문서 유형별 작성 원칙

이 문서는 블로그와 저장소의 기술 문서를 **목적에 맞는 구조로 작성하기 위한 공통 설계 원칙**을 정의한다.

문체·용어·표기 방법은 [`WRITING_STYLE.md`](WRITING_STYLE.md)를 따르고, 개념을 어떤 단위로 묶고 나눌지는 [`KNOWLEDGE_ORGANIZATION.md`](KNOWLEDGE_ORGANIZATION.md)를 함께 따른다. 특정 하위 영역에 별도 작성 규칙이 있으면 이 문서 위에 추가로 적용한다.

## 1. 최상위 원칙 — 먼저 문서의 목적을 결정한다

모든 글에 하나의 형식을 강제하지 않는다. 문서를 작성하거나 크게 수정하기 전에 먼저 **이 문서가 독자에게 무엇을 제공하려는지** 결정한다.

```text
문서 목적
   │
   ├─ 지식을 이해시킨다
   │    → Roadmap / Concept / Architecture / Comparison
   │
   ├─ 도구를 이해하고 선택하게 한다
   │    → Tool
   │
   ├─ 작업을 수행하게 한다
   │    → How-to
   │
   ├─ 문제를 해결하게 한다
   │    → Troubleshooting
   │
   └─ 경험·결정·결과를 남긴다
        → Record / Decision
```

문서 유형이 불분명하면 본문을 쓰기 전에 목적을 먼저 좁힌다. 한 글이 여러 유형을 과도하게 섞으면 분리하거나 주 유형을 정하고 나머지는 보조 Section으로 제한한다.

### 이해 가능성이 완전성보다 우선한다

기술 문서의 최우선 목적은 정보를 빠짐없이 담는 것이 아니라 **독자가 쉽게 이해하고 머릿속에 전체 구조와 관계를 그릴 수 있게 하는 것**이다.

- 정확한 정보라도 현재 문서의 이해 흐름에 필요하지 않으면 본문에서 줄이거나 하위 문서·Reference로 보낸다.
- 큰 그림만으로 충분한 주제는 그 깊이에서 멈춘다.
- 핵심 원리·동작·경계를 더 이해해야 하는 지점에서만 선택적으로 Zoom-in 한다.
- 세부 정보는 필요할 때 다시 찾을 수 있도록 연결하되, 상위 문서의 흐름을 방해하지 않게 한다.

> **문서의 품질은 담긴 정보량보다, 읽고 난 뒤 독자의 머릿속에 구조와 관계가 얼마나 선명하게 남는지로 우선 판단한다.**

## 2. 공통 구조 원칙은 지식 구성 원칙을 따른다

큰 그림에서 필요한 만큼 Zoom-in하고, 실제 관계를 따르며, 서로 다른 분류축을 억지로 한 줄에 세우지 않는 기준은 [저장소 공통 지식 구성 원칙](KNOWLEDGE_ORGANIZATION.md)을 정본으로 따른다.

이 문서에서는 그 원칙을 다시 설명하지 않고 **Roadmap, Concept, Architecture, Comparison, Tool, How-to, Troubleshooting, Record / Decision이 각각 무엇을 우선해야 하는지**만 추가한다.

이해형 문서에서 공통으로 기억할 최소 흐름은 다음 정도다.

```text
큰 그림 / 현재 위치
        ↓
필요한 관계·경계
        ↓
필요한 만큼만 Zoom-in
        ↓
세부 이해 후 다시 상위 구조 확인
```

처리 과정은 가능하면 `입력 → 처리 → 출력`, 비교는 먼저 비교축을 확인하고, 실제 인과가 없으면 Story를 강제하지 않는다.

## 3. Roadmap — 전체 지형과 학습 순서를 보여준다

### 목적

독자가 영역의 전체 구조를 먼저 보고 **무엇을 어떤 순서로 이해해야 하는지** 판단하게 한다.

### 권장 흐름

```text
영역의 목적·범위
   ↓
전체 지도
   ↓
큰 축과 관계
   ↓
권장 학습 순서
   ↓
각 단계의 핵심 질문
   ↓
개별 문서 연결
   ↓
다른 Roadmap과의 경계
```

### 원칙

Roadmap은 처음 한 번 보고 지나가는 목차가 아니라 **세부 학습 중 반복해서 돌아오는 좌표계**다.

```text
Roadmap에서 전체 위치 확인
        ↓
필요한 Concept로 Zoom-in
        ↓
세부 원리·동작 이해
        ↓
Roadmap으로 Zoom-out
        ↓
전체에서 위치·관계 재확인
        ↓
다음 학습 대상 선택
```

세부를 이해한 뒤에는 해당 지식만 독립적으로 남겨두지 않고 Roadmap으로 돌아와 **전체 구조에서 어디에 위치하고 인접 개념과 어떻게 연결되는지** 다시 확인한다. 상세 학습에서 새로운 관계나 경계가 발견되면 Roadmap 자체도 보정한다.

- 개별 개념의 상세 설명보다 **위치·관계·순서**를 우선한다.
- **Roadmap은 영역의 모든 내용을 담는 목차나 백과사전이 아니다.** 독자가 큰 그림을 잡는 데 필요한 핵심 축·관계·대표 진입점만 남긴다.
- 단순 목차가 아니라 왜 이 순서로 보는지 드러나야 한다. 실제 선행관계가 없다면 억지 학습 단계로 만들지 않는다.
- 영역 전체에서 모든 하위 개념을 펼치지 않는다. 큰 가지와 대표적인 진입점만 남기고 필요한 곳에서 하위 Roadmap이나 상세 문서로 Zoom-in 한다.
- 한 Roadmap 안에서 서로 다른 거시 관점이 섞여 큰 그림이 흐려지면, 분량이 아니라 **이해 축**을 기준으로 여러 Roadmap으로 나눌 수 있다.
- 하위 문서는 개수나 분량 때문에 기계적으로 만들지 않고, 연관 개념을 한 번 더 함께 볼 때 이해가 좋아지는 경우에 만든다.
- 영역 밖의 주제와 경계를 명시해 Roadmap이 무한히 커지지 않게 한다.
- 세부 설명은 해당 Concept 문서로 연결하고 Roadmap에서 반복하지 않는다.

## 4. Concept — 개념을 이해하고 다시 도출할 수 있게 한다

### 목적

정의 암기보다 **왜 존재하고 어떻게 동작하며 어디에 연결되는지** 이해하게 한다.

### 권장 흐름

```text
전체에서의 위치
   ↓
왜 필요한가
   ↓
핵심 정의
   ↓
전체 처리 흐름·관계
   ↓
구조·구성요소
   ↓
동작 원리
   ↓
예제·Diagram
   ↓
인접 개념과 경계
```

### 원칙

- 세부 API나 옵션부터 시작하지 않는다.
- 처음에는 큰 그림을 잡고 필요한 만큼만 내부로 내려간다.
- 실제 인과가 있으면 `왜 필요한가 → 어떻게 해결하는가 → 어떤 결과·Trade-off가 생기는가`가 읽히게 한다.
- 인과가 없으면 비교·계층·경계·조합 관계를 사용한다.
- 처리 메커니즘은 가능하면 입력과 출력이 보이게 설명한다.
- Text/ASCII Diagram이 관계 이해에 도움이 되면 적극 사용한다.
- 관련 있다는 이유만으로 주변 지식을 끝없이 확장하지 않는다.

## 5. Architecture / Analysis — 구조와 상호작용을 설명한다

### 목적

시스템·프레임워크·애플리케이션의 **구성요소와 책임, 상호작용, 설계 선택**을 이해하게 한다.

### 권장 흐름

```text
대상과 문제
   ↓
전체 Architecture
   ↓
구성요소와 책임
   ↓
Data / Control Flow
   ↓
핵심 상호작용
   ↓
설계 선택과 Trade-off
   ↓
경계·한계·결론
```

### 원칙

- 구성요소 목록보다 관계를 먼저 보여준다.
- 복잡한 내부 호출은 먼저 `입력 → 처리 → 출력/상태 변화`로 단순화한 뒤 필요한 부분만 확대한다.
- 서로 다른 분류축의 구성요소를 한 계층처럼 섞지 않는다.
- Diagram은 박스 수보다 **흐름과 책임**이 읽히는지가 중요하다.
- 구현 세부는 Architecture 판단에 필요한 수준까지만 포함한다.

## 6. Comparison — 비교축을 먼저 정의한다

### 목적

여러 기술·도구·접근법의 차이를 이해하고 **상황에 맞는 선택**을 할 수 있게 한다.

### 권장 흐름

```text
왜 비교하는가
   ↓
비교 대상의 공통 좌표
   ↓
비교축 정의
   ↓
큰 차이
   ↓
축별 비교
   ↓
Trade-off
   ↓
선택 기준
```

### 원칙

- 기능 목록을 나열하기 전에 비교축을 먼저 정한다.
- 서로 다른 분류축의 대상을 억지로 같은 발전 단계나 우열 관계로 만들지 않는다.
- 우열보다 어떤 조건에서 차이가 의미 있는지 설명한다.
- 표는 비교축이 명확할 때 사용하고, 표만으로 결론을 대신하지 않는다.

## 7. Tool — 도구의 위치와 사용 가치를 설명한다

### 목적

도구가 무엇이고 생태계에서 어디에 위치하며 **언제 왜 쓰는지** 이해하게 한다.

### 권장 흐름

```text
무엇인가
   ↓
생태계에서의 위치
   ↓
해결하는 문제
   ↓
핵심 기능·특징
   ↓
최소 사용 예
   ↓
언제 유용한가 / 대안과 차이
```

### 원칙

- 설치법·옵션·명령어 전체를 복제하는 Reference 문서가 되지 않는다.
- 도구의 일반 사용법 원본이 devkit에 있으면 블로그에는 비교·선택·적용 경험과 필요한 최소 예시만 둔다.
- Concept 설명이 길어지면 별도 Concept 문서로 분리한다.

## 8. How-to — 목표 달성이 우선이다

### 목적

독자가 특정 작업을 **빠르고 재현 가능하게 수행**하게 한다.

### 권장 흐름

```text
목표
   ↓
전제조건
   ↓
절차
   ↓
결과 확인
   ↓
주의점 / 되돌리기
```

### 원칙

- 거시 배경 설명보다 실행 순서를 우선한다.
- 명령만 나열하지 말고 성공 여부를 확인하는 방법을 포함한다.
- 선택지가 많으면 기본 경로를 먼저 제시하고 대안은 뒤로 보낸다.

## 9. Troubleshooting — 증상에서 원인과 해결로 간다

### 목적

같은 문제를 다시 만났을 때 **빠르게 재현·진단·해결**할 수 있게 한다.

### 권장 흐름

```text
증상
   ↓
발생 조건·환경
   ↓
원인
   ↓
확인 방법
   ↓
해결
   ↓
왜 해결되는가
   ↓
재발 방지·주의점
```

### 원칙

- Troubleshooting 여부는 기술 주제가 아니라 **문서의 Primary Purpose**로 판단한다.
- 글의 중심이 `문제 발생 → 증상 확인 → 진단 → 원인 → 해결`이라면, 그 과정에서 재사용 가능한 원리를 설명하더라도 Troubleshooting 문서다.
- 반대로 Error Handling, Permission, Debugger처럼 오류와 관련된 주제라도 정상 동작의 개념·구조·사용법을 설명하는 것이 중심이면 Troubleshooting으로 분류하지 않는다.
- 필요한 경우 첫 문장에서 문제가 발생한 계층만 짧게 짚는다.
- 제품 역사나 상위 개념을 장황하게 설명하지 않는다.
- 시행착오를 모두 기록하기보다 원인 규명에 의미 있었던 확인 과정을 남긴다.
- 해결 명령만 남기지 말고 왜 해결되는지 설명한다.
- Troubleshooting은 기본 학습 Roadmap의 필수 순서에 넣지 않고, 실제 증상을 만났을 때 검색·링크로 진입하는 기록으로 취급한다.

## 10. Record / Decision — 맥락과 결과를 보존한다

### 목적

작업·실험·설계 결정·운영 경험을 나중에 다시 봤을 때 **왜 그렇게 했는지 복원**할 수 있게 한다.

### 권장 흐름

```text
배경·상황
   ↓
무엇을 했거나 결정했는가
   ↓
이유
   ↓
결과
   ↓
남은 문제·후속
```

### 원칙

- 사건의 시간 순서가 중요하면 Chronological Flow를 우선해도 된다.
- 모든 기록을 Concept 글처럼 거시 → 미시로 재구성하지 않는다.
- 결정의 근거와 결과를 남겨 나중에 판단을 재현할 수 있게 한다.

## 11. 짧은 Tip은 독립 유형으로 강제하지 않는다

한두 가지 사실이나 짧은 해결법이 핵심인 글은 억지로 긴 구조를 만들지 않는다.

```text
문제 또는 질문
   ↓
답
   ↓
필요한 최소 설명
```

으로 충분하다.

다만 Tip이 계속 커져 개념 설명·절차·트러블슈팅 중 하나의 성격이 명확해지면 해당 유형으로 승격한다.

## 12. 문서 유형이 섞일 때

한 문서에는 **주 유형 하나**를 정한다.

예를 들어 Tool 글 안에 작은 How-to가 포함될 수 있고, Troubleshooting 글에 원인을 이해하기 위한 짧은 Concept 설명이 들어갈 수 있다. 하지만 보조 유형이 본문의 대부분을 차지하면 별도 문서로 분리한다.

판단 기준은 다음과 같다.

> 이 글을 검색해서 들어온 독자가 가장 먼저 얻으려는 것은 무엇인가?

그 답이 문서의 주 유형이다.

## 13. 상세화하면서 상위 구조도 다시 보정한다

Roadmap이나 상위 분류를 처음 만든 상태로 고정하지 않는다.

```text
상위 구조에서 위치 파악
   ↓
세부 문서 작성·학습
   ↓
새 관계·경계·의존성 발견
   ↓
상위 Roadmap·분류 보정
```

세부 내용을 이해하면서 기존 상위 구조가 부정확하다는 것이 드러나면 **세부 문서만 고치고 끝내지 말고 상위 구조도 다시 확인한다.**

이는 모든 수정에서 반드시 Roadmap을 바꾸라는 뜻이 아니라, 새로 발견한 관계가 상위 구조에 영향을 줄 때 양방향으로 보정하라는 뜻이다.

## 14. 작성 전 체크

새 문서를 작성하거나 기존 문서를 크게 재구성하기 전에 확인한다.

1. 이 글의 주 목적은 이해, 선택, 수행, 해결, 기록 중 무엇인가?
