# 문서 유형별 작성 원칙

이 문서는 블로그와 저장소의 기술 문서를 **목적에 맞는 구조로 작성하기 위한 공통 설계 원칙**을 정의한다.

문체·용어·표기 방법은 [`WRITING_STYLE.md`](WRITING_STYLE.md)를 따르고, 개념을 어떤 단위로 묶고 나눌지는 [`KNOWLEDGE_ORGANIZATION.md`](KNOWLEDGE_ORGANIZATION.md)를 함께 따른다. 특정 하위 영역에 별도 작성 규칙이 있으면 이 문서 위에 추가로 적용한다.

## 1. 최상위 원칙 — 먼저 문서의 목적을 결정한다

모든 글에 하나의 형식을 강제하지 않는다. 문서를 작성하거나 크게 수정하기 전에 먼저 **이 문서가 독자에게 무엇을 제공하려는지** 결정한다.

```text
문서 목적
   │
   ├─ 지식을 이해시킨다
   │    → Roadmap / Concept / Architecture / Comparison
   │
   ├─ 도구를 이해하고 선택하게 한다
   │    → Tool
   │
   ├─ 작업을 수행하게 한다
   │    → How-to
   │
   ├─ 문제를 해결하게 한다
   │    → Troubleshooting
   │
   └─ 경험·결정·결과를 남긴다
        → Record / Decision
```

문서 유형이 불분명하면 본문을 쓰기 전에 목적을 먼저 좁힌다. 한 글이 여러 유형을 과도하게 섞으면 분리하거나 주 유형을 정하고 나머지는 보조 Section으로 제한한다.

## 2. 이해형 문서는 큰 그림에서 필요한 만큼 Zoom-in 한다

**Roadmap, Concept, Architecture, Comparison처럼 이해가 목적인 문서는 거시에서 미시로 내려간다.**

독자가 세부사항을 보기 전에 최소한 다음을 파악할 수 있어야 한다.

1. 지금 다루는 대상이 전체 구조의 어디에 있는가
2. 왜 이 개념이나 계층이 필요한가
3. 인접 개념과 어떤 관계가 있는가
4. 그다음 내부 구조와 세부 동작은 무엇인가

```text
큰 그림
   ↓
현재 위치
   ↓
인접 관계·경계
   ↓
필요한 부분만 Zoom-in
   ↓
핵심 구조·동작
   ↓
세부 사항
```

**Zoom-in은 상위 문서 안에 모든 세부를 계속 펼치는 과정이 아니다.** 현재 목적을 이해하는 데 필요한 깊이까지만 내려가고, 독립적으로 깊게 볼 가치가 있는 세부는 하위 또는 별도 문서로 연결한다.

단, 거시 → 미시는 모든 문서에 강제하는 형식이 아니다. 문제 해결이나 기록이 목적인 문서에서 불필요한 상위 개념 설명을 길게 추가하지 않는다. Troubleshooting에서는 문제가 발생한 계층을 한두 문장으로 좌표만 잡은 뒤 증상과 원인으로 들어갈 수 있고, 짧은 Tip이나 Record에서는 거시 설명을 생략할 수 있다.

## 3. 실제 관계를 설명하고 스토리를 억지로 만들지 않는다

문서의 흐름은 실제 개념 관계를 따라야 한다.

실제 인과가 있다면:

```text
문제
  ↓
해결 개념
  ↓
새 한계
  ↓
확장 개념
```

처럼 설명할 수 있다.

하지만 모든 대상을 발전사나 `왜 → 어떻게 → 그래서`의 한 줄 이야기로 만들 필요는 없다. 관계에 따라 계층, 비교, 경계, 의존, 조합 형태를 선택한다.

```text
계층형 : 상위 → 하위
비교형 : A ↔ B ↔ C
경계형 : 비슷한 개념의 역할·범위 구분
의존형 : 선행 → 다음 개념
조합형 : 여러 개념이 실제 시스템에서 합류
```

> **스토리를 만들기 위해 관계를 왜곡하지 않는다. 관계가 있다면 그 관계가 읽히게 한다.**

서로 다른 분류축의 개념을 하나의 발전 단계처럼 세우지 않는다. 여러 축이 실제 시스템에서 만난다면 각 축을 구분한 뒤 조합 관계를 별도로 보여준다.

## 4. 처리 과정은 입력 → 처리 → 출력으로 먼저 단순화한다

동작 원리를 설명하는 Concept·Architecture 문서에서는 복잡한 내부 구현으로 바로 들어가기 전에 가능한 경우 처리 흐름을 먼저 잡는다.

```text
입력
 ↓
핵심 처리
 ↓
출력 / 상태 변화
```

그다음 필요한 단계만 확대한다.

```text
입력
 ↓
단계 A
 ↓
단계 B
 ↓
상태 변화
 ↓
출력
```

각 단계에서 무엇을 받아 무엇으로 바꾸는지가 보이면 구현 세부를 외우지 않고도 동작을 다시 도출하기 쉽다.

## 5. 비슷한 개념은 차이보다 먼저 비교축을 확인한다

이름이나 결과가 비슷한 개념은 무엇이 다른지만 나열하지 않고 **같은 축에서 비교 가능한 대상인지** 먼저 확인한다.

```text
A와 B는
├─ 같은 문제의 대안인가?
├─ 상위/하위 관계인가?
├─ 서로 다른 분류축인가?
└─ 실제 시스템에서 조합되는가?
```

같은 축의 대안이면 차이와 Trade-off를 비교하고, 축이 다르면 억지로 우열이나 발전 단계로 만들지 않는다.

## 6. 이해에 결정적이었던 설명은 보존한다

기존 문서를 정리할 때 단순히 더 짧고 일반적인 설명으로 바꾸지 않는다.

특정 예제, 질문, 비유, Diagram 또는 설명 순서가 개념을 이해하는 데 결정적이었다면 **그 이해 장치를 우선 보존**한다.

- 비유는 실제 개념과 동일시하지 않고 이해의 발판으로 사용한다.
- 작은 예제가 추상 개념의 경계를 보여준다면 유지한다.
- 실제로 헷갈렸던 질문은 FAQ로 쌓기보다 자연스러운 설명 흐름에 녹인다.
- 문서 리팩터링이 "이해가 됐던 이유"를 지우는 작업이 되지 않게 한다.

## 7. Roadmap — 전체 지형과 학습 순서를 보여준다

### 목적

독자가 영역의 전체 구조를 먼저 보고 **무엇을 어떤 순서로 이해해야 하는지** 판단하게 한다.

### 권장 흐름

```text
영역의 목적·범위
   ↓
전체 지도
   ↓
큰 축과 관계
   ↓
권장 학습 순서
   ↓
각 단계의 핵심 질문
   ↓
개별 문서 연결
   ↓
다른 Roadmap과의 경계
```

### 원칙

- 개별 개념의 상세 설명보다 **위치·관계·순서**를 우선한다.
- 단순 목차가 아니라 왜 이 순서로 보는지 드러나야 한다.
- 영역 전체에서 모든 하위 개념을 펼치지 않는다. 큰 가지와 대표적인 진입점만 남기고 필요한 곳에서 하위 문서로 Zoom-in 한다.
- 하위 문서는 개수나 분량 때문에 기계적으로 만들지 않고, 연관 개념을 한 번 더 함께 볼 때 이해가 좋아지는 경우에 만든다.
- 영역 밖의 주제와 경계를 명시해 Roadmap이 무한히 커지지 않게 한다.
- 세부 설명은 해당 Concept 문서로 연결하고 Roadmap에서 반복하지 않는다.

## 8. Concept — 개념을 이해하고 다시 도출할 수 있게 한다

### 목적

정의 암기보다 **왜 존재하고 어떻게 동작하며 어디에 연결되는지** 이해하게 한다.

### 권장 흐름

```text
전체에서의 위치
   ↓
왜 필요한가
   ↓
핵심 정의
   ↓
전체 처리 흐름·관계
   ↓
구조·구성요소
   ↓
동작 원리
   ↓
예제·Diagram
   ↓
인접 개념과 경계
```

### 원칙

- 세부 API나 옵션부터 시작하지 않는다.
- 처음에는 큰 그림을 잡고 필요한 만큼만 내부로 내려간다.
- 실제 인과가 있으면 `왜 필요한가 → 어떻게 해결하는가 → 어떤 결과·Trade-off가 생기는가`가 읽히게 한다.
- 인과가 없으면 비교·계층·경계·조합 관계를 사용한다.
- 처리 메커니즘은 가능하면 입력과 출력이 보이게 설명한다.
- Text/ASCII Diagram이 관계 이해에 도움이 되면 적극 사용한다.
- 관련 있다는 이유만으로 주변 지식을 끝없이 확장하지 않는다.

## 9. Architecture / Analysis — 구조와 상호작용을 설명한다

### 목적

시스템·프레임워크·애플리케이션의 **구성요소와 책임, 상호작용, 설계 선택**을 이해하게 한다.

### 권장 흐름

```text
대상과 문제
   ↓
전체 Architecture
   ↓
구성요소와 책임
   ↓
Data / Control Flow
   ↓
핵심 상호작용
   ↓
설계 선택과 Trade-off
   ↓
경계·한계·결론
```

### 원칙

- 구성요소 목록보다 관계를 먼저 보여준다.
- 복잡한 내부 호출은 먼저 `입력 → 처리 → 출력/상태 변화`로 단순화한 뒤 필요한 부분만 확대한다.
- 서로 다른 분류축의 구성요소를 한 계층처럼 섞지 않는다.
- Diagram은 박스 수보다 **흐름과 책임**이 읽히는지가 중요하다.
- 구현 세부는 Architecture 판단에 필요한 수준까지만 포함한다.

## 10. Comparison — 비교축을 먼저 정의한다

### 목적

여러 기술·도구·접근법의 차이를 이해하고 **상황에 맞는 선택**을 할 수 있게 한다.

### 권장 흐름

```text
왜 비교하는가
   ↓
비교 대상의 공통 좌표
   ↓
비교축 정의
   ↓
큰 차이
   ↓
축별 비교
   ↓
Trade-off
   ↓
선택 기준
```

### 원칙

- 기능 목록을 나열하기 전에 비교축을 먼저 정한다.
- 서로 다른 분류축의 대상을 억지로 같은 발전 단계나 우열 관계로 만들지 않는다.
- 우열보다 어떤 조건에서 차이가 의미 있는지 설명한다.
- 표는 비교축이 명확할 때 사용하고, 표만으로 결론을 대신하지 않는다.

## 11. Tool — 도구의 위치와 사용 가치를 설명한다

### 목적

도구가 무엇이고 생태계에서 어디에 위치하며 **언제 왜 쓰는지** 이해하게 한다.

### 권장 흐름

```text
무엇인가
   ↓
생태계에서의 위치
   ↓
해결하는 문제
   ↓
핵심 기능·특징
   ↓
최소 사용 예
   ↓
언제 유용한가 / 대안과 차이
```

### 원칙

- 설치법·옵션·명령어 전체를 복제하는 Reference 문서가 되지 않는다.
- 도구의 일반 사용법 원본이 devkit에 있으면 블로그에는 비교·선택·적용 경험과 필요한 최소 예시만 둔다.
- Concept 설명이 길어지면 별도 Concept 문서로 분리한다.

## 12. How-to — 목표 달성이 우선이다

### 목적

독자가 특정 작업을 **빠르고 재현 가능하게 수행**하게 한다.

### 권장 흐름

```text
목표
   ↓
전제조건
   ↓
절차
   ↓
결과 확인
   ↓
주의점 / 되돌리기
```

### 원칙

- 거시 배경 설명보다 실행 순서를 우선한다.
- 명령만 나열하지 말고 성공 여부를 확인하는 방법을 포함한다.
- 선택지가 많으면 기본 경로를 먼저 제시하고 대안은 뒤로 보낸다.

## 13. Troubleshooting — 증상에서 원인과 해결로 간다

### 목적

같은 문제를 다시 만났을 때 **빠르게 재현·진단·해결**할 수 있게 한다.

### 권장 흐름

```text
증상
   ↓
발생 조건·환경
   ↓
원인
   ↓
확인 방법
   ↓
해결
   ↓
왜 해결되는가
   ↓
재발 방지·주의점
```

### 원칙

- 필요한 경우 첫 문장에서 문제가 발생한 계층만 짧게 짚는다.
- 제품 역사나 상위 개념을 장황하게 설명하지 않는다.
- 시행착오를 모두 기록하기보다 원인 규명에 의미 있었던 확인 과정을 남긴다.
- 해결 명령만 남기지 말고 왜 해결되는지 설명한다.

## 14. Record / Decision — 맥락과 결과를 보존한다

### 목적

작업·실험·설계 결정·운영 경험을 나중에 다시 봤을 때 **왜 그렇게 했는지 복원**할 수 있게 한다.

### 권장 흐름

```text
배경·상황
   ↓
무엇을 했거나 결정했는가
   ↓
이유
   ↓
결과
   ↓
남은 문제·후속
```

### 원칙

- 사건의 시간 순서가 중요하면 Chronological Flow를 우선해도 된다.
- 모든 기록을 Concept 글처럼 거시 → 미시로 재구성하지 않는다.
- 결정의 근거와 결과를 남겨 나중에 판단을 재현할 수 있게 한다.

## 15. 짧은 Tip은 독립 유형으로 강제하지 않는다

한두 가지 사실이나 짧은 해결법이 핵심인 글은 억지로 긴 구조를 만들지 않는다.

```text
문제 또는 질문
   ↓
답
   ↓
필요한 최소 설명
```

으로 충분하다.

다만 Tip이 계속 커져 개념 설명·절차·트러블슈팅 중 하나의 성격이 명확해지면 해당 유형으로 승격한다.

## 16. 문서 유형이 섞일 때

한 문서에는 **주 유형 하나**를 정한다.

예를 들어 Tool 글 안에 작은 How-to가 포함될 수 있고, Troubleshooting 글에 원인을 이해하기 위한 짧은 Concept 설명이 들어갈 수 있다. 하지만 보조 유형이 본문의 대부분을 차지하면 별도 문서로 분리한다.

판단 기준은 다음과 같다.

> 이 글을 검색해서 들어온 독자가 가장 먼저 얻으려는 것은 무엇인가?

그 답이 문서의 주 유형이다.

## 17. 상세화하면서 상위 구조도 다시 보정한다

Roadmap이나 상위 분류를 처음 만든 상태로 고정하지 않는다.

```text
상위 구조에서 위치 파악
   ↓
세부 문서 작성·학습
   ↓
새 관계·경계·의존성 발견
   ↓
상위 Roadmap·분류 보정
```

세부 내용을 이해하면서 기존 상위 구조가 부정확하다는 것이 드러나면 **세부 문서만 고치고 끝내지 말고 상위 구조도 다시 확인한다.**

이는 모든 수정에서 반드시 Roadmap을 바꾸라는 뜻이 아니라, 새로 발견한 관계가 상위 구조에 영향을 줄 때 양방향으로 보정하라는 뜻이다.

## 18. 작성 전 체크

새 문서를 작성하거나 기존 문서를 크게 재구성하기 전에 확인한다.

1. 이 글의 주 목적은 이해, 선택, 수행, 해결, 기록 중 무엇인가?
2. 주 문서 유형은 무엇인가?
3. 이해형 문서라면 전체 좌표가 먼저 제시되는가?
4. 필요한 만큼만 Zoom-in하고 상위 문서에 모든 세부를 펼치고 있지 않은가?
5. 실제 관계가 아닌 스토리를 억지로 만들고 있지 않은가?
6. 비교 대상의 분류축이 같은지 확인했는가?
7. 처리 메커니즘의 입력·처리·출력이 보이는가?
