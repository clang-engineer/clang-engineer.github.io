# 저장소 공통 문체·표기 원칙

이 문서는 이 저장소의 한국어 기술 문서를 작성하거나 수정할 때 공통으로 적용하는 문체·용어·표기 기준이다.

특정 학습자료나 게시물 형식에 종속되지 않는다. `_posts`, `_archive`, 학습 문서, 기술 정리, 설계·운영 메모 등 사람이 읽는 한국어 기술 문서 전반에 적용한다. 하위 디렉터리에 별도 작성 규칙이 있으면 이 공통 원칙 위에 해당 규칙을 추가로 적용한다.

핵심 목표는 **억지로 한글화하는 것**이 아니라, 국내 IT 실무자가 자연스럽게 읽으면서도 전문용어의 정확성과 개념의 경계를 유지하는 것이다.

---

## 1. 자연스럽게 통용되는 기술용어는 억지로 번역하지 않는다

프로세스, 트랜잭션, 캐시, 인덱스, API, 테스트처럼 국내 IT 문서에서 널리 쓰이는 표현은 그대로 사용한다.

어색한 직역 때문에 익숙한 개념이 오히려 낯설어지지 않도록 한다.

```text
지양: 소프트웨어 시험
권장: 소프트웨어 테스트

지양: 단위 시험 / 통합 시험 / 인수 시험
권장: 단위 테스트 / 통합 테스트 / 인수 테스트

지양: 시험 케이스
권장: 테스트 케이스
```

일반적인 자격시험이나 평가 자체를 뜻하는 `시험`은 그대로 사용한다.

> 번역 가능 여부보다 국내에서 실제로 어떤 표현이 자연스럽게 통용되는지를 우선한다.

---

## 2. 번역투를 피한다

영어 문장 구조를 그대로 옮겨 한국어 조사만 붙인 표현을 피한다.

```text
지양:
Traffic을 Classification하고 Marking한 후 Scheduling한다.

권장:
트래픽을 분류(Classification)하고 우선순위를 표시(Marking)한 뒤,
큐와 스케줄링 정책에 따라 전송 순서를 결정한다.
```

```text
지양:
Parameter를 efficient하게 update한다.

권장:
매개변수(Parameter)를 효율적으로 갱신한다.
```

다만 `Tool`, `Context`, `Embedding`처럼 해당 분야에서 영어 표현 자체가 더 자연스럽고 의미 경계가 분명한 경우에는 억지로 한국어로 바꾸지 않는다.

---

## 3. 약어는 처음 나올 때만 풀어서 설명한다

핵심 약어는 처음 등장할 때 다음 순서로 적는다.

```text
약어(원어, 쉬운 뜻 또는 역할)
```

예:

```text
RAG(Retrieval-Augmented Generation, 검색한 외부 지식을 LLM에 함께 제공하는 방식)

HNSW(Hierarchical Navigable Small World, 그래프 기반 근사 최근접 검색 인덱스)

VDI(Virtual Desktop Infrastructure, 사용자 Desktop 실행환경을 중앙에서 제공하는 구조)
```

원어가 개념 이해에 별 도움이 되지 않거나 이미 매우 익숙한 약어는 과도하게 풀어 쓰지 않는다. 첫 등장 이후에는 보통 약어만 사용한다.

---

## 4. 공식 용어와 쉬운 설명은 처음 한 번만 병기한다

정확한 공식 용어가 필요한 경우 버리지 않고 처음 등장할 때 쉬운 설명을 함께 붙인다.

```text
Cache Coherence(캐시 일관성)

Schema Linking(질문의 개념을 실제 Table·Column·Value와 연결하는 작업)

Policing(초과 트래픽을 즉시 제한하는 방식)
```

이후 문장마다 괄호 설명을 반복하지 않는다.

---

## 5. 영어 명사를 여러 개 이어 붙이지 않는다

영어 기술용어를 연속해서 나열하면 관계가 잘 보이지 않을 수 있다.

```text
지양:
Metadata Retrieval 이후 Schema Linking Result를 Context에 Injection한다.

권장:
관련 Metadata를 먼저 검색한 뒤 Schema Linking 결과를 LLM Context에 넣는다.
```

누가 무엇을 하는지 불분명하면 주어와 동사를 보완한다.

---

## 6. 쉬운 표현을 위해 정확한 용어를 없애지 않는다

쉽게 설명하는 것과 용어를 부정확하게 만드는 것은 다르다.

```text
지양:
Embedding = Vector

권장:
Embedding은 Text를 Vector 표현으로 만드는 개념이다.
실무에서는 그 결과 Vector 자체를 Embedding이라고 부르기도 한다.
```

```text
지양:
MCP = Agent용 API

권장:
MCP는 Agent가 외부 Tool과 Resource를 발견하고 호출하기 위한 공통 Protocol이다.
기존 API를 MCP Server 내부에서 호출할 수 있다.
```

**쉬운 설명 → 정확한 기술적 경계** 순으로 연결한다.

---

## 7. 같은 개념의 한글·영문 표현을 문서 안에서 뒤섞지 않는다

처음 표기를 정한 뒤 문서 전체에서 일관되게 사용한다.

```text
정적 테스트
동적 테스트
명세 기반 테스트
구조 기반 테스트
단위 테스트
통합 테스트
시스템 테스트
인수 테스트
```

한 문서 안에서 `정적 시험`, `Static Testing`, `정적 테스트`를 특별한 이유 없이 번갈아 쓰지 않는다. 영문이 필요한 경우 처음 한 번만 병기한다.

---

## 8. 제품·표준·고유명사는 공식 명칭을 존중한다

다음은 임의로 번역하지 않는다.

- 제품명
- Protocol명
- 표준명
- Framework명
- API명
- 명령어·Code Symbol

예:

```text
PostgreSQL
pgvector
Kubernetes
MCP
MESI
HNSW
```

공식 명칭을 유지하고 필요하면 뒤에 쉬운 설명을 붙인다.

---

## 9. 문장은 짧게 만들기보다 관계가 분명하게 만든다

무조건 짧은 문장이 좋은 것은 아니다.

```text
지양:
DiffServ는 Class 기반이다. 확장성이 좋다.

권장:
DiffServ는 개별 Flow 상태를 Router마다 유지하지 않고 Traffic을 Class로 묶어 처리하므로,
Flow 수가 많아져도 Core Router의 상태 관리 부담이 상대적으로 작다.
```

문장의 길이보다 원인과 결과, 조건과 결과, 비교 대상의 관계가 분명한지를 우선한다.

---

## 10. 이미 자연스럽게 쓰는 용어를 불필요하게 바꾸지 않는다

기존 문서나 작업 맥락에서 `테스트`, `캐시`, `에이전트`, `벡터 DB`처럼 자연스럽게 사용해 온 용어가 있고 기술적으로 문제가 없다면 굳이 다른 번역어로 바꾸지 않는다.

문서 정리 과정에서 익숙한 표현을 낯선 교과서식 표현으로 바꾸어 기존 문맥과 이해 흐름을 훼손하지 않는다.

---

## 11. 번역이 여러 개 가능한 용어는 억지로 하나의 한국어로 고정하지 않는다

예를 들어 Verification과 Validation은 문헌이나 문맥에 따라 `검증`, `확인`, `유효성 확인` 등 번역이 달라질 수 있다.

이런 경우 처음에는 영문 용어를 함께 제시하고 의미 차이를 설명한 뒤, 해당 문서에서 사용할 표현을 정한다.

```text
Verification
= 만들어야 할 것을 명세대로 올바르게 만들고 있는가

Validation
= 실제 사용자가 필요로 하는 올바른 제품을 만들었는가
```

번역어 자체보다 개념의 경계를 우선한다.

---

## 12. Diagram 안에서도 같은 원칙을 적용한다

Text/ASCII Diagram이라고 해서 영어 명사를 과도하게 나열하지 않는다.

```text
지양:
Input → Classification → Marking → Policing → Queueing → Scheduling → Output

권장:
트래픽 입력
  ↓
분류(Classification)
  ↓
우선순위 표시(Marking)
  ↓
속도 통제(Policing / Shaping)
  ↓
Queue와 Scheduling
  ↓
전송
```

Diagram은 전문용어를 없애는 곳이 아니라 전문용어 사이의 관계를 쉽게 보여주는 곳이다.

---

## 13. 문서의 목적과 독자를 우선한다

공통 문체를 적용하더라도 모든 문서를 같은 형식과 밀도로 만들지 않는다.

- 학습 문서는 이해와 개념 연결을 우선한다.
- 게시글은 독자의 읽기 흐름과 설명 완결성을 우선한다.
- 설계·운영 문서는 판단 근거, 조건, 절차와 결과를 명확히 한다.
- 짧은 메모는 필요한 정보만 남기되 용어와 사실 관계의 정확성은 유지한다.

공통 규칙은 문서의 역할을 덮어쓰는 Template이 아니라, 문서마다 다른 목적 위에 적용되는 기본 문체 기준이다.

---

## 14. 빠르게 변하는 정보는 현행성을 확인한다

제품·모델·가격·표준·법령·CLI 옵션처럼 시간이 지나면 달라질 수 있는 정보는 문서를 수정할 때 공식 자료에서 현재 상태를 확인한다.

`updated` 날짜만 바꾸거나 과거 정보를 그대로 두지 않는다.

특히 다음 정보는 시점 의존성이 높다.

- AI Model 이름·Model ID·가격·Context Window·지원 기능
- Cloud·SaaS 요금과 Plan별 제한
- CLI 옵션·명령어·기본 동작
- 표준·Protocol의 안정 버전과 Deprecated 항목
- Framework·Library의 현재 API
- 법령·제도·인증 기준

구체적인 숫자나 버전을 적어야 한다면 **기준 시점**을 함께 적는 것을 권장한다.

```text
권장:
아래 가격은 2026-08 기준이다.
실제 도입 전에는 공식 가격표를 다시 확인한다.
```

변경 가능성이 큰 숫자가 문서의 핵심이 아니라면 세부 값을 고정하기보다 공식 자료에서 확인해야 할 항목과 판단 기준을 설명한다.

```text
지양:
캐시 읽기 비용은 항상 입력 가격의 0.1배다.

권장:
캐시 적용 여부와 현재 가격은 Usage 값과 공식 가격표에서 확인한다.
```

공식 자료를 확인하지 못한 추정이나 오래된 값은 현재 사실처럼 단정하지 않는다.

## 16. 한 문장 원칙

> **전문용어는 정확하게 유지하되, 억지 번역과 번역투를 피하고 국내 IT 실무자가 자연스럽게 읽는 한국어로 설명한다.**
