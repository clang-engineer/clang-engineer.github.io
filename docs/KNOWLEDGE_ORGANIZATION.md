# 저장소 공통 지식 구성 원칙

이 문서는 `_posts`, `_archive`, 학습 문서, 기술 정리 등 저장소에서 **개념과 지식을 어떤 단위로 묶고 나눌지** 정하는 공통 원칙이다.

문체·용어·표기는 [`WRITING_STYLE.md`](WRITING_STYLE.md)를 따르고, 특정 자료 형식에 별도 작성 규칙이 있으면 이 원칙 위에 해당 규칙을 추가로 적용한다.

핵심 기준은 **주제명·목차·분량이 아니라, 함께 보았을 때 이해가 더 좋아지는가**이다.

## 1. 함께 이해하면 좋은 개념을 하나의 단위로 묶는다

문서나 Section의 경계는 개별 Keyword 수에 맞추지 않는다.

여러 개념을 함께 보았을 때 각각의 위치·원리·차이·경계가 더 잘 이해된다면 하나의 설명 단위로 묶을 수 있다.

```text
함께 보면 이해가 좋아지는 관계
├─ 상위 ↔ 하위
├─ 문제 → 해결 → 한계 → 확장
├─ 개념 A ↔ 개념 B 비교·대안
├─ 개념 사이의 경계
├─ 선행 → 의존
└─ 실제 시스템에서의 조합·합류
```

개념 수가 적거나 관계가 단순하더라도 함께 보는 편이 이해에 도움이 되면 묶을 수 있다.

반대로 같은 분야나 같은 교재 Chapter에 있다는 이유만으로 서로의 이해에 도움이 되지 않는 개념을 한 문서에 억지로 묶지 않는다.

## 2. 스토리는 관계 표현 방식 중 하나일 뿐이다

실제 문제·원인·해결·한계·확장 관계가 있다면 그 흐름을 살려 설명한다.

```text
문제
  ↓
해결 개념
  ↓
새 한계
  ↓
확장 개념
```

하지만 모든 개념을 하나의 이야기나 발전 순서로 만들 필요는 없다.

관계에 따라 적절한 형태를 선택한다.

```text
스토리형 : 문제 → 해결 → 한계 → 확장
비교형   : A ↔ B ↔ C
계층형   : 상위 → 하위
경계형   : 서로 비슷해 보이는 개념의 역할·범위 구분
조합형   : 여러 개념이 실제 시스템에서 합류
```

> **스토리를 만들기 위해 관계를 왜곡하지 않는다. 관계가 있다면 그 관계가 읽히게 한다.**

## 3. 복잡성이나 분량만으로 분리하지 않는다

다음 이유만으로 문서를 나누지 않는다.

- 파일이 길어졌다.
- Keyword가 여러 개다.
- 교재에서 별도 Topic으로 나뉘어 있다.
- 개념마다 파일 하나를 대응시키고 싶다.

반대로 관계가 복잡하지 않더라도 함께 설명할 때 이해가 좋아진다면 하나의 문서나 Section으로 유지할 수 있다.

분리 여부는 다음 질문으로 판단한다.

> **이 내용을 따로 보았을 때보다 함께 보았을 때 개념을 더 정확하고 쉽게 이해할 수 있는가?**

## 4. 큰 그림과 상세 설명은 필요에 따라 Zoom한다

넓은 영역을 한 문서에 모두 펼치거나 모든 Topic마다 하위 문서를 만들지 않는다.

```text
큰 그림
  ↓
함께 탐색할 가치가 있는 연관 개념 묶음
  ↓
필요한 부분만 Zoom-in
  ↓
상세 원리·동작·예제
```

중간 단계는 고정된 계층이 아니다. 연관 개념을 한 번 더 함께 보는 것이 이해에 도움이 될 때만 만든다.

따라서 어떤 영역은 `큰 그림 → 상세 설명`으로 바로 내려갈 수 있고, 다른 영역은 중간에 하나 이상의 관계 지도가 필요할 수 있다.

### 세부 개념보다 상위 질문과 분류축을 먼저 세운다

한 문서 안에 여러 세부 개념이 등장한다면 용어부터 차례로 나열하지 않는다. 먼저 그 개념들을 같은 좌표 위에 놓을 수 있는 **상위 질문·분류축·관계**를 제시한다.

```text
상위 질문 / 분류축
        ↓
세부 개념 A · B · C의 위치 확인
        ↓
각 개념의 원리와 차이로 Zoom-in
```

예를 들어 `AOT`, `JIT`, `Interpreter`, `VM`, `Runtime`을 설명한다면 각 용어를 바로 나열하기보다 먼저 다음처럼 질문을 세울 수 있다.

```text
언제 실행 가능한 형태로 바꾸는가?
무엇으로 바꾸는가?
누가 실행하는가?
Runtime은 어디에 있고 무엇을 맡는가?
```

이후 각 세부 개념이 어느 질문의 답인지 보이게 설명한다.

- 상위 질문은 억지 분류를 만들기 위한 목차가 아니라 **세부 개념의 위치와 관계를 복원하기 위한 좌표**여야 한다.
- 문서를 읽다가 세부 내용으로 내려가더라도 **지금 어느 상위 질문을 설명하고 있는지 다시 찾을 수 있어야 한다.**
- 실제 인과관계가 없는데 순서를 만들거나, 서로 다른 축을 하나의 발전 단계처럼 표현하지 않는다.
- 세부 개념이 추가될수록 상위 질문이 더 정확해져야 하며, 필요하면 상세 학습 결과를 반영해 상위 구조를 다시 보정한다.

### 거시 구조와 세부학습의 깊이는 선택적으로 설계한다

특히 기술사 Knowledge처럼 범위가 넓은 학습 영역에서는 하나의 상위 지도에 모든 내용을 담지 않는다.

```text
상위 파트 지도
  ↓
한 시야에서 함께 봐야 이해되는 축별 Roadmap
  ↓
필요한 핵심 개념 묶음
  ↓
이해 깊이가 더 필요한 지점만 세부학습
```

- 어떤 주제는 거시적 위치와 관계만으로 충분할 수 있다.
- 어떤 주제는 원리·동작·경계를 이해하기 위해 세부학습까지 내려가야 한다.
- 모든 주제를 같은 깊이로 상세화하지 않는다.
- 한 파트 안에서도 서로 다른 거시 관점이 있으면 여러 Roadmap으로 나눌 수 있다.
- Roadmap을 나누는 기준은 분량이 아니라 **한 장에서 함께 보았을 때 하나의 큰 그림이 그려지는가**이다.

> **먼저 구조를 이해하고, 필요한 곳에서만 깊이를 추가한다.**

## 5. 문서 형식보다 이해 단위를 우선한다

같은 원칙을 자료의 목적에 맞게 적용한다.

- 게시글: 독자가 하나의 문제나 개념 관계를 끊기지 않고 이해할 수 있는 범위를 우선한다.
- 학습 문서: 함께 공부할 때 기억과 이해가 좋아지는 개념 흐름을 우선한다.
- 개념지도: 연관 개념의 위치·관계·이동 경로를 한눈에 탐색할 수 있는 범위를 우선한다.
- 설계·운영 문서: 하나의 판단·문제·변경·운영 맥락을 이해하는 데 필요한 정보를 함께 둔다.

형식이 다르더라도 **문서 구조가 개념 관계를 가리지 않도록 한다.**

## 6. 지식 영역과 실전 기록 영역의 역할을 구분한다

저장소에는 성격이 다른 두 종류의 지식이 공존할 수 있다.

```text
Knowledge 영역
"무엇인가? 왜 그런가? 무엇과 연결되는가?"
        ↓
체계적인 개념 지도와 상세 지식

Practice / Blog 영역
"어떻게 했나? 왜 실패했나? 무엇을 선택했나?"
        ↓
How-to / Troubleshooting / Tool / Record / 실무 분석
```

기초·핵심 Concept을 여러 개의 작은 게시글로 반복해서 관리하기보다, **체계적인 Knowledge 영역에서 큰 그림과 세부 지식을 함께 탐색할 수 있게 하는 방향을 우선한다.**

- Knowledge 영역은 개별 Keyword마다 문서를 하나씩 만드는 사전식 파편화를 목표로 하지 않는다. 개념지도에서 위치를 찾고, 함께 이해할 가치가 있는 지식 단위로 Zoom-in할 수 있어야 한다.
- Practice / Blog 영역은 Knowledge 영역을 다시 요약해서 중복 보관하는 곳이 아니다. 실제 설정, 문제 해결, 도구 선택, 운영 경험, 비교·분석처럼 독립적인 사용 맥락이 있는 내용을 우선한다.
- 같은 Topic이 양쪽에 등장할 수 있다. 중복 여부는 Keyword가 아니라 **문서 목적과 설명 역할이 같은지**로 판단한다.
- Knowledge 영역의 Concept과 실질적으로 같은 설명을 하는 Blog 문서는 별도 가치가 없다면 통합·삭제를 검토한다.
- Blog의 How-to나 Troubleshooting에서 개념 설명이 필요하면 필요한 만큼만 설명하고, 상세 Concept은 Knowledge 영역을 참조할 수 있다.

현재 `_archive/정보관리기술사/`는 시험 학습 자료인 동시에 이러한 **정보공학 Knowledge Base로 발전시키는 중심 작업 영역**이다. 장기적으로 공개 위치나 이름이 바뀌더라도, 개념 지식은 체계적인 Knowledge 영역에서 탐색하고 실전 기록은 Blog 영역에서 다룬다는 역할 구분은 유지할 수 있다.

## 7. 상세화하면서 상위 구조도 다시 보정한다

처음 만든 분류나 문서 구조를 완성된 정답으로 보지 않는다.

상세 내용을 공부하거나 작성하면서 새로운 관계·경계·의존성을 발견하면 상위 문서와 큰 그림도 다시 보정한다.

```text
큰 그림에서 위치와 관계 파악
  ↓
상세 내용 이해
  ↓
새로운 관계·경계 발견
  ↓
상위 구조 보정
  ↓
새로운 인접 개념 탐색
```

지식 구조는 상세화할수록 고정되는 것이 아니라 **더 정확한 관계를 반영하며 정교해진다.**

## 8. Blog의 물리 폴더와 파일명은 역할을 분리한다

`_posts/`의 물리 폴더는 세부 분류 체계를 모두 표현하는 곳이 아니다. 파일을 찾을 때 실제로 도움이 되는 **독립된 문서 영역의 경계**만 남긴다.

```text
물리 Folder
= 독립된 문서 영역 / Roadmap 단위

Filename
= 개별 글의 실제 주제 식별

categories / tags
= 세부 논리 분류와 검색
```

### Roadmap이 있는 독립 영역은 폴더 단위로 유지할 수 있다

Roadmap이 있고 그 아래에 여러 대표 Zoom-in과 세부 글이 연결되는 영역은 하나의 작은 문서 생태계를 이룬다. 이런 경우 물리 폴더가 곧 탐색 경계가 되므로 별도 폴더를 유지할 수 있다.

예를 들어 `neovim/`, `tmux/`, `terminal/`, `cpp/`, `go/`, `rust/`처럼 Roadmap이 해당 영역의 진입점 역할을 하고 여러 글을 묶는 경우다.

반대로 다음 이유만으로 새 최상위 폴더를 만들지 않는다.

- 글이 1~2개 생겼다.
- front matter의 category 이름과 폴더 이름을 맞추고 싶다.
- 기존 폴더보다 조금 더 세부적인 Topic이다.
- 파일명을 짧게 만들기 위해 문맥을 폴더에 숨기고 싶다.

> **`_posts/` 루트에는 게시글 Markdown을 직접 두지 않는다. 모든 게시글은 의미 있는 1단계 폴더 안에 둔다. 다만 폴더 수를 줄이기 위해 계층을 더 깊게 만들지 않고, `_posts/<영역>/` 한 단계 깊이를 기본으로 유지한다.**

Roadmap이 없는 소수의 글도 루트에 흩어놓지 않는다. 서로 같은 독립 Topic은 아니더라도 **같은 넓은 실전 영역으로 자연스럽게 묶이고 앞으로도 재사용할 수 있는 대분류**가 있다면 그 폴더를 사용한다. 예를 들어 특정 도구의 단독 글은 `tools/`, Roadmap까지 만들 정도는 아닌 범용 소프트웨어·컴퓨터 기술 글은 `engineering/`처럼 넓은 경계에 둘 수 있다.

단, `misc/`처럼 무엇이든 넣는 임시 폴더를 습관적으로 만들지 않는다. 대분류 이름만 보고도 어떤 성격의 글이 들어가는지 설명할 수 있어야 한다.

### Roadmap이 없는 세부 주제는 먼저 기존 큰 영역에 포함할 수 있는지 본다

Roadmap 없이 몇 개의 글만 존재하는 Topic은 별도 폴더를 만들기 전에 다음을 확인한다.

1. 이미 존재하는 독립 영역의 실전 맥락에 포함되는가?
2. 더 넓은 공통 영역에 두고 파일명으로 주제를 식별할 수 있는가?
3. category/tag만으로 충분히 탐색 가능한가?
4. 앞으로도 독립된 Roadmap과 문서 생태계로 성장할 가능성이 실제로 있는가?

단순히 분류명이 다르다는 이유만으로 물리 폴더를 늘리지 않는다.

### 파일명만 보고도 주제가 식별되어야 한다

폴더 문맥을 제거해도 파일의 영역과 핵심 주제가 드러나도록 이름을 정한다.

기본 형태는 다음을 권장한다.

```text
YYYY-MM-DD-<subject>-<specific-topic>.md
```

좋은 예:

```text
2026-07-12-go-error-handling-defer.md
2026-07-12-rust-ownership-borrow-lifetime.md
2026-06-19-neovim-buffer-window-extmark.md
2026-07-11-linux-systemd-service-management.md
2026-09-05-terminal-tty-pty.md
```

피할 예:

```text
2026-07-12-basics.md
2026-07-12-intro.md
2026-07-12-guide.md
2026-07-12-tips.md
```

`basics`, `guide`, `tips` 같은 역할어는 보조적으로 사용할 수 있지만, 그것만으로 실제 주제를 대신하지 않는다.

### 물리 구조를 바꿀 때는 링크와 공개 URL을 별도로 본다

폴더 이동은 Source의 물리 위치를 바꾸는 작업이다. 이동 전에 상대경로 Markdown link가 깨지는지 확인하고, 공개 permalink 호환이 필요한 경우 기존 `redirect_from` 정책을 유지한다.

> **Roadmap은 독립 영역의 폴더 경계를 만들고, 개별 글의 주제는 파일명이 책임지며, 세부 분류는 category/tag가 담당한다. 폴더를 줄이기 위해 불필요한 하위 계층을 만들지 않는다.**

## 9. 지식 원본과 공개·열람 계층을 분리해서 본다

Markdown 파일과 Git 저장소를 **지식의 원본(Source of Truth)** 으로 두고, Jekyll·Quartz·Obsidian 같은 도구는 원본을 작성하거나 보여 주는 계층으로 본다.

```text
Markdown + GitHub
지식 원본 / 이력 관리
        ↓
작성·탐색 도구
Obsidian 등
        ↓
공개·열람 도구
Jekyll / Quartz / GitHub Pages 등
```

도구를 바꾸기 위해 지식 원본의 구조를 불필요하게 종속시키지 않는다.

- 현재 `clang-engineer.github.io`의 Jekyll/Chirpy는 **Blog / Practice 공개 계층**으로 유지한다.
- 모바일에서 기존 Markdown을 읽는 목적만으로 별도 동기화 체계를 추가하지 않는다. 현재 GitHub Pages로 충분하면 그대로 사용한다.
- Knowledge 영역에서 `[[Wiki Link]]`, Backlink, Graph, 연관 문서 탐색처럼 **지식망 자체를 탐색하는 경험**이 중요해질 때 Quartz 같은 Knowledge 전용 공개 계층을 검토한다.
- Quartz는 Jekyll의 플러그인이나 상위 개념이 아니라 별도의 Static Site Generator다. 도입한다면 기존 Blog를 교체하기보다 역할을 먼저 구분한다.
- Blog와 Knowledge 공개 계층을 동시에 운영해야 한다면 하나의 빌드 파이프라인에 억지로 결합하기보다, 필요할 때 별도 Repository와 배포 파이프라인으로 분리하는 방향을 우선한다.
- 따라서 Quartz는 현재 필수 구성요소가 아니라 **Knowledge 탐색 요구가 커졌을 때 선택하는 표현 계층**으로 취급한다.

핵심은 다음과 같다.

> **Markdown과 Git을 정본으로 유지하고, Jekyll·Quartz·Obsidian은 목적에 따라 교체 가능한 작성·탐색·공개 도구로 둔다.**

## 10. 한 문장 원칙

> **개념 지식은 먼저 큰 그림과 관계를 이해할 수 있게 구성하고, 필요한 지점에서만 선택적으로 세부학습으로 내려간다. Knowledge 영역은 이 관계와 깊이를 따라 탐색할 수 있게 관리하고, Blog는 실전 맥락과 경험을 중심으로 유지하되, Markdown과 Git을 정본으로 삼는다.**
